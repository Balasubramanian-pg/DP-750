# Configure Attribute-Based Access Control (ABAC) Tags and Policies

As data platforms scale, traditional Role-Based Access Control (RBAC) becomes increasingly difficult to manage. In an RBAC model, you must manually assign every user to specific roles for every table or view. If you have 100 tables and 50 users, you are managing thousands of individual grants. When a new table is created, you must remember to grant access to the right people. This manual process is error-prone, slow, and does not scale.

**Attribute-Based Access Control (ABAC)** solves this by shifting the focus from *who* the user is to *what* attributes the data and the user possess. Instead of granting access to `Table_A`, you define a policy that says: *"Any user with the attribute `Department=Finance` can access any table tagged with `Domain=Finance`."*

In Unity Catalog, ABAC is implemented through **Governed Tags** and **Access Policies**. This allows you to enforce fine-grained, dynamic permissions that automatically apply to new data assets as they are created, ensuring consistent security at scale.

## 1. The Foundation: Governed Tags

Not all tags are created equal. While standard tags are useful for organization and search, **Governed Tags** are special key-value pairs that are registered at the metastore level. They are the only type of tag that can be referenced in ABAC policies.

### Why Governed Tags?
*   **Standardization:** They ensure that everyone uses the same keys and values (e.g., preventing `sensitivity: high` vs. `Sensitivity: High`).
*   **Security:** Only authorized admins can create or modify governed tag definitions, preventing users from tagging data incorrectly to bypass security.
*   **Policy Integration:** They are the only tags visible to the Unity Catalog policy engine.

### Creating a Governed Tag Definition

Before you can tag data for ABAC, you must define the tag structure in the metastore.

```sql
-- Create a governed tag definition for data sensitivity
CREATE TAG sensitivity 
COMMENT 'Defines the sensitivity level of the data' 
ALLOW VALUES ('public', 'internal', 'confidential', 'restricted');

-- Create a governed tag definition for business domain
CREATE TAG domain 
COMMENT 'Identifies the business domain owning the data' 
ALLOW VALUES ('finance', 'hr', 'sales', 'marketing');
```

> [!IMPORTANT]
> **Privileges Required**
> To create governed tag definitions, you must be a **Metastore Admin** or have the `CREATE TAG` privilege on the metastore.

### Applying Governed Tags to Data Assets

Once defined, you can apply these tags to catalogs, schemas, tables, views, and columns.

```sql
-- Apply tags to a table
ALTER TABLE finance.transactions 
SET TAGS (
    domain = 'finance', 
    sensitivity = 'confidential'
);

-- Apply tags to a specific column containing PII
ALTER TABLE hr.employees 
ALTER COLUMN ssn 
SET TAGS (
    sensitivity = 'restricted', 
    pii_type = 'ssn'
);
```

## 2. Defining Access Policies

An access policy is a SQL-like rule that determines whether a user can perform an action (like `SELECT`) on an object. Policies use the attributes of the **principal** (the user or group) and the **resource** (the table or column) to make decisions.

### Policy Structure

A policy consists of:
1.  **Target:** What objects does this policy apply to? (e.g., all tables with `sensitivity = 'confidential'`).
2.  **Condition:** Under what circumstances is access granted? (e.g., if the user’s `department` attribute matches the table’s `domain` tag).
3.  **Effect:** Allow or Deny.

### Example: Domain-Based Access Policy

Suppose you want to ensure that users can only read tables from their own business domain.

```sql
CREATE ACCESS POLICY domain_isolation_policy 
ON TABLE 
WHERE 
    -- Check if the table has a 'domain' tag
    EXISTS (SELECT 1 FROM system.information_schema.table_tags 
            WHERE tag_name = 'domain') 
AND 
    -- Check if the user's department attribute matches the table's domain tag
    CURRENT_USER().department = GET_TAG('domain')
GRANT SELECT;
```

> [!NOTE]
> **Principal Attributes**
> For this policy to work, users must have attributes assigned to their identities in Azure Databricks. These attributes can be synced from Azure Active Directory (Entra ID) or managed manually. For example, a user might have the attribute `department = 'finance'`.

### Example: Sensitivity-Based Column Masking

ABAC can also drive dynamic masking. You can create a policy that redacts sensitive columns for users who do not have a specific clearance level.

```sql
CREATE ACCESS POLICY mask_pii_policy 
ON COLUMN 
WHERE 
    GET_TAG('sensitivity') IN ('confidential', 'restricted') 
AND 
    CURRENT_USER().clearance_level != 'high'
RETURN REDACTED;
```

In this scenario, if a user queries a table with a column tagged `sensitivity = 'confidential'`, and their `clearance_level` is not `high`, they will see `REDACTED` instead of the actual value.

## 3. Implementing ABAC in Practice

### Step 1: Define Your Taxonomy
Work with your governance council to define the standard tags your organization needs. Common examples include:
*   `sensitivity`: public, internal, confidential, restricted
*   `domain`: finance, hr, sales, engineering
*   `environment`: dev, test, prod
*   `data_owner`: team_name

### Step 2: Create Governed Tag Definitions
Use SQL or Catalog Explorer to create these definitions at the metastore level. Ensure that the allowed values are comprehensive and mutually exclusive where possible.

### Step 3: Tag Your Data Assets
Apply these tags to your existing data. This can be done manually via SQL or automated using scripts that scan table names or metadata. For new tables, consider using **Table Cloning** or **Pipeline Templates** that automatically apply standard tags.

### Step 4: Assign Principal Attributes
Ensure that your users have the necessary attributes in their identity profiles. This is often done through SCIM provisioning from Azure AD (Entra ID), where group memberships or custom attributes are synced to Databricks.

### Step 5: Create and Test Policies
Start with simple policies, such as restricting access to `sensitivity = 'restricted'` tables to a specific security group. Test these policies thoroughly in a development environment before applying them to production.

### Step 6: Monitor and Refine
Use Unity Catalog’s audit logs to monitor policy evaluations. Look for "Denied" events to identify users who legitimately need access but are blocked by overly restrictive policies. Refine your tags and policies iteratively.

## 4. Benefits of ABAC Over RBAC

| Feature | Role-Based Access Control (RBAC) | Attribute-Based Access Control (ABAC) |
| :--- | :--- | :--- |
| **Scalability** | Low. Requires manual grants for each new table/user. | High. Policies automatically apply to new assets based on tags. |
| **Granularity** | Coarse. Typically at the table or schema level. | Fine. Can be applied at the column or row level. |
| **Maintenance** | High. Constant updates needed as teams and data change. | Low. Once policies are set, they self-enforce. |
| **Context Awareness** | None. Access is static. | Dynamic. Access can depend on time, location, or user attributes. |
| **Error Proneness** | High. Easy to forget a grant or revoke. | Low. Logic is centralized in policies. |

## 5. Best Practices for ABAC Implementation

1.  **Start Small:** Do not try to tag your entire data estate overnight. Start with your most sensitive data (e.g., PII or financial records) and build policies around those tags.
2.  **Keep Tags Simple:** Avoid creating dozens of tag keys. Stick to a few high-impact dimensions like `sensitivity` and `domain`.
3.  **Automate Tagging:** Use Delta Live Tables or CI/CD pipelines to automatically apply tags based on folder structures or naming conventions.
4.  **Document Your Policies:** Clearly document what each policy does and who it affects. This helps troubleshoot access issues and ensures transparency.
5.  **Regular Audits:** Periodically review your governed tags and policies to ensure they still align with business requirements and compliance standards.

By implementing ABAC with governed tags and policies, you move from a reactive, manual security model to a proactive, automated governance framework. This ensures that your data remains secure and compliant, even as your platform grows in complexity and scale.
