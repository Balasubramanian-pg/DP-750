# Integration with Microsoft Fabric

## Microsoft Fabric and Azure Databricks Integration

Microsoft Fabric and Azure Databricks are complementary pillars in modern data architecture. While Azure Databricks specializes in high-performance data engineering, large-scale processing, and advanced machine learning, Microsoft Fabric provides a unified SaaS platform with deeply integrated business intelligence, reporting, and real-time analytics. Integrating these platforms allows organizations to leverage the computational power of Databricks alongside the end-to-end usability of Fabric.

### Bidirectional Integration Patterns

The connection between Azure Databricks and Microsoft Fabric is bidirectional, supporting both read and write operations through **OneLake**, the single, logical data lake for the entire Microsoft Fabric tenant.

| Direction | Mechanism | Description |
| :--- | :--- | :--- |
| **Fabric Reads from Databricks** | Unity Catalog Connector | Fabric tools (such as Power BI or Data Engineering experiences) can directly query data registered in Azure Databricks Unity Catalog. This allows users to build reports and perform analysis on governed Databricks data without moving it. |
| **Databricks Writes to Fabric** | OneLake Integration | Azure Databricks can write processed data directly into OneLake using the Delta Lake format. This enables Databricks to serve as a high-performance ingestion and transformation engine for the broader Fabric ecosystem. |

### Strategic Considerations

Each integration pattern serves distinct scenarios and requires careful attention to governance and security:

*   **Governance Continuity:** When Fabric reads from Unity Catalog, access controls defined in Databricks are respected, ensuring that fine-grained permissions travel with the data.
*   **Data Movement vs. Virtualization:** Reading via Unity Catalog avoids data duplication, while writing to OneLake creates a physical copy optimized for Fabric’s native engines. Choosing between them depends on latency requirements and storage costs.
*   **Security Models:** Integrations may use pass-through credentials for user-specific access or service principals for automated, cross-platform workflows.

> [!NOTE]
> By combining these platforms, you can create a "best-of-both-worlds" architecture: using Azure Databricks for heavy-lifting data preparation and ML model training, while leveraging Microsoft Fabric for widespread data distribution, self-service analytics, and executive reporting.

## Access Unity Catalog Data from Fabric

Microsoft Fabric can read tables registered in Unity Catalog without physically replicating the data. This integration leverages **OneLake shortcuts** to provide a virtualized view of your Databricks data within the Fabric ecosystem, enabling seamless cross-platform analytics while maintaining a single source of truth.

### The Mirroring Mechanism

When you create a **Mirrored Azure Databricks Catalog** item in Fabric, the platform performs the following actions:

1.  **Structure Replication:** It mirrors the catalog and schema hierarchy from Unity Catalog into Fabric.
2.  **Shortcut Creation:** It automatically generates OneLake shortcuts for each table. These shortcuts point directly to the underlying Delta tables stored in Azure Data Lake Storage (ADLS).
3.  **Credential Management:** Fabric uses Unity Catalog’s open APIs to obtain short-lived credentials for accessing these storage paths. These credentials refresh every hour and can be revoked at any time through Unity Catalog.

> [!IMPORTANT]
> **No Data Copying:** The mirroring process does not move or copy your data. It creates a logical link, allowing Fabric engines to query the data directly from its original location in ADLS.

### Security and Authorization Model

While this integration offers convenience, it introduces a significant shift in how authorization is enforced. Understanding this distinction is critical for maintaining security compliance.

*   **Configuration Identity:** The authentication mechanism relies on the identity of the user who **configured** the connection. This user must possess the `EXTERNAL USE SCHEMA` privilege in Unity Catalog to allow the issuance of storage credentials.
*   **Downstream Access:** Once the connection is established, **Unity Catalog governance policies do not apply to downstream Fabric users.** Any Fabric user with access to the mirrored catalog can query the data, regardless of their specific permissions in Unity Catalog.
*   **Privilege Requirement:** Only the initial configurator needs the `EXTERNAL USE SCHEMA` privilege. Downstream users do not need this privilege, nor do they need direct access to the Unity Catalog metastore.

> [!WARNING]
> **Security Implication:** Because fine-grained Unity Catalog permissions (such as row-level filters or column masks) are bypassed during Fabric queries, you must evaluate whether this "broad access" model aligns with your organization's security requirements.

### Limitations and Constraints

This integration pattern is powerful but comes with specific technical constraints:

| Constraint | Details |
| :--- | :--- |
| **Supported Objects** | Only **Delta format tables** are supported. |
| **Unsupported Objects** | Views, materialized views, streaming tables, and Delta Sharing catalogs cannot be mirrored. |
| **Governance Features** | Row-level security filters and column masks defined in Unity Catalog are **not enforced** in Fabric. |
| **Network Restrictions** | The integration does not work with workspaces protected by private endpoints or IP access lists. |
| **Lineage Tracking** | Operations performed within Fabric are not tracked in Unity Catalog lineage graphs. |

> [!NOTE]
> To ensure a successful integration, verify that your source tables are in Delta format and that your network configuration allows public API access for credential exchange. For highly sensitive data requiring strict row-level security, consider alternative integration patterns such as exporting governed aggregates to OneLake instead of mirroring raw tables.



## Integration scenarios
These integration patterns enable several practical scenarios for organizations using both platforms. You can build data pipelines where Databricks handles complex transformations and machine learning workloads, then publishes curated datasets to Fabric for business analytics. Data engineers work in Azure Databricks while business analysts access the results through familiar Fabric tools.
With Fabric reading from Unity Catalog, you can make specific datasets available for reporting without duplicating storage. Business users create Power BI reports that query data managed in Unity Catalog, maintaining a single source of truth. This approach applies when you have data governance established in Unity Catalog and want to extend access to Fabric users for specific tables.
For scenarios requiring real-time or near-real-time analytics, Databricks streaming jobs can write processed data to OneLake continuously. Fabric workloads can then consume this data as it arrives. This pattern separates the responsibilities of data engineering and business intelligence while keeping them connected through shared storage.
When you need to combine data from multiple sources, you can use Azure Databricks to join and transform data from various systems, then land the integrated results in OneLake. Fabric serves as the presentation layer, providing self-service analytics on the prepared datasets. This architecture lets data engineers focus on data quality and transformation logic while business users create their own analyses.

## Key considerations
Security and governance are critical factors when you implement these integrations. The Fabric-to-Unity Catalog integration bypasses Unity Catalog's fine-grained access controls for downstream users by default. Carefully consider which tables to expose and ensure your organization accepts this security model. You can partially address this by enabling OneLake security on the Mirrored Azure Databricks Catalog item. This two-step approach first synchronizes a Microsoft Entra group and grants it the necessary Unity Catalog privileges using Automatic Identity Management, then assigns that group a OneLake Data Access Role in the Fabric workspace to control access to the corresponding shortcuts. For scenarios requiring row-level filters or column masks at the individual user level, Power BI DirectQuery remains the recommended path, as it honors Unity Catalog permissions directly.
Performance and cost also matter. Reading Unity Catalog data from Fabric requires a running Fabric capacity for metadata scans and refreshes, which introduces additional costs. When writing from Azure Databricks to OneLake, network transfer costs apply if data crosses region boundaries. Plan your architecture to minimize unnecessary data movement and optimize for your workload patterns.
Storage architecture remains important. Both integration patterns leverage Azure Data Lake Storage as the underlying storage layer. Azure Databricks uses Unity Catalog to manage and govern this storage, while Fabric accesses it through OneLake abstractions. Understanding this shared foundation helps you design efficient solutions that avoid data duplication and maintain consistency.
The choice between integration patterns depends on your specific requirements. Use Fabric reading from Unity Catalog when you want to expose existing Databricks-managed data to Fabric users and can accept the security model. Use Azure Databricks writing to OneLake when you need to publish curated datasets specifically for Fabric consumption and want more control over what data is shared. In many architectures, you might use both patterns for different scenarios within the same organization.
