# Integration with Microsoft Fabric

## Microsoft Fabric and Azure Databricks Integration

Microsoft Fabric and Azure Databricks are complementary pillars in modern data architecture. While Azure Databricks specializes in high-performance data engineering, large-scale processing, and advanced machine learning, Microsoft Fabric provides a unified SaaS platform with deeply integrated business intelligence, reporting, and real-time analytics. Integrating these platforms allows organizations to leverage the computational power of Databricks alongside the end-to-end usability of Fabric.

### Bidirectional Integration Patterns

The connection between Azure Databricks and Microsoft Fabric is bidirectional, supporting both read and write operations through **OneLake**, the single, logical data lake for the entire Microsoft Fabric tenant.

| Direction | Mechanism | Description |
| :--- | :--- | :--- |
| **Fabric Reads from Databricks** | Unity Catalog Connector | Fabric tools (such as Power BI or Data Engineering experiences) can directly query data registered in Azure Databricks Unity Catalog. This allows users to build reports and perform analysis on governed Databricks data without moving it. |
| **Databricks Writes to Fabric** | OneLake Integration | Azure Databricks can write processed data directly into OneLake using the Delta Lake format. This enables Databricks to serve as a high-performance ingestion and transformation engine for the broader Fabric ecosystem. |

### Strategic Considerations

Each integration pattern serves distinct scenarios and requires careful attention to governance and security:

*   **Governance Continuity:** When Fabric reads from Unity Catalog, access controls defined in Databricks are respected, ensuring that fine-grained permissions travel with the data.
*   **Data Movement vs. Virtualization:** Reading via Unity Catalog avoids data duplication, while writing to OneLake creates a physical copy optimized for Fabric’s native engines. Choosing between them depends on latency requirements and storage costs.
*   **Security Models:** Integrations may use pass-through credentials for user-specific access or service principals for automated, cross-platform workflows.

> [!NOTE]
> By combining these platforms, you can create a "best-of-both-worlds" architecture: using Azure Databricks for heavy-lifting data preparation and ML model training, while leveraging Microsoft Fabric for widespread data distribution, self-service analytics, and executive reporting.

## Access Unity Catalog Data from Fabric

Microsoft Fabric can read tables registered in Unity Catalog without physically replicating the data. This integration leverages **OneLake shortcuts** to provide a virtualized view of your Databricks data within the Fabric ecosystem, enabling seamless cross-platform analytics while maintaining a single source of truth.

### The Mirroring Mechanism

When you create a **Mirrored Azure Databricks Catalog** item in Fabric, the platform performs the following actions:

1.  **Structure Replication:** It mirrors the catalog and schema hierarchy from Unity Catalog into Fabric.
2.  **Shortcut Creation:** It automatically generates OneLake shortcuts for each table. These shortcuts point directly to the underlying Delta tables stored in Azure Data Lake Storage (ADLS).
3.  **Credential Management:** Fabric uses Unity Catalog’s open APIs to obtain short-lived credentials for accessing these storage paths. These credentials refresh every hour and can be revoked at any time through Unity Catalog.

> [!IMPORTANT]
> **No Data Copying:** The mirroring process does not move or copy your data. It creates a logical link, allowing Fabric engines to query the data directly from its original location in ADLS.

### Security and Authorization Model

While this integration offers convenience, it introduces a significant shift in how authorization is enforced. Understanding this distinction is critical for maintaining security compliance.

*   **Configuration Identity:** The authentication mechanism relies on the identity of the user who **configured** the connection. This user must possess the `EXTERNAL USE SCHEMA` privilege in Unity Catalog to allow the issuance of storage credentials.
*   **Downstream Access:** Once the connection is established, **Unity Catalog governance policies do not apply to downstream Fabric users.** Any Fabric user with access to the mirrored catalog can query the data, regardless of their specific permissions in Unity Catalog.
*   **Privilege Requirement:** Only the initial configurator needs the `EXTERNAL USE SCHEMA` privilege. Downstream users do not need this privilege, nor do they need direct access to the Unity Catalog metastore.

> [!WARNING]
> **Security Implication:** Because fine-grained Unity Catalog permissions (such as row-level filters or column masks) are bypassed during Fabric queries, you must evaluate whether this "broad access" model aligns with your organization's security requirements.

### Limitations and Constraints

This integration pattern is powerful but comes with specific technical constraints:

| Constraint | Details |
| :--- | :--- |
| **Supported Objects** | Only **Delta format tables** are supported. |
| **Unsupported Objects** | Views, materialized views, streaming tables, and Delta Sharing catalogs cannot be mirrored. |
| **Governance Features** | Row-level security filters and column masks defined in Unity Catalog are **not enforced** in Fabric. |
| **Network Restrictions** | The integration does not work with workspaces protected by private endpoints or IP access lists. |
| **Lineage Tracking** | Operations performed within Fabric are not tracked in Unity Catalog lineage graphs. |

> [!NOTE]
> To ensure a successful integration, verify that your source tables are in Delta format and that your network configuration allows public API access for credential exchange. For highly sensitive data requiring strict row-level security, consider alternative integration patterns such as exporting governed aggregates to OneLake instead of mirroring raw tables.

## Write Data to OneLake from Databricks

Azure Databricks can write processed and transformed data directly into Microsoft Fabric lakehouses hosted on **OneLake**. This integration enables a seamless handoff where Databricks serves as the high-performance engine for data engineering and machine learning, while Fabric handles downstream analytics, reporting, and business intelligence.

### Connection Architecture

To connect Azure Databricks to OneLake, you utilize the **Azure Blob Filesystem (ABFS)** driver with specific OneLake endpoints. The connection path identifies your target Fabric workspace and lakehouse, allowing Databricks to treat OneLake as a standard distributed file system.

The path structure follows this format:

```
abfss://<workspace-name>@onelake.dfs.fabric.microsoft.com/<lakehouse-name>.lakehouse/Files/
```

### Authentication Methods

You can authenticate to OneLake using two primary methods, each with distinct compatibility requirements:

| Method | Description | Compatibility |
| :--- | :--- | :--- |
| **Microsoft Entra Credential Passthrough** | User identities flow through from Databricks to OneLake, enabling user-level access control. | Requires a **Premium** workspace and classic clusters with ADLS credential passthrough enabled. |
| **Service Principal** | Uses a fixed application identity for authentication. Ideal for automated workflows and job execution. | Works with both **classic clusters** and **serverless compute**. |

> [!IMPORTANT]
> **Credential passthrough is not supported with serverless compute.** If you are using serverless workloads, you must use service principal authentication.

### Workflow and Execution

The process of writing data to OneLake is straightforward and leverages standard Spark operations:

1.  **Load & Transform:** Ingest data into Databricks and apply transformations using Spark or Delta Lake.
2.  **Write to OneLake:** Use standard Spark write operations to save the results to the ABFS path pointing to your Fabric lakehouse.
3.  **Immediate Availability:** Once the data lands in OneLake, it is immediately accessible to Power BI, Fabric Data Warehouses, and other Fabric services without any additional data movement or copying.

### Serverless Compute Considerations

This integration fully supports **serverless compute**, allowing you to run workloads without the overhead of provisioning and managing clusters. However, there are specific requirements for serverless environments:

*   **Authentication:** You must use **service principal** authentication.
*   **Configuration:** Ensure your code does not modify unsupported Spark configuration properties.
*   **Permissions:** The service principal must have appropriate workspace role assignments in Fabric to permit write access to the target lakehouse.

> [!NOTE]
> By writing directly to OneLake, you eliminate the need for complex ETL pipelines between platforms. This "write-once, read-many" approach ensures that your analytics teams in Fabric are always working with the most recent, governed data produced by your engineering teams in Databricks.

## Integration Scenarios

The bidirectional connectivity between Azure Databricks and Microsoft Fabric enables several practical architectural patterns. These scenarios allow organizations to leverage the computational power of Databricks for engineering and AI while utilizing Fabric’s unified interface for business intelligence and self-service analytics.

### 1. The Curated Data Pipeline
In this pattern, Azure Databricks serves as the primary engine for complex data transformations, heavy-lifting ETL, and machine learning model training. Once the data is refined, it is published to OneLake or exposed via Unity Catalog for consumption in Fabric.

*   **Workflow:** Data engineers build robust pipelines in Databricks $\rightarrow$ Curated datasets are landed in OneLake or registered in Unity Catalog $\rightarrow$ Business analysts access these trusted datasets through Fabric tools like Power BI.
*   **Benefit:** This separates the responsibilities of data preparation from data consumption, ensuring that business users work with high-quality, pre-validated data.

### 2. Virtualized Reporting with Unity Catalog
By enabling Fabric to read directly from Unity Catalog, organizations can extend the reach of their governed data without creating physical copies.

*   **Workflow:** Fabric creates shortcuts to Delta tables managed in Unity Catalog $\rightarrow$ Power BI reports query this data directly via OneLake shortcuts.
*   **Benefit:** Maintains a **single source of truth**. Storage costs are minimized because data is not duplicated, and governance policies defined in Databricks provide the foundational security layer (though downstream enforcement in Fabric requires careful configuration).

### 3. Real-Time Analytics Streaming
For use cases requiring near-real-time insights, Databricks Structured Streaming jobs can continuously process incoming data and write the results to OneLake.

*   **Workflow:** Databricks ingests and transforms streaming data $\rightarrow$ Processed data is written incrementally to OneLake $\rightarrow$ Fabric workloads consume the updated data as it arrives.
*   **Benefit:** Enables low-latency analytics by decoupling the high-throughput ingestion engine (Databricks) from the presentation layer (Fabric), connected only by shared storage.

### 4. Multi-Source Data Integration
When data resides in disparate systems, Azure Databricks acts as the central integration hub. It joins, cleans, and transforms data from various sources before landing the integrated results in OneLake.

*   **Workflow:** Databricks connects to multiple external systems $\rightarrow$ Complex joins and transformations are applied $\rightarrow$ Unified datasets are stored in OneLake $\rightarrow$ Fabric provides self-service analytics on the prepared data.
*   **Benefit:** Allows data engineers to focus on complex logic and data quality while empowering business users to create their own analyses on a clean, integrated foundation.

> [!NOTE]
> Choosing the right scenario depends on your latency requirements, governance model, and team structure. Whether you need real-time streaming or batch-curated reporting, the integration between Databricks and Fabric ensures that data flows seamlessly from raw ingestion to actionable business insight.
