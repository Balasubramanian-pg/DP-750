## Choosing the Right Integration Method

Selecting the appropriate integration pattern depends on your specific workflow, security requirements, and the division of labor between data engineers and business analysts. Each method serves a distinct purpose in the end-to-end analytics lifecycle.

### Integration Patterns by Use Case

| Method | Primary Use Case | Key Benefits |
| :--- | :--- | :--- |
| **Power BI Desktop** | Interactive exploration and report authoring by business analysts. | Provides a flexible drag-and-drop environment; allows combining multiple data sources; supports both Import and DirectQuery modes. |
| **Publish from Databricks** | Sharing curated, governed datasets initiated by data engineers. | Ensures engineering teams control which tables are exposed; automatically transfers metadata (column descriptions) from Unity Catalog to Power BI. |
| **Power BI Tasks** | Automating semantic model refreshes within data pipelines. | Coordinates BI updates with upstream ETL/ELT jobs; ensures reports only refresh after source data processing is complete. |
| **Power BI Gateway** | Secure connectivity for private network environments. | Enables access to Azure Databricks workspaces protected by private endpoints or IP access lists without exposing them to the public internet. |

### Private Network Connectivity

For organizations with strict network security mandates, **Power BI Gateways** provide a secure bridge between the Power BI service and private Azure Databricks environments.

*   **Configuration:** You install and configure an on-premises or virtual network gateway with your Azure Databricks connection details and authentication credentials.
*   **Routing:** The Power BI service routes queries through the gateway, which then connects to your private Azure Databricks workspace.
*   **Security:** This approach eliminates the need to expose Databricks endpoints publicly, maintaining compliance with enterprise network isolation policies.

> [!NOTE]
> In many mature architectures, these methods are not mutually exclusive. An organization might use **Power BI Desktop** for initial prototyping, **Publish from Databricks** for production-grade curated datasets, and **Power BI Tasks** to ensure those datasets remain current as part of an automated nightly pipeline.
