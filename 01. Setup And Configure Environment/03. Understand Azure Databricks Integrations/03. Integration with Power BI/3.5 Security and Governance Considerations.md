## Security and Governance Considerations

The security architecture of the Azure Databricks and Power BI integration varies significantly depending on the connection method and authentication type chosen. Understanding these differences is essential for maintaining compliance and enforcing least-privilege access.

### Unity Catalog Enforcement by Connection Type

| Connection Method | Authentication Mechanism | Unity Catalog Enforcement | Lineage Tracking |
| :--- | :--- | :--- | :--- |
| **Power BI Desktop (DirectQuery)** | Microsoft Entra ID (Pass-through) | **Full Enforcement:** Row-level filters, column masks, and table permissions are evaluated for each individual user. | Tracked per user; provides detailed audit trails of who accessed what data. |
| **Power BI Desktop (Import)** | Service Principal or User Token | **Limited Enforcement:** Permissions are checked only during the initial data import/refresh. Once imported, Power BI’s internal security applies. | Tracked at the dataset level; does not reflect individual user queries against the source. |
| **Publish to Power BI Service** | OAuth (User or Service Principal) | **Variable:** Depends on configuration. If using user-pass-through, full enforcement applies. If using service principals, access is broad based on the principal's privileges. | Tracked at the semantic model level; downstream report usage is tracked in Power BI, not Databricks. |
| **Power BI Tasks** | Service Principal / Machine-to-Machine | **Service-Level Only:** The task runs under the identity of the service principal. Individual user permissions are not evaluated during the refresh. | Tracked as an automated workflow step; attributes the action to the service principal. |

### Key Security Implications

*   **Identity Passthrough vs. Fixed Credentials:**
    *   **Passthrough (Microsoft Entra ID):** Ensures that governance travels with the data. It is the most secure option for interactive reporting but requires proper network and identity configuration.
    *   **Fixed Credentials (Service Principals/Tokens):** Simplifies automation and connectivity but creates a "super-user" effect if the principal has broad access. Use this only for trusted, automated processes where individual user context is not required.

*   **Data Residency and Movement:**
    *   **DirectQuery:** Data remains in Azure Databricks. No physical copy is created in Power BI, reducing the risk of data sprawl.
    *   **Import Mode:** Creates a physical copy of the data within the Power BI service. Ensure that your organization’s data retention and security policies account for this duplication.

> [!IMPORTANT]
> **Audit and Compliance**
> For highly regulated industries, prefer **DirectQuery with Microsoft Entra ID passthrough**. This ensures that every query is logged in both Power BI and Azure Databricks audit logs, providing a complete, end-to-end trail of data access from the report viewer back to the source table.
