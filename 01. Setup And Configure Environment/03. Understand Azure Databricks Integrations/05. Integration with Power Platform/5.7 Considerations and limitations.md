## Considerations and limitations
While the Azure Databricks Power Platform connector offers robust integration capabilities, successful implementation requires careful attention to architectural constraints, performance characteristics, and governance boundaries.

### Environmental and Regional Constraints

*   **Government Clouds:** The connector is **not supported** in sovereign cloud environments, including US Government (GCC High, DoD) and China Cloud regions. Organizations operating in these jurisdictions must utilize alternative integration patterns, such as custom APIs or direct database connections via gateways.

### Performance and Delegation in Power Apps

Power Apps relies on **delegation** to push computation down to the data source. However, not all Power Fx formulas are delegable to Azure Databricks.

*   **Local Processing Risk:** Non-delegable formulas force Power Apps to retrieve data locally before calculating values. For large datasets, this leads to significant performance degradation and potential accuracy issues due to row limits.
*   **Best Practice:** Perform filtering, sorting, and aggregations using **SQL queries within Azure Databricks** before exposing the data to Power Apps. This ensures that only the necessary, pre-computed result set is transferred to the client application.

### Concurrency and Write Conflicts

When multiple users or flows attempt to modify the same data simultaneously, write conflicts can occur.

*   **Row-Level Concurrency:** Recent versions of Databricks Runtime support row-level concurrency features that help mitigate these conflicts.
*   **Design Implication:** Ensure your Databricks Runtime is up-to-date and design your application logic to handle potential retry scenarios or optimistic locking when performing high-volume write operations from Power Automate or Canvas Apps.

### Choosing Between Virtual Tables and Direct Connections

The choice between these two integration methods involves a trade-off between architectural flexibility and performance/governance fidelity.

| Feature | Virtual Tables (Dataverse) | Direct Connections (Canvas Apps) |
| :--- | :--- | :--- |
| **App Type** | Model-driven Apps | Canvas Apps |
| **Ecosystem Integration** | Deep integration with Dataverse relationships and business logic. | Standalone connection; limited Dataverse interoperability. |
| **Authentication** | Uses fixed credentials; **no OAuth passthrough**. | Supports **OAuth passthrough** for user-level governance. |
| **Performance** | Generally slower due to abstraction layer. | Faster query response times. |
| **Governance** | Relies on service principal permissions. | Enforces Unity Catalog policies per user. |

> [!NOTE]
> If strict user-level auditing and row-level security are required, **Direct Connections** are the superior choice. If you need to build complex model-driven apps with deep Dataverse integration and can accept service-level access, **Virtual Tables** are appropriate.

### Data Policies and Compliance

Power Platform **Data Loss Prevention (DLP)** policies play a critical role in managing connector usage.

*   **Business Data Policies:** You can classify the Azure Databricks connector as "Business" data within your DLP policies. This allows you to control which other connectors (e.g., personal email, social media) are permitted to share data with Databricks, ensuring compliance with internal data handling regulations and preventing accidental data exfiltration.
