## Key Considerations for Integration

Implementing integrations between Azure Databricks and Microsoft Fabric requires careful planning around security, performance, and storage architecture. While these platforms complement each other, their distinct governance models and operational costs must be managed to ensure a secure and efficient data estate.

### Security and Governance Models

The most critical consideration is how access control is enforced across platform boundaries. The default behavior of the **Fabric-to-Unity Catalog** integration differs significantly from direct Databricks access.

*   **Authorization Bypass:** By default, Fabric engines authorize access using the identity of the user who configured the connection, not the individual querying the data. This means Unity Catalog’s fine-grained permissions (such as row-level filters or column masks) are **not enforced** for downstream Fabric users.
*   **Mitigating Risk with OneLake Security:** To restore some level of control, you can enable **OneLake security** on the Mirrored Azure Databricks Catalog item. This involves a two-step process:
    1.  Synchronize a Microsoft Entra group and grant it necessary Unity Catalog privileges via Automatic Identity Management.
    2.  Assign that group a **OneLake Data Access Role** in the Fabric workspace to control access to the specific shortcuts.
*   **The DirectQuery Alternative:** For scenarios where strict, user-level enforcement of row-level security or column masking is mandatory, **Power BI DirectQuery** remains the recommended path. It honors Unity Catalog permissions directly by passing individual user credentials through to the Databricks SQL warehouse.

### Performance and Cost Implications

Integration introduces new cost centers and performance variables that must be accounted for in your architecture.

| Factor | Impact | Mitigation Strategy |
| :--- | :--- | :--- |
| **Fabric Capacity** | Reading from Unity Catalog requires running Fabric capacity for metadata scans and data refreshes. | Monitor capacity utilization and schedule refreshes during off-peak hours. |
| **Network Transfer** | Writing from Databricks to OneLake incurs network transfer costs if data crosses region boundaries. | Co-locate your Databricks workspace and Fabric tenant in the same Azure region whenever possible. |
| **Data Movement** | Unnecessary duplication of data increases storage costs and latency. | Prefer virtualization (shortcuts) over physical copying unless performance dictates otherwise. |

### Storage Architecture Foundation

Both integration patterns rely on **Azure Data Lake Storage (ADLS)** as the underlying physical layer. 
*   **Databricks Perspective:** Uses Unity Catalog to manage and govern this storage, ensuring transactional reliability and metadata consistency.
*   **Fabric Perspective:** Accesses the same storage through **OneLake** abstractions, treating it as part of a unified logical data lake.

Understanding this shared foundation is essential for designing solutions that avoid data silos. It allows you to maintain a single copy of your data while serving multiple consumption patterns.

### Choosing the Right Pattern

The decision between integration patterns should be driven by your specific security and operational requirements:

*   **Use Fabric Reading from Unity Catalog When:** You want to expose existing, Databricks-managed data to Fabric users quickly without moving data, and your security model can accommodate the "configuration identity" authorization approach.
*   **Use Databricks Writing to OneLake When:** You need to publish curated, transformed datasets specifically for Fabric consumption, require strict control over what data is shared, or need to bypass Unity Catalog limitations (such as unsupported view types).

> [!NOTE]
> In many mature architectures, organizations use **both patterns** simultaneously. They might use Databricks-to-OneLake writes for high-performance, curated reporting tables while using Unity Catalog mirroring for ad-hoc exploration of raw or semi-processed data. This hybrid approach maximizes flexibility while maintaining governance standards.
