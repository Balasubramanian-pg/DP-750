## Azure Databricks Architecture for Data Engineering

Deploying Azure Databricks for data engineering requires a clear understanding of its underlying architecture. This foundation dictates how data is organized, how security is enforced, and how compute resources are allocated. By mastering these structural elements, you can design environments that balance performance with strict governance and operational efficiency.

### The Two-Plane Architecture

Azure Databricks operates on a dual-plane model that separates management from execution:

*   **Control Plane:** Managed by Microsoft, this layer handles orchestration, workspace configuration, user identity, and backend services. It ensures that the platform remains secure and up-to-date without requiring direct intervention from your team.
*   **Compute Plane:** This is where your data is actually processed. It resides within your Azure subscription (in Classic deployments) or in a fully managed environment (in Serverless deployments). This separation allows you to scale workloads efficiently while maintaining tight control over data residency and network security.

### Storage Patterns

Storage in Azure Databricks has evolved to support diverse organizational needs, offering three primary patterns:

| Pattern | Description | Best For |
| :--- | :--- | :--- |
| **Default Storage** | Fully managed storage provided automatically in serverless workspaces. | Getting started quickly with zero configuration overhead. |
| **External Storage** | Connects Unity Catalog to existing cloud storage accounts (e.g., Azure Data Lake Storage). | Organizations that need to govern data managed outside of Databricks while maintaining a unified view. |
| **Unity Catalog Managed Storage** | Allows you to define specific storage locations at the catalog or schema level. | Scenarios requiring fine-grained control over data placement and lifecycle management. |

### Hierarchical Resource Organization

Resources are organized through a structured hierarchy that spans from high-level governance down to individual data objects:

1.  **Account Level:** The top-level container for managing users, groups, and workspaces across an organization.
2.  **Metastore:** The central repository for metadata and governance policies, typically shared across multiple workspaces within a region.
3.  **Workspace:** The collaborative environment where teams build notebooks, jobs, and dashboards.
4.  **Data Objects:** The actual assets—tables, views, and volumes—organized within catalogs and schemas.

You will learn how to leverage the account hierarchy for cross-workspace governance, how to choose the right compute plane for your security requirements, and how to select the storage pattern that best aligns with your data engineering workflows.
