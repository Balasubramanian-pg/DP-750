# Understand Azure Databricks architecture

## Architectural Foundations for Data Engineers

For data engineers, a deep understanding of Azure Databricks architecture is not just theoretical—it is the basis for making informed decisions about data organization, compute configuration, and security enforcement. The architecture dictates how workloads execute, where data physically resides, and how the various components of the platform interact to deliver a unified analytics experience.

### Core Structural Principles

Azure Databricks relies on two fundamental architectural concepts to provide flexibility and security:

*   **Hierarchical Resource Organization:** Resources are structured in a logical hierarchy that spans from the high-level account down to individual data objects. This ensures that governance policies and access controls can be applied consistently at every level of the data estate.
*   **Plane Separation:** The platform distinguishes between the **Control Plane** (managed by Microsoft for orchestration and backend services) and the **Compute Plane** (where data processing occurs within your Azure subscription or a managed environment). This separation allows you to maintain strict security boundaries while scaling compute resources independently.

> [!NOTE]
> By mastering these structural elements, you can design data engineering workflows that are both performant and compliant with your organization's operational requirements.

## Azure Databricks Account Hierarchy

Azure Databricks organizes resources through a structured hierarchy that begins at the account level. This model separates organizational governance from project-level execution, allowing you to manage identity, billing, and policies centrally while providing teams with isolated environments for their work.

### The Account Level
The account is the top-level construct for managing Azure Databricks across your organization. At this level, you handle:

-   **Identity and Access Management:** Centralized user and group provisioning.
-   **Workspace Lifecycle:** Creating, configuring, and managing multiple workspaces.
-   **Metastore Attachment:** Linking Unity Catalog metastores to workspaces for unified governance.
-   **Billing and Policies:** Overseeing consumption and enforcing organization-wide security standards.

### Unity Catalog Metastore
The metastore serves as the top-level container for metadata within Unity Catalog. It registers information about data and AI assets—including tables, views, volumes, models, and functions—along with the permissions governing them.

-   **Region-Specific:** Each metastore is bound to a specific Azure region.
-   **Unified View:** Workspaces attached to the same metastore share a single, consistent view of data and governance policies.
-   **Account-Level Scope:** Unlike legacy systems, Unity Catalog metastores operate at the account level, enabling you to define access policies once and apply them consistently across all attached workspaces.

### Three-Level Namespace
Unity Catalog organizes data using a structured namespace:

`<catalog-name>.<schema-name>.<object-name>`

This hierarchy replaces the workspace-scoped legacy Hive metastore with an account-scoped model designed for centralized governance.

> [!NOTE]
> **Legacy Hive Metastore Compatibility**
> When a workspace is enabled for Unity Catalog, the legacy Hive metastore remains accessible as a catalog named `hive_metastore`. You can query existing data using the format:
>
> `hive_metastore.<schema-name>.<table-name>`
>
> However, migrating to Unity Catalog is strongly recommended to benefit from enhanced security, centralized governance, and built-in auditing.

### Workspaces
Workspaces are the collaborative environments where teams execute compute workloads, including data ingestion, interactive exploration, scheduled jobs, and machine learning training. While each workspace provides isolation for specific projects or teams, they all inherit governance from the account-level metastore.

This hierarchical approach enables a clean separation of concerns:

-   **Account Level:** Organization-wide policies, identity, and billing.
-   **Metastore Level:** Centralized data governance and metadata management.
-   **Workspace Level:** Project isolation and team collaboration.

## Control Plane and Compute Plane

Azure Databricks architecture is built on a fundamental separation between management and execution, divided into two distinct planes: the **Control Plane** and the **Compute Plane**. This design allows for centralized orchestration while ensuring data processing occurs in secure, isolated environments.

### The Control Plane
Managed entirely by Microsoft within your Azure Databricks account, the control plane hosts the backend services that power the platform. It is responsible for:

*   **User Interface:** Hosting the web application used for interaction, configuration, and monitoring.
*   **Orchestration:** Handling job scheduling, cluster lifecycle management, and workspace administration.
*   **Metadata Management:** Maintaining the state of your workspaces and user identities.

> [!IMPORTANT]
> The control plane **does not process your data**. It acts solely as the management layer, ensuring that instructions are passed securely to the compute plane where the actual work happens.

### The Compute Plane
The compute plane is where data processing and execution occur. Azure Databricks offers two models for this plane, each catering to different operational and security requirements:

| Feature | Serverless Compute | Classic (Hybrid) Compute |
| :--- | :--- | :--- |
| **Location** | Runs within the Azure Databricks account infrastructure. | Runs directly within your Azure subscription. |
| **Management** | Fully managed by Azure Databricks; automatic scaling and patching. | Provisions resources (VMs, storage) in your subscription’s virtual network. |
| **Networking** | Uses managed network boundaries and internal security controls. | Provides natural isolation via your own Virtual Network (VNet). |
| **Best For** | Teams seeking minimal operational overhead and fast startup times. | Organizations requiring strict control over networking, custom peering, or on-premises connectivity. |

> [!NOTE]
> In the Azure portal, **Classic workspaces** are often referred to as **Hybrid workspaces**. This terminology reflects their nature of bridging Databricks management with your own Azure infrastructure.

### Benefits of Separation
This architectural split provides several key advantages:
*   **Security:** Data remains within your defined boundaries (especially in Classic mode), while management tools remain isolated.
*   **Scalability:** The control plane can manage thousands of workspaces independently of the compute resources required to process data.
*   **Operational Efficiency:** You can choose between the ease of Serverless or the control of Classic without compromising the centralization of your governance policies.


## Workspace storage
Workspace storage is handled differently depending on your workspace type. Classic workspaces have an associated workspace storage account that resides in your Azure subscription. Serverless workspaces use default storage—a fully managed storage location within your Azure Databricks account, not in your own Azure subscription. You'll explore default storage in detail in a later unit.
Regardless of workspace type, workspace storage contains two categories of data.
Workspace file system data includes the assets that you and your team create and manage through the Azure Databricks UI—notebooks, SQL queries and dashboards, alerts, repos, libraries, and other small files such as Python or YAML configuration files.
Workspace system data is generated internally by Azure Databricks features and includes SQL query results, job run results, notebook revisions, SQL query plans used for observability, and cluster logs.
In classic workspaces, both categories reside in the workspace storage account in your Azure subscription. If your classic workspace was enabled for Unity Catalog automatically, the workspace storage account also contains the default workspace catalog. All users in your workspace can create data assets in the default schema within this catalog. Users access this data through Unity Catalog's governance layer and don't have direct access to the underlying storage, ensuring security and proper access control.
The classic workspace storage account may also contain DBFS (Databricks File System), which is a distributed file system accessible under the dbfs:/ namespace. DBFS root and DBFS mounts are legacy features. Storing and accessing data using DBFS root or DBFS mounts is a deprecated pattern. Instead, you should use Unity Catalog-managed tables and volumes for better governance and security.

```
dbfs:/
```

Understanding where your data resides helps you implement appropriate security controls, such as enabling firewall support for your workspace storage account to limit access to authorized resources and networks only.
