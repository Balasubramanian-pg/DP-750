# Configure compute feature settings

Compute features determine the functional capabilities available to your workloads. Unlike performance settings that tune resource allocation, feature settings enable specific technologies and runtime environments. Selecting appropriate features ensures your compute resource supports your workload requirements while maximizing efficiency.

## Enable Photon Acceleration

Photon is a high-performance, native vectorized query execution engine built into Azure Databricks. It replaces standard Spark JVM-based components with optimized C++ code, significantly accelerating SQL queries and DataFrame operations. By leveraging modern CPU architectures, Photon delivers substantial performance gains for data-intensive workloads without requiring code changes.

### Workload Suitability

Photon is not a universal solution; its impact varies based on the complexity and scale of your data processing tasks.

> [!IMPORTANT]
> **Ideal Candidates for Photon**
> Photon excels in scenarios involving heavy computational lifting. You will see the most significant performance improvements in:
> *   Complex joins and aggregations across large datasets.
> *   Scans of wide tables with many columns.
> *   Workloads that frequently access disk or perform repeated data transformations.
> *   Hourly or daily aggregation queries processing millions of rows.

> [!NOTE]
> **When to Skip Photon**
> For simple batch ETL jobs that process small datasets or complete in under two seconds, the performance gain is negligible. In these cases, the marginal cost of Photon-enabled compute may not be justified by the minimal reduction in execution time.

### Configuration and Compatibility

Photon is enabled by default on **Databricks Runtime 9.1 LTS** and all subsequent versions. You can verify or modify this setting during cluster or warehouse creation in the **Performance** section of the configuration UI.

> [!WARNING]
> **GPU Incompatibility**
> Photon is **not supported** on GPU-enabled clusters. If your workload requires GPU instances for machine learning, deep learning, or image processing, you must explicitly disable Photon. Attempting to use both simultaneously will result in configuration errors or fallback to standard execution.

### Performance Verification

To determine if Photon is providing value for your specific workload, monitor the **Spark UI**. Look for reduced stage durations and lower shuffle spill rates compared to non-Photon executions. If your queries involve complex logic and large data volumes, enabling Photon is often the single most effective step you can take to improve performance and reduce overall DBU consumption through faster completion times.

## Select Databricks Runtime and Spark Version

The Databricks Runtime (DBR) is the foundational software layer that powers your compute resources. It bundles Apache Spark with optimized libraries, security patches, and performance enhancements. The version you select dictates not only the capabilities available to your code but also the stability and maintenance cadence of your environment.

### Runtime Selection Strategy

Choosing the right runtime depends on the lifecycle stage of your workload.

> [!TIP]
> **Interactive Development: Use the Latest Version**
> For all-purpose compute used in notebooks and data exploration, select the most current runtime version. This ensures access to the latest optimizations, bug fixes, and compatibility with modern Python or Scala packages. In a development environment, agility and feature availability outweigh the risk of minor behavioral changes.

> [!IMPORTANT]
> **Production Workloads: Use Long Term Support (LTS)**
> For job compute and operational pipelines, prioritize stability over novelty. LTS versions are supported for an extended period and receive only critical security and reliability updates. This predictability allows data engineering teams to thoroughly test pipelines before committing to an upgrade, preventing unexpected disruptions in daily transformations.

### The Spark Version Dependency

The Apache Spark version is intrinsically tied to the Databricks Runtime. You do not select Spark independently; choosing a DBR automatically determines the underlying Spark engine.

*   **Newer Runtimes:** Include recent Spark releases with advanced features, improved SQL optimization, and broader connector support.
*   **Older Runtimes:** Offer proven stability but may lack newer APIs or performance improvements introduced in later Spark versions.

> [!NOTE]
> **Upgrade Protocol**
> Never apply a runtime upgrade directly to production compute. Always test your workload in a development environment using the target runtime version first. Verify that all libraries, custom configurations, and SQL syntax remain compatible before migrating production jobs to ensure seamless continuity.

## Configure Machine Learning Environments

Machine learning workloads demand a distinct computational environment compared to standard data engineering tasks. They require specialized runtimes, specific hardware accelerators, and configurations that prioritize model training efficiency over distributed data shuffling.

### Databricks Runtime ML

The foundation of any ML workload in Azure Databricks is the **Databricks Runtime ML**. Unlike the standard runtime, this version comes pre-installed with a comprehensive suite of popular machine learning libraries, including TensorFlow, PyTorch, scikit-learn, and XGBoost.

> [!TIP]
> **Reduce Setup Friction**
> By selecting a Databricks Runtime ML version, you eliminate the time-consuming process of manually installing and resolving dependencies for complex ML frameworks. This ensures immediate compatibility between packages and allows data scientists to begin experimentation the moment the cluster starts.

### Hardware Configuration: CPU vs. GPU

The choice of hardware depends heavily on the complexity of the models being trained.

*   **Single-Node CPU for Experimentation:** For initial model prototyping and testing with smaller datasets, a single-node compute resource with a large instance type is often sufficient. This configuration minimizes the overhead of distributed shuffle operations while providing ample memory and CPU power for local processing.
*   **GPU Acceleration for Deep Learning:** For computationally intensive tasks such as image recognition, natural language processing (NLP), and neural network training, GPU-enabled instances are essential. These instances leverage parallel processing to accelerate matrix operations, reducing training times from hours to minutes.

> [!WARNING]
> **Photon Incompatibility**
> When using GPU-enabled instances, you **must disable Photon acceleration**. The Photon engine is optimized for CPU-based vectorized execution and is not compatible with the GPU drivers and CUDA frameworks required for deep learning workloads. Attempting to use both will result in configuration errors.

### Strategic Environment Setup

1.  **Start Small:** Begin with a single-node CPU cluster for data cleaning and baseline model training.
2.  **Scale Up with GPUs:** Transition to multi-node GPU clusters only when moving to deep learning models or when dataset sizes make CPU training impractical.
3.  **Verify Dependencies:** Even with Runtime ML, always verify that specific library versions match your code requirements, especially when migrating models from local development environments.

> [!NOTE]
> Properly configured ML environments not only speed up model training but also ensure reproducibility. By standardizing on Databricks Runtime ML and appropriate hardware profiles, teams can share notebooks and experiments with confidence that the underlying infrastructure supports their computational needs.
