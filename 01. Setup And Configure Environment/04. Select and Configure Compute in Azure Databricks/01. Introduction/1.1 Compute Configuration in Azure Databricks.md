## Compute Configuration in Azure Databricks

Every Azure Databricks workload depends on compute resources, yet the choice of compute type and configuration is rarely neutral. Selecting the wrong option leads to unnecessary expense, degraded performance, or functional limitations. Conversely, aligning compute with workload characteristics unlocks efficiency, security, and developer velocity.

### Choosing the Right Compute Type

Azure Databricks offers distinct compute options, each optimized for specific patterns:

-   **Serverless Compute:** Starts in seconds and eliminates infrastructure management. Ideal for interactive exploration and ad-hoc analysis, but does not support RDD APIs or certain legacy libraries.
-   **Classic Compute:** Provides complete flexibility and full API support. Suitable for complex ETL, custom machine learning workflows, or workloads requiring specific network configurations, though it demands more operational oversight.
-   **SQL Warehouses:** Optimized for analytical queries and BI workloads. They leverage Photon acceleration and serverless scaling to deliver fast, cost-efficient SQL execution.
-   **Job Clusters:** Designed for automated, scheduled workflows. They spin up for a specific job and terminate upon completion, minimizing idle costs compared to all-purpose clusters.

### Configuration Dimensions

Beyond the compute type, granular configuration choices shape performance, cost, and security across multiple dimensions:

| Configuration Element | Impact | Consideration |
| :--- | :--- | :--- |
| **Node Types** | Determines CPU, memory, and storage capacity. | Match instance families to workload profiles (e.g., memory-optimized for large joins, compute-optimized for ML training). |
| **Autoscaling** | Balances responsiveness with cost efficiency. | Configure min/max workers based on expected concurrency and latency requirements. |
| **Access Permissions** | Controls who can create, manage, or use compute. | Enforce least-privilege principles through workspace and cluster policies. |
| **Library Installations** | Provides code dependencies at runtime. | Use cluster-scoped or notebook-scoped libraries to avoid conflicts and ensure reproducibility. |
| **Photon Acceleration** | Enhances SQL query performance significantly. | Enable for SQL warehouses and compatible Delta Lake workloads to reduce query latency and cost. |
| **Instance Pools** | Reduces cluster startup time by maintaining warm capacity. | Trade off idle costs for faster provisioning in high-frequency or latency-sensitive scenarios. |
| **Access Modes** | Defines isolation and permission boundaries. | Use dedicated or shared access modes to enforce data governance and prevent unauthorized cross-user access. |

### Lifecycle-Aware Configuration

Compute strategy must evolve with the development lifecycle:

-   **Exploration Phase:** Prioritize fast iteration and minimal setup. Serverless compute or small autoscaling clusters reduce friction during prototyping and ad-hoc analysis.
-   **Production Phase:** Prioritize stability, predictability, and cost control. Right-size node types, enable Photon for SQL workloads, and use job clusters for batch pipelines to eliminate waste.
-   **Collaboration & Security:** Dedicated access modes enable secure group collaboration while enforcing permission boundaries. Shared access modes reduce costs for trusted teams but require careful governance.

> [!NOTE]
> Getting compute configuration right is not a one-time decision. It requires continuous evaluation as workloads mature, data volumes grow, and organizational priorities shift.
