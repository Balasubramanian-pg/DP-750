# Create a catalog

Your organization's data governance policies require clear separation between development, testing, and production environments. You need production data in dedicated storage, development work isolated from live systems, and sensitive customer information protected from operational data. Unity Catalog's catalog structure helps you meet these requirements while maintaining centralized governance and access control.

## What is a Catalog?

A catalog is the highest-level container in Unity Catalog’s three-layer namespace. It serves as the foundational boundary for your data organization, functioning much like the foundation of a house before you begin decorating the rooms inside. Every data asset in Unity Catalog exists within this strict hierarchy: `catalog.schema.table`.

### The Role of the Catalog

Catalogs are the primary unit of data isolation and organization. They provide a logical and often physical separation that allows you to manage large-scale data estates with precision.

*   **Physical Separation:** Each catalog can be mapped to its own storage location in cloud object storage. This ensures that data from different domains or environments remains physically distinct.
*   **Security Boundaries:** Access policies are often applied at the catalog level. By restricting access to a specific catalog, you ensure that sensitive information remains isolated from general-purpose datasets.
*   **Lifecycle Management:** Catalogs are ideal for separating environments. For example, you might have a `dev` catalog for experimentation and a `prod` catalog for mission-critical business data, preventing accidental modifications to production assets.

### The Three-Layer Hierarchy

Because Unity Catalog uses a fixed three-layer structure, understanding the specific role of each layer is essential for effective design:

1.  **Catalog:** Handles the highest level of separation, typically mapping to business domains (e.g., `sales`, `finance`), security requirements, or lifecycle stages (e.g., `dev`, `prod`).
2.  **Schema:** Organizes the interior of the catalog, grouping related tables and views together (similar to a traditional database schema).
3.  **Table/Volume:** Stores the actual structured data or unstructured files.

> [!NOTE]
> **Think of it as a File System**
> If you are familiar with traditional file systems, a **Catalog** is like a top-level drive or folder, a **Schema** is a subfolder, and a **Table** is the file itself. This structure provides a clear, navigable path to every piece of data in your organization.

## Organize Data with Catalogs

Designing your catalog structure is the first step in establishing a robust data governance framework. Because catalogs represent the highest level of the Unity Catalog namespace, they define the primary boundaries for security, performance, and organizational logic. Your strategy should reflect how your teams operate and where your most critical data access boundaries lie.

### Common Isolation Patterns

There are two primary approaches to organizing catalogs, each serving different operational needs:

#### 1. Environment-Based Isolation
This pattern separates data by its stage in the software development lifecycle. It is ideal for preventing accidental modifications to live data and ensuring that experimental workloads do not impact production performance.

*   **Structure:** `dev_catalog`, `staging_catalog`, `prod_catalog`
*   **Benefit:** Creates a clear "firewall" between experimentation and business-critical operations. Developers can iterate freely in `dev_catalog` without risking the integrity of validated datasets in `prod_catalog`.

#### 2. Sensitivity-Based Isolation
This pattern organizes data by security classification or business domain. It is essential for organizations with strict compliance requirements (such as GDPR or HIPAA) or distinct business units with separate data ownership models.

*   **Structure:** `public_data`, `customer_pii`, `financial_records`, `hr_analytics`
*   **Benefit:** Allows for granular access control. You can grant broad read access to `public_data` while strictly limiting `customer_pii` to authorized personnel only, simplifying audit trails and policy enforcement.

### Performance and Cost Optimization

Your catalog structure has direct implications for infrastructure efficiency. Because each catalog can be associated with a specific **managed storage location**, you can tailor your storage strategy to the value and usage frequency of the data.

| Strategy | Implementation | Benefit |
| :--- | :--- | :--- |
| **Tiered Storage** | Map `prod_catalog` to high-performance SSD storage and `archive_catalog` to cost-effective object storage. | Optimizes costs by aligning storage performance with data utility. |
| **Regional Compliance** | Leverage regional metastores to ensure catalogs inherit local data residency requirements. | Simplifies compliance with laws requiring data to remain within specific geographic borders. |

> [!NOTE]
> **Storage Location Flexibility**
> While Unity Catalog provides a default storage location for the metastore, you can override this at the catalog level. This allows you to keep high-value production data in a premium storage tier while directing less frequently accessed development or historical data to more economical options, all within the same governed workspace.


## Configure managed storage
While creating a catalog without specifying storage is possible, configuring a managed storage location is strongly recommended. Managed storage defines where Unity Catalog stores the data files for managed tables and volumes within your catalog. Without a catalog-level storage location, managed objects fall back to the metastore's default storage, which might not align with your organizational policies or regional requirements.
To specify managed storage, you need an external location already configured in Unity Catalog and the CREATE MANAGED STORAGE privilege on that location. The storage path must point to a cloud storage container, like an Azure Data Lake Storage Gen2 container, that meets your security and compliance requirements.

```
CREATE CATALOG IF NOT EXISTS prod_catalog MANAGED LOCATION 'abfss://prod-data@mystorageaccount.dfs.core.windows.net/catalog-root' COMMENT 'Production catalog with dedicated ADLS Gen2 storage';
```


```
CREATE CATALOG IF NOT EXISTS prod_catalog MANAGED LOCATION 'abfss://prod-data@mystorageaccount.dfs.core.windows.net/catalog-root' COMMENT 'Production catalog with dedicated ADLS Gen2 storage';
```

This command creates a catalog with dedicated production storage. All managed tables and volumes created in this catalog's schemas store their data files under this location, providing complete physical isolation from other catalogs. You can even specify a subpath within an external location, giving you flexibility to organize storage containers while maintaining centralized security credentials.
Managed storage serves two critical purposes. First, it provides physical data isolation by storing each catalog's data in separate cloud storage paths. When you drop a managed table, Unity Catalog can safely delete the underlying files after eight days without affecting data in other catalogs. Second, it helps you meet compliance requirements by ensuring sensitive data resides in specific storage accounts or regions that match your regulatory obligations.
If your metastore doesn't have a default storage location configured, you must specify managed storage when creating catalogs. This requirement ensures that Unity Catalog always knows where to place managed data files, preventing confusion and maintaining clear data governance boundaries.
Catalogs form the foundation of Unity Catalog's data organization model, providing the highest level of isolation and access control. By thoughtfully designing your catalog structure around environment boundaries or sensitivity levels, you create a governance framework that scales with your organization. Now that you understand how to create and configure catalogs, you're ready to organize the interior by adding schemas and data objects within those catalogs.
