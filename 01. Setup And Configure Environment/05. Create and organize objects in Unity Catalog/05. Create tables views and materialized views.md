# Create tables views and materialized views

## Tables and Views: The Foundation of Data Organization

In Unity Catalog, tables and views are the primary mechanisms for storing, accessing, and optimizing data. Each serves a distinct purpose in the data lifecycle: **tables** persist data for long-term storage, **views** simplify complex logic and control access, and **materialized views** bridge the gap by precomputing results for performance. Understanding when to use each is critical for building efficient, maintainable pipelines.

### Managed Tables: The Default Standard

Managed tables are the cornerstone of Unity Catalog. When you create a managed table, Azure Databricks assumes full responsibility for both the table metadata and the underlying data files. This includes automatic storage optimization, lifecycle management, and complete cleanup when the table is dropped.

*   **Format:** By default, managed tables use the **Delta Lake** format, providing ACID transactions, time travel capabilities, and strict schema enforcement.
*   **Cleanup:** Dropping a managed table deletes both the metadata and the physical files, preventing "orphaned" data from cluttering your storage accounts.

#### Creating a Managed Table

You can create tables using either fully qualified names or by setting the current context.

```sql
-- Option 1: Fully Qualified Name
CREATE TABLE production.sales.sales_transactions (
    transaction_id BIGINT,
    customer_id INT,
    product_name STRING,
    amount DECIMAL(10,2),
    transaction_date DATE
);

-- Option 2: Setting Context
USE CATALOG production;
USE SCHEMA sales;
CREATE TABLE sales_transactions (
    transaction_id BIGINT,
    customer_id INT,
    product_name STRING,
    amount DECIMAL(10,2),
    transaction_date DATE
);
```

### Enhancing Data Quality with Constraints and Generated Columns

For production workloads, relying solely on basic column definitions is often insufficient. Unity Catalog supports **constraints** to enforce data quality rules and **generated columns** to automate calculations.

```sql
CREATE TABLE customer_orders (
    order_id BIGINT NOT NULL,
    customer_email STRING NOT NULL,
    order_total DECIMAL(10,2),
    -- Automatically calculates tax based on order total
    tax_amount DECIMAL(10,2) GENERATED ALWAYS AS (order_total * 0.08),
    -- Ensures no negative or zero-order totals are inserted
    CONSTRAINT valid_total CHECK (order_total > 0)
);
```

> [!IMPORTANT]
> **Why Use Constraints?**
> While Delta Lake provides schema enforcement (ensuring the right data types), constraints like `CHECK` and `NOT NULL` enforce business logic at the point of ingestion. This prevents bad data from ever entering your trusted datasets, reducing the need for downstream cleaning.

### Comparing Table and View Types

| Feature | Managed Table | View | Materialized View |
| :--- | :--- | :--- | :--- |
| **Data Storage** | Persists physical data files. | No physical data; stores only query logic. | Persists physical data files (cached results). |
| **Performance** | Depends on query optimization. | Depends on underlying table performance. | High; results are precomputed. |
| **Freshness** | Real-time (as data is written). | Real-time (reflects current state of tables). | Refreshed on a schedule or trigger. |
| **Use Case** | Long-term storage, raw/curated data. | Simplifying complex joins, security masking. | Accelerating frequent, heavy aggregations. |

By strategically combining these objects, you create a data architecture that is not only governed and secure but also optimized for both developer productivity and query performance.

## Define Primary Keys and Foreign Keys

Primary keys and foreign keys in Unity Catalog serve as critical metadata for documenting relationships and enabling query optimizations. Available in Databricks Runtime 11.3 LTS and above (fully GA in Runtime 15.2+), these constraints are **informational only**. They do not enforce referential integrity at write time, meaning they will not prevent invalid data from being inserted. However, they provide immense value by allowing the query optimizer to make smarter decisions about join strategies and execution plans.

### Primary Keys

A primary key uniquely identifies each record in a table. When defined, primary key columns are implicitly treated as `NOT NULL`.

#### Single-Column Primary Key
```sql
CREATE TABLE customers (
    customer_id BIGINT NOT NULL,
    customer_name STRING,
    email STRING,
    CONSTRAINT customers_pk PRIMARY KEY (customer_id)
);
```

#### Composite Primary Key
For tables where uniqueness is determined by multiple columns, list all key columns in the constraint definition:

```sql
CREATE TABLE order_items (
    order_id BIGINT NOT NULL,
    item_id BIGINT NOT NULL,
    product_name STRING,
    quantity INT,
    price DECIMAL(10,2),
    CONSTRAINT order_items_pk PRIMARY KEY (order_id, item_id)
);
```

### Foreign Keys

Foreign keys define relationships between tables by referencing a primary key in another table. This metadata helps the optimizer understand how tables relate, which is especially valuable for complex multi-table joins.

```sql
CREATE TABLE orders (
    order_id BIGINT NOT NULL PRIMARY KEY,
    customer_id BIGINT,
    order_date DATE,
    total_amount DECIMAL(10,2),
    CONSTRAINT orders_customers_fk FOREIGN KEY (customer_id) REFERENCES customers(customer_id)
);
```

### Adding Constraints to Existing Tables

You can add or modify constraints on existing tables using `ALTER TABLE` statements. This is useful when retrofitting metadata onto legacy datasets or when constraints were omitted during initial creation.

```sql
-- Add a primary key to an existing table
ALTER TABLE orders ADD CONSTRAINT orders_pk PRIMARY KEY (order_id);

-- Add a foreign key relationship
ALTER TABLE order_items 
ADD CONSTRAINT order_items_orders_fk 
FOREIGN KEY (order_id) REFERENCES orders(order_id);
```

> [!IMPORTANT]
> **Informational, Not Enforced**
> Unlike traditional RDBMS systems, Unity Catalog does not validate primary or foreign key constraints during data ingestion. You remain responsible for ensuring data quality through ETL logic, `CHECK` constraints, or Delta Live Tables expectations. The primary value of PK/FK constraints here is **optimizer hints** and **data documentation**.

### Why Use Informational Constraints?

| Benefit | Description |
| :--- | :--- |
| **Query Optimization** | The optimizer uses PK/FK metadata to eliminate unnecessary joins, reorder operations, and select more efficient execution plans. |
| **Data Documentation** | Constraints serve as self-documenting schema metadata, making relationships discoverable in Catalog Explorer and BI tools. |
| **BI Tool Integration** | Many BI platforms (e.g., Power BI, Tableau) automatically detect relationships from PK/FK metadata, simplifying semantic model creation. |
| **AI/BI Genie** | Genie spaces leverage constraint metadata to better understand table relationships when generating SQL from natural language queries. |

By defining primary and foreign keys—even though they are not enforced—you invest in a richer metadata layer that pays dividends in query performance, discoverability, and downstream tool integration.

## Create External Tables

External tables provide a bridge between Unity Catalog’s governance layer and data stored in external systems. Unlike managed tables, where Databricks controls both the metadata and the physical files, external tables only register the metadata. The underlying data remains in its original location, untouched by Unity Catalog’s lifecycle management.

### Key Characteristics

*   **Metadata Only:** Dropping an external table removes it from the catalog but leaves the physical files intact in cloud storage.
*   **Shared Access:** Ideal for scenarios where multiple systems or workspaces need to read the same dataset without duplicating it.
*   **Format Flexibility:** You can query data in its native format (CSV, JSON, Parquet) without requiring an ETL process to move it into Delta Lake.

### Creating an External Table

To create an external table, you must specify a `LOCATION` clause pointing to a path protected by a configured **external location** in Unity Catalog.

```sql
CREATE EXTERNAL TABLE archived_sales 
USING CSV 
LOCATION 'abfss://container@storage.dfs.core.windows.net/sales/archive' 
OPTIONS (
    header 'true', 
    inferSchema 'true'
);
```

> [!IMPORTANT]
> **Prerequisite: External Location**
> The storage path specified in the `LOCATION` clause must be registered as an external location in Unity Catalog. This ensures that the necessary storage credentials and access policies are in place for Databricks to read the data securely.

### Managed vs. External Tables

| Feature | Managed Table | External Table |
| :--- | :--- | :--- |
| **Data Ownership** | Unity Catalog manages files and metadata. | You manage files; Unity Catalog manages metadata. |
| **Drop Behavior** | Deletes both metadata and physical files. | Deletes only metadata; files remain in storage. |
| **Optimizations** | Full Delta Lake features (Z-Order, V-Order). | Limited to the capabilities of the source format. |
| **Best For** | New pipelines, curated data, production workloads. | Legacy data, cross-system sharing, raw ingestion. |

> [!NOTE]
> **Strategic Recommendation**
> For new data pipelines, **prefer managed tables**. They offer superior performance through Delta Lake optimizations, automatic cleanup, and tighter security integration. Use external tables only when you have a specific requirement to keep data in its original location or when integrating with non-Databricks systems that must maintain direct file access.

## Create Standard Views

Standard views act as a virtual layer over your tables, defined by a SQL query that executes dynamically every time the view is accessed. Because they do not store physical data, views are lightweight and always reflect the most current state of the underlying tables. They are ideal for simplifying complex joins, encapsulating recurring business logic, or providing a consistent interface for downstream consumers.

### Creating a View

To create a view, use the `CREATE VIEW` statement paired with a `SELECT` query. The following example creates a summary view that aggregates customer order data:

```sql
CREATE VIEW customer_order_summary AS 
SELECT 
    c.customer_id, 
    c.customer_name, 
    c.region, 
    COUNT(o.order_id) AS total_orders, 
    SUM(o.order_total) AS total_spent 
FROM customers c 
INNER JOIN orders o ON c.customer_id = o.customer_id 
GROUP BY c.customer_id, c.customer_name, c.region;
```

### Key Characteristics

*   **Real-Time Data:** Since views compute results on demand, they automatically update whenever the source tables change. There is no need for manual refreshes.
*   **No Storage Cost:** Views consume no storage space because they only store the query definition (metadata), not the data itself.
*   **Logical Abstraction:** They allow you to hide complex join logic or column transformations behind a simple table-like interface, making it easier for analysts to query data without understanding the underlying schema complexity.

> [!NOTE]
> **Performance Considerations**
> While views are convenient, they can introduce performance overhead if the underlying query is complex. Every time a user queries the view, the database must execute the full `SELECT` statement, including any joins or aggregations. For frequently accessed reports involving large datasets, this "compute-on-read" model may result in slower response times compared to precomputed solutions.

### Layering and Best Practices

You can build views on top of other views to create multi-level abstractions, breaking down complex logic into manageable steps. However, excessive layering can make troubleshooting difficult and degrade performance due to nested query execution.

*   **Keep it Simple:** Aim for shallow view hierarchies. If a view depends on more than two or three other views, consider consolidating the logic or using a materialized view instead.
*   **Document Logic:** Use comments in your `CREATE VIEW` statements to explain the business purpose of the abstraction, helping future users understand why the view exists.

By using standard views strategically, you can streamline data access and enforce consistent business definitions across your organization without incurring additional storage costs.

## Create Dynamic Views for Access Control

Dynamic views extend the functionality of standard views by embedding fine-grained security controls directly into the query logic. They allow you to apply row-level filters and column-level masks based on the identity or group membership of the user querying the view. This enables a "single source of truth" model where one view serves multiple audiences with different access levels, eliminating the need to duplicate tables or maintain complex permission sets.

### Column-Level Masking

Column masking hides sensitive data from unauthorized users while allowing privileged groups to see the original values. This is achieved using a `CASE` statement combined with the `is_account_group_member()` function.

```sql
CREATE VIEW sales_redacted AS 
SELECT 
    user_id, 
    CASE 
        WHEN is_account_group_member('auditors') THEN email 
        ELSE 'REDACTED' 
    END AS email, 
    country_region, 
    product, 
    total 
FROM sales_raw;
```

In this example, members of the `auditors` group see the actual email addresses, while all other users see the static string `'REDACTED'`.

### Row-Level Security (RLS)

Row-level security restricts which records a user can see based on conditional logic in the `WHERE` clause.

```sql
CREATE VIEW sales_filtered AS 
SELECT 
    user_id, 
    country_region, 
    product, 
    total 
FROM sales_raw 
WHERE 
    CASE 
        WHEN is_account_group_member('managers') THEN TRUE 
        ELSE total <= 1000000 
    END;
```

Here, managers see all transactions, while other users are restricted to transactions with a total value of 1 million or less.

> [!IMPORTANT]
> **Prerequisites for Dynamic Views**
> Dynamic views require specific compute configurations to evaluate user context at query time:
> *   **Compute:** SQL Warehouses, Standard Access Mode, or Dedicated Access Mode.
> *   **Runtime:** Databricks Runtime 15.4 LTS or above.
>
> Without these, the `is_account_group_member()` function may not resolve correctly, potentially exposing data or causing errors.

## Create Materialized Views

Materialized views bridge the gap between the flexibility of views and the performance of tables. Unlike standard views, which recalculate results on every query, materialized views precompute and cache query results as physical Delta tables. This makes them significantly faster for complex aggregations and frequently accessed dashboards.

### Creating a Materialized View

To create a materialized view, use the `CREATE MATERIALIZED VIEW` statement. The result is stored physically, meaning it consumes storage but offers rapid read performance.

```sql
CREATE MATERIALIZED VIEW daily_sales_summary AS 
SELECT 
    transaction_date, 
    COUNT(*) AS transaction_count, 
    SUM(amount) AS total_sales, 
    AVG(amount) AS average_sale 
FROM sales_transactions 
GROUP BY transaction_date;
```

### Refresh Strategies: Incremental vs. Full

Materialized views must be refreshed to reflect changes in the underlying data. Unity Catalog supports two strategies:

1.  **Full Refresh:** Recomputes the entire view from scratch. Simple but resource-intensive.
2.  **Incremental Refresh:** Processes only the data that has changed since the last refresh. This is far more efficient for large datasets.

#### Enabling Incremental Refresh

To support incremental refresh, your source tables must be Delta tables with **row tracking** enabled. Row tracking assigns a unique, immutable ID to each row, allowing the engine to identify exactly which rows have been inserted, updated, or deleted.

```sql
ALTER TABLE sales_transactions 
SET TBLPROPERTIES (delta.enableRowTracking = true);
```

> [!WARNING]
> **Row Tracking Considerations**
> *   **Runtime Requirement:** Requires Databricks Runtime 14.1 or above.
> *   **Irreversible Change:** Enabling row tracking upgrades the table protocol version and cannot be reversed.
> *   **Initial Overhead:** For existing large tables, enabling row tracking assigns IDs to all rows, which can take significant time and create multiple new table versions.

### Scheduling Refreshes

You can automate maintenance by scheduling refreshes during creation. This ensures your materialized views remain up-to-date without manual intervention.

```sql
CREATE MATERIALIZED VIEW daily_sales_summary 
SCHEDULE EVERY 1 DAY 
AS 
SELECT 
    transaction_date, 
    COUNT(*) AS transaction_count, 
    SUM(amount) AS total_sales 
FROM sales_transactions 
GROUP BY transaction_date;
```

### When to Use Materialized Views

| Scenario | Recommendation | Rationale |
| :--- | :--- | :--- |
| **Heavy Aggregations** | Materialized View | Precomputing sums/counts avoids repeating expensive calculations for every dashboard load. |
| **High Concurrency** | Materialized View | Multiple users querying the same summary benefit from reading cached data rather than hitting source tables. |
| **Real-Time Needs** | Standard View | If data changes constantly and users need sub-second freshness, the latency of a scheduled refresh may be unacceptable. |

By strategically using dynamic views for security and materialized views for performance, you create a data platform that is both secure and responsive, tailored to the diverse needs of your organization.

# Best practices for tables and views
When creating tables, start with managed tables unless you have a specific need for external storage. Managed tables provide better integration with Unity Catalog features, automatic optimization, and simpler lifecycle management. Enable row tracking on Delta tables that serve as sources for materialized views to support efficient incremental refreshes.
For views, keep the underlying queries focused and avoid creating too many layers. While layering views provides logical organization, it can make debugging difficult and hide performance issues. Document the purpose of each view and its intended audience to help other team members understand your data model.
Use dynamic views to implement data security policies at the view level rather than duplicating tables for different user groups. This approach centralizes security logic and reduces data redundancy. Combine dynamic views with Unity Catalog permissions to create a comprehensive data governance strategy.
When choosing between standard and materialized views, consider query performance and data freshness requirements. Use standard views for queries that run quickly or when you need real-time data. Use materialized views for expensive aggregations or when eventual consistency is acceptable. Monitor the refresh behavior of materialized views to ensure they update incrementally rather than fully reprocessing data.
Apply liquid clustering to tables and materialized views instead of traditional partitioning for better query performance and easier maintenance. Liquid clustering automatically optimizes data layout based on query patterns, while partitioning requires manual configuration and can create skewed partitions. Use the CLUSTER BY clause when creating tables or materialized views to enable this optimization.

```
CLUSTER BY
```
