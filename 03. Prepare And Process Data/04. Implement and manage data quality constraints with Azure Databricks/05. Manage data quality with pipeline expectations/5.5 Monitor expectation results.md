# Monitor expectation results

After you define expectations, you can track their results through the pipeline UI. This visibility helps you understand data quality trends and identify recurring issues. Monitoring expectations is not just about seeing how many records failed. It is about understanding the health of your data pipelines over time. It is about detecting changes in data quality before they affect downstream consumers. It is about building trust in your data. In Lakeflow Spark Declarative Pipelines, expectations produce metrics that are captured during pipeline runs. These metrics are available in the pipeline UI and through the event log. You can view them manually, query them programmatically, and build alerts and dashboards on top of them.

This section explains how to monitor expectation results in detail. It covers the pipeline UI, the Data quality tab, the metrics for warn, drop, and fail actions, the error messages for fail expectations, and programmatic access through the event log. It also provides commented code examples for querying the event log with SQL and PySpark. By the end, you will know how to track data quality trends, investigate violations, and build custom monitoring solutions.

## Why monitoring expectation results matters

Data quality is not a one-time check. It is an ongoing process. Source systems change. Data volumes grow. Business rules evolve. A pipeline that passes all expectations today may fail tomorrow. Monitoring expectation results gives you early warning. It helps you detect problems before they reach downstream consumers. It helps you understand the impact of changes in source systems. It helps you prioritize fixes. It helps you communicate data quality to stakeholders.

Monitoring also helps you tune your expectations. If an expectation is too strict, it may drop or fail too many records. If it is too loose, it may miss important problems. By monitoring pass rates and violation counts, you can adjust thresholds and actions. You can also identify expectations that never fail. These may be redundant or may need to be tightened. You can identify expectations that always fail. These may indicate a systemic problem in the source system or a bug in your pipeline.

Monitoring also supports compliance and auditing. Many organizations require evidence that data quality controls are in place and effective. Expectation metrics provide that evidence. You can show auditors how many records passed and failed each rule. You can show that violations are detected and handled. You can show that the pipeline is reliable.

## Viewing expectation metrics in the pipeline UI

The pipeline UI provides a visual way to monitor expectation results. To view expectation metrics, follow these steps.

First, open Jobs & Pipelines in the Azure Databricks workspace sidebar. This is where you can see all your jobs and pipelines. You can filter by name or by status. You can also search for a specific pipeline.

Second, select your pipeline by name. This opens the pipeline details page. The pipeline details page shows the pipeline graph, the run history, and the configuration. It also shows the datasets that are defined in the pipeline.

Third, select a dataset that has expectations defined. Datasets are the tables or views that are defined in the pipeline. They appear as nodes in the pipeline graph. You can click on a dataset to see its details. The dataset details page shows the schema, the expectations, and the data quality metrics.

Fourth, open the Data quality tab in the right sidebar. This tab shows the expectation metrics for the selected dataset. It shows how many records passed or failed each expectation during pipeline runs. It also shows the pass rate over time. You can use this information to understand data quality trends and identify recurring issues.

The Data quality tab typically displays the following information for each expectation:

- The expectation name.
- The constraint expression.
- The action: warn, drop, or fail.
- The number of records that passed.
- The number of records that failed.
- The pass rate as a percentage.
- A trend chart showing pass rate over time.

For warn and drop actions, you see counts of violations. A violation is a record that failed the constraint. For warn, the record is still written to the target table. For drop, the record is removed before write. In both cases, the violation is counted. You can see how many records were affected. You can also see the pass rate, which is the number of passing records divided by the total number of records.

For fail actions, the pipeline stops before metrics are recorded. This means you may not see a count of violations in the Data quality tab for fail expectations. Instead, the pipeline run fails. The error message includes details about the violating record. You can use the error message to investigate. After you fix the problem and restart the pipeline, the metrics for other expectations may be recorded. But the fail expectation itself will not show a violation count because the pipeline stopped before the metric could be written.

The Data quality tab also allows you to filter by expectation name or by action. You can sort by pass rate or by violation count. You can click on an expectation to see more details, such as the history of violations and the sample records that failed. This is useful for debugging.

## Interpreting fail expectation error messages

When a fail expectation triggers, the pipeline stops. The error message provides context to help you investigate. The error message typically includes the following information:

- The pipeline name or flow name.
- The name of the expectation that was violated.
- The input data that caused the violation.

Here is an example error message from the original text:

```
[EXPECTATION_VIOLATION.VERBOSITY_ALL] Flow 'sensor-pipeline' failed to meet 
the expectation. Violated expectations: 'temperature_in_valid_range'. 
Input data: '{"id":"TEMP_001","temperature":-500,"timestamp_ms":"1710498600"}'.
```

Let us break down this error message.

The first part is `[EXPECTATION_VIOLATION.VERBOSITY_ALL]`. This is a tag that indicates the type of error. `EXPECTATION_VIOLATION` means that an expectation was violated. `VERBOSITY_ALL` means that the error message includes all available details, including the input data.

The second part is `Flow 'sensor-pipeline' failed to meet the expectation.` This tells you which flow or pipeline failed. In this case, the flow is named `sensor-pipeline`. A flow is a logical unit of work in the pipeline. It may correspond to a dataset or a transformation.

The third part is `Violated expectations: 'temperature_in_valid_range'.` This tells you which expectation was violated. The name is `temperature_in_valid_range`. This name should be descriptive. It tells you that the temperature is expected to be in a valid range.

The fourth part is `Input data: '{"id":"TEMP_001","temperature":-500,"timestamp_ms":"1710498600"}'.` This is the record that caused the violation. It is shown as a JSON string. In this example, the record has an `id` of `TEMP_001`, a `temperature` of `-500`, and a `timestamp_ms` of `1710498600`. The temperature is `-500`, which is likely outside the valid range. This is why the expectation failed.

You can use this information to debug. You can look at the record and understand why it failed. For example, a temperature of `-500` might be a sensor error or a data entry mistake. You can then investigate the source system, fix the data, and restart the pipeline.

## Programmatic access to expectation metrics via the event log

You can also query expectation metrics programmatically through the Lakeflow Spark Declarative Pipelines event log. This approach enables you to build custom dashboards or trigger alerts based on data quality thresholds. The event log is a Delta table that stores events from pipeline runs. It includes events for expectation violations, pipeline start and stop, and other operational events. You can query the event log using SQL or PySpark. You can join it with other tables. You can aggregate the data. You can create views and dashboards.

The event log is typically stored in a Unity Catalog schema or in a location that you configure. The exact table name depends on your pipeline configuration. It is often named something like `event_log` or `pipeline_event_log`. You can find the event log location in the pipeline settings or in the pipeline details page. In Databricks, the event log is often stored in a schema like `event_log` or in the pipeline's metadata location.

The event log contains a column that stores the event details. The details are often in JSON format. You can parse the JSON to extract the expectation name, the action, the violation count, and other fields. The event log also contains columns for the timestamp, the pipeline ID, the run ID, and the flow name.

The following SQL example shows how to query the event log for expectation violations. Each line is commented.

```sql
-- Query the event log for expectation violations.
-- The event log table is named event_log.
-- The table is in the schema governance.pipeline_events.
-- You may need to adjust the table name and schema to match your environment.
SELECT
    -- The timestamp when the event occurred.
    timestamp,
    -- The name of the pipeline.
    pipeline_name,
    -- The ID of the pipeline run.
    run_id,
    -- The name of the flow or dataset.
    flow_name,
    -- The name of the expectation that was violated.
    -- The expectation name is extracted from the JSON details.
    -- The JSON path may vary depending on the event schema.
    -- In this example, we assume the details column is a JSON string.
    -- We use the get_json_object function to extract the expectation name.
    get_json_object(details, '$.expectation_name') AS expectation_name,
    -- The action that was taken: warn, drop, or fail.
    get_json_object(details, '$.action') AS action,
    -- The number of records that failed the expectation.
    -- This is available for warn and drop actions.
    get_json_object(details, '$.violation_count') AS violation_count
FROM
    governance.pipeline_events.event_log
WHERE
    -- Filter for expectation violation events.
    -- The event type is stored in the event_type column.
    event_type = 'EXPECTATION_VIOLATION'
    -- Filter for a specific pipeline.
    AND pipeline_name = 'sensor-pipeline'
    -- Filter for a specific time range.
    AND timestamp >= '2026-01-01'
ORDER BY
    timestamp DESC;
```

In this query, we select the timestamp, pipeline name, run ID, flow name, expectation name, action, and violation count. We use `get_json_object` to extract fields from the JSON details column. We filter for `EXPECTATION_VIOLATION` events. We filter for a specific pipeline and a specific time range. We order by timestamp descending to see the most recent violations first.

You can also aggregate the data to see trends. The following SQL example shows how to count violations per expectation per day.

```sql
-- Count expectation violations per day per expectation.
SELECT
    -- The date of the event.
    DATE(timestamp) AS event_date,
    -- The name of the expectation.
    get_json_object(details, '$.expectation_name') AS expectation_name,
    -- The action.
    get_json_object(details, '$.action') AS action,
    -- The total number of violations.
    SUM(CAST(get_json_object(details, '$.violation_count') AS INT)) AS total_violations
FROM
    governance.pipeline_events.event_log
WHERE
    event_type = 'EXPECTATION_VIOLATION'
    AND pipeline_name = 'sensor-pipeline'
    AND timestamp >= '2026-01-01'
GROUP BY
    DATE(timestamp),
    get_json_object(details, '$.expectation_name'),
    get_json_object(details, '$.action')
ORDER BY
    event_date DESC,
    total_violations DESC;
```

This query groups by date, expectation name, and action. It sums the violation counts. You can use this to build a dashboard that shows violation trends over time. You can also set up alerts when the total violations exceed a threshold.

You can also use PySpark to query the event log. The following PySpark code shows how to read the event log, filter for expectation violations, and extract fields.

```python
# Import the required functions.
from pyspark.sql.functions import col, get_json_object, to_date, sum as _sum

# Read the event log table.
event_log = spark.read.table("governance.pipeline_events.event_log")

# Filter for expectation violation events for a specific pipeline.
violations = event_log.filter(
    (col("event_type") == "EXPECTATION_VIOLATION") &
    (col("pipeline_name") == "sensor-pipeline") &
    (col("timestamp") >= "2026-01-01")
)

# Extract the expectation name, action, and violation count from the JSON details.
violations_extracted = violations.select(
    col("timestamp"),
    get_json_object(col("details"), "$.expectation_name").alias("expectation_name"),
    get_json_object(col("details"), "$.action").alias("action"),
    get_json_object(col("details"), "$.violation_count").cast("int").alias("violation_count")
)

# Group by date, expectation name, and action, and sum the violation counts.
daily_violations = violations_extracted.groupBy(
    to_date(col("timestamp")).alias("event_date"),
    col("expectation_name"),
    col("action")
).agg(
    _sum(col("violation_count")).alias("total_violations")
).orderBy(
    col("event_date").desc(),
    col("total_violations").desc()
)

# Show the results.
daily_violations.show()
```

This PySpark code does the same thing as the SQL example. It reads the event log, filters for violations, extracts fields from JSON, groups by date and expectation, and sums the violation counts. You can write the results to a Delta table, create a view, or use them in a dashboard.

## Building custom dashboards and alerts

Once you can query expectation metrics programmatically, you can build custom dashboards and alerts. Databricks SQL provides a dashboarding feature. You can create a dashboard that shows pass rates, violation counts, and trends over time. You can add filters for pipeline, dataset, expectation, and date range. You can share the dashboard with your team.

You can also set up alerts. Databricks SQL alerts allow you to run a query on a schedule and send notifications when the results meet certain conditions. For example, you can create an alert that triggers when the pass rate for a critical expectation falls below 99 percent. You can send notifications via email, Slack, PagerDuty, or a webhook. The following example shows a conceptual alert configuration. This is not executable code, but it illustrates the settings you would configure in the Databricks SQL interface.

```
Alert name: Critical expectation pass rate below threshold
Query: SELECT pass_rate FROM data_quality_metrics WHERE expectation_name = 'valid_amount' AND pipeline_name = 'payments_pipeline' ORDER BY timestamp DESC LIMIT 1
Condition: pass_rate < 0.99
Schedule: Every 15 minutes
Notification: Send email to data-engineering@example.com
```

You can also use the Databricks REST API to create alerts programmatically. You can integrate with external monitoring tools such as Prometheus, Grafana, or Datadog. You can export metrics to these tools using the Databricks SQL connector or the REST API.

## Best practices for monitoring expectations

Monitor your expectations regularly. Set up a schedule to review the Data quality tab or your custom dashboards. Do not wait for a pipeline failure to check data quality.

Set up alerts for critical expectations. Use fail or drop actions for critical rules. Set up alerts when violations occur. Use warn for less critical rules. Set up alerts when pass rates fall below a threshold.

Track trends over time. A single violation may not be a problem. A trend of increasing violations may indicate a systemic issue. Use historical data to identify trends.

Investigate violations promptly. When a fail expectation triggers, investigate the error message. Look at the input data. Identify the root cause. Fix the source system or the pipeline. Restart the pipeline.

Document your expectations. Keep a record of what each expectation checks and why it exists. Update the documentation when you change an expectation. This helps new team members understand the data quality rules.

Use a centralized rules table. Store expectations in a Unity Catalog Delta table. This makes them version-controlled, auditable, and queryable. It also makes it easy to apply the same rules across multiple pipelines.

Test your expectations. Before deploying to production, test with sample data. Verify that valid records pass and invalid records are handled correctly. Test each action: warn, drop, and fail.

Review your expectations periodically. Remove expectations that are no longer needed. Update expectations that are too strict or too loose. Add new expectations for new data quality requirements.

## Common pitfalls in monitoring expectations

One common pitfall is not monitoring expectations at all. If you do not monitor, you will not know when data quality degrades. You may find out when downstream consumers report problems. This is too late.

Another pitfall is monitoring only fail expectations. Fail expectations stop the pipeline. But warn and drop expectations also provide valuable information. They can show gradual degradation of data quality before it becomes critical.

Another pitfall is ignoring violations. If you see violations but do not investigate, the problem may get worse. A small number of violations today may become a large number tomorrow. Investigate and fix the root cause.

Another pitfall is setting thresholds too high or too low. If you set a threshold too high, you may get too many alerts. This leads to alert fatigue. If you set it too low, you may miss important problems. Tune your thresholds based on historical data.

Another pitfall is not documenting expectations. If you do not document what each expectation checks, it is hard to understand violations. New team members may not know why an expectation exists or how to fix a violation.

Another pitfall is not testing expectations. If you do not test, you may find that an expectation is too strict or too loose. You may also find that the action is not what you intended. Always test with sample data.
