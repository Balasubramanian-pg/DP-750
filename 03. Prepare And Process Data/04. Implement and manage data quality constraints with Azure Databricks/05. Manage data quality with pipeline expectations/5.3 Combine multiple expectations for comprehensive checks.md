# Combine multiple expectations for comprehensive checks

Real-world data validation often requires multiple rules. You can stack expectations on a single dataset to check different aspects of data quality. Each expectation has a name, a constraint, and an action. When you combine them, you create a comprehensive data quality contract for your dataset. This contract documents what valid data looks like. It also determines what happens when data does not meet those standards. Combining expectations is common because a single rule rarely covers all the ways data can be wrong. You might need to check that an amount is positive, that a currency is one of a set of allowed values, that a timestamp is not in the future, and that a customer ID is not null. Each of these is a separate rule. Together they provide comprehensive coverage.

The benefit of combining expectations is that you can validate many aspects of your data in one place. You can apply different actions to different rules. You can monitor each rule separately. You can see which rules fail most often. You can also group rules that share the same action. This makes your pipeline easier to maintain and your data quality easier to manage.

## Stacking expectations in Python

In Python, you can add multiple decorator calls to the same function. Each decorator adds one expectation. The decorators are applied in order. The function returns the DataFrame that contains the data. The expectations are evaluated for each record. The action is determined by the decorator you use. The decorators `@dp.expect`, `@dp.expect_or_drop`, and `@dp.expect_or_fail` each add a single expectation. You can stack as many as you need.

The following example shows three expectations stacked on a single dataset. Each line is commented.

```python
# Import the pipelines module from pyspark.
from pyspark import pipelines as dp

# The @dp.table decorator defines a streaming table.
@dp.table
# The @dp.expect decorator adds a warn expectation.
# The name is "valid_amount".
# The constraint is "amount > 0".
# If the amount is not greater than zero, the record fails the expectation.
# Because this is @dp.expect, the record is still written to the target.
# The violation is recorded in the data quality metrics.
@dp.expect("valid_amount", "amount > 0")
# The @dp.expect decorator adds a second warn expectation.
# The name is "valid_currency".
# The constraint is "currency IN ('USD', 'EUR', 'GBP')".
# This checks that the currency is one of the allowed values.
# If the currency is not in the list, the record fails the expectation.
# The record is still written to the target.
@dp.expect("valid_currency", "currency IN ('USD', 'EUR', 'GBP')")
# The @dp.expect decorator adds a third warn expectation.
# The name is "valid_timestamp".
# The constraint is "created_at <= current_timestamp()".
# This checks that the created_at timestamp is not in the future.
# If the timestamp is in the future, the record fails the expectation.
# The record is still written to the target.
@dp.expect("valid_timestamp", "created_at <= current_timestamp()")
def validated_payments():
    # The function returns a streaming DataFrame.
    # The DataFrame is read from the raw_payments table.
    # The expectations are applied to each record as it is processed.
    # All three expectations are evaluated for each record.
    # A record can fail one, two, or all three expectations.
    # Because all three use @dp.expect, the record is always written to the target.
    # The metrics record which expectations failed.
    return spark.readStream.table("raw.payments")
```

In this example, all three expectations use the warn action. This means invalid records are written to the target table. The pipeline does not stop. The metrics show how many records failed each expectation. You can monitor these metrics to understand data quality. If you want a different action for some rules, you can mix decorators. For example, you might use `@dp.expect_or_drop` for one rule and `@dp.expect_or_fail` for another. The order of the decorators does not affect the action. Each decorator applies its own action independently.

## Grouping expectations into reusable dictionaries

Python also supports grouping expectations into reusable dictionaries. This approach helps you maintain consistency across multiple tables. Instead of writing the same decorators on every table, you define a dictionary of rules once and reuse it. The dictionary maps expectation names to constraint expressions. You can then use the `expect_all`, `expect_all_or_drop`, or `expect_all_or_fail` decorators to apply the same action to all expectations in the group.

The following example defines a dictionary of payment rules. Each line is commented.

```python
# Define a dictionary of payment rules.
# The keys are expectation names.
# The values are SQL constraint expressions.
payment_rules = {
    # The valid_amount rule checks that the amount is greater than zero.
    "valid_amount": "amount > 0",
    # The valid_currency rule checks that the currency is one of the allowed values.
    "valid_currency": "currency IN ('USD', 'EUR', 'GBP')",
    # The valid_timestamp rule checks that the created_at timestamp is not in the future.
    "valid_timestamp": "created_at <= current_timestamp()"
}

# The @dp.expect_all_or_drop decorator applies the drop action to all rules in the dictionary.
# The dictionary is passed as the argument.
# If any record fails any rule, the record is dropped before write.
# The pipeline continues processing other records.
# The drop count is recorded for each rule in the data quality metrics.
@dp.expect_all_or_drop(payment_rules)
def clean_payments():
    # Read from the raw_payments source.
    # The returned DataFrame is the input to the dataset.
    # All rules in the dictionary are evaluated for each record.
    return spark.readStream.table("raw.payments")
```

In this example, the `payment_rules` dictionary is defined once. The `@dp.expect_all_or_drop` decorator applies the drop action to all three rules. If a record fails any of the rules, it is dropped. This is useful when you want to ensure that only records that pass all rules reach the target table. You can reuse the same dictionary on multiple tables. This ensures that the same rules are applied consistently. If you need to change a rule, you change it in one place. All tables that use the dictionary are updated automatically.

## The expect_all decorators

There are three decorators for applying the same action to a group of expectations.

The `@dp.expect_all` decorator applies the warn action to all expectations in the group. Invalid records are written to the target. Metrics are recorded for each rule.

The `@dp.expect_all_or_drop` decorator applies the drop action to all expectations in the group. Invalid records are removed before write. The pipeline continues.

The `@dp.expect_all_or_fail` decorator applies the fail action to all expectations in the group. The pipeline stops when any record violates any rule. The current transaction rolls back.

Each decorator accepts a dictionary where keys are expectation names and values are SQL constraint expressions. You can define multiple dictionaries for different groups of rules. For example, you might have a dictionary of critical rules that use fail, and a dictionary of non-critical rules that use warn. You can apply both dictionaries to the same dataset using different decorators. The following example shows how to combine different actions.

```python
# Define critical rules that should cause the pipeline to fail.
critical_rules = {
    "valid_customer_id": "customer_id IS NOT NULL",
    "valid_amount": "amount > 0"
}

# Define warning rules that should only be monitored.
warning_rules = {
    "valid_currency": "currency IN ('USD', 'EUR', 'GBP')",
    "valid_timestamp": "created_at <= current_timestamp()"
}

# Apply the fail action to the critical rules.
@dp.expect_all_or_fail(critical_rules)
# Apply the warn action to the warning rules.
@dp.expect_all(warning_rules)
def validated_payments():
    # Read from the raw_payments source.
    return spark.readStream.table("raw.payments")
```

In this example, the critical rules are checked first because the decorator is applied last? Actually, decorators are applied bottom-up. The order of evaluation of expectations within a record may depend on the engine. But each rule has its own action. If a critical rule fails, the pipeline stops. If a warning rule fails, the record is written and a metric is recorded. This allows you to apply the right level of strictness to each group of rules.

## SQL multiple constraints

In SQL, you separate multiple constraints with commas. Each constraint has a name, an `EXPECT` clause, and an `ON VIOLATION` clause. You can mix actions within the same table definition. The following example creates a streaming table with multiple constraints. Each line is commented.

```sql
-- Create or refresh a streaming table named validated_payments.
CREATE OR REFRESH STREAMING TABLE validated_payments(
    -- The valid_amount constraint checks that amount is greater than zero.
    -- There is no ON VIOLATION clause.
    -- The default action is warn.
    -- Invalid records are written to the target.
    CONSTRAINT valid_amount EXPECT (amount > 0),
    -- The valid_currency constraint checks that currency is one of the allowed values.
    -- ON VIOLATION DROP ROW means invalid records are dropped before write.
    CONSTRAINT valid_currency EXPECT (currency IN ('USD', 'EUR', 'GBP')) ON VIOLATION DROP ROW,
    -- The valid_timestamp constraint checks that created_at is not in the future.
    -- ON VIOLATION FAIL UPDATE means the pipeline stops if any record violates this constraint.
    CONSTRAINT valid_timestamp EXPECT (created_at <= current_timestamp()) ON VIOLATION FAIL UPDATE
) AS SELECT * FROM STREAM(raw_payments);
```

In this example, the `valid_amount` constraint uses the warn action. The `valid_currency` constraint uses the drop action. The `valid_timestamp` constraint uses the fail action. Each constraint is evaluated independently. A record can fail one, two, or all three constraints. The actions are applied according to the `ON VIOLATION` clause for each constraint. If a record fails `valid_amount`, it is still written to the target. If it fails `valid_currency`, it is dropped. If it fails `valid_timestamp`, the pipeline stops. This flexibility allows you to tailor the response to each rule.

## Storing expectations in a Unity Catalog Delta table

The tip in the original text says: In-memory dictionaries are convenient for simple pipelines, but they embed rules inside your notebook. For production workloads where the same rules should apply across multiple pipelines, store expectations in a Unity Catalog Delta table instead. Rules become version-controlled, auditable, and queryable like any other governed asset.

This is an important best practice. When you define rules in a notebook, they are tied to that notebook. If you have multiple pipelines that need the same rules, you have to copy the rules. If you change a rule, you have to change it in every notebook. This is error-prone and hard to maintain. Storing rules in a Delta table solves these problems. You define the rules once. All pipelines read from the same table. When you update a rule, all pipelines pick up the change on their next run. The rules table is a Delta table, so it supports time travel. You can see the history of changes. You can audit who changed what rule and when. You can query the rules using SQL. You can also use the rules table as a single source of truth for data quality across the organization.

The following example shows how you might structure a rules table. Each line is commented.

```sql
-- Create a Delta table to store data quality rules.
CREATE TABLE IF NOT EXISTS governance.data_quality_rules (
    -- The name of the rule.
    rule_name STRING,
    -- The name of the table or dataset that the rule applies to.
    target_table STRING,
    -- The SQL constraint expression.
    constraint_expression STRING,
    -- The action to take when the rule is violated.
    -- Allowed values are 'warn', 'drop', or 'fail'.
    action STRING,
    -- A description of the rule.
    description STRING,
    -- The timestamp when the rule was created.
    created_at TIMESTAMP,
    -- The timestamp when the rule was last updated.
    updated_at TIMESTAMP,
    -- The user who created or last updated the rule.
    updated_by STRING
);
```

You can insert rules into this table. The following example inserts the payment rules.

```sql
-- Insert rules for the payments dataset.
INSERT INTO governance.data_quality_rules VALUES
('valid_amount', 'payments', 'amount > 0', 'warn', 'Amount must be positive', current_timestamp(), current_timestamp(), 'data_engineer'),
('valid_currency', 'payments', 'currency IN (''USD'', ''EUR'', ''GBP'')', 'drop', 'Currency must be one of USD, EUR, GBP', current_timestamp(), current_timestamp(), 'data_engineer'),
('valid_timestamp', 'payments', 'created_at <= current_timestamp()', 'fail', 'Timestamp cannot be in the future', current_timestamp(), current_timestamp(), 'data_engineer');
```

In your pipeline, you can read the rules for the target table and build a dictionary. The following Python code shows how.

```python
# Read the rules for the payments table from the Delta table.
rules_df = spark.read.table("governance.data_quality_rules").filter("target_table = 'payments'")

# Collect the rules into a dictionary.
# The key is the rule name.
# The value is the constraint expression.
payment_rules = {row["rule_name"]: row["constraint_expression"] for row in rules_df.collect()}

# You can also separate rules by action if needed.
# For example, create a dictionary for rules with action 'drop'.
drop_rules = {row["rule_name"]: row["constraint_expression"] for row in rules_df.filter("action = 'drop'").collect()}

# Apply the rules using the appropriate decorator.
# In this example, we apply all rules with the drop action.
@dp.expect_all_or_drop(drop_rules)
def clean_payments():
    return spark.readStream.table("raw.payments")
```

This approach makes your rules version-controlled and auditable. You can use Delta time travel to see previous versions of the rules. You can query the rules table to see which rules apply to which tables. You can update rules without changing code. You can also use the rules table to generate documentation or to build a data quality dashboard.

## Best practices for combining expectations

Use descriptive names for each expectation. A good name describes the rule. For example, `valid_amount` is better than `check1`. Meaningful names make it easier to understand the metrics and diagnose failures.

Group related expectations. If several rules share the same action, group them in a dictionary. This reduces duplication and ensures consistency.

Use consistent actions for related rules. For example, all rules that check for required columns might use the drop action. All rules that check for critical financial constraints might use the fail action.

Store rules externally for production. In-memory dictionaries are fine for simple pipelines, but for production workloads, store rules in a Unity Catalog Delta table. This makes them version-controlled, auditable, and queryable.

Version control your rules. If you store rules in a Delta table, use Delta time travel to track changes. If you store rules in code, store the code in Git.

Test your rules with sample data. Create test cases that cover valid values, invalid values, nulls, empty strings, and boundary values. Verify that each rule behaves as expected.

Monitor your metrics. Set up alerts for unexpected changes. Investigate sudden increases in violations. Use the metrics to improve data quality at the source.

Document your rules. Keep a record of the rules and the reason for each rule. This helps new team members understand the data model. It also helps when you need to modify or remove a rule.

## Common mistakes to avoid

One common mistake is using generic names. Names like `check1` or `test` do not communicate the rule. They make it hard to understand metrics and diagnose failures.

Another common mistake is forgetting null handling. If you use `amount > 0` and amount is null, the record fails. If null is acceptable, you must add `amount IS NULL OR`. If null is not acceptable, you should be explicit.

Another common mistake is using `cast` instead of `try_cast` in constraints. If you use `cast` and the conversion fails, the expression may raise an error, which can fail the pipeline even if you chose `expect_or_drop`. Always use `try_cast` for type validation in constraints.

Another common mistake is using `expect_all_or_fail` for every rule. This can cause frequent pipeline stops. Use `expect_all_or_fail` only for critical rules. Use `expect_all_or_drop` or `expect_all` for less critical rules.

Another common mistake is not monitoring metrics. Expectations produce valuable data quality metrics. If you do not monitor them, you may miss systematic problems. Set up alerts and dashboards.

Another common mistake is not testing expectations. Always test with a variety of values. Test valid values, invalid values, nulls, empty strings, and boundary values. Verify the behavior of each action.

Another common mistake is embedding rules in notebooks without version control. This makes it hard to track changes and to reuse rules across pipelines. Store rules in a Delta table or in version control.
