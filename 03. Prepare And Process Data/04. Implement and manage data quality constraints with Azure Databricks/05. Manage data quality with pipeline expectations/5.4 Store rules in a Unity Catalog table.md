## Store rules in a Unity Catalog table

Centralizing expectations in a Unity Catalog table separates quality rules from pipeline logic. You update or audit rules in one place, and every pipeline that references the table picks up the change automatically. This pattern is a foundational practice for governed data quality at scale. Instead of embedding data quality rules inside notebooks or pipeline code, you store them as data in a Delta table that lives in Unity Catalog. The rules become a governed asset. They have lineage, access control, and audit logs. Teams can review them, update them, and understand their impact without reading pipeline code. Pipelines read the rules at runtime or at pipeline definition time and apply them to the data. This decouples the rules from the code. You can change a rule by updating one row in a table. You do not need to modify or redeploy the pipeline. This reduces risk, speeds up changes, and ensures consistency across multiple pipelines.

## The problem with embedding rules in notebooks

When you define expectations directly in a Python notebook, the rules are embedded in the code. This works for simple pipelines. But it creates several problems as your data estate grows. First, the same rule may be needed in multiple pipelines. You end up copying the rule into every notebook. If the rule changes, you must find and update every copy. This is error-prone. Second, the rules are not visible to people who do not read the notebook. Data stewards, auditors, and business users cannot easily see what rules are applied. Third, the rules are not versioned in a way that is easy to audit. You can use Git for the notebook, but the rules are mixed with transformation logic. Fourth, the rules are not governed by Unity Catalog. They do not have lineage, access control, or audit logs. You cannot easily answer questions like "Which pipelines use this rule?" or "Who changed this rule and when?" Fifth, changing a rule requires a code change and a deployment. This can be slow and risky.

## The solution: a Unity Catalog rules table

A Unity Catalog rules table solves these problems. You create a Delta table in a governed schema. The table contains one row per rule. Each row has a name, a constraint expression, and one or more tags. The tags allow you to group rules by domain, by table, by action, or by any other category. Pipelines read the rules table, filter by tag, and apply the rules to their data. Because the rules table is in Unity Catalog, it benefits from lineage tracking, access control, and audit logs. You can see which pipelines read the rules table. You can control who can edit the rules. You can see the history of changes. You can use Delta time travel to view previous versions. You can query the rules table with SQL. You can join it with other metadata tables. You can build dashboards that show rule coverage and violation trends.

## Creating the rules table

The first step is to create the rules table in a governed schema. The following SQL creates a table named `rules` in the schema `governance.data_quality`. It populates the table with four example rules. Each line is commented.

```sql
-- Create or replace the rules table in the governance.data_quality schema.
-- The CREATE OR REPLACE TABLE statement creates the table if it does not exist.
-- If the table already exists, it replaces it.
-- This is useful for initial setup, but in production you should use CREATE TABLE IF NOT EXISTS and then INSERT or MERGE to update rules.
CREATE OR REPLACE TABLE governance.data_quality.rules AS
-- The SELECT statement defines the columns and the data.
-- The first column is named name.
-- The second column is named constraint.
-- The third column is named tag.
SELECT col1 AS name, col2 AS constraint, col3 AS tag
-- The FROM clause uses a VALUES clause to provide inline data.
-- Each row in the VALUES clause represents one rule.
FROM (
  VALUES
    -- The first rule is named valid_amount.
    -- The constraint is amount > 0.
    -- The tag is financial.
    -- This rule checks that the amount is greater than zero.
    ('valid_amount',    'amount > 0',                              'financial'),
    -- The second rule is named valid_currency.
    -- The constraint is currency IN ('USD', 'EUR', 'GBP').
    -- The tag is financial.
    -- This rule checks that the currency is one of the allowed values.
    -- Note that the single quotes inside the string are escaped by doubling them.
    ('valid_currency',  'currency IN (''USD'', ''EUR'', ''GBP'')',  'financial'),
    -- The third rule is named non_null_email.
    -- The constraint is email IS NOT NULL.
    -- The tag is customer.
    -- This rule checks that the email is not null.
    ('non_null_email',  'email IS NOT NULL',                       'customer'),
    -- The fourth rule is named valid_hire_date.
    -- The constraint is hire_date <= current_date().
    -- The tag is hr.
    -- This rule checks that the hire date is not in the future.
    ('valid_hire_date', 'hire_date <= current_date()',             'hr')
);
```

This table has three columns. The `name` column is the name of the expectation. It should be unique within the table or at least within the tag. The `constraint` column is the SQL Boolean expression. It must be a valid SQL expression that evaluates to true or false. The `tag` column is a label that groups rules. You can use any string for the tag. In this example, the tags are `financial`, `customer`, and `hr`. You can have multiple rules with the same tag. You can also have multiple tags per rule, but that would require a different schema. For simplicity, this example uses a single tag per rule.

## Extending the rules table schema

The example rules table is minimal. In production, you may want to add more columns to capture additional metadata. Consider adding the following columns:

- `action`: The action to take when the rule is violated. Allowed values could be `warn`, `drop`, or `fail`. This allows you to store rules with different actions in the same table.
- `description`: A human-readable description of the rule. This helps users understand the purpose of the rule.
- `created_at`: The timestamp when the rule was created.
- `updated_at`: The timestamp when the rule was last updated.
- `updated_by`: The user who created or last updated the rule.
- `target_table`: The name of the table or dataset that the rule applies to. This is an alternative to tags or can be used in addition to tags.
- `severity`: A severity level such as `low`, `medium`, `high`, or `critical`. This helps prioritize violations.
- `enabled`: A Boolean flag that indicates whether the rule is currently active. This allows you to disable a rule without deleting it.

The following SQL shows how to create a more comprehensive rules table. Each line is commented.

```sql
-- Create a comprehensive rules table.
CREATE TABLE IF NOT EXISTS governance.data_quality.rules (
    -- The name of the rule.
    name STRING NOT NULL,
    -- The SQL constraint expression.
    constraint STRING NOT NULL,
    -- The tag or tags for grouping. In this example, a single tag.
    tag STRING NOT NULL,
    -- The action to take when the rule is violated.
    -- Allowed values are 'warn', 'drop', or 'fail'.
    action STRING NOT NULL DEFAULT 'warn',
    -- A description of the rule.
    description STRING,
    -- The severity level of the rule.
    severity STRING,
    -- Whether the rule is enabled.
    enabled BOOLEAN NOT NULL DEFAULT true,
    -- The timestamp when the rule was created.
    created_at TIMESTAMP NOT NULL DEFAULT current_timestamp(),
    -- The timestamp when the rule was last updated.
    updated_at TIMESTAMP NOT NULL DEFAULT current_timestamp(),
    -- The user who last updated the rule.
    updated_by STRING
);
```

You can then insert rules using INSERT statements. The following example inserts the same four rules with additional metadata.

```sql
-- Insert rules into the comprehensive rules table.
INSERT INTO governance.data_quality.rules
(name, constraint, tag, action, description, severity, enabled)
VALUES
('valid_amount', 'amount > 0', 'financial', 'drop', 'Amount must be positive', 'high', true),
('valid_currency', 'currency IN (''USD'', ''EUR'', ''GBP'')', 'financial', 'drop', 'Currency must be one of USD, EUR, GBP', 'medium', true),
('non_null_email', 'email IS NOT NULL', 'customer', 'warn', 'Email must not be null', 'medium', true),
('valid_hire_date', 'hire_date <= current_date()', 'hr', 'fail', 'Hire date cannot be in the future', 'critical', true);
```

This richer schema allows you to store rules with different actions and to filter by action, severity, or enabled status. You can also track who changed a rule and when.

## Defining the get_rules helper function

Once the rules table exists, you need a way to read the rules and apply them to your pipeline. The following Python code defines a helper function named `get_rules`. It reads the rules table, filters by tag, and returns a dictionary that maps rule names to constraint expressions. Each line is commented.

```python
# Import the pipelines module from pyspark.
from pyspark import pipelines as dp
# Import the col function for column references.
from pyspark.sql.functions import col

# Define a helper function that reads rules filtered by tag.
# The function takes a single argument, tag, which is a string.
# It returns a dictionary where keys are rule names and values are constraint expressions.
def get_rules(tag):
    # Read the rules table from Unity Catalog.
    # The table is governance.data_quality.rules.
    # spark.read.table reads the table as a DataFrame.
    df = spark.read.table("governance.data_quality.rules")
    # Filter the DataFrame to keep only rows where the tag column equals the given tag.
    # The col function references the tag column.
    # The == operator compares the column value to the tag.
    df = df.filter(col("tag") == tag)
    # Collect the filtered rows into a list on the driver.
    # The collect method brings the data to the driver node.
    # This is acceptable because the rules table is small.
    # If the rules table is large, you should not collect it.
    # Instead, you should join it with your data or use a broadcast join.
    rows = df.collect()
    # Build a dictionary from the rows.
    # The dictionary comprehension iterates over each row.
    # The key is the value of the name column.
    # The value is the value of the constraint column.
    return {row["name"]: row["constraint"] for row in rows}
```

This function is simple. It reads the entire rules table, filters by tag, and collects the results. Because the rules table is typically small, collecting the results is fine. If you have thousands of rules, you might want to filter more selectively or cache the rules. You can also add a filter for `enabled = true` if you have an enabled column. The following example shows an enhanced version.

```python
def get_rules(tag):
    # Read the rules table.
    df = spark.read.table("governance.data_quality.rules")
    # Filter by tag and enabled status.
    df = df.filter((col("tag") == tag) & (col("enabled") == True))
    # Collect the rows.
    rows = df.collect()
    # Return the dictionary.
    return {row["name"]: row["constraint"] for row in rows}
```

You can also return the action along with the constraint if you want to apply different actions to different rules. The following example returns a dictionary of dictionaries.

```python
def get_rules_with_actions(tag):
    # Read the rules table.
    df = spark.read.table("governance.data_quality.rules")
    # Filter by tag and enabled status.
    df = df.filter((col("tag") == tag) & (col("enabled") == True))
    # Collect the rows.
    rows = df.collect()
    # Build a dictionary where each key is a rule name and each value is a dictionary with constraint and action.
    return {row["name"]: {"constraint": row["constraint"], "action": row["action"]} for row in rows}
```

This allows you to separate rules by action and apply different decorators. We will show an example later.

## Using get_rules with pipeline decorators

Once you have the `get_rules` function, you can use it with the `expect_all`, `expect_all_or_drop`, and `expect_all_or_fail` decorators. These decorators accept a dictionary of rules and apply the same action to all rules in the dictionary. The following example defines two streaming tables. The first table applies financial rules with the drop action. The second table applies customer rules with the drop action. Each line is commented.

```python
# The @dp.table decorator defines a streaming table.
@dp.table
# The @dp.expect_all_or_drop decorator applies the drop action to all rules returned by get_rules("financial").
# The get_rules function reads the rules table and returns a dictionary.
# The decorator expects a dictionary where keys are rule names and values are constraint expressions.
# If any record fails any rule, the record is dropped before write.
# The pipeline continues processing other records.
# The drop count is recorded for each rule in the data quality metrics.
@dp.expect_all_or_drop(get_rules("financial"))
def validated_payments():
    # Read from the raw payments source.
    # The returned DataFrame is the input to the dataset.
    # All financial rules are evaluated for each record.
    return spark.readStream.table("raw.payments")

# The @dp.table decorator defines another streaming table.
@dp.table
# The @dp.expect_all_or_drop decorator applies the drop action to all customer rules.
@dp.expect_all_or_drop(get_rules("customer"))
def validated_customers():
    # Read from the raw customers source.
    # The returned DataFrame is the input to the dataset.
    # All customer rules are evaluated for each record.
    return spark.readStream.table("raw.customers")
```

In this example, the `get_rules` function is called when the pipeline is defined. It reads the current rules from the Unity Catalog table. The decorators are applied to the functions. When the pipeline runs, the rules are applied to each record. If you update the rules table, the pipeline will pick up the new rules the next time it is started or updated. You do not need to change the pipeline code. You only need to update the rules table and restart the pipeline or wait for the next scheduled run.

## Applying different actions to different rules

If you have rules with different actions in the same tag, you can separate them. The following example reads rules with actions and applies different decorators based on the action. Each line is commented.

```python
# Define a function that reads rules with actions and returns a dictionary.
def get_rules_with_actions(tag):
    df = spark.read.table("governance.data_quality.rules")
    df = df.filter((col("tag") == tag) & (col("enabled") == True))
    rows = df.collect()
    return {row["name"]: {"constraint": row["constraint"], "action": row["action"]} for row in rows}

# Read the rules for the financial tag.
financial_rules = get_rules_with_actions("financial")

# Separate the rules into dictionaries by action.
warn_rules = {name: rule["constraint"] for name, rule in financial_rules.items() if rule["action"] == "warn"}
drop_rules = {name: rule["constraint"] for name, rule in financial_rules.items() if rule["action"] == "drop"}
fail_rules = {name: rule["constraint"] for name, rule in financial_rules.items() if rule["action"] == "fail"}

# Apply the warn action to warn rules.
@dp.expect_all(warn_rules)
# Apply the drop action to drop rules.
@dp.expect_all_or_drop(drop_rules)
# Apply the fail action to fail rules.
@dp.expect_all_or_fail(fail_rules)
def validated_payments_with_actions():
    return spark.readStream.table("raw.payments")
```

This pattern gives you full control. You can store all rules in one table and apply the correct action to each rule. The rules table becomes the single source of truth for data quality.

## Benefits of Unity Catalog governance

Because the rules table lives in Unity Catalog, it benefits from lineage tracking, access control, and audit logs alongside your data tables. Lineage tracking shows which pipelines read the rules table and which tables are affected by the rules. You can see the flow of data and rules through your pipeline. Access control allows you to restrict who can edit the rules. You can grant read access to pipeline service principals and write access to data stewards. Audit logs record every change to the rules table. You can see who changed what rule and when. This is essential for compliance and governance.

Teams can update a constraint by editing one row in the rules table, without touching any pipeline notebook. This is a major operational advantage. It means that data stewards can manage data quality rules without needing to know Python or SQL pipeline code. It means that changes can be reviewed and approved through a data governance process. It means that changes are auditable. It means that you can roll back a rule change using Delta time travel if something goes wrong.

## Version control and time travel

Delta Lake supports time travel. You can query previous versions of the rules table. This is useful for auditing and rollback. The following SQL shows how to view the history of the rules table.

```sql
-- View the history of the rules table.
-- The history includes all operations such as CREATE, INSERT, UPDATE, and DELETE.
-- You can see when each operation occurred and who performed it.
DESCRIBE HISTORY governance.data_quality.rules;
```

You can query a specific version of the rules table. The following SQL shows how to query version 1.

```sql
-- Query the rules table as of version 1.
SELECT * FROM governance.data_quality.rules VERSION AS OF 1;
```

You can also query as of a timestamp.

```sql
-- Query the rules table as of a specific timestamp.
SELECT * FROM governance.data_quality.rules TIMESTAMP AS OF '2026-01-15 10:00:00';
```

This allows you to see what the rules were at any point in time. If a rule change causes problems, you can revert to a previous version or update the rule to a previous definition.

## Testing rules in development

You should test rules in a development environment before applying them to production. You can create separate rules tables for development and production. For example, you might have `governance.data_quality.rules_dev` and `governance.data_quality.rules_prod`. You can use a parameter or environment variable to select the correct table. The following Python code shows how.

```python
import os

# Determine the environment.
env = os.getenv("ENV", "dev")

# Select the rules table based on the environment.
if env == "prod":
    rules_table = "governance.data_quality.rules_prod"
else:
    rules_table = "governance.data_quality.rules_dev"

def get_rules(tag):
    df = spark.read.table(rules_table).filter(col("tag") == tag)
    rows = df.collect()
    return {row["name"]: row["constraint"] for row in rows}
```

This allows you to test new rules in development without affecting production. You can also use tags to stage rules. For example, you might add a `stage` tag to rules that are being tested. The development pipeline reads rules with the `stage` tag. The production pipeline reads rules with the `prod` tag. After testing, you change the tag to `prod`.

## SQL equivalent for static constraints

The original text includes a SQL example that creates a streaming table with hardcoded constraints. This is an alternative approach. It does not read from the Unity Catalog rules table. It embeds the constraints directly in the table definition. The following SQL is from the original text. Each line is commented.

```sql
-- Create or refresh a streaming table named validated_payments.
CREATE OR REFRESH STREAMING TABLE validated_payments(
    -- The valid_amount constraint checks that amount is greater than zero.
    -- There is no ON VIOLATION clause, so the default action is warn.
    CONSTRAINT valid_amount EXPECT (amount > 0),
    -- The valid_currency constraint checks that currency is one of the allowed values.
    -- There is no ON VIOLATION clause, so the default action is warn.
    CONSTRAINT valid_currency EXPECT (currency IN ('USD', 'EUR', 'GBP')),
    -- The valid_timestamp constraint checks that created_at is not in the future.
    -- There is no ON VIOLATION clause, so the default action is warn.
    CONSTRAINT valid_timestamp EXPECT (created_at <= current_timestamp())
) AS SELECT * FROM STREAM(raw.payments);
```

This approach is simple and works well for small pipelines. However, it does not benefit from centralization. The rules are embedded in the SQL. If you need to change a rule, you must edit the SQL and redeploy the pipeline. If you have multiple pipelines with the same rules, you must update each one. The Unity Catalog rules table approach is more scalable and more governable. It is recommended for production workloads where rules are shared across multiple pipelines and where governance is important.

## Best practices for storing rules in Unity Catalog

Use a dedicated schema for data quality rules. For example, `governance.data_quality`. This makes it easy to find and manage rules.

Use descriptive names for rules. A good name describes the rule. For example, `valid_amount` is better than `check1`.

Use tags to group rules. Tags can represent domains, tables, actions, or any other category. Use consistent tag names.

Store the action in the rules table if you have rules with different actions. This allows you to apply the correct action without changing code.

Store metadata such as description, severity, and owner. This helps users understand the purpose of the rule and who to contact.

Use `enabled` flag to disable rules without deleting them. This is useful for testing or for temporarily disabling a rule.

Version control the rules table using Delta time travel. You can also export the rules to Git for additional version control.

Control access to the rules table. Only authorized users should be able to edit rules. Pipeline service principals should have read access.

Monitor the rules table. Set up alerts when rules are added, removed, or changed. This helps you understand the impact of changes.

Test rules in development before applying them to production. Use separate tables or tags for development and production.

Document the rules table schema and the tags. This helps new team members understand how to use the rules table.

## Common pitfalls

One common pitfall is collecting too much data from the rules table. If the rules table is very large, collecting it to the driver can cause memory issues. Keep the rules table small. If you need many rules, consider filtering more selectively or using a broadcast join.

Another pitfall is not caching the rules. If the pipeline reads the rules table multiple times, it may be inefficient. Consider caching the rules DataFrame if it is used multiple times.

Another pitfall is not handling rule changes gracefully. If a rule is changed while a pipeline is running, the pipeline may not pick up the change until it is restarted. Plan for restarts when rules change.

Another pitfall is not testing rule changes. Always test new or modified rules in development before applying them to production. A bad rule can drop or fail many records.

Another pitfall is not monitoring rule violations. If you do not monitor the metrics, you may miss systematic problems. Set up alerts and dashboards.

Another pitfall is using generic names or tags. Generic names make it hard to understand metrics. Generic tags make it hard to filter rules.

Another pitfall is not documenting the rules. Without documentation, users may not understand why a rule exists or what it does.
