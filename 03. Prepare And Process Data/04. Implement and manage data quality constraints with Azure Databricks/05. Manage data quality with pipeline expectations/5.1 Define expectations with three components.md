## Define expectations with three components

Every expectation consists of three parts: a name, a constraint, and an action. Understanding these components helps you design effective data quality checks. The diagram referenced in the original text illustrates these three components. Typically, the diagram shows a box labeled "Expectation" with three sub-parts: Name, Constraint, Action. The name identifies the expectation. The constraint is the Boolean expression that determines whether a record passes or fails. The action is what happens when a record violates the constraint. By understanding each component, you can create expectations that are clear, maintainable, and aligned with your data quality goals.

Expectations are a core feature of Lakeflow Spark Declarative Pipelines. They allow you to define data quality rules directly in your pipeline definitions. They are evaluated as data flows through the pipeline. They produce metrics that you can view in the pipeline UI. They can warn, drop, or fail depending on the action you choose. They can be defined in Python using decorators such as `@dp.expect`, `@dp.expect_or_drop`, and `@dp.expect_or_fail`. They can also be defined in SQL using constraints with `EXPECT` and `ON VIOLATION` clauses. The three components are present in both Python and SQL definitions.

## The name component

The name identifies the expectation and appears in monitoring dashboards. Choose names that clearly describe what you are validating. For example, `valid_customer_age` communicates the rule's purpose better than `check_1`. The name is used in metrics, logs, error messages, and the pipeline UI. A good name makes it easy to understand what the expectation does without reading the constraint expression. It also makes it easy to search for the expectation in code and in monitoring tools.

When you define an expectation in Python, the name is the first argument to the decorator. For example, in `@dp.expect("valid_customer_age", "age BETWEEN 0 AND 150")`, the name is `"valid_customer_age"`. In SQL, the name is specified after the `CONSTRAINT` keyword. For example, `CONSTRAINT valid_customer_age EXPECT (age BETWEEN 0 AND 150)`. The name should be unique within the dataset. If you have multiple expectations, each should have a distinct name. This allows you to track them separately in metrics and to identify which expectation failed when a violation occurs.

### Characteristics of good names

A good name is descriptive. It tells you what column or columns are being checked and what rule is being applied. For example, `valid_customer_age` tells you that the rule is about customer age and that the age must be valid. `non_null_email` tells you that the email must not be null. `positive_transaction_amount` tells you that the transaction amount must be positive. `valid_date_range` tells you that a date must fall within a valid range.

A good name is consistent. Use the same naming conventions across all expectations. For example, use snake_case for names. Start with a prefix that indicates the type of check, such as `valid_`, `non_null_`, `positive_`, `unique_`, `in_range_`. Then include the column name. For example, `valid_customer_age`, `non_null_email`, `positive_amount`, `unique_order_id`, `in_range_discount_percent`. This makes names predictable and easy to understand.

A good name is concise but not too short. Avoid single-letter names or generic names like `check1`, `test`, `expectation1`. Avoid names that are so long that they are hard to read. A name like `valid_customer_age_between_zero_and_one_hundred_fifty` is too long. A name like `valid_age` is better. A name like `age_check` is acceptable but less descriptive than `valid_age`.

A good name avoids special characters. Use only letters, numbers, and underscores. Avoid spaces, hyphens, and punctuation. This ensures that the name works well in SQL, in metrics, and in URLs.

A good name is stable. Once you choose a name, avoid changing it. Changing a name can break monitoring dashboards, alerts, and historical comparisons. If you must change a name, treat it as a breaking change and update all references.

### Examples of good and bad names

Good names:

- `valid_customer_age`
- `non_null_email`
- `positive_transaction_amount`
- `valid_hire_date`
- `in_range_discount_percent`
- `unique_order_id`
- `valid_phone_number_format`
- `valid_account_balance`

Bad names:

- `check1`
- `test`
- `expectation`
- `rule`
- `age`
- `email_check`
- `amount_positive_or_zero`
- `valid_customer_age_between_zero_and_one_hundred_fifty`

The bad names are either too generic, too vague, or too long. They do not clearly communicate the rule. They may be confusing when viewed in a dashboard.

### How names appear in monitoring

In the pipeline UI, expectation names appear in the Data quality tab. You can see the number of records that passed, failed, were dropped, or caused a failure for each expectation. You can also see pass rates over time. If you use a descriptive name, you can immediately understand which rule is being violated. If you use a generic name, you have to look up the constraint to understand what it does.

In logs and error messages, the expectation name is included when a violation occurs. For example, if a record fails the `valid_customer_age` expectation, the error message might say "Expectation valid_customer_age violated". This helps you quickly identify the problem.

In alerts, you can configure notifications based on specific expectation names. For example, you can set up an alert that triggers when the `valid_customer_age` expectation has a pass rate below 99 percent. This allows you to focus on the most important rules.

## The constraint component

The constraint is a SQL Boolean expression that evaluates to true or false for each record. When a record fails the constraint, the expectation triggers. You can use any valid SQL syntax except custom Python functions, external service calls, or subqueries. The constraint is the heart of the expectation. It defines the rule that you want to enforce. It must be deterministic and efficient because it is evaluated for every record.

### What SQL syntax is allowed

You can use any valid SQL expression that returns a Boolean value. This includes comparison operators such as `=`, `!=`, `<>`, `>`, `>=`, `<`, `<=`. It includes logical operators such as `AND`, `OR`, `NOT`. It includes the `BETWEEN` clause, the `IN` clause, the `LIKE` clause, and the `REGEXP` operator. It includes functions such as `current_date()`, `current_timestamp()`, `try_cast`, `try_to_date`, `try_to_timestamp`, `trim`, `nullif`, `coalesce`, `length`, `substring`, `upper`, `lower`, `abs`, `round`, `floor`, `ceil`. It includes `CASE` expressions. It includes arithmetic operations such as `+`, `-`, `*`, `/`. It includes string concatenation with `||`. It includes date arithmetic such as `date_add`, `date_sub`, `datediff`, `months_between`. It includes any other built-in SQL function that is available in the execution engine.

### What is not allowed

You cannot use custom Python functions. This means you cannot define a Python function and call it from the constraint. You cannot use external service calls. This means you cannot call an API or a web service from the constraint. You cannot use subqueries. This means you cannot write a `SELECT` statement inside the constraint. These restrictions exist for several reasons.

Custom Python functions would require serialization and would break the declarative model. They would also be slower because they cannot be optimized by the query engine. External service calls would introduce non-determinism and would be very slow. They would also make the pipeline dependent on external systems, which is undesirable. Subqueries would require additional data scans and could cause performance issues. They would also make the constraint dependent on other tables, which complicates the pipeline logic. By restricting constraints to simple SQL expressions, the engine can evaluate them efficiently and deterministically.

### Examples of constraints

Here is a simple constraint that checks that a transaction date falls within an expected range. The constraint uses comparison operators and the `current_date()` function.

```
@dp.expect("valid_transaction_date", "transaction_date >= '2020-01-01' AND transaction_date <= current_date()")
```

The same constraint in SQL:

```
CONSTRAINT valid_transaction_date EXPECT (transaction_date >= '2020-01-01' AND transaction_date <= current_date())
```

This constraint checks that the transaction date is on or after January 1, 2020, and on or before today. If the transaction date is before 2020 or in the future, the record fails the constraint.

Here is a constraint that checks that an age is between 0 and 150 inclusive. The constraint uses the `BETWEEN` clause.

```
@dp.expect("valid_customer_age", "age BETWEEN 0 AND 150")
```

The same constraint in SQL:

```
CONSTRAINT valid_customer_age EXPECT (age BETWEEN 0 AND 150)
```

The `BETWEEN` clause is inclusive, so 0 and 150 are valid. If age is -1 or 151, the record fails.

Here is a constraint that checks that an email is not null and contains an at sign. The constraint uses `IS NOT NULL` and `LIKE`.

```
@dp.expect("valid_email", "email IS NOT NULL AND email LIKE '%@%'")
```

The same constraint in SQL:

```
CONSTRAINT valid_email EXPECT (email IS NOT NULL AND email LIKE '%@%')
```

This constraint checks that the email is not null and that it contains an at sign. If the email is null or does not contain an at sign, the record fails.

Here is a constraint that checks that an amount can be cast to a decimal with ten total digits and two decimal places. The constraint uses `try_cast`.

```
@dp.expect("valid_amount", "try_cast(amount AS DECIMAL(10,2)) IS NOT NULL")
```

The same constraint in SQL:

```
CONSTRAINT valid_amount EXPECT (try_cast(amount AS DECIMAL(10,2)) IS NOT NULL)
```

This constraint attempts to convert the amount to `DECIMAL(10,2)`. If the conversion succeeds, `try_cast` returns a non-null value. The expression `try_cast(...) IS NOT NULL` evaluates to true. If the conversion fails, `try_cast` returns null. The expression evaluates to false, so the record fails.

Here is a constraint that combines multiple conditions. It checks that a discount percent is between 0 and 100, and that if it is over 50, the customer tier is premium. The constraint uses `AND`, `OR`, and `BETWEEN`.

```
@dp.expect("valid_discount", """
    discount_percent >= 0 
    AND discount_percent <= 100
    AND (discount_percent <= 50 OR customer_tier = 'PREMIUM')
""")
```

The same constraint in SQL:

```
CONSTRAINT valid_discount EXPECT (
    discount_percent >= 0 
    AND discount_percent <= 100
    AND (discount_percent <= 50 OR customer_tier = 'PREMIUM')
)
```

This constraint ensures that discounts stay within bounds and enforces that only premium customers receive discounts over 50 percent. If a non-premium customer has a discount over 50, the record fails.

### Null handling in constraints

Null handling is a common source of confusion. In SQL, a comparison with null returns unknown. For example, `age > 0` returns unknown if age is null. In many systems, unknown is treated as not true, so the record fails the constraint. If you want to allow null values, you must write the constraint explicitly. For example, if you want to allow null ages but require non-null ages to be between 0 and 150, you can write:

```
age IS NULL OR age BETWEEN 0 AND 150
```

This expression evaluates to true when age is null. It also evaluates to true when age is between 0 and 150. It evaluates to false only when age is not null and outside the range.

Similarly, if you use `try_cast` and you want to allow null values, you can write:

```
amount IS NULL OR try_cast(amount AS DECIMAL(10,2)) IS NOT NULL
```

This allows null amounts but rejects non-null amounts that cannot be cast.

If you want to reject null values, you can use `IS NOT NULL` without the `IS NULL` condition. For example:

```
amount IS NOT NULL AND try_cast(amount AS DECIMAL(10,2)) IS NOT NULL
```

This rejects null amounts and non-null amounts that cannot be cast.

### Performance considerations for constraints

Constraints are evaluated for every record. Therefore, they should be as efficient as possible. Keep the expressions simple. Avoid complex regular expressions if a simpler check will do. Avoid repeated casts. If you need to use `try_cast` multiple times, consider creating an intermediate table that performs the cast once, and then apply expectations to the casted column. This reduces the number of times the conversion is attempted.

Avoid using functions that are expensive, such as `regexp_extract` on very long strings, or `from_json` on large JSON documents. If you must use them, test the performance with realistic data volumes.

Avoid subqueries and external calls. They are not allowed, but even if they were, they would be very slow.

Use built-in functions that are optimized by the query engine. For example, `current_date()` is very fast. `try_cast` is also fast for simple types.

If a constraint is complex, consider breaking it into multiple expectations. This makes the logic clearer and allows you to monitor each rule separately. It also allows the engine to short-circuit evaluation if one condition fails.

### Testing constraints

You should test your constraints with a variety of values. Create sample data that includes valid values, invalid values, null values, empty strings, and boundary values. For example, if your constraint is `age BETWEEN 0 AND 150`, test ages of -1, 0, 1, 149, 150, 151, and null. Verify that the expectation passes for 0 through 150 and fails for -1, 151, and null (unless null is allowed).

You can test constraints using SQL queries. For example, you can run `SELECT age BETWEEN 0 AND 150` on a set of test values and check the results. You can also write unit tests in your pipeline testing framework.

## The action component

The action determines what happens when a record violates the constraint. You have three options, each suited to different scenarios in your data pipeline. The three options are warn, drop, and fail.

### Warn action

The warn action logs the violation but keeps the record. The record is written to the target table. Metrics record the violation. This is the default action in many systems. In Python, you use `@dp.expect`. In SQL, you omit the `ON VIOLATION` clause.

The warn action is useful when you need visibility into data quality issues without blocking data flow. It is often used during initial data quality assessment, when you are not yet sure how widespread a problem is, or when the downstream consumers can tolerate some invalid records. For example, a missing phone number might be acceptable for some customers. You still want to know how many records are missing a phone number, but you do not want to drop those records or fail the pipeline. Warn gives you the ability to measure the problem and decide later whether to escalate to drop or fail.

Here is a Python example of a warn expectation:

```python
# The @dp.expect decorator attaches a warn expectation to the dataset.
# The first argument is the expectation name.
# The second argument is the SQL expression that must be true for the record to pass.
@dp.expect("has_phone", "phone_number IS NOT NULL")
# has_phone is the name of the expectation.
# The expression phone_number IS NOT NULL checks that the phone number is not null.
# If the expression is true, the record passes.
# If the expression is false or unknown, the record fails the expectation.
# Because this is @dp.expect, the record is still written to the target.
# The failure is recorded in the data quality metrics.
# The pipeline does not stop.
def customers():
    return spark.readStream.table("raw.customers")
```

Here is the same expectation in SQL:

```sql
CREATE OR REFRESH STREAMING TABLE customers(
    -- The has_phone constraint checks that phone_number is not null.
    -- There is no ON VIOLATION clause.
    -- Without an ON VIOLATION clause, the default behavior is to warn.
    -- Invalid records are written to the target.
    -- Violation metrics are recorded.
    CONSTRAINT has_phone EXPECT (phone_number IS NOT NULL)
) AS SELECT * FROM STREAM(raw.customers);
```

### Drop action

The drop action removes the invalid record before it is written to the target. The pipeline continues processing. The dropped record is not written to the target. Metrics record how many records were dropped. In Python, you use `@dp.expect_or_drop`. In SQL, you use `ON VIOLATION DROP ROW`.

The drop action is useful for data cleansing. It ensures that only valid records reach downstream consumers. It is often used when invalid records are not useful and can be safely discarded. For example, if an address is required for shipping, you might drop records that are missing a street or city. Those records cannot be used for shipping, so there is no point in writing them to the target. Dropping them keeps the target clean and prevents downstream errors.

Here is a Python example of a drop expectation:

```python
# The @dp.expect_or_drop decorator attaches an expectation that drops invalid rows.
@dp.expect_or_drop("complete_address", "street IS NOT NULL AND city IS NOT NULL")
# complete_address is the name of the expectation.
# The expression requires both street and city to be non-null.
# If either street or city is null, the record fails the expectation.
# Because this is @dp.expect_or_drop, the invalid record is removed before write.
# The pipeline continues processing other records.
# The drop count is recorded in the data quality metrics.
def customers():
    return spark.readStream.table("raw.customers")
```

Here is the same expectation in SQL:

```sql
CREATE OR REFRESH STREAMING TABLE customers(
    -- The complete_address constraint checks that street and city are both not null.
    -- ON VIOLATION DROP ROW means invalid records are removed before write.
    -- The pipeline continues.
    -- Dropped records are counted in the data quality metrics.
    CONSTRAINT complete_address EXPECT (street IS NOT NULL AND city IS NOT NULL) ON VIOLATION DROP ROW
) AS SELECT * FROM STREAM(raw.customers);
```

### Fail action

The fail action stops the pipeline when a validation fails. The current transaction rolls back. No records from the current update are written to the target. In Python, you use `@dp.expect_or_fail`. In SQL, you use `ON VIOLATION FAIL UPDATE`.

The fail action is useful when data integrity is critical and invalid records are unacceptable. It ensures that bad data does not reach downstream consumers. It also forces you to fix the problem before the pipeline can continue. For example, a negative account balance might indicate a bug in a financial system, a fraud attempt, or a data corruption issue. Writing that record to the target could cause incorrect balances, failed payments, or regulatory violations. Failing the pipeline prevents the bad data from spreading. It also alerts the team that something is wrong.

Here is a Python example of a fail expectation:

```python
# The @dp.expect_or_fail decorator attaches an expectation that fails the pipeline.
@dp.expect_or_fail("valid_account_balance", "balance >= 0")
# valid_account_balance is the name of the expectation.
# The expression requires balance to be zero or positive.
# If any record has a negative balance, the expectation fails.
# Because this is @dp.expect_or_fail, the pipeline stops.
# The current transaction rolls back.
# No records from the current update are written to the target.
def accounts():
    return spark.readStream.table("raw.accounts")
```

Here is the same expectation in SQL:

```sql
CREATE OR REFRESH STREAMING TABLE accounts(
    -- The valid_account_balance constraint checks that balance is zero or positive.
    -- ON VIOLATION FAIL UPDATE means the pipeline stops if any record violates the constraint.
    -- The current transaction rolls back.
    -- No records from the current update are written to the target.
    CONSTRAINT valid_account_balance EXPECT (balance >= 0) ON VIOLATION FAIL UPDATE
) AS SELECT * FROM STREAM(raw.accounts);
```

### Choosing the right action

Choosing the right action depends on several factors. Consider the criticality of the data. If invalid data can cause financial loss, regulatory violations, safety issues, or serious operational problems, use fail. If invalid data is inconvenient but not dangerous, use drop or warn. Consider the volume and pattern of invalid records. If invalid records are rare and isolated, drop may be sufficient. If invalid records are frequent and indicate a systemic issue, fail may be necessary to force a fix. If you are still investigating the problem, warn allows you to collect data without blocking the pipeline. Consider the tolerance of downstream consumers. If downstream systems can handle nulls or missing values, warn may be acceptable. If downstream systems require complete records, drop or fail may be necessary. Consider your ability to recover. If you can easily reprocess data after a failure, fail may be acceptable. If reprocessing is difficult or expensive, drop may be better because it allows the pipeline to continue. Consider compliance and audit requirements. If you must retain all records for auditing, do not drop them. Use warn and quarantine instead.

### Combining actions

You can combine actions across different expectations in the same dataset. For example, you might warn on a missing phone number, drop rows with an incomplete address, and fail on a negative account balance. This allows you to apply the right level of strictness to each rule. Here is a SQL example that combines all three actions:

```sql
CREATE OR REFRESH STREAMING TABLE customers(
    -- Warn: no ON VIOLATION clause.
    CONSTRAINT has_phone EXPECT (phone_number IS NOT NULL),
    -- Drop: invalid rows are removed before write.
    CONSTRAINT complete_address EXPECT (street IS NOT NULL AND city IS NOT NULL) ON VIOLATION DROP ROW,
    -- Fail: pipeline stops if any balance is negative.
    CONSTRAINT valid_account_balance EXPECT (balance >= 0) ON VIOLATION FAIL UPDATE
) AS SELECT * FROM STREAM(raw.customers);
```

This example shows that you can mix actions in the same dataset. Each constraint has its own behavior.

### Quarantine as an alternative

Another pattern is to route invalid records to a separate quarantine table while allowing valid records to proceed. This is not one of the three built-in actions, but you can implement it using filters. The following Python example shows how to create two tables: one for valid records and one for quarantine records.

```python
from pyspark import pipelines as dp

@dp.table
def valid_transactions():
    return (
        spark.readStream.table("raw_transactions")
        .filter("amount IS NOT NULL AND transaction_date IS NOT NULL")
    )

@dp.table
def quarantine_transactions():
    return (
        spark.readStream.table("raw_transactions")
        .filter("amount IS NULL OR transaction_date IS NULL")
    )
```

This pattern lets you investigate problematic records without blocking your main data flow. You can add a reason column and a timestamp to the quarantine table for better analysis.

## Monitoring and metrics

Expectations produce metrics that you can view in the pipeline UI. Select a dataset with expectations and open the Data quality tab. The metrics show how many records passed, how many failed, how many were dropped, and how many were warned. You can also see pass rates over time. These metrics help you monitor validation pass rates and identify systematic data quality issues. You can set up alerts when violation counts exceed a threshold. For example, if the drop count for `valid_amount` suddenly increases, investigate the source system. If the pass rate falls below a certain percentage, consider whether the rule is too strict or whether the source data has a problem. You can also query the pipeline event log for custom monitoring and reporting.

## Best practices for defining expectations

Use descriptive names. A good name describes the rule. For example, `valid_customer_age` is better than `check1`. Meaningful names make it easier to understand the metrics and diagnose failures.

Keep constraints simple. Simple constraints are easier to understand and faster to evaluate. Avoid complex regular expressions and repeated casts. If you need complex logic, consider breaking it into multiple expectations or using an intermediate table.

Handle nulls explicitly. Decide whether null is acceptable for each column. If null is acceptable, add an `IS NULL` condition. If null is not acceptable, use `IS NOT NULL` without the `IS NULL` condition.

Test your expectations. Create sample data with valid values, invalid values, nulls, empty strings, and boundary values. Verify that valid records pass and invalid records are handled correctly. Test each action: warn, drop, and fail.

Monitor your metrics. Set up alerts for unexpected changes. Investigate sudden increases in violations. Use the metrics to improve data quality at the source.

Document your expectations. Keep a record of the rules and the reason for each rule. This helps new team members understand the data model. It also helps when you need to modify or remove an expectation.

Use a bronze, silver, and quarantine architecture. The bronze layer stores raw data. The silver layer stores cleaned data. The quarantine layer stores invalid records. This pattern separates concerns and makes it easier to manage data quality.

## Common mistakes to avoid

One common mistake is using generic names. Names like `check1` or `test` do not communicate the rule. They make it hard to understand metrics and diagnose failures.

Another common mistake is forgetting null handling. If you use `age BETWEEN 0 AND 150` and age is null, the record fails. If null is acceptable, you must add `age IS NULL OR`. If null is not acceptable, you should be explicit.

Another common mistake is using `cast` instead of `try_cast` in constraints. If you use `cast` and the conversion fails, the expression may raise an error, which can fail the pipeline even if you chose `expect_or_drop`. Always use `try_cast` for type validation in constraints.

Another common mistake is using `expect_or_fail` for every rule. This can cause frequent pipeline stops. Use `expect_or_fail` only for critical rules. Use `expect_or_drop` or `expect` for less critical rules.

Another common mistake is not monitoring metrics. Expectations produce valuable data quality metrics. If you do not monitor them, you may miss systematic problems. Set up alerts and dashboards.

Another common mistake is not testing expectations. Always test with a variety of values. Test valid values, invalid values, nulls, empty strings, and boundary values. Verify the behavior of each action.

Every expectation consists of three parts: a name, a constraint, and an action. The name identifies the expectation and appears in monitoring dashboards. Choose names that clearly describe what you are validating. The constraint is a SQL Boolean expression that evaluates to true or false for each record. When a record fails the constraint, the expectation triggers. You can use any valid SQL syntax except custom Python functions, external service calls, or subqueries. The action determines what happens when a record violates the constraint. You have three options: warn, drop, and fail. Warn logs the violation but keeps the record. Drop removes the invalid record before write. Fail stops the pipeline and rolls back the transaction. Each action suits different scenarios. By following these best practices, you can design effective data quality checks that maintain high data quality in your pipelines.
