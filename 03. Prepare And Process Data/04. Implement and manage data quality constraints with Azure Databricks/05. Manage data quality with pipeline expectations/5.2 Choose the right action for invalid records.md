## Choose the right action for invalid records

Your choice of action depends on how critical the data quality issue is and how you want to handle violations. In Lakeflow Spark Declarative Pipelines, expectations have three actions: warn, drop, and fail. Each action has different behavior, different use cases, and different impact on data quality and pipeline availability. Choosing the right action is both a business and a technical decision. It affects whether invalid records reach downstream consumers, whether the pipeline continues running, and whether you are alerted to problems. This section explains each action in detail, provides commented code examples, and offers guidance on how to choose.

The three actions are defined by the decorator you use in Python or the clause you use in SQL. In Python, `@dp.expect` is the warn action. `@dp.expect_or_drop` is the drop action. `@dp.expect_or_fail` is the fail action. In SQL, the `EXPECT` clause without an `ON VIOLATION` clause is the warn action. `ON VIOLATION DROP ROW` is the drop action. `ON VIOLATION FAIL UPDATE` is the fail action. Each action produces metrics that you can view in the pipeline UI. These metrics show how many records passed, how many failed, how many were dropped, and how many caused a failure. You can use these metrics to monitor data quality and to decide whether your chosen action is appropriate.

## Understanding the three actions

Before choosing an action, it helps to understand what each one does. The warn action writes all records to the target table, including invalid ones. It logs metrics about the failures. The drop action removes invalid records before they are written to the target table. The pipeline continues processing valid records. The fail action stops the pipeline immediately when any record violates the constraint. The current transaction rolls back. No records from the current update are written. The pipeline requires manual intervention to resume.

Each action has tradeoffs. Warn gives you visibility but allows bad data to flow through. Drop keeps the target clean but can hide problems and cause data loss. Fail protects data integrity but can cause frequent pipeline stops and requires manual intervention. The right choice depends on the criticality of the data, the tolerance of downstream consumers, and your ability to recover from failures.

## The warn action

The warn action is the default behavior. It writes all records to the target table, including invalid ones, while logging metrics about failures. This approach works well when you are establishing baselines or when downstream systems can handle some data quality issues. It is also useful during initial data quality assessment, when you are not yet sure how widespread a problem is. Warn allows you to collect data without blocking the pipeline. You can monitor the metrics and decide later whether to escalate to drop or fail.

Use warn when the invalid data is not critical enough to stop the pipeline or remove records. For example, a missing phone number might be acceptable for some customers. You still want to know how many records are missing a phone number, but you do not want to drop those records or fail the pipeline. Warn gives you the ability to measure the problem and decide later whether to take action.

The following Python example shows how to apply a warn expectation. Each line is commented.

# Because this is @dp.expect, the record is still written to the target.
# The failure is recorded in the data quality metrics.
# The pipeline does not stop.
# This is the warn action.
def customer_contacts():
    # Read from the raw customers source.
    # The returned DataFrame is the input to the dataset.
    # Expectations are applied to each record as it is processed.
    return spark.readStream.table("raw.customers")

```sql

CREATE OR REFRESH STREAMING TABLE customer_contacts(
    -- The non_null_email constraint checks that email is not null.
    -- There is no ON VIOLATION clause.

    -- Invalid records are written to the target.
    -- Violation metrics are recorded.
    CONSTRAINT non_null_email EXPECT (email IS NOT NULL)

```

Warn is appropriate when you are monitoring and analyzing data quality. It is not appropriate when invalid records can cause serious harm. If a negative account balance can trigger incorrect financial decisions, warn is too weak. If a missing phone number only affects marketing outreach, warn may be sufficient. Always consider the downstream impact before choosing warn.

## The drop action

The drop action removes records that fail validation before writing to the target. Use this when you need clean data downstream and can afford to lose some records. The pipeline continues processing valid records. The dropped records are not written to the target. Metrics record how many records were dropped. This action is useful for data cleansing. It ensures that only valid records reach downstream consumers. It is often used when invalid records are not useful and can be safely discarded.

Use drop when you want to filter out invalid records silently. For example, if an address is required for shipping, you might drop records that are missing a street or city. Those records cannot be used for shipping, so there is no point in writing them to the target. Dropping them keeps the target clean and prevents downstream errors.

The following Python example shows how to apply a drop expectation. Each line is commented.

```python
# The @dp.expect_or_drop decorator attaches an expectation that drops invalid rows.
# The first argument is the expectation name.
# The second argument is the SQL expression that must be true.
@dp.expect_or_drop("valid_price", "price >= 0 AND price <= 10000")
# valid_price is the name of the expectation.
# The expression requires price to be between 0 and 10000 inclusive.
# If price is outside this range, the record fails the expectation.
# Because this is @dp.expect_or_drop, the invalid record is removed before write.
# The pipeline continues processing other records.
# The drop count is recorded in the data quality metrics.
# This is the drop action.
def validated_orders():
    # Read from the raw orders source.
    # The returned DataFrame is the input to the dataset.
    # Expectations are applied to each record as it is processed.
    return spark.readStream.table("raw.orders")
```

The SQL equivalent uses `ON VIOLATION DROP ROW`. The following SQL example shows a streaming table with a drop expectation.

```sql
-- Create or refresh a streaming table named validated_orders.
CREATE OR REFRESH STREAMING TABLE validated_orders(
    -- The valid_price constraint checks that price is between 0 and 10000.
    -- ON VIOLATION DROP ROW means invalid records are removed before write.
    -- The pipeline continues.
    -- Dropped records are counted in the data quality metrics.
    CONSTRAINT valid_price EXPECT (price >= 0 AND price <= 10000) ON VIOLATION DROP ROW
) AS SELECT * FROM STREAM(raw.orders);
```

Drop is appropriate for data cleansing when invalid records are not useful. However, drop can hide problems. If you drop too many records, you may not notice that a source system is broken. Always monitor drop metrics. If the drop count increases suddenly, investigate the cause. Consider writing dropped records to a quarantine table for later inspection. A quarantine table allows you to audit the dropped records and reprocess them after fixing the data quality issue.

## The fail action

The fail action stops execution immediately when any record violates the constraint. The pipeline atomically rolls back any partial updates. This option makes sense for critical data where invalid records indicate a serious upstream problem. It ensures that bad data does not reach downstream consumers. It also forces you to fix the problem before the pipeline can continue.

Use fail when data integrity is critical and invalid records are unacceptable. For example, a negative account balance might indicate a bug in a financial system, a fraud attempt, or a data corruption issue. Writing that record to the target could cause incorrect balances, failed payments, or regulatory violations. Failing the pipeline prevents the bad data from spreading. It also alerts the team that something is wrong.

The following Python example shows how to apply a fail expectation. Each line is commented.

```python
# The @dp.expect_or_fail decorator attaches an expectation that fails the pipeline.
# The first argument is the expectation name.
# The second argument is the SQL expression that must be true.
@dp.expect_or_fail("required_customer_id", "customer_id IS NOT NULL")
# required_customer_id is the name of the expectation.
# The expression requires customer_id to be not null.
# If any record has a null customer_id, the expectation fails.
# Because this is @dp.expect_or_fail, the pipeline stops.
# The current transaction rolls back.
# No records from the current update are written to the target.
# This is the fail action.
def critical_transactions():
    # Read from the raw transactions source.
    # The returned DataFrame is the input to the dataset.
    # Expectations are applied to each record as it is processed.
    return spark.readStream.table("raw.transactions")
```

The SQL equivalent uses `ON VIOLATION FAIL UPDATE`. The following SQL example shows a streaming table with a fail expectation.

```sql
-- Create or refresh a streaming table named critical_transactions.
CREATE OR REFRESH STREAMING TABLE critical_transactions(
    -- The required_customer_id constraint checks that customer_id is not null.
    -- ON VIOLATION FAIL UPDATE means the pipeline stops if any record violates the constraint.
    -- The current transaction rolls back.
    -- No records from the current update are written to the target.
    CONSTRAINT required_customer_id EXPECT (customer_id IS NOT NULL) ON VIOLATION FAIL UPDATE
) AS SELECT * FROM STREAM(raw.transactions);
```

Fail is appropriate for critical data integrity. It is not appropriate for every validation rule. If you use fail for every minor issue, your pipeline may stop frequently. This can cause delays and require constant manual intervention. Use fail sparingly and only for rules that are truly critical. Ensure that you have proper alerting and runbooks so that the team can respond quickly when a fail occurs.

## How to choose the right action

Choosing the right action depends on several factors. Consider the criticality of the data. If invalid data can cause financial loss, regulatory violations, safety issues, or serious operational problems, use fail. If invalid data is inconvenient but not dangerous, use drop or warn. Consider the volume and pattern of invalid records. If invalid records are rare and isolated, drop may be sufficient. If invalid records are frequent and indicate a systemic issue, fail may be necessary to force a fix. If you are still investigating the problem, warn allows you to collect data without blocking the pipeline. Consider the tolerance of downstream consumers. If downstream systems can handle nulls or missing values, warn may be acceptable. If downstream systems require complete records, drop or fail may be necessary. Consider your ability to recover. If you can easily reprocess data after a failure, fail may be acceptable. If reprocessing is difficult or expensive, drop may be better because it allows the pipeline to continue. Consider compliance and audit requirements. If you must retain all records for auditing, do not drop them. Use warn and quarantine instead.

## Combining actions

You can combine actions across different expectations in the same dataset. For example, you might warn on a missing phone number, drop rows with an incomplete address, and fail on a negative account balance. This allows you to apply the right level of strictness to each rule. The following SQL example combines all three actions.

```sql
-- Create or refresh a streaming table named customers.
CREATE OR REFRESH STREAMING TABLE customers(
    -- Warn: no ON VIOLATION clause.
    -- Invalid phone numbers are written to the target.
    -- Violation metrics are recorded.
    CONSTRAINT has_phone EXPECT (phone_number IS NOT NULL),
    -- Drop: invalid rows are removed before write.
    -- Rows missing street or city are not written to the target.
    -- Drop metrics are recorded.
    CONSTRAINT complete_address EXPECT (street IS NOT NULL AND city IS NOT NULL) ON VIOLATION DROP ROW,
    -- Fail: pipeline stops if any balance is negative.
    -- The current transaction rolls back.
    -- No rows from the current update are written.
    CONSTRAINT valid_account_balance EXPECT (balance >= 0) ON VIOLATION FAIL UPDATE
) AS SELECT * FROM STREAM(raw.customers);
```

This example shows that you can mix actions in the same dataset. Each constraint has its own behavior. The warn constraint keeps records and records metrics. The drop constraint removes invalid records. The fail constraint stops the pipeline. This allows you to apply the right action to each rule.

## Note about parallel flows

When a pipeline has multiple parallel flows, a failure in one flow does not cause other flows to fail. Each flow operates independently. This is an important detail. If you have a pipeline that processes multiple datasets in parallel, and one dataset has a fail expectation that triggers, only that flow stops. The other flows continue processing. This can be useful because it isolates failures. However, it also means that you need to monitor each flow separately. A failure in one flow may not be immediately obvious if you are only looking at the overall pipeline status. You should set up alerts for each flow and for each expectation. You should also ensure that downstream consumers are aware of which flows are critical and which are not.

## Quarantine as an alternative

Another pattern is to route invalid records to a separate quarantine table while allowing valid records to proceed. This is not one of the three built-in actions, but you can implement it using filters. The following Python example shows how to create two tables: one for valid records and one for quarantine records. Each line is commented.

```python
# Import the pipelines module from pyspark.
from pyspark import pipelines as dp

# Define a table for valid transactions.
@dp.table
def valid_transactions():
    # Read from the raw transactions source.
    return (
        spark.readStream.table("raw_transactions")
        # Filter to keep only records where amount and transaction_date are not null.
        # The filter method applies a SQL expression.
        # Records that satisfy the expression are kept.
        # Records that do not satisfy the expression are excluded.
        .filter("amount IS NOT NULL AND transaction_date IS NOT NULL")
    )

# Define a table for quarantine transactions.
@dp.table
def quarantine_transactions():
    # Read from the same raw transactions source.
    return (
        spark.readStream.table("raw_transactions")
        # Filter to keep only records where amount or transaction_date is null.
        # The OR condition means a record is quarantined if either column is null.
        # Records that satisfy the expression are kept in the quarantine table.
        .filter("amount IS NULL OR transaction_date IS NULL")
    )
```

This pattern lets you investigate problematic records without blocking your main data flow. It preserves the invalid records for later analysis. You can add a reason column and a timestamp to the quarantine table for better analysis. The following example shows how to add a reason column.

```python
# Import the required functions.
from pyspark import pipelines as dp
from pyspark.sql.functions import col, when, current_timestamp, lit

# Define a table for quarantine transactions with a reason.
@dp.table
def quarantine_transactions_with_reason():
    # Read from the raw transactions source.
    df = spark.readStream.table("raw_transactions")
    # Add a reason column.
    # The when function checks the first condition.
    # If amount is null, it returns 'Missing amount'.
    # If not, it checks the next condition.
    # If transaction_date is null, it returns 'Missing transaction_date'.
    # If neither condition is true, it returns 'Unknown'.
    # The otherwise method provides the default value.
    df_with_reason = df.withColumn(
        "reason",
        when(col("amount").isNull(), lit("Missing amount"))
        .when(col("transaction_date").isNull(), lit("Missing transaction_date"))
        .otherwise(lit("Unknown"))
    )
    # Add a timestamp column to record when the record was quarantined.
    df_with_reason = df_with_reason.withColumn("quarantined_at", current_timestamp())
    # Filter to keep only records that have a reason other than 'Unknown'.
    # Actually, we want to keep records where either amount or transaction_date is null.
    # So we filter on the original conditions.
    return df_with_reason.filter("amount IS NULL OR transaction_date IS NULL")
```

This example adds a reason column that explains why the record was quarantined. It also adds a quarantined_at timestamp. This makes it easier to diagnose problems. You can group quarantined records by reason and by day. You can see trends over time. You can prioritize fixes based on the most common reasons.

## Monitoring and metrics

Expectations produce metrics that you can view in the pipeline UI. Select a dataset with expectations and open the Data quality tab. The metrics show how many records passed, how many failed, how many were dropped, and how many were warned. You can also see pass rates over time. These metrics help you monitor validation pass rates and identify systematic data quality issues. You can set up alerts when violation counts exceed a threshold. For example, if the drop count for valid_price suddenly increases, investigate the source system. If the pass rate falls below a certain percentage, consider whether the rule is too strict or whether the source data has a problem. You can also query the pipeline event log for custom monitoring and reporting.

## Best practices for choosing actions

Choose the right action for each expectation. Use warn for monitoring. Use drop for data cleansing. Use fail for critical data integrity. Do not use fail for every rule. It can cause frequent pipeline stops. Do not use drop for critical data. You might lose important records. Use quarantine for balanced handling.

Name your expectations clearly. A good name describes the rule. For example, valid_price is better than check1. Meaningful names make it easier to understand the metrics and diagnose failures.

Handle nulls explicitly. Decide whether null is acceptable for each column. If null is acceptable, add an IS NULL condition. If null is not acceptable, use IS NOT NULL without the IS NULL condition.

Test your expectations thoroughly. Create sample data with valid values, invalid values, nulls, empty strings, and boundary values. Verify that valid records pass and invalid records are handled correctly. Test each action: warn, drop, and fail.

Monitor your metrics. Set up alerts for unexpected changes. Investigate sudden increases in violations. Use the metrics to improve data quality at the source.

Document your expectations. Keep a record of the rules and the reason for each rule. This helps new team members understand the data model. It also helps when you need to modify or remove an expectation.

Use a bronze, silver, and quarantine architecture. The bronze layer stores raw data. The silver layer stores cleaned data. The quarantine layer stores invalid records. This pattern separates concerns and makes it easier to manage data quality.

## Common mistakes to avoid

One common mistake is using generic names. Names like check1 or test do not communicate the rule. They make it hard to understand metrics and diagnose failures.

Another common mistake is forgetting null handling. If you use price >= 0 AND price <= 10000 and price is null, the record fails. If null is acceptable, you must add price IS NULL OR. If null is not acceptable, you should be explicit.

Another common mistake is using cast instead of try_cast in constraints. If you use cast and the conversion fails, the expression may raise an error, which can fail the pipeline even if you chose expect_or_drop. Always use try_cast for type validation in constraints.

Another common mistake is using expect_or_fail for every rule. This can cause frequent pipeline stops. Use expect_or_fail only for critical rules. Use expect_or_drop or expect for less critical rules.

Another common mistake is not monitoring metrics. Expectations produce valuable data quality metrics. If you do not monitor them, you may miss systematic problems. Set up alerts and dashboards.

Another common mistake is not testing expectations. Always test with a variety of values. Test valid values, invalid values, nulls, empty strings, and boundary values. Verify the behavior of each action.

## Testing expectations

You should test your expectations with a variety of values. Create sample data that includes valid values, invalid values, null values, empty strings, and boundary values. For example, if your expectation is valid_price with the constraint price >= 0 AND price <= 10000, test prices of -1, 0, 1, 9999, 10000, 10001, and null. Verify that the expectation passes for 0 through 10000 and fails for -1, 10001, and null (unless null is allowed). You can test expectations using SQL queries. For example, you can run SELECT price >= 0 AND price <= 10000 on a set of test values and check the results. You can also write unit tests in your pipeline testing framework.
