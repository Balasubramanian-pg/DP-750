## Validate data cardinality

> [!IMPORTANT]
> The Criticality of Unique Identifiers
> 
> Data cardinality is not merely a structural preference. It is the backbone of relational integrity. When a column expected to be unique contains duplicates joins produce Cartesian products aggregations inflate metrics and business logic collapses. Validating uniqueness ensures that every transaction customer or entity remains distinct within your data estate.

### Enforcing Uniqueness in Pipelines

Pipeline expectations allow you to embed uniqueness checks directly into the transformation logic. This method transforms the data to reveal violations before they persist.

```python
from pyspark.sql.window import Window
from pyspark.sql.functions import count

@dp.table
@dp.expect("unique_ssn_per_person", "ssn_count = 1")
def employees():
    df = spark.table("raw.employees")
    w = Window.partitionBy("ssn")
    return df.withColumn("ssn_count", count("*").over(w))
```

*   **Window Function Logic**: The code uses a window partitioned by the target column `ssn`. This calculates how many times each value appears in the dataset.
*   **Expectation Condition**: The `@dp.expect` decorator checks if `ssn_count` equals 1. If a row has a count greater than 1 it indicates a duplicate.
*   **Active Enforcement**: By default this expectation will fail the pipeline if violated. You can modify it to `expect_or_drop` if you prefer to keep only the first occurrence or remove all duplicates depending on business rules.

### Investigative Materialized Views

Sometimes you need to identify and resolve duplicates rather than simply dropping them. A materialized view serves as a dedicated monitoring tool for cardinality issues.

```sql
CREATE OR REFRESH MATERIALIZED VIEW order_validation AS
SELECT 
    order_id,
    COUNT(*) as occurrence_count
FROM orders
GROUP BY order_id
HAVING COUNT(*) > 1;
```

*   **Aggregation Strategy**: This query groups records by `order_id` and counts occurrences.
*   **Filtering for Violations**: The `HAVING` clause isolates only those IDs appearing more than once.
*   **Operational Use**: This view remains empty when data quality is high. Any rows present represent active quality incidents requiring investigation. It provides a clear audit trail for data stewardship teams.

### Delta Lake Primary Key Constraints

Delta Lake allows you to define primary keys at the table level. However their behavior differs significantly from traditional relational databases.

```sql
CREATE TABLE orders (
    order_id INT NOT NULL,
    customer_id INT,
    order_date DATE,
    CONSTRAINT orders_pk PRIMARY KEY (order_id)
);
```

> [!WARNING]
> Informational vs. Enforced Constraints
> 
> *   **No Write-time Blocking**: Delta Lake does not reject duplicate writes based on primary key constraints. The constraint is informational.
> *   **Query Optimization**: The engine uses these constraints to optimize join strategies and improve query performance.
> *   **Documentation**: They serve as living documentation of the intended data model helping engineers understand relationships without reading external schemas.

> [!TIP]
> Best Practice for Uniqueness
> 
> Rely on pipeline expectations for active enforcement. Use Delta Lake primary key constraints for optimization and modeling clarity. Combining both gives you performance benefits while ensuring data integrity through real-time validation.
