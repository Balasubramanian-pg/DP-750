## Understand validation approaches in Azure Databricks

> [!NOTE]
> The Two Pillars of Validation
> 
> Azure Databricks distinguishes between validation during transformation and validation at storage. Understanding when to apply each mechanism is critical for building resilient data architectures.

### Pipeline Expectations

These checks operate within Lakeflow Spark Declarative Pipelines. They are designed for scenarios where data is in motion or being materialized through complex transformations.

> [!TIP]
> Characteristics of Pipeline Expectations
> 
> *   **Real-time Control**: Ideal for streaming tables and materialized views where immediate feedback is necessary.
> *   **Configurable Actions**: You can choose to warn stakeholders drop invalid records or fail the entire pipeline when rules are violated.
> *   **Transformation Context**: Checks apply during the data processing phase allowing you to filter or route bad data before it settles.

### Table Constraints

Constraints enforce rules directly on Delta Lake tables. This method acts as a final gatekeeper ensuring that only compliant data persists in your storage layer.

> [!IMPORTANT]
> Characteristics of Table Constraints
> 
> *   **Write-time Enforcement**: Invalid data is rejected at the point of ingestion. Bad records never enter the table.
> *   **Strict Integrity**: Best suited for batch processing and scenarios where absolute data correctness is non-negotiable.
> *   **Storage-level Guarantee**: Provides a persistent rule set that applies regardless of how the data was written.

### Dimensions of Data Quality

Both approaches allow you to validate three fundamental aspects of your data assets.

> [!WARNING]
> Key Validation Targets
> 
> *   **Nullability**: Ensures that required values exist and critical fields are not empty.
> *   **Data Cardinality**: Verifies uniqueness where expected preventing duplicate entries in key columns.
> *   **Range Checking**: Confirms that numeric or date values fall within acceptable business bounds.
