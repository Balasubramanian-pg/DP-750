## Implement nullability checks

> [!IMPORTANT]
> The Logic of Nullability
> 
> Nullability checks prevent the silent corruption of records. When a column like `email` or `customer_id` is empty downstream joins fail and analytics become unreliable. The implementation strategy depends on whether you are managing data in motion via pipelines or at rest in Delta Lake tables.

### Pipeline Expectations in Python

This approach uses decorators to attach quality rules directly to the function defining the streaming table. The `dp.expect_or_drop` decorator acts as a filter.

```python
from pyspark import pipelines as dp

@dp.table
@dp.expect_or_drop("valid_email", "email IS NOT NULL")
@dp.expect_or_drop("valid_customer_id", "customer_id IS NOT NULL")
def customers():
    return spark.readStream.table("raw.customers")
```

*   **Decorator Chain**: Each `@dp.expect_or_drop` adds a specific rule. The first argument is a unique name for the expectation. The second is the SQL expression that must evaluate to true.
*   **Action on Violation**: The `expect_or_drop` variant silently removes rows that fail the check. Other variants like `expect_or_fail` would stop the pipeline entirely.
*   **Execution Context**: These checks run as the data flows through the `customers` transformation ensuring only complete records are written to the target.

### Pipeline Expectations in SQL

SQL provides a declarative way to define the same logic within the `CREATE STREAMING TABLE` statement.

```sql
CREATE OR REFRESH STREAMING TABLE customers(
    CONSTRAINT valid_email EXPECT (email IS NOT NULL) ON VIOLATION DROP ROW,
    CONSTRAINT valid_customer_id EXPECT (customer_id IS NOT NULL) ON VIOLATION DROP ROW
) AS SELECT * FROM STREAM(raw.customers);
```

*   **Constraint Clause**: The `CONSTRAINT` keyword defines the rule name. `EXPECT` contains the boolean condition.
*   **Violation Handling**: `ON VIOLATION DROP ROW` specifies the behavior. This keeps the pipeline running while discarding invalid data. You could also use `FAIL UPDATE` to halt processing.
*   **Stream Source**: The `STREAM()` function indicates that the source is a live stream rather than a static batch.

### Delta Lake Table Constraints

For tables managed outside of Lakeflow pipelines you enforce nullability at the schema level. This provides a permanent guarantee for any process writing to the table.

```sql
CREATE TABLE customers (
    customer_id INT NOT NULL,
    email STRING NOT NULL,
    first_name STRING,
    last_name STRING
);
```

*   **Schema Definition**: The `NOT NULL` keyword is part of the column definition. It instructs the Delta Lake engine to reject any write operation containing nulls in these fields.
*   **Strict Enforcement**: Unlike pipeline expectations which can drop rows this constraint causes the entire write transaction to fail if violated.

### Modifying Existing Tables

You can add strict nullability rules to tables that already contain data.

```sql
ALTER TABLE customers ALTER COLUMN email SET NOT NULL;
```

*   **Pre-flight Validation**: Before applying the constraint Azure Databricks scans the existing data. If any row currently has a null value in the `email` column the command fails.
*   **Data Hygiene Requirement**: This forces you to clean or backfill missing values before you can enforce the stricter rule. It prevents you from accidentally locking out valid historical data or creating an inconsistent state.
