# Choose actions for validation failures

When validation fails, you choose how your pipeline responds. Each action suits different business requirements and data criticality levels. The action you choose determines whether invalid records are written to the target, removed before write, or cause the entire pipeline to stop. This decision is not only technical. It is also a business decision. A pipeline that stops too often can delay critical reporting. A pipeline that never stops can silently propagate bad data into dashboards, machine learning models, financial calculations, and operational systems. A pipeline that drops too many rows can hide systematic problems. A pipeline that warns too often can create alert fatigue. The goal is to match the action to the importance of the data and the tolerance of downstream consumers.

The three primary actions are warn, drop, and fail. Each one has a distinct behavior, a distinct use case, and a distinct impact on data quality and pipeline availability. You can also combine actions across different expectations in the same dataset. For example, you might warn on a missing phone number, drop rows with an incomplete address, and fail on a negative account balance. This allows you to apply the right level of strictness to each rule.

## Warn action

The warn action is the default behavior for expectations in many data quality frameworks. When a validation fails, the invalid record is still written to the target. The pipeline continues processing. The violation is recorded in metrics and logs. This action is useful when you need visibility into data quality issues without blocking data flow. It is often used during initial data quality assessment, when you are not yet sure how widespread a problem is, or when the downstream consumers can tolerate some invalid records.

Use warn when the invalid data is not critical enough to stop the pipeline or remove records. For example, a missing phone number might be acceptable for some customers. You still want to know how many records are missing a phone number, but you do not want to drop those records or fail the pipeline. Warn gives you the ability to measure the problem and decide later whether to escalate to drop or fail.

The following Python example shows how to apply a warn expectation. The comments explain each line.

```python

# The first argument is the expectation name, which appears in metrics.
# The second argument is the SQL expression that must be true for the record to pass.
@dp.expect("has_phone", "phone_number IS NOT NULL")
# has_phone is the name of the expectation.
# The expression phone_number IS NOT NULL checks that the phone number is not null.
# If the expression is true, the record passes.
# If the expression is false or unknown, the record fails the expectation.
# Because this is @dp.expect, the record is still written to the target.
# The failure is recorded in the data quality metrics.
# The pipeline does not stop.
# This is the warn action.
def customers():
    # Read from the raw customers source.
    # The returned DataFrame is the input to the dataset.
    # Expectations are applied to each record as it is processed.
    return spark.readStream.table("raw.customers")
```

```sql
-- Create or refresh a streaming table named customers.
CREATE OR REFRESH STREAMING TABLE customers(
    -- The has_phone constraint checks that phone_number is not null.
    -- There is no ON VIOLATION clause.
    -- Without an ON VIOLATION clause, the default behavior is to warn.
    -- Invalid records are written to the target.
    -- Violation metrics are recorded.
    CONSTRAINT has_phone EXPECT (phone_number IS NOT NULL)

```

Warn is appropriate when you are monitoring and analyzing data quality. It is not appropriate when invalid records can cause serious harm. If a negative account balance can trigger incorrect financial decisions, warn is too weak. If a missing phone number only affects marketing outreach, warn may be sufficient. Always consider the downstream impact before choosing warn.

## Drop action

The drop action removes invalid records before they are written to the target. The pipeline continues processing. The dropped records are not written to the target. Metrics record how many records were dropped. This action is useful for data cleansing. It ensures that only valid records reach downstream consumers. It is often used when invalid records are not useful and can be safely discarded.

Use drop when you want to filter out invalid records silently. For example, if an address is required for shipping, you might drop records that are missing a street or city. Those records cannot be used for shipping, so there is no point in writing them to the target. Dropping them keeps the target clean and prevents downstream errors.

The following Python example shows how to apply a drop expectation. The comments explain each line.

```python
# The @dp.expect_or_drop decorator attaches an expectation that drops invalid rows.
# The first argument is the expectation name.
# The second argument is the SQL expression that must be true.
@dp.expect_or_drop("complete_address", "street IS NOT NULL AND city IS NOT NULL")
# complete_address is the name of the expectation.
# The expression requires both street and city to be non-null.
# If either street or city is null, the record fails the expectation.
# Because this is @dp.expect_or_drop, the invalid record is removed before write.
# The pipeline continues processing other records.
# The drop count is recorded in the data quality metrics.
# This is the drop action.
def customers():
    # Read from the raw customers source.
    # The returned DataFrame is the input to the dataset.
    # Expectations are applied to each record as it is processed.
    return spark.readStream.table("raw.customers")
```

In SQL, the drop action is specified with ON VIOLATION DROP ROW. The following example shows a streaming table with a drop expectation.

```sql
-- Create or refresh a streaming table named customers.
CREATE OR REFRESH STREAMING TABLE customers(
    -- The complete_address constraint checks that street and city are both not null.
    -- ON VIOLATION DROP ROW means invalid records are removed before write.
    -- The pipeline continues.
    -- Dropped records are counted in the data quality metrics.
    CONSTRAINT complete_address EXPECT (street IS NOT NULL AND city IS NOT NULL) ON VIOLATION DROP ROW
) AS SELECT * FROM STREAM(raw.customers);
```

Drop is appropriate for data cleansing when invalid records are not useful. However, drop can hide problems. If you drop too many records, you may not notice that a source system is broken. Always monitor drop metrics. If the drop count increases suddenly, investigate the cause. Consider writing dropped records to a quarantine table for later inspection. A quarantine table allows you to audit the dropped records and reprocess them after fixing the data quality issue.

## Fail action

The fail action stops the pipeline when a validation fails. The current transaction rolls back. No records from the current update are written to the target. This action is useful when data integrity is critical and invalid records are unacceptable. It ensures that bad data does not reach downstream consumers. It also forces you to fix the problem before the pipeline can continue.

Use fail when invalid records indicate a serious problem. For example, a negative account balance might indicate a bug in a financial system, a fraud attempt, or a data corruption issue. Writing that record to the target could cause incorrect balances, failed payments, or regulatory violations. Failing the pipeline prevents the bad data from spreading. It also alerts the team that something is wrong.

The following Python example shows how to apply a fail expectation. The comments explain each line.

```python
# The @dp.expect_or_fail decorator attaches an expectation that fails the pipeline.
# The first argument is the expectation name.
# The second argument is the SQL expression that must be true.
@dp.expect_or_fail("valid_account_balance", "balance >= 0")
# valid_account_balance is the name of the expectation.
# The expression requires balance to be zero or positive.
# If any record has a negative balance, the expectation fails.
# Because this is @dp.expect_or_fail, the pipeline stops.
# The current transaction rolls back.
# No records from the current update are written to the target.
# This is the fail action.
def accounts():

    # The returned DataFrame is the input to the dataset.
    # Expectations are applied to each record as it is processed.
    return spark.readStream.table("raw.accounts")
```

In SQL, the fail action is specified with ON VIOLATION FAIL UPDATE. The following example shows a streaming table with a fail expectation.

```sql
-- Create or refresh a streaming table named accounts.
CREATE OR REFRESH STREAMING TABLE accounts(
    -- The valid_account_balance constraint checks that balance is zero or positive.
    -- ON VIOLATION FAIL UPDATE means the pipeline stops if any record violates the constraint.
    -- The current transaction rolls back.
    -- No records from the current update are written to the target.
    CONSTRAINT valid_account_balance EXPECT (balance >= 0) ON VIOLATION FAIL UPDATE
) AS SELECT * FROM STREAM(raw.accounts);
```

Fail is appropriate for critical data integrity. It is not appropriate for every validation rule. If you use fail for every minor issue, your pipeline may stop frequently. This can cause delays and require constant manual intervention. Use fail sparingly and only for rules that are truly critical. Ensure that you have proper alerting and runbooks so that the team can respond quickly when a fail occurs.

## Viewing expectation metrics

You can view expectation metrics in the pipeline UI. Select a dataset that has expectations and open the Data quality tab. The metrics show how many records passed, how many failed, how many were dropped, and how many were warned. You can also see pass rates over time. These metrics help you monitor validation pass rates and identify systematic data quality issues.

Metrics are important because they tell you whether your chosen action is working as intended. If you chose warn, you can see how many invalid records are still reaching the target. If you chose drop, you can see how many records are being removed. If you chose fail, you can see which expectation caused the pipeline to stop. You can use these metrics to set alerts. For example, you can alert when the drop count exceeds a threshold, or when the pass rate falls below a certain percentage. You can also query the pipeline event log for custom monitoring and reporting.

## SQL equivalents for warn, drop, and fail

In SQL, you can apply the same actions to streaming tables. The following example combines all three actions in a single table definition. The comments explain each constraint.

```sql
-- Create or refresh a streaming table named customers.
CREATE OR REFRESH STREAMING TABLE customers(
    -- Warn: no ON VIOLATION clause.
    -- Invalid phone numbers are written to the target.
    -- Violation metrics are recorded.
    CONSTRAINT has_phone EXPECT (phone_number IS NOT NULL),
    -- Drop: invalid rows are removed before write.
    -- Rows missing street or city are not written to the target.
    -- Drop metrics are recorded.
    CONSTRAINT complete_address EXPECT (street IS NOT NULL AND city IS NOT NULL) ON VIOLATION DROP ROW,
    -- Fail: pipeline stops if any balance is negative.
    -- The current transaction rolls back.
    -- No rows from the current update are written.
    CONSTRAINT valid_account_balance EXPECT (balance >= 0) ON VIOLATION FAIL UPDATE
) AS SELECT * FROM STREAM(raw.customers);
```

This example shows that you can mix actions in the same dataset. Each constraint has its own behavior. The warn constraint keeps records and records metrics. The drop constraint removes invalid records. The fail constraint stops the pipeline. This allows you to apply the right action to each rule.

## Delta Lake CHECK constraints

For Delta Lake tables, you can use CHECK constraints to enforce ranges at write time. CHECK constraints are different from expectations. They do not support warn or drop. They only fail. When a write violates a CHECK constraint, the write fails. The entire write operation is rejected. You must fix the data or the constraint before writing again.

The following example adds a CHECK constraint to an existing Delta table.

```sql
-- Add a CHECK constraint to an existing Delta table.
-- The constraint requires balance to be zero or positive.
-- If a write violates the constraint, the write fails.
-- There is no warn or drop behavior.
-- This is similar to the fail action.
ALTER TABLE accounts ADD CONSTRAINT valid_account_balance CHECK (balance >= 0);
```

CHECK constraints are useful when you want to enforce data integrity at the storage layer. They are not a replacement for expectations in a pipeline. If you need warn or drop behavior, use expectations in the pipeline. If you need to guarantee that no invalid data can ever be written to the table, use a CHECK constraint.

## How to choose the right action

Choosing the right action depends on several factors. Consider the criticality of the data. If invalid data can cause financial loss, regulatory violations, safety issues, or serious operational problems, use fail. If invalid data is inconvenient but not dangerous, use drop or warn.

Consider the volume and pattern of invalid records. If invalid records are rare and isolated, drop may be sufficient. If invalid records are frequent and indicate a systemic issue, fail may be necessary to force a fix. If you are still investigating the problem, warn allows you to collect data without blocking the pipeline.

Consider the tolerance of downstream consumers. If downstream systems can handle nulls or missing values, warn may be acceptable. If downstream systems require complete records, drop or fail may be necessary. If downstream systems cannot tolerate any invalid records, fail is the safest choice.

Consider your ability to recover. If you can easily reprocess data after a failure, fail may be acceptable. If reprocessing is difficult or expensive, drop may be better because it allows the pipeline to continue. However, dropping data can also cause problems if the dropped data is needed later. In that case, consider writing dropped records to a quarantine table.

Consider compliance and audit requirements. If you must retain all records for auditing, do not drop them. Use warn and quarantine instead. If you must ensure that no invalid records are ever stored, use fail or CHECK constraints.

## Combining actions in practice

You can combine actions to balance visibility, cleansing, and integrity. For example, you might have a dataset with the following rules:

- Warn on missing phone number. This gives you visibility into how many customers are missing a phone number, but it does not block the pipeline.
- Drop rows with incomplete address. This ensures that only complete addresses are used for shipping.
- Fail on negative account balance. This prevents critical financial data from being corrupted.

This combination allows you to monitor minor issues, cleanse non-critical records, and protect critical data. The key is to match the action to the importance of the rule. Do not use fail for every rule. Do not use drop for critical data. Do not use warn for data that must be correct.

## Testing and monitoring validation actions

You should test each validation action with sample data. Test records that pass, records that fail, and records that are null. For warn, verify that invalid records are written to the target and that metrics are recorded. For drop, verify that invalid records are removed and that the drop count is correct. For fail, verify that the pipeline stops and that the transaction rolls back.

Monitor your validation metrics regularly. Set up alerts for unexpected changes. For example, if the drop count suddenly increases, investigate the source system. If the fail count increases, check whether a new data source or a recent code change introduced a problem. If the warn count is high, consider whether the rule should be tightened or whether the data quality issue should be fixed at the source.

## Summary

When validation fails, you choose how your pipeline responds. Warn writes invalid records to the target and records metrics. Drop removes invalid records before write and records metrics. Fail stops the pipeline and rolls back the transaction. Each action suits different business requirements and data criticality levels. Use warn for monitoring and analysis. Use drop for data cleansing. Use fail for critical data integrity. You can combine actions across different expectations in the same dataset. You can view expectation metrics in the pipeline UI and use them to monitor pass rates and identify systematic data quality issues. For Delta Lake tables, CHECK constraints enforce integrity at write time but only fail. They do not support warn or drop. Choose your actions carefully, test them thoroughly, and monitor them continuously. This ensures that your data pipelines maintain quality standards for nullability, cardinality, and value ranges.
