# Apply Range Checking

Range validation confirms that numeric, date, and other values fall within acceptable bounds. This check catches data entry errors, system glitches, and integration issues that produce out-of-range values. In a data pipeline, range checking is one of the simplest and most effective data quality controls. It is easy to express, cheap to evaluate, and easy to monitor. It can prevent bad records from reaching downstream consumers, machine learning models, financial reports, and operational dashboards. A negative salary, a future hire date, an age of 999, a transaction amount of zero, or a quantity of one million can all indicate a problem in the source system, a broken integration, or a bug in an upstream transformation. Range checks stop those problems at the boundary of your pipeline.

## Why range checking matters

Data quality problems are often caused by small mistakes. A user might type the wrong number into a form. A system might send a default value such as zero or negative one when a field is missing. An integration might map columns incorrectly and place a timestamp into an age column. A batch process might use the wrong time zone and produce a future date. Range checking catches these issues because the invalid value falls outside a known acceptable interval. It does not require complex logic. It only requires that you know what values are reasonable for a column.

Range checks also help enforce business rules. For example, a discount percentage should normally be between zero and one hundred. A customer loyalty tier might allow a larger discount only for premium customers. A transaction amount should be greater than zero. A quantity should be positive and not absurdly large. These rules can be expressed as range conditions and combined with other conditions when necessary.

## Defining range expectations with comparison operators and BETWEEN

You can define range expectations using comparison operators or the BETWEEN clause. The common comparison operators are greater than, greater than or equal to, less than, less than or equal to, equal to, and not equal to. The BETWEEN clause is inclusive. That means `age BETWEEN 0 AND 150` accepts both 0 and 150. If you want to exclude an endpoint, use strict comparison operators such as `age > 0` or `age < 150`.

The following Python example shows how to attach range expectations to a streaming table in a Databricks Lakeflow declarative pipeline. The comments explain each line.

```python

# in the declarative pipeline. The function below returns the input data.
@dp.table
# The @dp.expect_or_fail decorator adds a data quality expectation.
# If the expectation is violated, the pipeline fails instead of keeping bad data.
@dp.expect_or_fail("valid_age", "age BETWEEN 0 AND 150")
# valid_age: age must be between 0 and 150 inclusive.
# BETWEEN is inclusive, so 0 and 150 are valid.
# If age is NULL, the expression evaluates to NULL, which is not true.
# To make null handling explicit, use "age IS NOT NULL AND age BETWEEN 0 AND 150".
@dp.expect_or_fail("valid_salary", "salary >= 0")
# valid_salary: salary cannot be negative.
# This allows zero salary, which may be valid for unpaid roles or volunteers.
# If zero is not valid, change the condition to "salary > 0".
@dp.expect_or_fail("valid_hire_date", "hire_date <= current_date()")
```

In SQL, you can apply the same range checks to a streaming table. The following example creates or refreshes a streaming table named transactions. Each constraint has a name, an EXPECT expression, and an ON VIOLATION action. The ON VIOLATION DROP ROW action drops invalid rows instead of failing the pipeline. The comments explain each part.

```sql
-- Create or refresh a streaming table named transactions.
-- The table has three constraints that validate ranges.
CREATE OR REFRESH STREAMING TABLE transactions(
    -- valid_amount: amount must be greater than zero.
    -- This rejects zero and negative amounts.
    -- ON VIOLATION DROP ROW means invalid rows are dropped instead of failing the pipeline.
    CONSTRAINT valid_amount EXPECT (amount > 0) ON VIOLATION DROP ROW,
    -- valid_date: transaction_date cannot be in the future.
    -- current_date() returns today's date.
    -- If transaction_date is a timestamp, consider casting it to date or using current_timestamp().
    CONSTRAINT valid_date EXPECT (transaction_date <= current_date()) ON VIOLATION DROP ROW,
    -- valid_quantity: quantity must be between 1 and 10000 inclusive.
    -- BETWEEN includes both endpoints, so 1 and 10000 pass.
    CONSTRAINT valid_quantity EXPECT (quantity BETWEEN 1 AND 10000) ON VIOLATION DROP ROW
) AS SELECT * FROM STREAM(raw.transactions);
```

For Delta Lake tables, you can use CHECK constraints to enforce ranges at write time. A CHECK constraint is part of the table definition. When a write violates the constraint, the write fails. Existing data must satisfy the constraint when the constraint is added. The following example adds range constraints to existing Delta tables.

```sql
-- Add a CHECK constraint to an existing Delta table.
-- The constraint is enforced when new data is written.
-- If a write violates the constraint, the write fails.
-- Existing data must satisfy the constraint when it is added.
ALTER TABLE employees ADD CONSTRAINT valid_age CHECK (age >= 18 AND age <= 120);

-- Add a CHECK constraint that requires amount to be positive.
-- This prevents negative or zero amounts from being written.
ALTER TABLE transactions ADD CONSTRAINT positive_amount CHECK (amount > 0);
```

Range checks can also validate business rules that combine multiple conditions. The following expectation ensures discounts stay within bounds and enforces that only premium customers receive discounts over 50 percent. The comments explain the logic.

```python
# The @dp.expect decorator records the violation but keeps the row.
# Use this when you want to monitor data quality without stopping the pipeline.
@dp.expect("valid_discount", """
    discount_percent >= 0 
    AND discount_percent <= 100
    AND (discount_percent <= 50 OR customer_tier = 'PREMIUM')
""")
# Explanation:
# discount_percent >= 0: discount cannot be negative.
# discount_percent <= 100: discount cannot exceed 100 percent.
# discount_percent <= 50 OR customer_tier = 'PREMIUM':
#   If discount is 50 or less, any customer tier is allowed.
#   If discount is greater than 50, the customer must be PREMIUM.
# This enforces the business rule that only premium customers get large discounts.
```

## Null handling and type safety

Null handling is important in range checks. In SQL, a comparison with NULL returns UNKNOWN. Many systems treat UNKNOWN as not true, so the record may be considered invalid. Other systems, such as some CHECK constraints, may allow NULL because the constraint is only violated when the expression is FALSE. To avoid ambiguity, write the condition explicitly. If the column must not be null and must be in range, use `column IS NOT NULL AND column BETWEEN lower AND upper`. If null is acceptable, use `column IS NULL OR column BETWEEN lower AND upper`. For example, an optional discount column might use `discount_percent IS NULL OR discount_percent BETWEEN 0 AND 100`.

Type safety is also important. A range check only works correctly if the column has the expected type. If age is stored as a string, then `age BETWEEN 0 AND 150` may not behave as intended. The database might try to cast the string to a number, or it might compare strings lexicographically. Either way, the result may be surprising. It is better to enforce the correct schema before applying range checks. If you must handle dirty data, use explicit casts and handle cast failures separately.

## Date and time range checks

Date and time range checks are common. For example, a hire date should not be in the future. A transaction date should not be after today. A birth date should not be after today and should not be before a reasonable minimum date. Use `current_date()` for date-only comparisons and `current_timestamp()` for timestamp comparisons. Be careful with time zones. If your data is stored in UTC and your business logic uses local time, convert the values before comparing them. Also be careful when comparing a date column to a timestamp function. In some systems, the date is implicitly cast to a timestamp at midnight, which can affect boundary cases. If you want to allow today, use `transaction_date <= current_date()`. If you want to allow only dates before today, use `transaction_date < current_date()`.

## Choosing violation behavior

Different violation behaviors are appropriate for different situations. In declarative pipelines, `expect` records the violation and keeps the row. This is useful when you want to monitor data quality without interrupting the pipeline. `expect_or_drop` drops the invalid row. This is useful when invalid rows are not useful downstream and can be safely discarded. `expect_or_fail` fails the pipeline. This is useful when invalid data indicates a serious problem that must be fixed before the pipeline continues. `expect_or_quarantine` moves invalid rows to a quarantine table for later inspection. In SQL, `ON VIOLATION DROP ROW` drops invalid rows, while `ON VIOLATION FAIL UPDATE` fails the update. In Delta Lake, CHECK constraints fail the write. They do not drop rows. This means the entire write operation is rejected, and you must fix the data or the constraint before writing again.

## Testing and monitoring range checks

Range checks should be tested with edge cases. Test the lower bound, the upper bound, a value just below the lower bound, a value just above the upper bound, and a null value. For example, if the range is 0 to 150, test 0, 150, -1, 151, and null. If the range is `salary >= 0`, test 0, -1, and null. If the range is `hire_date <= current_date()`, test today, tomorrow, yesterday, and null. This helps you confirm that the check behaves as expected.

Monitoring is also important. In Databricks, expectations produce metrics that appear in the pipeline event log and the user interface. You can set up alerts when violation counts exceed a threshold. For Delta CHECK constraints, failed writes appear as errors in the job or query logs. You should monitor these errors because they indicate that data is not being written. If a constraint is too strict, it may block legitimate data. If it is too loose, it may allow bad data through.

## Performance considerations

Range checks are usually cheap because they are simple comparisons. They do not require complex joins or user-defined functions. However, performance can still be affected if the checks are applied to very large volumes of data or if they use expensive functions. Keep the expressions simple. Use built-in functions such as `current_date()` and `current_timestamp()`. Avoid calling expensive functions for every row if the value is constant for the query. Delta CHECK constraints are evaluated per row during writes. They do not create indexes, so they do not speed up reads. Their purpose is data quality, not query performance.

## Common mistakes

A common mistake is forgetting that BETWEEN is inclusive. If you want to exclude an endpoint, use strict comparison operators. Another mistake is ignoring nulls. If a column is nullable, decide whether null is valid and write the condition explicitly. A third mistake is using the wrong date function. If the column is a date, use `current_date()`. If the column is a timestamp, use `current_timestamp()`. A fourth mistake is assuming that a CHECK constraint will drop rows. It will not. It will fail the write. A fifth mistake is using `@dp.expect` when you meant `@dp.expect_or_fail`. The first records a warning and keeps the row. The second stops the pipeline. A sixth mistake is not testing the boundaries. Always test the lower and upper limits and the values just outside them.

## Summary

Range checking is a fundamental data quality technique. It confirms that numeric, date, and other values fall within acceptable bounds. You can define ranges with comparison operators or the BETWEEN clause. In declarative pipelines, you can use expectations with different violation behaviors. In SQL streaming tables, you can use constraints with ON VIOLATION actions. In Delta Lake, you can use CHECK constraints to enforce ranges at write time. You can combine multiple conditions to enforce business rules. Always handle nulls explicitly, test edge cases, and monitor violations. Range checks are simple, but they are powerful. They catch data entry errors, system glitches, and integration issues before those problems reach downstream consumers.
