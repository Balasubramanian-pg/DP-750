# Apply best practices for schema management

Managing schema effectively requires a combination of technical controls and operational practices. Schema management is not a one-time task. It is an ongoing discipline that spans the entire lifecycle of your data pipelines. It involves defining schemas, enforcing them, detecting changes, responding to changes, and documenting everything along the way. The best practices described here help you maintain data quality while adapting to the inevitable changes in your source systems. They help you avoid unexpected pipeline failures, data corruption, and downstream confusion. They also help you build trust in your data estate.

The following sections expand on each best practice with detailed explanations, code examples, and commented code. The examples use Databricks, Delta Lake, PySpark, and SQL, but the principles apply to any modern data platform.

## Document your expected schemas explicitly

Documentation is the foundation of effective schema management. If you do not know what your schema should look like, you cannot detect when it changes. If you do not have a reference for the expected schema, you cannot diagnose problems quickly. If you do not store schema definitions in a central place, you cannot coordinate changes across teams. Explicit documentation solves these problems. It makes your expectations clear. It makes changes visible. It makes debugging faster.

### Why documentation matters

When a source system changes its schema, you need to know what changed and how it affects your pipeline. If you have a documented expected schema, you can compare the incoming schema to the expected schema. You can see which columns were added, removed, or renamed. You can assess the impact on downstream consumers. You can decide whether to adapt, fail, or quarantine. Without documentation, you are guessing. You may not notice the change until a pipeline fails. You may not know which downstream reports are affected. You may not know who to contact about the change.

Documentation also helps with onboarding. New team members can read the schema documentation to understand the data model. They can see which columns are required, which are optional, and what types they should have. They can understand the relationships between tables. They can write queries and transformations with confidence.

Documentation also helps with governance. If you have a schema registry or a data catalog, you can publish your schemas there. Consumers can discover your data and understand its structure. They can subscribe to changes. They can provide feedback. This creates a collaborative data ecosystem.

### Store schema definitions in version control

Store schema definitions in version control alongside your pipeline code. This ensures that schema changes are tracked, reviewed, and versioned. You can use Git, Azure DevOps, or any other version control system. You can store schemas as SQL DDL files, JSON files, YAML files, or Avro schema files. The format depends on your preferences and your tooling. The key is to keep the schema definition close to the code that uses it.

When you store schemas in version control, you can see the history of changes. You can use pull requests to review schema changes. You can use branching to test changes in isolation. You can use tags to mark releases. You can roll back to a previous version if something goes wrong. This is much safer than making ad-hoc changes in a production database.

The following example shows a simple SQL DDL file that defines the expected schema for a customers table. You can store this file in a `schemas/` directory in your repository.

```sql
-- schemas/customers.sql
-- This file defines the expected schema for the customers table.
-- It is stored in version control alongside the pipeline code.
-- Any change to this file should be reviewed and approved.
-- The schema includes column names, data types, and nullability.
-- It also includes comments that explain the purpose of each column.

CREATE TABLE customers (
    customer_id INT NOT NULL COMMENT 'Unique identifier for the customer',
    name STRING COMMENT 'Full name of the customer',
    email STRING COMMENT 'Email address of the customer',
    phone_number STRING COMMENT 'Phone number of the customer, optional',
    created_at TIMESTAMP COMMENT 'Timestamp when the customer record was created',
    updated_at TIMESTAMP COMMENT 'Timestamp when the customer record was last updated'
);
```

You can also store schemas as JSON. The following example shows a JSON schema for the same table.

```json
{
  "type": "struct",
  "fields": [
    {"name": "customer_id", "type": "integer", "nullable": false, "metadata": {"comment": "Unique identifier for the customer"}},
    {"name": "name", "type": "string", "nullable": true, "metadata": {"comment": "Full name of the customer"}},
    {"name": "email", "type": "string", "nullable": true, "metadata": {"comment": "Email address of the customer"}},
    {"name": "phone_number", "type": "string", "nullable": true, "metadata": {"comment": "Phone number of the customer, optional"}},
    {"name": "created_at", "type": "timestamp", "nullable": true, "metadata": {"comment": "Timestamp when the customer record was created"}},
    {"name": "updated_at", "type": "timestamp", "nullable": true, "metadata": {"comment": "Timestamp when the customer record was last updated"}}
  ]

```

You can load this JSON schema in PySpark using the `StructType.fromJson` method. The following code shows how.

```python
# Import the StructType class.
from pyspark.sql.types import StructType

# Read the JSON schema file from the repository.
# The file is stored in version control.
# The path is relative to the repository root.
with open("schemas/customers.json", "r") as f:
    schema_json = f.read()

# Parse the JSON schema into a StructType.
# The fromJson method converts the JSON string into a Spark schema.
# This schema can be used to enforce the expected structure.
expected_schema = StructType.fromJson(schema_json)

# Print the schema to verify it.
expected_schema.printTreeString()
```

This approach makes your schema explicit and versioned. You can use the schema when reading data, writing data, or validating data. You can compare the expected schema to the actual schema. You can detect drift.

### Comparing expected and actual schemas

Once you have an expected schema, you can compare it to the actual schema of incoming data. This comparison can be done at runtime. If the schemas differ, you can take action. You can fail the pipeline, log a warning, or route the data to a quarantine table. The following PySpark code shows how to compare the expected schema to the actual schema of a streaming DataFrame.

```python
# Read a streaming source.
streaming_df = spark.readStream.table("raw_customers")

# Get the actual schema.
actual_schema = streaming_df.schema

# Compare the expected schema to the actual schema.
# The schema equality check compares field names, types, and nullability.
# If the schemas are equal, the code prints a message.
# If they are not equal, the code prints the differences.
if expected_schema == actual_schema:
    print("Schema matches the expected schema.")
else:
    print("Schema drift detected.")
    # Find columns that are in the actual schema but not in the expected schema.
    expected_names = {field.name for field in expected_schema.fields}
    actual_names = {field.name for field in actual_schema.fields}
    extra_columns = actual_names - expected_names
    missing_columns = expected_names - actual_names
    print(f"Extra columns: {extra_columns}")
    print(f"Missing columns: {missing_columns}")
    # You can also compare types for common columns.
    for field in expected_schema.fields:
        if field.name in actual_names:
            actual_field = actual_schema[field.name]
            if field.dataType != actual_field.dataType:
                print(f"Type mismatch for {field.name}: expected {field.dataType}, actual {actual_field.dataType}")
```

This code helps you detect drift early. You can integrate it into your pipeline. For example, you can use it in a `foreachBatch` function or in a data quality check. You can log the results to a monitoring system. You can send alerts.

## Implement alerting for schema drift

Alerting is essential for proactive schema management. Even if your pipeline handles schema drift automatically, you should be notified when drift occurs. Early awareness helps you understand evolving data patterns. It helps you anticipate downstream impacts. It helps you communicate with source system owners. It helps you update documentation and training materials.

### Why alerting matters

Schema drift is often a symptom of a larger change. A new column might indicate a new feature in a source application. A removed column might indicate a deprecated feature. A type change might indicate a bug or a data migration. If you are not aware of these changes, you may not understand why your data looks different. You may not be able to answer questions from business users. You may not be able to fix problems quickly.

Alerting also helps you maintain service level agreements. If a pipeline fails due to schema drift, you need to know immediately. If you wait for a user to report a problem, you may violate your SLA. If you detect the problem early, you can fix it before it affects users.

Alerting also helps you track the frequency and nature of schema changes. If a source system changes frequently, you may need to adjust your schema evolution strategy. If a source system changes in unexpected ways, you may need to talk to the source system owner. If a source system changes in ways that violate your data contract, you may need to enforce stricter controls.

### Detection points for schema drift

There are several points where you can detect schema drift. You can detect it when you read data. Auto Loader stores the inferred schema in a schema location. You can monitor this location for changes. You can detect it when you write data. Delta Lake's schema enforcement may fail a write if the schema does not match. You can monitor the error logs for these failures. You can detect it when you compare the expected schema to the actual schema, as shown in the previous section. You can detect it by monitoring the rescued data column. If rescued data appears, it means unexpected data was encountered. You can detect it by querying the Delta transaction log. The transaction log records schema changes over time.

Each detection point has advantages. Reading-time detection catches drift before it affects your pipeline. Write-time detection catches drift at the boundary of your table. Comparison-based detection gives you full control over the logic. Rescued data detection preserves the unexpected data. Transaction log detection gives you a historical view.

### Example: Querying Delta history for schema changes

Delta Lake stores the history of all operations in the transaction log. You can query this history to see when the schema changed. The following SQL query shows how to view the history of a table and filter for schema changes.

```sql
-- View the history of the customers table.
-- The history includes operations such as CREATE, WRITE, ALTER TABLE, and others.
-- The operationParameters column contains details about the operation.
-- For ALTER TABLE operations, it includes the changes that were made.
-- For WRITE operations, it includes the schema that was written.
-- You can filter for operations that changed the schema.
SELECT
    version,
    timestamp,
    operation,
    operationParameters,
    userMetadata
FROM (
    DESCRIBE HISTORY customers
)
WHERE operation IN ('CREATE TABLE', 'ALTER TABLE', 'WRITE', 'MERGE')
ORDER BY version DESC;
```

This query returns the version, timestamp, operation, parameters, and user metadata for each operation. You can inspect the `operationParameters` to see schema changes. For example, an `ALTER TABLE ADD COLUMNS` operation will show the new columns. A `WRITE` operation will show the schema of the written data. If the schema changed, you will see it in the parameters.

You can also use the `information_schema` to query column metadata. The following SQL query shows the columns of a table.

```sql
-- Query the information schema for column metadata.
-- This returns the column name, data type, and nullability.
-- You can use this to compare the current schema to the expected schema.
SELECT
    column_name,
    data_type,
    is_nullable
FROM information_schema.columns
WHERE table_name = 'customers'
ORDER BY ordinal_position;
```

You can schedule this query to run periodically. You can compare the results to the expected schema. If they differ, you can send an alert.

### Example: Monitoring rescued data

If you use Auto Loader with the `rescue` mode, unexpected data is stored in the rescued data column. You can monitor this column to detect schema drift. The following PySpark code shows how to count the number of records with rescued data.

```python
# Read the streaming table that contains the rescued data column.
df = spark.read.table("target_table")

# Count the number of records where the rescued data column is not null.
# The rescued data column is named "_rescued_data" in this example.
rescued_count = df.filter("_rescued_data IS NOT NULL").count()

# Print the count.
print(f"Number of records with rescued data: {rescued_count}")

# If the count is greater than zero, you can analyze the rescued data.
# The rescued data column is a JSON string.
# You can use JSON functions to extract the unexpected fields.
from pyspark.sql.functions import from_json, col
from pyspark.sql.types import MapType, StringType

# Define a schema for the rescued data.
# The rescued data is a map of field names to values.
rescued_schema = MapType(StringType(), StringType())

# Parse the rescued data and explode the map into rows.
rescued_df = df.filter("_rescued_data IS NOT NULL") \
    .select(from_json(col("_rescued_data"), rescued_schema).alias("rescued")) \
    .selectExpr("explode(rescued) as (field, value)")

# Group by field and count occurrences.
rescued_df.groupBy("field").count().orderBy("count", ascending=False).show()
```

This code counts the records with rescued data and analyzes which fields are being rescued. You can use this information to understand schema drift. You can set up an alert when the rescued count exceeds a threshold. You can also create a dashboard that shows rescued data trends over time.

## Use consistent naming conventions

Consistent naming conventions are a simple but powerful best practice. They reduce case-sensitivity issues. They make schema validation more predictable. They make it easier to write queries and transformations. They make it easier to understand the data model. They also make it easier to automate schema management.

### Why naming conventions matter

Different systems have different rules for naming. Some systems are case-sensitive. Some are case-insensitive. Some systems allow spaces and special characters. Some do not. When you integrate data from multiple sources, inconsistent naming can cause problems. For example, if one source uses `CustomerID` and another uses `customer_id`, you may need to rename columns to join the data. If you use case-insensitive matching, you may get unexpected results. If you use case-sensitive matching, you may get errors.

Consistent naming also makes schema validation easier. If you know that all column names follow a pattern, you can write a regular expression to validate them. You can detect columns that do not follow the pattern. You can enforce the pattern in your pipeline.

Consistent naming also makes documentation clearer. If all tables use the same naming conventions, readers can understand the structure quickly. They can predict column names. They can write queries without looking up the schema every time.

### Recommended naming conventions

There is no single correct naming convention. The best convention depends on your organization and your tools. However, some conventions are widely used and recommended. Use snake_case for column names. This means lowercase letters with underscores between words. For example, `customer_id` instead of `CustomerID` or `customerID`. Snake_case is easy to read and works well with SQL. Avoid spaces and special characters. Use only letters, numbers, and underscores. Avoid reserved words. Do not name a column `select`, `from`, `where`, `order`, `group`, or any other SQL keyword. If you must use a reserved word, quote it or prefix it. Use consistent suffixes for timestamps. For example, use `_at` for timestamps, `_date` for dates, and `_time` for times. Use consistent prefixes for foreign keys. For example, use `customer_id` for the primary key of the customers table and `customer_id` as a foreign key in other tables. Use singular names for tables. For example, use `customer` instead of `customers`. This is a matter of preference, but consistency is key.

### Enforcing naming conventions with code

You can enforce naming conventions in your pipeline. The following PySpark code shows how to validate column names against a regular expression. If any column name does not match, the code raises an error.

```python
import re
from pyspark.sql.functions import col

# Define the regular expression for valid column names.
# The pattern allows lowercase letters, numbers, and underscores.
# It requires the name to start with a letter.
# It allows underscores between words.
valid_column_pattern = re.compile(r"^[a-z][a-z0-9_]*$")

# Define a function to validate column names.
def validate_column_names(df):
    # Get the list of column names.
    columns = df.columns
    # Check each column name.
    for column in columns:
        if not valid_column_pattern.match(column):
            raise ValueError(f"Invalid column name: {column}. Column names must match {valid_column_pattern.pattern}")
    return df

# Read a streaming source.
streaming_df = spark.readStream.table("raw_customers")

# Validate the column names.
validated_df = validate_column_names(streaming_df)

# Write the validated DataFrame to a target table.
validated_df.writeStream.format("delta").option("checkpointLocation", "/path/to/checkpoint").start("customers")
```

This code raises an error if any column name does not match the pattern. You can customize the pattern to match your naming conventions. You can also use this function to rename columns automatically. For example, you can convert camelCase to snake_case. The following code shows how to rename columns.

```python
def to_snake_case(name):
    # Convert camelCase to snake_case.
    # Insert an underscore before each uppercase letter and convert to lowercase.
    import re
    s1 = re.sub('(.)([A-Z][a-z]+)', r'\1_\2', name)
    return re.sub('([a-z0-9])([A-Z])', r'\1_\2', s1).lower()

def rename_columns_to_snake_case(df):
    # Rename each column to snake_case.
    for column in df.columns:
        new_name = to_snake_case(column)
        if new_name != column:
            df = df.withColumnRenamed(column, new_name)
    return df

# Read a streaming source.
streaming_df = spark.readStream.table("raw_customers")

# Rename columns to snake_case.
renamed_df = rename_columns_to_snake_case(streaming_df)

# Write the renamed DataFrame to a target table.
renamed_df.writeStream.format("delta").option("checkpointLocation", "/path/to/checkpoint").start("customers")
```

This code ensures that all column names follow the snake_case convention. It makes your schema more predictable and easier to work with.

## Test schema handling in development

Testing is essential for schema management. Before deploying pipelines to production, verify that your schema enforcement and drift handling work as expected with test data that includes edge cases. Testing helps you catch problems early. It helps you understand how your pipeline behaves when the schema changes. It helps you validate that your error handling strategies are correct.

### Why testing is essential

Schema drift is unpredictable. It can happen at any time. It can take many forms. If you do not test your schema handling, you may not know how your pipeline will respond. You may assume that it will fail, but it might silently ignore the change. You may assume that it will adapt, but it might drop data. You may assume that it will quarantine, but it might write bad data to the target table. Testing eliminates these assumptions. It gives you confidence that your pipeline will behave correctly when schema drift occurs.

Testing also helps you validate your expectations and constraints. You can test that valid records pass and invalid records are dropped, warned, or cause a failure. You can test null handling. You can test type casting. You can test edge cases like empty strings, whitespace, and boundary values. Testing ensures that your data quality rules work as intended.

### Creating test cases for schema drift

Create test cases for each type of schema drift. Test adding a new column. Test removing a column. Test renaming a column. Test changing a column type. Test reordering columns. Test nested schema changes. For each test case, define the expected behavior. Does the pipeline fail? Does it adapt? Does it quarantine? Does it drop the record? Write a test that simulates the drift and asserts the expected behavior.

You can use a testing framework like pytest or unittest. You can create a small source table with a known schema. Write a pipeline that processes the data. Then change the source schema. Run the pipeline again. Check the target table and the quarantine table. Assert that the behavior matches your expectations.

The following example shows a pytest test for schema evolution. The test creates a source table, writes data, then adds a new column and writes data again. It verifies that the new column is added to the target table when schema evolution is enabled.

```python
import pytest
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, lit

# Create a Spark session.
spark = SparkSession.builder.appName("SchemaDriftTest").getOrCreate()

def test_schema_evolution_adds_new_column():
    # Create a source table with an initial schema.
    spark.sql("DROP TABLE IF EXISTS source_customers")
    spark.sql("""
        CREATE TABLE source_customers (
            customer_id INT,
            name STRING
        )
    """)
    # Insert some data.
    spark.sql("INSERT INTO source_customers VALUES (1, 'Alice'), (2, 'Bob')")

    # Create a target table with the same schema.
    spark.sql("DROP TABLE IF EXISTS target_customers")
    spark.sql("""
        CREATE TABLE target_customers (
            customer_id INT,
            name STRING
        )
    """)
    # Write the initial data to the target table.
    spark.sql("INSERT INTO target_customers SELECT * FROM source_customers")

    # Add a new column to the source table.
    spark.sql("ALTER TABLE source_customers ADD COLUMNS (email STRING)")
    # Insert data with the new column.
    spark.sql("INSERT INTO source_customers VALUES (3, 'Charlie', 'charlie@example.com')")

    # Write the source data to the target table with schema evolution enabled.
    spark.read.table("source_customers").write \
        .format("delta") \
        .mode("append") \
        .option("mergeSchema", "true") \
        .saveAsTable("target_customers")

    # Verify that the target table now has the email column.
    target_columns = spark.table("target_customers").columns
    assert "email" in target_columns

    # Verify that the new record has the email value.
    result = spark.sql("SELECT email FROM target_customers WHERE customer_id = 3").collect()
    assert result[0]["email"] == "charlie@example.com"

    # Verify that the old records have null for the email column.
    result = spark.sql("SELECT email FROM target_customers WHERE customer_id = 1").collect()
    assert result[0]["email"] is None
```

This test simulates additive schema drift. It verifies that schema evolution works as expected. You can write similar tests for other types of drift. You can also test the behavior of expectations and constraints. The following example shows a test for an expectation that drops records with null values.

```python
def test_expectation_drops_null_records():
    # Create a source table with a nullable column.
    spark.sql("DROP TABLE IF EXISTS source_orders")
    spark.sql("""
        CREATE TABLE source_orders (
            order_id INT,
            amount DECIMAL(10,2)
        )
    """)
    # Insert valid and invalid records.
    spark.sql("INSERT INTO source_orders VALUES (1, 100.00), (2, NULL), (3, 200.00)")

    # Create a target table.
    spark.sql("DROP TABLE IF EXISTS target_orders")
    spark.sql("""
        CREATE TABLE target_orders (
            order_id INT,
            amount DECIMAL(10,2)
        )
    """)

    # Define a pipeline with an expectation that drops records with null amount.
    # In a real pipeline, you would use the @dp.expect_or_drop decorator.
    # For testing, we simulate the behavior with a filter.
    valid_df = spark.table("source_orders").filter("amount IS NOT NULL")
    valid_df.write.mode("append").saveAsTable("target_orders")

    # Verify that only valid records were written.
    result = spark.sql("SELECT COUNT(*) FROM target_orders").collect()
    assert result[0][0] == 2
```

These tests help you validate your schema handling logic. You can run them as part of your continuous integration pipeline. You can catch regressions before they reach production.

## Consider the tradeoffs between strictness and flexibility

Schema management involves a tradeoff between strictness and flexibility. Strict schema enforcement catches problems early but requires more maintenance. Flexible approaches like schema evolution reduce operational overhead but might allow unexpected changes. The right balance depends on your business requirements, your data governance policies, and the criticality of your data.

### Strict schema enforcement

Strict schema enforcement means that any deviation from the expected schema causes the pipeline to fail. This is the default behavior of Delta Lake. It is also the behavior of the `failOnNewColumns` mode in Auto Loader. Strict enforcement is appropriate when data integrity is critical. It prevents unexpected columns from entering your tables. It prevents type mismatches from corrupting your data. It forces you to review every schema change. It gives you full control.

However, strict enforcement can cause frequent pipeline stops. If your source systems change frequently, you may spend a lot of time updating schemas and restarting pipelines. This can slow down your data delivery. It can also cause frustration for your team. Strict enforcement also requires a process for handling failures. You need alerting, runbooks, and clear ownership. Without these, failures may go unnoticed.

### Flexible schema evolution

Flexible schema evolution means that your pipeline automatically adapts to schema changes. New columns are added. Type changes are widened. Unexpected data is preserved in a rescued data column. Flexible evolution is appropriate when you want to minimize operational overhead. It keeps your pipeline running. It ensures that new data is not lost. It reduces the need for manual intervention.

However, flexible evolution can lead to unexpected changes. Your table schema may grow over time. New columns may appear that you did not anticipate. Downstream consumers may break if they are not prepared for new columns. Type changes may affect calculations. Flexible evolution also requires monitoring. You need to know what changes are happening. You need to review rescued data. You need to communicate with downstream consumers.

### Hybrid approaches

A hybrid approach combines strict and flexible elements. For example, you can use a bronze, silver, and quarantine architecture. The bronze layer is flexible. It accepts any schema. It uses Auto Loader with rescue mode to preserve unexpected data. The silver layer is strict. It has a stable schema. It uses expectations and constraints to enforce data quality. The quarantine layer captures records that cannot be processed. This approach gives you the best of both worlds. You do not lose data. You maintain a stable schema for downstream consumers. You have visibility into schema drift.

Another hybrid approach is to use schema evolution for some columns and strict enforcement for others. For example, you might allow new columns to be added automatically, but you might enforce strict types for critical columns. You can use expectations to check types and drop or quarantine invalid records. You can use CHECK constraints to enforce hard guarantees on the silver table.

### Decision framework

To choose the right balance, consider the following factors. Consider the criticality of the data. If invalid data can cause financial loss, regulatory violations, safety issues, or serious operational problems, lean toward strict enforcement. If the data is less critical, lean toward flexibility. Consider the frequency of schema changes. If the source schema changes frequently, lean toward flexibility. If it changes rarely, strict enforcement may be manageable. Consider the tolerance of downstream consumers. If downstream systems can handle new columns or missing columns, flexibility may be fine. If they require a stable schema, strict enforcement or a hybrid approach may be necessary. Consider your ability to recover. If you can easily reprocess data after a failure, strict enforcement may be acceptable. If reprocessing is difficult or expensive, flexibility may be better. Consider compliance and audit requirements. If you must retain all records for auditing, use flexibility with quarantine. If you must ensure that no unexpected schema changes are ever stored, use strict enforcement.

### Example: Bronze, silver, and quarantine architecture with Auto Loader

The following example shows a hybrid architecture using Auto Loader, Delta Lake, and expectations. The bronze layer uses Auto Loader with rescue mode. The silver layer uses expectations to drop invalid records. The quarantine layer captures invalid records. This example is conceptual but shows how the pieces fit together.

```python
from pyspark import pipelines as dp
from pyspark.sql.functions import col, current_timestamp, lit

# Bronze layer: ingest raw data with Auto Loader in rescue mode.
@dp.table
def bronze_customers():
    return (
        spark.readStream
            .format("cloudFiles")
            .option("cloudFiles.format", "json")
            .option("cloudFiles.schemaLocation", "/path/to/schema")
            .option("cloudFiles.schemaEvolutionMode", "rescue")
            .option("rescuedDataColumn", "_rescued_data")
            .load("/path/to/source")
    )

# Silver layer: select known columns, cast types, and apply expectations.
@dp.table
@dp.expect_or_drop("valid_customer_id", "customer_id IS NOT NULL")
@dp.expect_or_drop("valid_email", "email IS NOT NULL AND email LIKE '%@%'")
def silver_customers():
    return (
        spark.readStream.table("bronze_customers")
            .select(
                col("customer_id").cast("int").alias("customer_id"),
                col("name").cast("string").alias("name"),
                col("email").cast("string").alias("email")
            )
    )

# Quarantine layer: capture records that fail expectations.
@dp.table
def quarantine_customers():
    return (
        spark.readStream.table("bronze_customers")
            .filter("customer_id IS NULL OR email IS NULL OR email NOT LIKE '%@%'")
            .withColumn("quarantined_at", current_timestamp())
            .withColumn("reason", lit("Type or null validation failed"))
    )
```

In this example, the bronze layer accepts any schema. It uses rescue mode to preserve unexpected data in the `_rescued_data` column. The silver layer selects only the known columns. It casts them to the correct types. It applies expectations to drop records with null customer ID or invalid email. The quarantine layer captures records that fail the expectations. It adds a timestamp and a reason. This architecture gives you flexibility at the bronze layer and strictness at the silver layer. It preserves invalid records for analysis. It maintains a stable schema for downstream consumers.

## Summary

Managing schema effectively requires a combination of technical controls and operational practices. Document your expected schemas explicitly. Store schema definitions in version control alongside your pipeline code. When source systems change, you have a clear reference for understanding the impact. Implement alerting for schema drift. Configure your pipelines to send notifications when schema changes are detected, even if the pipeline handles them automatically. Early awareness helps you understand evolving data patterns. Use consistent naming conventions. Standardize column names across your data estate to reduce case-sensitivity issues and make schema validation more predictable. Test schema handling in development. Before deploying pipelines to production, verify that your schema enforcement and drift handling work as expected with test data that includes edge cases. Consider the tradeoffs between strictness and flexibility. Strict schema enforcement catches problems early but requires more maintenance. Flexible approaches like schema evolution reduce operational overhead but might allow unexpected changes. With these strategies in place, your data pipelines can maintain data quality while adapting to the inevitable changes in your source systems.
