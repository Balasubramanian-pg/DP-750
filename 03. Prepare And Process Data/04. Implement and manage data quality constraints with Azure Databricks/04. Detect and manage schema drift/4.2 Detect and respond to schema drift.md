# Detect and respond to schema drift

Schema drift occurs when the structure of incoming data changes over time. Your data pipelines must detect these changes and respond appropriately, either by adapting to the new schema or by alerting operators to investigate. Schema drift is not a type validation problem. Type validation checks whether values match expected types. Schema drift checks whether the structure of the data matches the expected structure. Structure includes column names, column presence, column order, and nested fields. A source system might add a new column, remove a column, rename a column, reorder columns, change a column type, or change the structure of a nested field. These changes happen independently of type validation. You can have perfectly valid types but still have schema drift. For example, all values in a new column might be valid strings, but the column itself is new and unexpected.

Azure Databricks provides several approaches for handling schema drift depending on your requirements. The two main approaches are to fail on schema mismatch or to automatically adapt to new columns. Each approach has tradeoffs. Failing on schema mismatch gives you control and prevents unexpected changes. Automatically adapting to new columns keeps the pipeline running but may introduce columns you did not expect. The right choice depends on your business requirements, your data governance policies, and the criticality of the data.

## What schema drift is

Schema drift is any change to the structure of data that occurs after the initial schema is defined. It is common in data pipelines that ingest data from external systems. External systems evolve. Applications add new features. Vendors change their APIs. Databases add columns. Files change their formats. These changes are often legitimate and necessary. But they can break pipelines that expect a fixed schema. Schema drift is not a bug in your pipeline. It is a natural consequence of integrating with systems that you do not fully control. The challenge is to detect it and respond to it gracefully.

Schema drift can be additive, subtractive, or modifying. Additive drift means a new column appears. Subtractive drift means a column disappears. Modifying drift means a column is renamed, reordered, or its type changes. Each type of drift requires a different strategy. Some drift is safe. Some drift is dangerous. Some drift should be accepted automatically. Some drift should be rejected and reviewed by a human. The right strategy depends on your business requirements and your data governance policies.

## Why detection and response matter

Detection is the first step. You cannot respond to schema drift if you do not know it happened. Detection can happen at different points in the pipeline. You can detect drift when you read the data. You can detect drift when you write the data. You can detect drift when you compare the incoming schema to the expected schema. You can detect drift by monitoring error logs, metrics, and alerts. Once you detect drift, you must decide how to respond. You can fail the pipeline. You can adapt the schema. You can quarantine the data. You can alert an operator. The response should match the severity of the drift and the criticality of the data.

If you ignore schema drift, several problems can occur. The pipeline may fail unexpectedly. Downstream consumers may receive data with missing columns or extra columns. Queries may break. Reports may be incorrect. Machine learning models may use features that are no longer present. Data quality may degrade. By detecting and responding to schema drift, you can maintain the reliability and trustworthiness of your data pipelines.

## Fail on schema mismatch

The strictest approach stops processing when schema drift is detected. This strategy works well when data structure changes require manual review before pipeline updates. With Auto Loader, you can configure this behavior using the `failOnNewColumns` mode. Auto Loader is a Databricks feature that incrementally and efficiently processes new data files as they arrive in cloud storage. It supports schema inference and schema evolution. The `failOnNewColumns` mode tells Auto Loader to stop the stream when it encounters a new column that is not defined in the schema.

The following Python code shows how to configure Auto Loader with `failOnNewColumns`. Each line is commented to explain what it does.

```python
# Start a streaming read using Auto Loader.
# The format is "cloudFiles", which is the Auto Loader format.
(spark.readStream
    .format("cloudFiles")
    # The cloudFiles.format option specifies the format of the source files.
    # In this example, the source files are JSON.
    .option("cloudFiles.format", "json")
    # The cloudFiles.schemaLocation option specifies where Auto Loader stores the schema.
    # Auto Loader uses this location to track the schema over time.
    # It stores the inferred schema and any schema evolution information.
    .option("cloudFiles.schemaLocation", "/path/to/schema")
    # The cloudFiles.schemaEvolutionMode option controls how Auto Loader handles schema changes.
    # The value "failOnNewColumns" means that the stream stops when a new column appears.
    # The stream raises an UnknownFieldException.
    # You must update the schema or remove the offending data before the pipeline can resume.
    .option("cloudFiles.schemaEvolutionMode", "failOnNewColumns")
    # The load method specifies the source path.
    # Auto Loader monitors this path for new files.
    .load("/path/to/source")
    # The writeStream method starts a streaming write.
    .writeStream
    # The checkpointLocation option specifies where the stream stores its progress.
    # This is required for streaming.
    .option("checkpointLocation", "/path/to/checkpoint")
    # The toTable method writes the stream to a Delta table named target_table.
    .toTable("target_table")
)
```

When Auto Loader encounters a new column not defined in the schema, the stream stops with an `UnknownFieldException`. You must update the schema or remove the offending data before the pipeline can resume. This approach is useful when you want to review every schema change before it is applied. It prevents unexpected columns from entering your table. It also prevents data loss because the pipeline stops instead of silently dropping the new column. However, it requires manual intervention. If the source system changes frequently, the pipeline may stop often. You need a process to handle these stops quickly.

The `UnknownFieldException` typically includes information about the new column. It tells you the column name and the file where it was found. You can use this information to decide how to proceed. You can add the column to the schema manually. You can update your pipeline code to handle the new column. You can also remove the offending file if it was sent by mistake. After you fix the issue, you can restart the stream. Auto Loader resumes from the last checkpoint.

## Automatically adapt to new columns

For scenarios where adding new columns is acceptable, you can enable schema evolution. This approach automatically adds new columns to the target table without manual intervention. Schema evolution is convenient. It keeps the pipeline running. It ensures that new data is not lost. However, it also means that the table schema can change without review. This can break downstream consumers. You should use schema evolution carefully. It is often better to have a governance process. For example, you might require that new columns are reviewed before they are added to production tables. You can use a separate process to add columns with `ALTER TABLE ADD COLUMNS`. Then the pipeline can continue with the new schema.

Enable schema evolution for write operations using the `mergeSchema` option. The following Python code shows how to write a DataFrame to a Delta table with schema evolution. Each line is commented.

```python
# Write a DataFrame to a Delta table.
(df.write
    # The format is "delta".
    .format("delta")
    # The mode is "append".
    # This adds new data to the existing table without overwriting it.
    .mode("append")
    # The mergeSchema option enables schema evolution.
    # When set to "true", Delta Lake adds new columns from the DataFrame to the target table.
    # Existing rows get null for the new columns.
    # New rows get the values from the DataFrame.
    .option("mergeSchema", "true")
    # The saveAsTable method writes the DataFrame to a table named target_table.
    .saveAsTable("target_table")
)
```

For `MERGE` operations, use the schema evolution syntax. The following SQL code shows how to merge data with schema evolution. Each line is commented.

```sql
-- Merge data from a source into a target table with schema evolution.
-- The WITH SCHEMA EVOLUTION clause allows new columns from the source to be added to the target.
MERGE WITH SCHEMA EVOLUTION INTO target_table t
-- The USING clause specifies the source data.
USING source_data s
-- The ON clause specifies the join condition.
ON t.customer_id = s.customer_id
-- The WHEN MATCHED clause specifies what to do when a row matches.
-- UPDATE SET * updates all columns in the target with values from the source.
WHEN MATCHED THEN UPDATE SET *
-- The WHEN NOT MATCHED clause specifies what to do when a row does not match.
-- INSERT * inserts all columns from the source into the target.
WHEN NOT MATCHED THEN INSERT *
```

New columns from the source are automatically added to the target table. However, you should carefully consider when to use schema evolution. Automatic changes might introduce columns you did not expect. They might also introduce columns with names that conflict with existing columns. They might introduce columns with types that are not compatible with downstream consumers. You should monitor schema evolution and review changes regularly.

## Choosing between fail and adapt

The choice between failing on schema mismatch and automatically adapting to new columns depends on several factors. Consider the criticality of the data. If invalid data can cause financial loss, regulatory violations, safety issues, or serious operational problems, failing may be safer. Failing forces a human to review the change. If the data is less critical and the new columns are likely to be useful, adapting may be acceptable.

Consider the frequency of schema changes. If the source schema changes frequently, failing may cause frequent pipeline stops. This can be frustrating and time-consuming. Adapting may be more practical. If the source schema changes rarely, failing may be fine. You can review each change as it happens.

Consider the tolerance of downstream consumers. If downstream systems can handle new columns or missing columns, adapting may be fine. If downstream systems require a stable schema, failing may be necessary. If downstream systems cannot tolerate any unexpected changes, failing is the safest choice.

Consider your ability to recover. If you can easily reprocess data after a failure, failing may be acceptable. If reprocessing is difficult or expensive, adapting may be better because it allows the pipeline to continue. However, adapting can also cause problems if the new schema is not what you want. You may need to quarantine the data instead.

Consider compliance and audit requirements. If you must retain all records for auditing, do not drop data. Use adapt and quarantine. If you must ensure that no unexpected schema changes are ever stored, use fail.

## Other response options

Failing and adapting are the two main approaches. But there are other options. You can warn. You can log a warning when schema drift is detected but continue processing. This gives you visibility without stopping the pipeline. You can quarantine. You can route records with unexpected schemas to a quarantine table for later analysis. This preserves the data without polluting the target table. You can use a bronze, silver, and quarantine architecture. The bronze layer accepts any schema. The silver layer has a stable schema. The quarantine layer captures records that cannot be processed.

You can also use schema contracts. A schema contract is an agreement between the producer and the consumer about the structure of the data. The producer agrees to send data with a specific schema. The consumer agrees to process data with that schema. If the producer changes the schema, they must update the contract and notify the consumer. Schema contracts help prevent unexpected schema drift. They make schema changes intentional and coordinated.

## Monitoring and alerting

You should monitor schema drift. Set up alerts when the schema changes. You can use the pipeline event log, the Delta transaction log, or a custom monitoring solution. For example, you can query the Delta table history to see when columns were added or removed. You can use the `DESCRIBE HISTORY` command to view the history of a Delta table. The following SQL shows how to view the history. Each line is commented.

```sql
-- View the history of the target_table.
-- The history includes operations such as CREATE, WRITE, ALTER TABLE, and others.
-- You can see when the schema changed and what changed.
DESCRIBE HISTORY target_table;
```

You can also use the `DESCRIBE DETAIL` command to view the current schema. The following SQL shows how to view the schema. Each line is commented.

```sql
-- View the details of the target_table.
-- The output includes the schema, partitioning, and other metadata.
DESCRIBE DETAIL target_table;
```

You can set up alerts based on these queries. For example, you can alert when a new column is added to a table. You can alert when a write fails due to schema mismatch. You can alert when the quarantine table grows beyond a threshold. You can also track the number of records written to quarantine tables. If the number increases, investigate the cause.

## Testing schema drift handling

You should test your schema drift handling. Create test cases for each type of drift. Test adding a new column. Test removing a column. Test renaming a column. Test changing a type. Test nested changes. Verify that your pipeline handles each case correctly. For example, if you use `mergeSchema`, verify that the new column is added to the target table. If you fail on new columns, verify that the stream stops with the expected exception. If you quarantine, verify that the invalid records are captured.

You can use a testing framework to automate these tests. Create a small source table with a known schema. Write a pipeline that processes the data. Then change the source schema. Run the pipeline again. Check the target table and the quarantine table. Assert that the behavior matches your expectations. This helps you catch problems before they affect production.

## Best practices for handling schema drift

Define your expected schema explicitly. Do not rely on schema inference. Explicit schemas make your pipeline more predictable and easier to debug.

Use schema evolution carefully. Schema evolution is convenient, but it can lead to unexpected changes. Have a governance process for schema changes. Review new columns before adding them to production tables.

Prefer additive changes over subtractive changes. Adding a column is usually safe. Removing a column is usually breaking. Renaming a column is breaking. Type changes can be breaking. Coordinate breaking changes with downstream consumers.

Use a bronze, silver, and quarantine architecture. The bronze layer can accept schema drift. The silver layer has a stable schema. The quarantine layer captures records that cannot be processed.

Monitor schema drift. Set up alerts for schema changes and write failures. Investigate unexpected changes.

Document your schema. Keep a record of the expected columns and types. Update the documentation when the schema changes.

Test your schema drift handling. Create test cases for each type of drift. Verify that your pipeline behaves as expected.

Use schema contracts or a schema registry if you have many producers and consumers. These tools help manage schema evolution at scale.

## Summary

Schema drift occurs when the structure of incoming data changes over time. Your data pipelines must detect these changes and respond appropriately, either by adapting to the new schema or by alerting operators to investigate. Azure Databricks provides several approaches for handling schema drift depending on your requirements. You can fail on schema mismatch using Auto Loader with `failOnNewColumns`. This stops the stream with an `UnknownFieldException` and requires manual review. You can automatically adapt to new columns using `mergeSchema` for writes or `MERGE WITH SCHEMA EVOLUTION` for merge operations. This adds new columns to the target table without manual intervention. You should choose the approach that matches your business requirements, your data governance policies, and the criticality of the data. You should monitor schema drift, test your handling, and follow best practices. By detecting and responding to schema drift, you can keep your pipelines running smoothly even as your data sources evolve.
