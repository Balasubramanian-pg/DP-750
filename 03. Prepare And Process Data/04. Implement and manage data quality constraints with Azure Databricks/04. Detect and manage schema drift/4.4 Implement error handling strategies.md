## Implement error handling strategies

Beyond automatic schema management, you need strategies for handling records that violate your data quality rules. Lakeflow Spark Declarative Pipelines provides expectations that let you define constraints and specify how to handle violations. Expectations are data quality rules attached to a dataset. They are evaluated as data flows through the pipeline. They can warn, drop, or fail depending on the action you choose. They also produce metrics that you can view in the pipeline UI. This section explains three common error handling strategies: dropping invalid records, failing on critical violations, and quarantining problematic records. Each strategy has different tradeoffs. The right choice depends on the criticality of the data, the tolerance of downstream consumers, and your ability to recover from failures.

## Understanding expectations in declarative pipelines

In Lakeflow Spark Declarative Pipelines, expectations are defined using decorators in Python or constraints in SQL. The decorator `@dp.expect` logs violations but keeps the record. The decorator `@dp.expect_or_drop` drops the record before it reaches the target table. The decorator `@dp.expect_or_fail` stops the pipeline when a violation occurs. In SQL, the equivalent is `CONSTRAINT ... EXPECT ... ON VIOLATION DROP ROW` or `ON VIOLATION FAIL UPDATE`. If you omit the `ON VIOLATION` clause, the default is to warn. Expectations are part of the pipeline definition. They are evaluated as data is processed. They produce metrics that show how many records passed, how many failed, and how many were dropped or caused a failure. These metrics help you monitor data quality and diagnose problems.

Expectations can check many things. They can check that a column is not null. They can check that a value falls within a range. They can check that a value can be cast to a specific type. They can check that a string matches a pattern. They can combine multiple conditions using logical operators. Expectations are written as SQL expressions. They must evaluate to true for a record to pass. If the expression evaluates to false or unknown, the record fails the expectation. The action you choose determines what happens next.

## Drop invalid records

Use expectations to filter out records that do not meet your structure requirements. Dropping invalid records is a form of data cleansing. It ensures that only valid records reach downstream consumers. It keeps the target table clean. It allows the pipeline to continue processing other records. It also produces metrics that show how many records were dropped. You can monitor these metrics to understand data quality trends.

The following Python example defines a streaming table with an expectation that drops records missing required columns. Each line is commented.

```python
# Import the pipelines module from pyspark.
# This module provides the decorators for defining tables and expectations.
from pyspark import pipelines as dp

# The @dp.table decorator defines a streaming table or materialized view.
# The function below returns the input data for the table.
@dp.table
# The @dp.expect_or_drop decorator adds an expectation that drops invalid records.
# The first argument is the expectation name: "required_columns_present".
# The second argument is the SQL expression: "customer_id IS NOT NULL AND email IS NOT NULL".
# The expression checks that both customer_id and email are not null.
# If both are not null, the record passes.
# If either is null, the record fails the expectation.
# Because this is @dp.expect_or_drop, the invalid record is dropped before reaching the target table.
# The pipeline continues processing other records.
# Metrics record how many records were dropped.
@dp.expect_or_drop("required_columns_present", 
    "customer_id IS NOT NULL AND email IS NOT NULL")
def validated_customers():
    # The function returns a streaming DataFrame.
    # The DataFrame is read from the raw_customers table.
    # The raw table contains the data as it arrived from the source.
    # The expectation is applied to each record as it is processed.
    # Records that fail the expectation are dropped.
    return spark.readStream.table("raw_customers")
```

In this example, the expectation `required_columns_present` checks that `customer_id` and `email` are both not null. If a record has a null `customer_id` or a null `email`, it is dropped. The target table `validated_customers` receives only records that pass the expectation. The pipeline continues processing. The metrics show how many records were dropped. You can view these metrics in the pipeline UI by selecting the dataset and opening the Data quality tab.

Dropping invalid records is useful when the invalid records are not needed and can be safely discarded. It is also useful when you want to keep the pipeline running without manual intervention. However, dropping records can hide problems. If you drop too many records, you may not notice that a source system is broken. You should monitor the drop count. If it increases suddenly, investigate the cause. Consider writing dropped records to a quarantine table for later analysis. This combines the benefits of dropping with the benefits of preservation.

## Fail on critical violations

When data structure issues indicate a serious problem, configure expectations to halt processing. Failing the pipeline prevents invalid data from propagating downstream. It forces you to fix the problem before the pipeline can continue. It is appropriate when data integrity is critical and invalid records are unacceptable. It is also appropriate when you want to review every violation manually. However, failing the pipeline can cause delays. It requires manual intervention. You should use it sparingly and only for rules that are truly critical.

The following SQL example creates a streaming table with a constraint that fails the pipeline when records are missing required columns. Each line is commented.

```sql
-- Create or refresh a streaming table named validated_orders.
-- The table has a constraint named valid_structure.
CREATE OR REFRESH STREAMING TABLE validated_orders (
    -- The constraint checks that order_id and product_id are not null.
    -- The EXPECT clause contains the Boolean expression.
    -- If both are not null, the record passes.
    -- If either is null, the record fails the constraint.
    -- ON VIOLATION FAIL UPDATE means the pipeline stops immediately.
    -- The current transaction rolls back.
    -- No records from the current update are written to the target.
    CONSTRAINT valid_structure 
    EXPECT (order_id IS NOT NULL AND product_id IS NOT NULL) 
    ON VIOLATION FAIL UPDATE
)
-- The AS SELECT clause defines the source of the data.
-- STREAM(raw_orders) reads from the raw_orders streaming source.
-- The constraint is applied to each record as it is processed.
AS SELECT * FROM STREAM(raw_orders);
```

In this example, the constraint `valid_structure` checks that `order_id` and `product_id` are both not null. If any record violates this constraint, the pipeline stops. The current transaction rolls back. No records from the current update are written. The pipeline does not resume until you fix the problem. You might fix the source data, update the pipeline code, or remove the offending records. After you fix the issue, you can restart the pipeline. It resumes from the last checkpoint.

Failing on critical violations is useful when you cannot tolerate invalid data. For example, if you are loading financial transactions, a missing order ID might indicate a serious problem. Writing that record to the target could cause incorrect financial calculations. Failing the pipeline prevents the bad data from spreading. It also alerts the team that something is wrong. You should have proper alerting and runbooks so that the team can respond quickly when a fail occurs. You should also test the failure behavior to ensure that it works as expected.

## Quarantine problematic records

For a balanced approach, route invalid records to a separate quarantine table while allowing valid records to proceed. This pattern lets you investigate problematic records without blocking your main data flow. It preserves the invalid records for later analysis. It also keeps the target table clean. It is often the best choice when you want to continue processing valid data while still capturing bad data for review.

The following Python example defines two tables: one for valid transactions and one for quarantine transactions. Each line is commented.

```python
# Import the pipelines module from pyspark.
from pyspark import pipelines as dp

# Define a table for valid transactions.
@dp.table
def valid_transactions():
    # Read from the raw_transactions streaming source.
    return (
        spark.readStream.table("raw_transactions")
        # Filter to keep only records where amount and transaction_date are not null.
        # The filter method applies a SQL expression.
        # Records that satisfy the expression are kept.
        # Records that do not satisfy the expression are excluded.
        .filter("amount IS NOT NULL AND transaction_date IS NOT NULL")
    )

# Define a table for quarantine transactions.
@dp.table
def quarantine_transactions():
    # Read from the same raw_transactions streaming source.
    return (
        spark.readStream.table("raw_transactions")
        # Filter to keep only records where amount or transaction_date is null.
        # The OR condition means a record is quarantined if either column is null.
        # Records that satisfy the expression are kept in the quarantine table.
        .filter("amount IS NULL OR transaction_date IS NULL")
    )
```

In this example, the `valid_transactions` table contains records where both `amount` and `transaction_date` are not null. The `quarantine_transactions` table contains records where either `amount` or `transaction_date` is null. The two tables are complementary. Every record from the raw source goes to exactly one of the two tables. The valid records proceed to downstream consumers. The invalid records are preserved for investigation. You can analyze the quarantine table to understand why the records failed. You can count how many records are quarantined. You can group them by reason. You can set up alerts when the quarantine count exceeds a threshold.

This pattern is powerful because it does not block the pipeline. It does not drop data. It does not stop processing. It simply separates good data from bad data. You can then decide how to handle the bad data. You might fix the source system. You might update your validation logic. You might reprocess the quarantined records after fixing the issue. You might delete them if they are not needed. The choice is yours.

You can enhance the quarantine pattern by adding a reason column. The following Python example shows how to add a reason column using the `withColumn` method and a `when` expression. Each line is commented.

```python
# Import the required functions.
from pyspark import pipelines as dp
from pyspark.sql.functions import col, when, current_timestamp, lit

# Define a table for quarantine transactions with a reason.
@dp.table
def quarantine_transactions_with_reason():
    # Read from the raw_transactions streaming source.
    df = spark.readStream.table("raw_transactions")
    # Add a reason column.
    # The when function checks the first condition.
    # If amount is null, it returns 'Missing amount'.
    # If not, it checks the next condition.
    # If transaction_date is null, it returns 'Missing transaction_date'.
    # If neither condition is true, it returns 'Unknown'.
    # The otherwise method provides the default value.
    df_with_reason = df.withColumn(
        "reason",
        when(col("amount").isNull(), lit("Missing amount"))
        .when(col("transaction_date").isNull(), lit("Missing transaction_date"))
        .otherwise(lit("Unknown"))
    )
    # Add a timestamp column to record when the record was quarantined.
    df_with_reason = df_with_reason.withColumn("quarantined_at", current_timestamp())
    # Filter to keep only records that have a reason other than 'Unknown'.
    # Actually, we want to keep records where either amount or transaction_date is null.
    # So we filter on the original conditions.
    return df_with_reason.filter("amount IS NULL OR transaction_date IS NULL")
```

This example adds a `reason` column that explains why the record was quarantined. It also adds a `quarantined_at` timestamp. This makes it easier to diagnose problems. You can group quarantined records by reason and by day. You can see trends over time. You can prioritize fixes based on the most common reasons.

## Comparing the three strategies

Each strategy has advantages and disadvantages. Dropping invalid records is simple and keeps the pipeline running. It is useful when invalid records are not needed. However, it can hide problems. It can also cause data loss if you later realize that the dropped records were important. Failing on critical violations is strict and prevents invalid data from propagating. It forces you to fix problems. However, it can cause frequent pipeline stops. It requires manual intervention. Quarantining problematic records is balanced. It keeps the pipeline running and preserves invalid records for analysis. It does not block the main data flow. It does not drop data. However, it requires additional storage and processing. It also requires you to monitor and manage the quarantine table.

The right choice depends on the criticality of the data. For non-critical data, dropping may be sufficient. For critical data, failing may be necessary. For data where you want to investigate problems without blocking the pipeline, quarantine is the best choice. You can also combine strategies. For example, you might drop records with minor issues, fail on records with serious issues, and quarantine records with unknown issues. You can apply different expectations to different columns or different datasets.

## Using expectations with type checking

Expectations are often used with type checking. You can use `try_cast` to check whether a value can be converted to a target type. The following Python example shows an expectation that drops records where the amount cannot be cast to a decimal. Each line is commented.

```python
@dp.table
@dp.expect_or_drop("valid_amount", "try_cast(amount AS DECIMAL(10,2)) IS NOT NULL")
def validated_transactions():
    return spark.readStream.table("raw_transactions")
```

In this example, the expectation `valid_amount` checks that `amount` can be cast to `DECIMAL(10,2)`. If the cast fails, `try_cast` returns null. The expression `try_cast(...) IS NOT NULL` evaluates to false. The record is dropped. This is a common pattern for type validation. You can combine it with other expectations. For example, you can also check that `transaction_date` can be cast to a date. You can use multiple `@dp.expect_or_drop` decorators. They are applied in order. A record must pass all expectations to be written to the target table.

## Using expectations with null checks

Null checks are another common use of expectations. The following SQL example creates a streaming table with a constraint that drops records where the customer ID is null. Each line is commented.

```sql
CREATE OR REFRESH STREAMING TABLE validated_customers (
    CONSTRAINT valid_customer_id 
    EXPECT (customer_id IS NOT NULL) 
    ON VIOLATION DROP ROW
) AS SELECT * FROM STREAM(raw_customers);
```

In this example, the constraint `valid_customer_id` checks that `customer_id` is not null. If it is null, the record is dropped. The pipeline continues. Metrics record the drop. You can view these metrics in the pipeline UI.

## Monitoring and metrics

Expectations produce metrics that you can view in the pipeline UI. Select a dataset with expectations and open the Data quality tab. The metrics show how many records passed, how many failed, how many were dropped, and how many were warned. You can also see pass rates over time. These metrics help you monitor validation pass rates and identify systematic data quality issues. You can set up alerts when violation counts exceed a threshold. For example, if the drop count for `valid_amount` suddenly increases, investigate the source system. If the pass rate falls below a certain percentage, consider whether the rule is too strict or whether the source data has a problem. You can also query the pipeline event log for custom monitoring and reporting.

## Best practices for error handling

Choose the right action for each expectation. Use `expect` for monitoring. Use `expect_or_drop` for data cleansing. Use `expect_or_fail` for critical data integrity. Do not use `expect_or_fail` for every rule. It can cause frequent pipeline stops. Do not use `expect_or_drop` for critical data. You might lose important records. Use quarantine for balanced handling.

Name your expectations clearly. A good name describes the rule. For example, `valid_amount` is better than `check1`. Meaningful names make it easier to understand the metrics and diagnose failures.

Handle nulls explicitly. Decide whether null is acceptable for each column. If null is acceptable, add an `IS NULL` condition. If null is not acceptable, use `IS NOT NULL` without the `IS NULL` condition.

Test your expectations thoroughly. Create sample data with valid values, invalid values, nulls, empty strings, and boundary values. Verify that valid records pass and invalid records are handled correctly. Test each action: warn, drop, and fail.

Monitor your metrics. Set up alerts for unexpected changes. Investigate sudden increases in violations. Use the metrics to improve data quality at the source.

Document your expectations. Keep a record of the rules and the reason for each rule. This helps new team members understand the data model. It also helps when you need to modify or remove an expectation.

Use a bronze, silver, and quarantine architecture. The bronze layer stores raw data. The silver layer stores cleaned data. The quarantine layer stores invalid records. This pattern separates concerns and makes it easier to manage data quality.

## Summary

Lakeflow Spark Declarative Pipelines provides expectations that let you define constraints and specify how to handle violations. You can drop invalid records using `@dp.expect_or_drop` or `ON VIOLATION DROP ROW`. You can fail on critical violations using `@dp.expect_or_fail` or `ON VIOLATION FAIL UPDATE`. You can quarantine problematic records by routing them to a separate table. Each strategy has tradeoffs. The right choice depends on the criticality of the data and your business requirements. Expectations produce metrics that you can view in the pipeline UI. You should monitor these metrics, test your expectations, and follow best practices. By implementing robust error handling strategies, you can maintain high data quality and keep your pipelines running smoothly.
