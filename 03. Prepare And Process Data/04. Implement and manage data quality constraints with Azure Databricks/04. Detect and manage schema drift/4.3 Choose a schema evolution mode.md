## Choose a schema evolution mode

Auto Loader is a Databricks feature that incrementally and efficiently processes new data files as they arrive in cloud storage. It supports schema inference, schema evolution, and rescued data columns. The option `cloudFiles.schemaEvolutionMode` controls how Auto Loader responds when the schema of incoming data changes. There are five schema evolution modes. Choosing the right mode depends on whether you need strict control, automatic adaptation, or a way to capture unexpected data without blocking the pipeline. Each mode has different behavior when a new column appears or when a column type changes. Understanding these modes helps you build pipelines that are resilient to schema drift while still protecting data quality.

## Overview of the five schema evolution modes

The five modes are `addNewColumns`, `rescue`, `failOnNewColumns`, `none`, and `addNewColumnsWithTypeWidening`. The default mode is `addNewColumns`. Each mode determines whether the stream stops, whether the schema evolves, and whether unexpected data is preserved. The modes range from strict to flexible. `failOnNewColumns` is the strictest. It stops the stream and requires manual intervention. `rescue` is the most flexible for preserving unexpected data without changing the schema. `none` silently ignores new columns unless a rescued data column is configured. `addNewColumnsWithTypeWidening` is like `addNewColumns` but also handles supported type widening automatically.

## addNewColumns mode

The `addNewColumns` mode is the default. When a new column appears in the source data, the stream stops. The new column is added to the schema on restart. Existing column types are unchanged. This mode balances control and convenience. It does not silently ignore new columns. It does not automatically change existing types. It stops the stream so that you are aware of the change. When you restart the stream, Auto Loader adds the new column to the schema. Existing rows get null for the new column. New rows get the values from the source. This mode is useful when you want to review new columns before they are used, but you do not want to manually update the schema every time. The restart can be automated, but the stop gives you an opportunity to monitor and alert.

## rescue mode

The `rescue` mode never evolves the schema. Unexpected data is stored in the rescued data column. The stream continues. This mode is designed for preserving data that does not match the schema without modifying the target structure. When a new column appears, a type mismatch occurs, or a case difference is detected, the unexpected data is written to a separate column, typically named `_rescued_data`. The main columns remain unchanged. The stream continues processing without interruption. You can analyze the rescued data later to understand schema changes. This mode is useful when you want to avoid pipeline interruptions and investigate schema drift asynchronously. It is also useful when you are ingesting data from many sources and you cannot control the schema. The rescued data column acts as a safety net. It ensures that no data is lost, even if it does not fit the expected schema.

## failOnNewColumns mode

The `failOnNewColumns` mode is the strictest. When a new column appears, the stream stops with an `UnknownFieldException`. You must update the schema manually or remove the offending data before the pipeline can resume. This mode is useful when data structure changes require manual review before pipeline updates. It gives you full control. It prevents unexpected columns from entering your table. It also prevents data loss because the pipeline stops instead of silently dropping the new column. However, it requires manual intervention. If the source system changes frequently, the pipeline may stop often. You need a process to handle these stops quickly. You can configure this mode with Auto Loader using the option `cloudFiles.schemaEvolutionMode` set to `failOnNewColumns`. When the stream stops, the error message includes information about the new column. You can use this information to decide how to proceed. You can add the column to the schema manually, update your pipeline code, or remove the offending file. After you fix the issue, you can restart the stream. Auto Loader resumes from the last checkpoint.

## none mode

The `none` mode never evolves the schema. New columns are silently ignored unless a rescued data column is set. If a new column appears and no rescued data column is configured, the data in that column is lost. The stream continues. This mode is useful when you want to enforce a fixed schema and you do not care about new columns. However, it can cause data loss if you are not careful. If you set a rescued data column, the new column data is stored there. The stream continues. This mode is similar to `rescue` but without the explicit intention of preserving unexpected data. In `none` mode, the rescued data column is optional. In `rescue` mode, the rescued data column is the primary mechanism. You should use `none` mode only when you are certain that new columns are not important. Otherwise, use `rescue` mode to preserve the data.

## addNewColumnsWithTypeWidening mode

The `addNewColumnsWithTypeWidening` mode is like `addNewColumns` but also handles supported type changes automatically. When a new column appears, the stream stops. On restart, the new column is added to the schema. When a supported type change occurs, such as `INT` to `LONG`, the column type is widened automatically. This is useful when source systems gradually expand numeric ranges. For example, a row count column might grow beyond the `INT` limit. Instead of routing those records to the rescued data column, Auto Loader widens the column type automatically on restart. Unsupported type changes, such as `INT` to `STRING`, are still captured in the rescued data column when this mode is active. This mode requires Databricks Runtime 16.4 or above and is in Public Preview. It is useful when you want the convenience of automatic schema evolution for both new columns and type widening, but you still want to capture unsupported changes for review.

## Code example for addNewColumnsWithTypeWidening

The following Python code configures Auto Loader to use the `addNewColumnsWithTypeWidening` mode. Each line is commented to explain what it does.

```python
# Start a streaming read using Auto Loader.
# The format is "cloudFiles", which is the Auto Loader format.
(spark.readStream
    .format("cloudFiles")
    # The cloudFiles.format option specifies the format of the source files.
    # In this example, the source files are JSON.
    .option("cloudFiles.format", "json")
    # The cloudFiles.schemaLocation option specifies where Auto Loader stores the schema.
    # Auto Loader uses this location to track the schema over time.
    # It stores the inferred schema and any schema evolution information.
    .option("cloudFiles.schemaLocation", "/path/to/schema")
    # The cloudFiles.schemaEvolutionMode option controls how Auto Loader handles schema changes.
    # The value "addNewColumnsWithTypeWidening" enables both new columns and type widening.
    # New columns are added to the schema.
    # Supported type changes, such as INT to LONG, are widened automatically.
    # This mode requires Databricks Runtime 16.4 or above and is in Public Preview.
    .option("cloudFiles.schemaEvolutionMode", "addNewColumnsWithTypeWidening")
    # The load method specifies the source path.
    # Auto Loader monitors this path for new files.
    .load("/path/to/source")
    # The writeStream method starts a streaming write.
    .writeStream
    # The checkpointLocation option specifies where the stream stores its progress.
    # This is required for streaming.
    .option("checkpointLocation", "/path/to/checkpoint")
    # The toTable method writes the stream to a Delta table named target_table.
    .toTable("target_table")
)
```

In this code, the stream reads JSON files from a source path. The schema location is where Auto Loader stores the evolving schema. The schema evolution mode is set to `addNewColumnsWithTypeWidening`. When a new column appears, the stream stops. On restart, the new column is added. When a supported type change occurs, the column type is widened automatically. For example, if a column is initially `INT` and later values exceed the `INT` range, Auto Loader changes the column type to `LONG`. Unsupported type changes, such as `INT` to `STRING`, are captured in the rescued data column if it is configured. The stream writes to a Delta table named `target_table`. The checkpoint location ensures exactly-once processing.

## Code example for rescue mode

The following Python code configures Auto Loader to use the `rescue` mode. Each line is commented to explain what it does.

```python
# Start a streaming read using Auto Loader.
(spark.readStream
    .format("cloudFiles")
    # The source files are JSON.
    .option("cloudFiles.format", "json")
    # The schema location stores the schema.
    # In rescue mode, the schema never evolves.
    # The stored schema remains fixed.
    .option("cloudFiles.schemaLocation", "/path/to/schema")
    # The schema evolution mode is set to "rescue".
    # This means unexpected data is stored in the rescued data column.
    # The stream continues processing without interruption.
    .option("cloudFiles.schemaEvolutionMode", "rescue")
    # The rescuedDataColumn option specifies the name of the rescued data column.
    # In this example, the column is named "_rescued_data".
    # Data that does not match the schema is stored in this column as JSON.
    # This includes new columns, type mismatches, and case differences.
    .option("rescuedDataColumn", "_rescued_data")
    # The source path.
    .load("/path/to/source")
    # Start the streaming write.
    .writeStream
    # The checkpoint location.
    .option("checkpointLocation", "/path/to/checkpoint")
    # Write to the target table.
    .toTable("target_table")
)
```

In this code, the stream reads JSON files from a source path. The schema evolution mode is `rescue`. The rescued data column is named `_rescued_data`. When the source data contains a new column, a type mismatch, or a case difference, the unexpected data is stored in the `_rescued_data` column as JSON. The main columns remain unchanged. The stream continues. You can analyze the rescued data later to understand schema changes. This is useful when you want to avoid pipeline interruptions. It is also useful when you are ingesting data from many sources and you cannot control the schema. The rescued data column acts as a safety net. It ensures that no data is lost, even if it does not fit the expected schema.

## How rescue mode works in detail

In rescue mode, Auto Loader compares each record to the expected schema. If a record contains a column that is not in the schema, the value of that column is stored in the rescued data column. If a record contains a value that cannot be cast to the expected type, the value is stored in the rescued data column. If a record contains a column name with different casing, the value is stored in the rescued data column. The rescued data column is a JSON string. It contains the unexpected fields and values. You can query the rescued data column using JSON functions. For example, you can use `get_json_object` or `from_json` to extract fields. You can count how many records have rescued data. You can analyze which fields are being rescued. You can set up alerts when rescued data appears. This helps you understand schema changes without stopping the pipeline.

## How type widening works in detail

Type widening is the automatic conversion of a column from a narrower type to a wider type. Supported type changes include `INT` to `LONG`, `FLOAT` to `DOUBLE`, and `SMALLINT` to `INT`. When a source system sends values that exceed the range of the current type, Auto Loader can widen the type automatically. This prevents data loss and avoids routing records to the rescued data column. For example, if a row count column is initially `INT` and later values exceed 2,147,483,647, Auto Loader changes the column type to `LONG`. This allows the values to be stored correctly. Unsupported type changes, such as `INT` to `STRING`, cannot be widened automatically. In `addNewColumnsWithTypeWidening` mode, unsupported type changes are captured in the rescued data column when the mode is active. This ensures that the data is preserved for review. Type widening requires Databricks Runtime 16.4 or above and is in Public Preview. You should test type widening with your data to ensure that it behaves as expected.

## How to choose a schema evolution mode

Choosing the right mode depends on several factors. Consider the criticality of the data. If invalid data can cause financial loss, regulatory violations, safety issues, or serious operational problems, you may want stricter control. `failOnNewColumns` stops the pipeline and requires manual review. `addNewColumns` stops the pipeline but adds new columns automatically on restart. `rescue` keeps the pipeline running and preserves unexpected data. `none` keeps the pipeline running but may ignore new columns. `addNewColumnsWithTypeWidening` stops the pipeline for new columns but handles type widening automatically.

Consider the frequency of schema changes. If the source schema changes frequently, `failOnNewColumns` may cause frequent pipeline stops. This can be frustrating and time-consuming. `addNewColumns` may also cause frequent stops. `rescue` is more practical because it keeps the pipeline running. `addNewColumnsWithTypeWidening` reduces stops for type changes but still stops for new columns.

Consider the tolerance of downstream consumers. If downstream systems can handle new columns or missing columns, `addNewColumns` or `addNewColumnsWithTypeWidening` may be fine. If downstream systems require a stable schema, `rescue` or `none` may be better because they do not change the target schema. If downstream systems cannot tolerate any unexpected changes, `failOnNewColumns` is the safest choice.

Consider your ability to recover. If you can easily reprocess data after a failure, `failOnNewColumns` or `addNewColumns` may be acceptable. If reprocessing is difficult or expensive, `rescue` may be better because it allows the pipeline to continue and preserves the data. You can reprocess the rescued data later.

Consider compliance and audit requirements. If you must retain all records for auditing, do not use `none` without a rescued data column. Use `rescue` or `addNewColumnsWithTypeWidening` to preserve unexpected data. If you must ensure that no unexpected schema changes are ever stored, use `failOnNewColumns`.

## Best practices for schema evolution modes

Define your expected schema explicitly. Do not rely on schema inference. Explicit schemas make your pipeline more predictable and easier to debug. Use the schema location to store the schema. Monitor the schema location for changes. Use the rescued data column to preserve unexpected data. Review the rescued data regularly. Set up alerts when rescued data appears. Test each mode with sample data. Verify that the stream stops, continues, or evolves as expected. Use a bronze, silver, and quarantine architecture. The bronze layer can accept schema drift. The silver layer has a stable schema. The quarantine layer captures records that cannot be processed. Use schema contracts or a schema registry if you have many producers and consumers. These tools help manage schema evolution at scale. Document your schema and your schema evolution strategy. Keep a record of the expected columns and types. Update the documentation when the schema changes.

## Monitoring and testing schema evolution

You should monitor schema evolution. Set up alerts when the schema changes. You can use the pipeline event log, the Delta transaction log, or a custom monitoring solution. For example, you can query the Delta table history to see when columns were added or removed. You can use the `DESCRIBE HISTORY` command to view the history of a Delta table. You can use the `DESCRIBE DETAIL` command to view the current schema. You can also track the number of records written to the rescued data column. If the number increases, investigate the cause. You can set up alerts based on these queries. For example, you can alert when a new column is added to a table. You can alert when a write fails due to schema mismatch. You can alert when the rescued data column contains new fields.

You should test your schema evolution handling. Create test cases for each mode. Test adding a new column. Test removing a column. Test renaming a column. Test changing a type. Test nested changes. Verify that your pipeline handles each case correctly. For example, if you use `rescue`, verify that the unexpected data is stored in the rescued data column. If you use `failOnNewColumns`, verify that the stream stops with the expected exception. If you use `addNewColumnsWithTypeWidening`, verify that supported type changes are widened and unsupported changes are rescued. You can use a testing framework to automate these tests. Create a small source table with a known schema. Write a pipeline that processes the data. Then change the source schema. Run the pipeline again. Check the target table and the rescued data column. Assert that the behavior matches your expectations. This helps you catch problems before they affect production.

## Summary

Auto Loader supports five schema evolution modes controlled by the `cloudFiles.schemaEvolutionMode` option. Choosing the right mode depends on whether you need strict control, automatic adaptation, or a way to capture unexpected data without blocking the pipeline. The modes are `addNewColumns`, `rescue`, `failOnNewColumns`, `none`, and `addNewColumnsWithTypeWidening`. The `addNewColumns` mode is the default. It stops the stream and adds new columns on restart. The `rescue` mode never evolves the schema and stores unexpected data in the rescued data column. The `failOnNewColumns` mode stops the stream and requires manual intervention. The `none` mode never evolves the schema and silently ignores new columns unless a rescued data column is set. The `addNewColumnsWithTypeWidening` mode adds new columns and widens supported type changes automatically. It requires Databricks Runtime 16.4 or above and is in Public Preview. You should choose the mode that matches your business requirements, your data governance policies, and the criticality of the data. You should monitor schema drift, test your handling, and follow best practices. By choosing the right schema evolution mode, you can keep your pipelines running smoothly even as your data sources evolve.
