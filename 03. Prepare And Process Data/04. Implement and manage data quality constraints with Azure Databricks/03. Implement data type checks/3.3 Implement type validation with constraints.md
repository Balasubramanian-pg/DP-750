# Implement type validation with constraints

CHECK constraints let you define custom validation rules that are enforced whenever data is inserted or updated. While typically used for value ranges and patterns, you can combine them with type-aware functions to create sophisticated type checks. A CHECK constraint is a Boolean expression attached to a table. When a write occurs, the expression is evaluated for each row. If the expression evaluates to TRUE, the row is accepted. If the expression evaluates to FALSE, the write is rejected. If the expression evaluates to UNKNOWN, which happens when NULL values are involved in some comparisons, the row is usually accepted. This behavior is important to understand because it affects how you write constraints that involve nullable columns. CHECK constraints are part of the Delta Lake transaction log. They are enforced for all write operations, including INSERT, UPDATE, MERGE, and streaming writes. They are not enforced on reads. They provide a hard guarantee that the data in the table conforms to the rules you define.

Type validation with constraints is useful when you receive data as strings but you need to ensure that the strings represent valid numbers, dates, timestamps, or other types. You might receive data from an external system that sends everything as text. You might have a column that is declared as STRING because some records contain invalid values, but you want to reject new invalid records. You might want to enforce a specific format for identifiers, phone numbers, or email addresses. CHECK constraints allow you to express these rules directly in the table definition. They are evaluated at write time, so invalid data never enters the table.

## Creating a table with a CHECK constraint

You can define a CHECK constraint when you create a table. The following example creates a table named orders with two columns. The order_id column is an integer. The order_total column is a string. The constraint valid_order_total ensures that the string contains only numeric characters and an optional decimal part. The comments explain each part.

```sql
-- Create a table named orders.
-- The table has two columns.
-- order_id is an integer and is the identifier for the order.
-- order_total is a string that should contain a numeric value.
-- We store order_total as a string because the raw data arrives as text.
-- We will use a CHECK constraint to ensure that the text looks like a number.
CREATE TABLE orders (
    order_id INT,
    order_total STRING
);

-- Add a CHECK constraint to the orders table.
-- The constraint is named valid_order_total.
-- The CHECK expression uses the REGEXP operator.
-- REGEXP checks whether the string matches the regular expression pattern.
-- The pattern is '^[0-9]+(\\.[0-9]+)?$'.
-- The caret ^ anchors the match at the beginning of the string.
-- [0-9]+ matches one or more digits.
-- (\\.[0-9]+)? is an optional group.
-- The backslash is escaped as double backslash because the pattern is inside a SQL string literal.
-- \\. matches a literal dot character.
-- [0-9]+ matches one or more digits after the dot.
-- The question mark ? makes the entire decimal part optional.
-- The dollar sign $ anchors the match at the end of the string.
-- This pattern accepts values like '123', '123.45', and '007'.
-- It rejects values like 'abc', '12.34.56', '-10', '1,000', and '12.'.
ALTER TABLE orders
ADD CONSTRAINT valid_order_total CHECK (order_total REGEXP '^[0-9]+(\\.[0-9]+)?$');
```

This constraint catches malformed data before it enters the table. For example, if an application tries to insert the string 'fifty' into order_total, the CHECK expression evaluates to FALSE. The insert fails. The invalid row is not written. If an application tries to insert '100.50', the CHECK expression evaluates to TRUE. The insert succeeds. The string '100.50' is stored as a string. If you need to perform calculations on this value, you can cast it to a decimal type in your queries. The constraint ensures that the cast will succeed.

## Understanding the regular expression

The regular expression used in the previous example is worth examining in detail. The pattern is `^[0-9]+(\\.[0-9]+)?$`. In a SQL string literal, the backslash is an escape character. To represent a literal backslash in the regular expression, you write two backslashes. The regular expression engine receives a single backslash. The dot character `.` has a special meaning in regular expressions. It matches any single character. To match a literal dot, you escape it with a backslash. So `\\.` in the SQL string becomes `\.` in the regular expression, which matches a literal dot.

The pattern can be broken down as follows. The caret `^` asserts the start of the string. The character class `[0-9]` matches any digit from zero to nine. The plus sign `+` means one or more of the preceding element. So `[0-9]+` matches one or more digits. The parentheses group the decimal part. The backslash-dot `\\.` matches a literal dot. The second `[0-9]+` matches one or more digits after the dot. The question mark `?` makes the entire group optional. The dollar sign `$` asserts the end of the string. This pattern does not allow a leading plus or minus sign. It does not allow commas. It does not allow spaces. It does not allow scientific notation. It does not allow a trailing dot. It allows leading zeros, so '007' is accepted. If you want to disallow leading zeros, you need a more complex pattern. If you want to allow negative numbers, you can add an optional minus sign at the beginning. If you want to allow a specific number of decimal places, you can replace the second `+` with a fixed number of digits.

## Validating numeric strings with try_cast

Instead of using a regular expression, you can use the `try_cast` function to validate that a string contains a valid number. The `try_cast` function attempts to convert a value to a target data type. If the conversion succeeds, it returns the converted value. If the conversion fails, it returns NULL. You can use this behavior in a CHECK constraint. The following example adds a constraint that requires order_total to be convertible to a decimal with ten total digits and two decimal places.

```sql
-- Add a CHECK constraint named valid_order_total_decimal.
-- The constraint uses try_cast to attempt to convert order_total to DECIMAL(10,2).
-- If the conversion succeeds, try_cast returns a non-NULL decimal value.
-- The expression try_cast(order_total AS DECIMAL(10,2)) IS NOT NULL evaluates to TRUE.
-- If the conversion fails, try_cast returns NULL.
-- The expression evaluates to FALSE, so the constraint is violated.
-- This constraint is stricter than the regular expression because it enforces the precision and scale.
-- For example, '12345678.90' fits in DECIMAL(10,2), but '123456789.01' does not.
-- The regular expression would accept '123456789.01' because it only checks the format.
ALTER TABLE orders
ADD CONSTRAINT valid_order_total_decimal CHECK (try_cast(order_total AS DECIMAL(10,2)) IS NOT NULL);
```

This approach is often better than a regular expression because it uses the database's own type conversion rules. It automatically handles edge cases such as leading and trailing spaces, which some engines trim before conversion. It also enforces the precision and scale of the target type. However, it may accept values that you do not want, such as '1e3' for scientific notation, depending on the engine. You should test the behavior with your specific data and engine. You can combine `try_cast` with additional range checks to enforce both type and value constraints.

## Validating dates with try_cast

Date validation is another common use case for CHECK constraints. Dates often arrive as strings in various formats. You can use `try_cast` to validate that a string contains a valid date. The following example adds a constraint to an events table. The table has a column named event_date_str that is declared as STRING. The constraint ensures that the string can be converted to a DATE.

```sql
-- Create a table named events.
-- The table has an event_id column and an event_date_str column.
-- event_date_str is a string that should contain a date.
CREATE TABLE events (
    event_id INT,
    event_date_str STRING
);

-- Add a CHECK constraint named valid_event_date.
-- The constraint uses try_cast to attempt to convert event_date_str to DATE.
-- If the conversion succeeds, try_cast returns a date value.
-- The expression try_cast(event_date_str AS DATE) IS NOT NULL evaluates to TRUE.
-- If the conversion fails, try_cast returns NULL.
-- The expression evaluates to FALSE, so the constraint is violated.
-- This approach rejects records where event_date_str does not contain a valid date format.
ALTER TABLE events 
ADD CONSTRAINT valid_event_date CHECK (try_cast(event_date_str AS DATE) IS NOT NULL);
```

There is an important nuance with NULL values. If event_date_str is NULL, then `try_cast(NULL AS DATE)` returns NULL. The expression `NULL IS NOT NULL` evaluates to FALSE. Therefore, the constraint is violated. This means the constraint rejects NULL values in event_date_str. If you want to allow NULL values, you must write the constraint differently. You can use `event_date_str IS NULL OR try_cast(event_date_str AS DATE) IS NOT NULL`. This expression evaluates to TRUE when event_date_str is NULL. It evaluates to TRUE when event_date_str is a valid date. It evaluates to FALSE when event_date_str is a non-null invalid date. The following example shows this pattern.

```sql
-- Add a CHECK constraint that allows NULL values.
-- The expression first checks whether event_date_str IS NULL.
-- If it is NULL, the OR condition is TRUE, so the constraint passes.
-- If it is not NULL, the expression evaluates the second part.
-- The second part checks whether try_cast succeeds.
-- If the string is a valid date, the second part is TRUE, so the constraint passes.
-- If the string is an invalid date, the second part is FALSE, so the constraint fails.
ALTER TABLE events
ADD CONSTRAINT valid_event_date_nullable CHECK (event_date_str IS NULL OR try_cast(event_date_str AS DATE) IS NOT NULL);
```

You can use the same pattern with `try_to_date` or `try_to_timestamp` if you need to enforce a specific format. For example, `try_to_date(event_date_str, 'yyyy-MM-dd')` attempts to parse the string using the format `yyyy-MM-dd`. If the string does not match that format, it returns NULL. This gives you more control than `try_cast`, which may accept multiple formats depending on the session settings.

## Validating multiple types in one table

You can add multiple CHECK constraints to the same table. Each constraint is evaluated independently. A row must satisfy all constraints to be written. The following example creates a table for transactions and adds several type validation constraints.

```sql
-- Create a table named transactions.
-- The table stores raw string values for amount, transaction_date, and quantity.
-- These values will be validated by CHECK constraints.
CREATE TABLE transactions (
    transaction_id INT,
    amount_str STRING,
    transaction_date_str STRING,
    quantity_str STRING
);

-- Add a constraint that validates amount_str as a decimal.
-- The amount must be convertible to DECIMAL(10,2).
ALTER TABLE transactions
ADD CONSTRAINT valid_amount CHECK (try_cast(amount_str AS DECIMAL(10,2)) IS NOT NULL);

-- Add a constraint that validates transaction_date_str as a date.
-- The date must be convertible to DATE.
-- NULL values are allowed because of the IS NULL check.
ALTER TABLE transactions
ADD CONSTRAINT valid_transaction_date CHECK (transaction_date_str IS NULL OR try_cast(transaction_date_str AS DATE) IS NOT NULL);

-- Add a constraint that validates quantity_str as an integer.
-- The quantity must be convertible to INT.
-- The quantity must also be greater than zero.
-- The combination of type validation and range validation is common.
ALTER TABLE transactions
ADD CONSTRAINT valid_quantity CHECK (try_cast(quantity_str AS INT) IS NOT NULL AND try_cast(quantity_str AS INT) > 0);
```

In the last constraint, the expression uses `try_cast` twice. This is acceptable for clarity, but it can be inefficient. If performance is a concern, you can use a single `try_cast` and compare the result. For example, `try_cast(quantity_str AS INT) > 0` would work because if the cast fails, the result is NULL, and `NULL > 0` evaluates to UNKNOWN, which is treated as a violation in many systems. However, the behavior of UNKNOWN in CHECK constraints can vary. It is safer to use the explicit `IS NOT NULL` check. If you want to avoid the double cast, you can use a generated column or a more complex expression, but that is usually not necessary. The performance overhead of a simple cast is small.

## Adding constraints to existing tables

You can add a CHECK constraint to an existing table using the ALTER TABLE statement. Before adding the constraint, Azure Databricks verifies that all existing rows satisfy the constraint. This is an important step. If any existing row violates the constraint, the ALTER TABLE statement fails. The constraint is not added. You must fix the data before you can add the constraint. On large tables, this validation step can be expensive. It requires scanning the entire table. You should plan for this validation step, especially on large tables. You may want to run it during a maintenance window or during a period of low activity. You may also want to clean the data first using a separate job. The following example shows how to add a constraint to an existing table.

```sql
-- Add a CHECK constraint to an existing table named events.
-- Azure Databricks will scan all existing rows in the events table.
-- It will evaluate the expression try_cast(event_date_str AS DATE) IS NOT NULL for each row.
-- If any row violates the constraint, the ALTER TABLE statement fails.
-- If all rows satisfy the constraint, the constraint is added.
-- Once added, the constraint is enforced for all future writes.
ALTER TABLE events 
ADD CONSTRAINT valid_event_date CHECK (try_cast(event_date_str AS DATE) IS NOT NULL);
```

If the table is very large, the validation scan can take a long time. You can reduce the impact by ensuring that the data is already clean. You can also consider adding the constraint during a period when the table is not being written to. If the ALTER TABLE fails because of existing violations, you need to identify the violating rows. You can use a query with `try_cast` to find them. For example, the following query returns the rows where the date conversion fails.

```sql
-- Find rows where event_date_str is not a valid date.
-- The WHERE clause uses try_cast to identify invalid values.
-- try_cast returns NULL for invalid values.
-- The IS NULL condition selects those rows.
SELECT *
FROM events
WHERE try_cast(event_date_str AS DATE) IS NULL;
```

You can then fix these rows by updating them, deleting them, or moving them to a quarantine table. After the data is clean, you can retry the ALTER TABLE statement.

## Managing constraints

You can view the constraints on a table using the SHOW CONSTRAINTS statement. The following example shows how to list the constraints on the orders table.

```sql
-- Show all constraints on the orders table.
-- The output includes the constraint name, the constraint type, and the expression.
SHOW CONSTRAINTS ON orders;
```

You can drop a constraint using the ALTER TABLE DROP CONSTRAINT statement. The following example drops the valid_order_total constraint.

```sql
-- Drop the valid_order_total constraint from the orders table.
-- After dropping the constraint, future writes are no longer validated against it.
-- Existing data is not changed.
ALTER TABLE orders
DROP CONSTRAINT valid_order_total;
```

You can also add multiple constraints in a single ALTER TABLE statement. The following example adds two constraints at once.

```sql
-- Add two constraints to the events table in one statement.
-- The first constraint validates event_date_str as a date.
-- The second constraint validates event_type as one of a set of allowed values.
ALTER TABLE events
ADD CONSTRAINT valid_event_date CHECK (event_date_str IS NULL OR try_cast(event_date_str AS DATE) IS NOT NULL),
ADD CONSTRAINT valid_event_type CHECK (event_type IN ('click', 'view', 'purchase'));
```

## Type validation with constraints in streaming pipelines

CHECK constraints apply to streaming writes as well as batch writes. When you write a streaming DataFrame to a Delta table, Delta Lake validates each micro-batch against the constraints. If any row in the micro-batch violates a constraint, the write fails. This can stop the stream. You should be careful when using strict constraints in streaming pipelines. If the source data is not perfectly clean, the stream may fail frequently. You may want to use expectations in a declarative pipeline instead. Expectations allow you to warn, drop, or quarantine invalid records without stopping the pipeline. You can then use CHECK constraints on the cleaned table to enforce a hard guarantee. The following example shows a streaming write to a table with a CHECK constraint. If the source data contains an invalid date, the write fails.

```python
# Read a streaming source.
streaming_df = spark.readStream.table("raw.events")

# Write the streaming data to a Delta table named events.
# The events table has a CHECK constraint on event_date_str.
# If any micro-batch contains a row where event_date_str is not a valid date, the write fails.
streaming_df.writeStream.format("delta").option("checkpointLocation", "/path/to/checkpoint").start("events")
```

If you want to handle invalid records without stopping the stream, you can use `try_cast` in the streaming query to filter or flag invalid records before writing. For example, you can write valid records to the constrained table and invalid records to a quarantine table.

```python
# Import the required functions.
from pyspark.sql.functions import expr

# Read a streaming source.
streaming_df = spark.readStream.table("raw.events")

# Create a column that indicates whether the date is valid.
streaming_df_validated = streaming_df.withColumn("is_valid_date", expr("try_cast(event_date_str AS DATE) IS NOT NULL"))

# Write valid records to the events table.
# The events table has a CHECK constraint, but the data is already valid.
streaming_df_validated.filter("is_valid_date = true").writeStream.format("delta").option("checkpointLocation", "/path/to/checkpoint_valid").start("events")

# Write invalid records to a quarantine table.
streaming_df_validated.filter("is_valid_date = false").writeStream.format("delta").option("checkpointLocation", "/path/to/checkpoint_quarantine").start("quarantine_events")
```

This pattern allows the stream to continue processing even when invalid records are present. The constrained table only receives valid records. The quarantine table receives the invalid records for later analysis.

## Performance considerations

CHECK constraints add overhead to write operations. The expression is evaluated for each row that is written. If the expression is simple, the overhead is small. If the expression is complex, such as a regular expression that matches a long string, the overhead can be significant. You should keep constraint expressions as simple as possible. Use `try_cast` instead of complex regular expressions when possible. `try_cast` is usually faster because it uses the database's built-in conversion routines. If you must use a regular expression, make it as specific as possible. Avoid patterns that cause excessive backtracking. Test the performance of your constraints with realistic data volumes.

CHECK constraints do not create indexes. They do not speed up reads. Their purpose is data quality, not query performance. They are evaluated only during writes. If you need to enforce data quality on reads, you should use queries with filters or views. CHECK constraints are a storage-layer guarantee. They ensure that the data in the table always satisfies the constraint.

When you add a constraint to an existing table, the validation scan can be expensive. The cost is proportional to the size of the table. For very large tables, you may want to use a more efficient approach. For example, you can create a new table with the constraint, copy the valid data, and then swap the tables. Or you can use a separate job to validate the data and then add the constraint when the data is known to be clean. Always plan for the validation step and communicate with stakeholders about the potential impact.

## Best practices for type validation with constraints

Use CHECK constraints for critical data integrity rules. Do not use them for every possible validation. Use expectations in a data pipeline for soft validation, monitoring, and quarantine. Use CHECK constraints for hard guarantees that must never be violated. For example, use a CHECK constraint to ensure that a primary key is not null. Use a CHECK constraint to ensure that a date is valid. Use a CHECK constraint to ensure that a numeric string is actually numeric. Do not use a CHECK constraint to enforce a business rule that might change frequently. Business rules are better handled in the pipeline or in the application layer.

Name your constraints meaningfully. A good constraint name describes the rule. For example, `valid_event_date` is better than `check1`. Meaningful names make it easier to understand the table schema and to diagnose failures. When a write fails, the error message includes the constraint name. A good name helps you quickly identify the problem.

Handle NULL values explicitly. As discussed earlier, CHECK constraints treat NULL differently depending on the expression. If you want to allow NULL, add an explicit `IS NULL` check. If you want to reject NULL, make sure the expression evaluates to FALSE for NULL. Test your constraints with NULL values to confirm the behavior.

Test your constraints thoroughly. Create a test table with sample data. Insert valid and invalid values. Verify that valid values are accepted and invalid values are rejected. Test edge cases such as empty strings, strings with leading and trailing spaces, strings with special characters, and values at the boundaries of the target type. Test the behavior with NULL values. If you use regular expressions, test them with a variety of inputs. Use a regular expression testing tool or a small script to verify the pattern.

Monitor constraint violations. When a write fails due to a constraint violation, the error is logged. You should monitor these errors. A sudden increase in constraint violations may indicate a problem in the source system. You can use the error messages to identify the violating rows and the constraint that was violated. You can also query the table to find rows that would violate a constraint before adding it.

Document your constraints. Keep a record of the constraints on each table and the reason for each constraint. This helps new team members understand the data model. It also helps when you need to modify or drop a constraint. You can use the SHOW CONSTRAINTS statement to list the constraints, but it does not explain why they exist. A separate document or a comment in the table definition can provide that context.

## Common mistakes with type validation constraints

One common mistake is assuming that a CHECK constraint allows NULL. In standard SQL, a CHECK constraint is satisfied if the condition is TRUE or UNKNOWN. However, the expression `try_cast(column AS DATE) IS NOT NULL` evaluates to FALSE when the column is NULL. This is because `IS NOT NULL` is a predicate that returns TRUE or FALSE, not UNKNOWN. So the constraint rejects NULL. If you want to allow NULL, you must write the condition as `column IS NULL OR try_cast(column AS DATE) IS NOT NULL`. Many developers forget this and are surprised when their inserts with NULL values fail.

Another common mistake is using a regular expression that is too strict or too loose. A regular expression that is too strict may reject valid values. For example, a pattern that only allows two decimal places may reject values with one decimal place. A regular expression that is too loose may accept invalid values. For example, a pattern that allows any number of digits may accept values that exceed the precision of the target type. Always test your regular expression with a variety of valid and invalid inputs.

Another common mistake is using implicit casts in constraints. For example, if you write `CHECK (amount > 0)` and amount is a string, the database may implicitly cast the string to a number. If the string contains an invalid value, the cast may fail, or it may behave unexpectedly. It is better to use explicit `try_cast` to validate the type first. For example, `CHECK (try_cast(amount AS DECIMAL(10,2)) > 0)`. This makes the intent clear and ensures that the type validation happens before the range validation.

Another common mistake is adding constraints to a large table without planning for the validation scan. The ALTER TABLE statement may take a long time. It may fail if existing data violates the constraint. You should always test the constraint on a sample of the data first. You can use a query with the constraint expression to see how many rows would violate it. If the number is large, you need to clean the data first.

Another common mistake is not considering the impact on streaming pipelines. A strict constraint can stop a stream. If the source data is not perfectly clean, the stream may fail repeatedly. You should use expectations or pre-filtering to handle invalid records before they reach the constrained table. Alternatively, you can use a quarantine table to capture invalid records without stopping the stream.

## Testing type validation constraints

Testing is essential for type validation constraints. You should write tests that cover the following scenarios. Test valid values that should be accepted. Test invalid values that should be rejected. Test NULL values to confirm the behavior. Test empty strings. Test strings with leading and trailing spaces. Test strings with special characters. Test values at the boundaries of the target type. Test values that are just outside the boundaries. Test the behavior with different locales and formats. For example, dates in `YYYY-MM-DD` and `DD/MM/YYYY` formats. Test the behavior with different time zones if timestamps are involved.

You can write tests using SQL. Create a temporary table with the same schema and constraints. Insert test values. Check whether the insert succeeds or fails. You can also use a testing framework in your programming language of choice. For example, you can use pytest in Python to run SQL statements and assert the results. The following example shows a simple SQL test for the valid_event_date constraint.

```sql
-- Create a test table with the same schema and constraint.
CREATE TABLE test_events (
    event_id INT,
    event_date_str STRING,
    CONSTRAINT valid_event_date CHECK (event_date_str IS NULL OR try_cast(event_date_str AS DATE) IS NOT NULL)
);

-- Insert a valid date.
-- This should succeed.
INSERT INTO test_events VALUES (1, '2026-01-15');

-- Insert a NULL date.
-- This should succeed because the constraint allows NULL.
INSERT INTO test_events VALUES (2, NULL);

-- Insert an invalid date.
-- This should fail because the constraint rejects invalid dates.
INSERT INTO test_events VALUES (3, 'not a date');

-- Insert another invalid date.
-- This should fail.
INSERT INTO test_events VALUES (4, '2026-13-01');

-- Clean up the test table.
DROP TABLE test_events;
```

You can run similar tests for numeric validation. Test values like '123', '123.45', 'abc', '12.34.56', '-10', '1,000', and empty string. Verify that the constraint accepts and rejects the correct values. Testing helps you catch mistakes before they affect production data.

CHECK constraints let you define custom validation rules that are enforced whenever data is inserted or updated. You can validate that a string column contains only numeric characters using a regular expression. You can validate that a string contains a valid date using `try_cast`. You can validate multiple types in the same table by adding multiple constraints. You can add constraints to existing tables, but Azure Databricks verifies that all existing rows satisfy the constraint before adding it. Plan for this validation step, especially on large tables. CHECK constraints add overhead to writes, so keep expressions simple. Use `try_cast` instead of complex regular expressions when possible. Handle NULL values explicitly. Test your constraints thoroughly. Monitor constraint violations. Document your constraints. Use CHECK constraints for critical data integrity rules. Use expectations for soft validation and monitoring. By following these practices, you can use CHECK constraints to enforce type validation and maintain high data quality in your Delta Lake tables.
