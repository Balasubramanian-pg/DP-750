# Handle type mismatches in pipelines

When processing data from external sources, type mismatches are common. External systems often send data as strings, even when the values represent numbers, dates, or timestamps. A CSV file might contain an amount column with values like `"100.50"`, `"abc"`, `"1,000"`, or an empty string. A JSON feed might contain a date field with values like `"2026-01-15"`, `"15/01/2026"`, `"not provided"`, or `null`. If you try to write these values directly into a table with numeric or date columns, the write may fail. If you use implicit casting, the behavior may be unpredictable. If you use strict casting, a single bad record can stop the entire pipeline.

The pattern shown here separates valid records from invalid records. Valid records are converted to the correct types and written to a clean target table, often called a silver table. Invalid records are written to a quarantine table for later investigation. This allows the pipeline to continue processing good data while preserving bad data for review. It also gives you visibility into data quality problems. You can monitor the quarantine table, identify systematic issues, and fix them at the source.

## The bronze, silver, and quarantine architecture

This pattern fits into a medallion-style architecture. The bronze layer stores raw data exactly as it arrived. The silver layer stores cleaned, validated, and typed data. The quarantine layer stores records that could not be validated. The bronze table is typically append-only and immutable. The silver table is the trusted source for downstream analytics and applications. The quarantine table is an operational table used by data engineers and data quality teams.

The bronze table might have all columns as strings. The silver table has proper data types. For example, the bronze table has `amount` as STRING and `transaction_date` as STRING. The silver table has `amount` as DECIMAL(10,2) and `transaction_date` as DATE. The quarantine table keeps the raw string values so you can see exactly what failed.

## Inserting valid records into the silver table

The first step is to insert valid records into the target table. The following SQL statement does this. Each line is commented to explain what it does.

```sql
-- Insert valid records into the silver_transactions table.
-- The silver table is the cleaned and validated version of the data.
-- It contains only records that passed type validation.
INSERT INTO silver_transactions
-- The target table is silver_transactions.
-- This table should have the correct data types for amount and transaction_date.
SELECT 
    transaction_id,
    -- transaction_id is copied without change.
    -- It is assumed to be a valid integer or string that does not need conversion.
    cast(amount AS DECIMAL(10,2)) AS amount,
    -- The cast function converts amount to DECIMAL(10,2).
    -- DECIMAL(10,2) means 10 total digits, 2 after the decimal point.
    -- Because the WHERE clause already verified that try_cast succeeds,
    -- this cast will not fail for the rows that reach this SELECT.
    -- The alias amount gives the converted column the target name.
    cast(transaction_date AS DATE) AS transaction_date
    -- The cast function converts transaction_date to DATE.
    -- Again, the WHERE clause already verified that try_cast succeeds.
    -- The alias transaction_date gives the converted column the target name.
FROM bronze_transactions
-- bronze_transactions is the raw source table.
-- It contains the data as it arrived from the external system.
-- The columns amount and transaction_date may be strings.
WHERE try_cast(amount AS DECIMAL(10,2)) IS NOT NULL
  -- The WHERE clause filters out rows where amount cannot be converted.
  -- try_cast returns NULL when the conversion fails.
  -- IS NOT NULL keeps only rows where the conversion succeeded.
  AND try_cast(transaction_date AS DATE) IS NOT NULL;
  -- This condition does the same for transaction_date.
  -- Both conditions must be true for the row to be considered valid.
  -- Rows with an invalid amount or an invalid date are excluded.
```

This statement uses `try_cast` in the `WHERE` clause to test whether each value can be converted. If the conversion succeeds, `try_cast` returns the converted value, which is not null. If the conversion fails, `try_cast` returns null. The `IS NOT NULL` check keeps only the rows where both conversions succeed.

The `SELECT` list uses `cast` instead of `try_cast`. This is safe because the `WHERE` clause has already filtered out any rows that would fail the cast. Using `cast` in the `SELECT` list makes it clear that the target columns should have the correct types. If you used `try_cast` in the `SELECT` list, the resulting column would be nullable, and you would need to handle nulls downstream. Since the `WHERE` clause guarantees no nulls from conversion failures, `cast` is appropriate.

## Capturing invalid records in the quarantine table

The second step is to insert invalid records into the quarantine table. The following SQL statement does this. Each line is commented.

```sql
-- Insert invalid records into the quarantine_transactions table.
-- The quarantine table stores records that failed type validation.
-- These records are kept for investigation and possible reprocessing.
INSERT INTO quarantine_transactions
-- The target table is quarantine_transactions.
-- It should have columns for the raw values, a timestamp, and a reason.
SELECT 
    transaction_id,
    -- Copy the transaction_id so you can trace the record back to the source.
    amount AS raw_amount,
    -- Store the original amount value without casting.
    -- This preserves the exact value that failed validation.
    -- The alias raw_amount makes it clear that this is the raw value.
    transaction_date AS raw_date,
    -- Store the original transaction_date value without casting.
    -- The alias raw_date makes it clear that this is the raw value.
    current_timestamp() AS quarantined_at,
    -- Record the time when the record was quarantined.
    -- current_timestamp() returns the current date and time.
    -- This helps with monitoring and auditing.
    'Type validation failed' AS reason
    -- Record a reason for quarantine.
    -- In this simple example, the reason is generic.
    -- In a real pipeline, you might include which column failed.
    -- For example, 'Invalid amount' or 'Invalid transaction_date'.
FROM bronze_transactions
-- Read from the same raw source table.
WHERE try_cast(amount AS DECIMAL(10,2)) IS NULL
   -- Select rows where amount cannot be converted.
   OR try_cast(transaction_date AS DATE) IS NULL;
   -- Or select rows where transaction_date cannot be converted.
   -- The OR condition means a row is quarantined if either column is invalid.
   -- A row that fails both conditions is quarantined once.
   -- The raw values are preserved so you can diagnose the problem.
```

This statement captures any row that failed at least one type validation. If a row has an invalid amount but a valid date, it is quarantined. If a row has a valid amount but an invalid date, it is quarantined. If a row has both invalid, it is quarantined once. The raw values are stored so you can see exactly what the source system sent.

## Why this pattern works

This pattern works because it separates concerns. The `try_cast` function is used for validation. It answers the question: can this value be converted to the target type? The `cast` function is used for conversion. It answers the question: convert this value to the target type. By using `try_cast` in the `WHERE` clause, you ensure that only convertible values reach the `cast` function. This prevents the pipeline from failing. By using `cast` in the `SELECT` list, you ensure that the target table receives properly typed values. By routing invalid records to quarantine, you ensure that bad data is not lost. You can analyze it later and decide whether to fix it, delete it, or reprocess it.

This pattern also makes data quality visible. If the quarantine table suddenly grows, you know something changed in the source system. You can investigate before the problem affects downstream consumers. If the quarantine table stays empty, you have confidence that the source data is clean.

## Improving the quarantine reason

The generic reason `'Type validation failed'` is not very helpful when you have multiple columns. You can use a `CASE` expression to provide a specific reason. The following example shows how.

```sql
-- Insert invalid records with a specific reason.
INSERT INTO quarantine_transactions
SELECT 
    transaction_id,
    amount AS raw_amount,
    transaction_date AS raw_date,
    current_timestamp() AS quarantined_at,
    CASE
        WHEN try_cast(amount AS DECIMAL(10,2)) IS NULL AND try_cast(transaction_date AS DATE) IS NULL
            THEN 'Invalid amount and invalid transaction_date'
        WHEN try_cast(amount AS DECIMAL(10,2)) IS NULL
            THEN 'Invalid amount'
        WHEN try_cast(transaction_date AS DATE) IS NULL
            THEN 'Invalid transaction_date'
        ELSE 'Unknown'
    END AS reason
    -- The CASE expression checks which conversion failed.
    -- It returns a specific reason for each case.
    -- This makes it easier to diagnose the problem.
FROM bronze_transactions
WHERE try_cast(amount AS DECIMAL(10,2)) IS NULL
   OR try_cast(transaction_date AS DATE) IS NULL;
```

This approach is more useful because you can group quarantine records by reason. For example, you can count how many records failed because of an invalid amount versus an invalid date. This helps you prioritize fixes.

## Avoiding repeated try_cast calls with a common table expression

In the previous examples, `try_cast` is called multiple times for the same column. In the valid insert, it is called twice in the `WHERE` clause. In the invalid insert with the `CASE` expression, it is called several times. This is inefficient because the conversion is attempted multiple times for each row. A better approach is to use a common table expression, also known as a CTE, to compute the conversions once. The following example shows how.

```sql
-- Define a common table expression named validated.
-- The CTE computes the try_cast results once for each row.
WITH validated AS (
    SELECT
        transaction_id,
        amount,
        transaction_date,
        try_cast(amount AS DECIMAL(10,2)) AS amount_cast,
        -- amount_cast is the result of converting amount.
        -- It is NULL if the conversion fails.
        try_cast(transaction_date AS DATE) AS date_cast
        -- date_cast is the result of converting transaction_date.
        -- It is NULL if the conversion fails.
    FROM bronze_transactions
)
-- Insert valid records into the silver table.
INSERT INTO silver_transactions
SELECT
    transaction_id,
    amount_cast AS amount,
    -- Use the precomputed amount_cast.
    date_cast AS transaction_date
    -- Use the precomputed date_cast.
FROM validated
WHERE amount_cast IS NOT NULL
  AND date_cast IS NOT NULL;
  -- Keep only rows where both conversions succeeded.

-- Insert invalid records into the quarantine table.
INSERT INTO quarantine_transactions
SELECT
    transaction_id,
    amount AS raw_amount,
    transaction_date AS raw_date,
    current_timestamp() AS quarantined_at,
    CASE
        WHEN amount_cast IS NULL AND date_cast IS NULL
            THEN 'Invalid amount and invalid transaction_date'
        WHEN amount_cast IS NULL
            THEN 'Invalid amount'
        WHEN date_cast IS NULL
            THEN 'Invalid transaction_date'
        ELSE 'Unknown'
    END AS reason
FROM validated
WHERE amount_cast IS NULL
   OR date_cast IS NULL;
   -- Select rows where at least one conversion failed.
```

This CTE approach is more efficient and easier to read. It also ensures that the conversion logic is consistent across both inserts.

## Making the pattern idempotent with MERGE

If your pipeline reruns, the simple `INSERT` statements may create duplicates. For example, if the pipeline fails after inserting valid records but before inserting invalid records, and then reruns, the valid records may be inserted twice. To make the pattern idempotent, you can use `MERGE` instead of `INSERT` for the silver table. The following example shows how.

```sql
-- Merge valid records into the silver table.
-- The MERGE statement updates existing records and inserts new ones.
MERGE INTO silver_transactions AS target
USING (
    SELECT
        transaction_id,
        cast(amount AS DECIMAL(10,2)) AS amount,
        cast(transaction_date AS DATE) AS transaction_date
    FROM bronze_transactions
    WHERE try_cast(amount AS DECIMAL(10,2)) IS NOT NULL
      AND try_cast(transaction_date AS DATE) IS NOT NULL
) AS source
ON target.transaction_id = source.transaction_id
-- Match on transaction_id.
WHEN MATCHED THEN UPDATE SET *
-- If the record already exists, update all columns.
WHEN NOT MATCHED THEN INSERT *
-- If the record does not exist, insert it.
;
```

For the quarantine table, you may want to keep all occurrences of invalid records. You can add a pipeline run identifier or a batch identifier to distinguish runs. Or you can use `MERGE` on a composite key such as `transaction_id` and `quarantined_at`. The right approach depends on your requirements.

## Handling null values correctly

Null handling is a common source of confusion. In the pattern above, if `amount` is null, `try_cast(null AS DECIMAL(10,2))` returns null. The `IS NOT NULL` check evaluates to false, so the row is not inserted into the silver table. The `IS NULL` check in the quarantine insert evaluates to true, so the row is quarantined. This means null values are treated as invalid. If null is acceptable, you must adjust the conditions.

To allow null amounts, change the valid condition to `(amount IS NULL OR try_cast(amount AS DECIMAL(10,2)) IS NOT NULL)`. Change the invalid condition to `(amount IS NOT NULL AND try_cast(amount AS DECIMAL(10,2)) IS NULL)`. The following example shows this.

```sql
-- Insert valid records, allowing null amounts.
INSERT INTO silver_transactions
SELECT
    transaction_id,
    cast(amount AS DECIMAL(10,2)) AS amount,
    cast(transaction_date AS DATE) AS transaction_date
FROM bronze_transactions
WHERE (amount IS NULL OR try_cast(amount AS DECIMAL(10,2)) IS NOT NULL)
  AND (transaction_date IS NULL OR try_cast(transaction_date AS DATE) IS NOT NULL);

-- Insert invalid records, excluding nulls that are allowed.
INSERT INTO quarantine_transactions
SELECT
    transaction_id,
    amount AS raw_amount,
    transaction_date AS raw_date,
    current_timestamp() AS quarantined_at,
    'Type validation failed' AS reason
FROM bronze_transactions
WHERE (amount IS NOT NULL AND try_cast(amount AS DECIMAL(10,2)) IS NULL)
   OR (transaction_date IS NOT NULL AND try_cast(transaction_date AS DATE) IS NULL);
```

This ensures that null values are not quarantined if they are acceptable.

## Handling empty strings and whitespace

Empty strings and strings with only whitespace are common in external data. Depending on the engine, `try_cast('' AS DECIMAL(10,2))` may return null or may fail. To be safe, trim the string before casting. You can use the `trim` function. The following example shows how.

```sql
-- Trim the amount before casting.
try_cast(trim(amount) AS DECIMAL(10,2))
```

You can apply the same to dates. If an empty string should be treated as null, you can use `nullif(trim(amount), '')`. For example, `try_cast(nullif(trim(amount), '') AS DECIMAL(10,2))`.

## Decimal precision and scale

`DECIMAL(10,2)` allows values up to 99,999,999.99. If your data contains larger values, the cast will fail or overflow. You should choose a precision and scale that match your business requirements. For financial data, `DECIMAL(18,2)` or `DECIMAL(38,2)` is common. If you are not sure, use a larger precision to avoid failures. You can also add a range check after casting to ensure the value is within acceptable bounds.

## Date formats and try_to_date

`try_cast` uses the engine's default date parsing rules. These rules may accept multiple formats or may depend on session settings. If you need to enforce a specific format, use `try_to_date` with a format string. For example, `try_to_date(transaction_date, 'yyyy-MM-dd')` attempts to parse the string using the format `yyyy-MM-dd`. If the string does not match that format, it returns null. This gives you more control and makes your validation more predictable.

## Streaming pipelines

In a streaming pipeline, you cannot easily run two separate `INSERT` statements in the same micro-batch. You can use `foreachBatch` in PySpark to process each micro-batch. Inside the `foreachBatch` function, you can register the micro-batch as a temporary view and run the same SQL statements. The following example shows how.

```python
def process_batch(batch_df, batch_id):
    # Register the micro-batch as a temporary view.
    batch_df.createOrReplaceTempView("bronze_batch")
    # Insert valid records.
    spark.sql("""
        INSERT INTO silver_transactions
        SELECT transaction_id, cast(amount AS DECIMAL(10,2)) AS amount, cast(transaction_date AS DATE) AS transaction_date
        FROM bronze_batch
        WHERE try_cast(amount AS DECIMAL(10,2)) IS NOT NULL
          AND try_cast(transaction_date AS DATE) IS NOT NULL
    """)
    # Insert invalid records.
    spark.sql("""
        INSERT INTO quarantine_transactions
        SELECT transaction_id, amount AS raw_amount, transaction_date AS raw_date, current_timestamp() AS quarantined_at, 'Type validation failed' AS reason
        FROM bronze_batch
        WHERE try_cast(amount AS DECIMAL(10,2)) IS NULL
           OR try_cast(transaction_date AS DATE) IS NULL
    """)

streaming_df = spark.readStream.table("bronze_transactions")
streaming_df.writeStream.foreachBatch(process_batch).option("checkpointLocation", "/path/to/checkpoint").start()
```

This pattern allows the stream to continue processing even when invalid records are present. The valid records go to the silver table. The invalid records go to the quarantine table.

## PySpark version

If you prefer DataFrame operations, you can implement the same pattern in PySpark. The following example shows how.

```python
from pyspark.sql.functions import col, expr, current_timestamp, lit

bronze = spark.read.table("bronze_transactions")

# Compute the try_cast results once.
validated = bronze.withColumn("amount_cast", expr("try_cast(amount as decimal(10,2))")) \
                  .withColumn("date_cast", expr("try_cast(transaction_date as date)"))

# Select valid records.
valid = validated.filter(col("amount_cast").isNotNull() & col("date_cast").isNotNull()) \
                 .select("transaction_id", col("amount_cast").alias("amount"), col("date_cast").alias("transaction_date"))

# Select invalid records.
invalid = validated.filter(col("amount_cast").isNull() | col("date_cast").isNull()) \
                   .select("transaction_id", col("amount").alias("raw_amount"), col("transaction_date").alias("raw_date"), current_timestamp().alias("quarantined_at"), lit("Type validation failed").alias("reason"))

# Write valid and invalid records.
valid.write.mode("append").saveAsTable("silver_transactions")
invalid.write.mode("append").saveAsTable("quarantine_transactions")
```

This approach is useful when you are working with DataFrames and want to avoid SQL strings. It also makes it easy to add additional transformations.

## Designing the quarantine table

The quarantine table should contain enough information to diagnose and reprocess the invalid records. Consider including the following columns:

- The primary key or identifier from the source record.
- The raw values of all columns that failed validation.
- The timestamp when the record was quarantined.
- The reason for quarantine.
- The pipeline run identifier or batch identifier.
- The source file name or source system.
- The full original record, possibly as a JSON string.

Storing the full original record is useful because it allows you to reprocess the record after fixing the validation logic. You can also use it to audit exactly what was received from the source system.

## Monitoring and alerting

You should monitor the quarantine table regularly. Set up alerts when the number of quarantined records exceeds a threshold. You can also track the ratio of valid to invalid records. If the ratio changes suddenly, investigate the source system. You can create a dashboard that shows the count of quarantined records by reason and by day. This helps you identify trends and prioritize fixes.

## Testing the pattern

You should test the pattern with a variety of values. Test valid values, invalid values, null values, empty strings, strings with whitespace, and values at the boundaries of the target types. For example, test `amount` values like `'100'`, `'100.50'`, `'abc'`, `''`, `'   '`, `null`, `'99999999.99'`, and `'100000000.00'`. Test `transaction_date` values like `'2026-01-15'`, `'15/01/2026'`, `'not a date'`, `''`, and `null`. Verify that valid records go to silver and invalid records go to quarantine. Verify that the reasons are correct.

## Performance considerations

The pattern uses `try_cast` multiple times per row. To improve performance, compute the conversions once in a CTE or a temporary view. Filter the data as early as possible. If the bronze table is large, consider partitioning it by date or by source. Use Delta Lake's optimized writes and file compaction to improve read and write performance. If the volume of invalid records is very small, the quarantine insert will be cheap. If the volume is large, you may need to optimize the quarantine table separately.

## Best practices

Keep the bronze layer immutable. Do not modify raw data in place. Use `try_cast` for validation and `cast` for final conversion. Route invalid records to a quarantine table with enough context to diagnose the problem. Make the silver write idempotent using `MERGE` if the pipeline can rerun. Monitor the quarantine table and alert on unexpected growth. Document the expected formats for each column. Use `try_to_date` or `try_to_timestamp` when you need to enforce a specific format. Use CHECK constraints on the silver table to enforce hard guarantees after the data is cleaned. Use expectations in declarative pipelines for soft validation and metrics.

## Summary

When processing data from external sources, type mismatches are common. Implement a pattern that separates valid from invalid records. Insert valid records into the target table using `cast` after filtering with `try_cast`. Capture invalid records in a quarantine table along with the raw values, a timestamp, and a reason. This pattern ensures your pipeline continues processing valid data while preserving invalid records for later analysis. You can improve the pattern with specific reasons, CTEs to avoid repeated casts, `MERGE` for idempotency, and `foreachBatch` for streaming. Handle nulls, empty strings, whitespace, decimal precision, and date formats carefully. Monitor the quarantine table and test the pattern thoroughly. By following these practices, you can build robust pipelines that handle dirty data gracefully.
