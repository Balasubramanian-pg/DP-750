# Use explicit type casting

The `cast` function converts values from one data type to another. When the conversion fails, an error is raised. The `try_cast` function works the same way but returns `NULL` instead of raising an error when the conversion fails. Explicit type casting is the practice of intentionally converting a column or expression from one type to another. It is called explicit because you, the developer, write the conversion in your code. This is different from implicit casting, where the system automatically converts types based on context. Explicit casting gives you control. It makes your intent clear. It also lets you decide what should happen when a conversion cannot be completed.

In data pipelines, explicit type casting is used constantly. Raw data often arrives as strings. Dates may be formatted inconsistently. Numbers may contain commas, currency symbols, or trailing spaces. Booleans may be represented as `0` and `1`, `Y` and `N`, or `true` and `false`. Before you can analyze or store this data, you need to convert it to the correct type. The `cast` function performs this conversion. If the data is clean, the conversion succeeds. If the data is dirty, the conversion fails. The `try_cast` function gives you a safer alternative. It attempts the conversion and returns `NULL` when the value cannot be converted. This allows your query or pipeline to continue running while you identify and handle the invalid values.

## Why explicit type casting matters

Explicit type casting matters because data quality problems often start with type mismatches. A column that should contain numbers might contain strings like `"unknown"` or `"N/A"`. A column that should contain dates might contain strings like `"not provided"` or `"0000-00-00"`. If you try to use these columns in calculations, comparisons, or joins, you may get errors or incorrect results. Explicit casting forces you to confront these problems. It either converts the data successfully or fails with an error. The error tells you that something is wrong. You can then decide how to handle it.

Explicit casting also matters because it makes your pipeline more predictable. When you rely on implicit casting, the behavior depends on the context. For example, a string might be implicitly cast to a number in one query but not in another. This can lead to inconsistent results. When you use explicit casting, you specify exactly what you want. The behavior is the same regardless of context. This makes your code easier to understand, test, and maintain.

Explicit casting is also important for schema enforcement. Delta Lake validates data types when you write to a table. If the incoming data does not match the target schema, Delta Lake attempts a safe cast. If the safe cast fails, the write fails. By using explicit casting before the write, you can control how the conversion happens. You can clean the data, handle errors, and ensure that the write succeeds. This is especially useful when you are loading data from external sources that you do not control.

## The difference between cast and try_cast

The `cast` function and the `try_cast` function are similar in syntax. Both take an expression and a target data type. Both attempt to convert the expression to the target type. The difference is what happens when the conversion fails. `cast` raises an error. The query stops. The error message tells you which value could not be converted and what the target type was. `try_cast` returns `NULL`. The query continues. The invalid value is replaced with `NULL`. You can then use `NULL` checks to identify, filter, flag, or quarantine the invalid records.

Use `cast` when you want strict validation that stops processing on invalid data. This is appropriate when invalid data indicates a serious problem that must be fixed immediately. For example, if you are loading financial transactions and a transaction amount cannot be converted to a decimal, you probably want the pipeline to stop. You do not want to silently replace the amount with `NULL` and continue processing. The error forces you to investigate the source of the bad data.

Use `try_cast` when you want to identify invalid values without failing the query. This is appropriate when you are profiling data, cleansing data, or building a quarantine process. For example, if you are ingesting a large file from an external partner, you may not know how many invalid values it contains. Using `try_cast` allows you to process the entire file, count the invalid values, and separate them into a quarantine table. You can then analyze the invalid values and decide how to handle them.

## Using cast for strict validation

The following SQL example uses `cast` to convert two columns from a staging table. The comments explain each part of the query.

```sql
-- Select columns from the staging_data table.
-- The cast function converts raw_amount to a decimal with 10 total digits and 2 decimal places.
-- The cast function converts raw_date to a date.
-- If either conversion fails, the query raises an error and stops.
-- This is useful when you want strict validation.
SELECT 
    cast(raw_amount AS DECIMAL(10,2)) AS amount,
    -- cast raw_amount to DECIMAL(10,2).
    -- DECIMAL(10,2) means 10 total digits, 2 of which are after the decimal point.
    -- For example, 12345678.90 fits, but 123456789.01 does not.
    -- If raw_amount contains a value like 'abc', the cast fails.
    -- If raw_amount contains a value like '123.456', the cast may round or truncate depending on the engine.
    -- The alias amount gives the converted column a clean name.
    cast(raw_date AS DATE) AS transaction_date
    -- cast raw_date to DATE.
    -- DATE expects a value in a format like 'YYYY-MM-DD'.
    -- If raw_date contains '2026-01-15', the cast succeeds.
    -- If raw_date contains '15/01/2026', the cast may fail unless the engine recognizes that format.
    -- If raw_date contains 'not a date', the cast fails.
    -- The alias transaction_date gives the converted column a clean name.
FROM staging_data;
-- staging_data is the source table.
-- It contains raw string values that need to be converted.
```

In this example, `cast` is used because the developer wants strict validation. If any row contains an invalid amount or an invalid date, the query fails. This is appropriate when the data is expected to be clean and any invalid value indicates a problem that must be fixed. For example, if this query is part of a nightly job that loads financial data, a failure alerts the team that the source system produced bad data. The team can then investigate and fix the source before rerunning the job.

## Using try_cast for safe validation

The following SQL example uses `try_cast` to identify invalid values without failing the query. The comments explain each part.

```sql
-- Select columns from the staging_data table.
-- The try_cast function attempts to convert raw_amount to a decimal.
-- If the conversion succeeds, the result is a decimal value.
-- If the conversion fails, the result is NULL.
-- The query continues running even if some values are invalid.
SELECT 
    raw_amount,
    -- Keep the original raw_amount column so you can see the original value.
    -- This is useful for debugging and for understanding what caused the conversion to fail.
    try_cast(raw_amount AS DECIMAL(10,2)) AS validated_amount,
    -- try_cast raw_amount to DECIMAL(10,2).
    -- If raw_amount is a valid number, validated_amount contains the decimal value.
    -- If raw_amount is not a valid number, validated_amount is NULL.
    -- The alias validated_amount makes it clear that this column contains the result of the conversion.
    CASE 
        WHEN try_cast(raw_amount AS DECIMAL(10,2)) IS NULL 
        THEN 'Invalid amount format'
        ELSE 'Valid'
    END AS validation_status
    -- The CASE expression checks whether the try_cast result is NULL.
    -- If it is NULL, the value could not be converted, so the status is 'Invalid amount format'.
    -- If it is not NULL, the value was converted successfully, so the status is 'Valid'.
    -- The alias validation_status gives the result a clear name.
FROM staging_data;
-- staging_data is the source table.
-- It contains raw string values that need to be validated.
```

In this example, `try_cast` is used because the developer wants to identify invalid values without stopping the query. The query returns every row from `staging_data`. For rows with valid amounts, `validated_amount` contains the converted decimal and `validation_status` is `'Valid'`. For rows with invalid amounts, `validated_amount` is `NULL` and `validation_status` is `'Invalid amount format'`. The developer can then use this result to filter, flag, or quarantine the invalid records.

## Avoiding repeated try_cast calls with a common table expression

In the previous example, `try_cast` is called twice for the same column. Once in the SELECT list and once in the CASE expression. This is inefficient because the conversion is performed twice for each row. It also makes the query harder to read. A better approach is to use a common table expression, also known as a CTE, to compute the conversion once. The following example shows how to do this. The comments explain each part.

```sql
-- Define a common table expression named validated.
-- The CTE computes the try_cast result once and stores it in a column named validated_amount.
WITH validated AS (
    SELECT
        raw_amount,
        -- Keep the original raw_amount column.
        try_cast(raw_amount AS DECIMAL(10,2)) AS validated_amount
        -- try_cast raw_amount to DECIMAL(10,2) once.
        -- The result is stored in validated_amount.
        -- This avoids repeating the conversion in the outer query.
    FROM staging_data
    -- staging_data is the source table.
)
-- Select from the CTE.
SELECT
    raw_amount,
    -- Keep the original raw_amount column.
    validated_amount,
    -- Include the precomputed validated_amount column.
    CASE
        WHEN validated_amount IS NULL THEN 'Invalid amount format'
        ELSE 'Valid'
    END AS validation_status
    -- Use the precomputed validated_amount to determine the validation status.
    -- This avoids calling try_cast again.
FROM validated;
-- validated is the CTE defined above.
```

This approach is more efficient and easier to maintain. It also makes it easier to add more validation logic. For example, you could add additional columns to the CTE that compute other conversions or checks.

## Filtering valid and invalid records

Once you have used `try_cast` to identify invalid records, you can filter them into separate tables. This is a common pattern for data cleansing. The following example shows how to insert valid records into a clean table and invalid records into a quarantine table. The comments explain each part.

```sql
-- Insert valid records into the clean_transactions table.
-- A record is valid if try_cast succeeds and returns a non-NULL value.
INSERT INTO clean_transactions
SELECT
    try_cast(raw_amount AS DECIMAL(10,2)) AS amount,
    -- Convert raw_amount to DECIMAL(10,2).
    -- Because we filter for non-NULL values, this conversion will succeed.
    try_cast(raw_date AS DATE) AS transaction_date
    -- Convert raw_date to DATE.
    -- Because we filter for non-NULL values, this conversion will succeed.
FROM staging_data
WHERE try_cast(raw_amount AS DECIMAL(10,2)) IS NOT NULL
  AND try_cast(raw_date AS DATE) IS NOT NULL;
  -- The WHERE clause keeps only rows where both conversions succeed.
  -- Rows with invalid amounts or invalid dates are excluded.

-- Insert invalid records into the quarantine_transactions table.
-- A record is invalid if either try_cast returns NULL.
INSERT INTO quarantine_transactions
SELECT
    raw_amount,
    -- Keep the original raw_amount value for investigation.
    raw_date,
    -- Keep the original raw_date value for investigation.
    'Invalid amount or date format' AS reason
    -- Add a reason column to explain why the record was quarantined.
FROM staging_data
WHERE try_cast(raw_amount AS DECIMAL(10,2)) IS NULL
   OR try_cast(raw_date AS DATE) IS NULL;
   -- The WHERE clause keeps only rows where at least one conversion fails.
   -- These rows are moved to the quarantine table for later analysis.
```

This pattern is powerful because it separates clean data from dirty data. The clean table contains only records that passed the type conversion. The quarantine table contains records that need attention. You can then analyze the quarantine table to understand why the conversions failed. For example, you might discover that the source system started sending dates in a different format. You can then update your conversion logic or fix the source system.

## Using try_cast to validate multiple columns

You can use `try_cast` on multiple columns in the same query. This is useful when you need to validate several fields. The following example validates an amount, a date, and a quantity. The comments explain each part.

```sql
SELECT
    raw_amount,
    raw_date,
    raw_quantity,
    -- Keep the original columns for reference.
    try_cast(raw_amount AS DECIMAL(10,2)) AS validated_amount,
    -- Attempt to convert raw_amount to DECIMAL(10,2).
    try_cast(raw_date AS DATE) AS validated_date,
    -- Attempt to convert raw_date to DATE.
    try_cast(raw_quantity AS INT) AS validated_quantity,
    -- Attempt to convert raw_quantity to INT.
    CASE
        WHEN try_cast(raw_amount AS DECIMAL(10,2)) IS NULL THEN 'Invalid amount'
        WHEN try_cast(raw_date AS DATE) IS NULL THEN 'Invalid date'
        WHEN try_cast(raw_quantity AS INT) IS NULL THEN 'Invalid quantity'
        ELSE 'Valid'
    END AS validation_status
    -- The CASE expression checks each conversion in order.
    -- The first failure determines the validation status.
    -- If all conversions succeed, the status is 'Valid'.
FROM staging_data;
-- staging_data is the source table.
```

This example is useful for data profiling. It tells you which columns have invalid values and what kind of invalid values they are. You can then prioritize your data cleansing efforts based on the results.

## Using try_cast in PySpark

In PySpark, you can use the `cast` method to convert columns. For `try_cast`, you can use the `expr` function to write a SQL expression. The following example shows how to do this. The comments explain each part.

```python
# Import the required functions.
from pyspark.sql.functions import col, expr, when

# Read the staging data into a DataFrame.
df = spark.read.table("staging_data")
# df is a DataFrame that contains the raw data.

# Use cast for strict validation.
# If any value cannot be converted, the job fails with an error.
df_cast = df.withColumn("amount", col("raw_amount").cast("decimal(10,2)")) \
            .withColumn("transaction_date", col("raw_date").cast("date"))
# withColumn creates a new column or replaces an existing one.
# col("raw_amount").cast("decimal(10,2)") converts raw_amount to decimal.
# col("raw_date").cast("date") converts raw_date to date.
# If a conversion fails, an error is raised.

# Use try_cast for safe validation.
# try_cast is available as a SQL expression in PySpark.
df_try_cast = df.withColumn("validated_amount", expr("try_cast(raw_amount as decimal(10,2))")) \
                .withColumn("validated_date", expr("try_cast(raw_date as date)")) \
                .withColumn("validation_status",
                            when(expr("try_cast(raw_amount as decimal(10,2))").isNull(), "Invalid amount")
                            .when(expr("try_cast(raw_date as date)").isNull(), "Invalid date")
                            .otherwise("Valid"))
# withColumn adds new columns to the DataFrame.
# expr("try_cast(raw_amount as decimal(10,2))") runs the SQL try_cast expression.
# The first withColumn creates validated_amount.
# The second withColumn creates validated_date.
# The third withColumn creates validation_status using a CASE-like when expression.
# when checks the first condition. If true, it returns 'Invalid amount'.
# If not, it checks the next condition. If true, it returns 'Invalid date'.
# otherwise returns 'Valid' if none of the conditions are true.
```

This PySpark example mirrors the SQL examples. It shows how to use `cast` for strict validation and `try_cast` for safe validation. It also shows how to use `when` and `otherwise` to create a validation status column.

## Casting nested types

Explicit type casting is not limited to simple scalar types. You can also cast nested types such as arrays, maps, and structs. The following examples show how to cast an array of strings to an array of integers, and a struct field from string to date. The comments explain each part.

```sql
-- Cast an array of strings to an array of integers.
SELECT
    cast(raw_array AS ARRAY<INT>) AS int_array
    -- raw_array is a column that contains an array of strings.
    -- ARRAY<INT> is the target type.
    -- Each element in the array is converted to an integer.
    -- If any element cannot be converted, the cast fails.
FROM staging_data;

-- Cast a struct field from string to date.
SELECT
    cast(raw_struct.field1 AS DATE) AS field1_date
    -- raw_struct is a column that contains a struct.
    -- raw_struct.field1 accesses the field named field1.
    -- The field is cast to DATE.
    -- If the field cannot be converted, the cast fails.
FROM staging_data;
```

You can also use `try_cast` with nested types. The behavior is the same. If any element or field cannot be converted, the entire result is `NULL`. This is important to understand because it means that a single invalid element can nullify the entire array or struct. If you need element-level error handling, you may need to use more advanced techniques such as `transform` or `filter` on arrays.

## Casting in streaming pipelines

Explicit type casting is especially important in streaming pipelines. Streaming data often arrives continuously from external sources. The schema may be inconsistent. Some records may have valid values. Some may have invalid values. If you use `cast` and a single record has an invalid value, the entire micro-batch fails. This can stop your stream. If you use `try_cast`, the invalid value becomes `NULL`. The stream continues. You can then handle the `NULL` values downstream.

The following example shows how to use `try_cast` in a streaming pipeline. The comments explain each part.

```sql
-- Create a streaming table from a raw streaming source.
CREATE OR REFRESH STREAMING TABLE clean_transactions AS
SELECT
    try_cast(raw_amount AS DECIMAL(10,2)) AS amount,
    -- Attempt to convert raw_amount to DECIMAL(10,2).
    -- If the conversion fails, amount is NULL.
    try_cast(raw_date AS DATE) AS transaction_date
    -- Attempt to convert raw_date to DATE.
    -- If the conversion fails, transaction_date is NULL.
FROM STREAM(raw_transactions)
WHERE try_cast(raw_amount AS DECIMAL(10,2)) IS NOT NULL
  AND try_cast(raw_date AS DATE) IS NOT NULL;
  -- The WHERE clause filters out records with invalid amounts or dates.
  -- This keeps the clean table free of NULL values caused by conversion failures.
```

In this example, `try_cast` is used to safely convert the streaming data. Records with invalid values are filtered out. This prevents the stream from failing. If you want to keep the invalid records for investigation, you can write them to a separate quarantine table. You can use a similar streaming query with a `WHERE` clause that selects records where `try_cast` returns `NULL`.

## Performance considerations

Explicit type casting has performance implications. `cast` and `try_cast` both require the engine to examine each value and attempt a conversion. This takes CPU time. In general, casting is fast for simple types like integers and dates. It is slower for complex types like decimals and strings. `try_cast` may be slightly slower than `cast` because it must handle conversion failures gracefully. However, the performance difference is usually small. The bigger performance concern is calling `try_cast` multiple times on the same column. As shown earlier, you should use a CTE or a subquery to compute the conversion once.

Another performance consideration is the target type. Casting to a smaller type, such as `INT`, is faster than casting to a larger type, such as `DECIMAL(38,18)`. Casting to a string is often faster than casting from a string to a numeric type because string formatting is simpler. When possible, choose the smallest and simplest target type that meets your needs.

You should also consider the volume of data. If you are processing billions of rows, even a small performance difference per row can add up. Test your queries with realistic data volumes. Use the query profile or execution plan to identify bottlenecks. If casting is a bottleneck, consider whether you can push the conversion upstream or whether you can use a more efficient data format.

## Best practices for explicit type casting

Follow these best practices to get the most out of explicit type casting:

- Always use explicit casting instead of relying on implicit casting. This makes your intent clear and your results predictable.
- Use `cast` when you want strict validation and you are confident that the data is clean. Use `try_cast` when you want to identify invalid values without failing the query.
- Use a CTE or subquery to avoid calling `try_cast` multiple times on the same column.
- Handle `NULL` values that result from `try_cast`. Decide whether to filter them out, replace them with a default, or quarantine them.
- Validate ranges and other business rules after casting. `try_cast` only checks type conversion. It does not check whether the value is within an acceptable range.
- Test your casting logic with edge cases. Test valid values, invalid values, nulls, empty strings, and values at the boundaries of the target type.
- Monitor casting failures. If you use `try_cast`, track how many `NULL` values are produced. If the number increases suddenly, investigate the source data.
- Document your casting rules. Explain why each column is cast to a particular type and what happens when the cast fails.
- Consider the impact of casting on downstream consumers. If you change a column type, make sure that downstream queries and applications can handle the new type.

## Common mistakes with explicit type casting

There are several common mistakes that developers make with explicit type casting. Understanding these mistakes helps you avoid them.

One common mistake is using `cast` when `try_cast` is more appropriate. If you are loading data from an unreliable source, `cast` may cause your pipeline to fail frequently. This can be frustrating and time-consuming. `try_cast` allows you to continue processing while you investigate the invalid values.

Another common mistake is ignoring the `NULL` values produced by `try_cast`. If you use `try_cast` and then use the converted column in calculations, the `NULL` values may produce unexpected results. For example, `NULL + 1` is `NULL`. You should explicitly handle `NULL` values by filtering them out, replacing them with a default, or using `COALESCE`.

Another common mistake is assuming that `try_cast` validates ranges. `try_cast` only checks whether a value can be converted to a type. It does not check whether the value is within a valid range. For example, `try_cast('999' AS INT)` succeeds and returns `999`. If your valid range is 1 to 100, you need an additional check. Use a `CASE` expression or a `WHERE` clause to enforce range checks.

Another common mistake is casting to the wrong type. For example, casting a decimal to an integer truncates the decimal portion. If you need to preserve the decimal portion, cast to a decimal type instead. Similarly, casting a timestamp to a date loses the time portion. Make sure you understand the target type and its limitations.

Another common mistake is not testing the boundaries of the target type. For example, `DECIMAL(10,2)` can hold values up to 99,999,999.99. If your data contains 100,000,000.00, the cast will fail. Test your data against the limits of the target type.

Another common mistake is using `try_cast` in a `WHERE` clause without considering performance. `try_cast` is evaluated for each row. If you use it in a `WHERE` clause, it may prevent predicate pushdown. This can slow down your query. Consider using a CTE to compute the conversion once and then filter on the result.

## Testing explicit type casting

Testing is essential for explicit type casting. You should write tests that cover the following scenarios:

- Valid values that convert successfully.
- Invalid values that cause `cast` to fail.
- Invalid values that cause `try_cast` to return `NULL`.
- `NULL` input values. In most systems, casting `NULL` returns `NULL`.
- Empty strings. Casting an empty string to a number may fail or return `NULL` depending on the engine.
- Values at the boundaries of the target type. For example, the maximum and minimum values.
- Values with leading or trailing spaces. Some engines trim spaces automatically. Others do not.
- Values with different formats. For example, dates in `YYYY-MM-DD` and `DD/MM/YYYY` formats.
- Values with special characters. For example, currency symbols, commas, or percent signs.

You can write tests using SQL or your programming language of choice. For example, you can create a small table with test values and run your casting query against it. Check that the results match your expectations. If you use a testing framework, you can automate these tests and run them as part of your continuous integration pipeline.

## Summary

The `cast` function converts values from one data type to another. When the conversion fails, an error is raised. The `try_cast` function works the same way but returns `NULL` instead of raising an error when the conversion fails. Use `cast` when you want strict validation that stops processing on invalid data. Use `try_cast` when you want to identify invalid values without failing the query. With `try_cast`, records with invalid values return `NULL` for the cast column. You can then filter, flag, or quarantine these records based on your data quality requirements.

Explicit type casting is a fundamental technique for building reliable data pipelines. It makes your intent clear, your results predictable, and your data quality visible. It works hand in hand with schema enforcement, range checks, and other validation mechanisms. By understanding the difference between `cast` and `try_cast`, and by following best practices, you can handle dirty data gracefully and keep your pipelines running smoothly.
