# Understand schema enforcement

Delta Lake validates data types automatically when you write data to a table. This built-in mechanism is called schema enforcement. It compares the data types of incoming columns against the target table's schema. When a type mismatch occurs, Delta Lake attempts to safely cast the value. If the cast fails, the write operation raises an error. Schema enforcement is a foundational feature of Delta Lake that helps maintain data quality and consistency. It prevents accidental corruption of table data by rejecting writes that do not conform to the expected structure. It also provides a predictable and reliable way to manage schema changes over time.

Schema enforcement is not the same as schema evolution. Schema enforcement rejects writes that do not match the existing schema. Schema evolution allows you to intentionally add new columns or change types under controlled conditions. Both are important, but they serve different purposes. Schema enforcement is the default behavior. Schema evolution is an opt-in feature that you enable when you want to allow the schema to change. Understanding the difference is critical for building robust data pipelines.

## How schema enforcement works

When you write data to a Delta table, Delta Lake performs a series of checks before committing the write. First, it verifies that all columns in the incoming data exist in the target table. If a column is missing from the target table, the write fails. This prevents accidental insertion of unexpected columns. Second, it verifies that the data type of each incoming column matches the data type of the corresponding target column, or that the incoming type can be safely cast to the target type. Safe casting means that the conversion will not lose information or produce an incorrect value. For example, an integer can be safely cast to a long or a double. A string that contains only digits can be safely cast to an integer. A string that contains letters cannot be safely cast to an integer.

If a type mismatch occurs and a safe cast is possible, Delta Lake performs the cast automatically and writes the data. If a safe cast is not possible, the write fails with an error. This behavior ensures that the table always contains data that conforms to its declared schema. It also ensures that queries against the table will not encounter unexpected type errors.

## Rules of schema enforcement

Schema enforcement applies the following rules during insert operations:

- All inserted columns must exist in the target table.
- All column data types must match or be safely castable to the target types.

These rules are enforced for all write operations, including INSERT, UPDATE, MERGE, and CREATE TABLE AS SELECT. They apply whether you are writing from a DataFrame, a SQL statement, or a streaming source. The rules are also enforced for batch and streaming writes. This consistency makes Delta Lake a reliable storage layer for both batch and streaming workloads.

## Example of schema enforcement

Consider a table with an integer column. The following SQL creates a table named inventory with three columns: product_id as an integer, quantity as an integer, and last_updated as a date.

```sql
-- Create a Delta table named inventory.
-- The table has three columns with explicit data types.
-- product_id is an integer.
-- quantity is an integer.
-- last_updated is a date.
CREATE TABLE inventory (
    product_id INT,
    quantity INT,
    last_updated DATE
);
```

Now consider an insert operation where the quantity column is provided as a string. The string '100' represents a number. Delta Lake attempts to safely cast the string to an integer. Because '100' can be converted to the integer 100 without losing information, the cast succeeds. The write operation completes successfully.

```sql
-- Insert a row into the inventory table.
-- The quantity value is provided as a string '100'.
-- Delta Lake attempts to cast the string to the target type INT.
-- Because '100' can be safely cast to 100, the insert succeeds.
-- The last_updated value is provided as a string '2026-01-15'.
-- Delta Lake casts it to the DATE type.
INSERT INTO inventory VALUES (1, '100', '2026-01-15');
```

However, consider an insert operation where the quantity column is provided as the string 'fifty'. This string does not represent a number. Delta Lake attempts to cast it to an integer, but the cast fails. The write operation raises an error. The row is not inserted.

```sql
-- Insert a row into the inventory table.
-- The quantity value is provided as a string 'fifty'.
-- Delta Lake attempts to cast the string to the target type INT.
-- Because 'fifty' cannot be cast to an integer, the cast fails.
-- The write operation raises an error.
-- The row is not inserted.
INSERT INTO inventory VALUES (2, 'fifty', '2026-01-15');
```

This example illustrates the core behavior of schema enforcement. It provides a first line of defense against type mismatches. It automatically handles safe conversions and rejects unsafe ones. This reduces the need for manual data cleaning and prevents many common data quality issues.

## Safe casting rules

Delta Lake uses a set of safe casting rules to determine whether a type can be converted to another type. These rules are based on the ANSI SQL standard and the capabilities of the underlying execution engine. In general, a cast is considered safe if it does not lose precision or produce an incorrect value. For example:

- An integer can be safely cast to a long, a float, a double, or a decimal with sufficient precision.
- A long can be safely cast to a double or a decimal with sufficient precision.
- A float can be safely cast to a double.
- A string can be safely cast to a numeric type if the string contains a valid numeric literal.
- A string can be safely cast to a date or timestamp if the string contains a valid date or timestamp literal.
- A date can be safely cast to a timestamp.
- A timestamp can be safely cast to a date, but this loses the time portion. Therefore, it is not always considered safe. In Delta Lake, casting a timestamp to a date is allowed but may be considered lossy. The exact behavior depends on the configuration.

If a cast is not safe, Delta Lake does not perform it automatically. Instead, it raises an error. This prevents silent data corruption. For example, casting a double to an integer is not safe because it loses the fractional part. Casting a string that contains non-numeric characters to an integer is not safe. Casting a timestamp to a date may be considered unsafe because it loses information.

## Explicit casting for more control

Schema enforcement provides automatic safe casting. However, there are times when you want more control over how mismatches are handled. You can use explicit casting to convert data types before writing. Explicit casting allows you to specify the exact conversion you want. It also allows you to handle errors gracefully. For example, you can use the CAST function in SQL or the cast method in PySpark.

```sql
-- Insert a row into the inventory table.
-- Explicitly cast the string '100' to an integer.
-- This is redundant because schema enforcement would do it automatically.
-- But it makes the intent clear.
INSERT INTO inventory VALUES (1, CAST('100' AS INT), CAST('2026-01-15' AS DATE));

-- Insert a row with a string that cannot be cast.
-- Use a CASE expression to handle the error.
-- If the string is not a valid integer, use a default value.
INSERT INTO inventory
SELECT
    2,
    CASE
        WHEN 'fifty' RLIKE '^[0-9]+$' THEN CAST('fifty' AS INT)
        ELSE 0
    END,
    CAST('2026-01-15' AS DATE);
```

In PySpark, you can use the cast method to explicitly convert columns before writing.

```python
# Read data from a source.
df = spark.read.table("raw.inventory")

# Explicitly cast the quantity column to integer.
# The cast will fail if any value cannot be converted.
# You can use the try_cast function to return null instead of failing.
from pyspark.sql.functions import col, expr

df_casted = df.withColumn("quantity", col("quantity").cast("int"))

# Write the casted data to the Delta table.
# Schema enforcement will still apply, but the data is already in the correct type.
df_casted.write.format("delta").mode("append").saveAsTable("inventory")
```

Explicit casting is useful when you want to transform data as part of the write operation. It is also useful when you want to handle errors in a specific way. For example, you might want to replace invalid values with a default, or you might want to route invalid records to a quarantine table. Schema enforcement alone does not provide these options. It either succeeds or fails. Explicit casting gives you more flexibility.

## Schema evolution

Schema enforcement prevents changes to the table schema. However, there are times when you need to add new columns or change column types. Delta Lake supports schema evolution, which allows you to intentionally modify the schema. Schema evolution is not enabled by default. You must explicitly enable it when writing data. For example, you can use the mergeSchema option in PySpark or the MERGE SCHEMA clause in SQL.

```python
# Write data with a new column.
# Enable schema evolution to add the new column to the table.
df.write.format("delta").option("mergeSchema", "true").mode("append").saveAsTable("inventory")
```

```sql
-- Insert data with a new column.
-- Enable schema evolution to add the new column to the table.
INSERT INTO inventory WITH SCHEMA EVOLUTION
SELECT 3, 200, '2026-02-01', 'new_column_value';
```

When schema evolution is enabled, Delta Lake adds new columns to the table schema. It does not change existing column types. Type changes are handled separately and are subject to safe casting rules. If a type change is not safe, the write fails even with schema evolution enabled. This ensures that schema evolution does not compromise data integrity.

Schema evolution is useful for handling changing data sources. It allows you to add columns without rewriting the entire table. It also allows you to handle new fields that appear in the source data. However, schema evolution should be used with caution. Adding too many columns can make the table difficult to manage. Changing column types can break downstream consumers. It is important to have a governance process for schema changes.

## Schema enforcement in streaming

Schema enforcement applies to streaming writes as well as batch writes. When you write a streaming DataFrame to a Delta table, Delta Lake validates the schema of each micro-batch. If the schema of the streaming data does not match the table schema, the write fails. This ensures that streaming data does not corrupt the table.

```python
# Read a streaming source.
streaming_df = spark.readStream.table("raw.inventory")

# Write the streaming data to a Delta table.
# Schema enforcement is applied to each micro-batch.
# If the schema does not match, the write fails.
streaming_df.writeStream.format("delta").option("checkpointLocation", "/path/to/checkpoint").start("inventory")
```

Streaming writes often encounter schema changes in the source. For example, a source system might add a new column. If schema evolution is not enabled, the streaming write will fail. You can enable schema evolution for streaming writes by setting the mergeSchema option. However, you should be careful because schema evolution in streaming can lead to unexpected changes. It is often better to handle schema changes explicitly in the streaming pipeline.

## Schema enforcement and merge operations

Schema enforcement also applies to MERGE operations. A MERGE operation combines insert, update, and delete actions. Delta Lake validates the schema of the source data against the target table schema. If the source data has a column that does not exist in the target, the merge fails. If the source data has a column with a type that cannot be safely cast to the target type, the merge fails.

```sql
-- Merge data from a source table into the inventory table.
-- The source table must have the same schema as the target table.
-- If the source has extra columns or incompatible types, the merge fails.
MERGE INTO inventory AS target
USING source_inventory AS source
ON target.product_id = source.product_id
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;
```

You can use schema evolution with MERGE operations to allow new columns to be added. However, you must explicitly enable it. For example, you can use the WITH SCHEMA EVOLUTION clause.

```sql
-- Merge data with schema evolution.
-- New columns in the source are added to the target table.
MERGE WITH SCHEMA EVOLUTION INTO inventory AS target
USING source_inventory AS source
ON target.product_id = source.product_id
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;
```

## Schema enforcement and Delta Lake internals

Delta Lake stores the table schema in the transaction log. The transaction log is a record of all changes to the table. When you write data, Delta Lake reads the schema from the transaction log and compares it to the schema of the incoming data. If the schemas match or can be safely cast, the write proceeds. If not, the write fails. The transaction log also stores metadata about the table, including the schema, partitioning, and table properties. This metadata is used to enforce schema and other constraints.

Schema enforcement is implemented at the Delta Lake layer, not at the underlying file system layer. This means that it applies regardless of the file format used to store the data. Delta Lake typically stores data in Parquet files. Parquet files have their own schema. Delta Lake uses the Parquet schema to read the data and then applies the Delta table schema. If there is a mismatch, Delta Lake can often resolve it using safe casting. If not, it raises an error.

## Best practices for schema enforcement

To get the most out of schema enforcement, follow these best practices:

- Define your table schema explicitly. Do not rely on schema inference. Explicit schemas make your pipeline more predictable and easier to debug.
- Use appropriate data types. Choose the smallest data type that can hold your data. This saves storage and improves performance. For example, use INT instead of BIGINT if your values fit in an integer.
- Avoid unnecessary type changes. Changing a column type can break downstream consumers. If you must change a type, do it carefully and communicate the change.
- Use explicit casting when you need to transform data during writes. This gives you more control and makes your intent clear.
- Enable schema evolution only when necessary. Schema evolution can be useful, but it can also lead to unexpected changes. Have a governance process for schema changes.
- Monitor schema enforcement errors. If writes are failing due to schema mismatches, investigate the cause. It may indicate a problem in the source data or a bug in your pipeline.
- Test your schema enforcement logic. Write tests that verify that valid data is written and invalid data is rejected. Test edge cases such as nulls, empty strings, and boundary values.

## Common schema enforcement errors

There are several common errors that you may encounter with schema enforcement. Understanding these errors helps you diagnose and fix issues quickly.

One common error is "Failed to merge fields" or "Cannot cast type". This occurs when the incoming data has a type that cannot be safely cast to the target type. For example, trying to insert a string that contains letters into an integer column. The solution is to clean the data before writing or to use explicit casting with error handling.

Another common error is "Column not found". This occurs when the incoming data has a column that does not exist in the target table. The solution is to either add the column to the target table using schema evolution or to remove the column from the incoming data.

Another common error is "Cannot write nullable values to non-null column". This occurs when the target column is defined as NOT NULL and the incoming data contains nulls. The solution is to either allow nulls in the target column or to filter out or replace nulls in the incoming data.

Another common error is "Schema mismatch". This occurs when the overall schema of the incoming data does not match the target table. The solution is to align the schemas or to use schema evolution.

## Schema enforcement vs. schema validation

Schema enforcement is sometimes confused with schema validation. Schema validation is a broader concept that includes checking data types, constraints, and business rules. Schema enforcement specifically focuses on data types and column existence. It does not check nullability, ranges, or other constraints. Those are handled by other mechanisms, such as CHECK constraints, NOT NULL constraints, and data quality expectations. Schema enforcement is the first line of defense. It ensures that the basic structure of the data is correct. Additional validation rules can be layered on top to enforce more specific requirements.

## Schema enforcement in the context of a data pipeline

In a data pipeline, schema enforcement plays a critical role. It ensures that data written to Delta tables is consistent and reliable. It prevents downstream consumers from encountering unexpected type errors. It also helps maintain the integrity of the data lake. When designing a pipeline, you should consider how schema enforcement interacts with other data quality checks. For example, you might use schema enforcement to catch type mismatches, range checks to catch out-of-range values, and nullability checks to catch missing values. Together, these mechanisms provide comprehensive data quality protection.

Schema enforcement also affects how you handle schema changes. If the source schema changes, you must decide whether to evolve the target schema or to transform the data to fit the existing schema. This decision should be based on the requirements of downstream consumers and the governance policies of your organization. In some cases, it is better to fail the pipeline and force a manual review. In other cases, it is better to automatically evolve the schema. Delta Lake gives you the flexibility to choose the right approach for each situation.
