## Use pipeline expectations for type checking

Lakeflow Spark Declarative Pipelines provides expectations that allow you to define data quality rules directly in your pipeline definitions. You can use expectations to check that values can be cast to expected types. Expectations are part of the pipeline definition. They are evaluated as data flows through the pipeline. They can warn, drop, or fail depending on the action you choose. They also produce metrics that you can view in the pipeline UI. This makes them a powerful tool for type checking and data quality validation.

Type checking is important because external data often arrives as strings. A column that should contain numbers may contain values like `"100"`, `"abc"`, `"1,000"`, or an empty string. A column that should contain dates may contain values like `"2026-01-15"`, `"15/01/2026"`, or `"not provided"`. If you write these values directly to a table with numeric or date columns, the write may fail. If you use expectations, you can validate the values before they reach the target table. You can drop invalid records, warn about them, or stop the pipeline. You can also monitor how many records pass and fail.

## What pipeline expectations are

Expectations are decorators in Python and constraints in SQL. They define a Boolean expression that must be true for a record to pass. The expression can use any SQL function, including `try_cast`. The `try_cast` function attempts to convert a value to a target type. If the conversion succeeds, it returns the converted value. If the conversion fails, it returns NULL. By checking `try_cast(...) IS NOT NULL`, you can verify that a value can be safely converted to the target type.

There are three main actions for expectations:

- `expect` logs violations but keeps the record. The record is written to the target table. Metrics record the violation. This is the warn action.
- `expect_or_drop` drops the record before it reaches the target table. The record is not written. Metrics record the drop. This is the drop action.
- `expect_or_fail` stops the pipeline when a violation occurs. The current transaction rolls back. No records from the current update are written. This is the fail action.

In SQL, the same actions are expressed with `ON VIOLATION DROP ROW` and `ON VIOLATION FAIL UPDATE`. If you do not specify an `ON VIOLATION` clause, the default is to warn.

## Python example explained line by line

The following Python example defines a streaming table with two type-checking expectations. Each line is commented.

```python
# Import the pipelines module from pyspark.
# This module provides the decorators for defining tables and expectations.
from pyspark import pipelines as dp

# The @dp.table decorator defines a streaming table or materialized view.
# The function below returns the input data for the table.
@dp.table
# The @dp.expect_or_drop decorator adds an expectation that drops invalid records.
# The first argument is the expectation name: "valid_amount".
# The second argument is the SQL expression: "try_cast(amount AS DECIMAL(10,2)) IS NOT NULL".
# The expression attempts to convert amount to DECIMAL(10,2).
# If the conversion succeeds, try_cast returns a non-NULL value.
# The expression try_cast(...) IS NOT NULL evaluates to TRUE.
# If the conversion fails, try_cast returns NULL.
# The expression evaluates to FALSE, so the record is dropped.
@dp.expect_or_drop("valid_amount", "try_cast(amount AS DECIMAL(10,2)) IS NOT NULL")
# The @dp.expect_or_drop decorator adds a second expectation.
# The name is "valid_date".
# The expression attempts to convert event_date to DATE.
# If the conversion succeeds, the record passes.
# If the conversion fails, the record is dropped.
@dp.expect_or_drop("valid_date", "try_cast(event_date AS DATE) IS NOT NULL")
def validated_transactions():
    # The function returns a streaming DataFrame.
    # The DataFrame is read from the raw_transactions table.
    # The raw table contains the data as it arrived from the source.
    # The expectations are applied to each record as it is processed.
    # Records that fail either expectation are dropped before reaching the target table.
    return spark.readStream.table("raw_transactions")
```

The decorators are applied bottom-up. The `@dp.expect_or_drop` decorators are applied first, then the `@dp.table` decorator. This means the expectations are attached to the table definition. The function `validated_transactions` returns the raw streaming DataFrame. The pipeline applies the expectations to each record. The target table receives only records that pass both expectations.

The expression `try_cast(amount AS DECIMAL(10,2)) IS NOT NULL` checks two things. First, it checks that `amount` can be converted to a decimal with ten total digits and two decimal places. Second, it checks that the result is not null. If `amount` is null, `try_cast` returns null, so the record fails. If you want to allow null values, you must change the expression. We will discuss null handling later.

## SQL example explained line by line

The following SQL example defines the same streaming table with two type-checking constraints. Each part is commented.

```sql
-- Create or refresh a streaming table named validated_transactions.
-- The table has two constraints that validate types.
CREATE OR REFRESH STREAMING TABLE validated_transactions (
    -- The valid_amount constraint checks that amount can be cast to DECIMAL(10,2).
    -- The EXPECT clause contains the Boolean expression.
    -- The expression uses try_cast to attempt the conversion.
    -- If the conversion succeeds, try_cast returns a non-NULL value.
    -- The expression try_cast(...) IS NOT NULL evaluates to TRUE.
    -- If the conversion fails, try_cast returns NULL.
    -- The expression evaluates to FALSE, so the constraint is violated.
    -- ON VIOLATION DROP ROW means the invalid record is dropped before write.
    CONSTRAINT valid_amount EXPECT (try_cast(amount AS DECIMAL(10,2)) IS NOT NULL) ON VIOLATION DROP ROW,
    -- The valid_date constraint checks that event_date can be cast to DATE.
    -- The same logic applies.
    -- Invalid records are dropped.
    CONSTRAINT valid_date EXPECT (try_cast(event_date AS DATE) IS NOT NULL) ON VIOLATION DROP ROW
)
-- The AS SELECT clause defines the source of the data.
-- STREAM(raw_transactions) reads from the raw_transactions streaming source.
-- The constraints are applied to each record as it is processed.
AS SELECT * FROM STREAM(raw_transactions);
```

The SQL syntax uses `CONSTRAINT` to name each expectation. The `EXPECT` keyword introduces the Boolean expression. The `ON VIOLATION DROP ROW` clause specifies the action. You can also use `ON VIOLATION FAIL UPDATE` to stop the pipeline. If you omit the `ON VIOLATION` clause, the default is to warn. The `AS SELECT` clause defines the input data. The constraints are applied to the records returned by the query.

## Choosing the right violation action

The action you choose depends on your business requirements and the criticality of the data. Use `expect` when you want visibility into data quality issues without blocking data flow. This is useful during initial data quality assessment. It is also useful when downstream consumers can tolerate some invalid records. The invalid records are still written to the target table. You can monitor the metrics and decide later whether to escalate to drop or fail.

Use `expect_or_drop` when invalid records should be filtered out silently. This is useful for data cleansing. It ensures that only valid records reach downstream consumers. It is often used when invalid records are not useful and can be safely discarded. However, dropping records can hide problems. You should monitor the drop count. If it increases suddenly, investigate the source system. Consider writing dropped records to a quarantine table for later analysis.

Use `expect_or_fail` when data integrity is critical and invalid records are unacceptable. This is useful for financial data, regulatory data, or safety-critical data. It ensures that bad data does not reach downstream consumers. It also forces you to fix the problem before the pipeline can continue. However, using fail for every minor issue can cause frequent pipeline stops. Use it sparingly and only for rules that are truly critical. Ensure that you have proper alerting and runbooks.

The following Python examples show each action.

```python
# Warn: log the violation but keep the record.
@dp.expect("valid_amount", "try_cast(amount AS DECIMAL(10,2)) IS NOT NULL")
```

```python
# Drop: remove the invalid record before write.
@dp.expect_or_drop("valid_amount", "try_cast(amount AS DECIMAL(10,2)) IS NOT NULL")
```

```python
# Fail: stop the pipeline when a violation occurs.
@dp.expect_or_fail("valid_amount", "try_cast(amount AS DECIMAL(10,2)) IS NOT NULL")
```

The SQL equivalents are shown below.

```sql
-- Warn: no ON VIOLATION clause.
CONSTRAINT valid_amount EXPECT (try_cast(amount AS DECIMAL(10,2)) IS NOT NULL)
```

```sql
-- Drop: remove the invalid record.
CONSTRAINT valid_amount EXPECT (try_cast(amount AS DECIMAL(10,2)) IS NOT NULL) ON VIOLATION DROP ROW
```

```sql
-- Fail: stop the pipeline.
CONSTRAINT valid_amount EXPECT (try_cast(amount AS DECIMAL(10,2)) IS NOT NULL) ON VIOLATION FAIL UPDATE
```

## Type checking patterns

You can use `try_cast` to check many types. The following examples show common patterns.

For decimal amounts, use `try_cast(amount AS DECIMAL(10,2)) IS NOT NULL`. Choose a precision and scale that match your data. `DECIMAL(10,2)` allows values up to 99,999,999.99. If your data can be larger, use `DECIMAL(18,2)` or `DECIMAL(38,2)`. If your data has more decimal places, increase the scale.

For integers, use `try_cast(quantity AS INT) IS NOT NULL`. If the values can be larger than the integer range, use `BIGINT`. If the values should be positive, add a range check: `try_cast(quantity AS INT) IS NOT NULL AND try_cast(quantity AS INT) > 0`.

For dates, use `try_cast(event_date AS DATE) IS NOT NULL`. If you need to enforce a specific format, use `try_to_date(event_date, 'yyyy-MM-dd') IS NOT NULL`. This function attempts to parse the string using the given format. If the string does not match the format, it returns NULL.

For timestamps, use `try_cast(event_time AS TIMESTAMP) IS NOT NULL` or `try_to_timestamp(event_time, 'yyyy-MM-dd HH:mm:ss') IS NOT NULL`.

For booleans, use `try_cast(is_active AS BOOLEAN) IS NOT NULL`. This accepts values like `'true'`, `'false'`, `'1'`, and `'0'` depending on the engine.

For strings that must match a pattern, use a regular expression. For example, `phone_number REGEXP '^[0-9]{10}$'` checks that the phone number is exactly ten digits. You can combine this with type checking if needed.

## Null handling

Null handling is a common source of confusion. In most engines, `try_cast(NULL AS DECIMAL(10,2))` returns NULL. The expression `try_cast(...) IS NOT NULL` evaluates to FALSE. This means the record fails the expectation. If null is not acceptable, this is the correct behavior. If null is acceptable, you must change the expression.

To allow null values, use `amount IS NULL OR try_cast(amount AS DECIMAL(10,2)) IS NOT NULL`. This expression evaluates to TRUE when `amount` is null. It also evaluates to TRUE when `amount` is a valid decimal. It evaluates to FALSE only when `amount` is a non-null invalid value. The following example shows this pattern.

```python
@dp.expect_or_drop("valid_amount", "amount IS NULL OR try_cast(amount AS DECIMAL(10,2)) IS NOT NULL")
```

In SQL, the same pattern applies.

```sql
CONSTRAINT valid_amount EXPECT (amount IS NULL OR try_cast(amount AS DECIMAL(10,2)) IS NOT NULL) ON VIOLATION DROP ROW
```

If you want to reject null but allow empty strings to be treated as null, you can use `nullif(trim(amount), '')`. For example, `try_cast(nullif(trim(amount), '') AS DECIMAL(10,2)) IS NOT NULL`. This trims whitespace, converts empty strings to null, and then attempts the cast.

## Empty strings and whitespace

Empty strings and strings with only whitespace are common in external data. Depending on the engine, `try_cast('' AS DECIMAL(10,2))` may return null or may fail. To handle this consistently, trim the string before casting. Use `trim(amount)`. If an empty string should be treated as null, use `nullif(trim(amount), '')`. The following example shows a robust expression.

```python
@dp.expect_or_drop("valid_amount", "try_cast(nullif(trim(amount), '') AS DECIMAL(10,2)) IS NOT NULL")
```

This expression trims leading and trailing spaces. If the result is an empty string, `nullif` converts it to null. Then `try_cast` attempts the conversion. If the value is a valid number, the record passes. If the value is invalid, the record is dropped.

## Date and timestamp formats

The `try_cast` function uses the engine's default date parsing rules. These rules may accept multiple formats or may depend on session settings. If you need to enforce a specific format, use `try_to_date` or `try_to_timestamp`. The following example enforces the format `yyyy-MM-dd`.

```python
@dp.expect_or_drop("valid_date", "try_to_date(event_date, 'yyyy-MM-dd') IS NOT NULL")
```

This expression attempts to parse `event_date` using the format `yyyy-MM-dd`. If the string is `'2026-01-15'`, it succeeds. If the string is `'15/01/2026'`, it fails. If you want to allow multiple formats, you can combine conditions with `OR`. For example, `try_to_date(event_date, 'yyyy-MM-dd') IS NOT NULL OR try_to_date(event_date, 'dd/MM/yyyy') IS NOT NULL`.

## Combining type checks with range and business rules

Type checking is often the first step. After you confirm that a value can be converted to the correct type, you may want to check that it falls within an acceptable range. You can combine type and range checks in a single expectation. The following example checks that `amount` is a valid decimal and that it is greater than zero.

```python
@dp.expect_or_drop("valid_amount", """
    try_cast(amount AS DECIMAL(10,2)) IS NOT NULL
    AND try_cast(amount AS DECIMAL(10,2)) > 0
""")
```

This expression uses `try_cast` twice. This is acceptable for clarity. If performance is a concern, you can create an intermediate table that casts the value once and then apply expectations to the casted column. We will discuss this later.

You can also combine type checks with business rules. For example, you might require that a discount percentage is between zero and one hundred, and that only premium customers receive discounts over fifty percent. The following expectation enforces this rule.

```python
@dp.expect("valid_discount", """
    discount_percent IS NULL
    OR (
        try_cast(discount_percent AS DECIMAL(5,2)) IS NOT NULL
        AND try_cast(discount_percent AS DECIMAL(5,2)) >= 0
        AND try_cast(discount_percent AS DECIMAL(5,2)) <= 100
        AND (try_cast(discount_percent AS DECIMAL(5,2)) <= 50 OR customer_tier = 'PREMIUM')
    )
""")
```

This expression allows null discounts. For non-null values, it checks that the value is a valid decimal, that it is between zero and one hundred, and that if it is over fifty, the customer tier is premium.

## Avoiding repeated casts with intermediate tables

In many expectations, you may need to use `try_cast` multiple times. This can be inefficient because the conversion is attempted multiple times for each record. A better approach is to create an intermediate table that performs the cast once. Then you can apply expectations to the casted column. The following example shows this pattern.

```python
# Define an intermediate table that casts the raw values.
@dp.table
def casted_transactions():
    # Read from the raw streaming source.
    return spark.readStream.table("raw_transactions").select(
        "transaction_id",
        # Attempt to cast amount to DECIMAL(10,2).
        # If the cast fails, the result is NULL.
        expr("try_cast(amount AS DECIMAL(10,2))").alias("amount"),
        # Attempt to cast event_date to DATE.
        # If the cast fails, the result is NULL.
        expr("try_cast(event_date AS DATE)").alias("event_date")
    )

# Define the validated table with expectations on the casted columns.
@dp.table
@dp.expect_or_drop("valid_amount", "amount IS NOT NULL")
@dp.expect_or_drop("valid_date", "event_date IS NOT NULL")
def validated_transactions():
    # Read from the intermediate table.
    # The columns are already casted.
    # The expectations check for NULL values, which indicate failed casts.
    return spark.readStream.table("casted_transactions")
```

This pattern separates casting from validation. The intermediate table performs the cast once. The validated table applies expectations to the casted columns. The expectations are simple null checks. This is more efficient and easier to maintain. You can also add range checks to the validated table. For example, `amount > 0`.

In SQL, you can use a common table expression or an intermediate streaming table. The following example uses an intermediate streaming table.

```sql
-- Create an intermediate streaming table that casts the raw values.
CREATE OR REFRESH STREAMING TABLE casted_transactions AS
SELECT
    transaction_id,
    try_cast(amount AS DECIMAL(10,2)) AS amount,
    try_cast(event_date AS DATE) AS event_date
FROM STREAM(raw_transactions);

-- Create the validated streaming table with expectations.
CREATE OR REFRESH STREAMING TABLE validated_transactions (
    CONSTRAINT valid_amount EXPECT (amount IS NOT NULL) ON VIOLATION DROP ROW,
    CONSTRAINT valid_date EXPECT (event_date IS NOT NULL) ON VIOLATION DROP ROW
)
AS SELECT * FROM STREAM(casted_transactions);
```

This approach avoids repeated casts and makes the pipeline easier to reason about.

## Metrics and monitoring

Expectations produce metrics that appear in the pipeline UI. You can select a dataset with expectations and open the Data quality tab. The metrics show how many records passed, how many failed, how many were dropped, and how many were warned. You can also see pass rates over time. These metrics help you monitor validation pass rates and identify systematic data quality issues.

You should set up alerts when violation counts exceed a threshold. For example, if the drop count for `valid_amount` suddenly increases, investigate the source system. If the pass rate falls below a certain percentage, consider whether the rule is too strict or whether the source data has a problem. You can also query the pipeline event log for custom monitoring and reporting.

## Defense in depth

Implementing data type checks at multiple levels creates defense in depth. Each layer catches issues that might slip past others. The layers include schema enforcement, explicit casting, constraints, and pipeline expectations.

Schema enforcement is built into Delta Lake. It validates data types automatically when you write to a table. If the incoming data does not match the target schema, Delta Lake attempts a safe cast. If the safe cast fails, the write fails. Schema enforcement is the first line of defense. It ensures that the basic structure of the data is correct.

Explicit casting is the practice of intentionally converting values to the correct type in your transformation logic. You can use `cast` for strict validation or `try_cast` for safe validation. Explicit casting gives you control and makes your intent clear. It also allows you to handle errors gracefully.

CHECK constraints are table-level rules that are enforced at write time. They can validate types, ranges, patterns, and business rules. They provide a hard guarantee that the data in the table conforms to the rules. They are evaluated for every write. If a write violates a constraint, the write fails.

Pipeline expectations are data quality rules defined in the pipeline. They can warn, drop, or fail. They produce metrics that you can monitor. They are evaluated as data flows through the pipeline. They allow you to handle invalid records without stopping the entire pipeline.

By combining these layers, you can achieve higher data quality in your Unity Catalog tables. For example, you might use expectations to drop invalid records early in the pipeline. Then you might use explicit casting to ensure the correct types. Then you might use CHECK constraints to enforce hard guarantees at the table level. Finally, schema enforcement ensures that the table schema is always respected.

## Best practices

Use `try_cast` in expectations instead of `cast`. If you use `cast` and a value cannot be converted, the expression may raise an error, which can fail the pipeline even if you chose `expect_or_drop`. `try_cast` returns NULL instead of raising an error, so the expectation can handle the failure gracefully.

Name your expectations clearly. A good name describes the rule. For example, `valid_amount` is better than `check1`. Meaningful names make it easier to understand the metrics and diagnose failures.

Handle nulls explicitly. Decide whether null is acceptable for each column. If null is acceptable, add an `IS NULL` condition. If null is not acceptable, use `try_cast(...) IS NOT NULL` without the `IS NULL` condition.

Use `trim` and `nullif` to handle empty strings and whitespace. These are common in external data. Trimming before casting makes your validation more robust.

Use `try_to_date` or `try_to_timestamp` when you need to enforce a specific format. `try_cast` may accept multiple formats, which can lead to inconsistent results.

Avoid repeated casts. Use an intermediate table or a common table expression to compute the cast once. Then apply expectations to the casted column.

Monitor your metrics. Set up alerts for unexpected changes. Investigate sudden increases in violations. Use the metrics to improve data quality at the source.

Test your expectations thoroughly. Create sample data with valid values, invalid values, nulls, empty strings, and boundary values. Verify that valid records pass and invalid records are handled correctly.

Document your expectations. Keep a record of the rules and the reason for each rule. This helps new team members understand the data model. It also helps when you need to modify or remove an expectation.

## Common mistakes

One common mistake is using `cast` instead of `try_cast` in expectations. This can cause the pipeline to fail even when you intended to drop invalid records. Always use `try_cast` for type validation.

Another common mistake is forgetting to handle nulls. If you use `try_cast(...) IS NOT NULL`, null values will fail the expectation. If null is acceptable, you must add an `IS NULL` condition.

Another common mistake is not trimming strings before casting. Empty strings and strings with whitespace can cause unexpected failures. Use `trim` and `nullif` to clean the values.

Another common mistake is using `expect_or_fail` for every rule. This can cause frequent pipeline stops. Use `expect_or_fail` only for critical rules. Use `expect_or_drop` or `expect` for less critical rules.

Another common mistake is not monitoring the metrics. Expectations produce valuable data quality metrics. If you do not monitor them, you may miss systematic problems. Set up alerts and dashboards.

Another common mistake is not testing the expectations. Always test with a variety of values. Test valid values, invalid values, nulls, empty strings, and boundary values. Verify the behavior of each action.

## Testing expectations

You can test expectations by running the pipeline with sample data. Create a small table with test values. Include valid values, invalid values, nulls, empty strings, and values at the boundaries. Run the pipeline and check the target table and the metrics. Verify that valid records are written and invalid records are dropped, warned, or cause a failure depending on the action.

You can also write unit tests for the expectation expressions. Use a SQL query to evaluate the expression against test values. For example, you can run `SELECT try_cast('abc' AS DECIMAL(10,2)) IS NOT NULL` and verify that it returns false. You can run `SELECT try_cast('100.50' AS DECIMAL(10,2)) IS NOT NULL` and verify that it returns true. This helps you confirm that the expression behaves as expected.
