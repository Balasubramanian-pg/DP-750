## Choose the right loading strategy

Loading data into a table is not a single operation. It is a family of operations, each designed for a different relationship between the incoming source data and the existing target data. The source might contain only new records, or it might contain a mix of new records and updates to existing ones. The target might need to be fully replaced, or only a specific partition might need refreshing. Choosing the wrong operation can lead to duplicate rows, lost history, unnecessary cost, or silent data corruption. Choosing the right operation keeps the target table accurate, efficient, and consistent with the source.

In Azure Databricks, the loading operations available are `INSERT INTO` for appending, `INSERT OVERWRITE` for full or partition replacement, `MERGE` for upserts, and the `REPLACE WHERE`, `REPLACE USING`, and `REPLACE ON` clauses for selective replacement. Each operation has a different cost profile and a different set of risks. Append is the cheapest but carries the highest duplicate risk. Merge is the most flexible but requires a unique match and is the most expensive. Replacement operations fall in between, depending on the scope of the replacement. The choice depends on what the source represents and what the target must become after the load.

These notes cover each loading strategy from first principles. They explain the scenario each operation is designed for, the syntax in SQL and PySpark, the conditions under which the operation fails, and the tradeoffs involved. They also cover the important requirement that `MERGE` operations need a unique match between source and target rows, and they explain how to deduplicate source data before merging. They cover schema enforcement, schema evolution, expectations, null handling, case sensitivity, time zones, and how loading strategies fit into the medallion architecture. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and confidently choose the right loading operation for any pipeline.

## Understanding the loading operations

Before choosing an operation, you need to understand what each one does and what it requires. Appending adds new rows to an existing table without changing existing rows. It is the correct choice when the source contains only new records that do not overlap with the target. Overwriting removes existing rows and writes new rows in their place. It is the correct choice when the source is a complete replacement for the target or for a specific partition. Merging compares source rows to target rows on a matching key and applies different actions depending on whether a match exists. It is the correct choice when the source contains a mix of inserts and updates, and sometimes deletes. The `REPLACE` clauses provide selective replacement based on a condition, a set of columns, or a custom matching expression. They are correct when you need to replace a specific slice of the target without a full overwrite and without the complexity of a full merge.

The following table summarizes the scenarios and the recommended operation for each.

| Scenario | Operation | When to use |
|---|---|---|
| New records only | `INSERT INTO` / append | Daily logs, event streams, incremental extracts |
| Full refresh | `INSERT OVERWRITE` | Lookup tables, aggregations, failed batch reprocessing |
| Mixed updates and inserts | `MERGE` | CDC feeds, dimension tables, data synchronization |
| Selective replacement by predicate | `REPLACE WHERE` | Correcting specific date ranges or logical conditions |
| Dynamic data overwrite (all compute types) | `REPLACE USING` | Recommended for row-level overwrites on any table type (partitioned, unpartitioned, liquid clustering) |
| Custom-condition row replacement | `REPLACE ON` | Row-level overwrites with NULL-safe or complex matching conditions |

The table shows that the choice is driven by the relationship between source and target. If the source is new data, append. If the source is a complete replacement, overwrite. If the source contains changes to existing records, merge or use a `REPLACE` clause. The rest of these notes explains each operation in detail.

## Appending new records with INSERT INTO

Appending is the simplest loading operation. It adds rows to the end of a table without modifying existing rows. In SQL, you use `INSERT INTO` with either a `VALUES` clause for literal rows or a `SELECT` statement for query results. In PySpark, you write a DataFrame with append mode using `write.mode("append").saveAsTable(...)` or `write.insertInto(...)`. Appending is fast and cheap because it only writes new files. It does not read or rewrite existing data. This makes it suitable for high-frequency ingestion, such as daily logs and event streams.

The risk of appending is duplicates. `INSERT INTO` does not check whether a row already exists. If you append the same batch twice, the table gets duplicate rows. This is the most common and most damaging mistake when appending. To avoid duplicates within a batch, deduplicate the source before appending. Use `SELECT DISTINCT` in SQL or `dropDuplicates` in PySpark. Deduplicating the source prevents duplicates within the batch, but it does not prevent duplicates between the batch and the existing table. If the batch contains a record that was already appended in a previous run, the append creates a duplicate. To prevent that, you need an idempotent write, which usually means using `MERGE` instead of append.

The following SQL example appends new transactions to a table, deduplicating the source first.

```sql
-- Append new transactions to the sales.transactions table.
-- The column list names the target columns in the order of the SELECT.
-- The SELECT must produce values compatible with those columns.
INSERT INTO sales.transactions (transaction_id, amount, transaction_date)
-- Select distinct rows from the staging table to remove duplicates
-- that may exist within the batch. This does not prevent duplicates
-- that already exist in the target table.
SELECT DISTINCT
    transaction_id,
    amount,
    transaction_date
FROM staging.daily_transactions
-- Filter to only today's transactions.
-- current_date() returns the current date in the session time zone.
WHERE transaction_date = current_date();
```

The statement appends only distinct transactions from today. The `DISTINCT` keyword removes exact duplicate rows from the source. If the staging table contains two identical transactions, only one is appended. If the target table already contains a transaction with the same ID, the append still creates a duplicate. To prevent that, you would use a merge.

The equivalent PySpark operation reads the staging table, deduplicates it, and appends it.

```python
# Import the functions needed for the example.
from pyspark.sql.functions import col, current_date

# Read the staging table into a DataFrame.
df_staging = spark.read.table("staging.daily_transactions")

# Filter to today's transactions.
# current_date() returns the current date in the session time zone.
df_today = df_staging.filter(col("transaction_date") == current_date())

# Remove duplicate rows based on transaction_id.
# dropDuplicates keeps the first occurrence of each transaction_id
# and removes the rest. This prevents duplicates within the batch.
df_deduped = df_today.dropDuplicates(["transaction_id"])

# Append the deduplicated DataFrame to the target table.
# mode("append") adds the rows without modifying existing rows.
# saveAsTable matches columns by name when the table already exists.
df_deduped.write.mode("append").saveAsTable("sales.transactions")
```

The PySpark example filters, deduplicates, and appends. The `saveAsTable` method matches columns by name, which is safer than the positional matching of `insertInto`. If the DataFrame has extra columns, the write fails unless schema evolution is enabled. If the table has columns that the DataFrame does not have, those columns are written as null if they are nullable. If they are non-nullable, the write fails.

Appending is the right choice when the source is known to be new and deduplicated. It is the wrong choice when the source may contain updates or duplicates that must be reconciled. In those cases, use a merge or a replace operation.

## Replacing data with INSERT OVERWRITE

Replacing data removes existing rows and writes new rows in their place. In SQL, `INSERT OVERWRITE` replaces the entire table or a specified partition. In PySpark, you write a DataFrame with `mode("overwrite")`. Overwriting is the correct choice when the source is a complete replacement for the target or for a specific partition. It is simpler than a merge because it does not need a matching key. It is more expensive than an append because it rewrites the affected data.

A full-table overwrite removes every row from the target table and writes the result of the query. This is useful for lookup tables, aggregations, and failed batch reprocessing. The following SQL example replaces the entire contents of a daily summary table.

```sql
-- Replace the entire contents of the daily summary table.
-- INSERT OVERWRITE removes all existing rows before inserting the new rows.
-- The table must already exist. The statement does not create the table.
INSERT OVERWRITE sales.daily_summary
-- Select the new contents of the table.
SELECT
    region,
    -- Sum the transaction amounts, ignoring nulls.
    SUM(amount) AS total_sales,
    -- Count all transactions in each region.
    COUNT(*) AS transaction_count
FROM sales.transactions
-- Filter to only today's transactions.
WHERE transaction_date = current_date()
-- Group the transactions by region.
GROUP BY region;
```

The statement removes every row in `sales.daily_summary` and inserts one row per region for the current date. The operation is atomic in Delta Lake. If the query fails, the table is left unchanged. If the query succeeds, the new rows replace the old rows.

The equivalent PySpark operation writes a DataFrame with overwrite mode.

```python
# Import the functions needed for the aggregation.
from pyspark.sql.functions import col, sum, count, current_date

# Read the transactions table.
df_transactions = spark.read.table("sales.transactions")

# Filter to today's transactions and aggregate by region.
df_summary = (
    df_transactions
    .filter(col("transaction_date") == current_date())
    .groupBy("region")
    .agg(
        # Sum the transaction amounts, ignoring nulls.
        sum("amount").alias("total_sales"),
        # Count all transactions in each region.
        count("*").alias("transaction_count")
    )
)

# Overwrite the daily summary table with the new aggregation.
# mode("overwrite") removes all existing rows and writes the new rows.
df_summary.write.mode("overwrite").saveAsTable("sales.daily_summary")
```

The PySpark example produces the same result. The `mode("overwrite")` replaces the table contents. If the DataFrame schema differs from the table schema, the write fails unless schema evolution is enabled.

For partitioned tables, you can overwrite only specific partitions. This is much cheaper than a full-table overwrite when the table is large and only a few partitions need refreshing. In SQL, you use `INSERT OVERWRITE` with a `PARTITION` clause. In PySpark, you write with `partitionBy` and overwrite mode.

The following SQL example overwrites only the January 2026 partition.

```sql
-- Replace only the January 2026 partition of the monthly report table.
-- INSERT OVERWRITE with PARTITION removes only the rows in the specified
-- partition and inserts the new rows. Other partitions are left untouched.
INSERT OVERWRITE sales.monthly_report
-- The PARTITION clause names the partition column and value.
PARTITION (report_month = '2026-01')
-- Select the new contents of the partition.
SELECT
    region,
    product_category,
    SUM(amount) AS revenue
FROM sales.transactions
-- Filter to transactions in January 2026.
WHERE transaction_date BETWEEN '2026-01-01' AND '2026-01-31'
GROUP BY region, product_category;
```

The statement removes the rows in the `report_month = '2026-01'` partition and inserts the new rows. Other partitions are not modified. This is a static partition overwrite. It always writes to the specified partition, regardless of the values in the data.

The PySpark equivalent adds a constant partition column and writes with `partitionBy`.

```python
# Read the transactions table.
df_transactions = spark.read.table("sales.transactions")

# Filter to January 2026 transactions and aggregate.
df_january = (
    df_transactions
    .filter(
        (col("transaction_date") >= "2026-01-01") &
        (col("transaction_date") <= "2026-01-31")
    )
    .groupBy("region", "product_category")
    .agg(sum("amount").alias("revenue"))
)

# Add the partition column with a constant value.
df_january = df_january.withColumn("report_month", lit("2026-01"))

# Overwrite the January partition.
# partitionBy("report_month") organizes the output by report_month.
# mode("overwrite") replaces the existing data in the partitions written.
df_january.write.mode("overwrite").partitionBy("report_month").saveAsTable("sales.monthly_report")
```

Dynamic partition overwrite is an alternative mode in which Spark replaces only the partitions present in the incoming data. This is useful when the incoming data touches multiple partitions. In PySpark, you enable it with `spark.conf.set("spark.sql.sources.partitionOverwriteMode", "dynamic")`. However, the SQL `INSERT OVERWRITE PARTITION` syntax combined with dynamic mode is restricted to classic compute only. It does not work on Databricks SQL warehouses or serverless compute. For new pipelines, Databricks recommends `REPLACE USING` over partition overwrite because partition overwrite can use stale data when partitioning changes.

## Upserting with MERGE

A merge, or upsert, combines updates and inserts in a single atomic operation. In SQL, you use `MERGE INTO`. In PySpark, you use the Delta Lake `merge()` method on a `DeltaTable` object. Merging is essential for processing change data capture feeds, maintaining slowly changing dimensions, and synchronizing data from source systems. The merge matches source rows to target rows using an `ON` clause, usually equality on a primary key. For each source row, the merge determines whether a match exists. `WHEN MATCHED` clauses specify actions for matched rows, such as `UPDATE SET` or `DELETE`. `WHEN NOT MATCHED` clauses specify actions for unmatched source rows, such as `INSERT`.

The following SQL example shows a basic merge that updates existing customers and inserts new ones.

```sql
-- Merge the customer_updates source into the customers target table.
-- The merge matches rows on customer_id.
MERGE INTO customers AS target
USING customer_updates AS source
ON target.customer_id = source.customer_id
-- When a customer already exists, update the mutable fields.
WHEN MATCHED THEN
    UPDATE SET
        target.email = source.email,
        target.phone = source.phone,
        target.last_updated = current_timestamp()
-- When a customer does not exist, insert a new row.
WHEN NOT MATCHED THEN
    INSERT (customer_id, name, email, phone, created_date, last_updated)
    VALUES (
        source.customer_id,
        source.name,
        source.email,
        source.phone,
        current_timestamp(),
        current_timestamp()
    );
```

The statement matches on `customer_id`. For each source row, if a target row with the same `customer_id` exists, the target row is updated. If no match exists, a new row is inserted. The merge is atomic. If any part fails, the entire merge is rolled back.

Conditional logic in `WHEN` clauses allows you to update only changed rows, delete rows under specific conditions, and apply different actions to different subsets. The following SQL example updates products only when the price has changed, deletes discontinued products, and inserts new products.

```sql
-- Merge the product_feed source into the products target table.
MERGE INTO products AS target
USING product_feed AS source
ON target.sku = source.sku
-- Update the price only when the source price differs from the target price.
WHEN MATCHED AND source.price <> target.price THEN
    UPDATE SET
        target.price = source.price,
        target.updated_at = current_timestamp()
-- Delete the product when the source marks it as discontinued.
WHEN MATCHED AND source.discontinued = true THEN
    DELETE
-- Insert a new product when the sku does not exist in the target.
WHEN NOT MATCHED THEN
    INSERT *;
```

The first `WHEN MATCHED` clause has a condition. The action is executed only if the condition is true. The second `WHEN MATCHED` clause deletes discontinued products. The `INSERT *` shorthand inserts all columns from the source that match the target schema.

The equivalent PySpark merge uses the Delta Lake API.

```python
# Import the DeltaTable class.
from delta.tables import DeltaTable

# Read the source data.
df_source = spark.read.table("staging.product_feed")

# Load the target Delta table.
delta_table = DeltaTable.forName(spark, "products")

# Perform the merge.
(delta_table.alias("target")
 .merge(
     df_source.alias("source"),
     "target.sku = source.sku"
 )
 .whenMatchedUpdate(
     condition="source.price <> target.price",
     set={
         "price": "source.price",
         "updated_at": "current_timestamp()"
     }
 )
 .whenMatchedDelete(
     condition="source.discontinued = true"
 )
 .whenNotMatchedInsertAll()
 .execute()
)
```

The PySpark version uses method chaining. The `whenMatchedUpdate` method takes a condition and a dictionary that maps target columns to source expressions. The `whenMatchedDelete` method takes a condition. The `whenNotMatchedInsertAll` method inserts all columns from the source. The `execute` method runs the merge.

An important requirement for merges is that the matching key must be unique on both sides. If multiple source rows match the same target row, the operation fails with an error about multiple matches. If multiple target rows match the same source row, the merge may update the target multiple times, and the final result is not deterministic. Always deduplicate the source before merging. The following table summarizes the merge clauses.

| Clause | Applies to | Typical action |
|---|---|---|
| `WHEN MATCHED THEN` | Rows that match the `ON` condition | `UPDATE SET`, `DELETE` |
| `WHEN MATCHED AND condition THEN` | Matched rows that also satisfy a condition | `UPDATE SET`, `DELETE` |
| `WHEN NOT MATCHED THEN` | Source rows with no match in target | `INSERT` |
| `WHEN NOT MATCHED BY SOURCE THEN` | Target rows with no match in source | `UPDATE SET`, `DELETE` |

The `WHEN NOT MATCHED BY SOURCE` clause handles target rows that have no source match. It is useful for synchronizing a target with a source that represents the complete set of current records. It requires Databricks Runtime 12.2 and above.

## Selective replacement with REPLACE WHERE

`REPLACE WHERE` deletes rows matching a condition before inserting new rows. It is more flexible than a full-table overwrite because it replaces only the rows that satisfy the condition. It is simpler than a merge because it does not require a source table reference or a key comparison. You use `INSERT INTO` with a `REPLACE WHERE` clause followed by a `SELECT` statement. The condition can reference any column in the target table. The rows that match the condition are deleted, and the rows from the `SELECT` are inserted.

The following SQL example replaces transactions for a specific date range.

```sql
-- Replace transactions for a specific date range.
-- INSERT INTO with REPLACE WHERE deletes rows in the target table
-- that match the condition, then inserts the rows from the SELECT.
INSERT INTO sales.transactions
-- The REPLACE WHERE clause specifies the condition for deletion.
REPLACE WHERE transaction_date BETWEEN '2026-01-01' AND '2026-01-07'
-- Select the corrected transactions to insert.
SELECT * FROM staging.corrected_transactions;
```

The statement deletes all rows in `sales.transactions` where the transaction date falls in the first week of January 2026, then inserts all rows from the staging table. The staging table should contain only the corrected transactions for that date range. The condition applies to the target table, not to the source. If the source contains rows outside the range, those rows are still inserted.

PySpark does not have a direct equivalent to `REPLACE WHERE`. You can achieve the same result with a Delta table delete followed by an append, but the two operations are not atomic together. For atomic replacement, use the SQL `REPLACE WHERE` clause or a merge operation.

## Dynamic replacement with REPLACE USING

`REPLACE USING` is the recommended approach for dynamic data overwrites in Databricks. It works across all compute types, including Databricks SQL warehouses and serverless compute, and it does not require Spark session configuration. Unlike partition overwrite, `REPLACE USING` supports partitioned tables, unpartitioned tables, and tables with liquid clustering. The clause atomically deletes rows in the target table that match incoming rows on the specified columns, then inserts the new rows. Rows that do not match the specified columns are left untouched.

The following SQL example replaces only the partitions touched by the incoming data.

```sql
-- Replace only the partitions touched by the incoming data.
-- INSERT INTO with REPLACE USING deletes rows in the target table
-- that match the incoming rows on the report_month column,
-- then inserts the new rows.
INSERT INTO sales.monthly_report
  -- The REPLACE USING clause names the columns used for matching.
  REPLACE USING (report_month)
-- Select the corrected data to insert.
SELECT
    region,
    product_category,
    SUM(amount) AS revenue,
    report_month
FROM staging.corrected_transactions
GROUP BY region, product_category, report_month;
```

The statement deletes rows in `sales.monthly_report` that have the same `report_month` as the incoming rows, then inserts the new rows. If the incoming data contains January and February, both months are replaced. March is left untouched. The operation is atomic. In Databricks Runtime 16.3 through 17.1, the `USING` columns must be the table's full set of partition columns. In Databricks Runtime 17.2 and above, any columns on any table type are supported.

`REPLACE USING` is more flexible and more predictable than partition overwrite. It is the recommended approach for new pipelines because it works everywhere and does not depend on the table's partitioning scheme.

## Custom matching with REPLACE ON

`REPLACE ON` replaces rows based on a user-defined condition across the source and target. It is more flexible than `REPLACE USING` because the condition can be any expression, not just equality on a set of columns. It also treats null values as equal, which is useful when the matching columns can contain nulls. `REPLACE ON` requires Databricks Runtime 17.1 and above.

The following SQL example replaces rows matching a custom condition.

```sql
-- Replace rows matching a user-defined condition across source and target.
INSERT INTO sales.transactions
  -- The REPLACE ON clause specifies the matching condition.
  REPLACE ON (target.transaction_id = source.transaction_id)
-- Select the corrected transactions from the staging table.
SELECT * FROM staging.corrected_transactions AS source;
```

The statement deletes rows in `sales.transactions` where the transaction ID matches a transaction ID in the staging table, then inserts the staging rows. The condition can be more complex than equality. `REPLACE ON` treats null values as equal, so if the matching column is null in both the target and the source, the rows are considered matching.

## Comparing the loading strategies

The following table compares the loading strategies across several dimensions.

| Strategy | Scope | Duplicate risk | Atomicity | Compute support | Typical use |
|---|---|---|---|---|---|
| `INSERT INTO` | New rows | High if source not deduplicated | Atomic | All | Incremental logs, event streams |
| `INSERT OVERWRITE` | Full table or partition | Low | Atomic | All | Full refresh, partition rebuild |
| `MERGE` | Matched and unmatched rows | Low if key is unique | Atomic | All | CDC, slowly changing dimensions |
| `REPLACE WHERE` | Rows matching a predicate | Low | Atomic | All | Correcting specific date ranges |
| `REPLACE USING` | Rows matching specified columns | Low | Atomic | All | Dynamic overwrites on any table type |
| `REPLACE ON` | Rows matching a custom condition | Low | Atomic | DBR 17.1+ | NULL-safe or complex matching |

The table shows that `REPLACE USING` and `REPLACE ON` are the most flexible replacement operations. `MERGE` is the most powerful for handling mixed updates and inserts. `INSERT INTO` is the cheapest but requires careful deduplication. `INSERT OVERWRITE` is the simplest for full refreshes.

## Handling duplicates and uniqueness

Duplicates are the most common source of data quality problems in loading pipelines. `INSERT INTO` does not check for duplicates, so appending the same batch twice creates duplicate rows. `MERGE` requires a unique match, so if the source contains duplicate keys, the merge fails. The solution is to deduplicate the source before loading. In SQL, use `SELECT DISTINCT` or a window function such as `ROW_NUMBER()` to keep one row per key. In PySpark, use `dropDuplicates`. The following example shows deduplication before a merge.

```sql
-- Deduplicate the source before merging.
-- The row_number() function assigns a sequential number to each row
-- within each partition of customer_id, ordered by last_updated descending.
-- The row with row_number 1 is the most recent record for each customer.
WITH deduped AS (
    SELECT *,
           ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY last_updated DESC) AS rn
    FROM customer_updates
)
-- Use only the most recent record for each customer.
SELECT * FROM deduped WHERE rn = 1;
```

In PySpark, the equivalent uses a window function.

```python
from pyspark.sql.window import Window
from pyspark.sql.functions import row_number, col

# Define a window partitioned by customer_id and ordered by last_updated descending.
window = Window.partitionBy("customer_id").orderBy(col("last_updated").desc())

# Add a row number and keep only the first row per customer.
df_deduped = (
    df_source
    .withColumn("rn", row_number().over(window))
    .filter(col("rn") == 1)
    .drop("rn")
)
```

Deduplicating the source ensures that the merge has a unique key and that appends do not create duplicates within the batch. For idempotent writes that prevent duplicates across batches, use `MERGE` instead of append.

## Schema enforcement, evolution, and expectations

Delta Lake enforces schema on all loading operations. When you append, overwrite, or merge, Delta Lake compares the schema of the incoming data with the schema of the target table. If the incoming data has extra columns, the operation fails by default. If the data is missing nullable columns, those columns are written as null. If a non-nullable column is missing, the operation fails. Schema evolution allows you to add new columns during a load. In SQL, you use `WITH SCHEMA EVOLUTION` in a `MERGE` statement. In PySpark, you use the `mergeSchema` option. Schema evolution should be used deliberately because it changes the table schema and may break downstream consumers.

Expectations are data quality rules that you attach to a pipeline. In Lakeflow pipelines, expectations can drop, fail, or warn on rows that violate a rule. For example, you can add an expectation that `customer_id` is not null. If a row violates the expectation, the pipeline can drop it before the load. Expectations help you enforce data quality at the point of ingestion. They complement schema enforcement, which validates structure.

## Null handling, case sensitivity, and time zones

Null handling differs across loading operations. In `INSERT INTO`, nulls are written as null if the target column is nullable. In `MERGE`, nulls in the matching key do not match unless you use `IS NOT DISTINCT FROM` or `eqNullSafe`. Nulls in `UPDATE SET` clauses are governed by the target column's nullability. In `REPLACE USING`, nulls in the matching columns do not match unless the clause treats them as equal. `REPLACE ON` treats nulls as equal. Always consider how nulls will behave in your chosen operation.

Case sensitivity affects string keys and values. By default, Spark's string comparisons are case-sensitive. `'ABC'` and `'abc'` do not match. If your data has inconsistent casing, normalize it before loading or use a case-insensitive collation. Time zones affect functions such as `current_timestamp()` and `current_date()`. These functions use the session time zone. Set the session time zone explicitly at the start of the job with `spark.conf.set("spark.sql.session.timeZone", "UTC")` to avoid off-by-hours errors. Store timestamps in UTC and convert to local time only for display.

## Loading strategies in the medallion architecture

In a medallion architecture, loading strategies are used differently in each layer. The bronze layer holds raw data as it arrived. Bronze tables are often append-only because the raw history is valuable for auditing and reprocessing. The silver layer holds cleaned, conformed data. Silver tables may use merges to apply change data capture feeds and maintain slowly changing dimensions. They may use `REPLACE USING` to reprocess failed batches. The gold layer holds aggregated, denormalized data. Gold tables are often fully overwritten on each refresh because they are derived from silver and do not need to preserve history at the gold level.

A common pattern is to merge changes into silver and then overwrite the affected partitions in gold. For example, if January transactions are corrected, you merge the corrections into the silver transactions table, then overwrite the January partition in the gold monthly summary table. This keeps the gold table consistent with the corrected silver data.

Delta Lake provides atomic transactions, file statistics, and optimistic concurrency control. Unity Catalog governs access and records lineage. Together they make loading operations safe and auditable.

## Best practices

Choose the loading operation based on the relationship between source and target. Use append for new records, overwrite for full refreshes, merge for mixed updates and inserts, and the `REPLACE` clauses for selective replacement.

Deduplicate the source before appending or merging. Use `SELECT DISTINCT`, `dropDuplicates`, or a window function to keep one row per key.

Use an explicit column list in `INSERT INTO` statements to make them independent of column order.

Set the session time zone explicitly to UTC at the start of the job.

Use schema evolution deliberately and communicate changes to downstream consumers.

Test loading logic with small datasets that include duplicates, nulls, and boundary values.

Run `OPTIMIZE` periodically to compact small files created by frequent appends and merges.

## Common mistakes and pitfalls

The most common mistake is appending the same batch twice, creating duplicate rows. Deduplicate the source and use `MERGE` for idempotent writes.

A second mistake is using a non-unique key in a merge. The merge fails or produces non-deterministic results. Always ensure the key is unique on both sides.

A third mistake is forgetting that nulls do not match in merge conditions. Use `IS NOT DISTINCT FROM` or `eqNullSafe` if nulls should match.

A fourth mistake is using `WHEN NOT MATCHED BY SOURCE` on a partial batch. This can mark many target rows as inactive or delete them. Verify that the source represents the intended scope.

A fifth mistake is enabling schema evolution without communication. Adding columns changes the table schema and may break downstream consumers.

A sixth mistake is using dynamic partition overwrite in SQL on serverless compute. It is restricted to classic compute. Use `REPLACE USING` instead.

## Testing loading strategies

Test each loading operation with small datasets that include the rows to be loaded, rows to be left unchanged, duplicates, and nulls. Verify that the correct rows are appended, updated, inserted, or deleted, and that rows outside the scope are untouched. The following example shows a test for a merge.

```python
from delta.tables import DeltaTable
from pyspark.sql import Row

# Build target and source DataFrames.
target_data = [Row(id=1, value="old"), Row(id=2, value="keep")]
source_data = [Row(id=1, value="new"), Row(id=3, value="insert")]
df_target = spark.createDataFrame(target_data)
df_source = spark.createDataFrame(source_data)

# Write the target to a temporary Delta table.
df_target.write.mode("overwrite").saveAsTable("tmp.target")

# Perform the merge.
delta_table = DeltaTable.forName(spark, "tmp.target")
(delta_table.alias("t").merge(df_source.alias("s"), "t.id = s.id")
 .whenMatchedUpdateAll()
 .whenNotMatchedInsertAll()
 .execute())

# Verify the result.
rows = spark.read.table("tmp.target").orderBy("id").collect()
assert rows[0].value == "new"  # id=1 updated
assert rows[1].value == "keep" # id=2 untouched
assert rows[2].value == "insert" # id=3 inserted
```

## Performance considerations

Append is the cheapest operation because it only writes new files. It does not read or rewrite existing data. However, many small appends create many small files. Run `OPTIMIZE` periodically to compact them.

Merge is the most expensive because it must read the target files that might contain matches, compare them to the source, and write new files. Use partitioning and clustering to reduce the number of files read. Choose a matching key that is well-distributed and has statistics.

`INSERT OVERWRITE` rewrites the entire table or partition. A full-table overwrite is expensive for large tables. Partition-level overwrite is cheaper because it rewrites only the affected partitions.

`REPLACE USING` and `REPLACE ON` are selective replacements. Their cost is proportional to the size of the replaced slice, not the entire table.

Use broadcast joins when merging a small source into a large target. Spark can broadcast the source to all executors and avoid shuffling the target.

## Summary

Choosing the right loading strategy depends on the relationship between the source data and the target table. Appending with `INSERT INTO` adds new rows and is correct when the source contains only new records. Overwriting with `INSERT OVERWRITE` replaces the table or a partition and is correct for full refreshes or partition rebuilds. Merging with `MERGE` performs upserts and is correct when the source contains a mix of updates and inserts. The `REPLACE WHERE`, `REPLACE USING`, and `REPLACE ON` clauses provide selective replacement based on a predicate, a set of columns, or a custom condition. `REPLACE USING` is recommended for dynamic overwrites because it works on all compute types and supports partitioned tables, unpartitioned tables, and liquid clustering.

Duplicates are the most common risk. `INSERT INTO` does not check for duplicates, so deduplicate the source before appending. `MERGE` requires a unique match on both sides, so deduplicate the source before merging. Use `SELECT DISTINCT`, `dropDuplicates`, or a window function to keep one row per key.

Schema enforcement, schema evolution, and expectations apply to all loading operations. Null handling, case sensitivity, and time zones affect matching and comparison. Set the session time zone explicitly, normalize string casing, and handle nulls deliberately.

In a medallion architecture, append is common in bronze, merge and selective replacement in silver, and full overwrite in gold. Delta Lake provides atomic transactions and file statistics. Unity Catalog governs access and records lineage.

Best practices include choosing the operation based on the source-target relationship, deduplicating before loading, using explicit column lists, setting the session time zone, using schema evolution deliberately, and testing with small datasets. Common mistakes include appending the same batch twice, using a non-unique merge key, forgetting that nulls do not match, and enabling schema evolution without communication. Performance depends on the scope of the operation. Append is cheapest, merge is most expensive, and selective replacement falls in between. Use partitioning, clustering, and `OPTIMIZE` to keep loads efficient. Used well, the right loading strategy keeps your Delta tables accurate, consistent, and performant.
