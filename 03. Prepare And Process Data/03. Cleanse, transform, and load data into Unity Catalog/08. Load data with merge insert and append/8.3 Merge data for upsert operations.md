## Merge data for upsert operations

A merge operation, often called an upsert, combines the actions of updating existing rows and inserting new rows in a single atomic statement. The term upsert is a contraction of update and insert. In Azure Databricks, the SQL statement for this is `MERGE INTO`, and the PySpark equivalent is the Delta Lake `merge()` method on a `DeltaTable` object. A merge matches rows from a source dataset to rows in a target table using a matching condition, usually equality on a primary key or business identifier. For each source row, the merge determines whether a matching target row exists. If it does, the merge can update the target row, delete it, or leave it unchanged. If it does not, the merge can insert the source row as a new target row. All of these actions happen in a single transaction. Readers see either the state before the merge or the state after the merge, never a partial state.

Merging matters because real-world data arrives as a stream of changes, not as a clean separation of new and updated records. A source system might send a batch of customer records where some customers are new and others have changed their email or phone number. If you append this batch, you create duplicates. If you overwrite the entire table, you lose history and incur unnecessary cost. A merge handles both cases correctly: it updates the existing customers and inserts the new ones. This pattern is essential for slowly changing dimensions, where you track changes to attributes over time. It is also essential for synchronizing data from source systems, where the source is the system of record and the target must reflect its current state. It is the standard way to process change data capture feeds, where a stream of insert, update, and delete events must be applied to a target table in order.

These notes cover merge operations from first principles. They explain the anatomy of a `MERGE` statement, including the `ON` clause that defines the match and the `WHEN MATCHED` and `WHEN NOT MATCHED` clauses that define the actions. They show how to add conditional logic to those clauses, how to delete rows during a merge, and how to use the `INSERT *` shorthand. They show how to perform merges in SQL and in PySpark using the Delta Lake API, including the convenience methods `whenMatchedUpdateAll` and `whenNotMatchedInsertAll`. They also cover null handling, case sensitivity, time zones, schema enforcement, schema evolution, expectations, and how merges interact with Delta Lake, Unity Catalog, and the medallion architecture. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand not only how to write a merge, but when a merge is the correct choice and how to avoid the mistakes that corrupt target tables.

## Understanding upsert and MERGE

An upsert is a database operation that updates a row if it exists and inserts it if it does not. The decision is based on a matching key. In a relational database, this is sometimes implemented with an `INSERT ... ON CONFLICT` statement or a `MERGE` statement. In Delta Lake on Databricks, the `MERGE` statement is the primary tool for upserts. It is more powerful than a simple upsert because it can also delete rows and apply different actions under different conditions. A merge can handle a mix of inserts, updates, and deletes in a single pass. This makes it suitable for processing change data capture feeds, where the source contains a sequence of operations that must be replayed against the target.

The merge operation works by comparing the source and target datasets. The `ON` clause defines the matching condition. For each row in the source, the merge evaluates the condition against the target. If a match is found, the row is considered matched. If no match is found, the row is considered not matched. The `WHEN MATCHED` clauses specify what to do with matched rows. The `WHEN NOT MATCHED` clauses specify what to do with unmatched source rows. In Spark SQL, you can also have `WHEN NOT MATCHED BY SOURCE` clauses to handle target rows that have no match in the source, which is useful for detecting deletions. The order of the `WHEN` clauses matters. The first clause whose condition evaluates to true is executed. Subsequent clauses are not evaluated for that row. This allows you to write a sequence of conditions, from most specific to most general, and ensure that each row is handled by exactly one clause.

The following table summarizes the clauses available in a Spark SQL `MERGE` statement.

| Clause | Applies to | Typical action |
|---|---|---|
| `WHEN MATCHED THEN` | Rows that match the `ON` condition | `UPDATE SET`, `DELETE` |
| `WHEN MATCHED AND condition THEN` | Matched rows that also satisfy a condition | `UPDATE SET`, `DELETE` |
| `WHEN NOT MATCHED THEN` | Source rows with no match in target | `INSERT` |
| `WHEN NOT MATCHED BY SOURCE THEN` | Target rows with no match in source | `UPDATE SET`, `DELETE` |

The table shows that `WHEN NOT MATCHED BY SOURCE` is a separate clause that operates on target rows rather than source rows. It is useful for synchronizing a target table with a source that represents the complete set of current records. If a target row has no corresponding source row, it may need to be deleted or marked as inactive. This clause requires Databricks Runtime 12.2 and above. Not all environments support it, so check your runtime version.

## MERGE syntax in SQL

The SQL `MERGE INTO` statement has a defined structure. It starts with `MERGE INTO` followed by the target table and an alias. Then `USING` followed by the source table or subquery and an alias. Then `ON` followed by the matching condition. Then one or more `WHEN` clauses. Each `WHEN` clause specifies an action. The actions are `UPDATE SET`, `DELETE`, or `INSERT`. The `UPDATE SET` action assigns new values to target columns. The `DELETE` action removes the target row. The `INSERT` action adds a new row to the target table. The `INSERT` action can use `INSERT *` to insert all columns from the source, or it can specify a column list and values.

The following example shows a basic merge that updates existing customers and inserts new ones.

```sql
-- Merge the customer_updates source into the customers target table.
-- The merge matches rows on customer_id.
-- Matched rows have their email and phone updated.
-- Unmatched source rows are inserted as new customers.
MERGE INTO customers AS target
USING customer_updates AS source
ON target.customer_id = source.customer_id
-- When a customer already exists, update the mutable fields.
-- The last_updated column is set to the current timestamp.
WHEN MATCHED THEN
    UPDATE SET
        target.email = source.email,
        target.phone = source.phone,
        target.last_updated = current_timestamp()
-- When a customer does not exist, insert a new row.
-- The created_date and last_updated columns are set to the current timestamp.
WHEN NOT MATCHED THEN
    INSERT (customer_id, name, email, phone, created_date, last_updated)
    VALUES (
        source.customer_id,
        source.name,
        source.email,
        source.phone,
        current_timestamp(),
        current_timestamp()
    );
```

The statement matches on `customer_id`. For each source row, if a target row with the same `customer_id` exists, the target row's email, phone, and last_updated columns are updated. If no match exists, a new row is inserted with the source values and the current timestamp for the date columns. The `current_timestamp()` function returns the current time in the session time zone. This is a common source of subtle bugs if the session time zone is not set explicitly. We will return to time zones later.

The merge is atomic. If any part of the statement fails, the entire merge is rolled back. This is important for data integrity. You never end up with a partially applied batch of changes. The merge also requires that the source and target have compatible schemas. The columns referenced in the `UPDATE SET` and `INSERT` clauses must exist in the target table. The source must provide values for the columns being inserted. If the source has extra columns that are not used, they are ignored. If the target has columns that are not mentioned, they are left unchanged for matched rows and set to null for inserted rows if they are nullable. If they are non-nullable, the insert fails.

## Conditional logic in MERGE

A basic merge updates every matched row. In practice, you often want to update only the rows that have actually changed. Updating every row on every merge creates unnecessary write amplification and can break downstream processes that rely on change detection. Spark SQL allows you to add a condition to a `WHEN MATCHED` clause. The action is executed only if the condition evaluates to true. This lets you write merges that update only changed rows, delete rows under specific conditions, or apply different updates to different subsets of rows.

The following SQL example shows a merge with conditional logic. It updates products only when the price has changed, deletes products that are marked as discontinued, and inserts new products.

```sql
-- Merge the product_feed source into the products target table.
-- The merge matches rows on sku.
-- Different actions are applied based on conditions.
MERGE INTO products AS target
USING product_feed AS source
ON target.sku = source.sku
-- Update the price only when the source price differs from the target price.
-- The condition prevents unnecessary updates when the price is unchanged.
WHEN MATCHED AND source.price <> target.price THEN
    UPDATE SET
        target.price = source.price,
        target.updated_at = current_timestamp()
-- Delete the product when the source marks it as discontinued.
-- The DELETE action removes the target row entirely.
WHEN MATCHED AND source.discontinued = true THEN
    DELETE
-- Insert a new product when the sku does not exist in the target.
-- INSERT * inserts all columns from the source that match the target schema.
WHEN NOT MATCHED THEN
    INSERT *;
```

The first `WHEN MATCHED` clause has the condition `source.price <> target.price`. This condition is evaluated for each matched row. If the price is the same, the condition is false, and the clause is skipped. The second `WHEN MATCHED` clause checks whether the source marks the product as discontinued. If so, the target row is deleted. The order of the clauses matters. The price update condition is checked first. If the price differs and the product is also discontinued, the price update is applied, and the delete clause is skipped because the first matching clause wins. If you want the delete to take precedence, place the delete clause first. The `INSERT *` shorthand inserts all columns from the source into the target. This requires that the source and target have the same column names and compatible types. If the schemas differ, the `INSERT *` fails.

The equivalent PySpark merge uses the Delta Lake API. The API is more verbose but gives you programmatic control over the conditions and actions. The following example shows the same logic in PySpark.

```python
# Import the DeltaTable class and functions.
from delta.tables import DeltaTable
from pyspark.sql.functions import col, current_timestamp

# Read the source data into a DataFrame.
df_source = spark.read.table("staging.product_feed")

# Load the target Delta table.
delta_table = DeltaTable.forName(spark, "products")

# Perform the merge.
# The alias method assigns names to the target and source for use in conditions.
# The merge method takes the source DataFrame and the matching condition.
(delta_table.alias("target")
 .merge(
     df_source.alias("source"),
     "target.sku = source.sku"
 )
 # Update the price only when the source price differs from the target price.
 # The condition is passed as a string and evaluated for each matched row.
 .whenMatchedUpdate(
     condition="source.price <> target.price",
     set={
         "price": "source.price",
         "updated_at": "current_timestamp()"
     }
 )
 # Delete the product when the source marks it as discontinued.
 .whenMatchedDelete(
     condition="source.discontinued = true"
 )
 # Insert a new product when the sku does not exist in the target.
 # whenNotMatchedInsertAll inserts all columns from the source.
 .whenNotMatchedInsertAll()
 .execute()
)
```

The PySpark version uses method chaining to build the merge. The `alias` method assigns names that are used in the condition strings. The `merge` method takes the source DataFrame and the matching condition. The `whenMatchedUpdate` method takes a condition and a dictionary that maps target columns to source expressions. The `whenMatchedDelete` method takes a condition. The `whenNotMatchedInsertAll` method inserts all columns from the source. The `execute` method runs the merge. The order of the `when` methods matters in the same way as the SQL clauses. The first matching condition wins.

## Merge with PySpark Delta Lake API

The Delta Lake Python API provides several methods for building merges. The most general is `whenMatchedUpdate` with a `set` dictionary and an optional `condition`. There are also convenience methods for common cases. `whenMatchedUpdateAll` updates all columns in the target that have the same name in the source. `whenNotMatchedInsertAll` inserts all columns from the source into the target. These convenience methods are useful when the source and target schemas match and you want to update or insert everything. They reduce the amount of code and the chance of a mismatch between column names.

The following example shows a merge using the convenience methods.

```python
# Import the DeltaTable class.
from delta.tables import DeltaTable

# Read the source data.
df_source = spark.read.table("staging.customer_updates")

# Load the target table.
delta_table = DeltaTable.forName(spark, "customers")

# Perform a simple upsert.
# The merge matches on customer_id.
# whenMatchedUpdateAll updates all columns in the target that have
# the same name in the source. This is equivalent to specifying
# each column individually in a set dictionary.
# whenNotMatchedInsertAll inserts all source columns into the target.
(delta_table.alias("target")
 .merge(
     df_source.alias("source"),
     "target.customer_id = source.customer_id"
 )
 .whenMatchedUpdateAll()
 .whenNotMatchedInsertAll()
 .execute()
)
```

The `whenMatchedUpdateAll` method updates every target column whose name matches a source column. It does not update columns that exist only in the target. For example, if the target has a `last_updated` column that is not in the source, that column is not updated. If you want to set `last_updated` to the current timestamp, you must use `whenMatchedUpdate` with a `set` dictionary that includes it. Similarly, `whenNotMatchedInsertAll` inserts all source columns into the target. If the target has additional non-nullable columns that are not in the source, the insert fails. You must either provide values for those columns or ensure they are nullable.

The convenience methods are not available for conditional updates or deletes. If you need a condition, you must use the more general methods. The following table compares the methods.

| Method | Action | Condition support |
|---|---|---|
| `whenMatchedUpdateAll` | Update all matching columns | No |
| `whenMatchedUpdate` | Update specified columns | Yes |
| `whenMatchedDelete` | Delete matched rows | Yes |
| `whenNotMatchedInsertAll` | Insert all source columns | No |
| `whenNotMatchedInsert` | Insert specified columns | Yes |

The table shows that the `All` methods are convenient but limited. Use them when the schemas match and you want to apply the action to every row. Use the general methods when you need conditional logic or when you need to specify a subset of columns.

## Advanced MERGE scenarios

Beyond basic upserts, merges can handle more complex scenarios. You can have multiple `WHEN MATCHED` clauses, each with its own condition and action. You can use `WHEN NOT MATCHED BY SOURCE` to handle target rows that have no match in the source. You can use `INSERT *` to insert all columns. You can also use the `mergeSchema` option to evolve the schema during a merge, which is useful when the source has new columns that should be added to the target.

The following SQL example shows a merge with multiple conditional clauses and a `WHEN NOT MATCHED BY SOURCE` clause.

```sql
-- Merge the customer_updates source into the customers target table.
-- This merge handles updates, deletes, inserts, and target rows
-- that have no corresponding source row.
MERGE INTO customers AS target
USING customer_updates AS source
ON target.customer_id = source.customer_id
-- Update the customer when the source has a newer record.
-- The condition checks the source's last_updated timestamp.
WHEN MATCHED AND source.last_updated > target.last_updated THEN
    UPDATE SET
        target.email = source.email,
        target.phone = source.phone,
        target.last_updated = source.last_updated
-- Delete the customer when the source marks it as deleted.
WHEN MATCHED AND source.is_deleted = true THEN
    DELETE
-- Insert a new customer when the customer_id does not exist in the target.
WHEN NOT MATCHED THEN
    INSERT (customer_id, name, email, phone, created_date, last_updated)
    VALUES (
        source.customer_id,
        source.name,
        source.email,
        source.phone,
        current_timestamp(),
        source.last_updated
    )
-- Mark target customers as inactive when they have no source row.
-- This clause requires Databricks Runtime 12.2 and above.
WHEN NOT MATCHED BY SOURCE THEN
    UPDATE SET target.is_active = false;
```

The statement has four `WHEN` clauses. The first updates a customer when the source record is newer. The second deletes a customer when the source marks it as deleted. The third inserts a new customer. The fourth updates target rows that have no matching source row by setting `is_active` to false. This is a common pattern for synchronizing a target with a source that represents the complete current state. If a customer is removed from the source, the target row is not deleted but marked inactive. This preserves history while reflecting the current state.

The PySpark equivalent uses the `whenNotMatchedBySourceUpdate` method. This method requires Databricks Runtime 12.2 and above. The following example shows the same logic.

```python
# Import the DeltaTable class and functions.
from delta.tables import DeltaTable
from pyspark.sql.functions import col, current_timestamp, lit

# Read the source data.
df_source = spark.read.table("staging.customer_updates")

# Load the target table.
delta_table = DeltaTable.forName(spark, "customers")

# Perform the advanced merge.
(delta_table.alias("target")
 .merge(
     df_source.alias("source"),
     "target.customer_id = source.customer_id"
 )
 # Update when the source record is newer.
 .whenMatchedUpdate(
     condition="source.last_updated > target.last_updated",
     set={
         "email": "source.email",
         "phone": "source.phone",
         "last_updated": "source.last_updated"
     }
 )
 # Delete when the source marks the record as deleted.
 .whenMatchedDelete(
     condition="source.is_deleted = true"
 )
 # Insert new customers.
 .whenNotMatchedInsert(
     values={
         "customer_id": "source.customer_id",
         "name": "source.name",
         "email": "source.email",
         "phone": "source.phone",
         "created_date": "current_timestamp()",
         "last_updated": "source.last_updated"
     }
 )
 # Mark target rows as inactive when they have no source row.
 .whenNotMatchedBySourceUpdate(
     set={
         "is_active": "false"
     }
 )
 .execute()
)
```

The PySpark version uses `whenNotMatchedBySourceUpdate` with a `set` dictionary. The value `"false"` is a string that Spark interprets as a boolean literal. If you need to set a column to a null value, you can use `"null"` or `lit(None)`. The `whenNotMatchedBySourceUpdate` method is powerful but should be used with care. It affects target rows that are not in the source. If the source is a partial batch rather than the complete set of current records, you may inadvertently mark many rows as inactive. Always verify that the source represents the intended scope.

## Null handling in MERGE

Null handling in merges requires attention because nulls behave differently in different parts of the statement. In the `ON` clause, nulls do not match. The condition `target.key = source.key` evaluates to null when either key is null, which is not true. This means that source rows with a null key do not match any target row, and target rows with a null key do not match any source row. If your data can have null keys, you must handle them explicitly. You can use `IS NOT DISTINCT FROM` instead of `=` to treat nulls as equal. The `IS NOT DISTINCT FROM` operator returns true when both sides are null, false when one side is null and the other is not, and the result of `=` otherwise. This is the correct way to match null keys.

The following SQL example uses `IS NOT DISTINCT FROM` to match null keys.

```sql
-- Merge using IS NOT DISTINCT FROM to treat nulls as equal.
-- This allows source rows with a null key to match target rows with a null key.
MERGE INTO customers AS target
USING customer_updates AS source
ON target.customer_id IS NOT DISTINCT FROM source.customer_id
WHEN MATCHED THEN
    UPDATE SET
        target.email = source.email,
        target.phone = source.phone
WHEN NOT MATCHED THEN
    INSERT (customer_id, name, email, phone)
    VALUES (source.customer_id, source.name, source.email, source.phone);
```

The `IS NOT DISTINCT FROM` operator is the null-safe equality operator. It is supported in Spark SQL. In PySpark, the equivalent is `eqNullSafe`. The following example shows the PySpark equivalent.

```python
# Import the DeltaTable class.
from delta.tables import DeltaTable

# Read the source data.
df_source = spark.read.table("staging.customer_updates")

# Load the target table.
delta_table = DeltaTable.forName(spark, "customers")

# Perform the merge with null-safe matching.
# The condition uses eqNullSafe to treat nulls as equal.
(delta_table.alias("target")
 .merge(
     df_source.alias("source"),
     "target.customer_id <=> source.customer_id"
 )
 .whenMatchedUpdateAll()
 .whenNotMatchedInsertAll()
 .execute()
)
```

The `<=>` operator is the null-safe equality operator in Spark SQL. It is equivalent to `IS NOT DISTINCT FROM`. Use it when the matching key can contain nulls and you want nulls to match. Be aware that null-safe matching can produce unexpected matches if nulls are used as placeholders for missing values. In many cases, a null key indicates a data quality issue that should be fixed at the source rather than matched during a merge.

Nulls in the `UPDATE SET` clause are handled according to the target column's nullability. If a target column is nullable, you can set it to a null value. If it is non-nullable, setting it to null fails. If the source value is null and the target column is non-nullable, the update fails. You must either filter out rows with null values before the merge or provide a default value using `coalesce`. The following example shows how to use `coalesce` to provide a default.

```sql
-- Update the email, using a default value when the source email is null.
-- coalesce returns the first non-null argument.
MERGE INTO customers AS target
USING customer_updates AS source
ON target.customer_id = source.customer_id
WHEN MATCHED THEN
    UPDATE SET
        target.email = coalesce(source.email, target.email),
        target.phone = coalesce(source.phone, target.phone);
```

The `coalesce` function returns the source email if it is not null, and the existing target email otherwise. This preserves the existing value when the source is null, which is often the desired behavior. If you want to set the target to null, you can use `source.email` directly, provided the target column is nullable.

## Case sensitivity and time zones

Case sensitivity affects merges in two ways. First, column names in Spark SQL are case-insensitive by default. This means `Customer_ID` and `customer_id` refer to the same column. However, if you have enabled case-sensitive mode, column names become case-sensitive. Second, string values in the matching condition are case-sensitive. `'ABC'` and `'abc'` do not match. If your matching key is a string and the source and target have inconsistent casing, the merge may not match rows that should match. You can normalize the case before the merge using `upper()` or `lower()`, or use a case-insensitive collation if the table is configured for one. Be aware that applying a function to the matching column can prevent predicate pushdown and may force a full scan.

Time zones affect merges when you use timestamp functions such as `current_timestamp()` or when you compare timestamp columns. Spark stores timestamps internally in UTC and displays them in the session time zone. The `current_timestamp()` function returns the current time in the session time zone. If the source data was written in a different time zone, the timestamps may not compare correctly. To avoid this, set the session time zone explicitly at the start of the job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Use timestamp literals with explicit offsets when comparing to timestamps. Store timestamps in UTC in the table, and convert to local time only for display. This keeps the data consistent across time zones.

## Schema enforcement, evolution, and expectations

Delta Lake enforces schema on merge. The source and target must have compatible schemas for the columns that are referenced. If the source has extra columns that are not used in the merge, they are ignored. If the source is missing a column that the target requires for an insert, the insert fails unless the target column is nullable. If you want to add new columns to the target during a merge, you can enable schema evolution. In SQL, you add `WITH SCHEMA EVOLUTION` to the `MERGE` statement. In PySpark, you set the `mergeSchema` option to `true` on the merge. Schema evolution adds new columns from the source to the target. Existing rows get null in the new columns. This is useful when the source schema changes and you want to propagate the change without a separate schema migration.

The following SQL example shows a merge with schema evolution.

```sql
-- Merge with schema evolution enabled.
-- New columns in the source are added to the target table.
-- Existing rows get null in the new columns.
MERGE WITH SCHEMA EVOLUTION INTO customers AS target
USING customer_updates AS source
ON target.customer_id = source.customer_id
WHEN MATCHED THEN
    UPDATE SET *
WHEN NOT MATCHED THEN
    INSERT *;
```

The `UPDATE SET *` and `INSERT *` shorthands update and insert all columns that match between the source and target. With schema evolution, new columns in the source are added to the target. The `UPDATE SET *` updates the matching columns, including the new ones. The `INSERT *` inserts all columns. Schema evolution should be used deliberately because it changes the table schema and may break downstream consumers. In a medallion architecture, schema changes are usually managed in the silver layer and propagated to the gold layer through a rebuild rather than through schema evolution on the gold table.

Expectations are data quality rules that you attach to a pipeline. In Lakeflow pipelines, expectations can drop, fail, or warn on rows that violate a rule. For example, you can add an expectation that `customer_id` is not null. If a row violates the expectation, the pipeline can drop it before the merge. Expectations help you enforce data quality at the point of ingestion. They are not a replacement for schema enforcement, but they complement it. Use expectations to validate business rules, and use schema enforcement to validate structure.

## MERGE and Delta Lake, Unity Catalog, and the medallion architecture

Delta Lake is the storage layer that makes merges efficient and reliable. Without Delta Lake, a merge would require reading the entire target table, comparing it to the source, and writing a new version of the table. Delta Lake stores data in Parquet files with a transaction log and per-file statistics. When you merge, Delta Lake can use the statistics to identify which files contain rows that might match the source. It reads only those files, applies the changes, and writes new files for the affected data. This is much faster than rewriting the entire table. Delta Lake also provides atomic transactions, so the merge is all-or-nothing. Readers never see a partially merged table.

Unity Catalog governs access to the tables involved in a merge. If you have permission to modify the target table, the merge succeeds. If you do not, it fails with a permission error. Unity Catalog also applies row-level filters and column masks before the merge. If the target table has a row-level filter that hides certain rows, those rows are not visible to the merge. This can affect which rows are matched and updated. If you need to merge into rows that are hidden by a policy, you need a policy that grants access. Unity Catalog also records lineage, so you can see which source tables contributed to a merge and which target tables were modified.

In a medallion architecture, merges are used in several places. In the bronze layer, merges are sometimes used to apply change data capture feeds to a raw table. In the silver layer, merges are used to maintain slowly changing dimensions and to synchronize cleaned data with source systems. In the gold layer, merges are less common because gold tables are often fully overwritten or rebuilt from silver. However, merges can be used in gold when the gold table is a large dimension that is updated incrementally. The choice between merge and overwrite depends on the size of the table and the frequency of updates. For large tables with frequent small updates, merge is more efficient. For small tables or full refreshes, overwrite is simpler.

## Best practices

Use a stable, unique key for the `ON` clause. The key should uniquely identify a row in the target. If the key is not unique, the merge may match multiple target rows for a single source row, which causes an error. If the key is not stable, the merge may match the wrong rows. Use a primary key or a business identifier that does not change.

Add conditions to `WHEN MATCHED` clauses to avoid unnecessary updates. Updating every row on every merge creates write amplification and can break change detection. Check whether the values have actually changed before updating.

Use `INSERT *` and `UPDATE SET *` when the source and target schemas match. These shorthands reduce the amount of code and the chance of a column mismatch. If the schemas do not match, specify the columns explicitly.

Handle nulls in the matching key explicitly. Use `IS NOT DISTINCT FROM` or `eqNullSafe` if nulls should match. Otherwise, ensure that the matching key does not contain nulls, or filter out rows with null keys before the merge.

Set the session time zone explicitly. `current_timestamp()` uses the session time zone. Set it to UTC at the start of the job to avoid off-by-hours errors.

Use schema evolution deliberately. Adding columns to the target changes the table schema and may break downstream consumers. Use schema evolution only when the change is intentional and communicated.

Test merges with small datasets that include matches, non-matches, nulls, and duplicates. Verify that the correct rows are updated, inserted, and deleted, and that rows outside the merge scope are untouched.

Monitor merge performance. Merges can be expensive if the target table is large and the source has many rows. Use partitioning and clustering to reduce the number of files that must be read. Run `OPTIMIZE` periodically to compact small files.

## Common mistakes and pitfalls

The most common mistake is using a non-unique key in the `ON` clause. If a source row matches multiple target rows, the merge fails with an error about multiple matches. If a target row matches multiple source rows, the merge may update the target multiple times, and the final result depends on the order of the source rows, which is not deterministic. Always ensure that the key is unique on both sides.

A second mistake is forgetting that nulls do not match in the `ON` clause. Source rows with a null key do not match any target row and are inserted as new rows. Target rows with a null key are not matched and are left unchanged. If you need nulls to match, use `IS NOT DISTINCT FROM` or `eqNullSafe`.

A third mistake is updating every matched row without a condition. This creates unnecessary writes and can break downstream processes that rely on change detection. Add a condition to update only rows that have changed.

A fourth mistake is using `WHEN NOT MATCHED BY SOURCE` when the source is a partial batch. This clause marks target rows that have no source match. If the source is not the complete set of current records, you may inadvertently mark many rows as inactive or delete them. Verify that the source represents the intended scope before using this clause.

A fifth mistake is enabling schema evolution without communicating the change. Adding columns to the target changes the table schema and may break downstream consumers that expect a fixed set of columns.

A sixth mistake is not setting the session time zone. `current_timestamp()` uses the session time zone. If the session time zone differs from the time zone in which the data was written, the timestamps may be inconsistent. Set the session time zone explicitly at the start of the job.

A seventh mistake is performing a merge without considering atomicity and isolation. Delta Lake provides atomic transactions, so readers see either the old or the new state. However, concurrent merges on the same table can conflict. Delta Lake uses optimistic concurrency control. If two merges modify the same files, one may fail with a concurrent modification error. Retry the failed merge or serialize the merges.

## Testing MERGE logic

Merge logic is business logic, and it should be tested. A test for a merge should verify that matched rows are updated correctly, unmatched rows are inserted, deleted rows are removed, and rows outside the merge scope are untouched. The following example shows a test for a simple upsert.

```python
# Import the test helpers and DeltaTable class.
import pytest
from delta.tables import DeltaTable
from pyspark.sql import Row

# Build a target table with two customers.
target_data = [
    Row(customer_id=1, name="Alice", email="alice@old.com", phone="111"),
    Row(customer_id=2, name="Bob", email="bob@old.com", phone="222"),
]
df_target = spark.createDataFrame(target_data)
df_target.write.mode("overwrite").saveAsTable("tmp.customers")

# Build a source DataFrame with one update and one insert.
source_data = [
    Row(customer_id=1, name="Alice", email="alice@new.com", phone="111"),
    Row(customer_id=3, name="Charlie", email="charlie@new.com", phone="333"),
]
df_source = spark.createDataFrame(source_data)

# Load the target Delta table.
delta_table = DeltaTable.forName(spark, "tmp.customers")

# Perform the merge.
(delta_table.alias("target")
 .merge(
     df_source.alias("source"),
     "target.customer_id = source.customer_id"
 )
 .whenMatchedUpdateAll()
 .whenNotMatchedInsertAll()
 .execute()
)

# Read the result and verify.
df_result = spark.read.table("tmp.customers").orderBy("customer_id")
rows = df_result.collect()

# Assert that customer 1 was updated.
assert rows[0].customer_id == 1 and rows[0].email == "alice@new.com", f"Update failed: {rows[0]}"
# Assert that customer 2 was untouched.
assert rows[1].customer_id == 2 and rows[1].email == "bob@old.com", f"Untouched failed: {rows[1]}"
# Assert that customer 3 was inserted.
assert rows[2].customer_id == 3 and rows[2].email == "charlie@new.com", f"Insert failed: {rows[2]}"
# Assert that there are exactly three rows.
assert len(rows) == 3, f"Row count failed: {len(rows)}"
```

The test verifies that the merge updated the existing customer, left the untouched customer unchanged, and inserted the new customer. Run tests like this in your CI pipeline against a small local Spark session. Clean up the temporary table after the test. For more complex merges, add tests for conditional updates, deletes, and null-safe matching.

## Performance considerations

Merge performance depends on the size of the target table, the size of the source, and the selectivity of the matching condition. A merge must read the target files that might contain matching rows, compare them to the source, and write new files for the affected rows. If the target is large and the source is small, the merge can be slow because it must scan the target to find matches. Delta Lake uses file statistics to skip files that cannot contain matches. The statistics include the minimum and maximum values of each column. If the matching key is within the range of a file's statistics, the file is read. If not, the file is skipped. This is why it is important to choose a matching key that is well-distributed and to ensure that statistics are collected for it.

Partitioning and clustering can improve merge performance. If the target table is partitioned by a column that is part of the matching condition, the merge can skip entire partitions that do not contain matching rows. For example, if the target is partitioned by date and the source contains only recent dates, the merge reads only the recent partitions. Liquid clustering provides similar benefits without the need to manage partitions manually. Choose partitioning or clustering columns based on the keys you use in merges.

The size of the source matters. If the source is large, the merge must compare many rows. Consider filtering the source to only the rows that have changed. If the source is a change data capture feed, it should already contain only changes. If the source is a full extract, you may need to compare it to the target to identify changes before the merge, which can be expensive. In some cases, it is more efficient to overwrite the target partition than to merge.

Merge is not always the best choice. If the target table is small, a full overwrite may be faster and simpler. If the source contains the complete set of current records and the target does not need to preserve history, an overwrite is appropriate. If the source contains a mix of inserts, updates, and deletes that must be applied in order, a merge is the right choice. If the source contains only inserts, an append is cheaper. Choose the operation that matches the shape of the data and the requirements of the pipeline.

Finally, monitor the number of files in the target table. Merges create new files and mark old files as removed. Over time, the table can accumulate many small files. Run `OPTIMIZE` periodically to compact small files into larger ones. In Databricks, predictive optimization can do this automatically for Unity Catalog managed tables. Compacting files improves read performance for subsequent merges and queries.

## Summary

A merge, or upsert, combines updates and inserts in a single atomic operation. In Azure Databricks, you write merges with the SQL `MERGE INTO` statement or the Delta Lake PySpark `merge()` method. The merge matches source rows to target rows using an `ON` clause, usually equality on a primary key or business identifier. For each source row, the merge determines whether a match exists. `WHEN MATCHED` clauses specify actions for matched rows, such as `UPDATE SET` or `DELETE`. `WHEN NOT MATCHED` clauses specify actions for unmatched source rows, such as `INSERT`. `WHEN NOT MATCHED BY SOURCE` clauses handle target rows with no source match.

Conditional logic in `WHEN` clauses allows you to update only changed rows, delete rows under specific conditions, and apply different actions to different subsets. The order of the clauses matters; the first matching clause wins. The `INSERT *` and `UPDATE SET *` shorthands insert or update all columns that match between source and target. The Delta Lake PySpark API provides convenience methods `whenMatchedUpdateAll` and `whenNotMatchedInsertAll` for simple upserts, and general methods for conditional logic.

Null handling requires care. In the `ON` clause, nulls do not match unless you use `IS NOT DISTINCT FROM` or `eqNullSafe`. Nulls in `UPDATE SET` clauses are governed by the target column's nullability. Case sensitivity affects string keys; normalize the case or use a collation if needed. Time zones affect `current_timestamp()`; set the session time zone explicitly. Delta Lake enforces schema on merge. Schema evolution can add new columns but should be used deliberately. Expectations can enforce data quality rules before the merge.

In a medallion architecture, merges are used in the bronze and silver layers to apply change data capture feeds and maintain slowly changing dimensions. In the gold layer, overwrites are more common. Delta Lake provides atomic transactions, file statistics, and optimistic concurrency control. Unity Catalog governs access and records lineage.

Best practices include using a stable, unique key, adding conditions to avoid unnecessary updates, handling nulls explicitly, setting the session time zone, and testing with small datasets. Common mistakes include using a non-unique key, forgetting that nulls do not match, using `WHEN NOT MATCHED BY SOURCE` on a partial batch, and enabling schema evolution without communication. Performance depends on the size of the target and source, the selectivity of the matching condition, and the table's partitioning and clustering. Use partitioning, clustering, and `OPTIMIZE` to keep merges efficient. Choose merge when the source contains a mix of updates and inserts, append when it contains only inserts, and overwrite when it contains the complete set of current records. Used well, merge is a powerful and reliable way to keep a Delta table synchronized with a changing source.
