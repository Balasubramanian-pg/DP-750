## Append data with INSERT INTO

Appending data is the operation of adding new rows to an existing table without changing the rows that are already there. In Azure Databricks, the SQL statement for this is `INSERT INTO`, and the PySpark equivalent is writing a DataFrame with append mode or calling `insertInto`. Appending is the correct choice when the new data does not overlap with existing records. Daily transaction logs, new event streams, and incremental extracts from source systems are typical examples. The existing table remains intact, and the new rows are added as an atomic transaction. If the append fails, no rows are added. If it succeeds, all new rows become visible at once.

Appending matters because most data arrives incrementally. A pipeline that ingests data every hour does not rebuild the entire table each time. It appends the new batch to the existing table. This is faster and cheaper than overwriting the table, because only the new files are written. Appending also preserves history. If you append a daily batch, the table becomes a record of every batch that has arrived. This is useful for auditing and for reprocessing. In a medallion architecture, appending is common in the bronze and silver layers, where raw and cleaned data accumulate over time. The gold layer often uses aggregation or merge instead, because gold tables are usually rebuilt or updated rather than appended.

These notes cover appending from first principles. They explain how appending works in Delta Lake, including the transaction log and schema enforcement. They show how to append rows with SQL `INSERT INTO` using `VALUES` and `SELECT`, and how to append DataFrames with PySpark using `write.mode("append")` and `insertInto`. They cover the differences between these methods, especially column matching and schema evolution. They also cover duplicate prevention, null handling, case sensitivity, time zones, partitioned tables, testing, and performance. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand not only how to append data, but when appending is safe and how to avoid the mistakes that create duplicate or inconsistent tables.

## How appending works in Delta Lake

A Delta table is a table stored in the lakehouse with a transaction log. The transaction log records every change to the table as an atomic commit. When you append data, Delta Lake writes new Parquet files to storage and adds a commit entry to the transaction log. The commit entry lists the new files. Readers see the table as of the latest commit. Existing files are not modified. This design makes appends fast and safe. Appends do not need to rewrite existing data. They only add new files. Because the transaction log is the source of truth, an append either commits fully or not at all. There is no partial append visible to readers.

Appending is different from overwriting and merging. Overwriting replaces the table contents, either entirely or for a specified partition. Merging updates existing rows, inserts new rows, and deletes rows based on a matching condition. Appending only inserts new rows. It does not check whether a row already exists. If you append the same batch twice, you get duplicate rows. This is the most important characteristic of appending. It is simple, fast, and cheap, but it requires you to ensure that the source data is deduplicated before loading, or that duplicates are acceptable.

The following table compares append, overwrite, and merge.

| Operation | What it does | Duplicate risk | Typical use |
|---|---|---|---|
| Append | Adds new rows | High if source is not deduplicated | Incremental logs, event streams |
| Overwrite | Replaces table or partition | Low, because old data is removed | Full refresh, partition rebuild |
| Merge | Updates, inserts, deletes based on condition | Low when key is unique | Upserts, slowly changing dimensions |

The table shows that append is the cheapest operation but carries the highest duplicate risk. Overwrite is more expensive because it rewrites data. Merge is the most flexible but also the most expensive because it must compare source and target rows. Choose append when the source is known to be new and deduplicated. Choose merge when the source may contain updates or duplicates that must be reconciled.

Delta Lake enforces schema on append. The schema of the data you append must be compatible with the schema of the table. If the data has extra columns, the append fails unless schema evolution is enabled. If the data is missing columns, those columns are written as null if they are nullable. If they are non-nullable, the append fails. Unity Catalog governs access to the table. If you have permission to modify the table, the append succeeds. If you do not, it fails with a permission error. Unity Catalog also records lineage, so you can see which jobs appended to the table.

## Appending rows with SQL INSERT INTO

SQL provides the `INSERT INTO` statement for appending rows. You can append literal rows with `VALUES` or append the result of a query with `INSERT INTO ... SELECT`. Both forms add rows to the table. The table must already exist. `INSERT INTO` does not create the table. If the table does not exist, the statement fails.

### Inserting literal rows with VALUES

The `VALUES` form is useful for small numbers of rows, such as test data or configuration rows. The following example appends two transactions to a sales table.

```sql
-- Append two new transaction rows to the sales.transactions table.
-- The column list names the columns being inserted.
-- The column list is optional, but including it is safer because it
-- makes the statement independent of the table's column order.
INSERT INTO sales.transactions (transaction_id, amount, transaction_date)
-- The VALUES clause supplies one row per set of parentheses.
-- String literals use single quotes. Numeric literals do not.
-- The date literal uses the ISO format 'YYYY-MM-DD'.
VALUES
    -- First row: transaction TXN001 with amount 150.00 on 2026-01-15.
    ('TXN001', 150.00, '2026-01-15'),
    -- Second row: transaction TXN002 with amount 275.50 on 2026-01-15.
    ('TXN002', 275.50, '2026-01-15');
```

The statement appends two rows. The column list ensures that the values are matched to the correct columns even if the table has more columns or the columns are in a different order. Columns not listed in the column list are filled with null if they are nullable. If a non-nullable column is omitted, the statement fails. The `VALUES` form is not suitable for large datasets because every row must be written in the SQL text. For large datasets, use `INSERT INTO ... SELECT`.

### Inserting rows from a query

The `SELECT` form is the standard way to append data in production. It reads from a staging table, a view, or another query and inserts the result into the target table. The following example appends today's transactions from a staging table.

```sql
-- Append rows from the staging table to the sales.transactions table.
-- The column list names the target columns in the order of the SELECT.
-- The SELECT must produce values that are compatible with those columns.
INSERT INTO sales.transactions (transaction_id, amount, transaction_date)
-- Select the columns from the staging table.
-- The column names in the staging table may differ from the target,
-- but the positions must match the column list.
SELECT
    transaction_id,
    amount,
    transaction_date
FROM staging.daily_transactions
-- Filter to only today's transactions.
-- current_date() returns the current date in the session time zone.
-- If the staging table stores dates in a different time zone,
-- the filter may include or exclude rows incorrectly.
WHERE transaction_date = current_date();
```

The query appends only the rows where `transaction_date` equals the current date. The `current_date()` function uses the session time zone. If the session time zone is UTC and the source data is in a different time zone, the filter may not match the intended rows. To avoid this, set the session time zone explicitly at the start of the job, or use a date literal with an explicit time zone. The `SELECT` form can include joins, aggregations, and filters. It is as flexible as any query.

### Using an explicit column list

Always include an explicit column list in `INSERT INTO`. Without it, the statement depends on the table's column order. If the table schema changes, the statement may break or insert values into the wrong columns. With an explicit list, the statement is stable. The following example shows the safe form.

```sql
-- Append rows using an explicit column list.
-- The column list makes the statement independent of the table's column order.
-- If a new column is added to the table, this statement still works
-- as long as the new column is nullable.
INSERT INTO sales.transactions (transaction_id, amount, transaction_date)
SELECT
    transaction_id,
    amount,
    transaction_date
FROM staging.daily_transactions;
```

The explicit column list also documents which columns the statement populates. A reader can see that the statement does not populate any other columns. If the table has a column that should be populated, the reader can notice its absence.

## Appending DataFrames with PySpark

PySpark provides two main ways to append a DataFrame to an existing table. The first is `write.mode("append").saveAsTable(...)`. The second is `write.insertInto(...)`. Both add rows to the table. They differ in how they match columns and in what they require.

### Using write.mode("append").saveAsTable

The `saveAsTable` method writes the DataFrame to a table in the metastore. With `mode("append")`, it adds the rows to the existing table. If the table does not exist, it creates the table. The following example appends a DataFrame to the sales transactions table.

```python
# Import the functions needed for the example.
# col() references a column by name.
from pyspark.sql.functions import col

# Read the staging table into a DataFrame.
# The staging table holds the new transactions to append.
df_staging = spark.read.table("staging.daily_transactions")

# Filter to only today's transactions.
# current_date() returns the current date in the session time zone.
# The filter reduces the data to the rows that should be appended.
df_new = df_staging.filter(col("transaction_date") == current_date())

# Append the DataFrame to the target table.
# mode("append") adds the rows without modifying existing rows.
# saveAsTable matches columns by name when the table already exists.
# If the DataFrame has extra columns, the write fails unless
# schema evolution is enabled.
df_new.write.mode("append").saveAsTable("sales.transactions")
```

The example reads a staging table, filters to today's rows, and appends the result. The `saveAsTable` method matches columns by name. This means the order of columns in the DataFrame does not need to match the order in the table. However, the names must match. If the DataFrame has a column that the table does not have, the write fails unless schema evolution is enabled. If the table has a column that the DataFrame does not have, that column is written as null if it is nullable. If it is non-nullable, the write fails.

### Using insertInto

The `insertInto` method inserts a DataFrame into an existing table. It requires that the table already exist. Unlike `saveAsTable`, `insertInto` matches columns by position, not by name. This means the order of columns in the DataFrame must match the order of columns in the table. The following example shows `insertInto`.

```python
# Read the staging table into a DataFrame.
df_staging = spark.read.table("staging.daily_transactions")

# Select the columns in the same order as the target table.
# insertInto matches columns by position, so the order must be correct.
# If the order is wrong, values are inserted into the wrong columns.
df_new = df_staging.select(
    "transaction_id",
    "amount",
    "transaction_date"
)

# Insert the DataFrame into the existing table.
# insertInto does not create the table. The table must already exist.
# insertInto ignores column names and uses position-based matching.
# The schema of the DataFrame must be compatible with the table.
df_new.write.insertInto("sales.transactions")
```

The `insertInto` method is less forgiving than `saveAsTable` because it does not use column names. If the DataFrame columns are in a different order, the values are inserted into the wrong columns. This can produce incorrect data without an error if the types are compatible. Use `insertInto` only when you are certain that the column order matches the table. In most cases, `saveAsTable` with append mode is safer because it matches by name.

### Comparing saveAsTable and insertInto

The following table summarizes the differences.

| Aspect | saveAsTable with append | insertInto |
|---|---|---|
| Creates table if missing | Yes | No |
| Column matching | By name | By position |
| Schema evolution | Supported with option | Not supported |
| Risk of wrong column order | Low | High |
| Typical use | General appends | Append when order is guaranteed |

The table shows that `saveAsTable` is the safer default. Use `insertInto` when you have a specific reason, such as writing to a table with a known schema and a DataFrame that is already in the correct order. In most pipelines, `saveAsTable` with append mode is the better choice.

## Schema enforcement, evolution, and expectations

Delta Lake enforces schema on append. When you append a DataFrame or the result of a query, Delta Lake compares the schema of the new data with the schema of the table. If the new data has extra columns, the append fails by default. If the new data is missing columns, those columns are written as null if they are nullable. If a non-nullable column is missing, the append fails. This behavior protects the table from accidental schema changes and from data that does not fit the table's structure.

Schema evolution allows you to add new columns to the table during an append. In PySpark, you enable it with the `mergeSchema` option. In SQL, you enable it by setting `spark.databricks.delta.schema.autoMerge.enabled` to true, or by using the `WITH SCHEMA EVOLUTION` clause if it is supported in your environment. The following example shows schema evolution in PySpark.

```python
# Read the staging table, which has a new column called channel.
df_staging = spark.read.table("staging.daily_transactions")

# Append the DataFrame with schema evolution enabled.
# mergeSchema=true allows the write to add the new channel column
# to the target table. Existing rows get null in the new column.
# Use schema evolution only when you intend to change the table schema.
# Downstream consumers may break if they do not expect the new column.
df_staging.write.mode("append").option("mergeSchema", "true").saveAsTable("sales.transactions")
```

Schema evolution is powerful but should be used with care. Adding a column changes the table schema. Queries that use `SELECT *` will return the new column. Downstream code that expects a fixed set of columns may break. In a medallion architecture, schema changes are usually managed deliberately. The silver layer may evolve as source systems change, and the gold layer is rebuilt from silver. Use schema evolution when the change is intentional and communicated. Do not use it as a way to avoid fixing schema mismatches.

Expectations are data quality rules that you attach to a pipeline. In Lakeflow pipelines, expectations can drop, fail, or warn on rows that violate a rule. For example, you can add an expectation that `transaction_id` is not null. If a row violates the expectation, the pipeline can drop it before the append. Expectations help you enforce data quality at the point of ingestion. They are not a replacement for schema enforcement, but they complement it. Use expectations to validate business rules, and use schema enforcement to validate structure.

## Handling duplicates and idempotency

`INSERT INTO` does not check for duplicates. If you run the same append twice, the table gets duplicate rows. This is the most common and most damaging mistake when appending. To avoid duplicates, you must either deduplicate the source before appending or use a merge operation instead of an append.

Deduplicating the source is the simplest approach. In SQL, use `SELECT DISTINCT` or a window function to keep only one row per key. In PySpark, use `dropDuplicates`. The following example shows both.

```sql
-- Append only distinct transactions from the staging table.
-- SELECT DISTINCT removes exact duplicate rows from the source.
-- This does not prevent duplicates that already exist in the target table.
-- It only prevents duplicates within the batch being appended.
INSERT INTO sales.transactions (transaction_id, amount, transaction_date)
SELECT DISTINCT
    transaction_id,
    amount,
    transaction_date
FROM staging.daily_transactions;
```

```python
# Read the staging table.
df_staging = spark.read.table("staging.daily_transactions")

# Remove duplicate rows based on transaction_id.
# dropDuplicates keeps the first occurrence of each transaction_id
# and removes the rest. This prevents duplicates within the batch.
# It does not prevent duplicates that already exist in the target table.
df_deduped = df_staging.dropDuplicates(["transaction_id"])

# Append the deduplicated DataFrame.
df_deduped.write.mode("append").saveAsTable("sales.transactions")
```

Deduplicating the source prevents duplicates within the batch. It does not prevent duplicates between the batch and the existing table. If the batch contains a transaction that was already appended in a previous run, the append creates a duplicate. To prevent that, you need an idempotent write. The standard way to make an append idempotent is to use `MERGE` instead of `INSERT INTO`. A merge matches rows on a key and updates existing rows or inserts new ones. If the key already exists, the merge does not insert a duplicate. The following SQL example shows a merge that is idempotent.

```sql
-- Merge the staging data into the target table.
-- The merge matches on transaction_id.
-- If the transaction already exists, it is updated.
-- If it does not exist, it is inserted.
-- Running this merge twice produces the same result as running it once.
MERGE INTO sales.transactions AS target
USING staging.daily_transactions AS source
ON target.transaction_id = source.transaction_id
WHEN MATCHED THEN
    UPDATE SET
        target.amount = source.amount,
        target.transaction_date = source.transaction_date
WHEN NOT MATCHED THEN
    INSERT (transaction_id, amount, transaction_date)
    VALUES (source.transaction_id, source.amount, source.transaction_date);
```

The merge is idempotent because it checks for existence before inserting. If you need exactly-once semantics, use a merge or a `replaceWhere` operation. Append is at-least-once by nature. It will add rows every time it runs. Use append only when the source is guaranteed to be new, or when duplicates are acceptable and can be removed later.

## Null handling, case sensitivity, and time zones

Null handling in appends follows the table's schema. If a column is nullable, you can append null values. If a column is non-nullable, appending a null fails. If you omit a nullable column from the column list, it is written as null. If you omit a non-nullable column, the append fails. This means that adding a non-nullable column to a table requires a default value or a backfill before you can append new rows. Delta Lake does not have a default value constraint in all versions, so plan schema changes carefully.

Case sensitivity affects column names and string values. In Spark SQL, column names are case-insensitive by default. This means `Transaction_ID` and `transaction_id` refer to the same column. String values, however, are case-sensitive. `'TXN001'` and `'txn001'` are different values. If your source data has inconsistent casing in a key column, an append will insert both versions, and downstream joins may not match them. Normalize the case of string keys before appending, or use a case-insensitive collation if the table is configured for one. Unity Catalog can define collations at the column level. Be aware that applying a function such as `upper()` to a column before an append can prevent predicate pushdown on later queries.

Time zones affect appends when you use date or timestamp functions. `current_date()` and `current_timestamp()` return values in the session time zone. If the source data was written in a different time zone, the filter that selects rows to append may include or exclude the wrong rows. To avoid this, set the session time zone explicitly at the start of the job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Use timestamp literals with explicit offsets when comparing to timestamps. Store timestamps in UTC in the table, and convert to local time only for display. This keeps the data consistent across time zones.

## Appending to partitioned tables

A partitioned table stores rows in separate directories based on the values of one or more partition columns. When you append to a partitioned table, Delta Lake writes new files into the appropriate partition directories. If the append includes rows for existing partitions, those partitions get new files. If it includes rows for new partitions, new directories are created. Partitioning can improve query performance because queries that filter on the partition column can skip entire partitions.

The following example appends to a table partitioned by `transaction_date`.

```sql
-- Append transactions to a table partitioned by transaction_date.
-- Delta Lake writes each row into the partition directory that matches
-- its transaction_date value. Existing partitions get new files.
-- New partitions get new directories.
INSERT INTO sales.transactions_partitioned (transaction_id, amount, transaction_date)
SELECT
    transaction_id,
    amount,
    transaction_date
FROM staging.daily_transactions;
```

Partitioning has tradeoffs. A table with too many small partitions creates many small files, which slows down queries and metadata operations. A table with too few partitions may not benefit from partition pruning. Choose partition columns that are commonly used in filters and that have a reasonable number of distinct values. Date columns are common partition keys. High-cardinality columns such as transaction ID are poor partition keys. In Databricks, liquid clustering is an alternative to traditional partitioning. It organizes data by clustering keys and can adapt as data grows. Use liquid clustering when you need flexible clustering without managing partitions manually.

## Best practices

Deduplicate the source before appending. `INSERT INTO` does not check for duplicates. If the same batch is loaded twice, the table gets duplicate rows. Use `SELECT DISTINCT` or `dropDuplicates` to remove duplicates within the batch. For duplicates across batches, use `MERGE` instead of append.

Use an explicit column list in `INSERT INTO`. Without it, the statement depends on the table's column order. With it, the statement is stable and self-documenting.

Prefer `saveAsTable` with append mode over `insertInto`. `saveAsTable` matches columns by name, which is safer than the positional matching of `insertInto`. Use `insertInto` only when you are certain that the column order matches.

Set the session time zone explicitly. `current_date()` and `current_timestamp()` use the session time zone. Set it to UTC at the start of the job to avoid off-by-hours errors.

Use schema evolution deliberately. `mergeSchema` adds new columns to the table. This changes the schema and may break downstream consumers. Use it only when the change is intentional and communicated.

Monitor table size and file count. Appending many small batches creates many small files. Run `OPTIMIZE` periodically to compact small files into larger ones. In Databricks, predictive optimization can do this automatically for Unity Catalog managed tables.

Use Unity Catalog for governance. Unity Catalog controls who can append to a table and records lineage. If an append fails with a permission error, check the grants on the table and the schema.

## Common mistakes and pitfalls

The most common mistake is appending the same batch twice. This creates duplicate rows. `INSERT INTO` does not check for duplicates. Deduplicate the source and use `MERGE` for idempotent writes.

A second mistake is omitting the column list in `INSERT INTO`. Without it, the statement depends on column order. If the table schema changes, the statement may insert values into the wrong columns.

A third mistake is using `insertInto` when the DataFrame column order does not match the table. `insertInto` matches by position, so a mismatch inserts values into the wrong columns. This can produce incorrect data without an error if the types are compatible.

A fourth mistake is assuming that `saveAsTable` with append mode creates the table with the correct schema. If the table does not exist, `saveAsTable` creates it from the DataFrame schema. This may not match the schema you intended. Create the table explicitly before appending, or verify the schema after the first write.

A fifth mistake is using `current_date()` without considering the session time zone. The function returns the date in the session time zone. If the source data is in a different time zone, the filter may select the wrong rows.

A sixth mistake is enabling schema evolution without communicating the change. Adding a column changes the table schema. Downstream queries that use `SELECT *` will see the new column. Code that expects a fixed set of columns may break.

A seventh mistake is appending to a table with a non-nullable column and omitting that column. The append fails. If you need to add a non-nullable column, backfill the existing rows and provide a value for new rows.

## Testing append logic

Append logic should be tested with small datasets that include duplicates, nulls, and boundary values. A test should verify that the append adds the expected rows, that running the append twice does not create duplicates if the logic is designed to be idempotent, and that the schema is compatible. The following example shows a test for a deduplicated append.

```python
# Import the test helpers.
import pytest
from pyspark.sql import Row

# Build a small DataFrame with duplicate rows.
# The data includes two rows with the same transaction_id.
test_data = [
    Row(transaction_id="TXN001", amount=100.0, transaction_date="2026-01-15"),
    Row(transaction_id="TXN001", amount=100.0, transaction_date="2026-01-15"),
    Row(transaction_id="TXN002", amount=200.0, transaction_date="2026-01-15"),
]
df_test = spark.createDataFrame(test_data)

# Deduplicate the DataFrame by transaction_id.
# dropDuplicates keeps the first occurrence of each transaction_id.
df_deduped = df_test.dropDuplicates(["transaction_id"])

# Assert that the deduplicated DataFrame has two rows.
# The duplicate TXN001 is removed, leaving TXN001 and TXN002.
assert df_deduped.count() == 2, f"Dedup count failed: {df_deduped.count()}"

# Collect the transaction IDs to verify which rows remain.
ids = [row.transaction_id for row in df_deduped.collect()]
assert set(ids) == {"TXN001", "TXN002"}, f"IDs failed: {ids}"
```

The test verifies that the deduplication removes the duplicate row and keeps one row per transaction ID. Run tests like this in your CI pipeline against a small local Spark session. For an end-to-end test, create a temporary Delta table, append the DataFrame, and assert the row count. Append the same DataFrame again and assert that the row count doubles if duplicates are allowed, or stays the same if the logic is idempotent.

## Performance considerations

Appending is the cheapest write operation in Delta Lake because it only adds new files. It does not read or rewrite existing data. The cost is proportional to the size of the new data, not the size of the table. This makes append suitable for high-frequency ingestion. However, many small appends create many small files. Small files are inefficient because each file has metadata overhead and because queries must open many files. Run `OPTIMIZE` periodically to compact small files into larger ones. In Databricks, predictive optimization can handle this automatically for Unity Catalog managed tables.

Use partitioning or liquid clustering to organize data for query performance. Partition columns should be commonly used in filters and have a reasonable number of distinct values. Avoid high-cardinality partition columns. Liquid clustering is more flexible and can adapt as data changes.

Control the number of output files by adjusting the number of partitions before the write. If the DataFrame has too many partitions, the append writes many small files. If it has too few, the write may be slow because each task writes a large file. Use `coalesce` to reduce the number of partitions without a full shuffle, or `repartition` to increase parallelism. The right number depends on the data size and the cluster size. A common guideline is to aim for files of 100 MB to 1 GB.

Use `INSERT INTO ... SELECT` to let Spark parallelize the read and the write. The query reads the source in parallel, filters and transforms the data, and writes the result in parallel. This is more efficient than reading the data into the driver and writing it row by row.

Delta Lake stores per-file statistics that help queries skip files. When you append, new files get statistics for the columns. Filters on raw columns can use these statistics. Filters on expressions cannot. If you filter on a transformed value frequently, materialize the transformed value in a column at append time so that statistics are collected for it.
