## Replace data with INSERT OVERWRITE

Replacing data is the operation of removing existing rows from a table or partition and writing new rows in their place. In Azure Databricks, the SQL statement for full or partition-level replacement is `INSERT OVERWRITE`, and the PySpark equivalent is writing a DataFrame with overwrite mode. Replacement differs from appending because it does not preserve the existing rows. It differs from merging because it does not compare source and target rows to decide whether to update or insert. Instead, it removes a defined set of rows and writes new ones. The removal and the write happen as a single atomic transaction in Delta Lake, so readers see either the old data or the new data, never a partial state.

Replacement matters when the source data is a complete replacement for a known slice of the target. Reprocessing a failed batch is the classic example. If a batch of daily transactions was loaded incorrectly, you do not want to append a corrected batch, because that would create duplicates. You want to remove the incorrect rows and write the corrected rows. Refreshing a lookup table is another example. A lookup table that maps product codes to product names may be rebuilt from a source system on a schedule. Replacing the entire table is simpler and safer than trying to merge individual changes. Rebuilding an aggregation is a third example. A daily summary table can be fully overwritten each night because the summary is derived from the transactions and does not need to preserve history at the summary level.

These notes cover replacement from first principles. They explain full-table overwrite, partition-level overwrite, and selective replacement with `REPLACE WHERE`. They explain the recommended `REPLACE USING` clause for dynamic overwrites and the `REPLACE ON` clause for custom matching conditions. They show how to perform each operation in SQL and in PySpark, and they explain the differences between static and dynamic partition overwrite. They also cover schema enforcement, schema evolution, expectations, null handling, case sensitivity, time zones, and how replacement interacts with Delta Lake, Unity Catalog, and the medallion architecture. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand not only how to replace data, but when replacement is the correct choice and how to avoid the mistakes that leave stale or duplicated rows.

## Understanding replacement versus append and merge

Replacement is one of three ways to load data into an existing table. Append adds new rows without changing existing rows. Merge compares source and target rows on a key and updates, inserts, or deletes rows based on the comparison. Replacement removes a set of rows and writes new rows in their place. The three operations have different costs and different risks. Append is the cheapest because it only writes new files. Merge is the most expensive because it must read both source and target and compare rows. Replacement is in between. A full-table overwrite rewrites the entire table, which is expensive for large tables. A partition-level overwrite rewrites only the affected partitions, which is much cheaper. A selective replacement with `REPLACE WHERE` or `REPLACE USING` removes only the rows that match a condition or a set of columns, then inserts the new rows.

The following table compares the three loading operations.

| Operation | What it does | Duplicate risk | Typical use |
|---|---|---|---|
| Append | Adds new rows | High if source is not deduplicated | Incremental logs, event streams |
| Replace | Removes a set of rows and writes new rows | Low if the replaced slice is correct | Reprocessing batches, refreshing lookups, rebuilding aggregations |
| Merge | Updates, inserts, deletes based on a condition | Low when key is unique | Upserts, slowly changing dimensions |

The table shows that replacement is the right choice when the incoming data is a complete replacement for a known slice of the target. If the incoming data contains only new rows, append is correct. If the incoming data contains a mix of updates and inserts that must be reconciled row by row, merge is correct. Replacement is simpler than merge because it does not need a row-by-row comparison. It removes and writes. The simplicity is an advantage when the slice is well defined, and a disadvantage when the slice is not. If you replace the wrong slice, you lose data that should have been kept.

## Full-table overwrite with INSERT OVERWRITE

A full-table overwrite removes every row from the target table and writes the result of the query in its place. In SQL, you write `INSERT OVERWRITE` followed by the table name and a `SELECT` statement. The table must already exist. The `SELECT` produces the new contents of the table. In PySpark, you write a DataFrame with `mode("overwrite")` and `saveAsTable`. The overwrite mode replaces the table contents.

The following SQL example replaces the entire contents of a daily summary table.

```sql
-- Replace the entire contents of the daily summary table.
-- INSERT OVERWRITE removes all existing rows before inserting the new rows.
-- The table must already exist. The statement does not create the table.
INSERT OVERWRITE sales.daily_summary
-- Select the new contents of the table.
-- The query aggregates transactions by region for the current date.
SELECT
    region,
    -- Sum the transaction amounts, ignoring nulls.
    SUM(amount) AS total_sales,
    -- Count all transactions in each region.
    COUNT(*) AS transaction_count
FROM sales.transactions
-- Filter to only today's transactions.
-- current_date() returns the current date in the session time zone.
WHERE transaction_date = current_date()
-- Group the transactions by region.
GROUP BY region;
```

The statement removes every row in `sales.daily_summary` and inserts one row per region for the current date. The operation is atomic in Delta Lake. If the query fails, the table is left unchanged. If the query succeeds, the new rows replace the old rows. The table schema is preserved. If the query produces columns that do not match the table schema, the statement fails unless schema evolution is enabled.

The equivalent PySpark operation writes a DataFrame with overwrite mode.

```python
# Import the functions needed for the aggregation.
# col() references a column by name.
# sum() and count() are aggregate functions.
from pyspark.sql.functions import col, sum, count, current_date

# Read the transactions table from Unity Catalog.
df_transactions = spark.read.table("sales.transactions")

# Filter to today's transactions and aggregate by region.
# current_date() returns the current date in the session time zone.
df_summary = (
    df_transactions
    .filter(col("transaction_date") == current_date())
    .groupBy("region")
    .agg(
        # Sum the transaction amounts, ignoring nulls.
        sum("amount").alias("total_sales"),
        # Count all transactions in each region.
        count("*").alias("transaction_count")
    )
)

# Overwrite the daily summary table with the new aggregation.
# mode("overwrite") removes all existing rows and writes the new rows.
# saveAsTable matches columns by name when the table already exists.
# If the DataFrame schema differs from the table schema, the write fails
# unless schema evolution is enabled with mergeSchema or overwriteSchema.
df_summary.write.mode("overwrite").saveAsTable("sales.daily_summary")
```

The PySpark example produces the same result as the SQL example. The `mode("overwrite")` replaces the table contents. The `saveAsTable` method matches columns by name. If the DataFrame has extra columns, the write fails unless schema evolution is enabled. If the table has columns that the DataFrame does not have, those columns are written as null if they are nullable. If they are non-nullable, the write fails.

## Partition-level overwrite

A partitioned table stores rows in separate directories based on the values of one or more partition columns. A partition-level overwrite removes only the rows in a specified partition or set of partitions and writes new rows in their place. The other partitions are left untouched. This is much cheaper than a full-table overwrite when the table is large and only a few partitions need to be refreshed. In SQL, you write `INSERT OVERWRITE` with a `PARTITION` clause. In PySpark, you write the DataFrame with `partitionBy` and overwrite mode.

The following SQL example overwrites only the January 2026 partition of a monthly report table.

```sql
-- Replace only the January 2026 partition of the monthly report table.
-- INSERT OVERWRITE with PARTITION removes only the rows in the specified
-- partition and inserts the new rows. Other partitions are left untouched.
INSERT OVERWRITE sales.monthly_report
-- The PARTITION clause names the partition column and value.
-- Only rows in the partition where report_month equals '2026-01' are replaced.
PARTITION (report_month = '2026-01')
-- Select the new contents of the partition.
SELECT
    region,
    product_category,
    -- Sum the amounts for each region and category.
    SUM(amount) AS revenue
FROM sales.transactions
-- Filter to transactions in January 2026.
-- The BETWEEN operator includes both endpoints.
WHERE transaction_date BETWEEN '2026-01-01' AND '2026-01-31'
-- Group by region and product category.
GROUP BY region, product_category;
```

The statement removes the rows in the `report_month = '2026-01'` partition and inserts the new rows. Other partitions are not modified. The query filters the source data to January 2026 and aggregates it. The result is written into the January partition. If the query produces rows for a different month, those rows are still written into the January partition because the partition value is specified in the `PARTITION` clause. This is a static partition overwrite. It always writes to the specified partition, regardless of the values in the data.

The PySpark equivalent uses `partitionBy` and overwrite mode.

```python
# Read the transactions table.
df_transactions = spark.read.table("sales.transactions")

# Filter to January 2026 transactions and aggregate.
df_january = (
    df_transactions
    .filter(
        (col("transaction_date") >= "2026-01-01") &
        (col("transaction_date") <= "2026-01-31")
    )
    .groupBy("region", "product_category")
    .agg(sum("amount").alias("revenue"))
)

# Add the partition column with a constant value.
# The partition column report_month is set to '2026-01' for every row.
# This ensures that the rows are written into the correct partition.
df_january = df_january.withColumn("report_month", lit("2026-01"))

# Overwrite the January partition.
# partitionBy("report_month") tells Spark to organize the output by report_month.
# mode("overwrite") replaces the existing data in the partitions that are written.
# By default, Spark uses static partition overwrite mode, which replaces only
# the partitions that are present in the DataFrame. Other partitions are kept.
df_january.write.mode("overwrite").partitionBy("report_month").saveAsTable("sales.monthly_report")
```

The PySpark example adds a constant partition column and writes with `partitionBy`. The `mode("overwrite")` replaces the partition that is written. By default, Spark uses static partition overwrite mode for DataFrame writes. This means it replaces only the partitions that are present in the DataFrame. Other partitions are kept. This is different from the SQL `INSERT OVERWRITE PARTITION` behavior, which always writes to the specified partition.

Dynamic partition overwrite is an alternative mode in which Spark replaces only the partitions that are present in the incoming data, regardless of which partitions are specified. This is useful when the incoming data touches multiple partitions and you want to replace each of them. In PySpark, you enable it with `partitionOverwriteMode=dynamic` in the Spark session configuration. The following example shows dynamic partition overwrite.

```python
# Enable dynamic partition overwrite mode.
# In this mode, Spark replaces only the partitions that are present
# in the incoming data. Partitions not present in the data are left untouched.
# This is different from static mode, which replaces only the specified partitions.
spark.conf.set("spark.sql.sources.partitionOverwriteMode", "dynamic")

# Read the corrected transactions for multiple months.
df_corrected = spark.read.table("staging.corrected_transactions")

# Write the corrected data with dynamic partition overwrite.
# Spark replaces the partitions that appear in df_corrected.
# For example, if the data contains January and February,
# both partitions are replaced. March is left untouched.
df_corrected.write.mode("overwrite").partitionBy("report_month").saveAsTable("sales.monthly_report")
```

Dynamic partition overwrite is convenient, but it has a restriction in SQL. The SQL `INSERT OVERWRITE PARTITION` syntax combined with `partitionOverwriteMode=dynamic` is restricted to classic compute only. It does not work on Databricks SQL warehouses or serverless compute. Python and Scala DataFrame writes using `partitionOverwriteMode=dynamic` work on all compute types. For new pipelines, Databricks recommends `REPLACE USING` over partition overwrite because partition overwrite can use stale data when partitioning changes.

The following table compares static and dynamic partition overwrite.

| Mode | What it replaces | Compute support | Risk |
|---|---|---|---|
| Static | Only the specified partitions | SQL and DataFrame on all compute | Low, because the target partitions are explicit |
| Dynamic | Only the partitions present in the incoming data | DataFrame on all compute; SQL only on classic compute | Higher, because stale data can remain if partitioning changes |

The table shows that static overwrite is more predictable. You specify exactly which partition to replace. Dynamic overwrite is more convenient when the incoming data spans multiple partitions, but it requires care. If the partitioning scheme changes, dynamic overwrite may leave stale data in partitions that are no longer written. `REPLACE USING` avoids this problem by matching on the columns you specify, regardless of the table's partitioning.

## Selective replacement with REPLACE WHERE

`REPLACE WHERE` is a clause that deletes rows matching a condition before inserting new rows. It is more flexible than a full-table overwrite because it replaces only the rows that satisfy the condition. It is simpler than a merge because it does not require a source table reference or a key comparison. You use `INSERT INTO` with a `REPLACE WHERE` clause followed by a `SELECT` statement. The condition can reference any column in the target table. The rows that match the condition are deleted, and the rows from the `SELECT` are inserted.

The following SQL example replaces transactions for a specific date range.

```sql
-- Replace transactions for a specific date range.
-- INSERT INTO with REPLACE WHERE deletes rows in the target table
-- that match the condition, then inserts the rows from the SELECT.
-- The table must already exist. The statement does not create it.
INSERT INTO sales.transactions
-- The REPLACE WHERE clause specifies the condition for deletion.
-- Rows where transaction_date is between January 1 and January 7, 2026
-- are deleted before the new rows are inserted.
REPLACE WHERE transaction_date BETWEEN '2026-01-01' AND '2026-01-07'
-- Select the corrected transactions to insert.
-- The SELECT must produce columns that are compatible with the target table.
SELECT * FROM staging.corrected_transactions;
```

The statement deletes all rows in `sales.transactions` where the transaction date falls in the first week of January 2026, then inserts all rows from the staging table. The staging table should contain only the corrected transactions for that date range. If the staging table contains transactions outside the range, those rows are still inserted, because the `REPLACE WHERE` condition applies to the target table, not to the source. This is a common point of confusion. The condition determines which rows are deleted from the target. It does not filter the source. You must ensure that the source contains only the rows that should be inserted.

PySpark does not have a direct equivalent to `REPLACE WHERE` in the DataFrame API. You can achieve the same result with a Delta table merge or with a combination of delete and append operations. The following example shows a delete-and-append approach.

```python
# Import the DeltaTable class for delete operations.
from delta.tables import DeltaTable
from pyspark.sql.functions import col

# Read the corrected transactions from the staging table.
df_corrected = spark.read.table("staging.corrected_transactions")

# Load the target Delta table.
delta_table = DeltaTable.forName(spark, "sales.transactions")

# Delete the rows that match the replacement condition.
# The condition deletes transactions in the first week of January 2026.
delta_table.delete("transaction_date BETWEEN '2026-01-01' AND '2026-01-07'")

# Append the corrected transactions.
# The append inserts the new rows after the delete.
# This is not atomic in the same way as REPLACE WHERE,
# because the delete and append are separate transactions.
df_corrected.write.mode("append").saveAsTable("sales.transactions")
```

The PySpark approach uses two separate operations: a delete and an append. These are not atomic together. A reader could see the table after the delete but before the append, which would show missing rows. In SQL, `REPLACE WHERE` is atomic. The delete and insert happen in a single transaction. For production pipelines where atomicity matters, use the SQL `REPLACE WHERE` clause or a merge operation. The PySpark delete-and-append approach is suitable for development or for pipelines where a brief inconsistency is acceptable.

## Dynamic replacement with REPLACE USING

`REPLACE USING` is the recommended approach for dynamic data overwrites in Databricks. It works across all compute types, including Databricks SQL warehouses and serverless compute, and it does not require Spark session configuration. Unlike partition overwrite, `REPLACE USING` supports partitioned tables, unpartitioned tables, and tables with liquid clustering. The clause atomically deletes rows in the target table that match incoming rows on the specified columns, then inserts the new rows. Rows that do not match the specified columns are left untouched.

The following SQL example replaces only the partitions touched by the incoming data.

```sql
-- Replace only the partitions touched by the incoming data.
-- INSERT INTO with REPLACE USING deletes rows in the target table
-- that match the incoming rows on the report_month column,
-- then inserts the new rows.
INSERT INTO sales.monthly_report
  -- The REPLACE USING clause names the columns used for matching.
  -- Rows in the target with the same report_month as incoming rows
  -- are deleted before the new rows are inserted.
  REPLACE USING (report_month)
-- Select the corrected data to insert.
-- The query aggregates transactions by region, category, and month.
SELECT
    region,
    product_category,
    SUM(amount) AS revenue,
    report_month
FROM staging.corrected_transactions
GROUP BY region, product_category, report_month;
```

The statement deletes rows in `sales.monthly_report` that have the same `report_month` as the incoming rows, then inserts the new rows. If the incoming data contains January and February, both months are replaced. March is left untouched. The operation is atomic. The matching is on the columns listed in the `REPLACE USING` clause. In Databricks Runtime 16.3 through 17.1, the `USING` columns must be the table's full set of partition columns. This is legacy behavior. In Databricks Runtime 17.2 and above, any columns on any table type, including unpartitioned tables and tables with liquid clustering, are supported.

The following table compares `REPLACE USING` with partition overwrite.

| Aspect | Partition overwrite | REPLACE USING |
|---|---|---|
| Compute support | SQL dynamic mode restricted to classic compute; DataFrame works on all | Works on all compute types |
| Session configuration | Requires `partitionOverwriteMode` for dynamic | None |
| Table types | Partitioned tables | Partitioned, unpartitioned, liquid clustering |
| Matching | On partition columns | On specified columns |
| Stale data risk | Higher when partitioning changes | Lower because matching is explicit |

The table shows that `REPLACE USING` is more flexible and more predictable than partition overwrite. It is the recommended approach for new pipelines because it works everywhere and does not depend on the table's partitioning scheme. Use `REPLACE USING` when you need to replace a slice of data that is defined by the values of one or more columns.

## Flexible matching with REPLACE ON

`REPLACE ON` is a clause that replaces rows based on a user-defined condition across the source and target. It is more flexible than `REPLACE USING` because the condition can be any expression, not just equality on a set of columns. It also treats null values as equal, which is useful when the matching columns can contain nulls. `REPLACE ON` requires Databricks Runtime 17.1 and above. You use `INSERT INTO` with a `REPLACE ON` clause followed by a `SELECT` statement that references the source.

The following SQL example replaces rows matching a custom condition.

```sql
-- Replace rows matching a user-defined condition across source and target.
-- INSERT INTO with REPLACE ON deletes rows in the target table
-- that match the condition, then inserts the rows from the source.
INSERT INTO sales.transactions
  -- The REPLACE ON clause specifies the matching condition.
  -- target refers to the existing table, source refers to the SELECT.
  -- Rows where the transaction IDs match are replaced.
  REPLACE ON (target.transaction_id = source.transaction_id)
-- Select the corrected transactions from the staging table.
-- The alias source is used in the REPLACE ON condition.
SELECT * FROM staging.corrected_transactions AS source;
```

The statement deletes rows in `sales.transactions` where the transaction ID matches a transaction ID in the staging table, then inserts the staging rows. The condition can be more complex than equality. You can use any expression that evaluates to true or false, such as a range comparison or a combination of columns. `REPLACE ON` treats null values as equal, so if the matching column is null in both the target and the source, the rows are considered matching. This is different from a join, where nulls do not match. Use `REPLACE ON` when you need custom matching logic or when the matching columns can contain nulls.

## Schema enforcement, evolution, and expectations

Delta Lake enforces schema on replacement. When you replace data, Delta Lake compares the schema of the new data with the schema of the table. If the new data has extra columns, the operation fails by default. If the new data is missing columns, those columns are written as null if they are nullable. If a non-nullable column is missing, the operation fails. This behavior protects the table from accidental schema changes. To allow a replacement to change the schema, you must enable schema evolution. In PySpark, you use the `overwriteSchema` option or the `mergeSchema` option. `overwriteSchema` replaces the table schema with the DataFrame schema. `mergeSchema` adds new columns to the table schema. In SQL, you use the `WITH SCHEMA EVOLUTION` clause if it is supported in your environment.

The following PySpark example shows an overwrite that changes the schema.

```python
# Read the new data, which has an additional column called channel.
df_new = spark.read.table("staging.daily_summary_with_channel")

# Overwrite the table with schema evolution enabled.
# overwriteSchema=true replaces the table schema with the DataFrame schema.
# This is more drastic than mergeSchema, which only adds new columns.
# Use overwriteSchema only when you intend to replace the schema entirely.
# Downstream consumers may break if the schema changes.
df_new.write.mode("overwrite").option("overwriteSchema", "true").saveAsTable("sales.daily_summary")
```

Schema evolution is powerful but should be used with care. Replacing the schema changes the table structure. Queries that use `SELECT *` will return the new columns. Code that expects a fixed set of columns may break. In a medallion architecture, schema changes are usually managed deliberately. The silver layer may evolve as source systems change, and the gold layer is rebuilt from silver. Use schema evolution when the change is intentional and communicated. Do not use it as a way to avoid fixing schema mismatches.

Expectations are data quality rules that you attach to a pipeline. In Lakeflow pipelines, expectations can drop, fail, or warn on rows that violate a rule. For example, you can add an expectation that `transaction_id` is not null. If a row violates the expectation, the pipeline can drop it before the replacement. Expectations help you enforce data quality at the point of ingestion. They are not a replacement for schema enforcement, but they complement it. Use expectations to validate business rules, and use schema enforcement to validate structure.

## Null handling, case sensitivity, and time zones

Null handling in replacement follows the table's schema. If a column is nullable, you can replace rows with null values. If a column is non-nullable, replacing a row with a null fails. If you omit a nullable column from the replacement data, it is written as null. If you omit a non-nullable column, the replacement fails. This means that adding a non-nullable column to a table requires a default value or a backfill before you can replace data. Delta Lake does not have a default value constraint in all versions, so plan schema changes carefully.

Nulls in partition columns require attention. If a partition column contains nulls, the rows are written into a special partition for null values. When you overwrite a partition, you must specify the null partition correctly. In SQL, you use `PARTITION (column = NULL)` or a similar syntax depending on the environment. In PySpark, the null partition is written automatically when the partition column contains nulls. Be aware that null partition values can be surprising in queries, because `IS NULL` must be used instead of `= NULL`.

Case sensitivity affects column names and string values. In Spark SQL, column names are case-insensitive by default. This means `Transaction_ID` and `transaction_id` refer to the same column. String values, however, are case-sensitive. `'TXN001'` and `'txn001'` are different values. If your source data has inconsistent casing in a key column, a replacement may not match the rows you expect. Normalize the case of string keys before replacement, or use a case-insensitive collation if the table is configured for one. Unity Catalog can define collations at the column level. Be aware that applying a function such as `upper()` to a column before a replacement can prevent predicate pushdown on later queries.

Time zones affect replacements when you use date or timestamp functions. `current_date()` and `current_timestamp()` return values in the session time zone. If the source data was written in a different time zone, the filter that selects rows to replace may include or exclude the wrong rows. To avoid this, set the session time zone explicitly at the start of the job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Use timestamp literals with explicit offsets when comparing to timestamps. Store timestamps in UTC in the table, and convert to local time only for display. This keeps the data consistent across time zones.

## Replacement in the medallion architecture

In a medallion architecture, replacement is used differently in each layer. The bronze layer holds raw data as it arrived. Bronze tables are often append-only, because the raw history is valuable for auditing and reprocessing. The silver layer holds cleaned, conformed data. Silver tables may use replacement to reprocess failed batches or to refresh a partition when the source data is corrected. The gold layer holds aggregated, denormalized data. Gold tables are often fully overwritten on each refresh because they are derived from silver and do not need to preserve history at the gold level.

A common pattern is to replace a partition in the silver layer and then rebuild the affected partitions in the gold layer. For example, if January transactions are corrected, you replace the January partition in the silver transactions table, then overwrite the January partition in the gold monthly summary table. This keeps the gold table consistent with the corrected silver data. The replacement in silver should be atomic, so that readers never see a partially corrected partition. The `REPLACE USING` clause is well suited to this pattern because it works on all compute types and matches on the columns you specify.

Delta Lake and Unity Catalog support this pattern. Delta Lake provides atomic transactions, so the replacement is safe. Unity Catalog governs access to the tables. If you have permission to modify the table, the replacement succeeds. If you do not, it fails with a permission error. Unity Catalog also records lineage, so you can trace a gold table back to the silver tables and the replacement jobs that produced it.

## Best practices

Use `REPLACE USING` for new pipelines. It works on all compute types, does not require session configuration, and supports partitioned tables, unpartitioned tables, and tables with liquid clustering. It is more predictable than partition overwrite because the matching is on explicit columns.

Use `REPLACE WHERE` when you need condition-based replacement without a source table reference. It is atomic and simple. Ensure that the source data contains only the rows that should be inserted, because the condition applies to the target, not the source.

Use `REPLACE ON` when you need custom matching logic or when the matching columns can contain nulls. It requires Databricks Runtime 17.1 and above.

Prefer partition-level replacement over full-table replacement when the table is large and only a few partitions need to be refreshed. Partition-level replacement is much cheaper because it rewrites only the affected partitions.

Avoid dynamic partition overwrite in SQL on serverless compute. The SQL `INSERT OVERWRITE PARTITION` syntax with `partitionOverwriteMode=dynamic` is restricted to classic compute. Use `REPLACE USING` instead, because it works everywhere.

Set the session time zone explicitly. `current_date()` and `current_timestamp()` use the session time zone. Set it to UTC at the start of the job to avoid off-by-hours errors.

Use schema evolution deliberately. Replacing the schema changes the table structure and may break downstream consumers. Use `mergeSchema` to add columns and `overwriteSchema` only when you intend to replace the schema entirely.

Test replacement logic with small datasets that include nulls, duplicates, and boundary values. Verify that the replaced rows are the ones you expect and that other rows are untouched.

## Common mistakes and pitfalls

The most common mistake is replacing the wrong slice of data. If the condition or the matching columns are wrong, you delete rows that should have been kept and insert rows that do not belong. Always verify the condition with a `SELECT` before running the replacement. Run the `SELECT` with the same condition to see which rows will be deleted, and verify that the source data contains only the rows that should be inserted.

A second mistake is assuming that `REPLACE WHERE` filters the source. It does not. The condition applies to the target table. The source data is inserted as-is. If the source contains rows outside the intended range, those rows are inserted. Filter the source explicitly if needed.

A third mistake is using dynamic partition overwrite and leaving stale data. If the partitioning scheme changes, dynamic overwrite may not replace partitions that are no longer written. Use `REPLACE USING` to match on explicit columns instead of relying on partitioning.

A fourth mistake is enabling schema evolution without communicating the change. Adding or replacing columns changes the table schema. Downstream queries that use `SELECT *` will see the new columns. Code that expects a fixed set of columns may break.

A fifth mistake is forgetting that nulls in matching columns behave differently in different clauses. `REPLACE USING` uses equality on the specified columns. Nulls do not match unless the clause is designed to treat them as equal. `REPLACE ON` treats nulls as equal. Choose the clause that matches your null handling requirements.

A sixth mistake is running a full-table overwrite when a partition-level replacement would suffice. A full-table overwrite rewrites the entire table, which is expensive and unnecessary if only one partition changed. Use partition-level replacement or `REPLACE USING` to limit the scope.

A seventh mistake is not considering atomicity. The PySpark delete-and-append approach is not atomic. A reader could see the table after the delete but before the append. Use SQL `REPLACE WHERE`, `REPLACE USING`, or `REPLACE ON` for atomic replacements, or use a merge operation.

## Testing replacement logic

Replacement logic should be tested with small datasets that include the rows to be replaced, rows to be kept, nulls, and boundary values. A test should verify that the replacement removes the correct rows and inserts the new rows, and that rows outside the replacement scope are untouched. The following example shows a test for a `REPLACE USING` operation.

```python
# Import the test helpers and functions.
import pytest
from pyspark.sql import Row
from pyspark.sql.functions import col, sum

# Build a target table with two months of data.
target_data = [
    Row(report_month="2026-01", region="East", revenue=100),
    Row(report_month="2026-02", region="East", revenue=200),
]
df_target = spark.createDataFrame(target_data)

# Build a source DataFrame with corrected January data.
source_data = [
    Row(report_month="2026-01", region="East", revenue=150),
]
df_source = spark.createDataFrame(source_data)

# Write the target data to a temporary Delta table.
df_target.write.mode("overwrite").saveAsTable("tmp.monthly_report")

# Run the replacement using SQL.
# REPLACE USING (report_month) deletes rows in the target with the same

df_source.createOrReplaceTempView("source_data")
```

## Performance considerations

Replacement performance depends on the scope of the replacement. A full-table overwrite rewrites the entire table. If the table is large, this is expensive. A partition-level replacement rewrites only the affected partitions. This is much cheaper. A selective replacement with `REPLACE WHERE`, `REPLACE USING`, or `REPLACE ON` removes only the rows that match the condition or columns, then inserts the new rows. The cost is proportional to the size of the replaced slice, not the size of the entire table.

Use partition-level replacement or `REPLACE USING` when you need to refresh a subset of the data. Avoid full-table overwrites unless the entire table is being rebuilt. If the table is partitioned by date, replacing a single date partition is fast because only that partition is rewritten. If the table is not partitioned, a selective replacement still scans the table to find the matching rows, but it does not rewrite the unaffected rows.

Control the number of output files. A replacement writes new files for the replaced data. If the DataFrame has too many partitions, the replacement writes many small files. Small files are inefficient because each file has metadata overhead and queries must open many files. Use `coalesce` to reduce the number of partitions before the write, or `repartition` to increase parallelism. Aim for files of 100 MB to 1 GB. Run `OPTIMIZE` periodically to compact small files into larger ones. In Databricks, predictive optimization can do this automatically for Unity Catalog managed tables.

Use Delta Lake statistics to skip files. When you replace data, Delta Lake writes new files with statistics for the columns. Filters on raw columns can use these statistics to skip files during later queries. Filters on expressions cannot. If you filter on a transformed value frequently, materialize the transformed value in a column at replacement time so that statistics are collected for it.

Be aware of the cost of schema evolution. Replacing the schema requires rewriting the table metadata and possibly the data files. Use `mergeSchema` to add columns when possible, because it is less disruptive than `overwriteSchema`. Use `overwriteSchema` only when you intend to replace the schema entirely.

## Summary

Replacing data removes existing rows from a table or partition and writes new rows in their place. In Azure Databricks, you replace data with SQL `INSERT OVERWRITE`, `REPLACE WHERE`, `REPLACE USING`, or `REPLACE ON`, and with PySpark overwrite mode. Replacement is the right choice when the incoming data is a complete replacement for a known slice of the target. It is different from append, which adds rows without removing existing ones, and from merge, which compares source and target rows to decide whether to update or insert.

A full-table overwrite removes every row from the target table and writes the new contents. A partition-level overwrite removes only the specified partitions. Static partition overwrite replaces the partitions you specify. Dynamic partition overwrite replaces the partitions present in the incoming data. The SQL `INSERT OVERWRITE PARTITION` syntax with `partitionOverwriteMode=dynamic` is restricted to classic compute. Python and Scala DataFrame writes with dynamic mode work on all compute types. `REPLACE USING` is the recommended approach for dynamic overwrites because it works on all compute types and supports partitioned tables, unpartitioned tables, and tables with liquid clustering.

`REPLACE WHERE` deletes rows matching a condition and inserts new rows. It is atomic in SQL. `REPLACE USING` deletes rows matching incoming rows on specified columns and inserts the new rows. It requires Databricks Runtime 17.2 and above for non-partition columns and unpartitioned tables. `REPLACE ON` replaces rows based on a custom condition and treats nulls as equal. It requires Databricks Runtime 17.1 and above.

Schema enforcement applies to replacements. Delta Lake compares the schema of the new data with the table schema. Extra columns cause a failure unless schema evolution is enabled. Missing nullable columns are written as null. Missing non-nullable columns cause a failure. Schema evolution should be used deliberately because it changes the table structure and may break downstream consumers.

Null handling, case sensitivity, and time zones affect replacements. Nulls in partition columns require special handling. String comparisons are case-sensitive by default. Time zone functions such as `current_date()` use the session time zone. Set the session time zone explicitly to avoid errors.

Best practices include using `REPLACE USING` for new pipelines, preferring partition-level replacement over full-table replacement, setting the session time zone, using schema evolution deliberately, and testing replacement logic with small datasets that include nulls and boundary values. Common mistakes include replacing the wrong slice, assuming `REPLACE WHERE` filters the source, using dynamic partition overwrite and leaving stale data, and enabling schema evolution without communication. Performance depends on the scope of the replacement. Partition-level and selective replacements are cheaper than full-table overwrites. Control file count, use Delta statistics, and run `OPTIMIZE` to keep the table efficient. Used well, replacement is a simple, atomic, and reliable way to refresh data in a Delta table.
