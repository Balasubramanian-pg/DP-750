## Choose temporal types correctly

Temporal data type selection depends on whether you need timezone awareness and what level of precision your application requires. Temporal data represents dates, times, timestamps, and durations. It is used for event times, transaction dates, hire dates, birth dates, scheduling, auditing, and any other value that represents a point in time or a calendar date. Choosing the right temporal type is critical for correctness, performance, and usability. A poorly chosen type can lead to incorrect calculations, confusing query results, and data quality issues. A well-chosen type ensures that your data behaves as expected across time zones and that your queries return the correct results.

Azure Databricks provides three temporal types: DATE, TIMESTAMP, and TIMESTAMP_NTZ. Each has a different purpose and behavior. DATE stores calendar dates without time components. TIMESTAMP stores date and time with timezone awareness. TIMESTAMP_NTZ stores date and time without timezone conversion. Understanding the differences between these types is essential for designing effective schemas and writing correct queries. This section explains each type in detail, provides commented code examples in SQL and PySpark, and offers guidance on when to use each type.

## Why temporal type selection matters

Temporal type selection matters for several reasons. First, it affects correctness. If you use the wrong type, your calculations may be off by hours or days. For example, if you store an event time as TIMESTAMP and query it from a different time zone, the displayed value may be different from what you expect. If you store a local meeting time as TIMESTAMP, it may be converted to UTC and then displayed in the session time zone, which may not be the local time. If you use DATE for a timestamp, you lose the time component and cannot perform time-based analysis.

Second, it affects performance. Temporal types have different storage sizes. DATE uses 4 bytes. TIMESTAMP and TIMESTAMP_NTZ use 8 bytes. Smaller types consume less storage and can improve query performance. Partitioning by date is a common technique for improving performance. Using the right type makes partitioning and filtering more efficient.

Third, it affects usability. Temporal functions and operations depend on the type. DATE supports date arithmetic such as adding days, months, and years. TIMESTAMP supports time arithmetic such as adding hours, minutes, and seconds. TIMESTAMP_NTZ supports similar arithmetic but without timezone conversion. Using the right type makes your queries simpler and more intuitive.

Fourth, it affects interoperability. When you exchange data with other systems, the temporal types must be compatible. Some systems use timezone-aware timestamps. Some use timezone-naive timestamps. Some use dates. Understanding the differences helps you map types correctly during ingestion and export.

## DATE type

DATE represents a calendar date without a time component. It stores year, month, and day. It does not store hours, minutes, seconds, or time zone. DATE is used for birthdays, hire dates, transaction dates, and any other value that is a date without a time. The range of DATE is from 0001-01-01 to 9999-12-31. It uses 4 bytes of storage.

The following SQL example creates a table named employees with DATE columns. Each line is commented.

```sql
-- Create a table named employees.
-- The employee_id column uses INT, which is suitable for identifiers.
-- The hire_date column uses DATE.
-- It stores only the date, not the time.
-- The birth_date column uses DATE.
-- It stores only the date, not the time.
CREATE TABLE employees (
    employee_id INT,
    hire_date DATE,
    birth_date DATE
);
```

The following PySpark example creates a DataFrame with the same schema and writes it to a table. Each line is commented.

```python
# Import the required types.
from pyspark.sql.types import StructType, StructField, IntegerType, DateType
from datetime import date

# Define the schema.
# IntegerType corresponds to INT.
# DateType corresponds to DATE.
schema = StructType([
    StructField("employee_id", IntegerType(), True),
    StructField("hire_date", DateType(), True),
    StructField("birth_date", DateType(), True)
])

# Create a DataFrame with sample data.
data = [(1, date(2020, 1, 15), date(1985, 5, 20)),
        (2, date(2021, 3, 10), date(1990, 8, 12))]

# Create the DataFrame.
df = spark.createDataFrame(data, schema)

# Write the DataFrame to a table.
df.write.saveAsTable("employees")
```

When you query a DATE column, it is displayed as a date in the format YYYY-MM-DD. You can use date functions such as current_date(), date_add, date_sub, datediff, year, month, day, and date_trunc. The following SQL example shows how to use some of these functions. Each line is commented.

```sql
-- Select the hire date and compute the number of years since hire.
SELECT
    employee_id,
    hire_date,
    -- current_date() returns today's date.
    current_date() AS today,
    -- datediff computes the difference in days between two dates.
    datediff(current_date(), hire_date) AS days_since_hire,
    -- year extracts the year from a date.
    year(hire_date) AS hire_year,
    -- month extracts the month from a date.
    month(hire_date) AS hire_month,
    -- day extracts the day from a date.
    day(hire_date) AS hire_day
FROM employees;
```

The following PySpark example shows the same operations using the DataFrame API. Each line is commented.

```python
from pyspark.sql.functions import current_date, datediff, year, month, day

# Read the employees table.
df = spark.read.table("employees")

# Select columns and compute date functions.
df_result = df.select(
    "employee_id",
    "hire_date",
    current_date().alias("today"),
    datediff(current_date(), df.hire_date).alias("days_since_hire"),
    year(df.hire_date).alias("hire_year"),
    month(df.hire_date).alias("hire_month"),
    day(df.hire_date).alias("hire_day")
)

# Show the results.
df_result.show()
```

## TIMESTAMP type

TIMESTAMP represents a date and time with a session time zone. It stores year, month, day, hour, minute, second, and fractional seconds. It also stores the time zone information. The time zone is the session time zone, which is typically UTC in Databricks. When you write a TIMESTAMP value, it is converted from the session time zone to UTC for storage. When you query a TIMESTAMP column, the value is converted from UTC to the session time zone for display. This behavior ensures consistent ordering across time zones but can cause confusion if you expect values to remain unchanged.

TIMESTAMP is used for event times, log times, audit times, and any value that includes both date and time and that must be consistent across time zones. The following SQL example creates a table named audit_log with a TIMESTAMP column. Each line is commented.

```sql
-- Create a table named audit_log.
-- The log_id column uses BIGINT, which is suitable for large identifiers.
-- The event_time column uses TIMESTAMP.
-- It stores both date and time, with time zone conversion.
-- The user_id column uses INT.
CREATE TABLE audit_log (
    log_id BIGINT,
    event_time TIMESTAMP,
    user_id INT
);
```

The following PySpark example creates a DataFrame with a TIMESTAMP column. Each line is commented.

```python
from pyspark.sql.types import StructType, StructField, LongType, TimestampType, IntegerType
from datetime import datetime

# Define the schema.
# LongType corresponds to BIGINT.
# TimestampType corresponds to TIMESTAMP.
# IntegerType corresponds to INT.
schema = StructType([
    StructField("log_id", LongType(), True),
    StructField("event_time", TimestampType(), True),
    StructField("user_id", IntegerType(), True)
])

# Create a DataFrame with sample data.
data = [(1001, datetime(2026, 1, 15, 10, 30, 0), 1),
        (1002, datetime(2026, 1, 15, 11, 45, 0), 2)]

# Create the DataFrame.
df = spark.createDataFrame(data, schema)

# Write the DataFrame to a table.
df.write.saveAsTable("audit_log")
```

When you query a TIMESTAMP column, it is displayed in the session time zone. You can use timestamp functions such as current_timestamp(), date_add, date_sub, datediff, date_trunc, extract, hour, minute, second, and to_timestamp. The following SQL example shows how to use some of these functions. Each line is commented.

```sql
-- Select the event time and compute the hour, minute, and second.
SELECT
    log_id,
    event_time,
    -- hour extracts the hour from a timestamp.
    hour(event_time) AS event_hour,
    -- minute extracts the minute from a timestamp.
    minute(event_time) AS event_minute,
    -- second extracts the second from a timestamp.
    second(event_time) AS event_second,
    -- date_trunc truncates the timestamp to the specified unit.
    -- In this example, it truncates to the hour.
    date_trunc('HOUR', event_time) AS event_hour_truncated
FROM audit_log;
```

The following PySpark example shows the same operations using the DataFrame API. Each line is commented.

```python
from pyspark.sql.functions import hour, minute, second, date_trunc

# Read the audit_log table.
df = spark.read.table("audit_log")

# Select columns and compute timestamp functions.
df_result = df.select(
    "log_id",
    "event_time",
    hour(df.event_time).alias("event_hour"),
    minute(df.event_time).alias("event_minute"),
    second(df.event_time).alias("event_second"),
    date_trunc("HOUR", df.event_time).alias("event_hour_truncated")
)

# Show the results.
df_result.show()
```

## TIMESTAMP_NTZ type

TIMESTAMP_NTZ represents a date and time without time zone. The NTZ stands for "no time zone". It stores year, month, day, hour, minute, second, and fractional seconds. It does not store time zone information. It does not perform any time zone conversion. The value is stored exactly as given. TIMESTAMP_NTZ is used when you want to store a local date and time without any time zone context. For example, a scheduled appointment time in a local time zone, or a business hours timestamp. It is also used when you want to avoid the complexity of time zone conversion.

The following SQL example creates a table named schedules with a TIMESTAMP_NTZ column. Each line is commented.

```sql
-- Create a table named schedules.
-- The schedule_id column uses INT.
-- The local_meeting_time column uses TIMESTAMP_NTZ.
-- It stores the local date and time without time zone conversion.
CREATE TABLE schedules (
    schedule_id INT,
    local_meeting_time TIMESTAMP_NTZ
);
```

The following PySpark example creates a DataFrame with a TIMESTAMP_NTZ column. Each line is commented.

```python
from pyspark.sql.types import StructType, StructField, IntegerType, TimestampNTZType
from datetime import datetime

# Define the schema.
# IntegerType corresponds to INT.
# TimestampNTZType corresponds to TIMESTAMP_NTZ.
schema = StructType([
    StructField("schedule_id", IntegerType(), True),
    StructField("local_meeting_time", TimestampNTZType(), True)
])

# Create a DataFrame with sample data.
data = [(1, datetime(2026, 1, 15, 14, 0, 0)),
        (2, datetime(2026, 1, 16, 9, 30, 0))]

# Create the DataFrame.
df = spark.createDataFrame(data, schema)

# Write the DataFrame to a table.
df.write.saveAsTable("schedules")
```

When you query a TIMESTAMP_NTZ column, it is displayed without any time zone conversion. The value is exactly as stored. You can use the same timestamp functions as with TIMESTAMP, but they operate on the local value without time zone adjustment. The following SQL example shows how to query a TIMESTAMP_NTZ column. Each line is commented.

```sql
-- Select the local meeting time and compute the hour, minute, and second.
SELECT
    schedule_id,
    local_meeting_time,
    hour(local_meeting_time) AS meeting_hour,
    minute(local_meeting_time) AS meeting_minute,
    second(local_meeting_time) AS meeting_second
FROM schedules;
```

```python

# Select columns and compute timestamp functions.

    second(df.local_meeting_time).alias("meeting_second")

```

## Comparison of temporal types

The following table summarizes the differences between DATE, TIMESTAMP, and TIMESTAMP_NTZ.

| Characteristic | DATE | TIMESTAMP | TIMESTAMP_NTZ |
| --- | --- | --- | --- |
| Stores date | Yes | Yes | Yes |
| Stores time | No | Yes | Yes |
| Stores time zone | No | Yes (session time zone) | No |
| Time zone conversion | No | Yes (to UTC on write, from UTC on read) | No |
| Storage size | 4 bytes | 8 bytes | 8 bytes |
| Range | 0001-01-01 to 9999-12-31 | 0001-01-01 00:00:00 to 9999-12-31 23:59:59.999999 | 0001-01-01 00:00:00 to 9999-12-31 23:59:59.999999 |
| Use cases | Birthdays, hire dates, transaction dates | Event times, log times, audit times | Local meeting times, schedules, business hours |

## Timezone behavior explained in detail

The timezone behavior of TIMESTAMP is a common source of confusion. When you write a TIMESTAMP value, Databricks interprets it in the session time zone and converts it to UTC for storage. For example, if the session time zone is America/New_York and you write the value 2026-01-15 10:00:00, Databricks converts it to 2026-01-15 15:00:00 UTC and stores that. When you read the value, Databricks converts it from UTC back to the session time zone and displays 2026-01-15 10:00:00. If you change the session time zone to America/Los_Angeles, the same stored value will be displayed as 2026-01-15 07:00:00. This is because the stored value is always UTC, and the display depends on the session time zone.

This behavior ensures that timestamps are ordered consistently regardless of time zone. It also ensures that you can compare timestamps from different time zones correctly. However, it can cause confusion if you expect the value to remain unchanged. For example, if you store a local meeting time as TIMESTAMP and then query it from a different session time zone, the displayed time will be different. This is why TIMESTAMP_NTZ is useful for local times that should not be converted.

You can set the session time zone using the SQL command SET TIME ZONE or the Spark configuration spark.sql.session.timeZone. The following SQL example shows how to set the session time zone. Each line is commented.

```sql
-- Set the session time zone to America/New_York.
-- This affects how TIMESTAMP values are interpreted and displayed.
SET TIME ZONE 'America/New_York';

-- Now when you query a TIMESTAMP column, it will be displayed in America/New_York time.
SELECT event_time FROM audit_log;
```

The following PySpark example shows how to set the session time zone. Each line is commented.

```python
# Set the session time zone to America/New_York.
spark.conf.set("spark.sql.session.timeZone", "America/New_York")

# Now when you query a TIMESTAMP column, it will be displayed in America/New_York time.
df = spark.read.table("audit_log")
df.show()
```

## Casting and conversion

When you read raw data, it often arrives as strings. You need to cast the strings to the correct temporal types. You can use the CAST function in SQL or the cast method in PySpark. You can use try_cast to safely cast and return null on failure. You can also use try_to_date and try_to_timestamp to parse strings with specific formats.

The following SQL example shows how to cast strings to DATE and TIMESTAMP. Each line is commented.

```sql
-- Cast strings to temporal types.
SELECT
    -- Cast the string to a date.
    CAST(raw_hire_date AS DATE) AS hire_date,
    -- Cast the string to a timestamp.
    CAST(raw_event_time AS TIMESTAMP) AS event_time,
    -- Cast the string to a timestamp without time zone.
    CAST(raw_local_time AS TIMESTAMP_NTZ) AS local_time,
    -- Use try_to_date to parse a date with a specific format.
    try_to_date(raw_hire_date, 'yyyy-MM-dd') AS hire_date_formatted,
    -- Use try_to_timestamp to parse a timestamp with a specific format.
    try_to_timestamp(raw_event_time, 'yyyy-MM-dd HH:mm:ss') AS event_time_formatted
FROM raw_data;
```

The following PySpark example shows how to cast columns to temporal types. Each line is commented.

```python
from pyspark.sql.functions import col, to_date, to_timestamp

# Read raw data.
df = spark.read.table("raw_data")

# Cast columns to temporal types.
df_casted = df.withColumn("hire_date", col("raw_hire_date").cast("date")) \
              .withColumn("event_time", col("raw_event_time").cast("timestamp")) \
              .withColumn("local_time", col("raw_local_time").cast("timestamp_ntz")) \
              .withColumn("hire_date_formatted", to_date(col("raw_hire_date"), "yyyy-MM-dd")) \
              .withColumn("event_time_formatted", to_timestamp(col("raw_event_time"), "yyyy-MM-dd HH:mm:ss"))

# Write the casted data to a new table.
df_casted.write.saveAsTable("clean_data")
```

When casting, be aware of format differences. DATE expects a format like YYYY-MM-DD. TIMESTAMP expects a format like YYYY-MM-DD HH:MM:SS. If the string does not match the expected format, the cast may fail or return null. Use try_cast or try_to_date with a format string to control parsing. Handle invalid values gracefully. Route them to a quarantine table.

## Precision and fractional seconds

TIMESTAMP and TIMESTAMP_NTZ support fractional seconds with microsecond precision. The fractional part can have up to 6 digits. For example, 2026-01-15 10:30:00.123456. DATE does not support fractional seconds. When you cast a string with fractional seconds to TIMESTAMP, the fractional part is preserved. When you cast a TIMESTAMP to DATE, the fractional part and the time component are truncated. The following SQL example shows how to work with fractional seconds. Each line is commented.

```sql
-- Select the event time and extract the fractional seconds.
SELECT
    event_time,
    -- Extract the microsecond part.
    extract(MICROSECOND FROM event_time) AS microseconds,
    -- Truncate to seconds.
    date_trunc('SECOND', event_time) AS truncated_to_second
FROM audit_log;
```

The following PySpark example shows the same operations. Each line is commented.

```python
from pyspark.sql.functions import extract, date_trunc

# Read the audit_log table.
df = spark.read.table("audit_log")

# Select columns and compute fractional seconds.
df_result = df.select(
    "event_time",
    extract("MICROSECOND", df.event_time).alias("microseconds"),
    date_trunc("SECOND", df.event_time).alias("truncated_to_second")
)

# Show the results.
df_result.show()
```

## Common temporal functions

Azure Databricks provides many functions for working with temporal data. Some of the most common are:

- current_date(): returns the current date.
- current_timestamp(): returns the current timestamp.
- date_add(date, days): adds days to a date.
- date_sub(date, days): subtracts days from a date.
- datediff(end_date, start_date): returns the number of days between two dates.
- date_trunc(unit, timestamp): truncates a timestamp to the specified unit.
- extract(field FROM timestamp): extracts a field such as year, month, day, hour, minute, second, microsecond.
- year(date): extracts the year.
- month(date): extracts the month.
- day(date): extracts the day.
- hour(timestamp): extracts the hour.
- minute(timestamp): extracts the minute.
- second(timestamp): extracts the second.
- to_date(string, format): parses a string to a date using the format.
- to_timestamp(string, format): parses a string to a timestamp using the format.
- from_utc_timestamp(timestamp, timezone): converts a UTC timestamp to the specified timezone.
- to_utc_timestamp(timestamp, timezone): converts a timestamp from the specified timezone to UTC.

The following SQL example shows how to use some of these functions. Each line is commented.

```sql
-- Use various temporal functions.
SELECT
    current_date() AS today,
    current_timestamp() AS now,
    date_add(current_date(), 7) AS one_week_later,
    date_sub(current_date(), 7) AS one_week_ago,
    datediff(current_date(), '2026-01-01') AS days_since_new_year,
    date_trunc('MONTH', current_timestamp()) AS start_of_month,
    extract(YEAR FROM current_timestamp()) AS current_year,
    year(current_timestamp()) AS current_year_alt,
    month(current_timestamp()) AS current_month,
    day(current_timestamp()) AS current_day,
    hour(current_timestamp()) AS current_hour,
    minute(current_timestamp()) AS current_minute,
    second(current_timestamp()) AS current_second;
```

The following PySpark example shows the same functions. Each line is commented.

```python

    year(current_timestamp()).alias("current_year_alt"),
    month(current_timestamp()).alias("current_month"),

    minute(current_timestamp()).alias("current_minute"),

```

## Best practices for choosing temporal types

Use DATE when you only need calendar dates without time components. Use DATE for birthdays, hire dates, transaction dates, and any value that is a date without a time. Use TIMESTAMP when you need timezone-aware timestamps. Use TIMESTAMP for event times, log times, audit times, and any value that must be consistent across time zones. Use TIMESTAMP_NTZ when you need timezone-naive timestamps. Use TIMESTAMP_NTZ for local meeting times, schedules, business hours, and any value that should remain as entered without timezone conversion.

Document your timezone assumptions. If you use TIMESTAMP, document which time zone the values are stored in (UTC) and how they are displayed (session time zone). If you use TIMESTAMP_NTZ, document that no timezone conversion is applied. This helps other team members understand the data.

Be consistent. If you use TIMESTAMP for event times in one table, use TIMESTAMP for event times in related tables. Consistency makes joins and comparisons easier.

Test with edge cases. Test dates at the boundaries of the range. Test leap years. Test daylight saving time transitions. Test timezone conversions. Verify that your queries return the expected results.

Monitor for data quality issues. Check for null values, out-of-range values, and future dates where they are not expected. Use expectations and constraints to enforce data quality.

Consider partitioning. Partitioning by date is a common technique for improving query performance. Use the DATE type for the partitioning column. This allows the query optimizer to prune partitions efficiently.

Consider storage. DATE uses 4 bytes. TIMESTAMP and TIMESTAMP_NTZ use 8 bytes. If storage is a concern, use DATE where possible.

## Common mistakes to avoid

One common mistake is using TIMESTAMP when TIMESTAMP_NTZ is needed. If you store a local meeting time as TIMESTAMP, it may be converted to UTC and then displayed in the session time zone, which may not be the local time. Use TIMESTAMP_NTZ for local times that should not be converted.

Another common mistake is assuming that TIMESTAMP stores local time. TIMESTAMP stores UTC internally and converts to the session time zone on read. If you change the session time zone, the displayed value changes. If you want the value to remain unchanged, use TIMESTAMP_NTZ.

Another common mistake is using DATE for a timestamp. If you use DATE for an event time, you lose the time component and cannot perform time-based analysis. Use TIMESTAMP or TIMESTAMP_NTZ instead.

Another common mistake is not handling timezones in pipelines. If you ingest data from multiple time zones, you must decide how to handle the timezone information. You may need to convert all timestamps to UTC for consistency. You may need to store the original timezone in a separate column. You may need to use TIMESTAMP_NTZ for local times. Plan your timezone strategy carefully.

Another common mistake is not testing with edge cases. Test leap years, daylight saving time transitions, and timezone conversions. Verify that your queries return the expected results. A common edge case is the transition from standard time to daylight saving time, where an hour may be skipped or repeated. Test your logic with these cases.

Another common mistake is not documenting timezone assumptions. Without documentation, other team members may not know whether a TIMESTAMP column is stored in UTC or local time. They may make incorrect assumptions and write incorrect queries. Document your choices.

Another common mistake is using the wrong format when casting. Different systems use different date formats. Use try_to_date and try_to_timestamp with explicit format strings to avoid ambiguity. Handle invalid values gracefully.

## Testing temporal types

You should test your temporal types with a variety of values. Create sample data that includes minimum dates, maximum dates, leap years, daylight saving time transitions, and timezone conversions. For example, test the date 2024-02-29 (leap year). Test the timestamp 2026-03-08 02:30:00 in America/New_York, which does not exist because of daylight saving time. Test the timestamp 2026-11-01 01:30:00 in America/New_York, which occurs twice. Verify that your queries handle these cases correctly.

The following SQL example tests leap year handling. Each line is commented.

```sql
-- Test leap year handling.
SELECT
    -- 2024 is a leap year, so February 29 is valid.
    CAST('2024-02-29' AS DATE) AS leap_day,
    -- 2025 is not a leap year, so February 29 is invalid.
    -- This will return null or raise an error depending on the settings.
    try_cast('2025-02-29' AS DATE) AS invalid_leap_day;
```

The following PySpark example tests timezone conversion. Each line is commented.

```python
from pyspark.sql.functions import to_timestamp, from_utc_timestamp, to_utc_timestamp

# Create a DataFrame with a timestamp string.
df = spark.createDataFrame([("2026-01-15 10:00:00",)], ["ts_string"])

# Convert the string to a timestamp.
df = df.withColumn("ts", to_timestamp("ts_string", "yyyy-MM-dd HH:mm:ss"))

# Convert to UTC.
df = df.withColumn("ts_utc", to_utc_timestamp("ts", "America/New_York"))

# Convert back to America/New_York.
df = df.withColumn("ts_ny", from_utc_timestamp("ts_utc", "America/New_York"))

# Show the results.
df.show()
```

These tests help you confirm that your temporal types behave as expected. They also help you catch mistakes before they affect production data.

## Performance considerations

Temporal types have different storage sizes. DATE uses 4 bytes. TIMESTAMP and TIMESTAMP_NTZ use 8 bytes. Smaller types consume less storage and can improve query performance. Partitioning by date is a common technique for improving performance. Use the DATE type for the partitioning column. This allows the query optimizer to prune partitions efficiently.

Consider using Delta Lake optimization features such as OPTIMIZE and ZORDER to compact files and improve data layout. ZORDER by a temporal column can improve query performance for time-based queries.

Consider collecting statistics on temporal columns. Statistics such as minimum and maximum values help the query optimizer estimate the cost of operations. Run ANALYZE TABLE after loading data.

Consider using generated columns for derived temporal values. For example, you can generate a year column from a date column. This can improve query performance for queries that filter by year. However, generated columns add storage and maintenance overhead. Use them judiciously.

## Summary

Temporal data type selection depends on whether you need timezone awareness and what level of precision your application requires. Use DATE when you only need calendar dates without time components. Use TIMESTAMP when you need timezone-aware timestamps. TIMESTAMP converts values to UTC for storage and applies the session timezone when retrieving values. Use TIMESTAMP_NTZ when you need timezone-naive timestamps. TIMESTAMP_NTZ does not perform any timezone conversion. Understanding the differences between these types is essential for designing effective schemas and writing correct queries. Document your timezone assumptions. Be consistent. Test with edge cases. Monitor for data quality issues. Consider partitioning and storage. By following these best practices, you can choose the right temporal type for each column and build reliable, efficient data pipelines.
