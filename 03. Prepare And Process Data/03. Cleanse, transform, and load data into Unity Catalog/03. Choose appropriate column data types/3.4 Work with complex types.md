## Work with complex types

Complex types let you store structured, nested, or repeated data within a single column. They are useful when your data does not fit a flat relational model. In a flat relational model, every value is atomic. A column contains a single value, such as a number, a string, or a date. But real-world data is often more complex. A product may have multiple tags. A device may have a set of properties. A customer may have an address with multiple fields. In a flat model, you would need separate tables and joins to represent this data. Complex types allow you to store this data directly in a single column. This reduces the need for additional tables and joins. It also makes the data more self-contained. However, complex types also make some operations more difficult. You cannot always use standard SQL operations on complex types. You may need to use special functions to access nested fields or to explode arrays into rows. You should consider your query patterns before choosing between normalized tables and complex types.

It shows how these values are nested within a single cell. It also shows how you can query them using indexing, key access, and dot notation. The diagram helps you visualize the structure of complex types and how they differ from flat columns.

Azure Databricks supports three complex types: ARRAY, MAP, and STRUCT. Each type serves a different purpose. ARRAY stores an ordered sequence of elements of the same type. MAP stores key-value pairs with dynamic keys. STRUCT stores a fixed set of named fields. You can also nest complex types within each other. For example, you can have an array of structs, or a map of arrays. This allows you to represent very rich data structures. In this section, we will explore each complex type in detail, provide commented code examples in SQL and PySpark, and offer guidance on when to use each type and how to query them effectively.

## ARRAY type

ARRAY stores an ordered sequence of elements. All elements must have the same type. For example, an array of integers, an array of strings, or an array of structs. ARRAY is used for lists, tags, phone numbers, and any other collection of values. Arrays are zero-indexed in Databricks SQL and PySpark. The first element is at index 0. The last element is at index size minus one. You can access elements by index. You can also use functions to manipulate arrays, such as array_contains, array_size, explode, and collect_list.

The following SQL example creates a table named products with an ARRAY column. Each line is commented.

```sql
-- Create a table named products.
-- The product_id column uses INT.
-- The name column uses STRING.
-- The tags column uses ARRAY<STRING>.
-- It stores an array of strings, such as ['electronics', 'computers'].
CREATE TABLE products (
    product_id INT,
    name STRING,
    tags ARRAY<STRING>
);
```

The following PySpark example creates a DataFrame with an ARRAY column and writes it to a table. Each line is commented.

```python
# Import the required types.
from pyspark.sql.types import StructType, StructField, IntegerType, StringType, ArrayType

# Define the schema.
# ArrayType(StringType(), True) corresponds to ARRAY<STRING>.
# The second argument True means the array can contain null elements.
schema = StructType([
    StructField("product_id", IntegerType(), True),
    StructField("name", StringType(), True),
    StructField("tags", ArrayType(StringType(), True), True)
])

# Create a DataFrame with sample data.
data = [
    (1, "Laptop", ["electronics", "computers"]),
    (2, "Shirt", ["clothing", "men"]),
    (3, "Phone", ["electronics", "mobile"])
]

# Create the DataFrame.
df = spark.createDataFrame(data, schema)

# Write the DataFrame to a table.
df.write.saveAsTable("products")
```

You can query array elements using indexing. The following SQL example shows how to access the first element of an array. Each line is commented.

```sql
-- Query array elements.
SELECT
    product_id,
    name,
    -- tags[0] accesses the first element of the array.
    -- Arrays are zero-indexed, so [0] is the first element.
    tags[0] AS primary_tag,
    -- tags[1] accesses the second element, if it exists.
    tags[1] AS secondary_tag,
    -- array_size returns the number of elements in the array.
    array_size(tags) AS tag_count
FROM products;
```

The following PySpark example shows the same operations using the DataFrame API. Each line is commented.

```python
from pyspark.sql.functions import col, array_size

# Read the products table.
df = spark.read.table("products")

# Select columns and access array elements.
df_result = df.select(
    "product_id",
    "name",
    # Access the first element using col("tags")[0].
    col("tags")[0].alias("primary_tag"),
    # Access the second element using col("tags")[1].
    col("tags")[1].alias("secondary_tag"),
    # Compute the size of the array.
    array_size(col("tags")).alias("tag_count")
)

# Show the results.
df_result.show()
```

You can also use the explode function to convert an array into multiple rows. This is useful when you want to analyze each element separately. The following SQL example shows how to use explode. Each line is commented.

```sql
-- Explode the tags array into multiple rows.
-- Each tag becomes a separate row.
SELECT
    product_id,
    name,
    -- explode takes an array and returns a new row for each element.
    exploded_tag
FROM products
-- The LATERAL VIEW clause is used with explode.
-- It creates a virtual table with the exploded values.
LATERAL VIEW explode(tags) AS exploded_tag;
```

The following PySpark example shows the same operation. Each line is commented.

```python
from pyspark.sql.functions import explode

# Read the products table.
df = spark.read.table("products")

# Explode the tags array.
df_exploded = df.select(
    "product_id",
    "name",
    # explode takes an array column and returns a new row for each element.
    explode("tags").alias("exploded_tag")
)

# Show the results.
df_exploded.show()
```

You can also use the array_contains function to check whether an array contains a specific value. The following SQL example shows how to filter products that have the tag "electronics". Each line is commented.

```sql
-- Filter products that have the tag 'electronics'.
SELECT
    product_id,
    name,
    tags
FROM products
-- array_contains returns true if the array contains the specified value.
WHERE array_contains(tags, 'electronics');
```

The following PySpark example shows the same filter. Each line is commented.

```python
from pyspark.sql.functions import array_contains

# Read the products table.
df = spark.read.table("products")

# Filter products that have the tag 'electronics'.
df_filtered = df.filter(array_contains("tags", "electronics"))

# Show the results.
df_filtered.show()
```

## MAP type

MAP stores key-value pairs. All keys must have the same type. All values must have the same type. MAP is used for dictionaries, attributes, and any other associative collection. Maps are useful when the keys are dynamic and not known in advance. For example, a device may have a set of properties such as firmware_version, model, and manufacturer. These properties may vary from device to device. A map allows you to store them in a single column. You can access values by key using bracket notation. You can also use functions such as map_keys, map_values, and explode to manipulate maps.

The following SQL example creates a table named devices with a MAP column. Each line is commented.

```sql
-- Create a table named devices.
-- The device_id column uses INT.
-- The properties column uses MAP<STRING, STRING>.
-- It stores key-value pairs where both keys and values are strings.
CREATE TABLE devices (
    device_id INT,
    properties MAP<STRING, STRING>
);
```

The following PySpark example creates a DataFrame with a MAP column and writes it to a table. Each line is commented.

```python
from pyspark.sql.types import StructType, StructField, IntegerType, StringType, MapType

# Define the schema.
# MapType(StringType(), StringType(), True) corresponds to MAP<STRING, STRING>.
# The third argument True means the map can contain null values.
schema = StructType([
    StructField("device_id", IntegerType(), True),
    StructField("properties", MapType(StringType(), StringType(), True), True)
])

# Create a DataFrame with sample data.
data = [
    (1, {"firmware_version": "1.2.3", "model": "X100", "manufacturer": "Acme"}),
    (2, {"firmware_version": "2.0.1", "model": "Y200", "manufacturer": "Acme"}),
    (3, {"firmware_version": "1.0.0", "model": "Z300", "manufacturer": "Beta"})
]

# Create the DataFrame.
df = spark.createDataFrame(data, schema)

# Write the DataFrame to a table.
df.write.saveAsTable("devices")
```

You can access map values by key. The following SQL example shows how to access the firmware_version property. Each line is commented.

```sql
-- Access map values by key.
SELECT
    device_id,
    -- properties['firmware_version'] accesses the value for the key 'firmware_version'.
    properties['firmware_version'] AS firmware,
    -- properties['model'] accesses the value for the key 'model'.
    properties['model'] AS model,
    -- properties['manufacturer'] accesses the value for the key 'manufacturer'.
    properties['manufacturer'] AS manufacturer
FROM devices;
```

The following PySpark example shows the same operations using the DataFrame API. Each line is commented.

```python
from pyspark.sql.functions import col

# Read the devices table.
df = spark.read.table("devices")

# Select columns and access map values.
df_result = df.select(
    "device_id",
    # Access the value for the key 'firmware_version'.
    col("properties")["firmware_version"].alias("firmware"),
    # Access the value for the key 'model'.
    col("properties")["model"].alias("model"),
    # Access the value for the key 'manufacturer'.
    col("properties")["manufacturer"].alias("manufacturer")
)

# Show the results.
df_result.show()
```

If a key does not exist in a map, the result is null. You can use the map_contains_key function to check whether a key exists. The following SQL example shows how to check for the existence of a key. Each line is commented.

```sql
-- Check whether a key exists in the map.
SELECT
    device_id,
    -- map_contains_key returns true if the key exists.
    map_contains_key(properties, 'firmware_version') AS has_firmware_version,
    map_contains_key(properties, 'serial_number') AS has_serial_number
FROM devices;
```

The following PySpark example shows the same check. Each line is commented.

```python
from pyspark.sql.functions import map_contains_key

# Read the devices table.
df = spark.read.table("devices")

# Check whether keys exist.
df_result = df.select(
    "device_id",
    map_contains_key("properties", "firmware_version").alias("has_firmware_version"),
    map_contains_key("properties", "serial_number").alias("has_serial_number")
)

# Show the results.
df_result.show()
```

You can explode a map into multiple rows using the explode function. Each key-value pair becomes a separate row. The following SQL example shows how to explode a map. Each line is commented.

```sql
-- Explode the properties map into multiple rows.
SELECT
    device_id,
    -- explode takes a map and returns a new row for each key-value pair.
    exploded_key,
    exploded_value
FROM devices
LATERAL VIEW explode(properties) AS exploded_key, exploded_value;
```

The following PySpark example shows the same operation. Each line is commented.

```python
from pyspark.sql.functions import explode

# Read the devices table.
df = spark.read.table("devices")

# Explode the properties map.
df_exploded = df.select(
    "device_id",
    # explode takes a map column and returns a new row for each key-value pair.
    explode("properties").alias("exploded_key", "exploded_value")
)

# Show the results.
df_exploded.show()
```

## STRUCT type

STRUCT stores a record with named fields. Each field has a name and a type. STRUCT is used for nested records, such as an address with street, city, state, and zip. STRUCT is useful when the fields are fixed and known in advance. You can access fields using dot notation. You can also use functions such as struct, named_struct, and explode to manipulate structs.

The following SQL example creates a table named customers with a STRUCT column. Each line is commented.

```sql
-- Create a table named customers.
-- The customer_id column uses INT.
-- The name column uses STRING.
-- The address column uses STRUCT<street:STRING, city:STRING, state:STRING, zip:STRING>.
-- It stores a nested record with four fields.
CREATE TABLE customers (
    customer_id INT,
    name STRING,
    address STRUCT<street: STRING, city: STRING, state: STRING, zip: STRING>
);
```

The following PySpark example creates a DataFrame with a STRUCT column and writes it to a table. Each line is commented.

```python
from pyspark.sql.types import StructType, StructField, IntegerType, StringType

# Define the schema for the address struct.
address_schema = StructType([
    StructField("street", StringType(), True),
    StructField("city", StringType(), True),
    StructField("state", StringType(), True),
    StructField("zip", StringType(), True)
])

# Define the schema for the table.
schema = StructType([
    StructField("customer_id", IntegerType(), True),
    StructField("name", StringType(), True),
    StructField("address", address_schema, True)
])

# Create a DataFrame with sample data.
data = [
    (1, "Alice", ("123 Main St", "Springfield", "IL", "62701")),
    (2, "Bob", ("456 Oak Ave", "Portland", "OR", "97201"))
]

# Create the DataFrame.
df = spark.createDataFrame(data, schema)

# Write the DataFrame to a table.
df.write.saveAsTable("customers")
```

You can access struct fields using dot notation. The following SQL example shows how to access the city field. Each line is commented.

```sql
-- Access struct fields.
SELECT
    customer_id,
    name,
    -- address.city accesses the city field of the address struct.
    address.city AS city,
    -- address.state accesses the state field.
    address.state AS state,
    -- address.zip accesses the zip field.
    address.zip AS zip
FROM customers;
```

The following PySpark example shows the same operations using the DataFrame API. Each line is commented.

```python
from pyspark.sql.functions import col

# Read the customers table.
df = spark.read.table("customers")

# Select columns and access struct fields.
df_result = df.select(
    "customer_id",
    "name",
    # Access the city field using col("address.city").
    col("address.city").alias("city"),
    # Access the state field.
    col("address.state").alias("state"),
    # Access the zip field.
    col("address.zip").alias("zip")
)

# Show the results.
df_result.show()
```

You can also flatten a struct using the star notation. The following SQL example shows how to select all fields of the address struct. Each line is commented.

```sql
-- Flatten the address struct.
SELECT
    customer_id,
    name,
    -- address.* selects all fields of the address struct.
    address.*

```

## Nested complex types

You can nest complex types within each other. For example, you can have an array of structs, a map of arrays, or a struct with an array field. This allows you to represent very rich data structures. The following SQL example creates a table with an array of structs. Each line is commented.

```sql
-- Create a table with an array of structs.
-- The orders column uses ARRAY<STRUCT<order_id:INT, amount:DECIMAL(10,2)>>.
-- It stores a list of orders, where each order has an order_id and an amount.
CREATE TABLE customer_orders (
    customer_id INT,
    name STRING,
    orders ARRAY<STRUCT<order_id: INT, amount: DECIMAL(10,2)>>
);
```

The following PySpark example creates a DataFrame with the same schema. Each line is commented.

```python
from pyspark.sql.types import StructType, StructField, IntegerType, StringType, ArrayType, DecimalType
from decimal import Decimal

# Define the schema for the order struct.
order_schema = StructType([
    StructField("order_id", IntegerType(), True),
    StructField("amount", DecimalType(10,2), True)
])

# Define the schema for the table.
schema = StructType([
    StructField("customer_id", IntegerType(), True),
    StructField("name", StringType(), True),
    StructField("orders", ArrayType(order_schema, True), True)
])

# Create a DataFrame with sample data.
data = [
    (1, "Alice", [(101, Decimal("100.00")), (102, Decimal("200.00"))]),
    (2, "Bob", [(103, Decimal("150.00"))])
]

# Create the DataFrame.
df = spark.createDataFrame(data, schema)

# Write the DataFrame to a table.
df.write.saveAsTable("customer_orders")
```

You can query nested complex types by chaining accessors. The following SQL example shows how to access the order_id and amount of each order. Each line is commented.

```sql
-- Access nested complex types.
SELECT
    customer_id,
    name,
    -- orders[0].order_id accesses the order_id of the first order.
    orders[0].order_id AS first_order_id,
    -- orders[0].amount accesses the amount of the first order.
    orders[0].amount AS first_order_amount
FROM customer_orders;
```

The following PySpark example shows the same operations. Each line is commented.

```python
# Read the customer_orders table.
df = spark.read.table("customer_orders")

# Select nested fields.
df_result = df.select(
    "customer_id",
    "name",
    # Access the order_id of the first order.
    col("orders")[0]["order_id"].alias("first_order_id"),
    # Access the amount of the first order.
    col("orders")[0]["amount"].alias("first_order_amount")
)

# Show the results.
df_result.show()
```

You can also explode an array of structs to analyze each order separately. The following SQL example shows how to explode the orders array. Each line is commented.

```sql
-- Explode the orders array into multiple rows.
SELECT
    customer_id,
    name,
    exploded_order.order_id AS order_id,
    exploded_order.amount AS amount
FROM customer_orders
LATERAL VIEW explode(orders) AS exploded_order;
```

The following PySpark example shows the same operation. Each line is commented.

```python
from pyspark.sql.functions import explode

# Read the customer_orders table.
df = spark.read.table("customer_orders")

# Explode the orders array.
df_exploded = df.select(
    "customer_id",
    "name",
    # Explode the orders array.
    explode("orders").alias("exploded_order")
).select(
    "customer_id",
    "name",
    # Access the fields of the exploded struct.
    col("exploded_order.order_id").alias("order_id"),
    col("exploded_order.amount").alias("amount")
)

# Show the results.
df_exploded.show()
```

## When to use complex types

Complex types are useful when your data does not fit a flat relational model. They reduce the need for additional tables and joins. They make the data more self-contained. They allow you to represent rich data structures. However, complex types also make some operations more difficult. You cannot always use standard SQL operations on complex types. You may need to use special functions to access nested fields or to explode arrays into rows. You may need to write more complex queries. You may need to use higher-order functions or user-defined functions.

Consider your query patterns before choosing between normalized tables and complex types. If you frequently need to query individual elements of an array or map, you may need to explode them, which can be expensive. If you frequently need to join the nested data with other tables, you may need to flatten it. If you mostly read the entire complex value as a single unit, complex types are convenient. If you need to update individual elements, complex types can be more difficult because Delta Lake does not support partial updates of complex types. You must rewrite the entire column.

Use ARRAY when you have multiple values of the same type and the order matters or the values are naturally a list. Use MAP when you have key-value pairs with dynamic keys and you need to look up values by key. Use STRUCT when you have a fixed set of named fields and you want to group related values together. Use nested complex types when you need to represent hierarchical data.

Consider the tradeoffs. Complex types reduce storage because they avoid the overhead of separate tables. They reduce the need for joins, which can improve query performance. But they can make queries more complex. They can make schema evolution more difficult. They can make data quality validation more challenging. You need to weigh these tradeoffs based on your use case.

## Best practices for working with complex types

Document your schema. Complex types can be hard to understand. Document the structure of each ARRAY, MAP, and STRUCT. Explain the meaning of each field. Explain the expected types. This helps other team members understand the data.

Use consistent field names. If you use STRUCT, use consistent field names across tables. This makes queries easier to write and understand. Avoid abbreviations that are not clear.

Validate complex types. Use expectations and constraints to validate the structure and contents of complex types. For example, check that an array is not empty. Check that a map contains required keys. Check that a struct field is not null. Use functions such as array_size, map_contains_key, and is not null.

Handle nulls. Complex types can be null. Individual elements can be null. Fields within a struct can be null. Decide how to handle nulls. Use coalesce, ifnull, or null checks in your queries.

Test with edge cases. Test empty arrays. Test arrays with one element. Test arrays with many elements. Test maps with missing keys. Test structs with null fields. Verify that your queries return the expected results.

Consider performance. Exploding arrays and maps can be expensive. Filtering on nested fields can be expensive. Use partitioning and ZORDER to improve performance. Consider flattening complex types into separate tables if you frequently query individual elements.

Use the right type for the job. Do not use a complex type when a simple type will do. Do not use a map when a struct is more appropriate. Do not use an array when a separate table is more appropriate. Choose the type that best matches your data and your query patterns.

## Common mistakes to avoid

One common mistake is using complex types when a normalized schema would be better. If you frequently need to join nested data with other tables, or if you need to update individual elements, a normalized schema may be more appropriate. Complex types are convenient for storage but can make queries and updates more difficult.

Another common mistake is not documenting the schema. Complex types can be hard to understand. Without documentation, other team members may not know what fields exist or what they mean. Always document your complex types.

Another common mistake is not handling nulls. Complex types can be null. Individual elements can be null. If you do not handle nulls, your queries may return unexpected results. Use null checks and coalesce.

Another common mistake is not testing with edge cases. Test empty arrays, maps, and structs. Test missing keys. Test null fields. Verify that your queries behave as expected.

Another common mistake is using the wrong index. Arrays are zero-indexed. If you use index 1 to access the first element, you will get the second element. If you use an index that is out of bounds, you will get null. Always check the array size before accessing elements by index.

Another common mistake is assuming that map keys are ordered. Maps are unordered. If you need ordered keys, use an array of structs instead.

Another common mistake is not considering performance. Exploding arrays and maps can be expensive. If you explode a large array, you may create many rows, which can slow down queries. Consider whether you can avoid exploding by using higher-order functions or by flattening the data at ingestion time.

## Summary

Complex types let you store structured, nested, or repeated data within a single column. They are useful when your data does not fit a flat relational model. Azure Databricks supports three complex types: ARRAY, MAP, and STRUCT. ARRAY stores an ordered sequence of elements of the same type. MAP stores key-value pairs with dynamic keys. STRUCT stores a fixed set of named fields. You can nest complex types within each other to represent rich data structures. You can query complex types using indexing, key access, dot notation, and functions such as explode, array_contains, map_contains_key, and array_size. Complex types reduce the need for additional tables and joins, but they also make some operations more difficult. Consider your query patterns before choosing between normalized tables and complex types. Document your schema. Validate complex types. Handle nulls. Test with edge cases. Consider performance. Use the right type for the job. By following these best practices, you can work with complex types effectively and build reliable, efficient data pipelines.
