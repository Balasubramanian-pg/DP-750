# Select the right numeric type

Numeric data requires careful type selection because different types have different precision, range, and storage characteristics. Your choice affects both data integrity and performance. A numeric column can store whole numbers, exact decimal values, or approximate floating-point values. Each category has a different purpose. Each type within a category has a different range and storage cost. Choosing the wrong type can cause overflow errors, rounding errors, wasted storage, slower queries, and incorrect results. Choosing the right type improves data quality, reduces storage, speeds up queries, and makes your schema easier to understand. This section explains integral types, decimal types, and floating-point types in detail. It provides commented code examples in SQL and PySpark. It also offers guidance on when to use each type and how to avoid common mistakes.

## Why numeric type selection matters

Numeric type selection matters for three main reasons. First, it affects data integrity. If you choose a type that is too small, values can overflow. For example, a TINYINT can store values from -128 to 127. If you use TINYINT for a counter that reaches 128, the write fails or the value wraps around. If you choose a floating-point type for money, you can get rounding errors. For example, 0.1 plus 0.2 may not equal 0.3 exactly. These errors can accumulate and cause incorrect financial calculations. If you choose DECIMAL with too small a precision, large values cannot be stored. If you choose DECIMAL with too small a scale, you lose fractional precision.

Second, it affects performance. Numeric types have different storage sizes. TINYINT uses 1 byte. SMALLINT uses 2 bytes. INT uses 4 bytes. BIGINT uses 8 bytes. FLOAT uses 4 bytes. DOUBLE uses 8 bytes. DECIMAL uses a variable number of bytes depending on precision. Smaller types consume less memory and less disk space. They also move faster through the network during shuffles and exchanges. They can be compressed more effectively. They can improve query performance, especially for large tables. However, smaller types have smaller ranges. You must balance storage efficiency with the need to store all possible values.

Third, it affects correctness. Different numeric types behave differently in calculations. Integer division truncates the fractional part. Floating-point arithmetic is approximate. Decimal arithmetic is exact within the specified precision and scale. If you use the wrong type, your calculations may produce unexpected results. For example, dividing two integers in SQL may return an integer instead of a decimal. Adding two large integers may overflow. Comparing a float to a decimal may produce unexpected results due to type coercion. Choosing the right type ensures that calculations behave as expected.

## Integral types

Integral types represent whole numbers. They do not have a fractional part. They are used for counts, identifiers, ages, quantities, status codes, years, and any other value that is naturally a whole number. Azure Databricks provides four integral types: TINYINT, SMALLINT, INT, and BIGINT. They differ in the range of values they can store and the amount of storage they consume.

The following table summarizes the range, storage, and common use cases for each integral type.

| Type | Range | Storage | Common use cases |
| --- | --- | --- | --- |
| TINYINT | -128 to 127 | 1 byte | Status codes, small counters, flags |
| SMALLINT | -32,768 to 32,767 | 2 bytes | Year values, small ranges, limited counters |
| INT | -2,147,483,648 to 2,147,483,647 | 4 bytes | Most identifiers, counts, quantities |
| BIGINT | -9,223,372,036,854,775,808 to 9,223,372,036,854,775,807 | 8 bytes | Large IDs, row counts, timestamps in milliseconds |

When creating tables, specify the appropriate type for each column. The following SQL example creates a table named orders with four integral columns. Each line is commented.

```sql
-- Create a table named orders.
-- The order_id column uses INT, which is suitable for most identifiers.
-- The status_code column uses TINYINT, which is sufficient for small status codes.
-- The total_items column uses SMALLINT, which is sufficient for typical order sizes.
-- The transaction_id column uses BIGINT, which can hold very large identifiers.
CREATE TABLE orders (
    order_id INT,
    status_code TINYINT,
    total_items SMALLINT,
    transaction_id BIGINT
);
```

The following PySpark example creates a DataFrame with the same schema and writes it to a table. Each line is commented.

```python
# Import the required types.
from pyspark.sql.types import StructType, StructField, IntegerType, ByteType, ShortType, LongType

# Define the schema.
# IntegerType corresponds to INT.
# ByteType corresponds to TINYINT.
# ShortType corresponds to SMALLINT.
# LongType corresponds to BIGINT.
schema = StructType([
    StructField("order_id", IntegerType(), True),
    StructField("status_code", ByteType(), True),
    StructField("total_items", ShortType(), True),
    StructField("transaction_id", LongType(), True)
])

# Create a DataFrame with sample data.
data = [(1, 1, 10, 10000000001), (2, 2, 5, 10000000002)]

# Create the DataFrame.
df = spark.createDataFrame(data, schema)

# Write the DataFrame to a table.
df.write.saveAsTable("orders")
```

When choosing an integral type, use the smallest type that can comfortably hold all possible values. This saves storage and can improve query performance. However, be careful not to choose a type that is too small. If a value exceeds the range of the type, the write fails or the value overflows. For example, if you use TINYINT for a counter that can exceed 127, you will eventually encounter an error. It is better to use INT or BIGINT if you are unsure. Consider future growth. A status code column may start with a few values, but new statuses may be added over time. A counter may grow as your business grows. Choose a type that has room for growth.

## Decimal types

Decimal types represent exact numeric values with a fixed precision and scale. They are used for financial data, monetary amounts, tax rates, percentages, and any value where exact precision is required. The decimal type in Azure Databricks is DECIMAL(p,s). The p is the precision, which is the total number of digits. The s is the scale, which is the number of digits to the right of the decimal point. For example, DECIMAL(10,2) can store values with up to 10 total digits, 2 of which are after the decimal point. The maximum value is 99,999,999.99. The minimum value is -99,999,999.99. The maximum precision supported by Databricks SQL is 38. The scale can range from 0 to the precision.

Decimal types are exact. They do not suffer from rounding errors like floating-point types. This makes them suitable for money. For example, if you store 0.1 and 0.2 as floating-point numbers and add them, you may get 0.30000000000000004. If you store them as decimals, you get exactly 0.3. This is critical for financial calculations. Decimal types are also used for any value where you need to control the number of decimal places, such as tax rates, percentages, and measurements.

The following SQL example creates a table named transactions with decimal columns. Each line is commented.

```sql
-- Create a table named transactions.
-- The amount column uses DECIMAL(10,2).
-- This allows values up to 99,999,999.99.
-- It is exact, so it is suitable for financial amounts.
-- The tax_rate column uses DECIMAL(5,4).
-- This allows values up to 9.9999.
-- It is suitable for tax rates with four decimal places.
CREATE TABLE transactions (
    transaction_id INT,
    amount DECIMAL(10,2),
    tax_rate DECIMAL(5,4)
);
```

The following PySpark example creates a DataFrame with decimal columns. Each line is commented.

```python
from pyspark.sql.types import StructType, StructField, IntegerType, DecimalType
from decimal import Decimal

# Define the schema.
# DecimalType(10,2) corresponds to DECIMAL(10,2).
# DecimalType(5,4) corresponds to DECIMAL(5,4).
schema = StructType([
    StructField("transaction_id", IntegerType(), True),
    StructField("amount", DecimalType(10,2), True),
    StructField("tax_rate", DecimalType(5,4), True)
])

# Create a DataFrame with sample data.
data = [(1, Decimal("12345.67"), Decimal("0.0825"))]

# Create the DataFrame.
df = spark.createDataFrame(data, schema)

# Write the DataFrame to a table.
df.write.saveAsTable("transactions")
```

When choosing a decimal type, choose a precision and scale that match your data. If you choose a precision that is too small, you will not be able to store large values. If you choose a scale that is too small, you will lose precision. If you choose a precision and scale that are too large, you will waste storage. For financial data, DECIMAL(18,2) or DECIMAL(38,2) is common. DECIMAL(38,2) can store values up to 99,999,999,999,999,999,999,999,999,999,999,999.99. This is more than enough for most financial applications. For tax rates, DECIMAL(5,4) allows values up to 9.9999. For percentages, DECIMAL(5,2) allows values up to 999.99. Choose the precision and scale based on the business requirements. Document your choices.

## Floating point types

Floating-point types represent approximate numeric values. They are used for scientific calculations, measurements, machine learning features, and any value where a small amount of imprecision is acceptable. The floating-point types in Azure Databricks are FLOAT and DOUBLE. FLOAT is a 4-byte single-precision floating-point number. DOUBLE is an 8-byte double-precision floating-point number. DOUBLE has more precision than FLOAT. It is the default for floating-point literals in many systems.

Floating-point types are not exact. They store values in a binary format that cannot represent all decimal fractions exactly. For example, 0.1 cannot be represented exactly as a floating-point number. This can lead to small rounding errors. For most scientific and engineering applications, these errors are acceptable. For financial applications, they are not. You should use decimal types for financial data.

The following SQL example creates a table named measurements with floating-point columns. Each line is commented.

```sql
-- Create a table named measurements.
-- The temperature column uses DOUBLE, which provides good precision.
-- The pressure column uses DOUBLE, which provides good precision.
-- The humidity column uses FLOAT, which saves storage and is sufficient for humidity.
CREATE TABLE measurements (
    sensor_id INT,
    temperature DOUBLE,
    pressure DOUBLE,
    humidity FLOAT
);
```

The following PySpark example creates a DataFrame with floating-point columns. Each line is commented.

```python
from pyspark.sql.types import StructType, StructField, IntegerType, DoubleType, FloatType

# Define the schema.
# DoubleType corresponds to DOUBLE.
# FloatType corresponds to FLOAT.
schema = StructType([
    StructField("sensor_id", IntegerType(), True),
    StructField("temperature", DoubleType(), True),
    StructField("pressure", DoubleType(), True),
    StructField("humidity", FloatType(), True)
])

# Create a DataFrame with sample data.
data = [(1, 23.5, 1013.25, 45.2), (2, 24.1, 1012.80, 46.8)]

# Create the DataFrame.
df = spark.createDataFrame(data, schema)

# Write the DataFrame to a table.
df.write.saveAsTable("measurements")
```

When choosing between FLOAT and DOUBLE, use DOUBLE if you need more precision. Use FLOAT if you need to save storage and you can tolerate less precision. In most cases, DOUBLE is the safer choice. FLOAT is useful when you have very large arrays of floating-point values and storage is a concern. DOUBLE is the default for most scientific computations. Avoid using FLOAT or DOUBLE for money. Use DECIMAL instead.

## Choosing between DECIMAL and floating point types

The choice between DECIMAL and floating point types depends on your precision requirements. DECIMAL is exact. It is suitable for financial calculations, monetary amounts, tax rates, and any value where exact base-10 precision matters. Floating point is approximate. It is suitable for scientific calculations, measurements, and machine learning features where a small amount of imprecision is acceptable.

The following table summarizes the differences.

| Characteristic | DECIMAL(p,s) | FLOAT | DOUBLE |
| --- | --- | --- | --- |
| Precision | Exact, user-defined | Approximate, about 7 decimal digits | Approximate, about 15 decimal digits |
| Range | Limited by precision | Very large | Very large |
| Storage | Variable, depends on precision | 4 bytes | 8 bytes |
| Use cases | Money, tax rates, percentages | Scientific measurements, ML features | Scientific measurements, ML features |
| Rounding errors | None within specified precision | Possible | Possible |

Use DECIMAL for financial data where exact precision matters. Use DOUBLE for scientific calculations where a large range and high precision are needed. Use FLOAT when storage is a concern and the required precision is lower. Never use FLOAT or DOUBLE for money. Never use DECIMAL for scientific calculations where the range of values exceeds the maximum precision of DECIMAL.

## Casting and type conversion

When you read raw data, it often arrives as strings. You need to cast the strings to the correct numeric types. You can use the CAST function in SQL or the cast method in PySpark. You can use try_cast to safely cast and return null on failure. The following SQL example shows how to cast strings to numeric types. Each line is commented.

```sql
-- Cast strings to numeric types.
SELECT
    -- Cast the string to an integer.
    CAST(raw_order_id AS INT) AS order_id,
    -- Cast the string to a tiny integer.
    CAST(raw_status_code AS TINYINT) AS status_code,
    -- Cast the string to a small integer.
    CAST(raw_total_items AS SMALLINT) AS total_items,
    -- Cast the string to a big integer.
    CAST(raw_transaction_id AS BIGINT) AS transaction_id,
    -- Cast the string to a decimal.
    CAST(raw_amount AS DECIMAL(10,2)) AS amount,
    -- Cast the string to a double.
    CAST(raw_temperature AS DOUBLE) AS temperature
FROM raw_orders;
```

The following PySpark example shows how to cast columns to numeric types. Each line is commented.

```python
from pyspark.sql.functions import col

# Read raw data.
df = spark.read.table("raw_orders")

# Cast columns to numeric types.
# The cast method converts the column to the specified type.
# If the conversion fails, an error is raised.
# Use try_cast if you want to return null on failure.
df_casted = df.withColumn("order_id", col("raw_order_id").cast("int")) \
              .withColumn("status_code", col("raw_status_code").cast("tinyint")) \
              .withColumn("total_items", col("raw_total_items").cast("smallint")) \
              .withColumn("transaction_id", col("raw_transaction_id").cast("bigint")) \
              .withColumn("amount", col("raw_amount").cast("decimal(10,2)")) \
              .withColumn("temperature", col("raw_temperature").cast("double"))

# Write the casted data to a new table.
df_casted.write.saveAsTable("clean_orders")
```

When casting, be aware of safe casting rules. Delta Lake attempts safe casts during writes. If a cast is not safe, the write fails. For example, casting a string that contains letters to an integer fails. Casting a double to an integer may truncate the fractional part. Casting a decimal to an integer may round or truncate. Always test your casts with edge cases. Use try_cast to handle invalid values gracefully. Route invalid records to a quarantine table. This is covered in more detail in the error handling sections.

## Storage and performance considerations

Numeric type selection affects storage and performance. Smaller types consume less storage. They also move faster through the network during shuffles and exchanges. They can be compressed more effectively. They can improve query performance, especially for large tables. However, smaller types have smaller ranges. You must balance storage efficiency with the need to store all possible values.

Consider the following guidelines. Use TINYINT for status codes and small counters. Use SMALLINT for year values and limited ranges. Use INT for most identifiers and counts. Use BIGINT for large identifiers and row counts. Use DECIMAL for money and exact values. Use DOUBLE for scientific calculations. Use FLOAT when storage is a concern and precision requirements are lower. Avoid using BIGINT when INT is sufficient. Avoid using DOUBLE when FLOAT is sufficient. Avoid using DECIMAL with unnecessarily large precision and scale.

Consider nullability. Nullable columns require extra storage for null flags. If a column is always populated, define it as NOT NULL. This can improve performance and reduce storage. Consider partitioning. Partitioning by a numeric column such as year or month can improve query performance. Consider statistics. Analyze tables after loading data to collect statistics. This helps the query optimizer choose efficient plans.

Consider compression. Delta Lake compresses data using Parquet. Numeric types compress well. Smaller types compress better than larger types. Consider file sizes. Small files can hurt performance. Use Delta Lake optimization features such as OPTIMIZE and ZORDER to compact files and improve data layout.

## Best practices for selecting numeric types

Match the type to the data. Use the smallest type that can comfortably hold all possible values. Consider future growth. Do not choose a type that is too small.

Use DECIMAL for financial data. Use DECIMAL for money, tax rates, percentages, and any value where exact base-10 precision matters. Never use FLOAT or DOUBLE for money.

Use DOUBLE for scientific calculations. Use DOUBLE for measurements, sensor readings, and machine learning features. Use FLOAT when storage is a concern and precision requirements are lower.

Use INT for most identifiers and counts. Use INT for order IDs, customer IDs, and typical counts. Use BIGINT for large IDs and row counts. Use SMALLINT for years and small ranges. Use TINYINT for status codes and flags.

Specify precision and scale for DECIMAL. Choose a precision and scale that match your business requirements. Document your choices. Avoid overly large precision and scale.

Define nullability explicitly. If a column must always have a value, define it as NOT NULL. This improves data quality and performance.

Test with boundary values. Test the minimum and maximum values for each type. Test null values. Test invalid values. Verify that your casts and calculations behave as expected.

Monitor for overflow. If a column is approaching the maximum value of its type, consider widening the type. Use schema evolution or ALTER TABLE to change the type.

Document your schema. Keep a record of the types and the reasons for choosing them. This helps new team members understand the schema. It also helps with auditing and compliance.

## Common mistakes to avoid

One common mistake is using FLOAT or DOUBLE for money. Floating-point types introduce rounding errors. Use DECIMAL instead. For example, if you store 0.1 and 0.2 as DOUBLE and add them, you may get 0.30000000000000004. If you use DECIMAL, you get exactly 0.3.

Another common mistake is using TINYINT for a counter that may exceed 127. Use SMALLINT or INT instead. Another mistake is using SMALLINT for a counter that may exceed 32,767. Use INT instead. Another mistake is using INT for a row count that may exceed 2.1 billion. Use BIGINT instead.

Another common mistake is using DECIMAL with too small a precision. For example, DECIMAL(5,2) can only store values up to 999.99. If you need to store larger amounts, use DECIMAL(10,2) or DECIMAL(18,2). Another mistake is using DECIMAL with too small a scale. For example, DECIMAL(10,0) cannot store fractional values. If you need fractional values, increase the scale.

Another common mistake is using DECIMAL with unnecessarily large precision and scale. For example, DECIMAL(38,18) uses more storage than needed for typical financial amounts. Use DECIMAL(18,2) for most financial data.

Another common mistake is forgetting nullability. If a column is always populated, define it as NOT NULL. This improves data quality and performance.

Another common mistake is not testing boundary values. Test the minimum and maximum values for each type. Test overflow. Test null values. Test invalid values. Verify that your casts and calculations behave as expected.

Another common mistake is not considering future growth. A column that starts small may grow over time. Choose a type that has room for growth.

## Testing numeric types

You should test your numeric types with a variety of values. Create sample data that includes minimum values, maximum values, values just outside the range, null values, and invalid values. For example, if you use TINYINT, test -128, 127, -129, 128, and null. If you use DECIMAL(10,2), test 0.00, 99,999,999.99, -99,999,999.99, 100,000,000.00, and null. If you use DOUBLE, test very large and very small values. Verify that valid values are stored correctly and invalid values are rejected or handled as expected.

The following SQL example tests boundary values for a TINYINT column. Each line is commented.

```sql
-- Create a test table with a TINYINT column.
CREATE TABLE test_tinyint (
    value TINYINT
);

-- Insert the minimum value. This should succeed.
INSERT INTO test_tinyint VALUES (-128);

-- Insert the maximum value. This should succeed.
INSERT INTO test_tinyint VALUES (127);

-- Insert a value below the minimum. This should fail.
INSERT INTO test_tinyint VALUES (-129);

-- Insert a value above the maximum. This should fail.
INSERT INTO test_tinyint VALUES (128);

-- Insert a null value. This should succeed if the column is nullable.
INSERT INTO test_tinyint VALUES (NULL);
```

The following PySpark example tests boundary values for a DECIMAL column. Each line is commented.

```python
from decimal import Decimal

# Create a test DataFrame with boundary values.
data = [
    (Decimal("0.00"),),
    (Decimal("99999999.99"),),
    (Decimal("-99999999.99"),),
    (Decimal("100000000.00"),)  # This exceeds DECIMAL(10,2) and will fail.
]

# Define the schema.
schema = "value DECIMAL(10,2)"

# Create the DataFrame.
df = spark.createDataFrame(data, schema)

# Try to write the DataFrame to a table.
# The last row exceeds the precision and will cause an error.
try:
    df.write.saveAsTable("test_decimal")
except Exception as e:
    print(f"Error: {e}")
```

These tests help you confirm that your chosen types behave as expected. They also help you catch mistakes before they affect production data.
