# Apply type selection best practices

When evaluating data for type selection, consider these practical guidelines. Type selection is not just a technical detail. It is a design decision that affects storage, performance, correctness, and maintainability. The choices you make when defining a schema ripple through every query, every transformation, and every downstream consumer. A schema that is well designed makes pipelines faster, reduces storage costs, and prevents errors. A schema that is poorly designed causes overflow errors, rounding problems, wasted space, and confusion. The best practices in this section help you avoid common pitfalls and build schemas that serve as a form of documentation and validation. They help you catch errors early, before they affect downstream analytics.

## Match the type to the data's nature and range

The first best practice is to match the type to the data's nature and range. Do not use BIGINT for values that never exceed a few thousand. The extra bytes multiply across millions of rows. Do not use DOUBLE for money. Do not use STRING for dates. Do not use DECIMAL with a precision of 38 when a precision of 10 is sufficient. Each of these choices wastes storage, slows down queries, and can cause errors.

### Why matching matters

When you choose a type that is too large, you waste storage. A BIGINT uses 8 bytes. An INT uses 4 bytes. A SMALLINT uses 2 bytes. A TINYINT uses 1 byte. If you have a column that stores values between 0 and 100, a TINYINT is sufficient. Using a BIGINT instead wastes 7 bytes per row. Across a billion rows, that is 7 gigabytes of wasted storage. That is not just a storage cost. It is also a performance cost. Larger types consume more memory during processing. They move more slowly through the network during shuffles. They compress less effectively. They can slow down every query that touches the column.

When you choose a type that is too small, you risk overflow. If you use a TINYINT for a counter that reaches 128, the write fails or the value wraps around. If you use a SMALLINT for a year that exceeds 32,767, the write fails. If you use an INT for a row count that exceeds 2.1 billion, the write fails. These errors can be difficult to diagnose, especially if they occur intermittently. Choosing a type that has room for growth avoids these problems.

When you choose a type that does not match the data's nature, you risk incorrect results. If you use a DOUBLE for money, you get rounding errors. If you use a STRING for dates, you cannot use date functions. If you use an INT for a percentage, you lose the fractional part. Matching the type to the data's nature ensures that operations behave as expected.

### How to match the type to the data

Start by profiling your data. Use the profiling techniques described earlier to understand the range, distribution, and null percentage of each column. Look at the minimum and maximum values. Look at the distinct count. Look at the frequency of values. Use this information to choose a type that comfortably covers the observed range.

Consider the nature of the data. Is it a whole number? Use an integral type. Is it a monetary amount? Use a decimal type. Is it a measurement? Use a floating-point type. Is it a date? Use a date type. Is it a timestamp? Use a timestamp type. Is it text? Use a string type. Is it a collection? Use a complex type.

Consider future growth. A column that starts small may grow over time. A counter that starts at zero may reach millions. A year column may need to store years beyond 9999. Choose a type that has room for growth. When in doubt, choose the next larger type. The cost of extra storage is usually less than the cost of an overflow error.

Consider the operations you will perform. If you will perform arithmetic, choose a numeric type that supports the required precision. If you will perform date arithmetic, choose a date or timestamp type. If you will perform string manipulation, choose a string type. If you will perform comparisons, choose a type that supports the required ordering.

### Code examples

The following SQL example shows how to choose the right type for each column based on the data's nature and range. Each line is commented.

```sql
-- Create a table named orders.
-- The order_id column uses INT because order IDs typically do not exceed 2.1 billion.
-- If order IDs may exceed 2.1 billion, use BIGINT instead.
-- The status_code column uses TINYINT because status codes are typically small (0 to 127).
-- If more than 127 statuses are possible, use SMALLINT or INT.
-- The total_items column uses SMALLINT because typical order sizes fit in 32,767.
-- If order sizes may exceed 32,767, use INT.
-- The amount column uses DECIMAL(10,2) because it is a monetary amount.
-- DECIMAL(10,2) allows values up to 99,999,999.99.
-- The tax_rate column uses DECIMAL(5,4) because tax rates need four decimal places.
-- The order_date column uses DATE because it is a calendar date.
-- The created_at column uses TIMESTAMP because it is an event time with time zone.
CREATE TABLE orders (
    order_id INT,
    status_code TINYINT,
    total_items SMALLINT,
    amount DECIMAL(10,2),
    tax_rate DECIMAL(5,4),
    order_date DATE,
    created_at TIMESTAMP
);
```

The following PySpark example shows the same schema and writes a DataFrame to a table. Each line is commented.

```python
# Import the required types.
from pyspark.sql.types import StructType, StructField, IntegerType, ByteType, ShortType, DecimalType, DateType, TimestampType
from decimal import Decimal
from datetime import date, datetime

# Define the schema.
# IntegerType corresponds to INT.
# ByteType corresponds to TINYINT.
# ShortType corresponds to SMALLINT.
# DecimalType(10,2) corresponds to DECIMAL(10,2).
# DecimalType(5,4) corresponds to DECIMAL(5,4).
# DateType corresponds to DATE.
# TimestampType corresponds to TIMESTAMP.
schema = StructType([
    StructField("order_id", IntegerType(), True),
    StructField("status_code", ByteType(), True),
    StructField("total_items", ShortType(), True),
    StructField("amount", DecimalType(10,2), True),
    StructField("tax_rate", DecimalType(5,4), True),
    StructField("order_date", DateType(), True),
    StructField("created_at", TimestampType(), True)
])

# Create a DataFrame with sample data.
data = [
    (1, 1, 10, Decimal("123.45"), Decimal("0.0825"), date(2026, 1, 15), datetime(2026, 1, 15, 10, 30, 0))
]

# Create the DataFrame.
df = spark.createDataFrame(data, schema)

# Write the DataFrame to a table.
df.write.saveAsTable("orders")
```

### Common mistakes

One common mistake is using BIGINT for all integer columns. This wastes storage and slows down queries. Use INT for most identifiers and counts. Use BIGINT only when the values may exceed 2.1 billion.

Another common mistake is using DOUBLE for all decimal columns. This causes rounding errors for money. Use DECIMAL for money. Use DOUBLE for scientific measurements.

Another common mistake is using STRING for all columns. This prevents type-specific operations and wastes storage. Use the appropriate type for each column.

Another common mistake is using DECIMAL with an unnecessarily large precision and scale. DECIMAL(38,18) uses more storage than DECIMAL(10,2). Use the smallest precision and scale that meet your requirements.

Another common mistake is using TINYINT for a counter that may exceed 127. Use SMALLINT or INT instead. Another mistake is using SMALLINT for a counter that may exceed 32,767. Use INT instead. Another mistake is using INT for a row count that may exceed 2.1 billion. Use BIGINT instead.

## Consider nullability

The second best practice is to consider nullability. If a column should never contain null values, document this constraint. While data types do not enforce nullability by default, you can add NOT NULL constraints to table definitions. Nullability is an important part of schema design. It affects data quality, query behavior, and performance.

### Why nullability matters

Nullability affects data quality. If a column should never be null but contains nulls, downstream consumers may encounter errors or incorrect results. For example, if a customer ID is null, joins may fail. If an amount is null, calculations may return null. If a date is null, date arithmetic may fail. Documenting and enforcing nullability prevents these problems.

Nullability affects query behavior. In SQL, null comparisons return unknown. This can lead to unexpected results. For example, `WHERE column = 'value'` does not return rows where column is null. You must use `WHERE column IS NULL` or `WHERE column IS NOT DISTINCT FROM 'value'`. Understanding nullability helps you write correct queries.

Nullability affects performance. Nullable columns require extra storage for null flags. They may also prevent certain optimizations. If a column is always populated, defining it as NOT NULL can improve performance and reduce storage.

Nullability affects schema evolution. If you add a new column to an existing table, it is nullable by default. Existing rows get null for the new column. If you want the column to be non-null, you must provide a default value or update existing rows. Understanding nullability helps you plan schema changes.

### How to consider nullability

Identify columns that should never be null. These are typically primary keys, foreign keys, and required attributes. For example, a customer ID should never be null. An order amount should never be null. A transaction date should never be null.

Identify columns that may be null. These are typically optional attributes. For example, a phone number may be null. A middle name may be null. A secondary email may be null. For these columns, allow nulls but document the behavior.

Add NOT NULL constraints to columns that should never be null. The following SQL example shows how to add NOT NULL constraints when creating a table. Each line is commented.

```sql
-- Create a table named customers.
-- The customer_id column is NOT NULL because every customer must have an ID.
-- The name column is NOT NULL because every customer must have a name.
-- The email column is nullable because some customers may not provide an email.
-- The phone_number column is nullable because some customers may not provide a phone number.
CREATE TABLE customers (
    customer_id INT NOT NULL,
    name STRING NOT NULL,
    email STRING,
    phone_number STRING
);
```

The following PySpark example shows how to define nullability in a schema and write a DataFrame to a table. Each line is commented.

```python
from pyspark.sql.types import StructType, StructField, IntegerType, StringType

# Define the schema.
# The third argument to StructField indicates whether the column is nullable.
# False means NOT NULL.
# True means nullable.
schema = StructType([
    StructField("customer_id", IntegerType(), False),
    StructField("name", StringType(), False),
    StructField("email", StringType(), True),
    StructField("phone_number", StringType(), True)
])

# Create a DataFrame with sample data.
data = [
    (1, "Alice", "alice@example.com", "555-1234"),
    (2, "Bob", None, None)
]

# Create the DataFrame.
df = spark.createDataFrame(data, schema)

# Write the DataFrame to a table.
df.write.saveAsTable("customers")
```

If you try to write a null value to a non-nullable column, the write fails. This enforces data quality. The following PySpark example shows what happens when you try to write a null to a non-nullable column. Each line is commented.

```python
# Create a DataFrame with a null value in a non-nullable column.
data = [(1, None, "alice@example.com", "555-1234")]

# Try to create the DataFrame.
# This will raise an error because the name column is not nullable.
try:
    df = spark.createDataFrame(data, schema)
    df.show()
except Exception as e:
    print(f"Error: {e}")
```

### Common mistakes

One common mistake is not defining NOT NULL constraints. If a column should never be null, define it as NOT NULL. This enforces data quality at the storage layer.

Another common mistake is defining NOT NULL constraints that are too strict. If a column may be null in some cases, do not define it as NOT NULL. This can cause writes to fail unexpectedly.

Another common mistake is not documenting nullability. If a column is nullable, document why. If a column is not nullable, document why. This helps other team members understand the schema.

Another common mistake is not handling nulls in queries. If a column is nullable, use IS NULL, IS NOT NULL, COALESCE, or IFNULL in your queries. Do not assume that the column always has a value.

Another common mistake is adding a NOT NULL column to an existing table without a default value. This fails if the table has existing rows. You must add the column as nullable, populate it, and then add the NOT NULL constraint. Alternatively, you can add the column with a default value.

## Validate types during ingestion

The third best practice is to validate types during ingestion. Cast incoming data to the target type early in your pipeline to catch type mismatches before they propagate. This is important because raw data often arrives as strings. It may contain invalid values, inconsistent formats, and unexpected characters. If you do not validate types early, these problems can propagate through your pipeline and cause failures downstream.

### Why validate during ingestion

Validating during ingestion catches problems early. It is easier to fix a problem at the source than to trace it through multiple transformations. It prevents invalid data from entering your clean tables. It ensures that downstream consumers receive data that conforms to the expected schema. It also improves performance because the query optimizer can use the correct types for planning.

Validating during ingestion also helps with schema enforcement. Delta Lake enforces schema when you write to a table. If the incoming data does not match the schema, the write fails. By casting early, you ensure that the data matches the schema. You can also use try_cast to handle invalid values gracefully. You can route invalid records to a quarantine table.

### How to validate during ingestion

Use explicit casts in your ingestion logic. In SQL, use the CAST function. In PySpark, use the cast method. Use try_cast when you want to handle invalid values gracefully. Use try_to_date and try_to_timestamp when you need to parse specific formats.

The following SQL example shows how to cast during data loading. Each line is commented.

```sql
-- Cast during data loading.
-- The target_table has columns with specific types.
-- The staging_table has raw string values.
-- The CAST function converts the strings to the target types.
-- If a conversion fails, the query raises an error.
-- Use try_cast if you want to return null on failure.
INSERT INTO target_table
SELECT 
    -- Cast the raw ID to an integer.
    CAST(raw_id AS INT) AS id,
    -- Cast the raw amount to a decimal.
    CAST(raw_amount AS DECIMAL(10,2)) AS amount,
    -- Cast the raw date to a date.
    CAST(raw_date AS DATE) AS transaction_date
FROM staging_table;
```

The following PySpark example shows the same operation. Each line is commented.

```python
from pyspark.sql.functions import col

# Read the staging table.
staging_df = spark.read.table("staging_table")

# Cast the columns to the target types.
target_df = staging_df.select(
    # Cast the raw ID to an integer.
    col("raw_id").cast("int").alias("id"),
    # Cast the raw amount to a decimal.
    col("raw_amount").cast("decimal(10,2)").alias("amount"),
    # Cast the raw date to a date.
    col("raw_date").cast("date").alias("transaction_date")
)

# Write the casted data to the target table.
target_df.write.saveAsTable("target_table")
```

### Handling invalid values

When you cast during ingestion, some values may be invalid. For example, a string that contains letters cannot be cast to an integer. A string that contains an invalid date cannot be cast to a date. You have several options for handling invalid values. You can fail the pipeline. You can drop the invalid records. You can quarantine the invalid records. You can replace invalid values with defaults.

The following SQL example shows how to use try_cast to identify invalid records and route them to a quarantine table. Each line is commented.

```sql
-- Insert valid records into the target table.
INSERT INTO target_table
SELECT
    try_cast(raw_id AS INT) AS id,
    try_cast(raw_amount AS DECIMAL(10,2)) AS amount,
    try_cast(raw_date AS DATE) AS transaction_date
FROM staging_table
WHERE try_cast(raw_id AS INT) IS NOT NULL
  AND try_cast(raw_amount AS DECIMAL(10,2)) IS NOT NULL
  AND try_cast(raw_date AS DATE) IS NOT NULL;

-- Insert invalid records into the quarantine table.
INSERT INTO quarantine_table
SELECT
    raw_id,
    raw_amount,
    raw_date,
    current_timestamp() AS quarantined_at,
    'Type validation failed' AS reason
FROM staging_table
WHERE try_cast(raw_id AS INT) IS NULL
   OR try_cast(raw_amount AS DECIMAL(10,2)) IS NULL
   OR try_cast(raw_date AS DATE) IS NULL;
```

The following PySpark example shows the same operation using filters. Each line is commented.

```python
from pyspark.sql.functions import col, current_timestamp, lit

# Read the staging table.
staging_df = spark.read.table("staging_table")

# Cast the columns using try_cast.
# try_cast returns null on failure.
casted_df = staging_df.select(
    expr("try_cast(raw_id as int)").alias("id"),
    expr("try_cast(raw_amount as decimal(10,2))").alias("amount"),
    expr("try_cast(raw_date as date)").alias("transaction_date")
)

# Select valid records.
valid_df = casted_df.filter(
    col("id").isNotNull() & col("amount").isNotNull() & col("transaction_date").isNotNull()
)

# Select invalid records.
invalid_df = casted_df.filter(
    col("id").isNull() | col("amount").isNull() | col("transaction_date").isNull()
).withColumn("quarantined_at", current_timestamp()).withColumn("reason", lit("Type validation failed"))

# Write valid records.
valid_df.write.saveAsTable("target_table")

# Write invalid records.
invalid_df.write.saveAsTable("quarantine_table")
```

### Common mistakes

One common mistake is not casting during ingestion. If you do not cast, the data remains as strings. This can cause problems downstream. Always cast to the target type early.

Another common mistake is using implicit casts. Implicit casts can succeed silently even when data is lost. For example, casting a decimal to an integer may truncate the fractional part. Use explicit casts to make your intentions clear.

Another common mistake is not handling invalid values. If you use cast and a value is invalid, the query fails. Use try_cast to handle invalid values gracefully. Route them to a quarantine table.

Another common mistake is not testing with edge cases. Test empty strings, whitespace, special characters, and boundary values. Verify that your casts behave as expected.

## Use explicit casts when converting types

The fourth best practice is to use explicit casts when converting types. Implicit conversions can succeed silently even when data is lost. Explicit casts make your intentions clear and help identify problems during testing. Explicit casts also give you control over the conversion behavior.

### Why explicit casts matter

Explicit casts make your intentions clear. When you write CAST(column AS INT), you are saying that you expect the column to contain values that can be converted to integers. This is self-documenting. It helps other team members understand the code.

Explicit casts help identify problems during testing. If a value cannot be converted, the cast fails with a clear error. This makes it easy to find and fix the problem. Implicit casts may succeed silently, hiding the problem until later.

Explicit casts give you control. You can choose the target type. You can choose whether to fail or return null on error. You can choose the format for date and timestamp parsing. Implicit casts use the engine's default behavior, which may not be what you want.

Explicit casts are portable. Different systems may have different implicit conversion rules. Explicit casts are more likely to behave consistently across systems.

### How to use explicit casts

Use CAST in SQL and cast in PySpark. Use try_cast when you want to return null on failure. Use try_to_date and try_to_timestamp when you need to parse specific formats.

The following SQL example shows explicit casts. Each line is commented.

```sql
-- Use explicit casts.
SELECT
    -- Explicitly cast the string to an integer.
    CAST('123' AS INT) AS int_value,
    -- Explicitly cast the string to a decimal.
    CAST('123.45' AS DECIMAL(10,2)) AS decimal_value,
    -- Explicitly cast the string to a date.
    CAST('2026-01-15' AS DATE) AS date_value,
    -- Explicitly cast the string to a timestamp.
    CAST('2026-01-15 10:30:00' AS TIMESTAMP) AS timestamp_value,
    -- Use try_cast to return null on failure.
    try_cast('abc' AS INT) AS invalid_int,
    -- Use try_to_date to parse a specific format.
    try_to_date('15/01/2026', 'dd/MM/yyyy') AS parsed_date;
```

The following PySpark example shows explicit casts. Each line is commented.

```python
from pyspark.sql.functions import col, expr

# Read a DataFrame.
df = spark.read.table("staging_table")

# Use explicit casts.
df_casted = df.select(
    # Explicitly cast the string to an integer.
    col("raw_id").cast("int").alias("int_value"),
    # Explicitly cast the string to a decimal.
    col("raw_amount").cast("decimal(10,2)").alias("decimal_value"),
    # Explicitly cast the string to a date.
    col("raw_date").cast("date").alias("date_value"),
    # Explicitly cast the string to a timestamp.
    col("raw_timestamp").cast("timestamp").alias("timestamp_value"),
    # Use try_cast to return null on failure.
    expr("try_cast(raw_id as int)").alias("invalid_int"),
    # Use to_date to parse a specific format.
    expr("to_date(raw_date, 'dd/MM/yyyy')").alias("parsed_date")
)

# Show the results.
df_casted.show()
```

### Common mistakes

One common mistake is relying on implicit casts. Implicit casts can succeed silently even when data is lost. Use explicit casts to make your intentions clear.

Another common mistake is not handling cast failures. If you use cast and a value is invalid, the query fails. Use try_cast to handle invalid values gracefully.

Another common mistake is not specifying the format for date and timestamp parsing. Different systems use different formats. Use try_to_date and try_to_timestamp with explicit format strings to avoid ambiguity.

Another common mistake is casting to the wrong type. For example, casting a decimal to an integer truncates the fractional part. If you need to preserve the fractional part, cast to a decimal type instead. Always verify that the target type is correct.

Another common mistake is not testing casts with edge cases. Test empty strings, whitespace, special characters, and boundary values. Verify that your casts behave as expected.

## How these practices work together

These four practices work together to create a robust type selection strategy. Matching the type to the data's nature and range ensures that you choose the right type. Considering nullability ensures that you define the right constraints. Validating types during ingestion ensures that you catch problems early. Using explicit casts ensures that your conversions are clear and controlled.

When you combine these practices, you build pipelines where data types serve as a form of documentation and validation. The schema documents the expected structure and types. The NOT NULL constraints document which columns are required. The casts document the expected conversions. The quarantine table documents which records failed validation. Together, these artifacts make your pipeline easier to understand, easier to maintain, and more reliable.

## Documenting your type choices

Documentation is an important part of type selection. When you choose a type for a column, document why. When you add a NOT NULL constraint, document why. When you use a cast, document why. When you route invalid records to quarantine, document why. This documentation helps other team members understand the schema. It also helps with auditing and compliance.

You can document your choices in several ways. You can add comments to your SQL DDL. You can add comments to your PySpark code. You can maintain a data dictionary. You can use table and column comments in Unity Catalog. The following SQL example shows how to add comments to a table and its columns. Each line is commented.

```sql
-- Create a table with comments.
CREATE TABLE orders (
    order_id INT NOT NULL COMMENT 'Unique identifier for the order',
    status_code TINYINT COMMENT 'Status code: 0=pending, 1=processing, 2=shipped, 3=delivered',
    total_items SMALLINT COMMENT 'Total number of items in the order',
    amount DECIMAL(10,2) COMMENT 'Total amount in USD, exact to 2 decimal places',
    tax_rate DECIMAL(5,4) COMMENT 'Tax rate as a decimal, e.g., 0.0825 for 8.25%',
    order_date DATE COMMENT 'Date the order was placed',
    created_at TIMESTAMP COMMENT 'Timestamp when the order record was created'
) COMMENT 'Table containing order transactions';
```

## Testing your type choices

Testing is essential for validating your type choices. Create test cases that cover the following scenarios. Test minimum and maximum values for each type. Test values just outside the range. Test null values. Test empty strings. Test whitespace. Test special characters. Test boundary values for decimal precision and scale. Test date and timestamp parsing with different formats. Test timezone conversions. Verify that valid values are accepted and invalid values are handled as expected.

The following SQL example tests boundary values for a TINYINT column. Each line is commented.

