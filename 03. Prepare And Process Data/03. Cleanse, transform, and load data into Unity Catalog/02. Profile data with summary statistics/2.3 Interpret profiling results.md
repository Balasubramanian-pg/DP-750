# Interpret profiling results

Profiling generates metrics that help you assess data quality and identify issues requiring attention. These metrics are not just numbers. They are signals. They tell you whether your data is complete, unique, within expected bounds, and stable over time. They help you answer questions such as: Are there missing values? Are there duplicate identifiers? Are there outliers? Has the distribution of values changed since yesterday? By interpreting these metrics correctly, you can design cleansing rules, validation checks, and monitoring alerts that keep your data reliable.

Data profiling in Unity Catalog produces two main metric tables. The profile metrics table contains summary statistics for each column. The drift metrics table contains statistical tests that quantify how much distributions have changed over time. Together, these tables give you a complete picture of your data quality. The exact schema of these tables depends on your Databricks Runtime version and your profiling configuration. In general, they contain columns such as table name, column name, metric name, metric value, and timestamp. You can query them with SQL or PySpark. You can join them with other metadata tables. You can build dashboards and alerts on top of them.

## Key metrics to examine

The profile metrics table contains statistics for each column. The following table explains each metric, what it reveals, and how to interpret it.

| Metric | What it reveals | How to interpret |
| --- | --- | --- |
| `count` and `num_nulls` | Data completeness. High null percentages might indicate ingestion issues. | `count` is the number of non-null values. `num_nulls` is the number of null values. The total number of rows is `count + num_nulls`. A high `num_nulls` relative to the total indicates missing data. |
| `distinct_count` | Cardinality. Unexpected values might suggest data quality problems. | For an identifier column, `distinct_count` should equal `count` if the identifier is unique. If it is lower, there are duplicates. For a categorical column, `distinct_count` tells you how many categories exist. An unexpected increase may indicate new categories or dirty data. |
| `min`, `max`, `avg`, `stddev` | Distribution characteristics. Outliers or skewed distributions. | `min` and `max` show the range. Values outside expected bounds are suspicious. `avg` and `stddev` describe the center and spread. A large `stddev` relative to `avg` indicates high variability. A `min` below zero for an amount column may indicate a data entry error. |
| `frequent_items` | Most common values. Helps identify dominant categories or duplicates. | This metric lists the most frequent values and their counts. It helps you spot default values, placeholder values, or unexpected dominant categories. For example, if 90 percent of records have the same email address, that is a problem. |
| `quantiles` | Value distribution. Useful for detecting skewness. | Quantiles divide the data into equal-sized groups. The median is the 50th percentile. The interquartile range is the difference between the 75th and 25th percentiles. Comparing the median to the mean reveals skewness. If the median is far from the mean, the distribution is skewed. |

These metrics are computed for each column. You can query them to find columns that need attention. For example, you can find columns with more than 5 percent nulls. You can find columns where the distinct count is unexpectedly low or high. You can find columns where the minimum or maximum is outside a valid range. You can find columns with a skewed distribution.

## Detect data quality issues

When you examine profiling results, look for these common indicators. Each indicator suggests a specific type of data quality problem. You can then design cleansing or validation rules to address it.

High null percentages in columns that should have values. For example, if a customer table has a `phone_number` column and 40 percent of records have null phone numbers, that may indicate an ingestion issue or a problem in the source system. You might decide to drop records with null phone numbers, fill them with a default, or flag them for review.

Unexpected distinct counts, such as unique identifiers that are not unique. If a `customer_id` column has a `distinct_count` that is less than the total `count`, there are duplicate customer IDs. This can cause incorrect joins and aggregations. You need to deduplicate the data. Similarly, if a categorical column has an unexpectedly high distinct count, it may contain dirty values that should be standardized.

Value ranges outside expected bounds, like negative amounts where only positives are valid. If an `amount` column has a `min` value of -500, that is likely an error. You might add a CHECK constraint or an expectation to reject negative amounts. You might also investigate the source system to find why negative values are appearing.

Distribution changes over time, which can indicate data drift. If the average transaction amount has increased significantly, or if the distribution of customer ages has shifted, the data may be drifting. This can affect machine learning models and business reports. You should monitor drift metrics to detect these changes early.

## Drift metrics table

The drift metrics table calculates statistical tests that quantify how much distributions have changed. For numeric columns, it uses the Kolmogorov-Smirnov (KS) test. For categorical columns, it uses the chi-squared test. These tests compare the distribution of a column in a current time window to a baseline or to a previous time window.

The KS test produces a statistic between 0 and 1. A value of 0 means the distributions are identical. A value of 1 means they are completely different. In practice, a KS statistic above 0.1 or 0.2 may indicate meaningful drift. The test also produces a p-value. A low p-value (typically below 0.05) indicates that the difference is statistically significant. You should look at both the statistic and the p-value. A large statistic with a low p-value is strong evidence of drift.

The chi-squared test produces a test statistic and a p-value. The statistic measures how much the observed frequencies differ from the expected frequencies. A larger statistic indicates a greater difference. The p-value tells you whether the difference is statistically significant. A low p-value indicates significant drift. For categorical columns, you should also look at which categories are driving the drift.

You can query the drift metrics table to find columns with high drift. The following SQL example shows how to query drift metrics. Each line is commented.

```sql
-- Query the drift metrics table for high drift.
-- Assume the table has columns: column_name, metric_name, metric_value, window_start, window_end.
-- The metric_name values include 'ks_statistic', 'ks_p_value', 'chi_squared_statistic', 'chi_squared_p_value'.
SELECT
    column_name,
    metric_name,
    metric_value,
    window_start,
    window_end
FROM
    catalog.schema.drift_metrics
WHERE
    -- Filter for KS statistic or chi-squared statistic.
    metric_name IN ('ks_statistic', 'chi_squared_statistic')
    -- Filter for values above a threshold.
    -- For KS, 0.1 is a common threshold.
    -- For chi-squared, the threshold depends on degrees of freedom, but a large value indicates drift.
    AND metric_value > 0.1
ORDER BY
    metric_value DESC;
```

This query returns columns with drift above the threshold. You can then investigate those columns. You might look at the profile metrics table to see how the distribution changed. You might look at sample records. You might talk to the source system owner.

## Querying profile metrics to find issues

You can write SQL queries to find specific data quality issues. The following examples show how to find high null percentages, unexpected distinct counts, and out-of-range values. Each query is commented.

```sql
-- Find columns with more than 5 percent nulls.
-- First, get the total count and null count for each column.
WITH counts AS (
    SELECT
        column_name,
        MAX(CASE WHEN metric_name = 'count' THEN metric_value END) AS total_count,
        MAX(CASE WHEN metric_name = 'num_nulls' THEN metric_value END) AS null_count
    FROM
        catalog.schema.profile_metrics
    GROUP BY
        column_name
)
SELECT
    column_name,
    total_count,
    null_count,
    -- Compute the null percentage.
    (null_count / total_count) * 100 AS null_percent
FROM
    counts
WHERE
    -- Filter for columns with more than 5 percent nulls.
    (null_count / total_count) * 100 > 5
ORDER BY
    null_percent DESC;
```

```sql
-- Find columns where the distinct count is less than the total count.
-- This indicates potential duplicates.
WITH counts AS (
    SELECT
        column_name,
        MAX(CASE WHEN metric_name = 'count' THEN metric_value END) AS total_count,
        MAX(CASE WHEN metric_name = 'distinct_count' THEN metric_value END) AS distinct_count
    FROM
        catalog.schema.profile_metrics
    GROUP BY
        column_name
)
SELECT
    column_name,
    total_count,
    distinct_count,
    -- Compute the difference.
    total_count - distinct_count AS duplicate_count
FROM
    counts
WHERE
    -- Filter for columns where distinct count is less than total count.
    distinct_count < total_count
ORDER BY
    duplicate_count DESC;
```

```sql
-- Find columns where the minimum value is below zero.
-- This is useful for amount columns that should be positive.
WITH mins AS (
    SELECT
        column_name,
        metric_value AS min_value
    FROM
        catalog.schema.profile_metrics
    WHERE
        metric_name = 'min'
)
SELECT
    column_name,
    min_value
FROM
    mins
WHERE
    min_value < 0
ORDER BY
    min_value ASC;
```

These queries help you quickly identify columns that need cleansing or validation. You can schedule them to run regularly. You can set up alerts when the results exceed thresholds.

## PySpark example for interpreting profiling results

You can also use PySpark to read the metric tables and compute summaries. The following example reads the profile metrics table, filters for null counts, and computes the null percentage. Each line is commented.

```python
# Import the required functions.
from pyspark.sql.functions import col, max as _max, when

# Read the profile metrics table.
profile_metrics = spark.read.table("catalog.schema.profile_metrics")

# Pivot the metrics so that each column has one row with count and num_nulls.
# The pivot operation turns metric_name values into columns.
# The aggregation uses max to pick the single value for each metric.
pivoted = profile_metrics.groupBy("column_name").pivot("metric_name").agg(_max("metric_value"))

# Compute the null percentage.
# The count column is the number of non-null values.
# The num_nulls column is the number of null values.
# The total is count + num_nulls.
# The null percentage is (num_nulls / total) * 100.
pivoted = pivoted.withColumn(
    "total_count",
    col("count") + col("num_nulls")
).withColumn(
    "null_percent",
    (col("num_nulls") / col("total_count")) * 100
)

# Filter for columns with more than 5 percent nulls.
high_nulls = pivoted.filter(col("null_percent") > 5).orderBy(col("null_percent").desc())

# Show the results.
high_nulls.show()
```

This code gives you a DataFrame of columns with high null percentages. You can write it to a table, create a view, or use it in a dashboard. You can also extend it to check other metrics.

## Best practices for interpreting profiling results

Establish baselines. Before you can detect anomalies, you need to know what normal looks like. Profile your data regularly and record the results. Use the historical data to establish baselines for each metric.

Monitor trends. A single metric value may not be meaningful. Look at how metrics change over time. A gradual increase in null percentage may indicate a slow degradation of data quality. A sudden spike may indicate a specific event.

Set thresholds. Define acceptable ranges for each metric. For example, null percentage should be below 5 percent. Distinct count for an identifier should equal the total count. Minimum value for an amount should be zero or greater. When a metric crosses a threshold, trigger an alert.

Investigate anomalies. When a metric is outside the expected range, investigate. Look at the profile metrics for related columns. Look at sample records. Talk to the source system owner. Find the root cause.

Integrate with expectations. Use the insights from profiling to design expectations. For example, if profiling shows that 10 percent of records have null emails, you might add an expectation to drop or warn on null emails. If profiling shows that amounts can be negative, you might add a CHECK constraint to reject negative amounts.

Document your findings. Keep a record of the issues you find and the actions you take. This helps you track progress and avoid repeating the same investigations.

Review regularly. Data changes. What was normal last month may not be normal this month. Review your profiling results regularly and update your baselines and thresholds.

## Summary

Profiling generates metrics that help you assess data quality and identify issues requiring attention. The profile metrics table contains statistics for each column, including count, num_nulls, distinct_count, min, max, avg, stddev, frequent_items, and quantiles. These metrics reveal completeness, cardinality, distribution characteristics, dominant categories, and skewness. The drift metrics table contains statistical tests such as the Kolmogorov-Smirnov test for numeric columns and the chi-squared test for categorical columns. These tests quantify how much distributions have changed over time. When you examine profiling results, look for high null percentages, unexpected distinct counts, value ranges outside expected bounds, and distribution changes. Use SQL or PySpark to query the metric tables and find columns that need attention. Establish baselines, monitor trends, set thresholds, investigate anomalies, integrate with expectations, document your findings, and review regularly. By interpreting profiling results correctly, you can design appropriate cleansing and validation rules for your data pipelines and maintain high data quality in your Unity Catalog tables.
