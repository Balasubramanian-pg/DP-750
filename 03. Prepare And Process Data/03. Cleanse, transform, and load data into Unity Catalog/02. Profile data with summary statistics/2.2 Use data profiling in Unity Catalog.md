# Use data profiling in Unity Catalog

Beyond SQL commands, Azure Databricks provides data quality monitoring in Unity Catalog. This is an umbrella term that covers two distinct capabilities: anomaly detection and data profiling. Both help you monitor the quality of your data, but they serve different purposes and operate at different levels of granularity. Understanding the difference is essential for designing an effective data quality strategy. Anomaly detection monitors all tables in a schema automatically. It analyzes historical patterns to evaluate each table's freshness and completeness. Freshness means how recently the table was updated. Completeness means whether the expected number of rows arrived. You enable anomaly detection once at the schema level in Catalog Explorer. Azure Databricks then handles the rest using intelligent scanning. You do not need to configure each table individually. This makes anomaly detection ideal for broad, automated coverage across all your tables. It acts as an early-warning system. If a table stops updating or if the row count drops unexpectedly, anomaly detection can alert you.

Data profiling, on the other hand, provides deep per-table statistical analysis. It tracks distributions, null percentages, drift metrics, and model performance over time. You configure data profiling individually for each table. You choose the profile type, the granularity, and the schedule. Data profiling is more detailed than anomaly detection. It gives you historical trends and detailed statistics. It is best used for your most critical tables where you need in-depth monitoring. For data engineering work focused on cleansing and quality, you will use both. Anomaly detection gives you broad coverage. Data profiling gives you deep insight. Together they form a comprehensive data quality monitoring solution.

## Understand profile types

Data profiling supports three analysis types. Each type is suited to different scenarios. The three types are Snapshot, Time series, and Inference. For data engineering tasks focused on data quality, the snapshot and time series profiles are most relevant. The inference profile is used for machine learning model inference tables.

A Snapshot profile is used for general-purpose tables. It computes metrics over the entire table with each refresh. This means that every time the profile runs, it scans the entire table and computes statistics such as count, mean, standard deviation, minimum, maximum, null count, distinct count, and quantiles. The snapshot profile does not track changes over time. It gives you a point-in-time view of the table. It is useful when you want to monitor the overall quality of a table and you do not need to see how metrics change from day to day. It is also the simplest profile to configure. You can think of it as a comprehensive version of the `describe()` method or the `ANALYZE TABLE` command, but with more metrics and with historical storage of results.

A Time series profile is used for tables that have timestamp columns. It tracks metrics across time windows to detect trends. Instead of computing a single set of metrics for the entire table, it computes metrics for each time window. For example, you might configure a time series profile with a daily granularity. The profile will compute metrics for each day. You can then see how the metrics change over time. You can detect trends, seasonality, and anomalies. You can see if null percentages are increasing. You can see if the distribution of a column is shifting. You can see if the row count is growing or shrinking. Time series profiles are more powerful than snapshot profiles because they give you a historical view. They are also more expensive because they require scanning the table multiple times or using a time-based partition. You should use time series profiles for tables where time is an important dimension and where you need to monitor changes over time.

An Inference profile is used for ML model inference tables. It monitors model inputs, predictions, and accuracy over time. This profile type is specialized for machine learning. It helps you detect model drift, data drift, and concept drift. It tracks the distribution of input features and the distribution of predictions. It also tracks accuracy metrics if ground truth is available. Inference profiles are essential for production machine learning systems. They help you ensure that your models continue to perform well over time. For data engineering tasks focused on data quality, you may not need inference profiles unless you are working with ML inference tables. The snapshot and time series profiles are the most relevant for general data engineering.

## Create a profile using the UI

You can create a data profiling monitor using the Catalog Explorer UI. The UI provides a guided experience. You do not need to write code. You can configure the profile type, granularity, and schedule. The following steps describe the process. First, navigate to your table in Catalog Explorer. You can search for the table by name or browse the catalog and schema. Second, select the Quality tab. This tab shows the data quality monitoring status for the table. If anomaly detection is not enabled for the schema, you will see an Enable button. If anomaly detection is already enabled, you will see a Configure button. Third, select Enable or Configure. This opens the Data Quality Monitoring dialog. Fourth, in the Data Quality Monitoring dialog, find the Data profiling field. Select Configure. This opens the data profiling configuration. Fifth, choose your profile type. You can choose Snapshot, Time series, or Inference. For data engineering, choose Snapshot or Time series. Then configure options like granularity and scheduling. Granularity determines the time window for time series profiles. For example, you can choose daily, hourly, or weekly. Scheduling determines how often the profile refreshes. You can choose a manual schedule or an automatic schedule. After you configure the options, save the profile. The profile will run according to the schedule. It will generate two metric tables. The first is a profile metrics table. This table contains summary statistics. The second is a drift metrics table. This table tracks distribution changes over time. You can query these tables to monitor data quality. You can also view the results in the UI.

## Create a profile using the API

For programmatic access, you can use the Databricks SDK. This allows you to create, update, and refresh profiles using Python code. You can integrate profile creation into your CI/CD pipelines. You can also automate the creation of profiles for many tables. Before you can use the SDK, you need to install or upgrade it. The following command installs the SDK. It requires version 0.68.0 or later.

```python
%pip install "databricks-sdk>=0.68.0"
```

This command uses the `%pip` magic in a Databricks notebook. It installs the SDK from PyPI. After installation, you can import the SDK and create a profile. The following code creates a snapshot profile for a table. Each line is commented to explain what it does.

```python
# Import the WorkspaceClient class from the Databricks SDK.
# WorkspaceClient provides a programmatic interface to the Databricks workspace.
from databricks.sdk import WorkspaceClient

# Import the Monitor, DataProfilingConfig, and SnapshotConfig classes.
# Monitor represents a data quality monitor.
# DataProfilingConfig represents the configuration for data profiling.
# SnapshotConfig represents the configuration for a snapshot profile.
from databricks.sdk.service.dataquality import Monitor, DataProfilingConfig, SnapshotConfig

# Create a WorkspaceClient instance.
# This uses the default authentication mechanism.
# In a Databricks notebook, authentication is automatic.
w = WorkspaceClient()

# Retrieve the table ID and schema ID required by the API.
# The API requires object IDs, not just names.
# The tables.get method retrieves metadata for a table by its full name.
# The full name is in the format catalog.schema.table.
table = w.tables.get(full_name="main.sales.transactions")

# The schemas.get method retrieves metadata for a schema by its full name.
# The full name is in the format catalog.schema.
schema = w.schemas.get(full_name="main.sales")

# Create the monitor using the data_quality.create_monitor method.
# The monitor parameter is a Monitor object.
# The object_type is "table".
# The object_id is the table ID.
# The data_profiling_config is a DataProfilingConfig object.
# The output_schema_id is the schema ID where the metric tables will be created.
# The assets_dir is the workspace directory where monitoring assets will be stored.
# The snapshot parameter is a SnapshotConfig object, which configures a snapshot profile.
w.data_quality.create_monitor(
    monitor=Monitor(
        object_type="table",
        object_id=table.table_id,
        data_profiling_config=DataProfilingConfig(
            output_schema_id=schema.schema_id,
            assets_dir="/Workspace/Users/user@example.com/monitoring",
            snapshot=SnapshotConfig()
        )
    )
)
```

This code creates a snapshot profile for the table `main.sales.transactions`. It stores the metric tables in the schema `main.sales`. It stores the monitoring assets in the workspace directory `/Workspace/Users/user@example.com/monitoring`. The `SnapshotConfig` object is empty because there are no additional options for a snapshot profile. For a time series profile, you would use a different config object and specify the timestamp column and granularity.

After you create the profile, you can refresh it to update the metrics. The following code refreshes the profile. Each line is commented.

```python
# Import the Refresh class from the Databricks SDK.
from databricks.sdk.service.dataquality import Refresh

# Create a refresh using the data_quality.create_refresh method.
# The object_type is "table".
# The object_id is the table ID.
# The refresh parameter is a Refresh object.
# The Refresh object specifies the object type and object ID.
# This triggers an immediate refresh of the profile.
w.data_quality.create_refresh(
    object_type="table",
    object_id=table.table_id,
    refresh=Refresh(object_type="table", object_id=table.table_id)
)
```

This code triggers an immediate refresh. The refresh runs asynchronously. You can check the status using the SDK. You can also schedule refreshes to run automatically. The SDK provides methods to list monitors, get monitor details, update monitors, and delete monitors. You can use these methods to manage your profiles programmatically.

## Understanding the metric tables

When you create a data profiling monitor, it generates two metric tables. The first is the profile metrics table. This table contains summary statistics for each column. The statistics depend on the profile type. For a snapshot profile, the table contains one row per column with metrics such as count, mean, standard deviation, minimum, maximum, null count, distinct count, and quantiles. For a time series profile, the table contains one row per column per time window. This allows you to track metrics over time. The second table is the drift metrics table. This table tracks distribution changes over time. It compares the distribution of a column in the current time window to a baseline or to a previous time window. It computes drift metrics such as population stability index (PSI) or Kullback-Leibler divergence. These metrics help you detect data drift. You can query these tables using SQL. You can join them with other tables. You can create dashboards and alerts. You can also view the metrics in the Catalog Explorer UI.

## Best practices for data profiling in Unity Catalog

Use anomaly detection for broad coverage. Enable it at the schema level. It will automatically monitor all tables in the schema. This gives you an early-warning system. You do not need to configure each table individually.

Use data profiling for critical tables. Configure snapshot or time series profiles for the tables that matter most. These are the tables that drive your most important analytics and machine learning models.

Choose the right profile type. Use snapshot for general-purpose tables. Use time series for tables with timestamp columns where you need to track trends. Use inference for ML model inference tables.

Configure a reasonable schedule. Do not refresh too frequently. Refreshing a profile scans the table. This can be expensive. Choose a schedule that matches how often the data changes. For daily data, a daily refresh is sufficient. For hourly data, an hourly refresh may be needed.

Monitor the metric tables. Set up alerts when key metrics change. For example, alert when the null percentage increases beyond a threshold. Alert when the distinct count drops. Alert when drift metrics exceed a threshold.

Use the API for automation. Create profiles programmatically for many tables. Integrate profile creation into your data pipeline. This ensures that new tables are monitored automatically.

Review the profiles regularly. Check the metrics. Investigate anomalies. Update the profiles as your data and requirements change.
