# Generate summary statistics using SQL

Azure Databricks provides SQL commands that collect and display statistics about your tables. These statistics help the query optimizer choose efficient execution plans and give you insight into your data's characteristics. Summary statistics are not just a nice-to-have feature. They are a fundamental part of a performant and well-understood data platform. When you collect statistics, you are telling the query optimizer about the shape and distribution of your data. The optimizer uses this information to decide how to execute a query. For example, it may choose a broadcast join instead of a shuffle join if it knows that one side of the join is very small. It may choose a different join order if it knows that one table is much larger than another. It may choose a more efficient scan strategy if it knows the minimum and maximum values of a column. Without statistics, the optimizer must guess. Guesses can lead to slow queries, excessive resource consumption, and frustrated users.

Statistics also help you understand your data. They reveal null counts, distinct value counts, minimum and maximum values, average column lengths, and more. These metrics are useful for data profiling. They help you identify data quality issues. They help you understand the distribution of your data. They help you design better schemas and better queries. They help you detect data drift over time. In short, summary statistics are valuable for both performance and insight.

## Collect statistics with ANALYZE TABLE

The `ANALYZE TABLE` command computes statistics for a table or specific columns. These statistics include row counts, column-level metrics like minimum and maximum values, null counts, and distinct value counts. The command is part of Delta Lake and Unity Catalog. It works on managed and external tables. It is available in SQL and in PySpark. You can run it manually or let predictive optimization run it automatically for Unity Catalog managed tables.

The basic syntax of `ANALYZE TABLE` is simple. You specify the table name and the `COMPUTE STATISTICS` clause. You can optionally specify `FOR COLUMNS` followed by a list of column names, or `FOR ALL COLUMNS`. The following SQL example shows the three common forms. Each line is commented to explain what it does.

```sql
-- Collect basic table statistics (row count and size)
-- This computes table-level statistics such as the number of rows and the total size in bytes.
-- It does not compute column-level statistics.
-- The optimizer uses these statistics for basic planning decisions.
ANALYZE TABLE sales.transactions COMPUTE STATISTICS;

-- Collect statistics for specific columns
-- This computes column-level statistics for the listed columns.
-- Column-level statistics include minimum value, maximum value, number of nulls, distinct count, average column length, and maximum column length.
-- You should analyze columns that are frequently used in filters, joins, and aggregations.
-- In this example, we analyze transaction_id, amount, and customer_id.
ANALYZE TABLE sales.transactions COMPUTE STATISTICS FOR COLUMNS 
    transaction_id, amount, customer_id;

-- Collect statistics for all columns
-- This computes column-level statistics for every column in the table.
-- This is more expensive than analyzing specific columns because it scans the entire table and computes metrics for each column.
-- It is useful when you are doing a full data profiling exercise or when you are not sure which columns are important.
-- For large tables, you may want to analyze only the most important columns to save time and resources.
ANALYZE TABLE sales.transactions COMPUTE STATISTICS FOR ALL COLUMNS;
```

The `ANALYZE TABLE` command is idempotent. You can run it multiple times. Each run recomputes the statistics and replaces the previous values. You should run it after bulk data loads or significant changes to ensure that the optimizer has accurate statistics. If statistics are stale, the optimizer may make poor decisions. For example, if a table has grown significantly but the statistics still show the old row count, the optimizer may choose a plan that is no longer efficient.

When you analyze a specific column, you get detailed metrics. You can view these metrics using the `DESC EXTENDED` command. The following SQL example shows how to view column-level statistics for the `amount` column in the `sales.transactions` table. Each line is commented.

```sql
-- View column-level statistics for the amount column.
-- The DESC EXTENDED command displays metadata and statistics for the specified column.
-- The output includes the minimum value, maximum value, number of nulls, distinct count, average column length, and maximum column length.
-- These metrics help you understand the distribution of values in the column.
-- They also help the query optimizer estimate the cost of operations that involve this column.
DESC EXTENDED sales.transactions amount;
```

The output of `DESC EXTENDED` for a column typically includes the following fields. The exact field names may vary depending on the Databricks Runtime version. The `data_type` field shows the data type of the column. The `comment` field shows any comment associated with the column. The `min` field shows the minimum value. The `max` field shows the maximum value. The `num_nulls` field shows the number of null values. The `distinct_count` field shows the number of distinct values. The `avg_col_len` field shows the average column length in bytes. The `max_col_len` field shows the maximum column length in bytes. These metrics are computed from the data. They are stored in the Delta transaction log or in the Unity Catalog metadata. They are used by the query optimizer.

## View statistics with DESCRIBE TABLE

The `DESCRIBE TABLE EXTENDED` command displays collected statistics alongside table metadata. This command is useful when you want to see both the schema and the statistics in one place. It shows the table's columns, data types, comments, and statistics. It also shows table properties, location, and other metadata. The following SQL example shows how to use `DESCRIBE TABLE EXTENDED`. Each line is commented.

```sql
-- View extended table metadata and statistics.
-- The DESCRIBE TABLE EXTENDED command displays the table schema, statistics, and other metadata.
-- The output includes the table name, database, owner, creation time, last access time, and other properties.
-- It also includes the statistics that have been collected by ANALYZE TABLE.
-- If statistics have not been collected, the statistics section may be empty or may show default values.
-- You should run ANALYZE TABLE before running this command if you want to see meaningful statistics.
DESCRIBE TABLE EXTENDED sales.transactions;
```

The output of `DESCRIBE TABLE EXTENDED` typically includes a section for table statistics. This section shows the number of rows, the total size in bytes, and the last analyzed time. It may also show column-level statistics if they have been collected. The output is displayed as a result set with columns such as `col_name`, `data_type`, `comment`, and `stats`. You can parse this output programmatically if needed.

You can also use PySpark to retrieve table metadata and generate summary statistics. The following PySpark example shows how to use the DataFrame API to generate summary statistics for numeric columns. Each line is commented.

```python
# Generate summary statistics for numeric columns using the DataFrame API
# Read the table into a DataFrame.
df = spark.table("sales.transactions")
# The describe() method computes summary statistics for numeric and string columns.
# For numeric columns, it returns count, mean, standard deviation, min, and max.
# For string columns, it returns count, mean, stddev, min, and max based on lexicographic order.
# The show() method displays the results.
df.describe().show()
```

The `describe()` method returns a DataFrame with one row per statistic and one column per column in the original DataFrame. The statistics are `count`, `mean`, `stddev`, `min`, and `max`. The `count` is the number of non-null values. The `mean` is the average. The `stddev` is the standard deviation. The `min` and `max` are the minimum and maximum values. For string columns, the `mean` and `stddev` are not meaningful. The `min` and `max` are lexicographic. You can use `describe()` for a quick overview of your data. It is not as detailed as `ANALYZE TABLE`, but it is convenient for exploratory analysis.

The output shows the table's size in bytes and row count, confirming that profiling has been performed. For Unity Catalog managed tables, predictive optimization automatically runs `ANALYZE` to keep statistics current. Predictive optimization is a feature that monitors table changes and automatically collects statistics when needed. It reduces the burden of manual statistics management. It ensures that the optimizer always has fresh statistics. It is enabled by default for Unity Catalog managed tables. You do not need to run `ANALYZE TABLE` manually for these tables. However, you can still run it manually if you want to force a refresh or if you want to collect statistics for specific columns.

## Best practices for generating summary statistics

Run `ANALYZE TABLE` after bulk data loads or significant changes. This ensures that the query optimizer has accurate statistics for planning efficient queries. If you load a large amount of data and do not analyze the table, the optimizer may still use old statistics. This can lead to slow queries.

Analyze columns that are frequently used in filters, joins, and aggregations. These are the columns where statistics have the most impact on query planning. You do not need to analyze every column. Analyzing all columns can be expensive. Focus on the columns that matter.

Monitor statistics freshness. If statistics are stale, the optimizer may make poor decisions. You can check the last analyzed time using `DESCRIBE TABLE EXTENDED`. You can set up alerts if statistics have not been refreshed recently. For Unity Catalog managed tables, predictive optimization handles this automatically.

Consider the cost of analyzing. `ANALYZE TABLE` scans the table to compute statistics. For very large tables, this can take time and consume resources. You should run it during off-peak hours. You can also analyze specific columns to reduce the cost. If you use predictive optimization, the cost is managed for you.

Use statistics to inform schema design. If you see that a column has a high distinct count and is frequently used in joins, you might consider indexing or partitioning. If you see that a column has many nulls, you might consider whether the column is necessary or whether you need to improve data quality at the source.

Use statistics to detect data drift. If you compare statistics over time, you can see changes in minimum and maximum values, distinct counts, and null counts. These changes may indicate data drift. You can set up alerts when statistics change beyond a threshold. This helps you catch data quality issues early.

## Detailed explanation of each command

The `ANALYZE TABLE` command is the primary tool for collecting statistics. It has several variants. The `COMPUTE STATISTICS` clause without `FOR COLUMNS` collects table-level statistics. These include the row count and the total size in bytes. The `FOR COLUMNS` clause collects column-level statistics for the specified columns. The `FOR ALL COLUMNS` clause collects column-level statistics for all columns. Column-level statistics include minimum value, maximum value, number of nulls, distinct count, average column length, and maximum column length.

The `DESC EXTENDED` command displays metadata and statistics for a specific column. It is useful when you want to see the detailed metrics for one column. The output includes the column name, data type, comment, and statistics. The statistics section shows the minimum value, maximum value, number of nulls, distinct count, average column length, and maximum column length. You can use this command to verify that statistics have been collected and to inspect the values.

The `DESCRIBE TABLE EXTENDED` command displays metadata and statistics for the entire table. It shows the table schema, table properties, and statistics. The statistics section shows the row count, total size, and last analyzed time. It may also show column-level statistics if they have been collected. You can use this command to get a comprehensive view of the table.

The PySpark `describe()` method computes summary statistics for a DataFrame. It returns count, mean, standard deviation, min, and max for numeric columns. For string columns, it returns count, mean, stddev, min, and max based on lexicographic order. This method is useful for quick exploratory analysis. It does not store statistics in the table metadata. It computes them on the fly. It is not a replacement for `ANALYZE TABLE`. It is a complementary tool.

## Example scenario

Suppose you have a table named `sales.transactions` with columns `transaction_id`, `amount`, `customer_id`, and `transaction_date`. You want to improve query performance and understand your data. You start by running `ANALYZE TABLE sales.transactions COMPUTE STATISTICS`. This collects the row count and size. You then run `ANALYZE TABLE sales.transactions COMPUTE STATISTICS FOR COLUMNS amount, customer_id`. This collects column-level statistics for the amount and customer_id columns. You view the statistics using `DESC EXTENDED sales.transactions amount`. You see that the minimum amount is 0, the maximum amount is 10000, the number of nulls is 0, and the distinct count is 5000. You view the table statistics using `DESCRIBE TABLE EXTENDED sales.transactions`. You see that the table has 1,000,000 rows and 50 MB in size. You also run `df.describe().show()` in PySpark to get a quick summary. You notice that the average amount is 250. You use this information to design a query that filters on amount. The optimizer uses the statistics to choose an efficient plan. You also notice that the customer_id column has a high distinct count. You consider partitioning the table by customer_id in the future. You set up a schedule to run `ANALYZE TABLE` weekly to keep statistics fresh. You monitor the statistics for data drift. You see that the maximum amount has increased to 20000 over time. You investigate and find that a new product line was launched. You update your data quality rules accordingly.

This scenario shows how summary statistics can be used for performance tuning and data understanding. The combination of `ANALYZE TABLE`, `DESC EXTENDED`, `DESCRIBE TABLE EXTENDED`, and PySpark `describe()` gives you a complete toolkit.
