## Combine rows with set operators

Set operators are SQL and DataFrame operations that combine the rows of two queries or DataFrames vertically, stacking them one on top of the other. Unlike joins, which combine columns horizontally based on a matching condition, set operators work on entire result sets. They do not match on a key. Instead, they require that both inputs have the same number of columns with compatible data types, and they treat each row as a whole. The three standard set operators are `UNION`, `INTERSECT`, and `EXCEPT`. `UNION` appends rows from both inputs. `INTERSECT` returns only the rows that appear in both inputs. `EXCEPT` returns the rows from the first input that do not appear in the second. In some SQL dialects, `EXCEPT` is also called `MINUS`.

Set operators matter because they solve a different class of problem than joins. When you need to combine data from two tables that have the same structure, such as active customers and archived customers, a set operator is the natural tool. When you need to find records that exist in one dataset but not another, such as customers who have never placed an order, an anti join works, but `EXCEPT` is often simpler when the comparison is on the entire row. Set operators are also useful for data quality checks. `INTERSECT` can reveal rows that appear in two systems that should be mutually exclusive. `EXCEPT` can reveal rows that are missing from a replica. These operations are declarative and easy to read, and they are optimized by the same query engine that handles joins and aggregations.

These notes cover set operators from first principles. They explain the requirements that both inputs must satisfy, the difference between `UNION` and `UNION ALL`, how `INTERSECT` and `EXCEPT` handle duplicates, and how nulls are treated. They show how to write set operations in SQL and how to achieve the same results in PySpark using `union()`, `intersect()`, `subtract()`, and their `ALL` variants. They also cover operator precedence, data type alignment, and how set operators interact with Delta Lake, Unity Catalog, and the medallion architecture. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand not only how to use set operators, but when they are the right tool and how to avoid the mistakes that produce incorrect results.

## Understanding set operators

Set operators work vertically. They take two result sets and produce a single result set by comparing or stacking rows. For a set operation to be valid, both inputs must have the same number of columns, and the data types of corresponding columns must be compatible. Compatible means that Spark can implicitly cast one type to the other, such as an integer to a long, or a string to a string. If the types are not compatible, the query fails with an analysis error. The column names in the result come from the first input. The second input's column names are ignored. This is important when you read the output: the column labels are determined by the first query, not by the second.

The three set operators differ in how they combine rows. `UNION` concatenates the rows from both inputs. By default, it removes duplicate rows from the result. If you want to keep duplicates, you use `UNION ALL`. `INTERSECT` returns only the rows that appear in both inputs. It also removes duplicates by default, but you can use `INTERSECT ALL` to keep duplicates. `EXCEPT` returns the rows from the first input that do not appear in the second. It removes duplicates by default, and `EXCEPT ALL` keeps them. In Spark SQL, `MINUS` is a synonym for `EXCEPT`. In PySpark, the DataFrame API provides `union()`, `intersect()`, and `subtract()`, along with `unionAll()`, `intersectAll()`, and `subtractAll()` in newer versions.

The following table summarizes the operators and their duplicate behavior.

| Operator | Returns | Duplicate behavior (default) | ALL variant |
|---|---|---|---|
| `UNION` | All rows from both inputs | Removes duplicates | `UNION ALL` keeps duplicates |
| `INTERSECT` | Rows in both inputs | Removes duplicates | `INTERSECT ALL` keeps duplicates |
| `EXCEPT` / `MINUS` | Rows in first input not in second | Removes duplicates | `EXCEPT ALL` keeps duplicates |

The table shows that each operator has a default behavior and an `ALL` variant. The default behavior removes duplicates, which requires a comparison of all columns across all rows. The `ALL` variant skips the deduplication step, which makes it faster. Use the `ALL` variant when you know there are no duplicates or when duplicates are meaningful, such as when you are stacking event logs where multiple identical events are legitimate.

## Merging datasets with UNION

`UNION` appends the rows of one query to the rows of another. It is the most common set operator. The default form removes duplicate rows. The `UNION ALL` form keeps all rows, including duplicates. In SQL, you write the two queries separated by the operator. In PySpark, you call the `union()` method on one DataFrame and pass the other as an argument. PySpark's `union()` behaves like `UNION ALL` by default; it does not remove duplicates. To remove duplicates, you call `distinct()` after the union.

The following SQL example combines active and archived customers and removes duplicates.

```sql
-- Combine active and archived customers into one result.
-- The UNION operator appends the rows and removes duplicates.
-- Both queries must have the same number of columns with compatible types.
-- The column names in the result come from the first query.
SELECT customer_id, name, email FROM active_customers
UNION
-- The second query must select the same number of columns in the same order.
-- The column names here are ignored; the first query's names are used.
SELECT customer_id, name, email FROM archived_customers;
```

The query returns one row for each distinct customer that appears in either table. If a customer appears in both tables with identical values in all three columns, the duplicate is removed. If the same customer appears with different values, both rows are kept because they are not exact duplicates. `UNION` compares entire rows, not just the key. This is a common point of confusion. If you want to deduplicate on a key, you need a different approach, such as a window function or a `GROUP BY`.

The following SQL example uses `UNION ALL` to keep duplicates.

```sql
-- Combine active and archived customers, keeping all rows.
-- UNION ALL does not remove duplicates, so it is faster than UNION.
-- Use it when duplicates are meaningful or when you know there are none.
SELECT customer_id, name, email FROM active_customers
UNION ALL
SELECT customer_id, name, email FROM archived_customers;
```

The result contains every row from both tables, including exact duplicates. This is the correct choice when you are stacking event logs or transaction records where multiple identical rows represent multiple distinct events.

In PySpark, the equivalent operations use `union()` and `distinct()`.

```python
# Read the active and archived customer tables from Unity Catalog.
df_active = spark.table("sales.active_customers")
df_archived = spark.table("sales.archived_customers")

# Combine both DataFrames using union().
# PySpark's union() behaves like UNION ALL: it keeps duplicates.
# The DataFrames must have the same number of columns with compatible types.
# The column names in the result come from the first DataFrame.
df_combined = df_active.union(df_archived)

# Remove duplicates if needed.
# distinct() compares entire rows and removes exact duplicates.
# This is equivalent to the SQL UNION operator without ALL.
df_distinct = df_active.union(df_archived).distinct()

# Display both results.
# df_combined contains all rows, including duplicates.
# df_distinct contains only unique rows.
display(df_combined)
display(df_distinct)
```

The PySpark example shows that `union()` keeps duplicates, so you must call `distinct()` to get the behavior of SQL `UNION`. This is a common source of confusion for people moving between SQL and PySpark. Remember that PySpark's `union()` is `UNION ALL`, and `unionAll()` is an alias for `union()`. If you want duplicate removal, add `distinct()`.

## Finding common rows with INTERSECT

`INTERSECT` returns only the rows that appear in both inputs. It is useful for finding overlapping data, such as customers who appear in two systems, or products that are listed in two catalogs. By default, `INTERSECT` removes duplicates, so the result contains each common row once. `INTERSECT ALL` keeps duplicates, so if a row appears twice in both inputs, it appears twice in the result.

The following SQL example finds customers who appear in both the active and archived tables.

```sql
-- Find customers that appear in both the active and archived tables.
-- INTERSECT returns only rows that exist in both queries.
-- The comparison is on the entire row, not just the customer_id.
-- If the same customer_id appears with different names or emails,
-- the rows are not considered matching.
SELECT customer_id, name, email FROM active_customers
INTERSECT
SELECT customer_id, name, email FROM archived_customers;
```

The query returns rows that are identical in all selected columns across both tables. If you only want to compare on `customer_id`, you should select only that column in both queries. This is a common pattern for data quality checks. You can use `INTERSECT` to verify that a replica contains all the rows of the source, or to find records that should not be in both places.

In PySpark, the equivalent method is `intersect()`.

```python
# Find rows that appear in both DataFrames.
# intersect() returns only rows that exist in both.
# It removes duplicates by default, like SQL INTERSECT.
df_intersect = df_active.intersect(df_archived)

# Display the intersection.
# The result contains rows that are identical in all columns.
display(df_intersect)
```

The PySpark `intersect()` method returns a new DataFrame containing rows that are present in both DataFrames. It removes duplicates. In Spark 3.0 and later, `intersectAll()` is available to keep duplicates. The following example shows `intersectAll()`.

```python
# Keep duplicates in the intersection.
# intersectAll() is available in Spark 3.0 and later.
# It returns rows that appear in both DataFrames, preserving duplicates.
# For example, if a row appears twice in both inputs, it appears twice.
df_intersect_all = df_active.intersectAll(df_archived)

# Display the result.
display(df_intersect_all)
```

Use `INTERSECT` when you need to find common rows and duplicates do not matter. Use `INTERSECT ALL` when the multiplicity of rows is meaningful.

## Excluding rows with EXCEPT

`EXCEPT` returns the rows from the first query that do not appear in the second. It is the opposite of `INTERSECT`. It is useful for finding gaps, such as customers who are in the active table but not in the archived table, or records that are missing from a replica. In Spark SQL, `MINUS` is a synonym for `EXCEPT`. By default, `EXCEPT` removes duplicates. `EXCEPT ALL` keeps duplicates.

The following SQL example finds active customers who are not in the archived table.

```sql
-- Find customers in the active table that are not in the archived table.
-- EXCEPT returns rows from the first query that do not appear in the second.
-- The comparison is on the entire row.
-- If a customer appears in both tables with different values,
-- the active row is returned because it is not an exact match.
SELECT customer_id, name, email FROM active_customers
EXCEPT
SELECT customer_id, name, email FROM archived_customers;
```

The query returns rows from `active_customers` that do not have an exact match in `archived_customers`. If you only want to compare on `customer_id`, select only that column in both queries. The `MINUS` synonym works the same way.

```sql
-- The same result using MINUS instead of EXCEPT.
-- MINUS is a synonym for EXCEPT in Spark SQL.
SELECT customer_id, name, email FROM active_customers
MINUS
SELECT customer_id, name, email FROM archived_customers;
```

In PySpark, the equivalent method is `subtract()`.

```python
# Find rows in the active DataFrame that are not in the archived DataFrame.
# subtract() returns rows from the left DataFrame that do not appear
# in the right DataFrame. It removes duplicates by default.
df_except = df_active.subtract(df_archived)

# Display the result.
# The result contains rows from df_active that are not in df_archived.
display(df_except)
```

The PySpark `subtract()` method removes duplicates. In Spark 3.0 and later, `subtractAll()` keeps duplicates. The following example shows `subtractAll()`.

```python
# Keep duplicates in the subtraction.
# subtractAll() is available in Spark 3.0 and later.
# It returns rows from the left DataFrame that do not appear in the right,
# preserving duplicates from the left.
df_except_all = df_active.subtractAll(df_archived)

# Display the result.
display(df_except_all)
```

Use `EXCEPT` or `subtract()` when you need to find rows that are missing from one dataset. Use the `ALL` variants when duplicates matter.

## Operator precedence and chaining

When you chain multiple set operators in a single SQL statement, precedence matters. In Spark SQL, `INTERSECT` has higher precedence than `UNION` and `EXCEPT`. This means that `A UNION B INTERSECT C` is evaluated as `A UNION (B INTERSECT C)`. If you want a different evaluation order, use parentheses. The following example shows the difference.

```sql
-- Without parentheses, INTERSECT binds tighter than UNION.
-- This is evaluated as A UNION (B INTERSECT C).
SELECT * FROM A
UNION
SELECT * FROM B
INTERSECT
SELECT * FROM C;

-- With parentheses, the union is evaluated first.
-- This is evaluated as (A UNION B) INTERSECT C.
(SELECT * FROM A
 UNION
 SELECT * FROM B)
INTERSECT
SELECT * FROM C;
```

The first query returns rows from A plus the rows that are in both B and C. The second query returns only the rows that are in both the union of A and B, and C. These are different results. Always use parentheses when you chain set operators to make the evaluation order explicit. In PySpark, you control the order by the order of method calls. For example, `df_a.union(df_b).intersect(df_c)` evaluates the union first, then the intersection. `df_a.union(df_b.intersect(df_c))` evaluates the intersection first. Parentheses in Python make the order clear.

## Null handling in set operators

Null handling in set operators differs from null handling in joins. In a join, null keys do not match. In a set operator, nulls are treated as equal for the purpose of duplicate elimination and comparison. This means that two rows where a column is null are considered duplicates if all other columns are equal. For `INTERSECT`, a row with a null in a column matches another row with a null in the same column. For `EXCEPT`, a row with a null is removed if the second input contains a row with a null in the same column and all other columns equal. This behavior is defined by the SQL standard and is implemented by Spark.

The following example shows how nulls behave in a union and an intersect.

```python
# Build two small DataFrames with nulls.
from pyspark.sql import Row
df_a = spark.createDataFrame([
    Row(id=1, name="Alice"),
    Row(id=2, name=None),      # Null name.
])
df_b = spark.createDataFrame([
    Row(id=2, name=None),      # Null name, same as in df_a.
    Row(id=3, name="Bob"),
])

# Union all rows, keeping duplicates.
# The row with id=2 and null name appears twice because union() keeps duplicates.
df_union = df_a.union(df_b)
display(df_union)

# Intersect the two DataFrames.
# The row with id=2 and null name appears in both, so it is returned.
# Nulls are treated as equal for the intersection.
df_intersect = df_a.intersect(df_b)
display(df_intersect)
```

The union result contains four rows: the two from `df_a` and the two from `df_b`. The row with `id=2` and `name=None` appears twice. The intersect result contains one row: `id=2` with `name=None`, because that row appears in both DataFrames and nulls are considered equal. If you used `distinct()` on the union, the duplicate null row would be removed. This behavior is important to remember when you use set operators on data that contains nulls.

## Data type alignment and column ordering

Set operators require that both inputs have the same number of columns and that the data types of corresponding columns are compatible. Compatibility means that Spark can implicitly cast one type to the other. For example, an integer and a long are compatible, and a string and a string are compatible. If the types are not compatible, such as a string and an integer, the query fails with an analysis error. You can use `CAST` to convert a column to a compatible type before the set operation.

Column order matters. The first column of the first query is matched with the first column of the second query, the second with the second, and so on. Column names do not need to match. The result uses the column names from the first query. If the columns are in a different order in the two queries, the set operation will compare the wrong columns and produce incorrect results. Always ensure that the columns are in the same order in both queries.

The following example shows a correct and an incorrect alignment.

```sql
-- Correct: both queries select the same columns in the same order.
SELECT customer_id, name, email FROM active_customers
UNION
SELECT customer_id, name, email FROM archived_customers;

-- Incorrect: the columns are in a different order.
-- The first query selects customer_id, name, email.
-- The second query selects name, customer_id, email.
-- Spark will match customer_id with name, and name with customer_id.
-- This produces a result that is almost certainly wrong.
SELECT customer_id, name, email FROM active_customers
UNION
SELECT name, customer_id, email FROM archived_customers;
```

The incorrect query may not raise an error if the data types happen to be compatible, but the result will be wrong. For example, if both `customer_id` and `name` are strings, Spark will not complain, but the rows will be mismatched. Always verify that the column order is identical in both queries.

## Set operators and Delta Lake, Unity Catalog, and the medallion architecture

Set operators are transformations that run on DataFrames or tables. They interact with the lakehouse in the same way as other transformations. Delta Lake stores data in Parquet files with a transaction log. When you apply a set operator to two Delta tables, Spark reads the relevant files, performs the set operation, and returns the result. If the tables are partitioned, Spark can sometimes avoid reading partitions that are not needed, but set operators generally require a full scan of both inputs because they compare entire rows.

Unity Catalog governs access to the tables you use in set operations. If a table has a row-level filter or column mask, those policies are applied before the set operation runs. The result reflects only the rows and column values you are allowed to see. This can make a `UNION` produce fewer rows than expected, or an `EXCEPT` produce more rows, because the hidden rows are not visible. Always check for policies if the result does not match your expectations.

In a medallion architecture, set operators are often used to combine data from multiple sources in the bronze or silver layer. For example, you might union together daily incremental loads into a single silver table. You might use `EXCEPT` to find records that exist in a source system but not in the lakehouse, which indicates a failed ingestion. You might use `INTERSECT` to verify that a replica matches its source. Set operators are simple and powerful tools for data integration and reconciliation. When you write the result to a Delta table, Delta Lake enforces the schema of the target table. If the set operation produces columns with different types or new columns, the write fails unless you enable schema evolution. Use `mergeSchema` only when you intend to evolve the schema.

## Best practices

Choose the correct operator for the job. Use `UNION ALL` when you want to stack rows and duplicates are meaningful or known to be absent. Use `UNION` when you need to remove duplicates, but be aware that deduplication requires a shuffle and is more expensive. Use `INTERSECT` to find common rows and `EXCEPT` to find gaps.

Use the `ALL` variants when possible. `UNION ALL`, `INTERSECT ALL`, and `EXCEPT ALL` skip the deduplication step and are faster than their default counterparts. Use them when duplicates are acceptable or when you know there are no duplicates.

Ensure that both inputs have the same number of columns in the same order with compatible types. A mismatch in column order can produce silently wrong results. Always verify the schema before writing a set operation.

Select only the columns you need. Set operators compare entire rows. If you include columns that are not relevant to the comparison, you may get unexpected results. For example, if you use `EXCEPT` to find missing customers but include a `last_updated` timestamp column, a customer whose timestamp changed will appear as missing. Select only the key columns when the comparison should be on the key alone.

Use parentheses when chaining set operators. `INTERSECT` has higher precedence than `UNION` and `EXCEPT`. Parentheses make the evaluation order explicit and prevent subtle bugs.

Be aware of null behavior. Nulls are treated as equal in set operators, unlike in joins. This is usually what you want, but it can be surprising if you are used to join semantics.

Test set operations with small datasets that include nulls and duplicates. Set operations are simple but easy to misconfigure. A test with known data catches alignment and null-handling mistakes.

## Common mistakes and pitfalls

The most common mistake is assuming that `UNION` in PySpark removes duplicates. It does not. PySpark's `union()` keeps duplicates. To remove duplicates, you must call `distinct()`. In SQL, `UNION` removes duplicates by default, so the behavior differs between the two surfaces.

A second mistake is mismatching the column order. If the columns are in a different order in the two inputs, Spark will compare the wrong columns and produce incorrect results. Always ensure the column order is identical.

A third mistake is including extra columns that are not part of the intended comparison. For example, if you use `EXCEPT` to find missing keys but include a timestamp column, rows whose timestamp changed will appear as missing even though the key exists. Select only the columns that should participate in the comparison.

A fourth mistake is forgetting that `INTERSECT` has higher precedence than `UNION` and `EXCEPT`. A chain of set operators without parentheses may not evaluate in the order you expect. Use parentheses to control the order.

A fifth mistake is using `UNION` when you meant `UNION ALL` and then wondering why rows are missing. `UNION` removes duplicates, which can remove rows you expected to keep. Use `UNION ALL` when duplicates are meaningful.

A sixth mistake is assuming that nulls do not match in set operators. They do match. A row with a null in a column is considered equal to another row with a null in the same column for the purpose of `UNION`, `INTERSECT`, and `EXCEPT`. This is the opposite of join behavior.

A seventh mistake is not accounting for Unity Catalog row-level filters. If a table has a row-level filter, the set operation sees only the rows you are allowed to see. The result may differ from what you expect based on the raw data. Check for policies when results are surprising.

## Testing set operations

Set operations are logic, and they should be tested. A test for a set operation should verify the number of rows, the presence or absence of specific rows, and the handling of nulls and duplicates. The following example shows a test for `UNION` and `EXCEPT`.

```python
# Import the test helpers.
import pytest
from pyspark.sql import Row

# Build small DataFrames with known values.
# The data includes a duplicate row and a null value.
df_a = spark.createDataFrame([
    Row(id=1, name="Alice"),
    Row(id=2, name="Bob"),
    Row(id=2, name="Bob"),      # Duplicate of the previous row.
    Row(id=3, name=None),       # Null name.
])
df_b = spark.createDataFrame([
    Row(id=2, name="Bob"),
    Row(id=3, name=None),
    Row(id=4, name="Dana"),
])

# Test UNION ALL: keeps all rows, including duplicates.
df_union_all = df_a.union(df_b)
# df_a has 4 rows, df_b has 3 rows, so the union has 7 rows.
assert df_union_all.count() == 7, f"Union all count failed: {df_union_all.count()}"

# Test UNION (distinct): removes exact duplicates.
df_union = df_a.union(df_b).distinct()
# The distinct rows are: (1, Alice), (2, Bob), (3, None), (4, Dana).
# The duplicate (2, Bob) is removed, and the two (3, None) rows are one.
assert df_union.count() == 4, f"Union distinct count failed: {df_union.count()}"

# Test EXCEPT: rows in df_a that are not in df_b.
df_except = df_a.subtract(df_b)
# df_a rows not in df_b: (1, Alice) and the duplicate (2, Bob) is removed
# because (2, Bob) is in df_b. The row (3, None) is in df_b, so it is removed.
# The result should be one row: (1, Alice).
assert df_except.count() == 1, f"Except count failed: {df_except.count()}"
```

The test verifies the row counts for union all, union distinct, and except. It includes duplicates and nulls to ensure that the behavior matches expectations. Run tests like this in your CI pipeline against a small local Spark session.

## Performance considerations

Set operators can be expensive because they often require a shuffle. `UNION ALL` is the cheapest because it simply concatenates the partitions of the two inputs without redistributing data. It does not compare rows. `UNION`, `INTERSECT`, and `EXCEPT` require a shuffle to compare rows and remove duplicates. The shuffle redistributes data so that identical rows end up on the same partition, where they can be compared.

Use `UNION ALL` whenever possible. If you know there are no duplicates, or if duplicates are acceptable, `UNION ALL` avoids the shuffle and is much faster. If you need to remove duplicates, consider whether you can deduplicate one input before the union, which may reduce the size of the shuffle.

For `INTERSECT` and `EXCEPT`, the cost is similar to a join because both inputs must be shuffled and compared. If one input is much smaller than the other, Spark can sometimes broadcast the smaller input, but this is not always possible with set operators. In general, reduce the size of both inputs by filtering and selecting only the needed columns before the set operation.

Be aware of data skew. If one value appears very frequently in the comparison columns, the partition handling that value will be larger and slower. This is the same issue that affects joins. Adaptive query execution can help mitigate skew in recent Spark versions.

Finally, use `explain()` to inspect the physical plan. The plan shows whether a shuffle is required and how Spark plans to execute the set operation. This is the best way to understand and optimize performance.

## Summary

Set operators combine rows vertically from two queries or DataFrames that have the same number of columns with compatible data types. `UNION` appends rows and removes duplicates by default; `UNION ALL` keeps duplicates. `INTERSECT` returns rows that appear in both inputs and removes duplicates by default; `INTERSECT ALL` keeps duplicates. `EXCEPT` returns rows from the first input that do not appear in the second and removes duplicates by default; `EXCEPT ALL` keeps duplicates. `MINUS` is a synonym for `EXCEPT` in Spark SQL.

In SQL, set operators are written between two queries. In PySpark, `union()` behaves like `UNION ALL` and keeps duplicates; use `distinct()` to remove them. `intersect()` and `subtract()` remove duplicates by default, and `intersectAll()` and `subtractAll()` keep them in Spark 3.0 and later. Nulls are treated as equal in set operators, unlike in joins. Column order matters: corresponding columns are matched by position, not by name. The result uses the column names from the first query.

Operator precedence matters when chaining set operators. `INTERSECT` has higher precedence than `UNION` and `EXCEPT`. Use parentheses to control evaluation order. Set operators interact with Delta Lake, Unity Catalog, and the medallion architecture in the same way as other transformations: Delta Lake provides storage and statistics, Unity Catalog applies row-level filters and column masks, and the medallion architecture uses set operators to combine and reconcile data across layers.

Best practices include using `UNION ALL` when possible, ensuring column alignment, selecting only the columns needed for comparison, using parentheses for chaining, and testing with nulls and duplicates. Common mistakes include assuming PySpark's `union()` removes duplicates, mismatching column order, including extra columns in the comparison, forgetting precedence, and assuming nulls do not match. Performance depends on whether a shuffle is required: `UNION ALL` is cheap, while `UNION`, `INTERSECT`, and `EXCEPT` require a shuffle to compare rows. Used well, set operators are simple, readable tools for combining and comparing datasets.
