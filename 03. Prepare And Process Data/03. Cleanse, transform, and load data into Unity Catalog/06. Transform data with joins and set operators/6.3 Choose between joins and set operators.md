## Choose between joins and set operators

A join and a set operator are both ways to combine two datasets, but they solve different problems. A join combines columns from two tables horizontally, matching rows based on a related key. A set operator combines rows vertically, stacking or comparing entire result sets that share the same column structure. The choice between them is not a matter of preference. It is determined by what you are trying to achieve. If you need to add customer names to an orders table, you use a join. If you need to append last month's orders to this month's orders, you use a set operator. If you need to find customers who have placed an order, you can use a semi join or an `INTERSECT`, and the right choice depends on whether you are comparing on a key or on the entire row.

Understanding the difference matters because using the wrong tool can produce incorrect results silently. A join on a non-unique key can multiply rows and inflate sums. A `UNION` that was meant to deduplicate on a key will not deduplicate if the rows differ in other columns. A semi join and an `INTERSECT` can return different answers when nulls are present or when the comparison involves more than one column. These notes explain the fundamental difference between horizontal and vertical combination, then walk through the situations where each approach is correct. They cover the join types that filter based on existence, the set operators that compare entire rows, and the tradeoffs between them. They also cover null handling, schema requirements, performance, and how the choice interacts with Delta Lake, Unity Catalog, and the medallion architecture. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and confidently choose the right operation for your transformation.

## The fundamental difference: horizontal versus vertical combination

A join combines two datasets by matching rows on a condition, usually equality on a key column. The result contains columns from both datasets. The number of rows in the result depends on how many rows match. If every row in the left table matches exactly one row in the right table, the result has the same number of rows as the left table. If some rows match multiple rows, the result has more rows. If some rows do not match, the result may have fewer rows, depending on the join type. A join is horizontal because it adds columns to each row.

A set operator combines two datasets by stacking or comparing entire rows. The result contains the same columns as the inputs. The number of rows depends on the operator. `UNION ALL` adds the row counts. `UNION` adds the row counts and then removes duplicates. `INTERSECT` returns only rows that appear in both inputs. `EXCEPT` returns rows from the first input that do not appear in the second. A set operator is vertical because it adds rows to the result, not columns.

The following table summarizes the difference.

| Aspect | Join | Set operator |
|---|---|---|
| Direction | Horizontal (adds columns) | Vertical (adds or compares rows) |
| Matching | On a condition, usually a key | On entire rows, by position |
| Schema requirement | Flexible; columns can differ | Same number of columns, compatible types |
| Result columns | From both inputs | From the first input |
| Null matching | Nulls do not match | Nulls are treated as equal |
| Typical use | Enrich, match, filter by existence | Append, find common, find unique |

The table shows that joins and set operators are complementary. A join answers the question "what columns from the other table belong with this row?" A set operator answers the question "which rows are shared, unique, or should be stacked together?" The rest of these notes explores each use case in detail.

## When to use joins

Joins are the correct tool when you need to combine columns from related tables. There are three main scenarios: enriching records by adding columns, matching records based on key relationships, and filtering data based on existence in another table. Each scenario maps to a specific join type or family of join types.

### Enriching records by adding columns

Enrichment is the most common use of joins. You have a fact table, such as orders, and you want to add descriptive attributes from dimension tables, such as customer name, product category, or region. You join on the foreign key and select the columns you need. The join type is usually an inner join if you only want orders with valid references, or a left join if you want to keep all orders even when a reference is missing.

The following SQL example enriches an orders table with customer details.

```sql
-- Select order columns and customer columns.
-- The join adds customer_name and region to each order.
SELECT
  o.order_id,
  o.order_date,
  o.order_amount,
  c.customer_name,
  c.region
FROM sales.orders o
-- LEFT JOIN keeps all orders, even if the customer is missing.
-- If a customer is missing, customer_name and region are null.
-- This is safer than an inner join when you do not want to lose orders.
LEFT JOIN sales.customers c ON o.customer_id = c.customer_id;
```

The query returns one row per order, with customer details appended. The left join ensures that no orders are lost. If you used an inner join, orders with a null or invalid customer ID would be dropped. The choice between inner and left depends on whether you can afford to lose rows.

The equivalent PySpark join uses the `join()` method with `how="left"`.

```python
# Import the col function to reference columns.
from pyspark.sql.functions import col

# Read the orders and customers tables from Unity Catalog.
df_orders = spark.read.table("sales.orders")
df_customers = spark.read.table("sales.customers")

# Join orders to customers on customer_id.
# how="left" keeps all orders and adds nulls for missing customers.
# The on parameter uses a column expression because the column names
# are the same in both DataFrames; using a string would also work.
df_enriched = df_orders.join(
    df_customers,
    on=df_orders.customer_id == df_customers.customer_id,
    how="left"
).select(
    "order_id",
    "order_date",
    "order_amount",
    "customer_name",
    "region"
)

# Display the enriched result.
display(df_enriched)
```

The PySpark version produces the same result. The `select` at the end keeps only the needed columns, which reduces the size of the result and makes the schema explicit.

### Matching records based on key relationships

Matching is similar to enrichment, but the goal is to find rows that have a corresponding row in another table. You use an inner join when you only want matching rows, or a full outer join when you want to see matches and non-matches on both sides. For example, you might match employees to departments to produce a report of which employees belong to which department, and which departments have no employees.

The following SQL example uses a full outer join to find matches and gaps on both sides.

```sql
-- Select employee and department columns.
-- The full outer join keeps all employees and all departments.
SELECT
  e.id AS employee_id,
  e.name AS employee_name,
  d.deptno,
  d.deptname
FROM hr.employee e
-- FULL OUTER JOIN keeps rows from both tables.
-- Employees without a department have null deptno and deptname.
-- Departments without employees have null employee_id and employee_name.
FULL OUTER JOIN hr.department d ON e.deptno = d.deptno;
```

The result contains every employee and every department. You can filter on nulls to find gaps. For example, `WHERE e.id IS NULL` finds departments with no employees, and `WHERE d.deptno IS NULL` finds employees with no department.

The PySpark version uses `how="full"`.

```python
# Read the employee and department tables.
df_employee = spark.read.table("hr.employee")
df_department = spark.read.table("hr.department")

# Full outer join to keep all rows from both tables.
# how="full" is the PySpark equivalent of SQL FULL OUTER JOIN.
df_full = df_employee.join(
    df_department,
    on="deptno",
    how="full"
)

# Display the result.
display(df_full)
```

The string form `on="deptno"` is used because both DataFrames have a column with that name. This avoids duplicate columns in the result.

### Filtering data based on existence

Semi and anti joins are specialized joins that filter the left table based on the existence of a match in the right table. They do not add columns from the right table. A semi join returns left rows that have a match. An anti join returns left rows that have no match. These joins are often more efficient than an inner join followed by a `SELECT DISTINCT`, because they do not need to produce the right table's columns or remove duplicates.

The following SQL example finds customers who have placed an order.

```sql
-- Find customers who have at least one order.
-- LEFT SEMI JOIN returns only columns from the left table.
-- It returns one row per matching customer, with no duplicates.
SELECT *
FROM sales.customers c
LEFT SEMI JOIN sales.orders o ON c.customer_id = o.customer_id;
```

The result contains only customers who appear in the orders table. Customers with no orders are excluded. The anti join does the opposite.

```sql
-- Find customers who have never placed an order.
-- LEFT ANTI JOIN returns only columns from the left table.
-- It returns customers with no matching orders.
SELECT *
FROM sales.customers c
LEFT ANTI JOIN sales.orders o ON c.customer_id = o.customer_id;
```

The PySpark versions use `how="semi"` and `how="anti"`.

```python
# Semi join: keep customers who have placed an order.
df_semi = df_customers.join(df_orders, on="customer_id", how="semi")

# Anti join: keep customers who have never placed an order.
df_anti = df_customers.join(df_orders, on="customer_id", how="anti")

# Display both results.
display(df_semi)
display(df_anti)
```

Semi and anti joins are the join-based way to answer existence questions. They are often the right choice when the comparison is on a key and you do not need columns from the other table.

## When to use set operators

Set operators are the correct tool when you need to combine rows from datasets that have the same shape. There are three main scenarios: appending records from multiple sources with identical schemas, finding common records across datasets, and identifying records unique to one dataset.

### Appending records with identical schemas

Appending is the most common use of set operators. You have two tables with the same columns and compatible types, and you want to stack them into one result. `UNION ALL` is the standard choice because it keeps all rows and does not require a deduplication shuffle. Use `UNION` only when you need to remove exact duplicates.

The following SQL example combines active and archived customers.

```sql
-- Combine active and archived customers into one result.
-- UNION ALL keeps all rows, including duplicates.
-- Both queries must select the same number of columns in the same order.
SELECT customer_id, name, email FROM sales.active_customers
UNION ALL
SELECT customer_id, name, email FROM sales.archived_customers;
```

The result contains every row from both tables. If you want to remove exact duplicates, use `UNION` instead of `UNION ALL`. Remember that `UNION` compares entire rows, so two rows with the same customer ID but different names are not considered duplicates.

The PySpark equivalent uses `union()`.

```python
# Read the active and archived customer tables.
df_active = spark.read.table("sales.active_customers")
df_archived = spark.read.table("sales.archived_customers")

# Combine both DataFrames.
# PySpark's union() behaves like UNION ALL: it keeps duplicates.
df_combined = df_active.union(df_archived)

# Remove duplicates if needed.
df_distinct = df_active.union(df_archived).distinct()

# Display both results.
display(df_combined)
display(df_distinct)
```

The PySpark `union()` keeps duplicates by default. To get the behavior of SQL `UNION`, you must call `distinct()` after the union.

### Finding common records across datasets

`INTERSECT` returns rows that appear in both inputs. It is useful for finding overlaps, such as customers who appear in two systems, or products listed in two catalogs. The comparison is on the entire row, so the rows must be identical in all selected columns.

The following SQL example finds customers who appear in both the active and archived tables.

```sql
-- Find customers that appear in both tables.
-- INTERSECT returns only rows that exist in both queries.
-- The comparison is on all selected columns.
SELECT customer_id, name, email FROM sales.active_customers
INTERSECT
SELECT customer_id, name, email FROM sales.archived_customers;
```

The PySpark equivalent uses `intersect()`.

```python
# Find rows that appear in both DataFrames.
df_intersect = df_active.intersect(df_archived)

# Display the result.
display(df_intersect)
```

If you only want to compare on `customer_id`, select only that column in both queries. Otherwise, differences in other columns will prevent a match.

### Identifying records unique to one dataset

`EXCEPT` returns rows from the first input that do not appear in the second. It is useful for finding gaps, such as customers who are in the active table but not in the archived table, or records missing from a replica. `MINUS` is a synonym for `EXCEPT` in Spark SQL.

The following SQL example finds active customers not in the archived table.

```sql
-- Find customers in the active table that are not in the archived table.
-- EXCEPT returns rows from the first query that do not appear in the second.
SELECT customer_id, name, email FROM sales.active_customers
EXCEPT
SELECT customer_id, name, email FROM sales.archived_customers;
```

The PySpark equivalent uses `subtract()`.

```python
# Find rows in the active DataFrame that are not in the archived DataFrame.
df_except = df_active.subtract(df_archived)

# Display the result.
display(df_except)
```

Again, the comparison is on all selected columns. To compare only on the key, select only the key in both queries.

## Comparing joins and set operators for similar tasks

Some tasks can be solved with either a join or a set operator, but the results differ in important ways. The following table compares the most common overlapping scenarios.

| Task | Join approach | Set operator approach | Key difference |
|---|---|---|---|
| Find rows in A that have a match in B | Semi join | `INTERSECT` | Semi join matches on a key; `INTERSECT` matches on the entire row |
| Find rows in A that have no match in B | Anti join | `EXCEPT` | Anti join matches on a key; `EXCEPT` matches on the entire row |
| Combine columns from A and B | Inner/left join | Not possible | Set operators cannot add columns |
| Stack rows from A and B | Not possible | `UNION ALL` | Joins cannot stack rows without a matching key |
| Find overlapping keys | Inner join on key | `INTERSECT` on key column only | Inner join can return duplicate rows if B has multiple matches; `INTERSECT` removes duplicates |

The table shows that the semi join and `INTERSECT` are similar but not identical. A semi join matches on a key and returns left rows that have at least one match. `INTERSECT` matches on the entire row and returns rows that are identical in all selected columns. If the right table has multiple rows with the same key but different other columns, a semi join returns the left row once, while `INTERSECT` returns nothing unless there is an exact row match. Similarly, an anti join and `EXCEPT` differ. An anti join returns left rows with no matching key. `EXCEPT` returns left rows that are not exact duplicates of any right row.

The following example shows the difference between a semi join and an `INTERSECT` when the right table has multiple rows per key.

```python
# Build a left DataFrame with one row per customer.
df_left = spark.createDataFrame([
    Row(customer_id=1, name="Alice"),
    Row(customer_id=2, name="Bob"),
])

# Build a right DataFrame with two rows for customer 1, with different names.
df_right = spark.createDataFrame([
    Row(customer_id=1, name="Alice"),
    Row(customer_id=1, name="Alicia"),
])

# Semi join on customer_id: returns Alice once because she has a match.
df_semi = df_left.join(df_right, on="customer_id", how="semi")
# df_semi contains one row: (1, Alice).

# INTERSECT on all columns: returns only exact matches.
df_intersect = df_left.intersect(df_right)
# df_intersect contains one row: (1, Alice), because that exact row
# appears in both DataFrames. The row (1, Alicia) is not in df_left.
```

The semi join returns Alice because she has a matching customer ID. The `INTERSECT` also returns Alice, but only because the exact row `(1, Alice)` exists in both. If the right table had only `(1, Alicia)`, the semi join would still return Alice, but the `INTERSECT` would return nothing. This is a crucial distinction. Use a semi join when the existence of the key is what matters. Use `INTERSECT` when the entire row must match.

## Null handling differences

Nulls behave differently in joins and set operators. In a join, a null key does not match any other key, including another null. The comparison `null = null` evaluates to null, which is not true, so the rows are not joined. In a set operator, nulls are treated as equal. Two rows with nulls in the same columns are considered duplicates for `UNION` and matches for `INTERSECT`.

The following example shows the difference.

```python
# Build two DataFrames with null values.
df_a = spark.createDataFrame([
    Row(id=1, name="Alice"),
    Row(id=2, name=None),
])
df_b = spark.createDataFrame([
    Row(id=2, name=None),
    Row(id=3, name="Bob"),
])

# Inner join on id: the row with id=2 does not match because
# the join is on id, and id=2 is not null. Both rows have id=2,
# so they do match on id. The null is in the name column, not the key.
df_join = df_a.join(df_b, on="id", how="inner")
# The result contains one row: (2, None, None).

# Intersect: the row (2, None) appears in both DataFrames.
# Nulls are treated as equal, so this row is returned.
df_intersect = df_a.intersect(df_b)
# The result contains one row: (2, None).
```

In this example, the join is on `id`, which is not null, so the rows match. The null in the `name` column does not affect the join because the join condition only compares `id`. If the join were on `name`, the nulls would not match. For set operators, the null in `name` is treated as equal to the other null, so the row is considered a match. Always consider how nulls will behave when choosing between a join and a set operator.

## Schema and data type considerations

Joins are flexible about schemas. The two inputs can have different numbers of columns and different column names. The join condition can reference any columns. The result contains columns from both inputs, and you select the ones you need. Set operators are strict. Both inputs must have the same number of columns, and the data types of corresponding columns must be compatible. The columns are matched by position, not by name. The result uses the column names from the first input.

This difference means that set operators require more careful preparation. You often need to select and cast columns so that the two inputs align. If the column order is different, the set operator will compare the wrong columns and produce incorrect results. The following example shows how to align columns before a union.

```sql
-- The two tables have the same columns but in a different order.
-- Select the columns explicitly in the same order for both queries.
SELECT customer_id, name, email FROM active_customers
UNION ALL
SELECT customer_id, name, email FROM archived_customers;
```

In PySpark, you can use `select()` to reorder and rename columns before calling `union()`.

```python
# Select and rename columns so that both DataFrames have the same schema.
df_active_aligned = df_active.select(
    col("id").alias("customer_id"),
    col("full_name").alias("name"),
    col("email_address").alias("email")
)
df_archived_aligned = df_archived.select(
    col("customer_id"),
    col("name"),
    col("email")
)

# Now the union is safe because the columns are aligned by position and name.
df_combined = df_active_aligned.union(df_archived_aligned)
```

Case sensitivity and time zones also affect both joins and set operators, but in different ways. For joins, string comparisons are case-sensitive by default, so `'ABC'` and `'abc'` do not match. For set operators, the same case sensitivity applies when comparing rows. If your data has inconsistent casing, normalize it before the operation. Time zones affect timestamp comparisons. In joins, timestamp comparisons use the internal UTC value, so the session time zone does not affect the join result. In set operators, timestamp values are compared as stored. If the timestamps were written in different time zones, they may not match even if they represent the same instant. Always store timestamps in UTC and convert to local time only for display.

## Performance considerations

Joins and set operators have different performance profiles. A join requires a shuffle unless one side is small enough to broadcast. During a shuffle, rows with the same join key are redistributed across the cluster. The shuffle is expensive because it writes data to disk and transfers it over the network. If one side of the join is small, Spark can broadcast it to all executors and avoid shuffling the large table. You can hint a broadcast join with `broadcast(df)` in PySpark or `/*+ BROADCAST(t) */` in SQL.

Set operators also have different costs. `UNION ALL` is the cheapest because it simply concatenates the partitions of the two inputs without redistributing data. It does not compare rows. `UNION`, `INTERSECT`, and `EXCEPT` require a shuffle to compare rows and remove duplicates. The shuffle redistributes data so that identical rows end up on the same partition. This is similar to the cost of a join.

The following table summarizes the performance characteristics.

| Operation | Shuffle required | Notes |
|---|---|---|
| Inner/left/right/full join | Yes, unless broadcast | Broadcast avoids shuffle when one side is small |
| Semi/anti join | Yes, unless broadcast | Can be more efficient than inner join because it does not materialize right columns |
| Cross join | Yes, unless broadcast | Produces Cartesian product; use with caution |
| `UNION ALL` | No | Simply concatenates partitions |
| `UNION` | Yes | Requires deduplication shuffle |
| `INTERSECT` | Yes | Requires comparison shuffle |
| `EXCEPT` | Yes | Requires comparison shuffle |

The table shows that `UNION ALL` is uniquely cheap. Use it whenever possible. For joins, use broadcast when one side is small. For set operators that require a shuffle, reduce the size of the inputs by filtering and selecting only the needed columns before the operation.

Delta Lake and Unity Catalog affect both. Delta Lake stores per-file statistics that can help the optimizer skip files during a join or a set operation. Unity Catalog applies row-level filters and column masks before the operation, which can change the result. In a medallion architecture, joins are used to enrich silver data into gold data, while set operators are used to combine data from multiple sources in the bronze or silver layer. Both operations write to Delta tables, and Delta Lake enforces the schema of the target table. If the result has a different schema, the write fails unless you enable schema evolution. Use `mergeSchema` only when you intend to evolve the schema.

## Best practices for choosing

Choose a join when you need to add columns from another table, match records on a key, or filter based on the existence of a key. Choose a set operator when you need to stack rows from tables with the same schema, find rows that are identical across datasets, or find rows unique to one dataset.

Use `UNION ALL` instead of `UNION` when duplicates are acceptable or known to be absent. `UNION ALL` avoids a shuffle and is much faster. Use `INTERSECT` and `EXCEPT` when the comparison is on the entire row. Use semi and anti joins when the comparison is on a key and you only need to filter the left table.

Align schemas before set operators. Ensure that both inputs have the same number of columns in the same order with compatible types. Select and cast columns explicitly to avoid silent mismatches.

Handle nulls deliberately. In joins, null keys do not match. In set operators, nulls are treated as equal. If nulls are present, decide whether they should match and choose the operation accordingly.

Filter and select before the operation. Reducing the size of the inputs reduces the shuffle for joins and the deduplication cost for set operators. Select only the columns you need.

Use broadcast joins for small dimension tables. This avoids shuffling the large fact table and can dramatically improve performance.

Test both approaches when the choice is not obvious. Build small datasets with known values, including nulls and duplicates, and verify that the result matches your expectations.

## Common mistakes and pitfalls

The most common mistake is using a join when a set operator is needed, or vice versa. For example, using an inner join to append two tables with the same schema will fail or produce a Cartesian product if the join condition is wrong. Using `UNION` to combine columns from two tables will not work because `UNION` does not add columns.

A second mistake is assuming that `UNION` in PySpark removes duplicates. It does not. PySpark's `union()` keeps duplicates. Use `distinct()` to remove them.

A third mistake is comparing on the wrong columns in a set operator. Set operators compare entire rows by position. If the columns are in a different order, the comparison is wrong. Always align the columns explicitly.

A fourth mistake is using a semi join when `INTERSECT` is needed. A semi join matches on a key and returns left rows with at least one match. `INTERSECT` returns rows that are identical in all selected columns. If the right table has multiple rows per key with different values, the two operations return different results.

A fifth mistake is forgetting that nulls do not match in joins. If your join keys contain nulls, those rows will not join. If you need them to match, handle the nulls explicitly before the join.

A sixth mistake is using `UNION` when `UNION ALL` would suffice. `UNION` requires a deduplication shuffle, which is expensive. If duplicates are acceptable or known to be absent, use `UNION ALL`.

## Testing strategies

Both joins and set operators are logic, and they should be tested. A test should verify the number of rows, the presence or absence of specific rows, and the handling of nulls and duplicates. The following example shows a test that compares a semi join and an `INTERSECT`.

```python
# Import the test helpers.
import pytest
from pyspark.sql import Row

# Build small DataFrames with known values.
# The right DataFrame has two rows for customer 1 with different names.
df_left = spark.createDataFrame([
    Row(customer_id=1, name="Alice"),
    Row(customer_id=2, name="Bob"),
])
df_right = spark.createDataFrame([
    Row(customer_id=1, name="Alice"),
    Row(customer_id=1, name="Alicia"),
])

# Semi join on customer_id: returns Alice once.
df_semi = df_left.join(df_right, on="customer_id", how="semi")
semi_ids = [row.customer_id for row in df_semi.collect()]
assert semi_ids == [1], f"Semi join failed: {semi_ids}"

# INTERSECT on all columns: returns only exact matches.
df_intersect = df_left.intersect(df_right)
intersect_rows = df_intersect.collect()
# The exact row (1, Alice) is in both, so it is returned.
assert len(intersect_rows) == 1, f"Intersect count failed: {len(intersect_rows)}"
assert intersect_rows[0].customer_id == 1 and intersect_rows[0].name == "Alice"
```

The test verifies that the semi join returns Alice and that the `INTERSECT` returns only the exact match. Run tests like this in your CI pipeline against a small local Spark session.

## An end-to-end example: reconciling customer data

Consider a scenario where you have two customer datasets: one from a CRM system and one from a billing system. You want to produce a single enriched view that includes all customers, with a flag indicating the source. You also want to find customers who appear in both systems and customers who appear in only one. The following example uses a combination of joins and set operators.

```python
# Import the functions needed.
from pyspark.sql.functions import col, lit

# Read the CRM and billing customer tables.
df_crm = spark.read.table("sales.crm_customers")
df_billing = spark.read.table("sales.billing_customers")

# Align the schemas so that both DataFrames have the same columns.
df_crm_aligned = df_crm.select(
    col("id").alias("customer_id"),
    col("name"),
    col("email")
).withColumn("source", lit("crm"))

df_billing_aligned = df_billing.select(
    col("customer_id"),
    col("name"),
    col("email")
).withColumn("source", lit("billing"))

# UNION ALL to stack all customers from both systems.
df_all = df_crm_aligned.union(df_billing_aligned)

# Find customers who appear in both systems using INTERSECT on the key.
df_both = (
    df_crm_aligned.select("customer_id")
    .intersect(df_billing_aligned.select("customer_id"))
)

# Find customers who are only in the CRM system using EXCEPT on the key.
df_crm_only = (
    df_crm_aligned.select("customer_id")
    .exceptAll(df_billing_aligned.select("customer_id"))
)

# Display the results.
display(df_all)
display(df_both)
display(df_crm_only)
```

The example shows how joins and set operators can be combined in a single pipeline. The `UNION ALL` stacks the customers. The `INTERSECT` finds customers in both systems. The `EXCEPT` finds customers only in the CRM. This is a common pattern for data reconciliation.

## Summary

The choice between joins and set operators depends on whether you need to combine columns or rows. A join combines columns from related tables horizontally, matching rows on a condition, usually a key. A set operator combines rows vertically, stacking or comparing entire result sets that have the same column structure.

Use joins when you need to enrich records by adding columns from related tables, match records based on key relationships, or filter data based on existence in another table using semi and anti joins. Use set operators when you need to append records from multiple sources with identical schemas, find common records across datasets using `INTERSECT`, or identify records unique to one dataset using `EXCEPT`.

Joins and set operators differ in null handling. In a join, null keys do not match. In a set operator, nulls are treated as equal. Joins are flexible about schemas; set operators require the same number of columns in the same order with compatible types. Joins often require a shuffle unless one side can be broadcast. `UNION ALL` does not require a shuffle, while `UNION`, `INTERSECT`, and `EXCEPT` do.

Best practices include using `UNION ALL` when possible, aligning schemas before set operators, choosing semi and anti joins for key-based existence checks, and using `INTERSECT` and `EXCEPT` for row-based comparisons. Common mistakes include assuming PySpark's `union()` removes duplicates, comparing on the wrong columns in a set operator, and forgetting that nulls behave differently. Testing with small datasets that include nulls and duplicates helps catch errors.

In a medallion architecture, joins enrich silver data into gold data, while set operators combine data from multiple sources in the bronze or silver layer. Both interact with Delta Lake and Unity Catalog, which enforce schema and apply policies. Used well, joins and set operators are complementary tools that form the foundation of effective data transformation pipelines.
