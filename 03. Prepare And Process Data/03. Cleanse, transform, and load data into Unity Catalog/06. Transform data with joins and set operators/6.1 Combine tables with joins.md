## Combine tables with joins

A join is an operation that combines rows from two tables or DataFrames based on a related column, called a join key. The join key establishes a relationship between the two datasets. For example, an orders table might contain a customer ID, and a customers table might contain the same customer ID along with customer details. A join uses that shared column to bring the two datasets together, producing a result that contains columns from both. In Azure Databricks, you can join tables with SQL using the `JOIN` clause, or you can join DataFrames with the PySpark `join()` method. Both surfaces produce the same kind of result and are executed by the same engine.

Joins matter because data is almost never stored in a single table. Relational databases and lakehouse tables are designed to avoid redundancy. Customer details are stored once in a customers table, and orders reference the customer by ID. To answer a question like "what is the total revenue per customer region," you must join the orders table to the customers table so that each order carries the region of its customer. Without joins, you would have to duplicate data across tables, which leads to inconsistency and wasted storage. Joins are the mechanism that reconstructs a complete picture from normalized data.

These notes cover joins from first principles. They explain each join type, including inner, left, right, full outer, semi, anti, and cross joins, and when to use each. They show how to write joins in SQL and in PySpark, how to handle duplicate column names, how nulls affect join keys, and how case sensitivity and time zones can change join results. They also cover performance considerations such as broadcast joins, shuffle joins, and data skew, and they explain how joins interact with Delta Lake, Unity Catalog, and the medallion architecture. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand not only how to write a join, but which join to write and how to avoid the mistakes that make joined results misleading.

## Understanding join types

The join type determines which rows appear in the result and how unmatched rows are handled. An inner join returns only rows that have a match in both tables. A left join returns all rows from the left table and adds nulls for the right table when there is no match. A right join returns all rows from the right table and adds nulls for the left table when there is no match. A full outer join returns all rows from both tables, adding nulls where there is no match on either side. A semi join returns rows from the left table that have a match in the right table, without including columns from the right table. An anti join returns rows from the left table that have no match in the right table. A cross join returns every possible combination of rows from both tables, also known as the Cartesian product.

The following table summarizes each join type, its behavior, and a typical use case.

| Join type | Description | Use case |
|---|---|---|
| `INNER` | Returns only matching rows from both tables | Link orders with valid customers |
| `LEFT` | Returns all left table rows; adds NULLs for right table when no match | Include all customers, even without orders |
| `RIGHT` | Returns all right table rows; adds NULLs for left table when no match | Include all departments, even without employees |
| `FULL` | Returns all rows from both tables; adds NULLs for non-matches | Combine datasets to find gaps on either side |
| `SEMI` | Returns left table rows that have matches in the right table | Filter customers who placed orders |
| `ANTI` | Returns left table rows that have no match in the right table | Find customers who never placed orders |
| `CROSS` | Returns Cartesian product of all rows | Generate all possible combinations |

The table shows that the join type is a business decision as much as a technical one. Choosing the wrong join type can silently drop rows or introduce nulls where you did not expect them. For example, if you use an inner join when you meant to keep all customers, you will lose customers who have no orders. If you use a left join when you meant to keep only matching rows, you will include rows with nulls that may break downstream calculations. Always decide which rows must appear in the result before you write the join.

### Inner joins

An inner join is the most common join type. It returns only the rows where the join condition is true in both tables. Rows that have no match are excluded from the result. In SQL, you write `INNER JOIN` or simply `JOIN`, which defaults to inner. In PySpark, you pass `how="inner"` to the `join()` method, which is also the default. The following SQL example joins an employee table to a department table on the department number.

```sql
-- Select employee columns and the department name.
-- The table aliases e and d make the query easier to read.
SELECT e.id, e.name, e.deptno, d.deptname
FROM employee e
-- INNER JOIN keeps only rows where the department number exists
-- in both the employee table and the department table.
-- Employees whose department number is not in the department table
-- are excluded from the result.
INNER JOIN department d ON e.deptno = d.deptno;
```

The query returns only employees whose department number exists in the department table. If an employee belongs to department 4, 5, or 6, and those departments are not in the department table, those employees do not appear. The `ON` clause specifies the join condition. The condition can use any comparison, but equality on a key column is the most common. The optimizer can use statistics and partitioning to make equality joins efficient.

The equivalent PySpark join uses the `join()` method with `how="inner"`. The following example shows the same join.

```python
# Read the employee and department tables from Unity Catalog.
# Both are Delta tables registered under the hr schema.
df_employee = spark.table("hr.employee")
df_department = spark.table("hr.department")

# Join the two DataFrames on the department number.
# how="inner" keeps only rows where the department number matches in both.
# The on parameter is a column expression that compares the two columns.
# Using the column expression form avoids ambiguity when both DataFrames
# have a column with the same name.
df_inner = df_employee.join(
    df_department,
    on=df_employee.deptno == df_department.deptno,
    how="inner"
)

# Display the joined result.
# The result contains columns from both DataFrames.
# Employees without a matching department are excluded.
display(df_inner)
```

The PySpark join produces the same result as the SQL inner join. The `on` parameter can be a column expression or a string. When the join column has the same name in both DataFrames, passing the column name as a string is simpler and avoids duplicate columns in the result. The following example shows the string form.

```python
# Join using the shared column name as a string.
# When the column name is the same in both DataFrames, passing the name
# as a string tells Spark to use that column for the join.
# The result contains only one copy of the join column, not two.
df_inner = df_employee.join(df_department, on="deptno", how="inner")

# Display the result.
# The deptno column appears once, followed by the other columns
# from both DataFrames.
display(df_inner)
```

The string form is cleaner when the column names match. If the column names differ, you must use a column expression or rename one of the columns before the join.

### Left, right, and full outer joins

A left join returns all rows from the left table and adds nulls for the right table when there is no match. A right join does the opposite. A full outer join returns all rows from both tables, adding nulls where there is no match on either side. These joins are used when you need to preserve rows that do not have a match. The following SQL example shows a left join that keeps all employees, even those without a department.

```sql
-- Select employee columns and the department name.
SELECT e.id, e.name, e.deptno, d.deptname
FROM employee e
-- LEFT JOIN keeps all rows from the left table (employee).
-- When there is no matching department, the deptname column is null.
-- This is useful for finding employees whose department is missing
-- from the department table.
LEFT JOIN department d ON e.deptno = d.deptno;
```

The query returns all employees. Employees with a matching department show the department name. Employees without a match show null in the `deptname` column. This is useful for auditing data quality. You can filter the result to show only rows where `d.deptname IS NULL` to find employees with invalid department numbers.

The equivalent PySpark left join uses `how="left"`.

```python
# Left join: keep all employees.
# The how parameter is set to "left" so that all rows from the left
# DataFrame (df_employee) are kept.
# Rows without a matching department get nulls in the department columns.
df_left = df_employee.join(df_department, on="deptno", how="left")

# Display the left join result.
display(df_left)
```

A right join is the mirror image. It keeps all rows from the right table. A full outer join keeps all rows from both tables. The following example shows both in PySpark.

```python
# Right join: keep all departments, even those without employees.
# The how parameter is set to "right" so that all rows from the right
# DataFrame (df_department) are kept.
# Employees without a matching department are excluded.
df_right = df_employee.join(df_department, on="deptno", how="right")

# Full outer join: keep all rows from both tables.
# The how parameter is set to "full" so that all rows from both
# DataFrames are kept. Rows without a match on either side get nulls
# in the columns from the other side.
df_full = df_employee.join(df_department, on="deptno", how="full")

# Display both results.
display(df_right)
display(df_full)
```

The full outer join is useful for reconciling two datasets. You can find rows that exist only in the left table, only in the right table, or in both. After a full outer join, you can filter on nulls in either side to identify gaps. For example, `df_full.filter(col("employee.id").isNull())` finds departments with no employees, and `df_full.filter(col("department.deptno").isNull())` finds employees with no department.

### Semi and anti joins

Semi and anti joins are filtering joins. They return rows from the left table based on the existence of a match in the right table, but they do not include columns from the right table. A semi join returns left rows that have a match. An anti join returns left rows that have no match. These joins are useful when you want to filter a dataset based on a condition in another dataset without bringing in extra columns. In SQL, the syntax is `LEFT SEMI JOIN` and `LEFT ANTI JOIN`. In PySpark, use `how="semi"` and `how="anti"`.

The following SQL example finds employees who belong to a listed department.

```sql
-- Find employees who belong to a department in the department table.
-- LEFT SEMI JOIN returns only the columns from the left table (employee).
-- It does not include any columns from the department table.
-- The result contains one row per matching employee, with no duplicates
-- even if the department table has multiple matching rows.
SELECT *
FROM employee
LEFT SEMI JOIN department ON employee.deptno = department.deptno;
```

The semi join is equivalent to an inner join followed by a `SELECT` of only the left table's columns, followed by a `DISTINCT`. However, the semi join is more efficient because Spark does not need to produce the extra columns or remove duplicates. The anti join is the opposite.

```sql
-- Find employees whose department is not listed in the department table.
-- LEFT ANTI JOIN returns only the columns from the left table.
-- It returns rows that have no match in the right table.
SELECT *
FROM employee
LEFT ANTI JOIN department ON employee.deptno = department.deptno;
```

The anti join is useful for finding orphaned records, such as orders with a customer ID that does not exist in the customers table. The following PySpark example shows both semi and anti joins.

```python
# Semi join: keep employees who have a matching department.
# how="semi" returns only the columns from the left DataFrame.
# The result has one row per matching employee, with no duplicates.
df_semi = df_employee.join(df_department, on="deptno", how="semi")

# Anti join: keep employees who have no matching department.
# how="anti" returns only the columns from the left DataFrame.
# The result has one row per employee without a match.
df_anti = df_employee.join(df_department, on="deptno", how="anti")

# Display both results.
display(df_semi)
display(df_anti)
```

Semi and anti joins are often faster than inner joins followed by filters because they can stop scanning the right table as soon as a match is found. They also avoid the cost of shuffling the right table's columns. Use them when you only need to filter the left table and do not need any columns from the right table.

### Cross joins

A cross join returns the Cartesian product of two tables. Every row from the left table is paired with every row from the right table. If the left table has 100 rows and the right table has 50 rows, the cross join produces 5,000 rows. Cross joins are rarely used in production because the result size grows multiplicatively. They are useful for generating combinations, such as pairing every product with every region to create a complete grid for a report. In SQL, you write `CROSS JOIN`. In PySpark, use `how="cross"`.

The following example shows a cross join.

```python
# Read the product and region tables.
df_product = spark.table("sales.product")
df_region = spark.table("sales.region")

# Cross join: pair every product with every region.
# how="cross" produces the Cartesian product.
# This is useful for generating a complete grid, but be careful:
# if the tables are large, the result can be enormous.
df_cross = df_product.join(df_region, how="cross")

# Display the cross join result.
# The result has (number of products) * (number of regions) rows.
display(df_cross)
```

A cross join can also be written in SQL as `CROSS JOIN` or by omitting the join condition in an inner join, but the explicit form is clearer. Because cross joins can produce very large results, always check the size of both tables before running one. If you need a cross join on large tables, consider whether the same result can be achieved with a different approach, such as generating the combinations in a controlled way or using a broadcast join with a small dimension table.

## Null handling in joins

Nulls affect joins in a way that often surprises people. In SQL and Spark, a null is not equal to any value, not even another null. This means that a join condition such as `left.key = right.key` does not match rows where both keys are null. The comparison `null = null` evaluates to null, which is not true, so the rows are not joined. This is different from some other systems where nulls are treated as equal for join purposes. In Spark, nulls never match in an equality join. If you need to join on null keys, you must handle the nulls explicitly before the join, for example by replacing them with a sentinel value using `coalesce()` or `fillna()`. However, be careful: replacing nulls with a sentinel can create false matches if the sentinel value also exists as a real key.

The following example shows how nulls behave in a join.

```python
# Build a small left DataFrame with a null key.
from pyspark.sql import Row
left_data = [
    Row(id=1, name="Alice"),
    Row(id=2, name="Bob"),
    Row(id=None, name="Charlie"),  # Null key.
]
df_left = spark.createDataFrame(left_data)

# Build a small right DataFrame with a null key.
right_data = [
    Row(id=1, dept="Sales"),
    Row(id=None, dept="Unknown"),  # Null key.
]
df_right = spark.createDataFrame(right_data)

# Inner join on the id column.
# The row with id=None in the left DataFrame does not match the row
# with id=None in the right DataFrame, because null = null is not true.
# Only the row with id=1 matches.
df_joined = df_left.join(df_right, on="id", how="inner")

# Display the result.
# Charlie and the Unknown department are not included.
display(df_joined)
```

The result contains only the row with `id=1`. The null keys do not match. If you want nulls to match, you must replace them before the join. For example, you could use `df_left.fillna({"id": -1})` and `df_right.fillna({"id": -1})`, but only if `-1` is not a valid ID. In general, it is better to understand why nulls exist in the key and whether they should participate in the join at all. Often, null keys indicate data quality issues that should be fixed at the source rather than handled in the join.

## Case sensitivity and time zone behavior

Case sensitivity affects joins on string keys. By default, Spark's string comparisons are case-sensitive, so `'ABC'` and `'abc'` are different values. If your data contains inconsistent casing, a join on a string key may fail to match rows that should match. You can normalize the keys before the join using `upper()` or `lower()`, or you can use a case-insensitive collation if the table is configured for one. Be aware that applying a function to the join key can prevent predicate pushdown and may force a full scan. If possible, normalize the data at write time so that the join key is stored in a consistent case.

Time zones affect joins on timestamp keys. Spark stores timestamps internally in UTC and displays them in the session time zone. When you join on a timestamp column, the comparison is performed on the internal UTC value, so the session time zone does not affect the join result. However, if you compare a timestamp to a string literal, the literal is interpreted in the session time zone. To avoid ambiguity, use timestamp literals with explicit offsets, or set the session time zone explicitly at the start of your job.

## Joins and Delta Lake, Unity Catalog, and the medallion architecture

Delta Lake stores data in Parquet files with a transaction log and per-file statistics. When you join two Delta tables, Spark reads the relevant files, shuffles the data so that rows with the same join key end up on the same partition, and then performs the join. If the join key aligns with the partitioning or clustering columns of the tables, Spark can reduce the shuffle by joining within partitions. This is one reason to choose partitioning and clustering columns based on the join keys you use most often.

Unity Catalog governs access to the tables you join. If a table has a row-level filter or column mask, those policies are applied before your query runs. The joined result reflects only the rows and column values you are allowed to see. This can make a join return fewer rows than expected. If you need to see all rows, you need a policy that grants access. Unity Catalog also records lineage, so you can see which tables a joined result depends on.

In a medallion architecture, joins are used to enrich data as it moves from silver to gold. Silver tables hold cleaned, normalized data. Gold tables often join several silver tables together to produce a denormalized, wide table that is optimized for analytics. For example, a gold sales table might join orders, customers, products, and regions to produce a single table with all the attributes needed for reporting. When you write a joined result to a Delta table, Delta Lake enforces the schema of the target table. If the join produces columns with different types or new columns, the write fails unless you enable schema evolution. Use `mergeSchema` only when you intend to evolve the schema, and be aware of the implications for downstream consumers.

## An end-to-end example: enriching orders with customer and product data

Consider a pipeline that reads orders from a silver table and enriches them with customer and product details to produce a gold table. The orders table contains customer IDs and product IDs. The customers table contains customer names and regions. The products table contains product names and categories. The pipeline joins the three tables and writes the result to a gold table.

```python
# Import the functions needed for the pipeline.
from pyspark.sql.functions import col

# Read the silver orders table.
df_orders = spark.read.table("sales.orders_silver")

# Read the customer and product dimension tables.
df_customers = spark.read.table("sales.customers")
df_products = spark.read.table("sales.products")

# Join orders to customers on customer_id.
# Use a left join to keep all orders, even if the customer is missing.
# This is important because we do not want to lose orders due to
# incomplete customer data.
df_enriched = df_orders.join(
    df_customers,
    on="customer_id",
    how="left"
)

# Join the result to products on product_id.
# Again, use a left join to keep all orders.
# The join adds product_name and category columns.
df_enriched = df_enriched.join(
    df_products,
    on="product_id",
    how="left"
)

# Select only the columns needed for the gold table.
# This reduces the size of the output and makes the schema explicit.
df_gold = df_enriched.select(
    "order_id",
    "order_date",
    "customer_id",
    "customer_name",
    "region",
    "product_id",
    "product_name",
    "category",
    "order_amount"
)

# Write the enriched data to a gold Delta table.
# mode("overwrite") replaces the table on each run.
df_gold.write.mode("overwrite").saveAsTable("sales.orders_enriched_gold")
```

The example joins three tables, selects the needed columns, and writes the result. The left joins ensure that no orders are lost if a customer or product is missing. The result is a denormalized table that is ready for reporting. If you needed to handle missing customers differently, you could use an inner join or add a filter after the join to inspect the nulls.

## Best practices

Choose the join type based on which rows must appear in the result. Use an inner join when you only want matching rows. Use a left join when you must keep all rows from the left table. Use a full outer join when you need to see gaps on both sides. Use semi and anti joins when you only need to filter the left table.

Join on columns with the same name using the string form when possible. This avoids duplicate columns and makes the query easier to read. If the column names differ, rename one of the columns before the join or use a column expression.

Filter early. If you can filter rows before the join, do so. A smaller input means a smaller shuffle and a faster join. Spark can sometimes push filters down, but writing them early makes the intent clear.

Select only the columns you need before or after the join. Column pruning reduces I/O and memory usage. If you join two wide tables and then select a few columns, the optimizer may prune the columns, but it is better to be explicit.

Be aware of nulls in join keys. Nulls do not match in equality joins. If null keys are valid in your data, decide whether they should match and handle them explicitly. Often, null keys indicate data quality issues that should be fixed upstream.

Use broadcast joins for small tables. If one side of the join is small enough to fit in memory, Spark can broadcast it to all executors and avoid a shuffle. You can hint a broadcast join with `broadcast(df)` in PySpark or `/*+ BROADCAST(t) */` in SQL. This is a major performance optimization.

Test your joins with small, known datasets that include edge cases such as null keys, duplicate keys, and missing matches. Joins are a common source of bugs, and tests catch them early.

## Common mistakes and pitfalls

The most common mistake is using an inner join when you meant to keep all rows from one side. This silently drops rows that have no match. Always ask which rows must appear in the result before choosing the join type.

A second mistake is joining on a column that is not unique in one of the tables. If the right table has multiple rows for the same key, the join produces multiple rows for each left row, which can inflate counts and sums. Check the cardinality of the join keys before joining. If you need only one row from the right table, deduplicate it first or use a window function to pick the latest row.

A third mistake is forgetting that nulls do not match. If your join keys contain nulls, those rows will not join. If you need them to match, handle the nulls explicitly before the join.

A fourth mistake is joining on a string key with inconsistent casing. `'ABC'` and `'abc'` do not match. Normalize the case before the join or use a case-insensitive collation.

A fifth mistake is using a cross join on large tables. A cross join produces the Cartesian product, which can be enormous. Always check the size of both tables before running a cross join.

A sixth mistake is not handling duplicate column names. When you join two DataFrames that have columns with the same name, the result contains both columns, which can cause ambiguity. Use the string form of the join to keep only one copy, or rename the columns before the join.

## Testing joins

Joins are business logic, and they should be tested. A test for a join should verify that the correct rows are returned for each join type, that nulls are handled as expected, and that duplicate keys do not produce unexpected row counts. The following example shows a test for an inner join and a left join.

```python
# Import the test helpers.
import pytest
from pyspark.sql import Row

# Build small DataFrames with known values.
# The left DataFrame has three rows, one with a null key.
# The right DataFrame has two rows, one with a null key.
left_data = [
    Row(id=1, name="Alice"),
    Row(id=2, name="Bob"),
    Row(id=None, name="Charlie"),
]
right_data = [
    Row(id=1, dept="Sales"),
    Row(id=None, dept="Unknown"),
]
df_left = spark.createDataFrame(left_data)
df_right = spark.createDataFrame(right_data)

# Inner join: only rows with matching non-null keys.
df_inner = df_left.join(df_right, on="id", how="inner")
inner_ids = [row.id for row in df_inner.collect()]
# Assert that only id=1 survives. The null key does not match.
assert inner_ids == [1], f"Inner join failed: {inner_ids}"

# Left join: all left rows, with nulls for missing right columns.
df_left_join = df_left.join(df_right, on="id", how="left")
left_join_rows = df_left_join.collect()
# Assert that the result has three rows, one for each left row.
assert len(left_join_rows) == 3, f"Left join row count failed: {len(left_join_rows)}"
# Assert that Charlie has a null department because the null key did not match.
charlie = [row for row in left_join_rows if row.name == "Charlie"][0]
assert charlie.dept is None, f"Charlie's dept should be null: {charlie.dept}"
```

The test verifies that the inner join excludes the null key and that the left join keeps all left rows and fills missing right columns with nulls. Run tests like this in your CI pipeline against a small local Spark session.

## Performance considerations

Joins are among the most expensive operations in a distributed query because they require a shuffle. During a shuffle, rows with the same join key are redistributed across the cluster so that they can be processed together. The shuffle writes data to disk and transfers it over the network. Reducing the amount of data that must be shuffled is the primary way to improve join performance.

Filter and select before the join. If you can reduce the number of rows or columns before the join, the shuffle is smaller. Spark can sometimes push filters and column pruning through the join, but explicit early filtering is more reliable.

Use broadcast joins for small tables. If one side of the join is small enough to fit in memory, Spark can broadcast it to all executors and avoid shuffling the large table. You can hint a broadcast join with `broadcast(df)` in PySpark or `/*+ BROADCAST(t) */` in SQL. The threshold for automatic broadcast is controlled by `spark.sql.autoBroadcastJoinThreshold`, which defaults to 10 MB. You can increase it if you have a larger dimension table and enough memory.

Be aware of data skew. If one join key appears much more frequently than others, the partitions handling that key will be much larger and will take longer to process. This is called skew. You can mitigate skew by salting the key, which adds a random suffix to the key before the join and then removes it after, or by using an adaptive query execution feature such as skew join optimization, which is enabled by default in recent Spark versions.

Partition and cluster tables on the join key. If both tables are partitioned or clustered on the join key, Spark can sometimes avoid a full shuffle by joining within partitions. This is most effective when the tables are large and the join key is commonly used.

Finally, use `explain()` to inspect the physical plan. The plan shows which join strategy Spark chose, whether a broadcast was used, and how many shuffles are required. This is the best way to understand and optimize a join.

## Summary

Joins combine rows from two tables or DataFrames based on a related column. The join type determines which rows appear in the result. An inner join returns only matching rows. A left join returns all rows from the left table and adds nulls for the right table when there is no match. A right join does the opposite. A full outer join returns all rows from both tables. A semi join returns left rows that have a match in the right table, without the right table's columns. An anti join returns left rows that have no match. A cross join returns the Cartesian product of all rows.

In SQL, joins are written with the `JOIN` clause and an `ON` or `USING` condition. In PySpark, the `join()` method takes the right DataFrame, a join condition, and a `how` parameter. When the join column has the same name in both DataFrames, passing the name as a string avoids duplicate columns. Nulls do not match in equality joins, so null keys are excluded unless handled explicitly. Case sensitivity and time zones affect string and timestamp joins.

Joins interact with Delta Lake, Unity Catalog, and the medallion architecture. Delta Lake stores statistics that can help the optimizer skip files, but the join key must be a raw column for the statistics to be used. Unity Catalog applies row-level filters and column masks before the join. In a medallion architecture, joins enrich silver data into gold data, often producing a denormalized table for reporting.

Best practices include choosing the join type based on which rows must appear, filtering and selecting before the join, using broadcast joins for small tables, and handling nulls explicitly. Common mistakes include using an inner join when a left join is needed, joining on non-unique keys, forgetting that nulls do not match, and using cross joins on large tables. Testing joins with small datasets that include nulls and duplicate keys catches regressions. Performance depends on the shuffle, so reduce data before the join, use broadcast joins when possible, and watch for skew. Used well, joins combine data from multiple tables into a single, coherent result that drives analysis and reporting.
