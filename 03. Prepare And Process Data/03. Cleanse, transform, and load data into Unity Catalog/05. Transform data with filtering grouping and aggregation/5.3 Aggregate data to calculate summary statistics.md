## Aggregate data to calculate summary statistics

Aggregation is the operation of taking many rows and producing a single value from them. When you count the orders in a region, sum the revenue for a product, or average the balance in a market segment, you are aggregating. In Azure Databricks, aggregation is expressed with aggregate functions such as `count()`, `sum()`, `avg()`, `min()`, and `max()`, applied either to a whole DataFrame or to the groups produced by `groupBy()` or `GROUP BY`. An aggregate function takes a set of input values and returns one output value, collapsing many rows into one. Without aggregation, a dataset can only be described row by row. With aggregation, it can be summarized at any level of granularity you choose.

Aggregation matters because summary statistics are how data becomes information. A table of ten million transactions is not directly useful to a decision maker, but the total revenue by month, the average order value by region, and the count of new customers by week are. Aggregation also reduces data volume dramatically. A billion-row silver table might collapse into a few thousand gold rows, one per group. That smaller result is cheaper to store, faster to scan, and easier to visualize. In a medallion architecture, aggregation is the step that produces the gold layer, the layer that dashboards, reports, and machine learning feature pipelines consume.

These notes cover aggregation from first principles. They explain the difference between aggregating a whole DataFrame and aggregating groups, the catalog of aggregate functions available in Spark SQL and PySpark, how nulls affect each function, how to write conditional aggregates that compute different statistics for different subsets in one pass, and how to filter groups with `HAVING`. They also cover statistical aggregates such as `stddev`, `variance`, `percentile`, and `approx_percentile`, the aggregate functions that return collections such as `collect_list` and `collect_set`, and how aggregation interacts with Delta Lake, Unity Catalog, and the medallion architecture. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand not only how to compute a summary statistic, but which statistic to compute and how to compute it correctly.

## Aggregating a whole DataFrame versus aggregating groups

Aggregation can be applied at two levels. The first level is the whole DataFrame, where every row is treated as belonging to a single group and the result is one row. The second level is grouped aggregation, where rows are partitioned by one or more columns and the result is one row per group. Whole-DataFrame aggregation answers questions like "how many rows are in this table" or "what is the total revenue across all orders." Grouped aggregation answers questions like "how many rows are in each region" or "what is the total revenue per product." Both use the same aggregate functions. The only difference is whether a grouping step precedes the aggregation.

In PySpark, you aggregate a whole DataFrame by calling `agg()` directly on it, without a preceding `groupBy()`. The result is a DataFrame with exactly one row. In SQL, you aggregate a whole table by using aggregate functions in the `SELECT` list without a `GROUP BY` clause. The result is a single row. The following example shows both forms.

```python
# Import the aggregate functions needed for the whole-DataFrame aggregation.
# count() counts rows. sum() totals a numeric column.
# avg() computes the arithmetic mean. min() and max() return extremes.
from pyspark.sql.functions import col, count, sum, avg, min, max

# Read the orders table from Unity Catalog.
# This is a Delta table registered under the sales schema.
df_orders = spark.read.table("sales.orders")

# Aggregate the entire DataFrame without grouping.
# Every row belongs to one implicit group, so the result has exactly one row.
# agg() accepts multiple expressions and computes them in a single pass.
df_summary = df_orders.agg(
    # Count all rows, including rows with null values in any column.
    count("*").alias("total_orders"),
    # Sum the order amounts, ignoring nulls.
    # If every order amount is null, the result is null, not zero.
    sum("order_amount").alias("total_revenue"),
    # Compute the average order amount, ignoring nulls.
    avg("order_amount").alias("avg_order_value"),
    # Find the smallest order amount, ignoring nulls.
    min("order_amount").alias("min_order_value"),
    # Find the largest order amount, ignoring nulls.
    max("order_amount").alias("max_order_value")
)

# Display the single-row result.
# The aggregation is lazy until display() triggers execution.
display(df_summary)
```

The example produces one row with five statistics. Each statistic is computed over the entire table. The aliases make the output columns readable. Without aliases, Spark would generate column names such as `sum(order_amount)`, which are awkward to reference downstream. The same computation in SQL looks like this.

```sql
-- Aggregate the entire orders table without a GROUP BY clause.
-- Every aggregate function collapses all rows into one value.
-- The result is a single row.
SELECT
  -- Count every row in the table, including rows with nulls.
  COUNT(*) AS total_orders,
  -- Sum the order amounts, ignoring nulls.
  SUM(order_amount) AS total_revenue,
  -- Compute the average order amount, ignoring nulls.
  AVG(order_amount) AS avg_order_value,
  -- Find the smallest order amount, ignoring nulls.
  MIN(order_amount) AS min_order_value,
  -- Find the largest order amount, ignoring nulls.
  MAX(order_amount) AS max_order_value
FROM sales.orders;
```

The SQL version is equivalent to the PySpark version. Both produce a single row. Both ignore nulls in the sum, average, min, and max. Both count all rows in `count(*)`. The choice between them is a matter of surrounding context. If the rest of your job is Python, use `agg()`. If the rest of your job is SQL, use the aggregate functions in a `SELECT` without `GROUP BY`.

Grouped aggregation adds a `groupBy()` call before `agg()`, or a `GROUP BY` clause after `FROM`. The result has one row per distinct combination of the grouping columns. The aggregate functions behave identically; they are simply applied to each group separately rather than to the whole table. The following example shows grouped aggregation with multiple statistics.

```python
# Import the aggregate functions used in the grouped aggregation.
from pyspark.sql.functions import count, sum, avg, max

# Read the order table.
df_orders = spark.read.table("sales.orders")

# Group by order priority.
# Each distinct priority becomes one group.
# groupBy() returns a GroupedData object, which must be aggregated.
df_grouped = df_orders.groupBy("o_orderpriority").agg(
    # Count the order keys in each group.
    # count("o_orderkey") counts only rows where the key is not null.
    count("o_orderkey").alias("order_count"),
    # Sum the total price in each group, ignoring nulls.
    sum("o_totalprice").alias("total_revenue"),
    # Compute the average total price in each group, ignoring nulls.
    avg("o_totalprice").alias("avg_order_value"),
    # Find the largest total price in each group, ignoring nulls.
    max("o_totalprice").alias("max_order")
)

# Display the grouped result.
# Each row represents one order priority.
display(df_grouped)
```

The example computes four statistics per group in a single pass over the data. Combining aggregates into one `agg()` call is important for performance. Each separate call to `count()`, `sum()`, or `avg()` on a `GroupedData` object would trigger a separate aggregation and a separate scan. The `agg()` method evaluates all expressions together. The equivalent SQL uses a `GROUP BY` clause.

```sql
-- Select the order priority and several aggregates.
-- o_orderpriority is in the GROUP BY clause, so it is valid in SELECT.
SELECT
  o_orderpriority,
  -- Count the order keys, which counts only non-null keys.
  COUNT(o_orderkey) AS order_count,
  -- Sum the total price per priority, ignoring nulls.
  SUM(o_totalprice) AS total_revenue,
  -- Compute the average total price per priority, ignoring nulls.
  AVG(o_totalprice) AS avg_order_value,
  -- Find the largest total price per priority, ignoring nulls.
  MAX(o_totalprice) AS max_order
FROM sales.orders
-- Group the rows by order priority.
-- Each distinct priority becomes one group.
GROUP BY o_orderpriority
-- Order the result by total revenue, largest first.
ORDER BY total_revenue DESC;
```

The SQL version produces the same result. The `GROUP BY` clause defines the groups, and the aggregate functions compute one value per group. The `ORDER BY` clause sorts the output for readability but does not affect the aggregation.

## The catalog of aggregate functions

Spark SQL and PySpark provide a rich set of aggregate functions. The most common are the counting, summing, averaging, and extreme-finding functions, but there are also statistical functions, collection-building functions, and functions that return the first or last value in a group. Understanding what each function does, and how it treats nulls, is essential for choosing the right one.

The following table summarizes the most widely used aggregate functions.

| Function | Returns | Null behavior | Typical use |
|---|---|---|---|
| `count(*)` | Number of rows in the group | Counts nulls | Row counts |
| `count(col)` | Number of non-null values | Ignores nulls | Count of valid values |
| `countDistinct(col)` | Number of distinct non-null values | Ignores nulls | Unique customers |
| `sum(col)` | Total of a numeric column | Ignores nulls | Revenue, quantity |
| `avg(col)` | Arithmetic mean | Ignores nulls | Average order value |
| `min(col)` | Smallest value | Ignores nulls | Earliest date, lowest price |
| `max(col)` | Largest value | Ignores nulls | Latest date, highest price |
| `first(col)` | First value in the group | Includes nulls | First event |
| `last(col)` | Last value in the group | Includes nulls | Most recent event |
| `stddev(col)` | Sample standard deviation | Ignores nulls | Spread of values |
| `variance(col)` | Sample variance | Ignores nulls | Spread of values |
| `collect_list(col)` | Array of all values | Includes nulls | Ordered list of events |
| `collect_set(col)` | Array of distinct values | Includes nulls | Distinct categories |
| `approx_count_distinct(col)` | Approximate distinct count | Ignores nulls | Cardinality estimation |

The table shows that functions differ in two important ways: what they return and how they treat nulls. `count(*)` counts every row, including rows where every column is null. `count(col)` counts only rows where the specified column is not null. `sum()`, `avg()`, `min()`, and `max()` ignore nulls, which means a group of all-null values produces a null result, not zero. `first()` and `last()` include nulls, which can be surprising if you expect them to skip nulls like the other aggregates. `collect_list()` and `collect_set()` include nulls in the resulting array. These differences are the source of many subtle bugs, and they are worth committing to memory.

The following example shows several of these functions in use on the same grouped data.

```python
# Import the aggregate functions used in this example.
# countDistinct counts unique non-null values.
# collect_set builds an array of distinct values.
# stddev computes the sample standard deviation.
from pyspark.sql.functions import (
    col, count, countDistinct, sum, avg,
    min, max, stddev, collect_set
)

# Read the order table.
df_orders = spark.read.table("sales.orders")

# Group by customer and compute a variety of statistics.
# Each aggregate produces one column in the result.
df_customer_stats = df_orders.groupBy("customer_id").agg(
    # Count all orders for this customer, including orders with null amounts.
    count("*").alias("order_count"),
    # Count distinct products this customer has ordered.
    # countDistinct ignores nulls, so orders with a null product_id
    # are not counted toward the distinct product total.
    countDistinct("product_id").alias("distinct_products"),
    # Sum the order amounts for this customer, ignoring nulls.
    sum("order_amount").alias("lifetime_value"),
    # Compute the average order amount for this customer, ignoring nulls.
    avg("order_amount").alias("avg_order_value"),
    # Find the earliest order date for this customer, ignoring nulls.
    min("order_date").alias("first_order_date"),
    # Find the latest order date for this customer, ignoring nulls.
    max("order_date").alias("last_order_date"),
    # Compute the sample standard deviation of order amounts.
    # This measures how spread out the customer's order values are.
    stddev("order_amount").alias("order_amount_stddev"),
    # Collect the distinct statuses this customer has seen.
    # collect_set returns an array and includes nulls if present.
    collect_set("order_status").alias("statuses_seen")
)

# Display the per-customer statistics.
# Each row represents one customer.
display(df_customer_stats)
```

The example computes eight statistics per customer in one pass. The `countDistinct` function counts unique products, which is different from counting orders. The `stddev` function measures the spread of order amounts. The `collect_set` function builds an array of distinct statuses. Each function has a specific purpose, and the choice depends on the question you are answering.

## Conditional aggregation

Conditional aggregation computes different statistics for different subsets of rows in a single pass. Instead of running multiple queries and joining the results, you embed a `CASE` expression or a boolean filter inside the aggregate function. The `CASE` expression returns a value only for rows that match the condition and null otherwise. Because most aggregate functions ignore nulls, only the matching rows contribute to the aggregate. This pattern is efficient because it scans the data once and produces all the statistics in a single result.

The following example computes the count of finished orders and the count of open orders in the same query.

```sql
-- Compute counts for different order statuses in a single pass.
SELECT
  region,
  -- Count only orders with status 'F'.
  -- The CASE expression returns 1 for matching rows and null otherwise.
  -- COUNT() ignores nulls, so only matching rows are counted.
  COUNT(CASE WHEN order_status = 'F' THEN 1 END) AS finished_count,
  -- Count only orders with status 'O'.
  COUNT(CASE WHEN order_status = 'O' THEN 1 END) AS open_count,
  -- Count only orders with status 'P'.
  COUNT(CASE WHEN order_status = 'P' THEN 1 END) AS pending_count,
  -- Sum the order amounts only for finished orders.
  -- The CASE expression returns the amount for finished orders and null otherwise.
  -- SUM() ignores nulls, so only finished orders contribute to the total.
  SUM(CASE WHEN order_status = 'F' THEN order_amount END) AS finished_revenue
FROM sales.orders
-- Group by region so that each row represents one region.
GROUP BY region;
```

The query produces one row per region with four statistics. The `CASE` expressions direct each row to the appropriate aggregate. Rows that do not match a condition contribute a null, which the aggregate ignores. This pattern is more efficient than running four separate queries and joining the results, because it scans the orders table only once.

The same pattern works in PySpark using the `when()` function from `pyspark.sql.functions`. The `when()` function is the PySpark equivalent of SQL's `CASE WHEN`.

```python
# Import the aggregate functions and the when() function.
# when() builds a conditional expression, the equivalent of SQL CASE WHEN.
from pyspark.sql.functions import col, count, sum, when

# Read the orders table.
df_orders = spark.read.table("sales.orders")

# Group by region and compute conditional aggregates.
# Each when() expression returns a value only for matching rows.
df_status_summary = df_orders.groupBy("region").agg(
    # Count finished orders. when() returns 1 for matching rows, null otherwise.
    # count() ignores nulls, so only finished orders are counted.
    count(when(col("order_status") == "F", 1)).alias("finished_count"),
    # Count open orders.
    count(when(col("order_status") == "O", 1)).alias("open_count"),
    # Count pending orders.
    count(when(col("order_status") == "P", 1)).alias("pending_count"),
    # Sum the order amounts for finished orders only.
    # when() returns the amount for matching rows, null otherwise.
    # sum() ignores nulls, so only finished orders contribute.
    sum(when(col("order_status") == "F", col("order_amount"))).alias("finished_revenue")
)

# Display the conditional summary.
display(df_status_summary)
```

The PySpark version is equivalent to the SQL version. The `when()` function builds the conditional expression, and the aggregate function ignores the nulls produced for non-matching rows. Conditional aggregation is a powerful technique because it lets you compute many statistics in one pass without joining separate queries.

## Filtering groups with HAVING

The `HAVING` clause filters groups after aggregation. It is different from `WHERE`, which filters rows before grouping. The distinction matters because aggregate functions do not exist until after grouping. You cannot reference an aggregate in a `WHERE` clause, and you cannot reference a raw column in a `HAVING` clause unless it is a grouping column. The following example shows both clauses in one query.

```sql
-- Find high-volume dealers and their total quantity.
SELECT
  id,
  -- Sum the quantity for each dealer.
  SUM(quantity) AS total_quantity,
  -- Count the orders for each dealer.
  COUNT(*) AS order_count
FROM dealer
-- Filter rows before grouping.
-- Keep only rows where quantity is positive.
-- This reduces the amount of data that is aggregated.
WHERE quantity > 0
-- Group the remaining rows by dealer id.
GROUP BY id
-- Filter groups after aggregation.
-- Keep only dealers whose total quantity exceeds 20.
-- HAVING operates on the aggregated result, not on individual rows.
HAVING SUM(quantity) > 20
-- Order the surviving groups by total quantity, largest first.
ORDER BY total_quantity DESC;
```

The `WHERE` clause removes rows with non-positive quantities before grouping. The `HAVING` clause removes groups whose total quantity is too small after aggregation. Both filters are necessary for different reasons. In PySpark, the equivalent is a `filter()` applied to the aggregated DataFrame.

```python
# Import the aggregate functions.
from pyspark.sql.functions import col, sum, count

# Read the dealer table.
df_dealer = spark.read.table("sales.dealer")

# Filter rows before grouping to reduce the input size.
# Keep only rows where quantity is positive.
df_filtered = df_dealer.filter(col("quantity") > 0)

# Group by dealer id and compute the total quantity and order count.
df_grouped = df_filtered.groupBy("id").agg(
    # Sum the quantity for each dealer.
    sum("quantity").alias("total_quantity"),
    # Count all orders for each dealer.
    count("*").alias("order_count")
)

# Filter groups after aggregation.
# This is the equivalent of the SQL HAVING clause.
# Keep only dealers whose total quantity exceeds 20.
df_final = df_grouped.filter(col("total_quantity") > 20)

# Order the surviving groups by total quantity, descending.
df_final = df_final.orderBy(col("total_quantity").desc())

# Display the final result.
display(df_final)
```

The PySpark version separates the row filter from the group filter, just as the SQL version separates `WHERE` from `HAVING`. The row filter is applied before `groupBy()`, and the group filter is applied after `agg()`. Applying the group filter before aggregation would be a type error, because the aggregated column does not exist yet.

## Statistical aggregates

Spark SQL and PySpark provide statistical aggregate functions for computing measures of spread and association. `stddev()` and `variance()` measure how spread out the values in a group are. `corr()` and `covar()` measure the relationship between two numeric columns. `percentile()` and `approx_percentile()` return the value below which a given percentage of values fall. `skewness()` and `kurtosis()` measure the shape of the distribution.

The following table summarizes the statistical aggregates.

| Function | Returns | Null behavior | Typical use |
|---|---|---|---|
| `stddev(col)` | Sample standard deviation | Ignores nulls | Spread of values |
| `stddev_pop(col)` | Population standard deviation | Ignores nulls | Spread of full population |
| `variance(col)` | Sample variance | Ignores nulls | Squared spread |
| `var_pop(col)` | Population variance | Ignores nulls | Squared spread |
| `corr(x, y)` | Pearson correlation | Ignores rows where either is null | Linear relationship |
| `covar_samp(x, y)` | Sample covariance | Ignores rows where either is null | Joint variability |
| `percentile(col, p)` | Exact percentile | Ignores nulls | Median, quartiles |
| `approx_percentile(col, p)` | Approximate percentile | Ignores nulls | Fast median on large data |
| `skewness(col)` | Skewness of the distribution | Ignores nulls | Asymmetry |
| `kurtosis(col)` | Kurtosis of the distribution | Ignores nulls | Tail heaviness |

The following example computes the median order amount and the standard deviation of order amounts per region.

```python
# Import the statistical aggregate functions.
# approx_percentile computes percentiles efficiently on large data.
# stddev computes the sample standard deviation.
# count computes the number of rows in each group.
from pyspark.sql.functions import (
    col, count, stddev, approx_percentile, percentile
)

# Read the orders table.
df_orders = spark.read.table("sales.orders")

# Group by region and compute statistical summaries.
df_stats = df_orders.groupBy("region").agg(
    # Count the orders in each region.
    count("*").alias("order_count"),
    # Compute the sample standard deviation of order amounts.
    # stddev measures how spread out the values are around the mean.
    stddev("order_amount").alias("amount_stddev"),
    # Compute the exact median using percentile() with p=0.5.
    # percentile() is exact but can be expensive on large groups.
    percentile("order_amount", 0.5).alias("median_amount_exact"),
    # Compute the approximate median using approx_percentile().
    # approx_percentile() is much faster and is accurate to within
    # a small relative error controlled by the accuracy parameter.
    approx_percentile("order_amount", 0.5).alias("median_amount_approx")
)

# Display the statistical summary.
display(df_stats)
```

The example computes both exact and approximate medians. The `percentile()` function is exact but requires sorting all values in each group, which is expensive on large datasets. The `approx_percentile()` function uses a sketch-based algorithm that is much faster and uses less memory, at the cost of a small approximation error. For large datasets, `approx_percentile()` is usually the right choice. For small datasets or when exact values are required, use `percentile()`.

## Aggregate functions that return collections

Some aggregate functions return collections rather than scalar values. `collect_list()` returns an array of all values in the group, including duplicates and nulls. `collect_set()` returns an array of distinct values, including nulls if present. These functions are useful when you need to preserve the individual values rather than reduce them to a single number. For example, you might want a list of all product IDs a customer has purchased, or a set of all statuses an order has passed through.

The following example shows both functions in use.

```python
# Import the collection aggregate functions.
# collect_list returns an array of all values.
# collect_set returns an array of distinct values.
from pyspark.sql.functions import col, collect_list, collect_set

# Read the orders table.
df_orders = spark.read.table("sales.orders")

# Group by customer and collect the products and statuses.
df_collected = df_orders.groupBy("customer_id").agg(
    # Collect all product IDs for this customer as an array.
    # collect_list includes duplicates, so a product ordered twice
    # appears twice in the array. The order is not guaranteed.
    collect_list("product_id").alias("all_products"),
    # Collect the distinct product IDs for this customer as an array.
    # collect_set removes duplicates. The order is not guaranteed.
    collect_set("product_id").alias("distinct_products"),
    # Collect the distinct order statuses this customer has seen.
    collect_set("order_status").alias("statuses_seen")
)

# Display the collected arrays.
# Each row represents one customer and contains arrays of values.
display(df_collected)
```

The example shows the difference between `collect_list()` and `collect_set()`. `collect_list()` preserves duplicates, while `collect_set()` removes them. Neither function guarantees the order of the resulting array. If you need a specific order, sort the array after collecting it, or use a window function to order the rows before aggregation. Be careful with these functions on large groups. They bring all values into a single row, which can exhaust memory if the group is very large. Use them only when the group size is bounded.

## Null handling in aggregation

Null handling is the most important detail in aggregation. Every aggregate function has a defined behavior with nulls, and using the wrong function can produce a result that looks plausible but is wrong. The key rules are as follows. `count(*)` counts all rows, including rows with nulls. `count(col)` counts only non-null values. `sum()`, `avg()`, `min()`, and `max()` ignore nulls. If every value in a group is null, `sum()` and `avg()` return null, not zero. `first()` and `last()` include nulls, so they may return null even when non-null values exist in the group. `collect_list()` and `collect_set()` include nulls in the resulting array.

The following example demonstrates these behaviors.

```python
# Import the aggregate functions.
from pyspark.sql.functions import col, count, sum, avg, first, last

# Build a small DataFrame with a group that contains nulls.
# The group 'A' has two non-null values and one null value.
# The group 'B' has only null values, which tests the all-null case.
from pyspark.sql import Row
test_data = [
    Row(grp="A", amount=100),
    Row(grp="A", amount=200),
    Row(grp="A", amount=None),
    Row(grp="B", amount=None),
]
df_test = spark.createDataFrame(test_data)

# Group by grp and apply several aggregates.
df_result = df_test.groupBy("grp").agg(
    # Count all rows, including the null amount.
    # Group A has 3 rows, group B has 1 row.
    count("*").alias("row_count"),
    # Count only non-null amounts.
    # Group A has 2 non-null amounts, group B has 0.
    count("amount").alias("non_null_count"),
    # Sum the amounts, ignoring nulls.
    # Group A sums to 300. Group B has no non-null values, so the sum is null.
    sum("amount").alias("total"),
    # Average the amounts, ignoring nulls.
    # Group A averages to 150. Group B has no non-null values, so the average is null.
    avg("amount").alias("average"),
    # Take the first value in the group, including nulls.
    # The result depends on the order of rows and is not deterministic
    # unless the data is sorted first.
    first("amount").alias("first_amount"),
    # Take the last value in the group, including nulls.
    last("amount").alias("last_amount")
)

# Display the results.
# Pay attention to the differences between the count columns and
# the null results for group B.
display(df_result)
```

The example shows that group B, which contains only a null value, has a row count of 1 and a non-null count of 0. Its sum and average are null, not zero. This is a common source of confusion. If you want a sum of zero for a group with no non-null values, wrap the sum in `coalesce()`. The following example shows how.

```python
# Import coalesce and lit.
# coalesce returns the first non-null argument.
# lit creates a literal column value.
from pyspark.sql.functions import col, sum, coalesce, lit

# Read the orders table.
df_orders = spark.read.table("sales.orders")

# Group by region and compute a sum that defaults to zero.
df_result = df_orders.groupBy("region").agg(
    # Sum the order amounts, ignoring nulls.
    # If every amount in a region is null, the sum is null.
    # coalesce replaces that null with zero.
    coalesce(sum("order_amount"), lit(0)).alias("total_revenue")
)

# Display the result.
# Regions with no non-null amounts now show zero instead of null.
display(df_result)
```

The `coalesce()` function returns the first non-null argument. When the sum is null, `coalesce()` returns the literal zero. This is the correct way to produce a zero total for empty groups. Do not use `fillna()` on the aggregated result unless you understand which columns can legitimately contain nulls, because `fillna()` will replace all nulls, including nulls that carry meaning.

## Aggregation and Delta Lake, Unity Catalog, and the medallion architecture

Aggregation is a transformation, not a storage feature, but it interacts with the lakehouse in important ways. Delta Lake stores data in Parquet files with a transaction log and per-file statistics. When you aggregate a Delta table, Spark reads the relevant files, shuffles the data so that rows with the same grouping key end up on the same partition, and computes the aggregates. The shuffle is the expensive part. If the grouping columns align with the table's partitioning or clustering columns, Spark can sometimes reduce the shuffle by aggregating within each partition first. This is one reason to choose partitioning and clustering columns based on the grouping keys you use most often.

Unity Catalog governs access to the tables you aggregate. If a table has a row-level filter or column mask, those policies are applied before your query runs. The aggregated result reflects only the rows and column values you are allowed to see. This can make a count or sum smaller than the true value in the table, and that is the intended behavior. If you need the true total, you need a policy that grants access to all rows. Unity Catalog also records lineage, so you can see which tables an aggregated result depends on.

In a medallion architecture, aggregation is the primary operation that turns silver data into gold data. Silver tables hold cleaned, row-level data. Gold tables hold aggregated data, often grouped by time, geography, product, or customer segment. Gold tables are typically much smaller than silver tables because aggregation collapses many rows into few. They are also denormalized, meaning they contain the grouping columns and the aggregates, and they are optimized for the queries that dashboards run. When you build a gold table, you aggregate the silver data, apply the statistics the business needs, and write the result as a Delta table. Because the gold table is small, you can often use `overwrite` mode to replace it entirely on each refresh, or `merge` mode to update only changed groups.

## An end-to-end example: building a gold table

Consider a pipeline that ingests raw order events into a bronze Delta table, cleans them into a silver table, and aggregates them into a gold table that reports daily sales by region and product category. The gold table should contain the order count, total revenue, average order value, and distinct customer count for each combination of date, region, and category. The following example shows the aggregation step that builds the gold table.

```python
# Import the aggregate functions needed for the gold table.
# countDistinct counts unique non-null values, which is used for customers.
# round rounds a numeric value to a specified number of decimal places.
from pyspark.sql.functions import (
    col, count, countDistinct, sum, avg, round
)

# Read the silver table, which holds cleaned, row-level order data.
# Silver data has already been filtered for nulls and invalid values.
df_silver = spark.read.table("sales.orders_silver")

# Aggregate the silver data into the gold summary.
# The grouping columns define the granularity of the gold table.
# Each distinct combination of date, region, and category becomes one row.
df_gold = df_silver.groupBy(
    "order_date",   # The date of the order, already truncated to day level.
    "region",       # The sales region.
    "category"      # The product category.
).agg(
    # Count all orders in each group.
    count("*").alias("order_count"),
    # Sum the order amounts, ignoring nulls.
    # This is the total revenue for the group.
    sum("order_amount").alias("total_revenue"),
    # Compute the average order amount, ignoring nulls.
    # round() rounds to 2 decimal places to keep the gold table tidy.
    round(avg("order_amount"), 2).alias("avg_order_value"),
    # Count distinct customers in each group.
    # countDistinct ignores nulls, so orders with a null customer_id
    # do not contribute to the distinct customer count.
    countDistinct("customer_id").alias("distinct_customers")
)

# Write the aggregated result to the gold table.
# mode("overwrite") replaces the table contents on each run.
# In production you would use merge to update only changed groups,
# or partition the gold table by order_date for efficient refreshes.
df_gold.write.mode("overwrite").saveAsTable("sales.daily_sales_gold")
```

The example reads silver, groups by three columns, computes four statistics, and writes the result to gold. The grouping columns define the granularity. The statistics answer the business questions. The gold table is much smaller than the silver table because the aggregation collapses many order rows into one row per date, region, and category. This is the pattern that powers most dashboards and reports.

## Best practices

Combine multiple aggregates into a single `agg()` call or a single `SELECT` with multiple aggregate functions. Each separate aggregation triggers a separate pass over the data. Combining them computes all statistics in one pass, which reduces the amount of data scanned.

Alias every aggregate column. Without aliases, Spark generates column names such as `sum(order_amount)`, which are awkward to reference in downstream code. Use clear, descriptive aliases such as `total_revenue` or `order_count`.

Use `coalesce()` to convert null sums and averages to zero when zero is the correct business meaning. A sum of no values is undefined, and Spark represents it as null. If the business expects zero, make that explicit.

Prefer `approx_percentile()` over `percentile()` on large datasets. The approximate function is much faster and uses less memory, and the approximation error is small enough for most analytical purposes.

Use `countDistinct()` or `approx_count_distinct()` instead of `collect_set().size()` when you only need the count of distinct values. Collecting the values into an array and then taking the size is much more expensive than counting distinct values directly.

Be explicit about null handling in every aggregate. Remember that `sum()` and `avg()` ignore nulls and return null when all values are null. Remember that `count(*)` and `count(col)` behave differently. Document the intended behavior in a comment.

Test aggregation logic with small, known DataFrames that include nulls, empty groups, and boundary values. Aggregation bugs are subtle and often produce plausible-looking results, so tests are essential.

## Common mistakes and pitfalls

The most common mistake is confusing `count(*)` with `count(col)`. `count(*)` counts every row in the group, including rows where the specified column is null. `count(col)` counts only rows where the column is not null. If you want to count how many orders have a non-null customer ID, use `count(customer_id)`, not `count(*)`.

A second mistake is assuming that a sum of nulls is zero. `sum()` of a column where every value is null returns null, not zero. If you need zero, use `coalesce(sum(col), lit(0))`. This is especially important when the result feeds into a calculation that cannot handle nulls.

A third mistake is using `first()` or `last()` and expecting a deterministic result. These functions return the first or last value encountered, but the order of rows in a distributed DataFrame is not guaranteed unless you explicitly sort the data before aggregating. If you need the value associated with the minimum or maximum of another column, use a window function or a `min_by`/`max_by` aggregate instead.

A fourth mistake is using `collect_list()` or `collect_set()` on large groups. These functions bring all values into a single row, which can exhaust memory. Use them only when the group size is bounded and small. For large groups, use an aggregate that returns a single value.

A fifth mistake is applying a `WHERE` clause to an aggregate. `WHERE COUNT(*) > 10` is invalid because the count does not exist until after grouping. Use `HAVING COUNT(*) > 10` in SQL, or apply a `filter()` to the aggregated DataFrame in PySpark.

A sixth mistake is grouping by a raw timestamp without truncating it. Grouping by a raw timestamp produces one group per distinct timestamp value, which is almost never what you want. Use `date_trunc()` or `to_date()` to group by day, month, or year.

## Testing aggregate logic

Aggregate logic is business logic, and it should be tested. A test for an aggregate should verify that each statistic returns the expected value for known inputs, including edge cases such as nulls, empty groups, and boundary values. The following example shows a test for a conditional aggregate.

```python
# Import the test helpers and aggregate functions.
import pytest
from pyspark.sql import Row
from pyspark.sql.functions import col, count, sum, when

# Build a small DataFrame with known values.
# The data includes finished and open orders in two regions,
# plus a null amount to test null handling in the sum.
test_data = [
    Row(region="East", status="F", amount=100),   # Finished, counts toward revenue.
    Row(region="East", status="O", amount=200),   # Open, excluded from revenue.
    Row(region="East", status="F", amount=None),  # Finished but null amount.
    Row(region="West", status="F", amount=50),    # Finished, counts toward revenue.
]
df_test = spark.createDataFrame(test_data)

# Define the transformation to test.
# Group by region and compute conditional counts and sums.
def summarize(df):
    return df.groupBy("region").agg(
        # Count finished orders. when() returns 1 for matching rows.
        count(when(col("status") == "F", 1)).alias("finished_count"),
        # Sum amounts only for finished orders.
        # The null amount for the third East row is ignored by sum().
        sum(when(col("status") == "F", col("amount"))).alias("finished_revenue")
    )

# Run the transformation and collect the results into a dictionary.
result = {
    row.region: (row.finished_count, row.finished_revenue)
    for row in summarize(df_test).collect()
}

# Assert that East has two finished orders but revenue of only 100,
# because the second finished order has a null amount that sum() ignores.
assert result["East"] == (2, 100), f"East failed: {result['East']}"
# Assert that West has one finished order with revenue of 50.
assert result["West"] == (1, 50), f"West failed: {result['West']}"
```

The test verifies both the count and the sum for each region. The East region has two finished orders, but the sum is only 100 because one of the finished orders has a null amount that `sum()` ignores. This is exactly the kind of subtle behavior that tests should capture. If someone later changes the sum to `coalesce(sum(...), lit(0))`, the test would still pass because the sum is not null. If someone changes the count to `count(*)`, the test would fail because the count would include the open order. Run tests like this in your CI pipeline against a small local Spark session.

## Performance considerations

Aggregation requires a shuffle, which is the most expensive operation in a distributed query. During a shuffle, rows are redistributed across the cluster so that all rows with the same grouping key end up on the same partition. The shuffle writes data to disk and transfers it over the network. Reducing the amount of data that must be shuffled is the primary way to improve aggregation performance.

Filter rows before aggregating whenever possible. A `WHERE` clause that removes half the rows also halves the shuffle size. If you are aggregating a large table and only need a subset of rows, filter first.

Group on columns that are already partitioned or clustered in the Delta table. If the table is partitioned by date and you group by date, Spark can often reduce the shuffle by aggregating within each partition and then combining the partial results. If you group by a column that is not aligned with the partitioning, a full shuffle is required.

Combine multiple aggregates into a single `agg()` call. Each separate aggregation triggers a separate scan and a separate shuffle. Combining them computes all statistics in one pass.

Use `approx_count_distinct()` instead of `countDistinct()` when an approximate count is acceptable. Exact distinct counting requires a large state and can be slow on high-cardinality columns. The approximate function uses a sketch that is much smaller and faster.

Be careful with high-cardinality grouping columns. Grouping by a column with millions of distinct values produces millions of groups, each with a small number of rows. The shuffle is large, and the aggregation overhead per group is high. If you need to group by a high-cardinality column, consider whether you can pre-aggregate at a coarser level first, or whether you can use a different approach.

Avoid `collect_list()` and `collect_set()` on large groups. These functions bring all values into a single row, which can cause out-of-memory errors. If you need to collect values, ensure the group size is bounded, or use a different aggregation that returns a single value.

## Summary

Aggregation calculates summary statistics such as counts, sums, averages, and extremes from a set of rows. In Azure Databricks, you aggregate with aggregate functions in SQL or with the `agg()` method in PySpark. You can aggregate a whole DataFrame, which produces a single row, or aggregate groups produced by `groupBy()` or `GROUP BY`, which produces one row per group. Aggregate functions include `count()`, `sum()`, `avg()`, `min()`, `max()`, `countDistinct()`, `stddev()`, `variance()`, `percentile()`, `approx_percentile()`, `collect_list()`, and `collect_set()`.

Null handling is the most important detail. `count(*)` counts all rows, including nulls. `count(col)` counts only non-null values. `sum()`, `avg()`, `min()`, and `max()` ignore nulls and return null when every value in the group is null. `first()` and `last()` include nulls and are not deterministic unless the data is sorted. `collect_list()` and `collect_set()` include nulls in the resulting array. Use `coalesce()` to convert null sums to zero when zero is the correct business meaning.

Conditional aggregation computes different statistics for different subsets in a single pass by embedding a `CASE` expression or a `when()` function inside the aggregate. The `HAVING` clause filters groups after aggregation, while `WHERE` filters rows before grouping. Statistical aggregates such as `stddev()`, `variance()`, `corr()`, and `approx_percentile()` measure spread, association, and distribution shape. Aggregate functions that return collections are useful for preserving individual values but must be used with care on large groups.

In a medallion architecture, aggregation is the primary operation that turns cleaned silver data into aggregated gold data. Delta Lake and Unity Catalog affect aggregation through file statistics, partitioning, row-level filters, and column masks. Best practices include combining aggregates into a single call, aliasing aggregate columns, using `coalesce()` for null sums, preferring approximate functions on large data, and testing aggregation logic with edge cases. Common mistakes include confusing `count(*)` with `count(col)`, assuming a sum of nulls is zero, expecting deterministic results from `first()` and `last()`, using `collect_list()` on large groups, and applying `WHERE` to aggregates instead of `HAVING`. Performance depends on the shuffle, so filter early, align grouping columns with partitioning, and avoid high-cardinality keys when possible. Used well, aggregation turns large row-level datasets into concise, meaningful summaries that drive analysis and reporting.
