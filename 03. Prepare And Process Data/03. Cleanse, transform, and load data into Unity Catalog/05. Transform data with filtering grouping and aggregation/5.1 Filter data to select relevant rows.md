## Filter data to select relevant rows

Filtering is the operation of removing rows from a dataset that do not satisfy a condition you specify. In Azure Databricks, the data you work with is typically held either in a Spark DataFrame, which is a distributed collection of rows organized into named columns, or in a Delta table, which is a table stored in the lakehouse with transactional guarantees. When you filter, you do not modify the original data. Instead, you produce a new DataFrame, or a new result set, that contains only the rows matching your predicate. A predicate is a logical expression that evaluates to true, false, or null for each row. Rows that evaluate to true are kept. Rows that evaluate to false or null are removed, because SQL and Spark use three-valued logic, a point that becomes important when nulls are present.

Filtering matters because it reduces the volume of data that moves through the rest of your pipeline. A smaller dataset is faster to process, cheaper to store and scan, and easier to reason about. In a medallion architecture, where raw data lands in a bronze layer, is cleaned into a silver layer, and is aggregated into a gold layer, filtering is one of the first operations applied as data moves from bronze to silver. Removing malformed rows, out-of-range values, or rows belonging to test accounts early means every downstream transformation works on a smaller and more trustworthy input. Filtering also shapes correctness. A query that joins two tables without filtering can multiply rows and produce misleading aggregates, so filtering before a join is often the difference between an accurate result and a wrong one.

These notes cover the two main ways to filter in Databricks: the PySpark DataFrame API and SQL. They explain the methods `filter()` and `where()`, the `col()` function, the logical operators used to combine conditions, and the SQL `WHERE` clause. They then treat null handling in depth, because null comparisons behave differently from comparisons on ordinary values and are a frequent source of bugs. The notes also cover data types, case sensitivity, time zone behavior, predicate pushdown, and how filtering interacts with Delta Lake, Unity Catalog, and the medallion architecture. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand not only how to filter, but when to filter and why a particular approach is correct.

## The two filtering surfaces: DataFrame API and SQL

Databricks gives you two surfaces for expressing a filter, and they are equivalent in power. The first is the PySpark DataFrame API, a set of Python methods that build a logical plan which the Spark optimizer then compiles and executes. The second is SQL, which you write either against a table, a view, or a temporary view registered from a DataFrame. Both surfaces produce the same kind of result, and both are executed by the same engine, so the choice between them is usually about readability and the surrounding context rather than about capability. If the rest of your job is written in Python, use the DataFrame API. If the rest of your job is written in SQL, use `WHERE`. Mixing them is allowed, and `spark.sql()` lets you run SQL and receive a DataFrame back.

The two surfaces differ in a few practical ways. The DataFrame API is composable, meaning you can chain filters with other transformations and store intermediate results in Python variables. SQL is declarative, meaning you describe the result you want and let the optimizer decide how to produce it. SQL is often more readable when the logic involves multiple joins or window functions. The DataFrame API is often more readable when the logic depends on Python control flow, such as building a list of values to filter against. The table below summarizes the comparison.

| Aspect | PySpark DataFrame API | SQL |
|---|---|---|
| Entry point | `df.filter(...)` or `df.where(...)` | `WHERE ...` clause or `spark.sql("... WHERE ...")` |
| Returns | A new DataFrame | A result set or DataFrame from `spark.sql()` |
| Combining conditions | `&` for AND, `|` for OR, `~` for NOT | `AND`, `OR`, `NOT` |
| Null checks | `isNull()`, `isNotNull()` | `IS NULL`, `IS NOT NULL` |
| Readability with Python logic | Strong | Weak, because SQL is embedded as a string |
| Readability with joins and windows | Moderate | Strong |
| Lazy evaluation | Yes, until an action is called | Yes, when returning a DataFrame |

The table shows that the two surfaces are close to interchangeable, with the tradeoff being where the logic lives. Neither is universally better. The rest of these notes treats both as first-class and shows each example in both forms where the topic applies.

## Filtering with the PySpark DataFrame API

The PySpark DataFrame API exposes two methods for filtering: `filter()` and `where()`. They are aliases, meaning they do exactly the same thing and differ only in name. Use whichever reads better in your code. The `col()` function, imported from `pyspark.sql.functions`, creates a column reference that you can compare against a literal or another column. You can also reference columns directly as attributes of the DataFrame, such as `df.order_amount`, but the `col()` form is safer because attribute access breaks when a column name contains spaces, dots, or characters that are not valid Python identifiers.

### Single-condition filters

A single-condition filter is the simplest form. You name a column, choose a comparison operator, and supply a value. The comparison operators available are the same ones you would expect: `>`, `<`, `>=`, `<=`, `==` for equality, and `!=` for inequality. Note that equality in PySpark is `==`, not `=`, because `=` is the Python assignment operator. The following example shows a single-condition filter on a customer table.

```python
# Import the col function, which builds a reference to a column by name.
# Without this, you would have to use attribute access, which fails on names
# containing spaces or special characters.
from pyspark.sql.functions import col

# Load the customer table into a DataFrame.
# This reads the Delta table registered in Unity Catalog under the sales schema.
df_customer = spark.read.table("sales.customer")

# Filter to customers whose account balance is greater than 1000.
# col("c_acctbal") references the balance column.
# The > operator keeps only rows where the balance is strictly greater than 1000.
# Rows with a null balance are removed, because null > 1000 evaluates to null,
# and null is not true.
df_filtered = df_customer.filter(col("c_acctbal") > 1000)

# Display the filtered DataFrame.
# display() is a Databricks notebook command that renders the result as a table.
# It triggers execution of the lazy filter plan.
display(df_filtered)
```

The example reads a Delta table, applies one comparison, and displays the result. The filter is lazy, meaning Spark records the intent to filter but does not read any data until `display()` is called. When execution happens, Spark scans the table, evaluates the predicate against each row, and keeps only the rows where the predicate is true. Rows with a null balance are dropped, which is usually what you want, but you should be aware of it so you do not accidentally lose data. The same logic in SQL looks like this.

```sql
-- Select every column from the customer table.
-- SELECT * is fine for exploration but should be replaced with explicit
-- column names in production queries to avoid reading unnecessary data.
SELECT *
FROM sales.customer
-- Keep only rows whose account balance is greater than 1000.
-- The > comparison excludes rows where c_acctbal is null, because
-- null > 1000 evaluates to null, which is not true.
WHERE c_acctbal > 1000;
```

The SQL version expresses the same predicate and produces the same result. The optimizer treats the `WHERE` clause as a filter node in the logical plan, identical to the DataFrame filter. There is no performance difference between the two forms.

### Combining multiple conditions

Real filters rarely involve a single condition. You usually want rows that satisfy several conditions at once, or rows that satisfy at least one of several conditions. In the DataFrame API, combine conditions with `&` for AND, `|` for OR, and `~` for NOT. Each condition must be wrapped in parentheses, because Python's operator precedence would otherwise bind the `&` before the comparison and produce an error or a wrong result. This is one of the most common mistakes when writing PySpark filters, and it is worth committing to memory: always parenthesize each condition.

The following example shows two combined filters, one using AND and one using OR.

```python
# Filter customers who are in nation 20 AND have a balance over 1000.
# Each condition is wrapped in parentheses so that the & operator applies
# to the two boolean results, not to the comparison operands.
# Without the parentheses, Python would try to evaluate 20 & col(...) first,
# which raises an error because & is not defined for an int and a Column.
df_filtered = df_customer.filter(
    (col("c_nationkey") == 20) & (col("c_acctbal") > 1000)
)

# Filter customers whose key matches either of two specific values.
# The | operator is logical OR, and again each condition is parenthesized.
# This is useful when you have a small set of known keys to include.
df_filtered = df_customer.filter(
    (col("c_custkey") == 412446) | (col("c_custkey") == 412447)
)

# Display the second result, which is the OR filter.
display(df_filtered)
```

The first filter keeps only rows that satisfy both conditions. The second keeps rows that satisfy either condition. The parentheses are not stylistic. They change the meaning of the expression, and in some cases they prevent a runtime error. For long chains of conditions, consider breaking the expression across multiple lines for readability, as shown. The equivalent SQL uses `AND` and `OR`, which have well-defined precedence but are still clearer when each condition is on its own line.

```sql
-- Select orders that are finished and expensive.
-- The AND operator requires both conditions to be true.
SELECT *
FROM sales.orders
-- Keep only orders whose status is 'F', meaning finished.
-- String literals in SQL use single quotes, not double quotes.
WHERE o_orderstatus = 'F'
  -- Keep only orders whose total price exceeds 50000.
  -- Both conditions must hold for a row to be kept.
  AND o_totalprice > 50000;

-- Select customers whose key is one of two specific values.
-- The OR operator requires at least one condition to be true.
SELECT *
FROM sales.customer
WHERE c_custkey = 412446
   OR c_custkey = 412447;
```

The SQL `AND` and `OR` operators follow the same three-valued logic as their PySpark counterparts. A row is kept when the overall predicate evaluates to true. If any part of an `AND` is null and the other part is true, the result is null, and the row is dropped. If any part of an `OR` is true, the result is true, and the row is kept regardless of nulls elsewhere. This asymmetry between `AND` and `OR` in the presence of nulls is a frequent source of confusion and is covered in the next section.

### When to use `isin`, `between`, and other helpers

PySpark provides helper functions for common filter patterns. `isin()` checks whether a column value is in a list. `between()` checks whether a value falls within an inclusive range. These are not separate filtering mechanisms; they are shorthand that expands into the same predicate. Use them when they make the intent clearer, and prefer them over long chains of `OR` conditions.

| Helper | Equivalent predicate | When to use |
|---|---|---|
| `col("x").isin(1, 2, 3)` | `(x = 1) OR (x = 2) OR (x = 3)` | A short list of discrete values |
| `col("x").between(10, 20)` | `(x >= 10) AND (x <= 20)` | An inclusive numeric or date range |
| `col("x").startswith("A")` | `x LIKE 'A%'` | A string prefix match |
| `col("x").contains("abc")` | `x LIKE '%abc%'` | A substring match |

The following example shows `isin()` and `between()` in use.

```python
# Keep rows whose nation key is one of three specific values.
# isin() is cleaner than three OR conditions and the optimizer treats it
# as an IN predicate, which can be pushed down to the data source.
df_filtered = df_customer.filter(col("c_nationkey").isin(20, 21, 22))

# Keep rows whose balance is between 1000 and 5000 inclusive.
# between() includes both endpoints, so a balance of exactly 1000 or
# exactly 5000 is kept.
df_filtered = df_customer.filter(col("c_acctbal").between(1000, 5000))
```

Both helpers produce the same logical plan as the expanded form, so there is no performance penalty for using them. They improve readability, which reduces the chance of a logic error.

## Filtering with SQL

SQL filtering uses the `WHERE` clause, which appears after `FROM` and before `GROUP BY`, `ORDER BY`, or `LIMIT`. The clause takes a predicate and keeps only the rows for which the predicate is true. You can run SQL directly in a Databricks notebook cell, where the default language is SQL, or you can call `spark.sql()` from a Python cell to run SQL and receive a DataFrame back. The latter is useful when you want to mix SQL filtering with Python transformations.

The following example shows a SQL filter run through `spark.sql()` and returned as a DataFrame.

```python
# Run a SQL query and return the result as a Spark DataFrame.
# The triple-quoted string allows the query to span multiple lines.
# spark.sql() returns a DataFrame, so you can chain further PySpark
# operations such as .groupBy() or .write() after this call.
df_filtered = spark.sql("""
    SELECT *
    FROM sales.transactions
    -- Keep only transactions with a positive amount.
    -- Transactions with a null amount are removed, because
    -- null > 100 is not true.
    WHERE amount > 100
      -- Keep only transactions on or after January 1, 2024.
      -- Date literals use the ISO format 'YYYY-MM-DD'.
      AND transaction_date >= '2024-01-01'
""")

# Display the resulting DataFrame.
# The query is not executed until this action is called.
display(df_filtered)
```

This pattern is common in notebooks where the analyst prefers SQL for the filter logic but wants to continue with Python for the rest of the job. The query is parsed, analyzed against the Unity Catalog metastore, optimized, and executed on the cluster. If the table or column names are wrong, or if the user lacks permission, the error surfaces at execution time, not at the time `spark.sql()` is called, because the call is lazy.

## Handling null values in filters

Null handling is the single most common source of incorrect filter results. In SQL and Spark, null represents an unknown value, not an empty string and not zero. Any comparison involving null evaluates to null, not to true or false. This means `null = 5` is null, `null != 5` is null, and `null > 5` is null. Because a filter keeps only rows where the predicate is true, rows with nulls in the compared column are dropped whenever the predicate involves that column. To keep or drop nulls explicitly, you must use the dedicated null-check functions.

### Why `!= None` does not work

A frequent mistake is to write `col("order_amount") != None` in Python, expecting to keep rows where the amount is not null. This does not work. In Python, `None` is a singleton object, and `!=` on a Column object compares object identity rather than SQL null. Spark translates the expression in a way that does not produce the intended predicate, and the result is either an error or a silently wrong result. The correct approach is to use `isNotNull()` and `isNull()`, which are methods on the Column object and produce the SQL `IS NOT NULL` and `IS NULL` predicates.

The following example shows the correct and incorrect approaches side by side.

```python
# Correct: use isNotNull() to keep rows where order_amount has a value.
# isNotNull() is a method on the Column object and produces the SQL
# predicate IS NOT NULL, which evaluates to true for non-null values
# and false for null values.
df_valid_orders = df.filter(col("order_amount").isNotNull())

# Correct: use isNull() to keep rows where order_amount is null.
# This is useful for isolating bad records for inspection before dropping them.
df_null_orders = df.filter(col("order_amount").isNull())

# Correct alternative: reference the column directly as a DataFrame attribute.
# This works when the column name is a valid Python identifier.
# It is equivalent to the col() form above.
df_valid_orders = df.filter(df.order_amount.isNotNull())

# Incorrect: do not use Python's None with comparison operators.
# The expression below does not reliably filter nulls and may raise an error
# or return an unexpected result. It is shown here only to be avoided.
# df_bad = df.filter(col("order_amount") != None)
```

The example shows three correct forms and one incorrect form. The incorrect form is commented out so that it does not run, but it is shown so you can recognize it. In SQL, the equivalent correct operators are `IS NULL` and `IS NOT NULL`.

```sql
-- Keep only orders where the amount has a value.
-- IS NOT NULL is the correct way to exclude nulls.
-- Writing amount != NULL would return no rows, because
-- amount != NULL evaluates to null for every row, including non-null rows.
SELECT *
FROM sales.orders
WHERE order_amount IS NOT NULL;

-- Keep only orders where the amount is null.
-- IS NULL is the correct way to isolate nulls.
SELECT *
FROM sales.orders
WHERE order_amount IS NULL;
```

The `IS NULL` and `IS NOT NULL` operators are the only reliable way to test for null in SQL. Any comparison using `=`, `!=`, `<`, or `>` against the literal `NULL` returns null for every row, so the filter keeps nothing. This is a common trap for analysts coming from languages where null is treated as an ordinary value.

### Removing rows with `dropna`

When your goal is not to isolate nulls but to remove every row that contains a null in one or more columns, use the `dropna()` method. It is a dedicated method for this purpose and is clearer than a chain of `isNotNull()` conditions. `dropna()` takes a `subset` parameter that names the columns to check, and a `how` parameter that controls whether a row is dropped when any of the columns are null or only when all of them are null. The default `how` is `"any"`, which drops a row if any column in the subset is null.

The following example shows `dropna()` in use.

```python
# Remove rows where order_amount is null.
# subset names the columns to check for nulls.
# how="any" is the default and means a row is dropped if any listed column
# is null. Set how="all" to drop a row only when every listed column is null.
df_clean = df.dropna(subset=["order_amount"])

# Remove rows where either order_amount or customer_id is null.
# With two columns in the subset and how="any", a row is dropped if either
# column is null. This is a common cleaning step before a join, because
# null keys do not match and would silently drop rows in an inner join.
df_clean = df.dropna(subset=["order_amount", "customer_id"], how="any")
```

`dropna()` is a convenience wrapper around an `isNotNull()` filter for each column combined with AND. It produces the same logical plan, so there is no performance difference. Use it when the intent is "remove incomplete rows," and use explicit `isNotNull()` when the intent is "keep rows where this specific column has a value" and you want the code to make that intent obvious.

## Data types, case sensitivity, and time zones

Filters compare values, and comparisons depend on data types. If you compare a string column to a number, Spark may attempt an implicit cast, or it may raise an error, depending on the configuration and the specific types involved. Implicit casts can produce surprising results, such as a string `"10"` comparing as greater than a numeric `9` because the comparison happens lexicographically rather than numerically. To avoid this, ensure that the literal you compare against matches the column type. Use `lit()` to construct a typed literal when needed, and use `cast()` to convert a column to the type you want before comparing.

Case sensitivity affects string comparisons. By default, Spark's string comparisons are case-sensitive, so `'F'` and `'f'` are different values. If your data contains inconsistent casing, either normalize it with `upper()` or `lower()` before filtering, or use a case-insensitive collation if your table is configured for one. Delta Lake and Unity Catalog support collations at the column level, which can make comparisons case-insensitive without changing the query. Be aware that adding a function such as `upper()` to the filtered column prevents predicate pushdown, because the data source cannot evaluate the function. If pushdown matters, normalize the data at write time instead.

Time zones affect timestamp comparisons. Spark stores timestamps internally in UTC and displays them in the session time zone, which is set by `spark.sql.session.timeZone`. When you compare a timestamp column to a string literal, Spark interprets the literal in the session time zone. If the session time zone differs from the time zone in which the data was written, the comparison can be off by hours. To avoid this, either set the session time zone explicitly at the start of your job, or compare against a timestamp literal that includes an explicit offset, such as `'2024-01-01T00:00:00+00:00'`. The following example shows a safe timestamp filter.

```python
# Set the session time zone to UTC so that all timestamp comparisons
# in this session are interpreted consistently. This must be set before
# any timestamp comparisons are evaluated.
spark.conf.set("spark.sql.session.timeZone", "UTC")

# Filter transactions on or after a specific UTC instant.
# The literal includes an explicit offset, so it is unambiguous regardless
# of the session time zone. This avoids off-by-hours errors when the
# cluster time zone and the data time zone differ.
df_filtered = df.filter(
    col("transaction_ts") >= lit("2024-01-01T00:00:00+00:00").cast("timestamp")
)
```

The example sets the session time zone and uses an explicit offset in the literal. Both steps reduce ambiguity. If you work with data from multiple time zones, store timestamps in UTC and convert to local time only for display.

## Predicate pushdown, Delta Lake, and Unity Catalog

Predicate pushdown is an optimization in which the filter is evaluated as close to the data as possible, ideally at the storage layer, so that fewer rows are read into memory. Delta Lake stores per-file statistics, including minimum and maximum values for each column, in the transaction log. When you filter on a column, the optimizer uses these statistics to skip entire files whose value range does not overlap the filter range. This is called file skipping, and it can reduce the amount of data read by orders of magnitude. For file skipping to work, the filter must be expressed in a way the optimizer can understand. Comparisons on raw columns work. Comparisons on expressions such as `upper(col("status")) = 'F'` do not, because the statistics are stored for the raw column, not for the uppercased value.

Unity Catalog adds governance on top of Delta Lake. It controls who can read which tables and columns, and it records lineage. Filtering interacts with Unity Catalog in two ways. First, row-level filters and column masks can be attached to a table as policies, and those policies are applied automatically to every query, including your filter. If a row-level filter hides certain rows, your query will not see them even if your own predicate would have kept them. Second, dynamic views can present a filtered subset of a table to certain users. When you filter a view, you filter the result of the view's own logic. Understanding these layers helps you predict what your query will return.

The following example shows a filter that benefits from file skipping on a Delta table.

```python
# Filter a Delta table on a partition-like column.
# Delta Lake stores min and max statistics per file for this column,
# so the optimizer can skip files whose range does not overlap the filter.
# This is most effective when the column is sorted or clustered in the table.
df_recent = spark.read.table("sales.transactions").filter(
    col("transaction_date") >= "2024-01-01"
)

# Filter on a raw column rather than an expression.
# The comparison below can use file statistics directly.
# If you wrapped the column in a function such as date_format(),
# the optimizer could not use the statistics and would scan every file.
df_recent = df_recent.filter(col("amount") > 0)
```

The example shows two filters that the optimizer can push down. The first uses a date column that is commonly used for partitioning or clustering, so file skipping is effective. The second compares a raw numeric column, so statistics are available. Both filters reduce the number of rows read. If you need to filter on a transformed value, consider materializing the transformed value in a separate column at write time so that statistics exist for it.

## An end-to-end example: bronze to silver filtering

Consider a pipeline that ingests raw order events into a bronze Delta table, cleans them into a silver table, and aggregates them into a gold table. The raw events include test orders, orders with null amounts, and orders with future dates caused by clock skew on the source system. The silver layer should contain only valid orders: non-null amounts, dates not in the future, and status values in a known set. The following example shows the filtering step that moves data from bronze to silver.

```python
# Import the functions needed for the filter.
# col() references a column. current_timestamp() returns the current
# time in the session time zone and is used to exclude future dates.
from pyspark.sql.functions import col, current_timestamp

# Read the bronze table, which holds raw order events.
# Bronze tables typically keep all data, including bad records,
# so that the raw history is preserved for auditing.
df_bronze = spark.read.table("sales.orders_bronze")

# Apply the cleaning filter that defines the silver layer.
# Each condition is parenthesized and combined with & (AND).
# The filter keeps a row only when every condition is true.
df_silver = df_bronze.filter(
    # Keep rows where the amount has a value.
    # Null amounts cannot be aggregated and are excluded here.
    col("order_amount").isNotNull()
    # Keep rows where the amount is positive.
    # Zero and negative amounts are treated as invalid for this pipeline.
    & (col("order_amount") > 0)
    # Keep rows whose order date is not in the future.
    # Future dates indicate clock skew or bad data on the source system.
    & (col("order_date") <= current_timestamp())
    # Keep rows whose status is one of the known valid values.
    # isin() expands into an IN predicate and is easier to read than
    # a chain of OR conditions.
    & col("order_status").isin("F", "O", "P")
)

# Write the cleaned data to the silver table.
# mode("overwrite") replaces the table contents on each run.
# In production you would use merge or append with a watermark instead.
df_silver.write.mode("overwrite").saveAsTable("sales.orders_silver")
```

The example reads bronze, applies four conditions, and writes silver. Each condition removes a specific class of bad data. The `isNotNull()` check removes nulls. The positivity check removes zero and negative amounts. The timestamp check removes future dates. The `isin()` check removes unknown statuses. Together they define what "valid order" means for this pipeline. The filter is applied before the write, so the silver table contains only valid rows, and every downstream aggregation can assume the data is clean.

## Best practices

Filter as early as possible in the pipeline. The earlier a row is removed, the less work every subsequent operation has to do. In a medallion architecture, this usually means filtering in the bronze-to-silver step, before joins and aggregations.

Always parenthesize each condition when combining with `&`, `|`, or `~` in PySpark. Parentheses prevent operator precedence errors and make the intent clear to readers.

Use `isNull()` and `isNotNull()` for null checks. Never compare against Python's `None` with `==` or `!=`. In SQL, use `IS NULL` and `IS NOT NULL`.

Prefer `isin()` over long chains of `OR` when checking membership in a small set. It is more readable and produces an `IN` predicate that the optimizer can push down.

Match the literal type to the column type. Compare numbers to numbers and strings to strings. Use `lit()` to construct typed literals when the default type is ambiguous.

Set the session time zone explicitly when filtering on timestamps, and use explicit offsets in timestamp literals when the data crosses time zones. This avoids off-by-hours errors.

Filter on raw columns rather than expressions when predicate pushdown matters. If you must filter on a transformed value, consider materializing that value in a column so that Delta statistics can be used.

Document the intent of each filter with a comment. A filter is a business rule, and the comment should explain the rule, not restate the code.

## Common mistakes and pitfalls

The most common mistake is forgetting parentheses around combined conditions in PySpark. Writing `col("a") > 1 & col("b") < 2` does not do what it appears to do, because `&` binds tighter than the comparison operators. The result is either an error or a silently wrong filter. Always write `(col("a") > 1) & (col("b") < 2)`.

The second most common mistake is using `!= None` to filter nulls. This does not work in Spark. Use `isNotNull()` instead. The same mistake in SQL is writing `!= NULL`, which returns no rows because every comparison with `NULL` evaluates to null.

A third mistake is assuming that nulls are kept by an inequality filter. They are not. `col("x") > 5` drops rows where `x` is null, because `null > 5` is null, and null is not true. If you want to keep nulls, add an explicit `isNull()` condition with `|`.

A fourth mistake is filtering on a column that is hidden by a row-level filter or column mask in Unity Catalog. If your query returns fewer rows than expected, check whether a policy is applied to the table. The policy is evaluated before your filter, and you cannot see the rows it hides.

A fifth mistake is comparing a timestamp column to a date string without considering the session time zone. The comparison is interpreted in the session time zone, which may differ from the time zone in which the data was written. Set the session time zone explicitly or use an offset in the literal.

A sixth mistake is applying a function to the filtered column and then expecting file skipping to work. `upper(col("status")) = 'F'` prevents pushdown because the statistics are stored for the raw column. Normalize the data at write time or accept the full scan.

## Testing filters

Filters encode business rules, and business rules change. A filter that was correct last quarter may be wrong this quarter. Write tests that assert the row counts and the boundary conditions of each filter. In PySpark, you can build small DataFrames with known values, apply the filter, and assert the result. The following example shows a test for a filter that keeps amounts greater than 100.

```python
# Import the test helpers.
# pytest is a common test runner. assert is a Python built-in.
import pytest
from pyspark.sql import Row

# Build a small DataFrame with known values, including edge cases.
# The values cover below, at, and above the threshold, plus a null.
# Testing the boundary (exactly 100) catches off-by-one errors.
test_data = [
    Row(order_id=1, amount=50),    # Below threshold, should be excluded.
    Row(order_id=2, amount=100),   # At threshold, excluded because > is strict.
    Row(order_id=3, amount=101),   # Above threshold, should be included.
    Row(order_id=4, amount=None),  # Null, excluded because null > 100 is null.
]
df_test = spark.createDataFrame(test_data)

# Apply the same filter used in production.
# Keeping the filter in a named variable lets the test and the pipeline
# share the exact same expression, so the test cannot drift from production.
def apply_filter(df):
    # Keep rows where amount is strictly greater than 100.
    # Nulls are excluded by the comparison, which is the intended behavior.
    return df.filter(col("amount") > 100)

# Run the filter and collect the surviving order IDs.
result_ids = [row.order_id for row in apply_filter(df_test).collect()]

# Assert that only the row above the threshold survived.
# This single assertion covers the below, at, above, and null cases.
assert result_ids == [3], f"Expected [3], got {result_ids}"
```

The test builds a DataFrame with four rows that cover the interesting cases: below the threshold, exactly at the threshold, above the threshold, and null. The assertion checks that only the above-threshold row survives. If someone later changes `>` to `>=`, the test fails because row 2 would then be included. Tests like this are cheap to write and catch regressions before they reach production. Run them as part of your CI pipeline against a small local Spark session.

## Performance considerations

Filtering reduces the amount of data that flows through the rest of the query, so it almost always improves performance. The main performance question is whether the filter can be pushed down to the storage layer. Delta Lake stores per-file min and max statistics, so filters on raw columns can skip files. Filters on expressions cannot, because the statistics do not exist for the expression. If you filter on a transformed value frequently, materialize the transformed value in a column at write time so that statistics are collected for it.

Partitioning and clustering affect filter performance. If a table is partitioned by date, a filter on the date column prunes entire partitions. If a table is clustered with liquid clustering on a high-cardinality column, a filter on that column can skip files within partitions. Choose partitioning and clustering columns based on the filters you run most often. A column that is rarely filtered on is a poor choice for partitioning.

The order of conditions in a filter does not affect performance. The optimizer reorders predicates and pushes down the most selective ones first. Write conditions in the order that is most readable, not the order you think is fastest.

Filtering before a join is usually better than filtering after, because it reduces the size of the join input. However, if the filter depends on a column from the other side of the join, you cannot apply it before the join. In that case, consider whether the join can be restructured so that the filter applies to one side first.

Finally, be aware that `count()` on a filtered DataFrame still scans the data to count rows. If you only need to know whether any rows match, use `limit(1).count()` or `isEmpty()` to stop after the first match. This is a small optimization but it matters on large tables.

## Summary

Filtering selects the rows that matter and discards the rest. In Azure Databricks, you filter with the PySpark DataFrame API or with SQL, and the two surfaces are equivalent in power and performance. The DataFrame API uses `filter()` and `where()`, which are aliases, and the `col()` function to reference columns. Combine conditions with `&`, `|`, and `~`, and always parenthesize each condition. SQL uses the `WHERE` clause with `AND`, `OR`, and `NOT`, and you can run SQL from Python with `spark.sql()` to receive a DataFrame back.

Null handling is the most important subtlety. In SQL and Spark, comparisons with null evaluate to null, not to true or false, so a filter that compares a column to a value drops rows where the column is null. Use `isNull()` and `isNotNull()` in PySpark, and `IS NULL` and `IS NOT NULL` in SQL. Never compare against Python's `None` or SQL's `NULL` with `=`, `!=`, `<`, or `>`. Use `dropna()` when the goal is to remove rows with nulls in a set of columns.

Data types, case sensitivity, and time zones affect filter correctness. Match literal types to column types, normalize string casing before filtering or use collations, and set the session time zone explicitly when filtering on timestamps. Predicate pushdown lets Delta Lake skip files whose statistics do not overlap the filter range, but pushdown only works on raw columns, not on expressions. Unity Catalog can apply row-level filters and column masks before your filter runs, so check for policies if results are smaller than expected.

Filter as early as possible in the pipeline, especially in the bronze-to-silver step of a medallion architecture. Write tests for boundary conditions, including the threshold value and nulls. Document the business rule behind each filter in a comment. Used well, filtering reduces cost, improves performance, and makes downstream results more trustworthy.
