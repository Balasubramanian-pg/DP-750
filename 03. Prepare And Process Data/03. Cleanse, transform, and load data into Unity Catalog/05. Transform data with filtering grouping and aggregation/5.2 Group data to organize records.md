## Group data to organize records

Grouping is the operation of arranging rows that share common values into categories, so that you can compute summary statistics for each category. In Azure Databricks, you group data in a Spark DataFrame or in a SQL query. The result of a grouping operation is not a filtered list of rows. It is a new dataset in which each row represents one group and contains the aggregated values you requested, such as a count, a sum, an average, a minimum, or a maximum. Grouping is the foundation of summarization. Without it, you can only describe an entire dataset at once. With it, you can describe each segment of the dataset separately, which is almost always more useful.

Grouping matters because most analytical questions are about segments, not totals. A business does not only want to know total revenue. It wants to know revenue by region, by product category, by month, and by customer segment. Each of those questions is answered by grouping on the relevant columns and applying an aggregate function. Grouping also reduces data volume. A table with a billion rows might produce a grouped result with only a few thousand rows, one per combination of grouping columns. That smaller result is cheaper to store, faster to query, and easier to visualize. In a medallion architecture, grouping is the step that turns cleaned silver data into aggregated gold data, which is the layer that dashboards and reports consume.

These notes cover grouping from first principles. They explain the PySpark `groupBy()` method and the SQL `GROUP BY` clause, the aggregate functions you can apply to groups, the `HAVING` clause that filters groups after aggregation, and advanced grouping features such as `rollup`, `cube`, `grouping sets`, and `pivot`. They also cover null handling in grouping, the relationship between grouping and Delta Lake, Unity Catalog, and the medallion architecture, and the performance implications of grouping large datasets. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand not only how to group data, but when grouping is the right tool and how to avoid the mistakes that make grouped results misleading.

## The purpose of grouping and aggregation

Grouping and aggregation are two distinct operations that are almost always used together. Grouping partitions the rows of a dataset into categories based on the values of one or more columns. Aggregation takes each partition and computes a single value from the rows in that partition. The grouping columns determine the granularity of the result. If you group by region, you get one row per region. If you group by region and month, you get one row per combination of region and month. If a combination does not exist in the data, no row appears for it unless you use an outer grouping feature such as `rollup` or `cube`, which are covered later.

An aggregate function is a function that takes many input values and returns one output value. `count()` returns the number of rows in a group. `sum()` returns the total of a numeric column. `avg()` returns the arithmetic mean. `min()` and `max()` return the smallest and largest values. `collect_list()` and `collect_set()` return arrays of values from the group. These functions ignore nulls in most cases, which is an important detail covered in the null handling section. The choice of aggregate function determines what the grouped result means. A count of orders and a sum of order amounts answer different questions, even when the grouping columns are the same.

The following table compares the most common aggregate functions and their behavior with nulls.

| Function | Purpose | Null behavior | Typical use |
|---|---|---|---|
| `count(*)` | Count all rows in the group | Counts nulls | Row counts, order counts |
| `count(col)` | Count non-null values in a column | Ignores nulls | Count of valid values |
| `sum(col)` | Sum of numeric values | Ignores nulls | Revenue, quantity |
| `avg(col)` | Arithmetic mean | Ignores nulls | Average order value |
| `min(col)` | Smallest value | Ignores nulls | Earliest date, lowest price |
| `max(col)` | Largest value | Ignores nulls | Latest date, highest price |
| `collect_list(col)` | Array of values including duplicates | Includes nulls | Ordered list of events |
| `collect_set(col)` | Array of distinct values | Includes nulls | Distinct categories |

The table shows that `count(*)` and `count(col)` behave differently. `count(*)` counts every row in the group, including rows where some or all columns are null. `count(col)` counts only the rows where the specified column is not null. This distinction is a frequent source of confusion. If you want to know how many orders exist, use `count(*)`. If you want to know how many orders have a non-null customer ID, use `count(customer_id)`.

## Grouping with the PySpark DataFrame API

The PySpark DataFrame API provides the `groupBy()` method to specify grouping columns. `groupBy()` returns a `GroupedData` object, which is not a DataFrame and cannot be displayed directly. A `GroupedData` object represents the intent to group. To produce a result, you must call an aggregation method on it, such as `count()`, `sum()`, `avg()`, `min()`, `max()`, or the general-purpose `agg()` method. The `agg()` method accepts one or more aggregate expressions, which you build with functions from `pyspark.sql.functions`.

The following example shows grouping by a single column and counting the rows in each group.

```python
# Import the functions needed for aggregation.
# count() counts rows. col() references a column by name.
from pyspark.sql.functions import col, count

# Load the customer table from Unity Catalog.
# This reads a Delta table registered under the sales schema.
df_customer = spark.read.table("sales.customer")

# Group the customer data by market segment.
# groupBy() returns a GroupedData object, not a DataFrame.
# The grouping column c_mktsegment defines the categories.
df_grouped = df_customer.groupBy("c_mktsegment")

# Apply the count() aggregation to each group.
# count() with no argument counts all rows in each group, including nulls.
# The result is a DataFrame with one row per market segment and a count column.
df_result = df_grouped.count()

# Display the aggregated result.
# The aggregation is lazy until display() triggers execution.
display(df_result)
```

The example groups by market segment and counts the rows. The `count()` method with no argument counts every row in each group. If you want to count non-null values in a specific column, pass the column name to `count()`. The result is a DataFrame with one row per distinct market segment. Segments with no rows do not appear in the result. If you need every segment to appear even when it has no rows, you would need an outer join or a `rollup` against a complete list of segments.

For multiple grouping columns, pass them as separate arguments or as a list. The result has one row per distinct combination of the grouping columns. The following example groups by two columns and computes several aggregates at once using `agg()`.

```python
# Import the aggregate functions used in the agg() call.
# sum() totals a numeric column. avg() computes the mean.
# max() returns the largest value. These are all aggregate functions.
from pyspark.sql.functions import col, sum, avg, max

# Group by market segment and nation key.
# Each distinct combination of the two columns becomes one group.
df_grouped = df_customer.groupBy("c_mktsegment", "c_nationkey")

# Apply multiple aggregations in a single agg() call.
# Each argument is a column expression that produces one output column.
# The alias() method renames the output column for readability.
# Without aliases, Spark would generate names like sum(c_acctbal).
df_result = df_grouped.agg(
    # Count all rows in the group, including rows with null balances.
    count("*").alias("customer_count"),
    # Sum the account balances, ignoring nulls.
    sum("c_acctbal").alias("total_balance"),
    # Compute the average account balance, ignoring nulls.
    avg("c_acctbal").alias("avg_balance"),
    # Find the largest account balance in the group, ignoring nulls.
    max("c_acctbal").alias("max_balance")
)

# Display the multi-aggregate result.
# Each row represents one market segment and nation combination.
display(df_result)
```

The example computes four aggregates in one pass over the data. Spark evaluates all four expressions together, so the data is scanned only once. This is more efficient than calling `count()`, then `sum()`, then `avg()` separately, which would scan the data multiple times. Always combine aggregates into a single `agg()` call when possible.

## Grouping with SQL

SQL uses the `GROUP BY` clause to organize rows into groups. The clause appears after `FROM` and `WHERE`, and before `HAVING`, `ORDER BY`, and `LIMIT`. Every column in the `SELECT` list must either appear in the `GROUP BY` clause or be wrapped in an aggregate function. This rule ensures that each output column has a single well-defined value per group. If you select a column that is neither grouped nor aggregated, the database cannot know which value to return when the group contains multiple distinct values, and the query fails.

The following example groups sales by region and counts the orders.

```sql
-- Select the region and a count of orders for each region.
-- region appears in the GROUP BY clause, so it is valid in SELECT.
-- COUNT(*) is an aggregate function, so it is also valid.
SELECT
  region,
  -- Count every row in the group, including rows with nulls.
  COUNT(*) AS order_count
FROM sales.orders
-- Group the rows by region. Each distinct region becomes one group.
-- All rows with the same region are processed together.
GROUP BY region;
```

The query returns one row per region, with the number of orders in that region. The `GROUP BY` clause defines the groups. The `COUNT(*)` aggregate computes the count for each group. If a region has no orders, it does not appear in the result. To include regions with zero orders, you would need a left join against a table of all regions, or a different query structure.

For multiple grouping columns, list them in the `GROUP BY` clause separated by commas. The result has one row per distinct combination. The following example groups by region and month and computes several aggregates.

```sql
-- Select the region, the month, and several aggregates.
-- region and month are in the GROUP BY clause, so they are valid.
-- The aggregate functions produce one value per group.
SELECT
  region,
  -- Extract the year and month from the order date.
  -- date_format() is a scalar function applied before grouping.
  -- The result is a string like '2024-01'.
  date_format(order_date, 'yyyy-MM') AS order_month,
  -- Count all orders in the group.
  COUNT(*) AS order_count,
  -- Sum the order amounts, ignoring nulls.
  SUM(order_amount) AS total_amount,
  -- Compute the average order amount, ignoring nulls.
  AVG(order_amount) AS avg_amount
FROM sales.orders
-- Group by both region and the formatted month.
-- Each distinct combination of region and month becomes one group.
GROUP BY region, date_format(order_date, 'yyyy-MM')
-- Order the result by region and month for readability.
ORDER BY region, order_month;
```

The query groups by region and by a formatted month derived from the order date. The `date_format()` function is applied to each row before grouping, so the grouping is on the formatted value, not on the raw timestamp. This is a common pattern for monthly reports. Note that the same expression appears in both the `SELECT` list and the `GROUP BY` clause. Some SQL dialects allow you to group by the alias `order_month`, but Spark SQL requires the full expression in the `GROUP BY` clause or the alias depending on the configuration. Using the full expression is always safe.

## Filtering groups with HAVING

The `WHERE` clause filters rows before grouping. The `HAVING` clause filters groups after aggregation. This distinction is important. If you want to keep only rows that satisfy a condition, use `WHERE`. If you want to keep only groups whose aggregate satisfies a condition, use `HAVING`. For example, to find regions with more than 100 orders, you group by region, count the orders, and then apply `HAVING COUNT(*) > 100`. You cannot use `WHERE` for this because the count does not exist until after grouping.

The following example shows both clauses in a single query.

```sql
-- Select the region and the total order amount.
SELECT
  region,
  -- Sum the order amounts for each region.
  SUM(order_amount) AS total_amount
FROM sales.orders
-- Filter rows before grouping.
-- Keep only orders placed in 2024. This reduces the data that is grouped.
WHERE order_date >= '2024-01-01'
  AND order_date < '2025-01-01'
-- Group the remaining rows by region.
GROUP BY region
-- Filter groups after aggregation.
-- Keep only regions whose total amount exceeds one million.
-- HAVING operates on the aggregated result, not on individual rows.
HAVING SUM(order_amount) > 1000000
-- Order the surviving groups by total amount, largest first.
ORDER BY total_amount DESC;
```

The `WHERE` clause removes orders from other years before grouping, which reduces the work the aggregation must do. The `HAVING` clause removes regions whose total is too small after aggregation. Both filters are necessary for different reasons. In PySpark, you filter groups by applying a `filter()` or `where()` transformation to the aggregated DataFrame, because the result of `agg()` is an ordinary DataFrame.

```python
# Import the functions needed for the aggregation and filter.
from pyspark.sql.functions import col, sum

# Read the orders table.
df_orders = spark.read.table("sales.orders")

# Filter rows before grouping to reduce the input size.
# Keep only orders from 2024.
df_filtered = df_orders.filter(
    (col("order_date") >= "2024-01-01") & (col("order_date") < "2025-01-01")
)

# Group by region and sum the order amounts.
# The result is a DataFrame with one row per region.
df_grouped = df_filtered.groupBy("region").agg(
    sum("order_amount").alias("total_amount")
)

# Filter groups after aggregation.
# This is the equivalent of the SQL HAVING clause.
# The filter is applied to the aggregated DataFrame, not to the raw rows.
df_final = df_grouped.filter(col("total_amount") > 1000000)

# Order the surviving groups by total amount, descending.
df_final = df_final.orderBy(col("total_amount").desc())

# Display the final result.
display(df_final)
```

The PySpark version separates the row filter from the group filter, just as the SQL version separates `WHERE` from `HAVING`. The row filter is applied before `groupBy()`, and the group filter is applied after `agg()`. This ordering is not optional. Applying the group filter before aggregation would be a type error, because the aggregated column does not exist yet.

## Advanced grouping: rollup, cube, and grouping sets

Basic `GROUP BY` produces one row per distinct combination of grouping columns that exists in the data. Sometimes you want subtotals and grand totals in the same result. `ROLLUP`, `CUBE`, and `GROUPING SETS` are SQL features that produce multiple levels of aggregation in a single query. They are useful for reports that show a hierarchy, such as total sales by country, then by region within country, and then a grand total.

`ROLLUP` produces a hierarchy of subtotals. `GROUP BY ROLLUP(country, region)` produces rows for each country and region combination, then rows for each country with region set to null, then a grand total row with both columns null. `CUBE` produces subtotals for every possible combination of the grouping columns, not just the hierarchy. `GROUPING SETS` lets you specify exactly which combinations you want.

The following table compares the three features.

| Feature | Combinations produced | Best for |
|---|---|---|
| `ROLLUP(a, b)` | (a, b), (a), () | Hierarchical subtotals |
| `CUBE(a, b)` | (a, b), (a), (b), () | All possible subtotals |
| `GROUPING SETS ((a), (b))` | (a), (b) | Precise control over subtotals |

The following SQL example shows `ROLLUP` for a hierarchical report.

```sql
-- Select the country, region, and total sales.
-- The grouping columns are country and region.
SELECT
  country,
  region,
  -- Sum the sales for each group.
  SUM(sales_amount) AS total_sales
FROM sales.transactions
-- ROLLUP produces subtotals for each level of the hierarchy.
-- The first row set is grouped by country and region.
-- The second row set is grouped by country alone, with region null.
-- The third row set is the grand total, with both columns null.
GROUP BY ROLLUP(country, region)
-- Order the result so that subtotals appear near their detail rows.
ORDER BY country, region;
```

The result contains detail rows, country subtotals, and a grand total. The null values in the grouping columns indicate subtotal rows. You can use the `GROUPING()` function to distinguish a null that represents a subtotal from a null that exists in the data. `GROUPING(country)` returns 1 when the row is a subtotal for country and 0 when it is a detail row. This is important when the grouping column itself can contain nulls.

In PySpark, `rollup`, `cube`, and `grouping sets` are available as methods on the `GroupedData` object. The following example shows `rollup`.

```python
# Import the aggregate function.
from pyspark.sql.functions import sum

# Read the transactions table.
df_transactions = spark.read.table("sales.transactions")

# Group by country and region using rollup.
# rollup() produces subtotals for each level of the hierarchy,
# just like the SQL ROLLUP clause.
df_rolled = df_transactions.rollup("country", "region").agg(
    sum("sales_amount").alias("total_sales")
)

# Display the result.
# Rows with null region are country subtotals.
# Rows with null country and null region are the grand total.
display(df_rolled)
```

The PySpark `rollup` method produces the same result as the SQL `ROLLUP` clause. The null values in the output indicate subtotal rows. To distinguish subtotal nulls from data nulls, you can add a grouping ID column using the `grouping_id()` function, which is available in both SQL and PySpark.

## Pivoting grouped data

Pivoting rotates a grouped result so that the values of one column become new columns. This is useful for producing cross-tabulation reports, where you want one row per category and one column per sub-category. In SQL, you can pivot with a `CASE` expression inside an aggregate function. In PySpark, the `GroupedData` object has a `pivot()` method that is followed by an aggregation.

The following SQL example pivots order counts by region and status.

```sql
-- Select the region and pivot the order status into columns.
SELECT
  region,
  -- Count orders with status 'F' and place the count in a column named finished.
  -- The CASE expression returns 1 for matching rows and null otherwise.
  -- COUNT() ignores nulls, so only matching rows are counted.
  COUNT(CASE WHEN order_status = 'F' THEN 1 END) AS finished,
  -- Count orders with status 'O' and place the count in a column named open.
  COUNT(CASE WHEN order_status = 'O' THEN 1 END) AS open,
  -- Count orders with status 'P' and place the count in a column named pending.
  COUNT(CASE WHEN order_status = 'P' THEN 1 END) AS pending
FROM sales.orders
-- Group by region so that each row represents one region.
GROUP BY region;
```

The query produces one row per region and one column per status. The `CASE` expression returns 1 when the status matches and null otherwise. Because `COUNT()` ignores nulls, only matching rows are counted. This pattern is portable across SQL dialects. In PySpark, the `pivot()` method is more concise.

```python
# Import the aggregate function.
from pyspark.sql.functions import count

# Read the orders table.
df_orders = spark.read.table("sales.orders")

# Group by region, pivot on order status, and count the rows.
# pivot() takes the column whose distinct values become new columns.
# The aggregation count() is applied to each pivoted group.
# The result has one row per region and one column per distinct status.
df_pivoted = df_orders.groupBy("region").pivot("order_status").count()

# Display the pivoted result.
display(df_pivoted)
```

The PySpark `pivot()` method automatically discovers the distinct values of the pivot column and creates one output column for each. This is convenient but can be expensive if the pivot column has many distinct values, because Spark must first compute the distinct values and then perform a second pass to pivot. If you know the distinct values in advance, you can pass them as a list to `pivot()` to avoid the extra pass.

## Null handling in grouping

Nulls affect grouping in two ways. First, null values in a grouping column form their own group. In SQL and Spark, all rows with a null in the grouping column are placed into a single group, and the output row for that group has a null in the grouping column. This is different from filtering, where a null comparison evaluates to null and the row is dropped. In grouping, nulls are treated as a distinct value for the purpose of forming groups. Second, aggregate functions ignore nulls in most cases. `sum()`, `avg()`, `min()`, and `max()` skip nulls. `count(col)` skips nulls, while `count(*)` counts them. `collect_list()` and `collect_set()` include nulls.

The following example shows how nulls form their own group and how aggregates treat them.

```python
# Import the aggregate functions.
from pyspark.sql.functions import col, count, sum, avg

# Read the customer table, which may contain null market segments.
df_customer = spark.read.table("sales.customer")

# Group by market segment.
# Rows with a null market segment form their own group.
# The output row for that group has a null in the c_mktsegment column.
df_grouped = df_customer.groupBy("c_mktsegment").agg(
    # Count all rows, including rows with null balances.
    count("*").alias("row_count"),
    # Count only rows where the balance is not null.
    count("c_acctbal").alias("non_null_balance_count"),
    # Sum the balances, ignoring nulls.
    # If every balance in the group is null, the sum is null, not zero.
    sum("c_acctbal").alias("total_balance"),
    # Compute the average balance, ignoring nulls.
    # If every balance in the group is null, the average is null.
    avg("c_acctbal").alias("avg_balance")
)

# Display the result.
# The row with a null market segment represents all customers
# whose market segment is unknown.
display(df_grouped)
```

The example shows that null grouping values are kept as a group, and the aggregates behave differently with nulls. The `count(*)` includes null balances, while `count("c_acctbal")` excludes them. The `sum()` and `avg()` ignore nulls, but if all values in a group are null, the result is null, not zero. This is a common source of confusion. If you want zero instead of null for an empty sum, use `coalesce(sum("c_acctbal"), lit(0))`.

## Grouping and Delta Lake, Unity Catalog, and the medallion architecture

Grouping is a transformation, not a storage feature, but it interacts with the lakehouse in important ways. Delta Lake stores data in Parquet files with a transaction log. When you group a Delta table, Spark reads the relevant files, shuffles the data so that rows with the same grouping key end up on the same partition, and then computes the aggregates. The shuffle is the expensive part. If the grouping columns align with the table's partitioning or clustering columns, Spark can sometimes avoid a full shuffle by using partition-local aggregation followed by a smaller shuffle. This is one reason to choose partitioning and clustering columns based on the grouping keys you use most often.

Unity Catalog governs access to the tables you group. If a table has a row-level filter or column mask, those policies are applied before your query runs. The grouped result reflects only the rows and column values you are allowed to see. This can make a count or sum smaller than the true value in the table, and that is the intended behavior. If you need the true total, you need a policy that grants access to all rows. Unity Catalog also records lineage, so you can see which tables a grouped result depends on.

In a medallion architecture, grouping is the primary operation that moves data from silver to gold. Silver tables hold cleaned, row-level data. Gold tables hold aggregated data, often grouped by time, geography, product, or customer segment. Gold tables are typically much smaller than silver tables because grouping collapses many rows into few. They are also denormalized, meaning they contain the grouping columns and the aggregates, and they are optimized for the queries that dashboards run. When you build a gold table, you group the silver data, apply the aggregates the business needs, and write the result as a Delta table. Because the gold table is small, you can often use `overwrite` mode to replace it entirely on each refresh, or `merge` mode to update only changed groups.

## Best practices

Group on the columns that define the segments you actually report on. Grouping on a high-cardinality column, such as a customer ID or a timestamp with millisecond precision, produces many small groups and can be slow. Grouping on a low-cardinality column, such as a status code or a region, produces fewer, larger groups and is usually faster.

Combine multiple aggregates into a single `agg()` call. Each call to `count()`, `sum()`, or `avg()` on a `GroupedData` object triggers a separate aggregation. Using `agg()` with several expressions computes them in one pass, which reduces the amount of data scanned.

Use `WHERE` to filter rows before grouping and `HAVING` to filter groups after aggregation. Filtering rows early reduces the amount of data that must be shuffled and aggregated.

Alias your aggregate columns. Without aliases, Spark generates column names like `sum(c_acctbal)`, which are hard to reference in downstream code. Use clear, descriptive aliases such as `total_balance` or `order_count`.

Be explicit about null handling. Remember that nulls form their own group and that aggregates ignore nulls by default. If you want nulls to be treated differently, use `coalesce()` or `fillna()` before grouping.

Use `rollup`, `cube`, or `grouping sets` only when you need subtotals in the same result. These features increase the number of output rows and can be more expensive than a simple `GROUP BY`. If you only need a grand total, compute it separately or use `rollup` with a single column.

For pivoting, specify the pivot values explicitly when you know them. This avoids an extra pass over the data to discover the distinct values and produces a stable schema that does not change when new values appear.

## Common mistakes and pitfalls

The most common mistake is selecting a column that is neither in the `GROUP BY` clause nor wrapped in an aggregate function. SQL requires every selected column to be either grouped or aggregated. PySpark enforces the same rule when you use `agg()`, but the error messages can be less clear. If you see an error about a column not being in the group by clause, add it to the grouping columns or wrap it in an aggregate.

A second mistake is confusing `WHERE` and `HAVING`. `WHERE` filters rows before grouping and cannot reference aggregate functions. `HAVING` filters groups after aggregation and can reference aggregate functions. Using `WHERE COUNT(*) > 10` is invalid because the count does not exist yet. Use `HAVING COUNT(*) > 10`.

A third mistake is assuming that a sum of nulls is zero. `sum()` of a column where every value is null returns null, not zero. If you need zero, use `coalesce(sum(col), lit(0))`. This is especially important when the result feeds into a calculation that cannot handle nulls.

A fourth mistake is forgetting that nulls in a grouping column form their own group. If you group by a column that contains nulls, the output will include a row with a null in that column, representing all rows with unknown values. If you do not want that group, filter out the nulls before grouping with `isNotNull()` or `WHERE col IS NOT NULL`.

A fifth mistake is grouping by a timestamp without truncating it. Grouping by a raw timestamp produces one group per distinct timestamp value, which is almost never what you want. Use `date_trunc()` or `date_format()` to group by day, month, or year. In PySpark, use `date_trunc("day", col("ts"))` or `to_date(col("ts"))`.

A sixth mistake is using `collect_list()` or `collect_set()` on a large group. These functions bring all values into a single row, which can exhaust memory if the group is very large. Use them only when the group size is bounded and small. For large groups, use an aggregate that returns a single value, such as `count()` or `sum()`.

## Testing grouped logic

Grouped logic is business logic, and it should be tested. A test for a grouped transformation should verify that the grouping columns produce the expected number of groups, that each aggregate returns the expected value, and that nulls and edge cases are handled correctly. The following example shows a test for a simple grouped aggregation.

```python
# Import the test helpers and aggregate functions.
import pytest
from pyspark.sql import Row
from pyspark.sql.functions import col, sum, count

# Build a small DataFrame with known values.
# The data includes two regions and a null region to test null grouping.
test_data = [
    Row(region="East", amount=100),   # East group, first row.
    Row(region="East", amount=200),   # East group, second row.
    Row(region="West", amount=50),    # West group, single row.
    Row(region=None, amount=75),      # Null region forms its own group.
]
df_test = spark.createDataFrame(test_data)

# Define the transformation to test.
# Group by region and compute the sum and count for each group.
def group_and_aggregate(df):
    # Group by region. Nulls form their own group.
    return df.groupBy("region").agg(
        # Sum the amounts, ignoring nulls.
        sum("amount").alias("total"),
        # Count all rows in the group.
        count("*").alias("row_count")
    )

# Run the transformation and collect the results into a dictionary.
# The dictionary is keyed by region so that assertions are easy to write.
result = {
    row.region: (row.total, row.row_count)
    for row in group_and_aggregate(df_test).collect()
}

# Assert that the East group has the correct sum and count.
assert result["East"] == (300, 2), f"East failed: {result['East']}"
# Assert that the West group has the correct sum and count.
assert result["West"] == (50, 1), f"West failed: {result['West']}"
# Assert that the null region group has the correct sum and count.
assert result[None] == (75, 1), f"Null group failed: {result[None]}"
```

The test builds a small DataFrame with two regions and a null region. It groups by region, computes the sum and count, and asserts the expected values. The null region is tested explicitly, because null grouping is a common source of bugs. If someone later changes the code to filter out nulls, the test fails. Run tests like this in your CI pipeline against a small local Spark session.

## Performance considerations

Grouping requires a shuffle, which is the most expensive operation in a distributed query. During a shuffle, rows are redistributed across the cluster so that all rows with the same grouping key end up on the same partition. The shuffle writes data to disk and transfers it over the network. Reducing the amount of data that must be shuffled is the primary way to improve grouping performance.

Filter rows before grouping whenever possible. A `WHERE` clause that removes half the rows also halves the shuffle size. If you are grouping a large table and only need a subset of rows, filter first.

Group on columns that are already partitioned or clustered in the Delta table. If the table is partitioned by date and you group by date, Spark can often avoid a full shuffle by aggregating within each partition and then combining the partial results. This is a significant optimization. If you group by a column that is not aligned with the partitioning, a full shuffle is required.

Use the smallest data types that fit your values. A grouping key stored as a string uses more memory and network bandwidth than the same key stored as an integer. If your grouping column is a code that can be represented as an integer, consider storing it that way.

Be careful with high-cardinality grouping columns. Grouping by a column with millions of distinct values produces millions of groups, each with a small number of rows. The shuffle is large, and the aggregation overhead per group is high. If you need to group by a high-cardinality column, consider whether you can pre-aggregate at a coarser level first, or whether you can use a different approach such as approximate aggregation.

Finally, avoid `collect_list()` and `collect_set()` on large groups. These functions bring all values into a single row, which can cause out-of-memory errors. If you need to collect values, ensure the group size is bounded, or use a different aggregation that returns a single value.

## Summary

Grouping organizes rows that share common values into categories so that you can compute summary statistics for each category. In Azure Databricks, you group with the PySpark `groupBy()` method or the SQL `GROUP BY` clause. The PySpark `groupBy()` method returns a `GroupedData` object, which you must combine with an aggregation such as `count()`, `sum()`, `avg()`, `min()`, `max()`, or the general-purpose `agg()` method. The SQL `GROUP BY` clause requires that every selected column either appear in the grouping clause or be wrapped in an aggregate function.

Aggregate functions take many input values and return one output value per group. `count(*)` counts all rows, including nulls. `count(col)` counts only non-null values. `sum()`, `avg()`, `min()`, and `max()` ignore nulls. `collect_list()` and `collect_set()` include nulls. Nulls in a grouping column form their own group, and the output row for that group has a null in the grouping column. A sum of all-null values returns null, not zero.

The `WHERE` clause filters rows before grouping, and the `HAVING` clause filters groups after aggregation. `ROLLUP`, `CUBE`, and `GROUPING SETS` produce subtotals and grand totals in a single query. Pivoting rotates a grouped result so that the values of one column become new columns, which is useful for cross-tabulation reports. In a medallion architecture, grouping is the primary operation that turns cleaned silver data into aggregated gold data. Delta Lake and Unity Catalog affect grouping through file statistics, partitioning, row-level filters, and column masks.

Best practices include grouping on the columns you report on, combining aggregates into a single `agg()` call, filtering rows before grouping, aliasing aggregate columns, and being explicit about null handling. Common mistakes include selecting ungrouped and unaggregated columns, confusing `WHERE` and `HAVING`, assuming a sum of nulls is zero, forgetting that nulls form their own group, grouping by raw timestamps, and using `collect_list()` on large groups. Testing grouped logic with small, known DataFrames that include edge cases such as nulls and boundary values helps catch regressions. Performance depends on the shuffle, so filter early, align grouping columns with partitioning, avoid high-cardinality keys when possible, and use bounded aggregations. Used well, grouping turns large row-level datasets into concise, meaningful summaries that drive analysis and reporting.
