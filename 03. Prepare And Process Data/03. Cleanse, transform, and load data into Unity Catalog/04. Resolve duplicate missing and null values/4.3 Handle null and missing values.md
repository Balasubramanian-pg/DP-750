## Handle null and missing values

Null values represent missing or unknown data. They are not the same as zero, an empty string, or a space. Zero is a numeric value. An empty string is a string of length zero. A space is a string containing a space character. Null means that no value is present. It means the data is missing, unknown, or not applicable. This distinction is important because nulls behave differently from other values in calculations, comparisons, and aggregations. If you treat null as zero, you may produce incorrect totals. If you treat null as an empty string, you may produce incorrect groupings. If you ignore nulls, you may miss data quality problems. Depending on your analysis requirements, you might need to remove rows with nulls, replace them with default values, or use statistical imputation. The right strategy depends on the meaning of the column, the business rules, and the tolerance of downstream consumers.

## Why null handling matters

Null handling matters for several reasons. First, nulls affect correctness. In SQL, any comparison with null returns unknown. For example, `amount > 100` returns unknown if amount is null. The row is not returned by the filter. This can lead to missing results. `amount = NULL` is never true. You must use `IS NULL` or `IS NOT NULL`. If you forget this, your queries may return incorrect results.

Second, nulls affect aggregations. Most aggregate functions ignore nulls. For example, `SUM(amount)` ignores rows where amount is null. `AVG(amount)` divides by the count of non-null values, not the total count. `COUNT(amount)` counts only non-null values. `COUNT(*)` counts all rows. This can lead to unexpected averages and totals. If you want to treat null as zero, you must use `COALESCE(amount, 0)` before aggregating.

Third, nulls affect joins. In SQL, nulls do not match each other in a join. If two rows have null in the join key, they will not be joined. This can cause missing data in the result. You may need to use null-safe joins or replace nulls with a sentinel value before joining.

Fourth, nulls affect constraints. If a column is defined as `NOT NULL`, you cannot insert or update a row with a null value. This enforces data quality. But if you have existing nulls, you cannot add the constraint until you fix them.

Fifth, nulls affect analytics and machine learning. Many algorithms cannot handle nulls. They may fail or produce biased results. You must either drop nulls, fill them, or use algorithms that handle nulls natively.

## Identify null values

The first step in handling nulls is to identify them. You need to know which columns contain nulls, how many nulls there are, and what patterns exist. You can use SQL or PySpark to find this information.

In SQL, use the `IS NULL` operator to find rows with null values. The following query finds rows where `amount` or `customer_id` is null. Each line is commented.

```sql
-- Select all columns from the transactions table.
SELECT *
FROM sales.transactions
-- Filter to keep only rows where amount is null or customer_id is null.
-- The OR condition means a row is returned if either column is null.
WHERE amount IS NULL 
   OR customer_id IS NULL;
```

You cannot use `= NULL`. The expression `amount = NULL` is never true. You must use `IS NULL`. Similarly, use `IS NOT NULL` to find rows where a column has a value.

To count null occurrences per column, use the difference between the total row count and the count of non-null values. The following SQL query shows how. Each line is commented.

```sql
-- Select the total row count and the null count for each column.
SELECT 
    -- COUNT(*) counts all rows.
    COUNT(*) AS total_rows,
    -- COUNT(amount) counts only non-null values in the amount column.
    -- The difference is the number of null values.
    COUNT(*) - COUNT(amount) AS null_amount_count,
    -- COUNT(customer_id) counts only non-null values in the customer_id column.
    -- The difference is the number of null values.
    COUNT(*) - COUNT(customer_id) AS null_customer_count
FROM sales.transactions;
```

This query gives you a quick summary of nulls in specific columns. You can extend it to include more columns. You can also compute the null percentage by dividing the null count by the total row count.

In PySpark, you can use the `isNull()` and `isNotNull()` methods. The following PySpark code finds rows with nulls. Each line is commented.

```python
from pyspark.sql.functions import col

# Read the transactions table.
df = spark.read.table("sales.transactions")

# Filter rows where amount is null or customer_id is null.
df_nulls = df.filter(col("amount").isNull() | col("customer_id").isNull())

# Display the rows.
df_nulls.show()
```

To count nulls per column in PySpark, you can use the `isNull()` method and aggregate. The following code shows how. Each line is commented.

```python
from pyspark.sql.functions import col, count, when

# Read the transactions table.
df = spark.read.table("sales.transactions")

# Count nulls for each column.
# The when function returns 1 if the column is null, otherwise 0.
# The sum function adds up the 1s.
# The alias gives the result a readable name.
null_counts = df.select(
    count("*").alias("total_rows"),
    sum(when(col("amount").isNull(), 1).otherwise(0)).alias("null_amount_count"),
    sum(when(col("customer_id").isNull(), 1).otherwise(0)).alias("null_customer_count")
)

# Display the result.
null_counts.show()
```

You can also use the `summary()` method to get count, mean, stddev, min, max, and percentiles. The count in the summary is the number of non-null values. You can compare it to the total row count to find nulls.

## Drop rows with null values

One strategy for handling nulls is to drop rows that contain them. This is appropriate when the nulls represent invalid or unusable data. For example, if a customer ID is null, you cannot use the record for customer-level analysis. If an amount is null, you cannot include it in financial totals. Dropping these rows keeps the remaining data clean.

In PySpark, the `dropna()` method removes rows containing null values. The following examples show different ways to use it. Each line is commented.

```python
# Drop rows where any column is null.
# The default how parameter is "any".
# This removes a row if any column contains null.
df_clean = df.dropna()

# Drop rows where all columns are null.
# The how parameter is set to "all".
# This removes a row only if every column contains null.
df_clean = df.dropna(how="all")

# Drop rows where specific columns are null.
# The subset parameter specifies the columns to check.
# A row is removed if any of the specified columns is null.
df_clean = df.dropna(subset=["customer_id", "amount"])
```

The `how` parameter controls the behavior. `"any"` drops rows with at least one null. This is the default. `"all"` drops rows only when all specified columns are null. The `subset` parameter limits the check to specific columns. If you do not specify `subset`, all columns are checked. You can also use the `thresh` parameter to specify the minimum number of non-null values required to keep the row. For example, `thresh=3` keeps a row only if it has at least three non-null values.

In SQL, you can delete rows with nulls using the `DELETE` statement. The following SQL example deletes rows where `customer_id` is null. Each line is commented.

```sql
-- Delete rows from the transactions table.
DELETE FROM sales.transactions
-- The WHERE clause specifies the condition.
-- Rows where customer_id is null are deleted.
WHERE customer_id IS NULL;
```

You can also filter out nulls in a `SELECT` statement. The following SQL example selects only rows where `customer_id` and `amount` are not null. Each line is commented.

```sql
-- Select rows where customer_id and amount are not null.
SELECT *
FROM sales.transactions
WHERE customer_id IS NOT NULL
  AND amount IS NOT NULL;
```

Dropping rows is simple but it can cause data loss. If you drop too many rows, you may lose important information. You should always measure how many rows will be dropped before you drop them. You can use the count queries shown earlier. If the number is large, consider whether dropping is the right strategy. You may want to fill nulls instead. You may want to quarantine the rows for review. You should document why you dropped the rows.

## Fill null values with defaults

Another strategy is to fill nulls with default values. This is appropriate when the nulls represent a known value. For example, if a quantity is null, it might mean zero. If a status is null, it might mean "Unknown". If a discount is null, it might mean no discount. Filling nulls allows you to keep the rows and perform calculations.

In PySpark, the `fillna()` method replaces null values with specified defaults. The following examples show different ways to use it. Each line is commented.

```python
# Fill all null values with a single value.
# The value 0 is used for all columns.
# This works for numeric columns.
# For string columns, you should use a string value.
df_filled = df.fillna(0)

# Fill specific columns with different values.
# The dictionary maps column names to fill values.
# The amount column is filled with 0.
# The status column is filled with "Unknown".
# The quantity column is filled with 1.
df_filled = df.fillna({
    "amount": 0,
    "status": "Unknown",
    "quantity": 1
})
```

You can also use the `fillna()` method with a subset of columns. The dictionary approach is flexible because you can specify different defaults for each column. You should choose defaults that make sense for the column. For numeric columns used in sums, zero is often appropriate. For numeric columns used in averages, zero may skew the average. Consider using the mean or median instead. For categorical columns, a placeholder like "Unknown" is common. For date columns, you might use a sentinel date or leave them null if the date is not required.

In SQL, use the `COALESCE` function to provide default values. `COALESCE` returns the first non-null value from a list of arguments. The following SQL example shows how. Each line is commented.

```sql
-- Select columns with defaults for nulls.
SELECT 
    customer_id,
    -- COALESCE(amount, 0) returns amount if it is not null, otherwise 0.
    COALESCE(amount, 0) AS amount,
    -- COALESCE(status, 'Unknown') returns status if it is not null, otherwise 'Unknown'.
    COALESCE(status, 'Unknown') AS status
FROM sales.transactions;
```

You can also use `IFNULL` or `NVL` depending on the SQL dialect. In Databricks SQL, `COALESCE` is the standard. You can use `CASE` expressions for more complex logic. The following SQL example shows a `CASE` expression that fills nulls based on another column. Each line is commented.

```sql
-- Fill null amount with a value based on the transaction type.
SELECT
    transaction_id,
    -- If amount is not null, use it.
    -- If amount is null and transaction_type is 'refund', use -1.
    -- Otherwise, use 0.
    CASE
        WHEN amount IS NOT NULL THEN amount
        WHEN transaction_type = 'refund' THEN -1
        ELSE 0
    END AS amount
FROM sales.transactions;
```

## Statistical imputation

Sometimes filling with a constant is not appropriate. For numeric columns, you might want to fill nulls with the mean, median, or mode. This is called statistical imputation. It preserves the distribution of the data better than filling with zero. However, it can introduce bias if the nulls are not missing at random. You should use imputation only when you have a good reason and when the missingness is random.

In PySpark, you can compute the mean and use it to fill nulls. The following code shows how. Each line is commented.

```python
from pyspark.sql.functions import mean, col

# Compute the mean of the amount column.
mean_amount = df.select(mean("amount")).collect()[0][0]

# Fill nulls in the amount column with the mean.
df_filled = df.fillna({"amount": mean_amount})
```

In SQL, you can use a subquery to compute the mean and then use it in `COALESCE`. The following SQL example shows how. Each line is commented.

```sql
-- Fill null amount with the average amount.
SELECT
    transaction_id,
    -- COALESCE returns amount if not null, otherwise the average.
    COALESCE(amount, (SELECT AVG(amount) FROM sales.transactions)) AS amount
FROM sales.transactions;
```

For time series data, you might use forward fill or backward fill. Forward fill replaces nulls with the last known value. Backward fill replaces nulls with the next known value. In PySpark, you can use the `last` and `first` functions with a window. In SQL, you can use window functions. These techniques are more advanced and should be used with care.

## Choose the right strategy

The appropriate null handling strategy depends on your data context. The following table summarizes common scenarios and recommended approaches.

| Scenario | Recommended approach |
| --- | --- |
| Nulls in required fields like identifiers | Drop the rows |
| Nulls in numeric fields for aggregation | Fill with zero or mean |
| Nulls in optional categorical fields | Fill with placeholder like "Unknown" |
| Nulls that would skew analysis | Drop or fill based on domain knowledge |
| Nulls in time series data | Forward fill or backward fill |
| Nulls in columns used for joins | Replace with sentinel value or use null-safe join |

When choosing a strategy, consider the meaning of the column. If a null means "not applicable", filling with zero may be misleading. If a null means "unknown", filling with a placeholder is reasonable. If a null means "missing data", dropping may be appropriate. Consider the downstream use. If the column is used in a sum, filling with zero gives the same result as ignoring the row. If the column is used in an average, filling with zero lowers the average. Consider the volume of nulls. If only a few rows have nulls, dropping may be fine. If many rows have nulls, filling or imputation may be necessary to preserve the dataset. Consider the source of the nulls. If nulls come from a broken integration, you may need to fix the integration rather than patch the data.

## Document your null handling decisions

Documentation is critical. Future analysts need to understand why certain values were replaced or removed to correctly interpret query results. If you filled nulls with zero, document that. If you dropped rows with null customer IDs, document that. If you used mean imputation, document that and explain why. Documentation can take several forms. You can add comments to your SQL and PySpark code. You can add column comments in Unity Catalog. You can maintain a data dictionary. You can write a data quality report. The important thing is that the information is available to anyone who uses the data. Without documentation, downstream consumers may misinterpret the data. They may treat a filled value as a real value. They may not realize that rows were dropped. This can lead to incorrect conclusions.

## Common mistakes

One common mistake is treating null as an empty string. In SQL, `''` is not null. `IS NULL` does not match empty strings. If you use `COALESCE(email, '')`, you are replacing null with an empty string. This may be appropriate, but it changes the meaning. You should be explicit about whether you want null or empty string.

Another common mistake is using `= NULL` instead of `IS NULL`. The expression `column = NULL` is never true. You must use `IS NULL` or `IS NOT NULL`.

Another common mistake is assuming that `COUNT(*)` counts nulls. `COUNT(*)` counts all rows. `COUNT(column)` counts non-null values. To count nulls, use `COUNT(*) - COUNT(column)` or `SUM(CASE WHEN column IS NULL THEN 1 ELSE 0 END)`.

Another common mistake is dropping too many rows. If you drop all rows with any null, you may lose most of your data. Check the null counts first. Consider dropping only rows with nulls in critical columns. Consider filling nulls in non-critical columns.

Another common mistake is filling nulls with misleading defaults. Filling a null quantity with 1 when the actual quantity is unknown can skew inventory calculations. Filling a null salary with 0 can skew average salary calculations. Choose defaults that are appropriate for the column and the analysis.

Another common mistake is not documenting null handling. Without documentation, future analysts may misinterpret the data. They may not know that nulls were filled or rows were dropped. Always document your decisions.

Another common mistake is ignoring nulls in joins. Nulls do not match in joins. If you join on a column with nulls, the rows with nulls will not be joined. You may need to use a null-safe join or replace nulls with a sentinel value before joining.

## Testing null handling

You should test your null handling logic with sample data. Create a DataFrame with known nulls. Run your drop or fill logic. Verify that the correct rows are removed or filled. Test with different columns. Test with different fill values. Test with all nulls. Test with no nulls. Verify that your logic behaves as expected.

The following PySpark example tests null handling. Each line is commented.

```python
from pyspark.sql import SparkSession

# Create a Spark session.
spark = SparkSession.builder.appName("NullHandlingTest").getOrCreate()

# Create a test DataFrame with nulls.
data = [
    (1, 100.0, "Active"),
    (2, None, "Active"),
    (3, 200.0, None),
    (4, None, None),
    (5, 300.0, "Inactive")
]

# Define the schema.
schema = ["id", "amount", "status"]

# Create the DataFrame.
df = spark.createDataFrame(data, schema)

# Drop rows where amount is null.
df_dropped = df.dropna(subset=["amount"])
assert df_dropped.count() == 3, "Expected 3 rows after dropping null amounts"

# Fill nulls in amount with 0 and status with "Unknown".
df_filled = df.fillna({"amount": 0, "status": "Unknown"})
assert df_filled.filter("amount = 0").count() == 2, "Expected 2 rows with amount 0"
assert df_filled.filter("status = 'Unknown'").count() == 2, "Expected 2 rows with status Unknown"

# Display the results.
df_dropped.show()
df_filled.show()
```

This test confirms that the drop and fill logic works as expected. You can write similar tests for SQL queries. You can use a testing framework such as pytest to automate the tests. You can run the tests as part of your continuous integration pipeline. This helps you catch regressions before they reach production.

## Performance considerations

Null handling can affect performance. Dropping rows with nulls requires scanning the table and filtering. Filling nulls requires scanning and updating. For large tables, these operations can be expensive. You should consider the following. If you frequently filter on a column, consider filling nulls at ingestion time so that queries do not need to handle them. If you frequently aggregate a column, consider filling nulls with zero or mean at ingestion time. If you use `COALESCE` in every query, consider creating a view or a generated column that already has the default applied. This can improve query performance. If you use `dropna` in PySpark, it shuffles data. Consider partitioning the table by a relevant column to reduce the shuffle. If you use `fillna` in PySpark, it also shuffles data. Consider doing the fill at ingestion time. If you use statistical imputation, computing the mean or median requires a full scan. Consider caching the result if you use it multiple times.

## Best practices for handling nulls

Understand the meaning of null in each column. Is it missing, unknown, or not applicable? Choose a strategy that matches the meaning. Document your strategy. Use `IS NULL` and `IS NOT NULL` instead of `= NULL`. Use `COALESCE` or `fillna` to provide defaults. Use `dropna` or `DELETE` to remove rows. Consider statistical imputation for numeric columns when appropriate. Consider forward fill or backward fill for time series. Monitor null counts over time. Set up alerts when null counts exceed a threshold. Investigate the source of nulls. Fix the root cause to prevent future nulls. Test your null handling logic with sample data. Review your strategy regularly. As data and requirements change, your null handling strategy may need to change.
