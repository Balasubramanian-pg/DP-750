## Remove duplicate records

Once you have identified duplicates, you can choose a resolution strategy based on your data requirements. Removing duplicates is not a one-size-fits-all operation. The right approach depends on what you consider a duplicate, which record you want to keep, and what you want to do with the records you remove. You might want to keep the most recent record, the oldest record, the record with the most complete data, or the record that matches a specific business rule. You might want to remove all duplicates entirely, or you might want to keep one representative record and move the rest to a quarantine table for review. You might want to remove duplicates within a single table, or you might want to compare two tables and remove records that appear in both. The strategies in this section help you choose the right approach and implement it correctly.

## Understanding duplicate removal strategies

Before you remove duplicates, you must decide which record to keep. This is a business decision, not just a technical one. Different strategies are appropriate for different scenarios.

Keep the first occurrence. This is the default behavior of many deduplication methods. You keep the first row that appears in the table and remove all subsequent rows with the same key. The definition of "first" depends on the order of the data. If the table has no natural order, the first occurrence is arbitrary. You may want to sort the data before deduplicating to control which row is kept.

Keep the most recent occurrence. This is common when you have a table that stores changes over time. For example, a customer table might have multiple rows for the same customer, each representing a different version of the customer's data. You want to keep the most recent version. You can sort by an updated_at or created_at timestamp in descending order and keep the first row.

Keep the oldest occurrence. This is the opposite of keeping the most recent. You might want to keep the original record and remove later duplicates. This is useful when the first record is the most authoritative, or when you want to preserve the original data for auditing.

Keep the record with the most complete data. You might have duplicates where one record has more non-null fields than another. You want to keep the record that is most complete. You can compute a completeness score and sort by that score.

Keep the record that matches a business rule. You might have a rule that says a certain status is preferred, or a certain source system is authoritative. You can sort by a custom expression and keep the first row.

Remove all duplicates entirely. In some cases, you might want to remove all records that have duplicates, not just keep one. This is useful when the presence of duplicates indicates a data quality problem that must be resolved at the source. You can identify duplicate keys and then delete all rows with those keys.

Move duplicates to a quarantine table. Instead of deleting duplicates, you can move them to a separate table for review. This preserves the data while keeping the main table clean. This is useful when you are not sure which record to keep, or when you want to investigate the cause of duplication.

The choice of strategy depends on your business requirements, your data governance policies, and the criticality of the data. You should document your strategy and apply it consistently.

## Remove duplicates in PySpark using dropDuplicates

The dropDuplicates method removes duplicate rows based on specified columns, keeping only the first occurrence. It is a convenient method in the PySpark DataFrame API. It takes one or more column names as arguments. It returns a new DataFrame with duplicates removed. The original DataFrame is not modified because DataFrames are immutable.

The following PySpark code shows how to use dropDuplicates. Each line is commented.

```python
# Read the source DataFrame.
df = spark.read.table("sales.customers")

# Remove duplicates based on customer_id and email.
# The dropDuplicates method keeps the first occurrence of each unique combination.
# The order of rows in the DataFrame determines which occurrence is considered first.
# If the DataFrame has no natural order, the first occurrence is arbitrary.
# To control which row is kept, sort the DataFrame before calling dropDuplicates.
df_clean = df.dropDuplicates(["customer_id", "email"])

# Display the result.
df_clean.show()
```

The dropDuplicates method is simple and efficient. It performs a shuffle to group rows by the specified columns. It then keeps one row per group. The shuffle can be expensive for large datasets, but it is often the fastest way to deduplicate. The method does not guarantee which row is kept unless you sort the DataFrame first. If you need deterministic results, you should sort the DataFrame before calling dropDuplicates. For example, you can sort by an updated_at column in descending order so that the most recent row is kept.

The following PySpark code shows how to sort before deduplicating. Each line is commented.

```python
from pyspark.sql.functions import col

# Read the source DataFrame.
df = spark.read.table("sales.customers")

# Sort the DataFrame by updated_at in descending order.
# This ensures that the most recent record appears first for each customer_id and email.
df_sorted = df.orderBy(col("updated_at").desc())

# Remove duplicates based on customer_id and email.
# Because the DataFrame is sorted, the most recent record is kept.
df_clean = df_sorted.dropDuplicates(["customer_id", "email"])

# Display the result.
df_clean.show()
```

Sorting the entire DataFrame before deduplicating can be expensive because it requires a full sort. A more efficient approach is to use a window function with row_number, which we will cover later. However, for small to medium datasets, sorting before dropDuplicates is a simple and effective solution.

You can also use dropDuplicates without arguments. In that case, it removes rows that are identical across all columns. This is equivalent to the distinct method. The following code shows both forms. Each line is commented.

```python
# Remove rows that are identical across all columns.
df_unique = df.dropDuplicates()

# This is equivalent to using distinct.
df_unique_alt = df.distinct()
```

The distinct method is a shorthand for dropDuplicates with no arguments. It removes duplicate rows across all columns. It is useful when you want to eliminate exact duplicates. However, it is less flexible than dropDuplicates because you cannot specify a subset of columns. If you have two rows that are identical except for one column, distinct will not remove them. You must use dropDuplicates with the relevant columns to treat them as duplicates.

## Remove duplicates in PySpark using distinct

The distinct method removes duplicate rows across all columns. It returns a new DataFrame with only unique rows. It is a simple and efficient operation. It is equivalent to dropDuplicates with no arguments. The following PySpark code shows how to use distinct. Each line is commented.

```python
# Read the source DataFrame.
df = spark.read.table("sales.customers")

# Remove rows that are identical across all columns.
df_unique = df.distinct()

# Display the result.
df_unique.show()
```

The distinct method is useful when you want to remove exact duplicates. For example, if a data integration job accidentally inserted the same row twice, distinct will remove the extra copy. However, if the duplicates differ in any column, distinct will not remove them. You must use dropDuplicates with the appropriate columns to treat rows as duplicates even when they differ in other columns.

## Keep specific rows using ROW_NUMBER with QUALIFY

When you need control over which duplicate to keep, use ROW_NUMBER with QUALIFY to select records based on criteria like the most recent update. The ROW_NUMBER function assigns a sequential number to each row within a partition. The partition is defined by the duplicate key. The order is defined by the criteria you choose. The QUALIFY clause filters the results to keep only rows where the row number equals one.

The following SQL query keeps the most recently updated record for each customer. Each line is commented.

```sql
-- Select all columns from the customers table.
SELECT *
FROM sales.customers
-- The QUALIFY clause filters the results of window functions.
-- The ROW_NUMBER function assigns a number to each row within the partition.
-- The PARTITION BY customer_id groups rows by customer_id.
-- The ORDER BY updated_at DESC sorts rows within each group by updated_at descending.
-- The most recent row gets row number 1.
-- The QUALIFY clause keeps only rows where the row number equals 1.
QUALIFY ROW_NUMBER() OVER (
    PARTITION BY customer_id 
    ORDER BY updated_at DESC
) = 1;
```

This query partitions records by customer_id, orders them by updated_at in descending order, and keeps only the most recently updated record for each customer. The result is a table with one row per customer, where each row is the most recent version. This is a common pattern for deduplicating slowly changing dimensions or versioned data.

You can change the partition key to match your duplicate definition. For example, if you consider duplicates to be based on customer_id and email, you can partition by both columns. The following SQL query shows how. Each line is commented.

```sql
-- Select all columns from the customers table.
SELECT *
FROM sales.customers
-- Partition by customer_id and email.
-- Order by updated_at descending.
-- Keep only the most recent row for each combination.
QUALIFY ROW_NUMBER() OVER (
    PARTITION BY customer_id, email 
    ORDER BY updated_at DESC
) = 1;
```

You can also change the order to keep the oldest record. Use ORDER BY updated_at ASC. You can keep the record with the most complete data by ordering by a completeness score. You can keep the record that matches a business rule by ordering by a custom expression.

The ROW_NUMBER with QUALIFY approach is flexible and efficient. It allows you to control exactly which row is kept. It does not require sorting the entire DataFrame before deduplicating. It uses a window function that can be optimized by the query engine. It is supported in Databricks SQL and many modern SQL engines. If your engine does not support QUALIFY, you can use a subquery. The following SQL query shows the equivalent using a subquery. Each line is commented.

```sql
-- Use a subquery to compute the row number.
SELECT *
FROM (
    SELECT
        *,
        -- The ROW_NUMBER function assigns a number to each row within the partition.
        ROW_NUMBER() OVER (
            PARTITION BY customer_id 
            ORDER BY updated_at DESC
        ) AS row_num
    FROM sales.customers
) AS subquery
-- Filter the subquery to keep only rows where row_num equals 1.
WHERE row_num = 1;
```

This query produces the same result as the QUALIFY version. It is more verbose but works in more engines. You can use either approach depending on your environment.

## Keep specific rows using ROW_NUMBER in PySpark

You can implement the same logic in PySpark using the Window class and the row_number function. The following PySpark code keeps the most recently updated record for each customer. Each line is commented.

```python
from pyspark.sql.functions import row_number, col
from pyspark.sql.window import Window

# Read the source DataFrame.
df = spark.read.table("sales.customers")

# Define the window specification.
# The partitionBy method defines the duplicate key.
# The orderBy method defines the order within each partition.
# The most recent record gets row number 1.
window_spec = Window.partitionBy("customer_id").orderBy(col("updated_at").desc())

# Add a row number column.
df_with_row_num = df.withColumn("row_num", row_number().over(window_spec))

# Keep only rows where row_num equals 1.
df_clean = df_with_row_num.filter(col("row_num") == 1).drop("row_num")

# Display the result.
df_clean.show()
```

This code is equivalent to the SQL ROW_NUMBER with QUALIFY approach. It partitions by customer_id, orders by updated_at descending, and keeps the first row. You can change the partition and order to match your requirements. You can partition by multiple columns by passing a list to partitionBy. You can order by multiple columns by passing a list to orderBy.

The following PySpark code shows how to keep the oldest record instead. Each line is commented.

```python
# Define the window specification with ascending order.
window_spec = Window.partitionBy("customer_id").orderBy(col("updated_at").asc())

# Add a row number column.
df_with_row_num = df.withColumn("row_num", row_number().over(window_spec))

# Keep only rows where row_num equals 1.
df_clean = df_with_row_num.filter(col("row_num") == 1).drop("row_num")
```

You can also keep the record with the most complete data. For example, you can compute a completeness score by counting non-null columns. The following PySpark code shows how. Each line is commented.

```python
from pyspark.sql.functions import when, col, sum as _sum

# Compute a completeness score for each row.
# The score is the number of non-null columns.
# You can list the columns to check.
columns_to_check = ["name", "email", "phone_number", "address"]
completeness_expr = _sum(
    when(col(c).isNotNull(), 1).otherwise(0) for c in columns_to_check
)

df_with_score = df.withColumn("completeness_score", completeness_expr)

# Define the window specification.
# Partition by customer_id.
# Order by completeness_score descending.
window_spec = Window.partitionBy("customer_id").orderBy(col("completeness_score").desc())

# Add a row number column.
df_with_row_num = df_with_score.withColumn("row_num", row_number().over(window_spec))

# Keep only rows where row_num equals 1.
df_clean = df_with_row_num.filter(col("row_num") == 1).drop("row_num", "completeness_score")
```

This approach keeps the record with the most non-null values. You can customize the completeness expression to weight certain columns more heavily or to check for specific conditions.

## Remove all duplicates entirely

Sometimes you want to remove all records that have duplicates, not just keep one. This is useful when the presence of duplicates indicates a serious data quality problem that must be resolved at the source. You can identify duplicate keys and then delete all rows with those keys. The following SQL query shows how. Each line is commented.

```sql
-- Delete all rows that have a duplicate customer_id.
DELETE FROM sales.customers
WHERE customer_id IN (
    -- Subquery to find customer_ids that appear more than once.
    SELECT customer_id
    FROM sales.customers
    GROUP BY customer_id
    HAVING COUNT(*) > 1
);
```

This query deletes all rows for customers that have duplicates. The result is a table with no duplicates because any customer with more than one row is removed entirely. This is a drastic approach. You should use it only when you are sure that duplicates indicate invalid data. You should back up the data before deleting. You might want to move the deleted rows to a quarantine table instead of deleting them permanently.

The following PySpark code shows how to achieve the same result. Each line is commented.

```python
from pyspark.sql.functions import count
from pyspark.sql.window import Window

# Read the source DataFrame.
df = spark.read.table("sales.customers")

# Define the window specification.
window_spec = Window.partitionBy("customer_id")

# Count the number of rows in each partition.
df_with_count = df.withColumn("row_count", count("*").over(window_spec))

# Keep only rows where row_count equals 1.
df_clean = df_with_count.filter(col("row_count") == 1).drop("row_count")

# Write the result.
df_clean.write.saveAsTable("sales.customers_clean")
```

This code keeps only the customers that have exactly one row. Customers with multiple rows are removed entirely. You can then replace the original table with the clean table or write to a new table.

## Move duplicates to a quarantine table

Instead of deleting duplicates, you can move them to a separate quarantine table for review. This preserves the data while keeping the main table clean. The following SQL example shows how to move duplicates to a quarantine table. Each line is commented.

```sql
-- Create a quarantine table to hold duplicates.
CREATE TABLE IF NOT EXISTS sales.customers_quarantine AS
SELECT * FROM sales.customers WHERE 1 = 0;

-- Insert duplicates into the quarantine table.
INSERT INTO sales.customers_quarantine
SELECT *
FROM sales.customers
-- Use QUALIFY to select rows that have duplicates.
QUALIFY COUNT(*) OVER (PARTITION BY customer_id) > 1;

-- Delete duplicates from the main table, keeping one row per customer.
DELETE FROM sales.customers
WHERE (customer_id, updated_at) IN (
    SELECT customer_id, updated_at
    FROM (
        SELECT
            customer_id,
            updated_at,
            ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY updated_at DESC) AS row_num
        FROM sales.customers
    ) AS subquery
    WHERE row_num > 1
);
```

This approach preserves the duplicates for investigation. You can analyze the quarantine table to understand why duplicates occurred. You can then decide whether to fix the source system, update your ingestion logic, or manually resolve the duplicates.

The following PySpark code shows the same pattern. Each line is commented.

```python
from pyspark.sql.functions import row_number, col
from pyspark.sql.window import Window

# Read the source DataFrame.
df = spark.read.table("sales.customers")

# Define the window specification.
window_spec = Window.partitionBy("customer_id").orderBy(col("updated_at").desc())

# Add a row number column.
df_with_row_num = df.withColumn("row_num", row_number().over(window_spec))

# Identify duplicates: rows where row_num > 1.
duplicates_df = df_with_row_num.filter(col("row_num") > 1).drop("row_num")

# Identify unique records: rows where row_num = 1.
unique_df = df_with_row_num.filter(col("row_num") == 1).drop("row_num")

# Write duplicates to a quarantine table.
duplicates_df.write.saveAsTable("sales.customers_quarantine")

# Write unique records to the main table.
unique_df.write.saveAsTable("sales.customers_clean")
```

This pattern is useful when you want to keep the main table clean but you do not want to lose the duplicate data. You can review the quarantine table at your convenience.

## Handling nulls in duplicate removal

Nulls require special attention. In PySpark, dropDuplicates treats nulls as equal. Two rows with null in the same column are considered duplicates. In SQL, the behavior depends on the engine. Some engines treat nulls as equal in window functions and GROUP BY. Some do not. You should test the behavior in your environment.

If you want to treat nulls as equal explicitly, you can use coalesce to replace nulls with a sentinel value before deduplicating. The following PySpark code shows how. Each line is commented.

```python
# Replace nulls in the duplicate key columns with sentinel values.
df_filled = df.fillna({"customer_id": -1, "email": "unknown@example.com"})

# Then remove duplicates.
df_clean = df_filled.dropDuplicates(["customer_id", "email"])
```

The following SQL example shows the same using coalesce. Each line is commented.

```sql
SELECT *
FROM sales.customers
QUALIFY ROW_NUMBER() OVER (
    PARTITION BY COALESCE(customer_id, -1), COALESCE(email, 'unknown@example.com')
    ORDER BY updated_at DESC
) = 1;
```

This ensures that nulls are grouped together and treated as duplicates.

## Handling case sensitivity and whitespace

Text columns may contain values that differ only in case or whitespace. You should normalize values before deduplicating. The following PySpark code shows how. Each line is commented.

```python
from pyspark.sql.functions import lower, trim

# Normalize the email column: convert to lower case and trim whitespace.
df_normalized = df.withColumn("email", lower(trim(col("email"))))

# Remove duplicates using the normalized email.
df_clean = df_normalized.dropDuplicates(["customer_id", "email"])
```

The following SQL example shows the same. Each line is commented.

```sql
SELECT *
FROM sales.customers
QUALIFY ROW_NUMBER() OVER (
    PARTITION BY customer_id, LOWER(TRIM(email))
    ORDER BY updated_at DESC
) = 1;
```

This ensures that values that differ only in case or whitespace are treated as duplicates.

## Performance considerations

Removing duplicates can be expensive. It requires shuffling data across the cluster to group rows by the duplicate key. The cost depends on the size of the table and the number of distinct keys. You can improve performance by partitioning the table by the duplicate key or by a related column. You can use ZORDER to co-locate related data. You can use Delta Lake optimization features such as OPTIMIZE and file compaction to reduce the number of files. You can use approximate distinct count functions when exact counts are not necessary. You can filter the data before deduplicating if you only need to process a subset.

The dropDuplicates method and the distinct method both require a shuffle. The window function approach also requires a shuffle. The exceptAll approach requires a full comparison of two DataFrames, which can be even more expensive. You should test performance with realistic data volumes. Use the query profile or execution plan to identify bottlenecks. If the operation is too slow, consider using a sample of the data to estimate the scope of duplication. Consider using a separate table or materialized view to store deduplicated results. Consider scheduling deduplication during off-peak hours.
