## Identify duplicate records

Before you can remove duplicates, you need to find them. Duplicates typically occur when the same record appears multiple times in a table. This can happen for many reasons. Data integration jobs may run more than once. Streaming pipelines may reprocess the same micro-batch after a failure. Concurrent write operations may insert the same record from two different sources. Source systems may send the same event twice. A missing primary key or unique constraint may allow duplicates to enter the table. A bug in a transformation may multiply rows. Understanding why duplicates occur helps you prevent them. Identifying them is the first step toward removing them and preventing them from affecting downstream analytics.

Duplicates can cause serious problems. They can skew aggregations. A sum or count may be too high. They can break joins. A join may return more rows than expected. They can waste storage. They can confuse users. They can cause machine learning models to overfit or produce incorrect predictions. They can violate business rules. For example, a customer may be billed twice. Finding duplicates is therefore an essential data quality task.

## Why duplicates occur

Duplicates occur for many reasons. Understanding the root cause helps you choose the right detection and prevention strategy.

Repeated ingestion is a common cause. A batch job may be scheduled to run every hour. If it fails halfway through and is restarted, it may reprocess the same data. Without an idempotent write strategy, the same records may be inserted again. A streaming job may reprocess a micro-batch after a failure. If the checkpoint is not managed correctly, the same events may be written twice.

Concurrent writes can also cause duplicates. Two jobs may write to the same table at the same time. If they both insert the same record, the table ends up with two copies. This can happen when multiple sources send the same data, or when a backfill job runs while a regular job is running.

Source system issues can cause duplicates. A source system may send the same event twice due to a network retry. A user may submit a form twice. A database trigger may fire twice. An integration tool may duplicate messages.

Missing constraints can allow duplicates. If a table does not have a primary key or a unique constraint, the database cannot prevent duplicates. Even with a primary key, duplicates can occur if the key is not truly unique. For example, a composite key may not be unique if one of its columns is null.

Transformation bugs can create duplicates. A join may multiply rows if the join condition is not unique. A union may include the same data twice. A window function may not partition correctly.

## Defining what a duplicate is

Before you can find duplicates, you must define what makes two rows duplicates. A duplicate is not always an exact copy of every column. Often, duplicates are defined by a subset of columns called the duplicate key or business key. For example, two rows may have the same customer_id and email, but different names or addresses. Are they duplicates? It depends on the business rules. You might consider them duplicates if the customer_id is supposed to be unique. You might consider them different if the email is the same but the customer_id is different.

You should define the duplicate key explicitly. Document it. Use it consistently across all detection and removal logic. Common duplicate keys include a single column such as order_id, a composite key such as customer_id and email, or a set of columns that together should be unique.

When you define the duplicate key, consider nulls. In SQL, nulls are not equal to each other. Two rows with null in the key column may not be considered duplicates by some operations. You may need to handle nulls explicitly. You may use coalesce or null-safe comparisons.

Consider case sensitivity. If a column contains text, two values may differ only in case. You may want to treat them as duplicates. You may need to normalize case before comparing. Consider leading and trailing whitespace. You may need to trim values before comparing. Consider different representations of the same value, such as "NY" and "New York". You may need to standardize values before comparing.

## Use GROUP BY and HAVING to find duplicates

The most straightforward way to identify duplicates is by grouping records and counting occurrences. The GROUP BY clause groups rows that have the same values in the specified columns. The COUNT(*) function counts the number of rows in each group. The HAVING clause filters the grouped results to show only groups that have more than one occurrence. The ORDER BY clause sorts the results by the occurrence count.

The following SQL query identifies duplicates based on customer_id and email. Each line is commented.

```sql
-- Select the duplicate key columns and the occurrence count.
SELECT 
    customer_id, 
    email, 
    -- COUNT(*) counts the number of rows in each group.
    -- The alias occurrence_count gives the count a readable name.
    COUNT(*) AS occurrence_count
-- The FROM clause specifies the table.
FROM sales.customers
-- The GROUP BY clause groups rows that have the same customer_id and email.
-- All rows with the same combination of customer_id and email are placed in the same group.
GROUP BY customer_id, email
-- The HAVING clause filters the groups.
-- It keeps only groups where the count is greater than 1.
-- Groups with exactly one row are excluded.
HAVING COUNT(*) > 1
-- The ORDER BY clause sorts the results by occurrence_count in descending order.
-- Groups with the most duplicates appear first.
ORDER BY occurrence_count DESC;
```

This query returns all combinations of customer_id and email that appear multiple times in the table. It helps you understand the scope of duplication. For example, if a customer_id appears three times with the same email, the query returns one row with occurrence_count equal to 3. If a customer_id appears with two different emails, those are not duplicates based on this key, so they are not returned.

The GROUP BY and HAVING approach is simple and efficient. It is supported by all SQL engines. It is a good first step when you want to count duplicates and understand which keys are affected. However, it has a limitation. It returns only the duplicate key columns and the count. It does not return the full rows. If you want to see the actual duplicate records, you need to join the result back to the original table or use a window function.

You can extend the query to return more information. For example, you can include the minimum and maximum created_at timestamps for each duplicate group. This helps you understand when the duplicates were created. The following SQL query shows how. Each line is commented.

```sql
-- Select the duplicate key columns and additional information.
SELECT 
    customer_id, 
    email, 
    COUNT(*) AS occurrence_count,
    -- MIN(created_at) returns the earliest creation time in the group.
    MIN(created_at) AS first_seen,
    -- MAX(created_at) returns the latest creation time in the group.
    MAX(created_at) AS last_seen
FROM sales.customers
GROUP BY customer_id, email
HAVING COUNT(*) > 1
ORDER BY occurrence_count DESC;
```

This query tells you not only how many duplicates there are but also when they first and last appeared. This is useful for investigating the source of duplication.

## Use QUALIFY with window functions

The QUALIFY clause provides a more elegant approach by filtering the results of window functions directly, without requiring subqueries. This approach is particularly useful when you need to see the actual duplicate rows, not just counts. The QUALIFY clause is supported in Databricks SQL and many modern SQL engines. It allows you to write a window function in the SELECT list or in the QUALIFY clause and filter on its result.

The following SQL query returns all columns from the duplicate rows. Each line is commented.

```sql
-- Select all columns from the table.
SELECT *
FROM sales.customers
-- The QUALIFY clause filters the results of window functions.
-- The window function COUNT(*) OVER (PARTITION BY customer_id, email) counts the number of rows in each partition.
-- The PARTITION BY clause defines the duplicate key.
-- The COUNT(*) OVER (...) expression returns the count for each row.
-- The QUALIFY clause keeps only rows where the count is greater than 1.
QUALIFY COUNT(*) OVER (PARTITION BY customer_id, email) > 1;
```

This query might return results like the following table. The table shows two rows for customer 1001 with the same email but different names, and two rows for customer 1002 with the same email but different names and statuses.

| customer_id | email | name | created_at | status |
| --- | --- | --- | --- | --- |
| 1001 | jane@contoso.com | Jane Doe | 2024-01-15 | Active |
| 1001 | jane@contoso.com | Jane D. | 2024-03-20 | Active |
| 1002 | bob@fabrikam.com | Bob Smith | 2024-02-10 | Pending |
| 1002 | bob@fabrikam.com | Robert Smith | 2024-02-11 | Active |

With this pattern, you get all columns from the duplicate rows. This makes it easier to investigate the source of duplication. You can see the differences between the duplicate rows. In the example, the names differ. This may indicate that the customer updated their name, and both the old and new records were kept. It may indicate a data entry error. It may indicate that two different customers were assigned the same customer_id by mistake.

The QUALIFY approach is concise and readable. It avoids the need for a subquery or a self-join. It is often the preferred method when you want to see the full duplicate rows. However, it may not be supported in all SQL engines. In engines that do not support QUALIFY, you can achieve the same result with a subquery. The following SQL query shows the equivalent using a subquery. Each line is commented.

```sql
-- Use a subquery to compute the count for each row.
SELECT *
FROM (
    SELECT
        *,
        -- The window function counts rows in each partition.
        COUNT(*) OVER (PARTITION BY customer_id, email) AS row_count
    FROM sales.customers
) AS subquery
-- Filter the subquery to keep only rows where row_count is greater than 1.
WHERE row_count > 1;
```

This query produces the same result as the QUALIFY version. It is more verbose but works in more engines. You can use either approach depending on your environment.

## Find duplicates using PySpark window functions

In PySpark, you can use window functions combined with filtering to identify duplicate records. The Window class defines the partition. The count function computes the number of rows in each partition. The withColumn method adds the count as a new column. The filter method keeps only rows where the count is greater than 1. The drop method removes the helper column.

The following PySpark code identifies duplicates based on customer_id and email. Each line is commented.

```python
# Import the count function and the Window class.
from pyspark.sql.functions import count
from pyspark.sql.window import Window

# Define the window specification.
# The partitionBy method defines the duplicate key.
# All rows with the same customer_id and email are placed in the same partition.
window_spec = Window.partitionBy("customer_id", "email")

# Add a row_count column using the window function.
# The count("*") function counts the number of rows in each partition.
# The over(window_spec) method applies the window function to each partition.
duplicates_df = (
    df.withColumn("row_count", count("*").over(window_spec))
    # Filter to keep only rows where row_count is greater than 1.
    .filter("row_count > 1")
    # Drop the helper column.
    .drop("row_count")
)

# Display the duplicate rows.
display(duplicates_df)
```

This code returns all columns from the duplicate rows. It is equivalent to the SQL QUALIFY approach. You can use it to investigate duplicates in a PySpark notebook or job. You can also write the result to a table for further analysis.

You can extend this code to rank duplicates. For example, you can use row_number to assign a number to each row in the partition. This allows you to keep the first row and identify the rest as duplicates. The following PySpark code shows how. Each line is commented.

```python
from pyspark.sql.functions import row_number
from pyspark.sql.window import Window

# Define the window specification with an order.
# The orderBy clause determines which row is first.
# In this example, we order by created_at descending, so the most recent row is first.
window_spec = Window.partitionBy("customer_id", "email").orderBy(col("created_at").desc())

# Add a row number column.
df_with_row_num = df.withColumn("row_num", row_number().over(window_spec))

# Identify duplicates: rows where row_num is greater than 1.
duplicates_df = df_with_row_num.filter("row_num > 1").drop("row_num")

# Display the duplicate rows.
display(duplicates_df)
```

This approach is useful when you want to keep one row and remove the others. The row with row_num equal to 1 is kept. The rows with row_num greater than 1 are duplicates. You can choose the order to decide which row to keep. For example, you might keep the most recent row, the oldest row, or the row with the most complete data.

## Find duplicates using exceptAll in PySpark

Alternatively, you can use the exceptAll method to compare the original DataFrame against a deduplicated version. The exceptAll method performs a set difference that preserves duplicates. It returns all rows from the first DataFrame that are not in the second DataFrame, keeping duplicate occurrences.

The following PySpark code identifies duplicates using exceptAll. Each line is commented.

```python
# Create a deduplicated version of the DataFrame.
# The dropDuplicates method removes duplicate rows based on the specified columns.
# It keeps one row for each unique combination of customer_id and email.
df_deduplicated = df.dropDuplicates(["customer_id", "email"])

# Use exceptAll to find the rows that are in the original but not in the deduplicated version.
# The exceptAll method preserves duplicates.
# It returns all rows from the first DataFrame that are not in the second DataFrame.
df_duplicates = df.exceptAll(df_deduplicated)

# Display the duplicate rows.
display(df_duplicates)
```

The exceptAll method works as follows. First, `df.dropDuplicates(["customer_id", "email"])` creates a DataFrame with one row per unique combination of customer_id and email. Second, `exceptAll()` compares the original DataFrame against this deduplicated version. Third, for each unique combination, one occurrence is matched and removed. The remaining occurrences are the extra duplicates. For example, if customer 1001 appears three times in the original DataFrame and once in the deduplicated version, `exceptAll()` returns two rows. These are the extra occurrences.

It is important to understand the difference between except and exceptAll. Unlike except, which removes all matching rows and returns distinct results, exceptAll preserves the duplicate structure. If you have three identical rows in the original and one in the deduplicated set, exceptAll returns exactly two rows. The except method would return zero rows because it removes all matching rows and returns distinct results. The exceptAll method is therefore the correct choice when you want to identify the extra duplicate occurrences.

The exceptAll approach is simple and concise. It does not require window functions or grouping. It works well when you want to find the exact rows that are duplicates. However, it may be less efficient than window functions for large datasets because it requires a full comparison of the DataFrames. You should test performance with your data.

## Comparing the methods

Each method for identifying duplicates has advantages and disadvantages. The GROUP BY and HAVING approach is simple and efficient. It returns counts and grouped keys. It is a good first step for understanding the scope of duplication. It does not return the full rows. The QUALIFY with window functions approach returns the full rows. It is concise and readable. It is supported in Databricks SQL and many modern engines. The PySpark window function approach is similar to QUALIFY but uses the DataFrame API. It is useful in notebooks and jobs. The exceptAll approach is simple and does not require window functions. It may be less efficient for large datasets.

You can use different methods for different purposes. Use GROUP BY and HAVING to count duplicates and identify which keys are affected. Use QUALIFY or window functions to see the actual duplicate rows. Use exceptAll for a quick set-based comparison. Use row_number to rank duplicates and decide which to keep. You can combine methods. For example, you can use GROUP BY to find keys with duplicates, then use QUALIFY to inspect the rows for those keys.

## Handling nulls in duplicate detection

Nulls require special attention. In SQL, nulls are not equal to each other. Two rows with null in the duplicate key column may not be considered duplicates by GROUP BY. In many engines, GROUP BY treats nulls as a single group. This means rows with null in the key column are grouped together. However, this behavior is not consistent across all engines. In PySpark, dropDuplicates treats nulls as equal. Two rows with null in the same column are considered duplicates. You should test the behavior in your environment.

If you want to treat nulls as equal explicitly, you can use coalesce to replace nulls with a sentinel value. For example, you can use `coalesce(customer_id, -1)` in the GROUP BY or window partition. This ensures that nulls are grouped together. You can also use null-safe comparison operators if your engine supports them.

The following SQL example uses coalesce to handle nulls in the duplicate key. Each line is commented.

```sql
-- Use coalesce to replace nulls with a sentinel value.
SELECT 
    customer_id, 
    email, 
    COUNT(*) AS occurrence_count
FROM sales.customers
-- The GROUP BY uses coalesce to treat nulls as equal.
-- If customer_id is null, it is replaced with -1 for grouping.
GROUP BY coalesce(customer_id, -1), email
HAVING COUNT(*) > 1
ORDER BY occurrence_count DESC;
```

The following PySpark example uses fillna to replace nulls before detecting duplicates. Each line is commented.

```python
# Replace nulls in the duplicate key columns with sentinel values.
df_filled = df.fillna({"customer_id": -1, "email": "unknown@example.com"})

# Then use dropDuplicates or window functions to find duplicates.
df_deduplicated = df_filled.dropDuplicates(["customer_id", "email"])
df_duplicates = df_filled.exceptAll(df_deduplicated)
display(df_duplicates)
```

## Case sensitivity, trimming, and normalization

Text columns may contain values that differ only in case or whitespace. For example, "jane@contoso.com" and "Jane@Contoso.com" may be considered duplicates. "New York" and "New York " may be considered duplicates. You should normalize values before comparing them.

You can use lower or upper to normalize case. You can use trim to remove leading and trailing whitespace. You can use regexp_replace to remove internal whitespace or special characters. You can use standardize functions to map different representations to a canonical form.

The following SQL example normalizes case and whitespace before grouping. Each line is commented.

```sql
SELECT 
    customer_id, 
    -- Normalize the email: convert to lower case and trim whitespace.
    lower(trim(email)) AS normalized_email,
    COUNT(*) AS occurrence_count
FROM sales.customers
GROUP BY customer_id, lower(trim(email))
HAVING COUNT(*) > 1
ORDER BY occurrence_count DESC;
```

The following PySpark example does the same. Each line is commented.

```python
from pyspark.sql.functions import lower, trim

# Normalize the email column.
df_normalized = df.withColumn("normalized_email", lower(trim(col("email"))))

# Detect duplicates using the normalized email.
df_deduplicated = df_normalized.dropDuplicates(["customer_id", "normalized_email"])
df_duplicates = df_normalized.exceptAll(df_deduplicated)
display(df_duplicates)
```

## Investigating duplicates

Once you identify duplicates, you need to investigate them. You want to understand why they occurred and how to prevent them. You can look at the duplicate rows and compare their columns. You can look at the created_at and updated_at timestamps. You can look at the source system or ingestion job. You can look at the data quality metrics.

The following SQL query uses QUALIFY to return duplicates with additional context. Each line is commented.

```sql
SELECT 
    *,
    -- Count the occurrences in the partition.
    COUNT(*) OVER (PARTITION BY customer_id, email) AS occurrence_count,
    -- Rank the rows by created_at descending.
    ROW_NUMBER() OVER (PARTITION BY customer_id, email ORDER BY created_at DESC) AS row_num
FROM sales.customers
-- Filter to keep only rows in partitions with more than one row.
QUALIFY COUNT(*) OVER (PARTITION BY customer_id, email) > 1
ORDER BY customer_id, email, created_at;
```

This query returns all duplicate rows with an occurrence count and a row number. The row number helps you see which row is the most recent. You can use this information to decide which row to keep and which to remove. You can also see if the duplicates have different names, addresses, or statuses. This helps you understand whether they are true duplicates or different records that share the same key.

## Performance considerations

Identifying duplicates can be expensive. Grouping and window functions require shuffling data across the cluster. The cost depends on the size of the table and the number of distinct keys. You can improve performance by partitioning the table by the duplicate key or by a related column. You can use ZORDER to co-locate related data. You can use Delta Lake optimization features such as OPTIMIZE and file compaction to reduce the number of files. You can use approximate distinct count functions when exact counts are not necessary. You can filter the data before grouping if you only need to check a subset.

You should test performance with realistic data volumes. Use the query profile or execution plan to identify bottlenecks. If the query is too slow, consider using a sample of the data to estimate the scope of duplication. Consider using a separate table or materialized view to store duplicate detection results. Consider scheduling duplicate detection during off-peak hours.
