## Handle semi-structured data

Semi-structured data sits between fully structured data, which fits neatly into rows and columns, and unstructured data, which has no inherent schema. JSON documents, XML records, and event payloads are common examples. They have some structure, such as key-value pairs and nested objects, but the structure can vary from record to record and can change over time. Traditionally, semi-structured data was stored as JSON strings, which are flexible but inefficient to query. Every query had to parse the string, and the database could not optimize access to nested fields. The VARIANT data type changes this. VARIANT stores semi-structured data in an optimized binary format that supports fast reads and writes while preserving the flexibility of a schemaless format.

VARIANT matters because semi-structured data is everywhere. Applications emit JSON events. APIs return JSON responses. Log files are often JSON. IoT devices send JSON payloads. Storing these as strings works for small volumes, but it becomes a bottleneck at scale. Parsing JSON strings on every query is expensive. VARIANT avoids this by encoding the data once and storing it in a format that the query engine can navigate directly. It supports nested objects, arrays, and scalar values. It allows you to query fields with a JSON path expression, cast values to concrete types, and inspect the schema of a variant value. It integrates with Delta Lake and Unity Catalog, so variant columns are governed like any other column.

These notes cover the VARIANT data type from first principles. They explain what VARIANT is, how it differs from JSON strings and native complex types, and how to create variant columns with `parse_json`. They explain how to query variant data with `variant_get`, the colon operator, and the `:` syntax. They explain how to inspect schemas with `schema_of_variant` and `schema_of_variant_agg`. They explain the limitations of VARIANT, including the inability to use variant columns for partitioning, clustering, comparisons, grouping, ordering, and set operations. They also cover performance optimization with variant shredding, null handling, case sensitivity, time zones, best practices, common mistakes, testing, and an end-to-end example. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand how to store, query, and optimize semi-structured data using VARIANT.

## Understanding the VARIANT data type

The VARIANT data type represents semi-structured data. It can store scalar values, objects, and arrays. A scalar is a single value, such as a number, string, boolean, or null. An object is a collection of key-value pairs, where the keys are strings. An array is an ordered list of values. These are the same structures that JSON supports, and VARIANT is designed to store JSON-like data. However, VARIANT is not limited to JSON. It can also store values that are cast from other types, such as a decimal number or a struct.

VARIANT was introduced in Databricks Runtime 15.3 and is generally available. It is supported by Delta Lake tables and Apache Iceberg v3 tables. To use VARIANT in a Delta table, you create a column with the VARIANT type. You can create the column explicitly with `CREATE TABLE`, or you can create a table from a query that produces a variant column. The following SQL example creates a table with a variant column.

```sql
-- Create a table with a variant column.
-- The raw_data column has the VARIANT type.
-- The table is created in the sales.bronze schema in Unity Catalog.
CREATE TABLE sales.bronze.events (
  event_id STRING,
  event_time TIMESTAMP,
  -- The payload column stores semi-structured data as VARIANT.
  -- VARIANT can store objects, arrays, and scalar values.
  payload VARIANT
);
```

The example creates a table with a variant column named `payload`. The column can store any semi-structured data. You can insert values into the column by casting a JSON string to VARIANT or by using `parse_json`. The following SQL example inserts a row with a JSON payload.

```sql
-- Insert a row into the events table.
-- The payload column is populated with a JSON object.
-- parse_json converts the JSON string to VARIANT.
INSERT INTO sales.bronze.events (event_id, event_time, payload)
VALUES (
  'evt_001',
  current_timestamp(),
  -- The JSON object has nested fields: user, action, and items.
  -- parse_json validates the JSON and converts it to VARIANT.
  parse_json('{
    "user": {"id": "u123", "name": "Alice"},
    "action": "purchase",
    "items": [
      {"sku": "A1", "quantity": 2},
      {"sku": "B2", "quantity": 1}
    ]
  }')
);
```

The example inserts a JSON object into the variant column. The `parse_json` function converts the JSON string to VARIANT. The JSON object contains a nested `user` object, an `action` string, and an `items` array of objects. VARIANT stores this structure in an optimized binary format.

## Creating variant values with parse_json

The `parse_json` function converts a JSON string to VARIANT. It is the primary way to create variant values from JSON data. In SQL, you call `parse_json` with a string literal or a column. In PySpark, you call `parse_json` from `pyspark.sql.functions`. The function returns a new column of type VARIANT. If the input string is not valid JSON, `parse_json` raises an error. To return null instead of an error for invalid JSON, use `try_parse_json`.

The following PySpark example reads a JSON file as text and converts each line to VARIANT.

```python
# Import the parse_json and col functions.
from pyspark.sql.functions import parse_json, col

# Read the JSON file as text.
# Each line of the file is a JSON object.
# The text format reads each line as a single string column named "value".
df_text = spark.read.text("/Volumes/sales/bronze/raw/events.json")

# Convert the JSON string column to VARIANT.
# parse_json parses the JSON string and returns a VARIANT column.
# The alias names the new column "data".
df_variant = df_text.select(parse_json(col("value")).alias("data"))

# Display the variant DataFrame.
# The data column contains the parsed semi-structured data.
display(df_variant)
```

The example reads a JSON file as text and converts each line to VARIANT. The `parse_json` function parses the JSON string and returns a variant column. If a line contains invalid JSON, `parse_json` raises an error. To handle invalid JSON gracefully, use `try_parse_json`, which returns null for invalid input. The following example uses `try_parse_json`.

```python
# Import the try_parse_json function.
from pyspark.sql.functions import try_parse_json, col

# Convert the JSON string column to VARIANT with error tolerance.
# try_parse_json returns null for invalid JSON instead of raising an error.
# This is useful when the source data may contain malformed JSON.
df_variant = df_text.select(try_parse_json(col("value")).alias("data"))

# Display the result.
display(df_variant)
```

The `try_parse_json` function is the safer choice when the source data may contain malformed JSON. It allows the pipeline to continue and lets you inspect the rows that failed to parse. You can filter on `data IS NULL` to find invalid rows.

## Querying variant data with variant_get

The `variant_get` function extracts a value from a variant expression using a JSON path expression. It takes three arguments: the variant expression, the path, and the target type. The path is a string literal that uses JSON path syntax. The target type is a string literal that names a SQL type, such as `string`, `int`, `double`, `array<int>`, or `object`. If the path does not exist, `variant_get` returns null. If the path exists but the value cannot be cast to the target type, `variant_get` raises an `INVALID_VARIANT_CAST` error. To return null instead of an error on a failed cast, use `try_variant_get`.

The following SQL example queries a variant column with `variant_get`.

```sql
-- Query the payload column using variant_get.
-- The first argument is the variant column.
-- The second argument is the JSON path expression.
-- The third argument is the target type.
SELECT
  event_id,
  -- Extract the user name as a string.
  -- The path $.user.name navigates to the name field inside the user object.
  variant_get(payload, '$.user.name', 'string') AS user_name,
  -- Extract the action as a string.
  variant_get(payload, '$.action', 'string') AS action,
  -- Extract the first item's SKU as a string.
  -- The path $.items[0].sku navigates to the sku field of the first item.
  variant_get(payload, '$.items[0].sku', 'string') AS first_sku
FROM sales.bronze.events;
```

The query extracts the user name, action, and first item SKU from the payload. The `$.` prefix denotes the root of the variant value. The `.` operator navigates into an object. The `[n]` operator navigates into an array by index. The target type `string` casts the extracted value to a string. If the value is a number and you request a string, `variant_get` casts it. If the value is an object and you request a string, the cast fails.

The equivalent PySpark query uses `variant_get` from `pyspark.sql.functions`.

```python
# Import the variant_get function.
from pyspark.sql.functions import variant_get, col

# Read the events table.
df_events = spark.read.table("sales.bronze.events")

# Extract fields from the payload column.
# variant_get takes the variant column, the path, and the target type.
df_extracted = df_events.select(
    "event_id",
    # Extract the user name as a string.
    variant_get(col("payload"), "$.user.name", "string").alias("user_name"),
    # Extract the action as a string.
    variant_get(col("payload"), "$.action", "string").alias("action"),
    # Extract the first item's SKU as a string.
    variant_get(col("payload"), "$.items[0].sku", "string").alias("first_sku")
)

# Display the extracted fields.
display(df_extracted)
```

The PySpark example produces the same result as the SQL example. The `variant_get` function is the most explicit way to extract values from a variant column. It requires you to specify the target type, which makes the result deterministic. If the path does not exist, the result is null. If the cast fails, the function raises an error.

## Querying variant data with the colon operator

VARIANT supports a shorthand syntax for navigating nested data. The colon operator (`:`) extracts a field from a variant object. The dot operator (`.`) navigates into a nested object. The bracket operator (`[n]`) accesses an array element by index. This syntax is similar to JSON path syntax and is often more concise than `variant_get`. The following SQL example uses the colon operator.

```sql
-- Query the payload column using the colon operator.
-- The syntax payload:user.name navigates to the name field
-- inside the user object.
SELECT
  event_id,
  -- Extract the user name using the colon operator.
  payload:user.name AS user_name,
  -- Extract the action using the colon operator.
  payload:action AS action,
  -- Extract the first item's SKU using the colon operator.
  payload:items[0].sku AS first_sku
FROM sales.bronze.events;
```

The colon operator is concise, but it returns a variant value, not a typed value. To cast the result to a concrete type, you use the `::` operator. The following example casts the extracted values.

```sql
-- Query the payload column and cast the results to concrete types.
SELECT
  event_id,
  -- Extract the user name and cast it to a string.
  payload:user.name::STRING AS user_name,
  -- Extract the action and cast it to a string.
  payload:action::STRING AS action,
  -- Extract the first item's SKU and cast it to a string.
  payload:items[0].sku::STRING AS first_sku
FROM sales.bronze.events;
```

The `::STRING` cast converts the variant value to a string. If the value cannot be cast, the query fails. Use `try_cast` to return null instead of an error. The colon operator is convenient for exploration and for simple queries. For production pipelines, `variant_get` is often preferred because it makes the target type explicit and allows you to choose between strict and tolerant casting.

## Inspecting the schema of variant data

The `schema_of_variant` function returns the schema of a variant expression in DDL format. It is useful for understanding the structure of your semi-structured data. The following SQL example inspects the schema of a variant value.

```sql
-- Inspect the schema of a variant value.
-- schema_of_variant returns a string containing the schema in DDL format.
SELECT schema_of_variant(parse_json('{
  "user": {"id": "u123", "name": "Alice"},
  "action": "purchase",
  "items": [
    {"sku": "A1", "quantity": 2},
    {"sku": "B2", "quantity": 1}
  ]
}'));
```

The result is a string like `OBJECT<action: STRING, items: ARRAY<OBJECT<quantity: BIGINT, sku: STRING>>, user: OBJECT<id: STRING, name: STRING>>`. The schema shows the types of each field. For arrays, the schema shows the element type. If the array contains conflicting types, the element type is inferred as VARIANT. The `schema_of_variant_agg` aggregate function returns the aggregated schema of a collection of variant values. It is useful when you have many rows and want to see the combined schema.

The following PySpark example uses `schema_of_variant` to inspect a variant column.

```python
# Import the schema_of_variant function.
from pyspark.sql.functions import schema_of_variant, col

# Read the events table.
df_events = spark.read.table("sales.bronze.events")

# Inspect the schema of the payload column.
# schema_of_variant returns a column containing the schema string.
df_schema = df_events.select(schema_of_variant(col("payload")).alias("schema"))

# Display the schema.
display(df_schema)
```

The example returns the schema of the payload column for each row. If the payloads have different structures, the schema may vary. Use `schema_of_variant_agg` to get a combined schema across all rows.

## Limitations of the VARIANT data type

VARIANT is powerful, but it has limitations. Understanding these limitations helps you decide when to use VARIANT and when to use native complex types such as structs and arrays. The following table summarizes the limitations.

| Limitation | Description |
|---|---|
| No partitioning or clustering | VARIANT columns cannot be used as partition columns, clustering keys, or Z-order keys. |
| No comparisons | VARIANT values cannot be compared with `<`, `>`, or `=`. You must extract typed values first. |
| No grouping or ordering | VARIANT columns cannot be used in `GROUP BY`, `ORDER BY`, or set operations. |
| No `[*]` syntax | The `[*]` syntax for unpacking all array elements is not supported. Use `variant_explode` instead. |
| Case-sensitive paths | Variant path elements are matched case-sensitively. JSON strings are case-insensitive. |
| Null encoding | VARIANT encodes nulls differently from JSON strings. A variant null is not the same as a SQL null. |
| Size limit | VARIANT values have a size limit. Values that exceed the limit cause an error. |

The table shows that VARIANT is not a drop-in replacement for native complex types in all cases. If you need to partition, cluster, compare, group, or order by a field, extract the field into a typed column first. If you need to explode an array, use `variant_explode` instead of `[*]`. If you need case-insensitive path matching, normalize the case of the keys before storing the data.

The case sensitivity of variant paths is a common source of confusion. In JSON strings, path expressions are case-insensitive. In VARIANT, they are case-sensitive. This means that `payload:user.name` and `payload:user.NAME` refer to different fields. If your data has inconsistent casing, you may need to normalize the keys before storing the data as VARIANT.

## Performance optimization with variant shredding

Variant shredding is a technique that improves query performance on VARIANT columns by storing commonly occurring fields as separate columns in the underlying Parquet files. When you enable shredding, the query engine can read the shredded fields directly, without navigating the variant binary format. This can significantly speed up queries that filter or aggregate on those fields. Shredding applies to top-level variant columns or variant fields in structs. It does not apply to variant data stored inside arrays or maps.

The following SQL example enables variant shredding on a table.

```sql
-- Enable variant shredding on the events table.
-- Shredding extracts commonly occurring fields into separate Parquet columns.
-- This improves query performance for those fields.
ALTER TABLE sales.bronze.events
SET TBLPROPERTIES (
  'delta.variant.shredding.enabled' = 'true'
);
```

The `delta.variant.shredding.enabled` property enables shredding. Once enabled, new data written to the table is shredded. Existing data is not automatically converted. To shred existing data, you must rewrite the table. Shredding adds some write overhead because the extra columns must be written, but it improves read performance for the shredded fields. You should enable shredding when you frequently query specific fields in the variant column.

The following table summarizes the tradeoffs of variant shredding.

| Aspect | Shredding disabled | Shredding enabled |
|---|---|---|
| Read performance | Navigates variant binary | Reads shredded columns directly |
| Write performance | Lower overhead | Higher overhead |
| Storage | Compact | Slightly larger |
| Existing data | Not affected | Not converted automatically |
| Use case | Ad-hoc queries | Frequent queries on known fields |

The table shows that shredding is a tradeoff between read performance and write overhead. Enable it when the read performance benefit outweighs the write cost. If you only query the variant column occasionally, shredding may not be worth the extra write overhead.

## Null handling, case sensitivity, and time zones

Null handling in VARIANT is different from null handling in JSON strings. In JSON, a null value is represented as the literal `null`. In VARIANT, a null is encoded in a way that distinguishes it from a SQL null. A variant null is not the same as a SQL null. If you extract a variant null with `variant_get`, the result is a SQL null. If you check `payload:field IS NULL`, the result may be false if the field contains a variant null. To check for a variant null, use `variant_get(payload, '$.field', 'string') IS NULL` or check `typeof(payload:field) = 'null'`.

Case sensitivity affects variant path expressions. As noted earlier, variant paths are matched case-sensitively. This is different from JSON strings, where paths are case-insensitive. If your data has inconsistent casing in keys, you should normalize the keys before storing the data as VARIANT. You can use `lower()` or `upper()` on the keys when constructing the variant value, or you can use a case-insensitive collation if the table is configured for one.

Time zones affect variant data when it contains timestamps. VARIANT stores timestamps as strings unless you cast them. When you extract a timestamp from a variant column, you must cast it to the `timestamp` type. Spark stores timestamps internally in UTC and displays them in the session time zone. To avoid off-by-hours errors, set the session time zone explicitly at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Use timestamp literals with explicit offsets when comparing to timestamps.

## Schema enforcement, evolution, and expectations

Delta Lake enforces schema on variant columns. The column type is VARIANT, so any valid variant value can be stored. Delta Lake does not enforce the internal structure of the variant value. This means that the schema of the data inside the variant column can vary from row to row. Schema evolution applies to the table schema, not to the variant structure. If you add a new column to the table, schema evolution handles it. If the variant data changes structure, Delta Lake does not enforce or evolve the internal structure. You must handle structural changes in your queries.

Expectations are data quality rules that you define in Lakeflow Spark Declarative Pipelines. You can attach expectations to tables with variant columns. For example, you can define an expectation that a variant field is not null. Expectations are evaluated on the extracted values, not on the variant structure itself. You must extract the field before applying the expectation. The following example shows a Lakeflow Spark Declarative Pipeline that reads a variant column and applies an expectation.

```python
import dlt
from pyspark.sql.functions import variant_get, col

# Define a silver table that reads from the bronze events table.
# The expectation checks that the user name is not null.
@dlt.table(
    name="silver_events",
    comment="Cleaned events with a data quality expectation"
)
@dlt.expect_or_drop("valid_user", "user_name IS NOT NULL")
def silver_events():
    return (dlt.read("sales.bronze.events")
            .select(
                "event_id",
                variant_get(col("payload"), "$.user.name", "string").alias("user_name"),
                variant_get(col("payload"), "$.action", "string").alias("action")
            ))
```

The example extracts the user name and action from the variant column and applies an expectation that the user name is not null. Rows that violate the expectation are dropped. Expectations help you maintain data quality even when the underlying variant structure varies.

## An end-to-end example

Consider a scenario where you ingest JSON events from a cloud storage volume into a bronze table with a variant column, then extract typed fields into a silver table, and finally aggregate the data into a gold table. The following example shows the complete pipeline.

```python
from pyspark.sql.functions import (
    parse_json, variant_get, col, to_timestamp, sum, count
)

# Read the JSON files as text from a Unity Catalog volume.
df_text = spark.read.text("/Volumes/sales/bronze/raw/events/")

# Convert each JSON line to VARIANT.
df_variant = df_text.select(parse_json(col("value")).alias("payload"))

# Write the variant data to a bronze Delta table.
df_variant.write.mode("overwrite").saveAsTable("sales.bronze.events_variant")

# Read the bronze table.
df_bronze = spark.read.table("sales.bronze.events_variant")

# Extract typed fields into a silver table.
df_silver = df_bronze.select(
    variant_get(col("payload"), "$.event_id", "string").alias("event_id"),
    variant_get(col("payload"), "$.user.id", "string").alias("user_id"),
    variant_get(col("payload"), "$.user.name", "string").alias("user_name"),
    variant_get(col("payload"), "$.action", "string").alias("action"),
    variant_get(col("payload"), "$.amount", "double").alias("amount"),
    to_timestamp(variant_get(col("payload"), "$.event_time", "string")).alias("event_time")
).filter(col("event_id").isNotNull())

# Write the silver table.
df_silver.write.mode("overwrite").saveAsTable("sales.silver.events_clean")

# Aggregate the silver data into a gold table.
df_gold = (spark.read.table("sales.silver.events_clean")
    .groupBy("action")
    .agg(
        sum("amount").alias("total_amount"),
        count("*").alias("event_count")
    ))

# Write the gold table.
df_gold.write.mode("overwrite").saveAsTable("sales.gold.events_by_action")
```

The example reads JSON files, converts them to VARIANT, writes a bronze table, extracts typed fields into a silver table, and aggregates into a gold table. The bronze table stores the raw semi-structured data. The silver table extracts the fields needed for analysis. The gold table aggregates the data. This is the medallion architecture applied to semi-structured data. The VARIANT type allows the bronze table to store data with varying structure without schema enforcement, while the silver table enforces a typed schema for downstream analysis.

## Best practices

Use VARIANT instead of JSON strings for semi-structured data. VARIANT provides better read and write performance and integrates with the query engine. Databricks recommends VARIANT as a replacement for storing semi-structured data as JSON strings.

Define the target type explicitly when extracting values with `variant_get`. The target type makes the result deterministic and avoids unexpected casts. Use `try_variant_get` when the data may contain values that cannot be cast.

Normalize the case of keys before storing data as VARIANT. Variant paths are case-sensitive, unlike JSON paths. If your source data has inconsistent casing, normalize it to avoid query errors.

Use `schema_of_variant` and `schema_of_variant_agg` to inspect the structure of your variant data. Understanding the schema helps you write correct queries and decide which fields to extract.

Enable variant shredding when you frequently query specific fields. Shredding improves read performance at the cost of write overhead. Enable it when the read benefit outweighs the write cost.

Extract typed fields into a silver or gold table when you need to partition, cluster, compare, group, or order by those fields. VARIANT columns cannot be used for these operations directly.

Set the session time zone explicitly to UTC. This avoids off-by-hours errors when extracting timestamps from variant data.

Define expectations for data quality. Extract the fields you want to validate and attach expectations to the extracted values.

## Common mistakes and pitfalls

The most common mistake is assuming that variant paths are case-insensitive. They are case-sensitive. If you use the wrong case, the path returns null. Normalize the case of keys or use the correct case in your queries.

A second mistake is trying to use a VARIANT column for partitioning, clustering, comparisons, grouping, ordering, or set operations. These operations are not supported. Extract the field into a typed column first.

A third mistake is using `parse_json` on malformed JSON. `parse_json` raises an error for invalid JSON. Use `try_parse_json` to return null instead of failing the pipeline.

A fourth mistake is forgetting that a variant null is not the same as a SQL null. If you check `payload:field IS NULL`, the result may be false even when the field contains a variant null. Use `variant_get` to extract the value and check for SQL null.

A fifth mistake is using `[*]` to explode an array in a variant column. The `[*]` syntax is not supported. Use `variant_explode` instead.

A sixth mistake is enabling shredding and expecting existing data to be shredded. Shredding only applies to new data written after the property is enabled. To shred existing data, rewrite the table.

## Testing variant logic

Test variant logic with small JSON strings and known data. Verify that `parse_json` produces the expected structure, that `variant_get` extracts the correct values, and that casts behave as expected. The following example shows a test for variant extraction.

```python
from pyspark.sql import Row
from pyspark.sql.functions import parse_json, variant_get, col

# Create a small DataFrame with a JSON string.
test_data = [
    Row(json_str='{"user": {"name": "Alice"}, "action": "purchase", "amount": 100.0}'),
    Row(json_str='{"user": {"name": "Bob"}, "action": "refund", "amount": 50.0}'),
]
df_test = spark.createDataFrame(test_data)

# Convert the JSON string to VARIANT.
df_variant = df_test.select(parse_json(col("json_str")).alias("payload"))

# Extract fields with variant_get.
df_extracted = df_variant.select(
    variant_get(col("payload"), "$.user.name", "string").alias("user_name"),
    variant_get(col("payload"), "$.action", "string").alias("action"),
    variant_get(col("payload"), "$.amount", "double").alias("amount")
)

# Collect the result and verify.
rows = df_extracted.collect()
assert rows[0].user_name == "Alice" and rows[0].action == "purchase"
assert rows[1].user_name == "Bob" and rows[1].action == "refund"
```

The test verifies that `variant_get` extracts the correct values. Run tests like this in your CI pipeline against a small local Spark session. For more complex variant structures, include nested objects and arrays in the test data.

## Performance considerations

VARIANT is designed for performance. It stores semi-structured data in an optimized binary format that is faster to read and write than JSON strings. The query engine can navigate the variant structure without parsing the entire string. However, VARIANT is not as fast as native typed columns for all operations. If you frequently filter or aggregate on a specific field, extracting that field into a typed column and using variant shredding can improve performance.

Variant shredding stores commonly occurring fields as separate Parquet columns. This allows the query engine to read only the shredded columns, avoiding the overhead of navigating the variant binary format. Shredding adds write overhead because the extra columns must be written, but it improves read performance. Enable shredding when the read performance benefit outweighs the write cost.

VARIANT columns are larger than typed columns because they store the structure of the data. If storage is a concern, extract the fields you need into typed columns and store the raw variant data separately or not at all. The medallion architecture supports this: store the raw variant data in bronze, extract typed fields in silver, and aggregate in gold.

Use `variant_get` with explicit types to avoid unnecessary casts. If you know the field is an integer, request an integer. If you request a string and then cast it, you do extra work. The target type in `variant_get` performs the cast in one step.

## Summary

The VARIANT data type stores semi-structured data such as JSON in an optimized binary format. It is available in Databricks Runtime 15.3 and above and is supported by Delta Lake and Apache Iceberg v3 tables. VARIANT can store scalar values, objects, and arrays. It is the recommended replacement for storing semi-structured data as JSON strings because it provides better read and write performance.

You create variant values with `parse_json`, which converts a JSON string to VARIANT. The `parse_json` function raises an error for invalid JSON. Use `try_parse_json` to return null instead. You query variant data with `variant_get`, which extracts a value by JSON path and casts it to a target type. The colon operator provides a shorthand syntax for navigating nested data, but it returns a variant value that must be cast to a concrete type. Use `schema_of_variant` and `schema_of_variant_agg` to inspect the structure of variant data.

VARIANT has limitations. Variant columns cannot be used for partitioning, clustering, comparisons, grouping, ordering, or set operations. Variant paths are case-sensitive, unlike JSON paths. Variant nulls are different from SQL nulls. The `[*]` syntax for exploding arrays is not supported. Use `variant_explode` instead.

Variant shredding improves query performance by storing commonly occurring fields as separate Parquet columns. Shredding adds write overhead and does not convert existing data automatically. Enable it when you frequently query specific fields.

Null handling, case sensitivity, and time zones affect variant data. Normalize the case of keys, check for variant nulls with `variant_get`, and set the session time zone explicitly to UTC. Delta Lake enforces the table schema but does not enforce the internal structure of variant values. Expectations can validate extracted fields.

Best practices include using VARIANT instead of JSON strings, defining target types explicitly, normalizing key casing, inspecting schemas, enabling shredding when beneficial, extracting typed fields for operations that VARIANT does not support, setting the session time zone, and defining expectations. Common mistakes include assuming case-insensitive paths, using VARIANT for unsupported operations, using `parse_json` on malformed JSON, confusing variant nulls with SQL nulls, using `[*]`, and expecting shredding to convert existing data.

Test variant logic with small JSON strings and known data. Performance depends on the operation and the structure of the data. Use `variant_get` with explicit types, enable shredding for frequently queried fields, and extract typed fields for filtering and aggregation. By understanding the VARIANT data type and its capabilities, you can store and query semi-structured data efficiently in Unity Catalog.
