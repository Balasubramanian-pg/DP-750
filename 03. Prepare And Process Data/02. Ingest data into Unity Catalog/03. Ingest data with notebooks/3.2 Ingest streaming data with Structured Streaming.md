## Ingest streaming data with Structured Streaming

Structured Streaming is a scalable, fault-tolerant stream processing engine built into Apache Spark. It lets you process data continuously as it arrives, rather than reading a bounded dataset once. Instead of `spark.read`, you use `spark.readStream` to create a streaming DataFrame that represents an unbounded table. As new data arrives, the streaming DataFrame is updated with new rows, and Spark processes only the new data incrementally. The same DataFrame API you use for batch processing works for streaming, so you can filter, group, aggregate, and join streaming data with the same operations you already know. The difference is that the source is unbounded and the results are computed continuously or in micro-batches.

Structured Streaming matters because many data sources produce data continuously. Message buses such as Kafka and Event Hubs deliver events in real time. Cloud storage directories receive new files as producers write them. Change data capture feeds from databases deliver a stream of inserts, updates, and deletes. Applications need to react to this data with low latency, not wait for a nightly batch. Structured Streaming provides exactly-once processing guarantees, so each record is processed exactly once even in the presence of failures. It uses checkpoints to track progress and resume after interruptions. It supports event-time processing and watermarks to handle late-arriving data. It integrates natively with Delta Lake and Unity Catalog, so streaming data lands in governed tables.

These notes cover Structured Streaming from first principles. They explain the difference between batch and streaming DataFrames, how to read from Kafka and file sources, how to define schemas for streaming, how to write to Unity Catalog tables, and how output modes and checkpoints work. They explain event-time processing, watermarks, windows, and triggers. They also cover schema enforcement, schema evolution, expectations, null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand how to build reliable streaming ingestion pipelines that land data in Unity Catalog with exactly-once guarantees.

## Batch versus streaming DataFrames

A batch DataFrame is bounded. It represents a fixed set of rows read from a source at a point in time. When you call `spark.read`, Spark reads the data and the DataFrame is complete. You can call actions like `count()` and `collect()` and get deterministic results, because the data does not change. A streaming DataFrame is unbounded. It represents a continuously growing set of rows. When you call `spark.readStream`, Spark does not read any data immediately. Instead, it records the intent to read from a streaming source and returns a streaming DataFrame. As new data arrives in the source, the streaming DataFrame is updated with new rows.

The API for streaming DataFrames is the same as for batch DataFrames for most operations. You can use `filter()`, `select()`, `withColumn()`, `groupBy()`, `agg()`, and `join()`. The difference is that some operations are not supported on streaming DataFrames, or they require special handling. For example, `count()` and `collect()` are not allowed on a streaming DataFrame because the result would never be complete. You cannot sort a streaming DataFrame globally because the sort would need to see all the data. You can, however, sort within a window or within a watermark. Streaming aggregations require a watermark to handle late data and to bound the state.

The following table summarizes the differences between batch and streaming DataFrames.

| Aspect | Batch DataFrame | Streaming DataFrame |
|---|---|---|
| Source | Bounded, read once | Unbounded, read continuously |
| Creation | `spark.read` | `spark.readStream` |
| Actions | `count()`, `collect()`, `show()` | `writeStream` only |
| Schema inference | Supported | Not supported for streaming sources |
| Ordering | Global sort supported | Global sort not supported |
| Aggregations | Full support | Requires watermark for some operations |
| Execution | One job per action | Continuous or micro-batch |
| Checkpoint | Not required | Required for fault tolerance |

The table shows that streaming DataFrames are more restrictive than batch DataFrames. The restrictions exist because the data is unbounded. You cannot compute a final count of an infinite stream. You can compute running aggregates, but you must define a watermark so that Spark knows when to finalize a window. You cannot sort an infinite stream, but you can sort within a window.

## Reading streaming data from Kafka

Kafka is a distributed message bus that stores events in topics. It is a common source for streaming ingestion. Structured Streaming can read from Kafka by using the `kafka` format. You provide the bootstrap servers, the topic to subscribe to, and the starting offsets. The following example reads from Kafka.

```python
# Read streaming data from Kafka.
# The format is "kafka".
# The kafka.bootstrap.servers option specifies the Kafka cluster.
# The subscribe option names the topic to read from.
# The startingOffsets option determines where to begin reading.
# "latest" means start from new data only. Use "earliest" to read
# from the beginning of the topic.
df_stream = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker:9092")
    .option("subscribe", "transactions")
    .option("startingOffsets", "latest")
    .load())

# Display the schema of the streaming DataFrame.
# Kafka returns a fixed schema with columns: key, value, topic,
# partition, offset, timestamp, and timestampType.
# The key and value columns are binary. You must cast them to string
# or parse them to use the data.
df_stream.printSchema()
```

The Kafka source returns a DataFrame with a fixed schema. The `key` and `value` columns are binary. The `topic`, `partition`, `offset`, `timestamp`, and `timestampType` columns provide metadata. In most pipelines, you cast the `value` column to a string and parse it as JSON or Avro. The following example parses JSON from Kafka.

```python
# Import the from_json function and the schema types.
from pyspark.sql.functions import col, from_json
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, TimestampType

# Define the schema of the JSON payload.
# The schema describes the structure of the value column.
schema = StructType([
    StructField("transaction_id", StringType(), nullable=False),
    StructField("customer_id", StringType(), nullable=True),
    StructField("amount", DoubleType(), nullable=True),
    StructField("transaction_time", TimestampType(), nullable=True),
])

# Cast the value column to string and parse the JSON.
# from_json parses the JSON string using the defined schema.
# The result is a struct column. The select statement expands
# the struct into separate columns.
df_parsed = (df_stream
    .select(from_json(col("value").cast("string"), schema).alias("data"))
    .select("data.*"))

# Display the parsed streaming DataFrame.
display(df_parsed)
```

The `startingOffsets` option determines where to begin reading when starting a new query. Use `latest` to read only new data, or `earliest` to read from the beginning of the topic. Once you configure a checkpoint location in the write stream, subsequent runs resume from the last processed offset, ignoring `startingOffsets`. This means that after the first run, the stream picks up where it left off, even if it was stopped and restarted.

## Processing file-based streams

Structured Streaming can also read from file sources. As new files arrive in a directory, the stream processes them incrementally. The following example reads CSV files from a directory.

```python
# Import the schema types.
from pyspark.sql.types import StructType, StructField, StringType, DoubleType

# Define the schema explicitly.
# Schema inference is not supported for streaming file sources
# because it would require reading the entire dataset, which is unbounded.
schema = StructType([
    StructField("transaction_id", StringType(), nullable=False),
    StructField("customer_id", StringType(), nullable=True),
    StructField("amount", DoubleType(), nullable=True),
])

# Read streaming CSV files from a directory.
# The format is "csv".
# The header option tells Spark to use the first row as column names.
# The schema option provides the explicit schema.
# The load path is the directory to monitor for new files.
df_file_stream = (spark.readStream
    .format("csv")
    .option("header", "true")
    .schema(schema)
    .load("/Volumes/sales/bronze/incoming/"))
```

The stream monitors the directory for new files. When a new file appears, the stream reads it and processes its rows. The stream tracks which files have been processed in the checkpoint location. If the stream is restarted, it resumes from the last processed file and does not reprocess old files. This gives exactly-once processing for file sources, provided the checkpoint location is reliable.

For streaming file sources, you should always define the schema explicitly. Schema inference is not supported for streaming sources because it requires reading the entire dataset, which is unbounded. If you do not provide a schema, the stream fails. Explicit schemas also make the pipeline deterministic and avoid the extra pass required for inference.

Auto Loader is a specialized file source that is optimized for streaming ingestion from cloud storage. It is the recommended approach for file-based streaming. Auto Loader automatically detects new files, infers the schema, and handles schema evolution. It is more efficient than the generic file source because it uses file notification services and can scale to millions of files. The following example uses Auto Loader.

```python
# Read streaming files using Auto Loader.
# The format "cloudFiles" is the Auto Loader source.
# The cloudFiles.format option specifies the file format (csv).
# The cloudFiles.schemaLocation stores the inferred schema.
# The header option tells Auto Loader that the CSV files have a header.
df_auto = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "csv")
    .option("cloudFiles.schemaLocation", "/schemas/transactions")
    .option("header", "true")
    .load("/Volumes/sales/bronze/incoming/"))
```

Auto Loader is the best choice for file-based streaming because it handles file detection, schema inference, and schema evolution automatically. It is more efficient and more robust than the generic file source.

## Writing streaming data to Unity Catalog tables

You write a streaming DataFrame with `writeStream`. The `writeStream` method returns a `DataStreamWriter` object. You configure it with the output mode, the checkpoint location, and the trigger, and then call `toTable()` to write to a Unity Catalog table. The following example writes a stream to a Delta table.

```python
# Write the streaming DataFrame to a Unity Catalog table.
# The format is "delta", which is the default for Unity Catalog tables.
# The outputMode "append" writes only new rows.
# The checkpointLocation stores the progress of the stream.
# The toTable method writes to the specified Unity Catalog table.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/checkpoints/transactions")
    .toTable("sales.bronze.transactions"))
```

The example writes the parsed stream to `sales.bronze.transactions`. The `outputMode("append")` writes only new rows. The `checkpointLocation` stores the progress of the stream. The `toTable` method writes to the Unity Catalog table. The table is created if it does not exist. If it exists, the stream appends to it according to the output mode.

The checkpoint location is critical. It stores the offsets of the source that have been processed. If the stream is stopped and restarted, it reads the checkpoint and resumes from the last processed offset. Without a checkpoint, the stream cannot recover from failures and may reprocess or lose data. The checkpoint location should be in reliable storage, such as cloud storage or a Unity Catalog volume. Do not use a local path, because it is not durable.

## Output modes

The output mode determines which records are written to the destination. There are three output modes: `append`, `update`, and `complete`. The mode you choose depends on the operation and the destination.

The following table summarizes the output modes.

| Output mode | Behavior | Supported operations |
|---|---|---|
| `append` | Only new rows are written | Most operations, including filters and joins |
| `update` | Changed rows are written | Aggregations without watermark finalization |
| `complete` | All rows are rewritten | Aggregations with complete result |

The `append` mode writes only new rows. It is the default for most operations. It is used when the stream produces new rows and never updates existing ones. Filters, projections, and joins typically use `append` mode. The `update` mode writes changed rows. It is used with aggregations that update the result as new data arrives. The `complete` mode rewrites all rows on each trigger. It is used with aggregations that need the complete result, such as a running count. It is not supported for all operations and can be expensive because it rewrites the entire result.

The following example shows an aggregation with `update` mode.

```python
# Import the aggregation functions.
from pyspark.sql.functions import col, sum, count

# Aggregate the stream by customer.
# The groupBy and agg operations are supported on streaming DataFrames.
# The result is a streaming DataFrame with one row per customer.
df_aggregated = (df_parsed
    .groupBy("customer_id")
    .agg(
        sum("amount").alias("total_amount"),
        count("*").alias("transaction_count")
    ))

# Write the aggregation with update mode.
# The update mode writes changed rows as new data arrives.
# The checkpoint location stores the progress of the stream.
(df_aggregated
    .writeStream
    .format("delta")
    .outputMode("update")
    .option("checkpointLocation", "/checkpoints/customer_totals")
    .toTable("sales.silver.customer_totals"))
```

The example aggregates transactions by customer and writes the result with `update` mode. As new transactions arrive, the totals for affected customers are updated in the destination table. The `update` mode writes only the rows that changed, which is more efficient than rewriting the entire result.

## Event-time processing, watermarks, and windows

Streaming data often arrives out of order and late. An event might be generated at one time and arrive at the stream minutes or hours later. Event-time processing uses the timestamp in the data, rather than the time the data arrived, to group and aggregate. A watermark is a threshold that tells Spark how long to wait for late data. When a watermark is set, Spark drops data that arrives later than the watermark. This bounds the state that Spark must maintain and allows it to finalize windows.

The following example uses a watermark and a window to aggregate transactions by time.

```python
# Import the window function.
from pyspark.sql.functions import window, sum

# Aggregate transactions in 10-minute windows using event time.
# The watermark is set to 10 minutes, which means Spark waits up to
# 10 minutes for late data before finalizing a window.
# The window function groups rows by the transaction_time column
# into 10-minute windows.
df_windowed = (df_parsed
    .withWatermark("transaction_time", "10 minutes")
    .groupBy(window("transaction_time", "10 minutes"))
    .agg(
        sum("amount").alias("total_amount")
    ))

# Write the windowed aggregation.
# The update mode writes the window result as it is updated.
(df_windowed
    .writeStream
    .format("delta")
    .outputMode("update")
    .option("checkpointLocation", "/checkpoints/windowed_totals")
    .toTable("sales.silver.windowed_totals"))
```

The example sets a watermark of 10 minutes on the `transaction_time` column. Spark waits up to 10 minutes for late data before finalizing a window. The `window` function groups rows into 10-minute windows. The result is a streaming DataFrame with one row per window. The `update` mode writes the result as it is updated. Watermarks are required for some streaming aggregations because they bound the state. Without a watermark, Spark would have to keep all data forever to handle arbitrarily late data.

## Triggers

A trigger controls how often the stream processes data. By default, Structured Streaming processes data as soon as it arrives, using micro-batches. You can change the trigger to process data at a fixed interval, to process all available data and stop, or to run continuously. The following table summarizes the trigger types.

| Trigger | Behavior | Use case |
|---|---|---|
| Default | Processes each micro-batch as soon as possible | Low-latency streaming |
| `processingTime` | Processes at a fixed interval | Controlled resource usage |
| `availableNow` | Processes all available data and stops | Scheduled jobs |
| `continuous` | Processes data continuously with low latency | Ultra-low-latency applications |

The `availableNow` trigger is useful for scheduled jobs. It processes all available data and then stops. This is more cost-effective than a continuously running cluster because the cluster can be shut down after the trigger completes. The following example uses the `availableNow` trigger.

```python
# Write the stream with the availableNow trigger.
# The availableNow trigger processes all available data and stops.
# This is useful for scheduled jobs that run at a fixed interval.
# The checkpoint location stores the progress so that the next run
# resumes from where the previous run stopped.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/checkpoints/transactions")
    .trigger(availableNow=True)
    .toTable("sales.bronze.transactions"))
```

The example uses `availableNow=True`. The stream processes all available data and stops. The next time the stream runs, it resumes from the checkpoint. This pattern is common for pipelines that need to run every few minutes or every hour without keeping a cluster running continuously.

## Schema enforcement, evolution, and expectations

Delta Lake enforces schema on streaming writes. When the stream writes to a Delta table, Delta Lake compares the schema of the streaming DataFrame with the table schema. If the DataFrame has extra columns, the write fails unless schema evolution is enabled. If the DataFrame is missing columns, those columns are written as null if they are nullable. If a non-nullable column is missing, the write fails. Schema enforcement protects the table from accidental corruption.

Schema evolution allows the stream to add new columns to the table. In PySpark, you enable it with the `mergeSchema` option. Auto Loader also supports schema evolution through its schema location. The following example shows a streaming write with schema evolution.

```python
# Write the stream with schema evolution enabled.
# The mergeSchema option allows the write to add new columns
# to the target table. Existing rows get null in the new columns.
# Use schema evolution deliberately, because it changes the table schema
# and may break downstream consumers that expect a fixed set of columns.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/checkpoints/transactions")
    .option("mergeSchema", "true")
    .toTable("sales.bronze.transactions"))
```

The example enables schema evolution. If the streaming DataFrame has a column that the table does not have, the column is added to the table. If the table has columns that the DataFrame does not have, those columns are written as null if they are nullable. Schema evolution should be used deliberately. Adding a column changes the table schema and may break downstream queries that use `SELECT *`.

Expectations are data quality rules that you define in Lakeflow Spark Declarative Pipelines. You can attach expectations to streaming tables. Expectations can drop, fail, or warn on rows that violate a rule. For example, you can define an expectation that `transaction_id` is not null. If a row violates the expectation, the pipeline can drop it before it reaches downstream tables. Expectations help you maintain data quality at the point of ingestion.

## Null handling, case sensitivity, and time zones

Null handling is important for streaming ingestion. The stream preserves nulls from the source. If a source column is null, the target column is null, provided the target column is nullable. If the target column is non-nullable, the write fails. You should ensure that non-nullable columns in the target have a default or that the source does not produce nulls for those columns. If the source uses empty strings to represent missing values, you may want to convert them to nulls before writing.

Case sensitivity affects string comparisons. By default, Spark's string comparisons are case-sensitive. If the source has inconsistent casing in a key column, joins and aggregations may not match rows that should match. You can normalize the case in the stream using `upper()` or `lower()`, or use a case-insensitive collation if the table is configured for one. Unity Catalog supports collations at the column level.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. The stream writes timestamps in UTC. When you query the data, the session time zone determines how the timestamps are displayed. To avoid confusion, set the session time zone explicitly at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Use timestamp literals with explicit offsets when comparing to timestamps. Event-time processing uses the timestamp in the data, which should be stored in UTC.

## An end-to-end example

Consider a scenario where you need to ingest transactions from Kafka into a bronze table, aggregate them by customer in real time, and write the result to a silver table. The following example shows the complete pipeline.

```python
from pyspark.sql.functions import col, from_json, window, sum, count
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, TimestampType

# Define the schema of the JSON payload.
schema = StructType([
    StructField("transaction_id", StringType(), nullable=False),
    StructField("customer_id", StringType(), nullable=True),
    StructField("amount", DoubleType(), nullable=True),
    StructField("transaction_time", TimestampType(), nullable=True),
])

# Read from Kafka.
df_stream = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker:9092")
    .option("subscribe", "transactions")
    .option("startingOffsets", "latest")
    .load())

# Parse the JSON payload.
df_parsed = (df_stream
    .select(from_json(col("value").cast("string"), schema).alias("data"))
    .select("data.*"))

# Write the parsed transactions to a bronze table.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/checkpoints/bronze_transactions")
    .toTable("sales.bronze.transactions"))

# Aggregate transactions by customer in 10-minute windows.
df_aggregated = (df_parsed
    .withWatermark("transaction_time", "10 minutes")
    .groupBy(
        window("transaction_time", "10 minutes"),
        "customer_id"
    )
    .agg(
        sum("amount").alias("total_amount"),
        count("*").alias("transaction_count")
    ))

# Write the aggregation to a silver table.
(df_aggregated
    .writeStream
    .format("delta")
    .outputMode("update")
    .option("checkpointLocation", "/checkpoints/silver_customer_totals")
    .toTable("sales.silver.customer_totals"))
```

The example reads from Kafka, parses JSON, writes the parsed transactions to a bronze table, aggregates them by customer in 10-minute windows, and writes the result to a silver table. The bronze write uses `append` mode because it writes raw transactions. The silver write uses `update` mode because it updates the aggregation as new data arrives. Both streams have their own checkpoint locations.

## Best practices

Always configure a checkpoint location. The checkpoint stores the progress of the stream and allows it to resume after a failure. Without a checkpoint, the stream cannot recover and may reprocess or lose data.

Use Auto Loader for file-based streaming. Auto Loader handles file detection, schema inference, and schema evolution automatically. It is more efficient and more robust than the generic file source.

Define schemas explicitly for streaming file sources. Schema inference is not supported for streaming sources because it requires reading the entire dataset. Explicit schemas make the pipeline deterministic.

Use watermarks for streaming aggregations. A watermark bounds the state that Spark must maintain and allows it to finalize windows. Without a watermark, Spark must keep all data forever to handle late data.

Use the `availableNow` trigger for scheduled jobs. It processes all available data and stops, which is more cost-effective than a continuously running cluster.

Set the session time zone explicitly to UTC. This avoids off-by-hours errors when reading and writing timestamps.

Use schema evolution deliberately. Adding columns changes the table schema and may break downstream consumers.

Monitor streaming queries. Track metrics such as input rate, processing rate, batch duration, and latency. Set up alerts for failures and for latency spikes.

## Common mistakes and pitfalls

The most common mistake is not configuring a checkpoint location. Without a checkpoint, the stream cannot recover from failures and may reprocess or lose data. Always configure a checkpoint.

A second mistake is using schema inference for streaming file sources. Schema inference is not supported for streaming sources. Define the schema explicitly.

A third mistake is using an output mode that is not supported for the operation. For example, `complete` mode is not supported for all operations. Check the documentation for the operation you are using.

A fourth mistake is not setting a watermark for streaming aggregations. Without a watermark, Spark must keep all data forever to handle late data. This can cause memory issues and slow performance.

A fifth mistake is using a local path for the checkpoint location. Local paths are not durable. Use cloud storage or a Unity Catalog volume.

A sixth mistake is not handling late data. If data arrives after the watermark, it is dropped. Decide how to handle late data based on your business requirements.

A seventh mistake is not monitoring the stream. Streaming queries can fail silently if not monitored. Set up alerts for failures and for latency spikes.

## Testing streaming pipelines

Testing streaming pipelines is more complex than testing batch pipelines because the data is unbounded. You can test streaming logic by using a batch DataFrame as a source, or by using a test source that you can control. The following example shows a test for a streaming aggregation using a batch DataFrame.

```python
from pyspark.sql import Row
from pyspark.sql.functions import window, sum
from datetime import datetime

# Create a batch DataFrame with test data.
# The data includes transactions at different times.
test_data = [
    Row(customer_id="C1", amount=100.0, transaction_time=datetime(2026, 1, 15, 10, 0)),
    Row(customer_id="C1", amount=200.0, transaction_time=datetime(2026, 1, 15, 10, 5)),
    Row(customer_id="C2", amount=150.0, transaction_time=datetime(2026, 1, 15, 10, 10)),
]
df_test = spark.createDataFrame(test_data)

# Apply the same aggregation logic used in the stream.
# The window function groups rows into 10-minute windows.
df_aggregated = (df_test
    .groupBy(window("transaction_time", "10 minutes"), "customer_id")
    .agg(sum("amount").alias("total_amount")))

# Collect the result and verify.
rows = df_aggregated.orderBy("customer_id").collect()
# Customer C1 has two transactions in the same 10-minute window,
# so the total should be 300.
assert rows[0].customer_id == "C1" and rows[0].total_amount == 300.0
# Customer C2 has one transaction, so the total should be 150.
assert rows[1].customer_id == "C2" and rows[1].total_amount == 150.0
```

The test uses a batch DataFrame to verify the aggregation logic. Streaming logic that does not depend on the streaming-specific features (such as watermarks) can be tested this way. For streaming-specific features, you can use a test source that produces data at a controlled rate.

## Performance considerations

Streaming performance depends on the source, the processing logic, and the destination. Kafka sources are fast but require careful configuration of partitions and consumer groups. File sources are limited by the rate at which files arrive and the number of files. Auto Loader is optimized for file sources and can scale to millions of files.

Micro-batch size affects latency and throughput. Smaller micro-batches reduce latency but increase overhead. Larger micro-batches increase throughput but increase latency. The default trigger processes data as soon as it arrives. You can use `processingTime` to control the interval.

State management is important for aggregations. Watermarks bound the state, but you should also monitor the state size. If the state grows too large, the stream may run out of memory. Use watermarks and windows to keep the state bounded.

Checkpointing adds overhead. The checkpoint is written on each micro-batch. Use a reliable storage location with low latency. Avoid using a location that is slow or has high contention.

Destination performance depends on file size and partitioning. The stream writes to Delta tables. It may create many small files. Run `OPTIMIZE` periodically to compact small files. Use partitioning or liquid clustering on columns that are commonly used in filters.

Use the `availableNow` trigger for scheduled jobs to process all available data and stop. This is more cost-effective than a continuously running cluster.
