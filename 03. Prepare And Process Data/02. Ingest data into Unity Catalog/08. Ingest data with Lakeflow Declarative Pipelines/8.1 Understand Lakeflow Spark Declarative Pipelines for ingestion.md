## Understand Lakeflow Spark Declarative Pipelines for ingestion

Lakeflow Spark Declarative Pipelines is a framework in Azure Databricks for building batch and streaming data pipelines using SQL or Python. Instead of writing imperative code that reads data, transforms it, and writes results step by step, you declare the tables and transformations you want, and the framework determines how to execute them. You define streaming tables, materialized views, and flows in source code files. You then configure a pipeline that processes those definitions. The pipeline handles orchestration, dependency resolution, retries, checkpointing, and incremental processing. For ingestion, the primary target is the streaming table, which is a Delta table designed for append-only or upsert workloads where data arrives continuously.

Declarative pipelines matter because data engineering involves many repetitive concerns that are easy to get wrong. You must determine the correct order to run transformations, manage dependencies between tables, handle failures and retries, checkpoint streaming queries, and ensure that each record is processed exactly once. Writing all of this imperatively is time-consuming and error-prone. A declarative pipeline handles these concerns for you. You focus on the logic of the transformation, and the framework handles the mechanics of execution. This reduces the amount of code you write and the number of places where bugs can hide. It also makes pipelines easier to understand because the structure of the code mirrors the structure of the data flow.

These notes cover Lakeflow Spark Declarative Pipelines from the perspective of ingestion. They explain what the framework is, how streaming tables work, what flows are, and how the pipeline orchestrates execution. They explain the benefits for ingestion: automatic orchestration, transient failure handling, exactly-once processing, and incremental processing. They show how to define tables and flows in SQL and Python, how to configure pipelines, and how to integrate with Unity Catalog and the medallion architecture. They also cover schema enforcement, schema evolution, expectations, null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand how to use declarative pipelines for ingestion into Unity Catalog.

## What Lakeflow Spark Declarative Pipelines is

Lakeflow Spark Declarative Pipelines is a framework that lets you define data pipelines declaratively. You write SQL or Python code that describes the tables you want and the transformations that produce them. The framework reads these definitions, builds a dependency graph, and executes the pipeline in the correct order. It handles the details of reading from sources, writing to sinks, managing state, and recovering from failures. The framework is part of the Lakeflow family, which also includes Lakeflow Connect for managed ingestion. Declarative pipelines are sometimes called DLT pipelines or Lakeflow pipelines. The underlying technology was originally called Delta Live Tables, and the `dlt` module name is still used in Python.

A declarative pipeline consists of two main types of objects: streaming tables and materialized views. A streaming table is a Delta table that is updated incrementally as new data arrives. It processes each row exactly once. A materialized view is a Delta table that is fully recomputed when the pipeline runs. It is used for transformations that cannot be expressed incrementally, such as complex aggregations that require the full dataset. For ingestion, streaming tables are the primary target because they support append-only and upsert workloads with exactly-once semantics. Materialized views are used downstream for aggregation and denormalization.

The following table compares streaming tables and materialized views.

| Aspect | Streaming table | Materialized view |
|---|---|---|
| Update mode | Incremental | Full recompute |
| Data scope | New rows only | Entire dataset |
| Exactly-once | Yes | Not applicable |
| Typical use | Ingestion, append-only | Aggregation, denormalization |
| Source type | Streaming sources, `STREAM` reads | Batch reads |
| Latency | Low | Depends on pipeline schedule |

The table shows that streaming tables are designed for incremental processing, while materialized views are designed for full recomputation. For ingestion, streaming tables are the right choice because they process only new data and guarantee exactly-once semantics. Materialized views are used after ingestion to aggregate and reshape the data.

## Streaming tables as ingestion targets

A streaming table is a Delta table with built-in support for streaming data. When you define a streaming table, the pipeline creates a streaming query that reads from a source, applies transformations, and writes to the table. The pipeline manages the checkpoint location automatically. You do not configure a checkpoint. The pipeline tracks progress and ensures that each input row is processed exactly once. This makes streaming tables ideal for append-only ingestion workloads where data continuously arrives.

The following SQL example defines a streaming table that reads from a Kafka topic.

```sql
-- Create a streaming table that ingests sensor readings from Kafka.
-- The STREAM keyword tells the pipeline to use incremental processing.
-- The table is created in Unity Catalog and is governed by Unity Catalog.
-- The pipeline manages the checkpoint location automatically.
CREATE OR REFRESH STREAMING TABLE manufacturing.bronze.sensor_readings
AS SELECT
    -- Parse the JSON payload from the Kafka value column.
    -- The value column is binary, so cast it to string first.
    from_json(
        CAST(value AS STRING),
        'sensor_id STRING, temperature DOUBLE, reading_time TIMESTAMP'
    ).sensor_id AS sensor_id,
    from_json(
        CAST(value AS STRING),
        'sensor_id STRING, temperature DOUBLE, reading_time TIMESTAMP'
    ).temperature AS temperature,
    from_json(
        CAST(value AS STRING),
        'sensor_id STRING, temperature DOUBLE, reading_time TIMESTAMP'
    ).reading_time AS reading_time
FROM STREAM read_kafka(
    bootstrapServers => 'broker:9092',
    subscribe => 'sensor-readings'
);
```

The SQL example defines a streaming table named `manufacturing.bronze.sensor_readings`. The `STREAM` keyword tells the pipeline to read incrementally from Kafka. The pipeline parses the JSON payload and extracts the sensor ID, temperature, and reading time. The table is created in Unity Catalog. The pipeline manages the checkpoint location and schema evolution automatically. When new messages arrive in Kafka, the pipeline processes them and appends the parsed rows to the table.

The following Python example defines the same streaming table using the `@dlt.table` decorator.

```python
import dlt
from pyspark.sql.functions import col, from_json
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, TimestampType

# Define the schema of the JSON payload.
schema = StructType([
    StructField("sensor_id", StringType(), nullable=False),
    StructField("temperature", DoubleType(), nullable=True),
    StructField("reading_time", TimestampType(), nullable=True),
])

# Define a streaming table using the @dlt.table decorator.
# The decorator registers the function as a streaming table in the pipeline.
# The function returns a streaming DataFrame that the pipeline writes to the table.
@dlt.table(
    name="manufacturing.bronze.sensor_readings",
    comment="Raw sensor readings ingested from Kafka"
)
def sensor_readings():
    # Read from Kafka as a stream.
    df_raw = (spark.readStream
        .format("kafka")
        .option("kafka.bootstrap.servers", "broker:9092")
        .option("subscribe", "sensor-readings")
        .load())
    # Parse the JSON payload.
    return (df_raw
        .select(from_json(col("value").cast("string"), schema).alias("data"))
        .select("data.*"))
```

The Python example defines the same streaming table using the `@dlt.table` decorator. The decorator registers the function as a streaming table. The function returns a streaming DataFrame. The pipeline executes the function when it runs and writes the result to the table. The pipeline manages checkpointing and schema evolution. The table is in Unity Catalog and is governed.

## Flows: defining how data moves

A flow is a definition of how data moves from a source to a target. In SQL, a flow is created implicitly when you define a streaming table with `AS SELECT`. In Python, you can define flows explicitly using the `@dlt.append_flow` decorator or by returning a DataFrame from a function decorated with `@dlt.table`. A flow has a source, a target, and a transformation. The pipeline uses flows to build the dependency graph. Each flow is executed as part of the pipeline update. The pipeline determines the correct order of execution based on the dependencies between flows.

The following SQL example defines multiple streaming tables and a materialized view that depends on them.

```sql
-- Define a streaming table for orders from Kafka.
CREATE OR REFRESH STREAMING TABLE sales.bronze.orders
AS SELECT * FROM STREAM read_kafka(
    bootstrapServers => 'broker:9092',
    subscribe => 'orders'
);

-- Define a streaming table for customers from Kafka.
CREATE OR REFRESH STREAMING TABLE sales.bronze.customers
AS SELECT * FROM STREAM read_kafka(
    bootstrapServers => 'broker:9092',
    subscribe => 'customers'
);

-- Define a materialized view that joins orders and customers.
-- The materialized view is recomputed when the pipeline runs.
-- It depends on the two streaming tables, so the pipeline runs them first.
CREATE OR REFRESH MATERIALIZED VIEW sales.silver.enriched_orders
AS SELECT
    o.order_id,
    o.order_date,
    o.amount,
    c.customer_name,
    c.region
FROM STREAM(sales.bronze.orders) o
JOIN STREAM(sales.bronze.customers) c
ON o.customer_id = c.customer_id;
```

The SQL example defines three objects: two streaming tables and one materialized view. The streaming tables ingest raw orders and customers from Kafka. The materialized view joins the two tables and produces enriched orders. The pipeline determines the execution order: the streaming tables run first, then the materialized view. The pipeline maximizes parallelism where possible. The materialized view is recomputed on each pipeline run, which means it processes the full dataset. For incremental joins, you would use a streaming table instead.

## Benefits of declarative pipelines for ingestion

Declarative pipelines provide several benefits for ingestion. The framework handles orchestration, transient failure handling, exactly-once processing, and incremental processing. These benefits reduce the amount of code you write and the number of failure modes you must handle. The following table summarizes the benefits.

| Benefit | Description |
|---|---|
| Automatic orchestration | The pipeline determines execution order and maximizes parallelism |
| Transient failure handling | Retries at the most granular level, starting with individual Spark tasks |
| Exactly-once processing | Each input row is processed exactly once |
| Incremental processing | Only new or changed data is processed during each update |

The table shows that declarative pipelines handle the mechanics of execution so that you can focus on the transformation logic. Automatic orchestration means you do not write code to sequence tasks. Transient failure handling means you do not write retry logic. Exactly-once processing means you do not manage checkpoints manually. Incremental processing means you do not write logic to identify new data.

### Automatic orchestration

The pipeline builds a dependency graph from the table and flow definitions. It determines the correct execution order. If table B depends on table A, the pipeline runs table A first. If table C and table D are independent, the pipeline runs them in parallel. This maximizes parallelism and minimizes the total runtime. You do not write code to sequence the tasks or to manage dependencies. The framework does it for you.

### Transient failure handling

If a task fails, the pipeline retries at the most granular level possible. It starts with individual Spark tasks. If the task failure is transient, such as a network timeout, the retry may succeed. If the failure persists, the pipeline retries at a higher level, such as the flow or the table. This granular retry reduces the amount of work that must be repeated. You do not write retry logic. The framework handles it.

### Exactly-once processing

Streaming tables guarantee that each input row is processed exactly once. The pipeline manages the checkpoint location and coordinates the checkpoint update with the Delta Lake commit. If the pipeline fails, it resumes from the checkpoint and continues processing. It does not reprocess rows that have already been written, and it does not miss rows that arrived during the failure. You do not manage checkpoints manually. The framework handles it.

### Incremental processing

Streaming tables process only new or changed data during each update. The pipeline tracks which data has been processed and reads only the new data. This reduces the amount of data that must be read and processed, which improves performance and reduces cost. Materialized views are recomputed fully, but they are used for transformations that cannot be expressed incrementally. For ingestion, streaming tables provide the incremental processing benefit.

## Defining tables and flows in Python

In Python, you define streaming tables using the `@dlt.table` decorator. You define materialized views using the same decorator with `@dlt.table` or `@dlt.view`. You define flows using `@dlt.append_flow`. The following example shows a Python pipeline with a streaming table, a materialized view, and an expectation.

```python
import dlt
from pyspark.sql.functions import col, sum, count

# Define a streaming table that reads from a cloud storage location.
# The @dlt.table decorator registers the function as a streaming table.
# The function returns a streaming DataFrame.
@dlt.table(
    name="sales.bronze.orders",
    comment="Raw orders ingested from cloud storage"
)
def bronze_orders():
    return (spark.readStream
        .format("cloudFiles")
        .option("cloudFiles.format", "json")
        .option("cloudFiles.schemaLocation", "/Volumes/sales/bronze/schemas/orders")
        .load("/Volumes/sales/bronze/raw/orders/"))

# Define a silver table that reads from the bronze table and applies an expectation.
# The @dlt.expect_or_drop decorator defines a data quality expectation.
# Rows that violate the expectation are dropped.
@dlt.table(
    name="sales.silver.orders",
    comment="Cleaned orders with a data quality expectation"
)
@dlt.expect_or_drop("valid_amount", "amount > 0")
def silver_orders():
    return (dlt.read_stream("sales.bronze.orders")
        .filter(col("amount").isNotNull()))

# Define a gold materialized view that aggregates the silver table.
@dlt.table(
    name="sales.gold.daily_sales",
    comment="Daily sales aggregation"
)
def gold_daily_sales():
    return (dlt.read("sales.silver.orders")
        .groupBy("order_date")
        .agg(
            sum("amount").alias("total_sales"),
            count("*").alias("order_count")
        ))
```

The Python example defines three tables: a bronze streaming table, a silver streaming table with an expectation, and a gold materialized view. The bronze table reads from cloud storage using Auto Loader. The silver table reads from the bronze table and drops rows where the amount is not positive. The gold table reads from the silver table and aggregates by date. The pipeline determines the execution order and manages checkpointing. The expectations validate data quality.

## Expectations and data quality

Expectations are data quality rules that you define on tables. They are one of the key features of declarative pipelines. You attach an expectation to a table or a column, and the framework evaluates the rule on each row. If a row violates the rule, the framework can drop the row, fail the pipeline, or warn. Expectations help you maintain data quality at the point of ingestion. They are not a replacement for schema enforcement, but they complement it. Schema enforcement validates structure. Expectations validate business rules.

The following table summarizes the expectation decorators in Python.

| Decorator | Behavior |
|---|---|
| `@dlt.expect` | Warns on violation, keeps the row |
| `@dlt.expect_or_drop` | Drops the row on violation |
| `@dlt.expect_or_fail` | Fails the pipeline on violation |
| `@dlt.expect_all` | Applies multiple expectations, warns on violation |
| `@dlt.expect_all_or_drop` | Applies multiple expectations, drops on violation |

The table shows that expectations can warn, drop, or fail. Use `expect` for monitoring, `expect_or_drop` for filtering invalid rows, and `expect_or_fail` for strict validation. The following SQL example defines expectations on a streaming table.

```sql
-- Create a streaming table with expectations.
-- The CONSTRAINT clause defines a data quality rule.
-- The EXPECT clause specifies the rule and the action.
-- The ON VIOLATION DROP ROW clause drops rows that violate the rule.
CREATE OR REFRESH STREAMING TABLE sales.silver.orders (
    CONSTRAINT valid_amount EXPECT (amount > 0) ON VIOLATION DROP ROW,
    CONSTRAINT valid_order_id EXPECT (order_id IS NOT NULL) ON VIOLATION DROP ROW
)
AS SELECT * FROM STREAM(sales.bronze.orders);
```

The SQL example defines two expectations. The first requires the amount to be positive. The second requires the order ID to be not null. Rows that violate either expectation are dropped. The expectations are evaluated as part of the pipeline update. You can query the event log to see how many rows passed or failed each expectation.

## Materialized views versus streaming tables

The choice between a streaming table and a materialized view depends on the transformation. Streaming tables process data incrementally and are ideal for append-only or upsert workloads. Materialized views recompute the full dataset and are ideal for aggregations and joins that cannot be expressed incrementally. The following table compares the two.

| Aspect | Streaming table | Materialized view |
|---|---|---|
| Processing | Incremental | Full recompute |
| Data scope | New rows only | Entire dataset |
| Exactly-once | Yes | Not applicable |
| Typical use | Ingestion, append-only | Aggregation, denormalization |
| Latency | Low | Depends on pipeline schedule |
| Cost | Lower for incremental | Higher for full recompute |

The table shows that streaming tables are more efficient for incremental workloads. Materialized views are simpler for complex transformations that require the full dataset. In a medallion architecture, streaming tables are used in bronze and silver, and materialized views are used in gold. For ingestion, streaming tables are the primary target.

## Integration with Unity Catalog

Declarative pipelines integrate with Unity Catalog. All tables and views created by a pipeline are registered in Unity Catalog. They are governed by Unity Catalog permissions, lineage, and auditing. You can grant access to the tables at the catalog, schema, or table level. You can apply row-level filters and column masks. You can track lineage from source to target. The pipeline itself is a Unity Catalog object. You can control who can run the pipeline and who can view its results.

The following table summarizes the Unity Catalog integration.

| Aspect | Integration |
|---|---|
| Table registration | All tables are registered in Unity Catalog |
| Permissions | Granted at catalog, schema, or table level |
| Row-level filters | Applied to tables |
| Column masks | Applied to tables |
| Lineage | Tracked from source to target |
| Auditing | Access is audited |

The table shows that declarative pipelines are fully integrated with Unity Catalog. This means that ingestion pipelines built with declarative pipelines are governed from the start. You do not need to configure governance separately.

## Null handling, case sensitivity, and time zones

Null handling in declarative pipelines follows the same rules as in other Spark operations. Nulls in the source are preserved unless you filter or replace them. If a target column is non-nullable, a null value causes the write to fail. You can use expectations to drop rows with nulls in required columns. You can use `coalesce` to replace nulls with defaults. In SQL, you can use `CASE` or `COALESCE`. In Python, you can use `when` and `otherwise` or `coalesce`.

Case sensitivity affects string comparisons and column names. In Spark SQL, column names are case-insensitive by default. String values are case-sensitive. If the source data has inconsistent casing, normalize it with `upper` or `lower`, or use a case-insensitive collation if the table is configured for one. Unity Catalog supports collations at the column level.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. When you use `current_timestamp()` or `current_date()` in a pipeline, the values are computed in the session time zone. To avoid off-by-hours errors, set the session time zone explicitly to UTC at the start of your pipeline with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Store timestamps in UTC and convert to local time only for display.

## Best practices

Use streaming tables for ingestion. They process data incrementally and provide exactly-once semantics. Use materialized views for aggregations and joins that cannot be expressed incrementally.

Define expectations for data quality. Use `expect` for monitoring, `expect_or_drop` for filtering, and `expect_or_fail` for strict validation. Monitor the event log to see how many rows pass or fail each expectation.

Use Unity Catalog for all tables. Declarative pipelines create tables in Unity Catalog, so they are governed automatically. Grant permissions at the catalog, schema, or table level.

Set the session time zone explicitly to UTC. This avoids off-by-hours errors when parsing timestamps.

Use Auto Loader for file-based ingestion. Auto Loader integrates with declarative pipelines and handles file detection, schema inference, and schema evolution automatically.

Monitor the pipeline. Use the event log to track progress, expectations, and errors. Set up alerts for failures and for data quality violations.

Test pipeline logic with small datasets. Use the pipeline testing framework to validate expectations and transformations. Run tests in your CI pipeline.

## Common mistakes and pitfalls

The most common mistake is using a materialized view for an incremental workload. Materialized views recompute the full dataset. If the dataset is large, this is expensive and slow. Use a streaming table for incremental workloads.

A second mistake is not defining expectations. Expectations catch data quality issues early. Without them, invalid rows may reach downstream tables and cause incorrect results.

A third mistake is using `expect_or_fail` for every expectation. Failing the pipeline on every violation can cause unnecessary downtime. Use `expect_or_drop` or `expect` for non-critical rules.

A fourth mistake is not setting the session time zone. Timestamps are stored in UTC. If you compare them to local time without converting, you may get incorrect results.

A fifth mistake is not monitoring the event log. The event log records progress, expectations, and errors. If you do not monitor it, you may miss data quality issues or failures.

A sixth mistake is using the wrong read mode. `dlt.read` reads the full table. `dlt.read_stream` reads incrementally. Use `dlt.read_stream` for streaming tables and `dlt.read` for materialized views.

A seventh mistake is not testing pipeline logic. Declarative pipelines are still code. Test the transformations and expectations with small datasets before deploying to production.

## Testing declarative pipelines

Testing declarative pipelines involves verifying that the transformations produce the expected results and that the expectations behave as intended. You can use the pipeline testing framework or test the logic with batch DataFrames. The following example shows a test for a transformation with an expectation.

```python
from pyspark.sql import Row
from pyspark.sql.functions import col

# Create a small DataFrame with test data.
# The data includes a row with a negative amount to test the expectation.
test_data = [
    Row(order_id=1, amount=100.0),
    Row(order_id=2, amount=-50.0),
    Row(order_id=3, amount=200.0),
]
df_test = spark.createDataFrame(test_data)

# Apply the same filter used in the silver table expectation.
df_filtered = df_test.filter(col("amount") > 0)

# Verify that the negative amount row is dropped.
assert df_filtered.count() == 2, f"Expected 2 rows, got {df_filtered.count()}"

# Verify that the remaining rows have positive amounts.
rows = df_filtered.collect()
assert rows[0].amount == 100.0
assert rows[1].amount == 200.0
```

The test verifies that the expectation drops the negative amount row. Run tests like this in your CI pipeline against a small local Spark session. For pipeline-level testing, use the pipeline testing framework to run the pipeline with test data and validate the output.

## Performance considerations

Declarative pipeline performance depends on the type of tables, the sources, and the cluster resources. Streaming tables are more efficient for incremental workloads because they process only new data. Materialized views recompute the full dataset, which can be expensive for large tables. Use streaming tables where possible.

Auto Loader is efficient for file-based ingestion. Use file notification mode with file events for high-volume workloads. Use `maxFilesPerTrigger` and `maxBytesPerTrigger` to control micro-batch size.

The pipeline maximizes parallelism by running independent tables in parallel. This improves performance but also increases resource usage. Size the cluster to match the workload. Use autoscaling to adjust the cluster size dynamically.

The event log records progress and expectations. Query the event log with filters to limit the amount of data scanned. Partition the event log by date if possible.

Use the `availableNow` trigger for scheduled pipelines. It processes all available data and stops, which reduces compute cost compared to a continuously running pipeline.

## An end-to-end example

Consider a scenario where you ingest sensor data from Kafka into a bronze streaming table, clean it into a silver streaming table with an expectation, and aggregate it into a gold materialized view. The following example shows the complete pipeline in Python.

```python
import dlt
from pyspark.sql.functions import col, from_json, window, avg, max, min
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, TimestampType

# Define the schema of the JSON payload.
schema = StructType([
    StructField("sensor_id", StringType(), nullable=False),
    StructField("temperature", DoubleType(), nullable=True),
    StructField("reading_time", TimestampType(), nullable=True),
])

# Define the bronze streaming table.
@dlt.table(
    name="manufacturing.bronze.sensor_readings",
    comment="Raw sensor readings ingested from Kafka"
)
def bronze_sensor_readings():
    df_raw = (spark.readStream
        .format("kafka")
        .option("kafka.bootstrap.servers", "broker:9092")
        .option("subscribe", "sensor-readings")
        .load())
    return (df_raw
        .select(from_json(col("value").cast("string"), schema).alias("data"))
        .select("data.*"))

# Define the silver streaming table with an expectation.
@dlt.table(
    name="manufacturing.silver.sensor_readings",
    comment="Cleaned sensor readings"
)
@dlt.expect_or_drop("valid_temperature", "temperature IS NOT NULL")
def silver_sensor_readings():
    return (dlt.read_stream("manufacturing.bronze.sensor_readings")
        .filter(col("temperature").isNotNull()))

# Define the gold materialized view with 5-minute aggregates.
@dlt.table(
    name="manufacturing.gold.sensor_aggregates",
    comment="5-minute aggregates of sensor readings"
)
def gold_sensor_aggregates():
    return (dlt.read("manufacturing.silver.sensor_readings")
        .groupBy(window("reading_time", "5 minutes"), "sensor_id")
        .agg(
            avg("temperature").alias("avg_temperature"),
            max("temperature").alias("max_temperature"),
            min("temperature").alias("min_temperature")
        ))
```

The example defines three tables: a bronze streaming table, a silver streaming table with an expectation, and a gold materialized view. The bronze table reads from Kafka. The silver table drops rows with null temperatures. The gold table aggregates by 5-minute windows and sensor ID. The pipeline determines the execution order, manages checkpoints, and validates data quality. All tables are in Unity Catalog and are governed.
