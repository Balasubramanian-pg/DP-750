## Configure flows for multiple sources

A flow is a definition of how data moves from a source to a target in a Lakeflow Spark Declarative Pipeline. When you create a streaming table with a query, the pipeline automatically creates a default flow that reads from the source and appends to the table. However, you can also define flows explicitly. Explicit flows let you handle more complex scenarios, such as ingesting data from multiple sources into a single target table. Instead of writing a single query that unions all sources, you create one flow per source. Each flow appends its data to the same target table independently. This approach is more flexible because you can add a new source flow without modifying the existing flows or triggering a full refresh of the target table.

Using multiple flows matters when your data arrives from different systems that share a common schema. For example, you might receive order data from a west region system and an east region system. Both produce the same columns, but they are separate sources. If you use a `UNION` in a single query, adding a new region later requires editing the query and potentially reprocessing all data. With separate flows, you simply add a new flow for the new region. The existing flows continue from their checkpoints, and the new flow starts from its own checkpoint. The target table accumulates data from all flows. This pattern is common in the bronze layer of a medallion architecture, where raw data from many sources lands in a single table for downstream processing.

These notes explain how to configure flows for multiple sources. They describe what a flow is, how to create a streaming table and attach flows in SQL and Python, how flows differ from `UNION`, and how checkpoints and flow names work. They also cover schema enforcement, schema evolution, expectations, null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand how to use flows to combine multiple sources into a single streaming table reliably.

## Understanding flows and their role

A flow is a unit of work in a declarative pipeline. It defines a source, a transformation, and a target. The pipeline uses flows to build a dependency graph. Each flow is executed as part of a pipeline update. When you define a streaming table with a query, the pipeline creates a default flow that reads from the query's source and writes to the table. You can also define flows explicitly to append data from additional sources. Explicit flows are useful when you want to combine multiple sources into one table without using a `UNION`.

The following table compares default flows with explicit flows.

| Aspect | Default flow | Explicit flow |
|---|---|---|
| Creation | Automatically created with a streaming table query | Created manually with `CREATE FLOW` or `@dp.append_flow` |
| Source | The source in the streaming table query | Any source you specify |
| Target | The streaming table | The streaming table you specify |
| Use case | Simple ingestion from one source | Ingesting from multiple sources into one table |
| Checkpoint | Managed by the pipeline | Managed by the pipeline, keyed by flow name |
| Flexibility | Limited to one source per table | Add new sources without modifying existing flows |

The table shows that explicit flows are more flexible. They let you add sources incrementally. Each flow has its own checkpoint, so it processes its source independently. The target table receives appends from all flows.

## Creating a streaming table with multiple flows in SQL

In SQL, you first create the target streaming table without a query. Then you create one flow per source. The flow uses `INSERT INTO target BY NAME SELECT * FROM STREAM(source)`. The `BY NAME` clause matches columns by name, which is safer than matching by position. The `STREAM` keyword reads the source incrementally. The following example creates a target table and two flows.

```sql
-- Create the target streaming table.
-- The table has no query, so no default flow is created.
-- The schema is defined by the first flow that writes to it,
-- or you can define it explicitly.
CREATE OR REFRESH STREAMING TABLE sales.bronze.orders_us;

-- Add a flow from the west region source.
-- The flow reads from the orders_west table incrementally.
-- The INSERT INTO ... BY NAME clause matches columns by name.
-- Each flow appends data to the target table independently.
CREATE FLOW orders_west_flow
AS INSERT INTO sales.bronze.orders_us BY NAME
SELECT * FROM STREAM(sales.bronze.orders_west);

-- Add a flow from the east region source.
-- This flow is independent of the west flow.
-- It has its own checkpoint and processes its source separately.
CREATE FLOW orders_east_flow
AS INSERT INTO sales.bronze.orders_us BY NAME
SELECT * FROM STREAM(sales.bronze.orders_east);
```

The example creates a target table `sales.bronze.orders_us` and two flows. The west flow reads from `sales.bronze.orders_west`. The east flow reads from `sales.bronze.orders_east`. Both flows append to the same target table. The `BY NAME` clause ensures that columns are matched by name, so the order of columns in the source does not matter. Each flow has its own checkpoint. If you add a new region later, you create a new flow without modifying the existing ones.

You can also define the target table schema explicitly to ensure that all flows produce compatible data. The following example defines the schema.

```sql
-- Create the target streaming table with an explicit schema.
-- The schema defines the columns and types that all flows must match.
-- This ensures that all sources produce compatible data.
CREATE OR REFRESH STREAMING TABLE sales.bronze.orders_us (
  order_id STRING,
  customer_id STRING,
  order_date DATE,
  amount DECIMAL(10,2),
  region STRING
);

-- Add a flow from the west region.
-- The BY NAME clause matches the columns in the source to the target.
-- If the source has extra columns, they are ignored.
-- If the source is missing a column, the target column is set to null.
CREATE FLOW orders_west_flow
AS INSERT INTO sales.bronze.orders_us BY NAME
SELECT * FROM STREAM(sales.bronze.orders_west);
```

The example defines the target schema explicitly. The `BY NAME` clause matches columns by name. If a source has extra columns, they are ignored. If a source is missing a column, the target column is set to null if it is nullable. If a non-nullable column is missing, the flow fails. Defining the schema explicitly is a good practice when multiple sources must conform to a common structure.

## Creating multiple flows in Python

In Python, you use the `@dp.append_flow` decorator to define a flow that appends to a target table. You first create the target streaming table with `dp.create_streaming_table`, then define one function per flow. The following example creates a target table and two flows.

```python
# Import the pipelines module.
# The dp module provides the create_streaming_table function
# and the append_flow decorator.
from pyspark import pipelines as dp

# Create the target streaming table.
# The table has no query, so no default flow is created.
# The schema is defined by the first flow that writes to it,
# or you can define it explicitly with a schema argument.
dp.create_streaming_table("sales.bronze.orders_us")

# Add a flow from the west region.
# The @dp.append_flow decorator registers the function as a flow
# that appends to the target table.
# The function returns a streaming DataFrame.
@dp.append_flow(target="sales.bronze.orders_us")
def orders_west_flow():
    # Read from the west region table as a stream.
    # The readStream method reads the table incrementally.
    return spark.readStream.table("sales.bronze.orders_west")

# Add a flow from the east region.
# This flow is independent of the west flow.
# It has its own checkpoint and processes its source separately.
@dp.append_flow(target="sales.bronze.orders_us")
def orders_east_flow():
    # Read from the east region table as a stream.
    return spark.readStream.table("sales.bronze.orders_east")
```

The example creates a target table `sales.bronze.orders_us` and two flows. The west flow reads from `sales.bronze.orders_west`. The east flow reads from `sales.bronze.orders_east`. Both flows append to the same target table. Each flow has its own checkpoint. The `@dp.append_flow` decorator takes the target table name as an argument. The function returns a streaming DataFrame. The pipeline manages the checkpoint and schema.

You can define the target table schema explicitly using the `schema` argument. The following example shows how.

```python
# Import the pipelines module.
from pyspark import pipelines as dp
from pyspark.sql.types import StructType, StructField, StringType, DateType, DecimalType

# Define the target schema.
# The schema defines the columns and types that all flows must match.
schema = StructType([
    StructField("order_id", StringType(), nullable=False),
    StructField("customer_id", StringType(), nullable=True),
    StructField("order_date", DateType(), nullable=True),
    StructField("amount", DecimalType(10,2), nullable=True),
    StructField("region", StringType(), nullable=True),
])

# Create the target streaming table with an explicit schema.
dp.create_streaming_table("sales.bronze.orders_us", schema=schema)

# Add a flow from the west region.
# The flow reads from the west region table and appends to the target.
@dp.append_flow(target="sales.bronze.orders_us")
def orders_west_flow():
    return spark.readStream.table("sales.bronze.orders_west")
```

The example defines the schema explicitly and passes it to `create_streaming_table`. The flows append data that matches the schema. If a flow produces data that does not match the schema, the pipeline fails. Defining the schema explicitly is a good practice when multiple sources must conform to a common structure.

## How flows differ from UNION

A `UNION` combines multiple sources in a single query. The pipeline reads all sources together and processes them as one flow. If you add a new source, you must modify the query and restart the flow. This can trigger a full refresh of the target table, which is expensive for large datasets. Separate flows avoid this problem. Each flow reads its source independently and appends to the target. Adding a new flow does not affect the existing flows. The existing flows continue from their checkpoints, and the new flow starts from its own checkpoint. The target table accumulates data from all flows.

The following table compares `UNION` with separate flows.

| Aspect | UNION | Separate flows |
|---|---|---|
| Number of flows | One flow for all sources | One flow per source |
| Adding a new source | Modify the query and restart the flow | Add a new flow without modifying existing flows |
| Checkpoint | One checkpoint for all sources | One checkpoint per flow |
| Full refresh risk | High when adding a source | None; existing flows continue |
| Flexibility | Limited | High |
| Typical use | Small, static set of sources | Dynamic, growing set of sources |

The table shows that separate flows are more flexible and avoid the risk of a full refresh. `UNION` is simpler for a small, static set of sources. For ingestion from multiple regional systems that may grow over time, separate flows are the better choice.

## Checkpoints and flow names

Each flow has its own checkpoint. The checkpoint stores the progress of the flow, including the source offsets or file states that have been processed. The pipeline manages the checkpoint automatically. You do not configure the checkpoint location. The checkpoint is keyed by the flow name. If you rename a flow, the checkpoint does not carry over. The renamed flow is treated as a new flow and starts processing from the beginning. This is an important consideration. Flow names should be stable once they are in production. If you need to change the logic of a flow, keep the name the same. If you need to create a new flow with different logic, give it a new name and leave the old flow in place until it is no longer needed.

The following table summarizes checkpoint behavior.

| Action | Effect on checkpoint |
|---|---|
| Create a new flow | New checkpoint created |
| Keep the same flow name | Checkpoint continues from last processed offset |
| Rename a flow | Old checkpoint abandoned; new flow starts from beginning |
| Delete a flow | Checkpoint is no longer used; target table retains appended data |
| Add a new flow | New checkpoint created; existing flows unaffected |

The table shows that renaming a flow is disruptive. It causes the flow to reprocess its source from the beginning. To avoid this, plan flow names carefully and keep them stable.

## Schema enforcement and evolution

Schema enforcement applies to flows. Each flow must produce data that matches the target table schema. The `BY NAME` clause matches columns by name. If a flow produces extra columns that are not in the target, the flow fails unless schema evolution is enabled. If a flow is missing a column that is nullable, the target column is set to null. If a non-nullable column is missing, the flow fails. Schema evolution allows the target table to add new columns when a flow produces them. You enable schema evolution in the pipeline settings. When schema evolution is enabled, new columns are added to the target table, and existing rows get null in the new columns.

The following table summarizes schema behavior with multiple flows.

| Situation | Behavior |
|---|---|
| Flow produces extra column | Fails unless schema evolution is enabled |
| Flow missing nullable column | Target column set to null |
| Flow missing non-nullable column | Flow fails |
| Schema evolution enabled | New columns added to target table |
| Schema evolution disabled | Extra columns cause failure |

The table shows that schema evolution should be used deliberately. If you have multiple flows and one flow adds a new column, the target table schema changes. Other flows that do not produce the new column will write null for that column. Downstream consumers may need to handle the new column. Communicate schema changes to downstream teams.

## Expectations and data quality

Expectations are data quality rules that you define on tables. You can define expectations on the target table. The expectations apply to all flows that write to the table. You can also apply filters or transformations in individual flows to enforce source-specific rules. For example, you might have an expectation that the amount is positive. If a flow produces a row with a negative amount, the expectation drops or fails the row. Expectations are evaluated per row. The pipeline records the results in the event log. You can query the event log to see how many rows passed or failed each expectation.

The following SQL example defines an expectation on the target table.

```sql
-- Create the target streaming table with an expectation.
-- The expectation requires the amount to be positive.
-- Rows that violate the expectation are dropped.
CREATE OR REFRESH STREAMING TABLE sales.bronze.orders_us (
  CONSTRAINT valid_amount EXPECT (amount > 0) ON VIOLATION DROP ROW
);

-- Add a flow from the west region.
CREATE FLOW orders_west_flow
AS INSERT INTO sales.bronze.orders_us BY NAME
SELECT * FROM STREAM(sales.bronze.orders_west);
```

The example defines an expectation on the target table. The expectation applies to all flows. If a flow produces a row with a non-positive amount, the row is dropped. The expectation helps maintain data quality across all sources. In Python, you can use the `@dp.expect_or_drop` decorator on the target table definition.

## Null handling, case sensitivity, and time zones

Null handling in flows follows the same rules as in other Spark operations. Nulls in the source are preserved unless you filter or replace them. If a target column is non-nullable, a null value causes the flow to fail. You can use expectations to drop rows with nulls in required columns. You can use `COALESCE` to replace nulls with defaults. In SQL, you use `COALESCE`. In Python, you use `coalesce`. The rescued data column, if enabled, captures values that do not match the schema.

Case sensitivity affects string comparisons and column names. In Spark SQL, column names are case-insensitive by default. String values are case-sensitive. If the source data has inconsistent casing, normalize it with `upper` or `lower`, or use a case-insensitive collation if the table is configured for one. Unity Catalog supports collations at the column level. The `BY NAME` clause matches column names case-insensitively by default. If the source has a column named `OrderID` and the target has `order_id`, the match may fail. Use consistent column naming across sources.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. When you use `current_timestamp()` or `current_date()` in a flow, the values are computed in the session time zone. To avoid off-by-hours errors, set the session time zone explicitly to UTC at the start of your pipeline with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Store timestamps in UTC and convert to local time only for display.

## Best practices

Use separate flows when you need to combine data from multiple sources into one table. Separate flows are more flexible than `UNION` because you can add new sources without modifying existing flows or triggering a full refresh.

Keep flow names stable. Flow names are used to identify checkpoints. Renaming a flow causes it to start from the beginning. Plan flow names carefully and avoid changing them in production.

Define the target table schema explicitly when multiple sources must conform to a common structure. An explicit schema ensures that all flows produce compatible data and makes the pipeline easier to understand.

Use `BY NAME` to match columns by name. This is safer than matching by position because it is resilient to column order changes in the source.

Define expectations on the target table to enforce data quality across all flows. Monitor the event log to see how many rows pass or fail each expectation.

Set the session time zone explicitly to UTC. This avoids off-by-hours errors when parsing timestamps.

Test flows with small datasets. Verify that each flow appends the expected rows and that the target table contains the combined data.

## Common mistakes and pitfalls

The most common mistake is renaming a flow. Renaming a flow causes the checkpoint to be abandoned, and the flow starts processing from the beginning. This can create duplicate rows in the target table. Keep flow names stable.

A second mistake is using `BY POSITION` instead of `BY NAME`. `BY POSITION` matches columns by their order in the source and target. If the source columns are in a different order, the wrong values are written to the wrong columns. Use `BY NAME` to match by name.

A third mistake is not defining the target table schema explicitly. Without an explicit schema, the schema is inferred from the first flow. If a later flow produces different types, the flow fails or produces incorrect data. Define the schema explicitly when multiple sources are involved.

A fourth mistake is enabling schema evolution without communicating the change. Adding a column to the target table changes the schema and may break downstream consumers. Communicate schema changes to downstream teams.

A fifth mistake is not setting the session time zone. Timestamps are stored in UTC. If you compare them to local time without converting, you may get incorrect results.

A sixth mistake is ignoring the event log. The event log records progress, expectations, and errors. If you do not monitor it, you may miss data quality issues or failures.

## Testing multiple flows

Testing multiple flows involves verifying that each flow appends the expected rows and that the target table contains the combined data. You can test with small datasets that simulate the sources. The following example shows a test for two flows that append to the same table.

```python
from pyspark.sql import Row

# Create test data for the west region.
west_data = [
    Row(order_id="W1", amount=100.0, region="west"),
    Row(order_id="W2", amount=200.0, region="west"),
]
df_west = spark.createDataFrame(west_data)
df_west.write.mode("overwrite").saveAsTable("tmp.orders_west")

# Create test data for the east region.
east_data = [
    Row(order_id="E1", amount=150.0, region="east"),
    Row(order_id="E2", amount=250.0, region="east"),
]
df_east = spark.createDataFrame(east_data)
df_east.write.mode("overwrite").saveAsTable("tmp.orders_east")

# In a real pipeline, you would run the pipeline that defines the flows.
# Here we simulate the append by writing both DataFrames to the target table.
df_west.write.mode("append").saveAsTable("tmp.orders_us")
df_east.write.mode("append").saveAsTable("tmp.orders_us")

# Verify that the target table contains all four rows.
df_target = spark.read.table("tmp.orders_us")
assert df_target.count() == 4, f"Expected 4 rows, got {df_target.count()}"

# Verify that the regions are present.
regions = [row.region for row in df_target.collect()]
assert "west" in regions and "east" in regions
```

The test creates two source tables, appends their data to a target table, and verifies the combined result. Run tests like this in your CI pipeline against a small local Spark session. For pipeline-level testing, use the pipeline testing framework to run the pipeline with test data and validate the output.

## Performance considerations

Multiple flows process independently. The pipeline can run them in parallel if the cluster has enough resources. Each flow has its own checkpoint, so it reads only new data from its source. This is efficient for incremental ingestion. The target table receives appends from all flows. The writes to the target table may contend if many flows write at the same time. The pipeline manages the writes and ensures exactly-once semantics.

The number of flows affects the number of checkpoints and the amount of state the pipeline manages. Each flow has its own checkpoint. If you have many flows, the pipeline has more state to manage. Keep the number of flows reasonable. If you have hundreds of sources, consider whether you can use a single flow with a `UNION` or a different pattern.

Schema evolution can cause the pipeline to restart. When a flow adds a new column, the pipeline may need to update the target schema. This adds latency. Use schema evolution deliberately.

Use the `availableNow` trigger for scheduled pipelines. It processes all available data and stops, which reduces compute cost compared to a continuously running pipeline.

## An end-to-end example

Consider a scenario where you receive order data from three regional systems: west, east, and central. You want to combine them into a single `orders_us` table. You define a target streaming table and three flows. The following SQL example shows the complete pipeline.

```sql
-- Create the target streaming table with an explicit schema.
CREATE OR REFRESH STREAMING TABLE sales.bronze.orders_us (
  order_id STRING,
  customer_id STRING,
  order_date DATE,
  amount DECIMAL(10,2),
  region STRING
);

-- Add a flow from the west region.
CREATE FLOW orders_west_flow
AS INSERT INTO sales.bronze.orders_us BY NAME
SELECT * FROM STREAM(sales.bronze.orders_west);

-- Add a flow from the east region.
CREATE FLOW orders_east_flow
AS INSERT INTO sales.bronze.orders_us BY NAME
SELECT * FROM STREAM(sales.bronze.orders_east);

-- Add a flow from the central region.
CREATE FLOW orders_central_flow
AS INSERT INTO sales.bronze.orders_us BY NAME
SELECT * FROM STREAM(sales.bronze.orders_central);
```

The example creates a target table and three flows. Each flow appends data from its regional source. The `BY NAME` clause matches columns by name. The target table accumulates data from all three regions. If you add a new region later, you create a new flow without modifying the existing ones. The existing flows continue from their checkpoints. This pattern is scalable and flexible.
