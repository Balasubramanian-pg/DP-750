## Create streaming tables for ingestion

A streaming table is a Delta table that is designed to be the target of an incremental ingestion flow. You define what data to read and how to transform it, and the pipeline that owns the streaming table manages the execution, the checkpointing, and the schema. In Lakeflow Spark Declarative Pipelines, you define a streaming table in SQL with `CREATE OR REFRESH STREAMING TABLE` or in Python with the `@dp.table` decorator. The definition describes the source, the transformation, and the resulting schema. It does not describe how to schedule the pipeline, how to retry failures, or where to store checkpoints. The framework handles those concerns. The result is a governed Delta table in Unity Catalog that is continuously or incrementally updated with new data.

Streaming tables matter because ingestion is the first step in almost every data pipeline, and it is the step most prone to subtle bugs. A manually written ingestion job must track which files or offsets have been processed, manage checkpoints, handle schema changes, retry transient failures, and ensure that each record is processed exactly once. Getting all of this right is difficult, and mistakes lead to duplicate rows, missing data, or silent corruption. A streaming table abstracts these concerns. You declare the source and the transformation. The pipeline coordinates checkpointing with Delta Lake commits, so each input record is processed exactly once. The pipeline also handles schema evolution and provides an event log for monitoring. This lets you focus on the logic of the transformation instead of the mechanics of ingestion.

These notes explain how to create streaming tables for ingestion. They describe the SQL and Python syntax, the role of the `STREAM` keyword, the `read_files` function, the `cloudFiles` source, and how the pipeline manages checkpoints automatically. They show how to read from files, Kafka, and other sources, and how to write the result to Unity Catalog. They also cover schema enforcement, schema evolution, expectations, null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand how to create streaming tables that ingest data reliably into Unity Catalog.

## What a streaming table is and when to use it

A streaming table is a Delta table that is registered in Unity Catalog and is updated incrementally by a pipeline. Each time the pipeline runs, the streaming table processes only the data that has arrived since the previous run. The pipeline tracks progress in a checkpoint location that it manages internally. You do not configure the checkpoint. You do not write code to identify new data. You do not write code to deduplicate rows. The streaming table definition describes the source and the transformation, and the pipeline handles the rest.

Streaming tables are the right choice for append-only ingestion workloads. A daily log file, a stream of events from Kafka, a continuous feed of change data capture records, and a set of Parquet files arriving in cloud storage are all candidates. If the source produces new rows over time and each row should appear in the target exactly once, a streaming table is the correct target. If the transformation requires recomputing the full dataset, such as a complex aggregation over all historical data, a materialized view is the better choice. The following table compares streaming tables with materialized views.

| Aspect | Streaming table | Materialized view |
|---|---|---|
| Update mode | Incremental | Full recompute |
| Data scope | New rows only | Entire dataset |
| Exactly-once | Yes | Not applicable |
| Typical use | Ingestion, append-only | Aggregation, denormalization |
| Source read | `STREAM` or `readStream` | Batch read |
| Checkpoint management | Automatic | Not applicable |

The table shows that streaming tables are designed for incremental ingestion. Materialized views are designed for full recomputation. In a medallion architecture, streaming tables are commonly used in the bronze and silver layers, and materialized views are commonly used in the gold layer. For the ingestion step itself, streaming tables are the primary target.

## Creating a streaming table with SQL

The SQL syntax for a streaming table is `CREATE OR REFRESH STREAMING TABLE`. The `CREATE OR REFRESH` part means that the table is created if it does not exist and refreshed if it does. The `STREAMING TABLE` part declares the table as a streaming table. The body of the statement is a `SELECT` query that defines the source and the transformation. The `STREAM` keyword is used in the `FROM` clause to indicate that the source should be read incrementally. The following SQL example creates a streaming table that reads JSON files from cloud storage.

```sql
-- Create a streaming table that reads JSON files from cloud storage.
-- The CREATE OR REFRESH clause creates the table if it does not exist
-- and refreshes it if it does.
-- The STREAMING TABLE keyword declares the table as a streaming table.
-- The table is created in Unity Catalog and is governed by Unity Catalog.
CREATE OR REFRESH STREAMING TABLE sales.bronze.orders_bronze
AS SELECT *
-- The STREAM keyword tells the pipeline to read the source incrementally.
-- The read_files function reads files from the specified path.
-- When used with STREAM, read_files enables Auto Loader capabilities
-- for incremental file detection and schema inference.
FROM STREAM read_files(
  -- The path specifies the directory to monitor for new files.
  -- The path is a Unity Catalog volume or an external location.
  'abfss://container@storage.dfs.core.windows.net/incoming/orders/',
  -- The format option specifies that the files are JSON.
  format => 'json'
);
```

The example creates a streaming table named `sales.bronze.orders_bronze`. The `read_files` function reads JSON files from the specified path. The `STREAM` keyword tells the pipeline to process the files incrementally. The pipeline manages the checkpoint location internally, so you do not configure a checkpoint. Each time the pipeline runs, it detects new files, reads them, and appends the parsed rows to the streaming table. The table is in Unity Catalog and is governed by Unity Catalog.

You can specify the file format explicitly, as shown above, or you can let `read_files` detect the format automatically. You can also provide options for parsing, such as the header row for CSV files or the schema for JSON files. The following SQL example reads CSV files with a header row.

```sql
-- Create a streaming table that reads CSV files with a header row.
-- The format option specifies that the files are CSV.
-- The header option tells read_files that the first row contains column names.
CREATE OR REFRESH STREAMING TABLE sales.bronze.customers_bronze
AS SELECT *
FROM STREAM read_files(
  '/Volumes/sales/bronze/raw/customers/',
  format => 'csv',
  header => 'true'
);
```

The example reads CSV files with a header row. The `header` option tells `read_files` to use the first row as column names. The resulting streaming table has the columns and types inferred by Auto Loader. You can provide schema hints to control the inferred types. The following SQL example provides a schema hint.

```sql
-- Create a streaming table with a schema hint.
-- The schemaHints option provides type hints for specific columns.
-- The hint "order_date DATE, amount DECIMAL(10,2)" tells read_files
-- to treat order_date as a DATE and amount as a DECIMAL(10,2).
CREATE OR REFRESH STREAMING TABLE sales.bronze.orders_bronze
AS SELECT *
FROM STREAM read_files(
  '/Volumes/sales/bronze/raw/orders/',
  format => 'csv',
  header => 'true',
  schemaHints => 'order_date DATE, amount DECIMAL(10,2)'
);
```

The example provides a schema hint for `order_date` and `amount`. Schema hints guide the inference and avoid type mismatches. They are especially useful for CSV and JSON files, where the default inference treats all columns as strings. If the source contains values that cannot be cast to the hinted types, the values are rescued if rescue mode is enabled, or the pipeline fails if rescue mode is not enabled.

## Creating a streaming table with Python

In Python, you define a streaming table using the `@dp.table` decorator. The `dp` module is the pipelines module in the Python API. The decorated function returns a streaming DataFrame. The function name becomes the table name by default, or you can specify the name explicitly with the `name` argument. The following Python example creates a streaming table that reads JSON files with Auto Loader.

```python
# Import the pipelines module.
# The dp module provides the table decorator and other pipeline APIs.
from pyspark import pipelines as dp

# Define a streaming table using the @dp.table decorator.
# The decorator registers the function as a streaming table in the pipeline.
# The function returns a streaming DataFrame that the pipeline writes to the table.
@dp.table
def orders_bronze():
    # Read from cloud storage using Auto Loader.
    # The cloudFiles format is the Auto Loader source.
    # The cloudFiles.format option specifies the file format (json).
    # The load method specifies the input directory to monitor.
    return (
        spark.readStream.format("cloudFiles")
            .option("cloudFiles.format", "json")
            .load("abfss://container@storage.dfs.core.windows.net/incoming/orders/")
    )
```

The example defines a streaming table named `orders_bronze`. The function returns a streaming DataFrame that reads JSON files with Auto Loader. The pipeline manages the checkpoint location and the schema location internally. You do not configure them. Each time the pipeline runs, it detects new files, reads them, and appends the parsed rows to the streaming table. The table is in Unity Catalog and is governed by Unity Catalog.

You can specify the table name, the comment, and other properties with arguments to the decorator. The following Python example specifies the table name and a comment.

```python
# Import the pipelines module.
from pyspark import pipelines as dp

# Define a streaming table with an explicit name and comment.
# The name argument specifies the fully qualified table name.
# The comment argument adds a description to the table.
@dp.table(
    name="sales.bronze.customers_bronze",
    comment="Raw customers ingested from cloud storage"
)
def customers_bronze():
    # Read from cloud storage using Auto Loader.
    # The cloudFiles.format option specifies that the files are CSV.
    # The header option tells Auto Loader that the first row contains column names.
    return (
        spark.readStream.format("cloudFiles")
            .option("cloudFiles.format", "csv")
            .option("header", "true")
            .load("/Volumes/sales/bronze/raw/customers/")
    )
```

The example defines a streaming table named `sales.bronze.customers_bronze` with a comment. The function reads CSV files with a header row. The pipeline manages checkpointing and schema evolution. The table is in Unity Catalog. This is the recommended way to define streaming tables in Python because it is concise and declarative.

## Reading from different sources

Streaming tables can read from many sources. The source is defined in the `SELECT` query or in the DataFrame returned by the Python function. The `STREAM` keyword in SQL and `readStream` in Python indicate that the source should be read incrementally. The following table summarizes common sources.

| Source | SQL | Python |
|---|---|---|
| Files in cloud storage | `STREAM read_files(...)` | `spark.readStream.format("cloudFiles")` |
| Kafka | `STREAM read_kafka(...)` | `spark.readStream.format("kafka")` |
| Delta table | `STREAM table_name` | `spark.readStream.table("table_name")` |
| Another streaming table | `STREAM table_name` | `dlt.read_stream("table_name")` |

The table shows that the source is specified with the `STREAM` keyword in SQL and with `readStream` or `read_stream` in Python. The following SQL example reads from Kafka.

```sql
-- Create a streaming table that reads from Kafka.
-- The read_kafka function reads from a Kafka topic.
-- The bootstrapServers option specifies the Kafka cluster.
-- The subscribe option names the topic to read from.
CREATE OR REFRESH STREAMING TABLE sales.bronze.orders_kafka
AS SELECT *
FROM STREAM read_kafka(
  bootstrapServers => 'broker:9092',
  subscribe => 'orders'
);
```

The example reads from a Kafka topic named `orders`. The `read_kafka` function returns a streaming DataFrame with the Kafka schema, including the `key`, `value`, `topic`, `partition`, `offset`, and `timestamp` columns. You typically cast the `value` column to string and parse it with `from_json`. The following SQL example parses the JSON payload.

```sql
-- Create a streaming table that parses JSON from Kafka.
-- The from_json function parses the JSON payload from the value column.
-- The schema describes the structure of the JSON.
CREATE OR REFRESH STREAMING TABLE sales.bronze.orders_kafka
AS SELECT
  from_json(
    CAST(value AS STRING),
    'order_id STRING, customer_id STRING, amount DOUBLE'
  ).order_id AS order_id,
  from_json(
    CAST(value AS STRING),
    'order_id STRING, customer_id STRING, amount DOUBLE'
  ).customer_id AS customer_id,
  from_json(
    CAST(value AS STRING),
    'order_id STRING, customer_id STRING, amount DOUBLE'
  ).amount AS amount
FROM STREAM read_kafka(
  bootstrapServers => 'broker:9092',
  subscribe => 'orders'
);
```

The example parses the JSON payload and extracts the `order_id`, `customer_id`, and `amount` fields. The `from_json` function parses the JSON string using the provided schema. The result is a streaming table with the parsed columns. You can add a watermark and window for event-time processing if needed.

## Reading from another streaming table

You can create a streaming table that reads from another streaming table. This is how you build a pipeline of transformations. In SQL, you use the `STREAM` keyword with the table name. In Python, you use `dlt.read_stream` or `dp.read_stream`. The following SQL example creates a silver streaming table that reads from a bronze streaming table and applies a filter.

```sql
-- Create a silver streaming table that reads from a bronze streaming table.
-- The STREAM keyword reads the bronze table incrementally.
-- The WHERE clause filters out invalid rows.
CREATE OR REFRESH STREAMING TABLE sales.silver.orders_clean
AS SELECT *
FROM STREAM sales.bronze.orders_bronze
WHERE amount > 0;
```

The example reads from the bronze table incrementally and filters out rows where the amount is not positive. The silver table is updated incrementally as new rows arrive in the bronze table. The pipeline determines the execution order: the bronze table runs first, then the silver table. The following Python example does the same.

```python
# Import the pipelines module.
from pyspark import pipelines as dp

# Define a silver streaming table that reads from a bronze streaming table.
# The dp.read_stream function reads the bronze table incrementally.
@dp.table
def orders_clean():
    return (
        dp.read_stream("sales.bronze.orders_bronze")
            .filter("amount > 0")
    )
```

The Python example reads from the bronze streaming table incrementally and filters out invalid rows. The `dp.read_stream` function reads the table as a stream. The pipeline determines the execution order and manages checkpointing. This is how you build a chain of streaming tables from bronze to silver to gold.

## Schema enforcement and evolution

Streaming tables inherit the schema behavior of the pipeline. When you define a streaming table with `SELECT *` from a source, the schema is derived from the source. For file sources, Auto Loader infers the schema and stores it in a schema location that the pipeline manages. For Kafka sources, the schema is the Kafka schema unless you parse the payload. When the source schema changes, the pipeline can evolve the streaming table schema if schema evolution is enabled. The following table summarizes the schema behavior.

| Aspect | Behavior |
|---|---|
| Schema inference | Auto Loader infers the schema for file sources |
| Schema location | Managed by the pipeline |
| Schema evolution | Controlled by the pipeline settings |
| Rescued data column | Available if enabled |
| Schema hints | Supported in `read_files` |

The table shows that the pipeline manages schema inference and evolution. You do not configure the schema location. You can provide schema hints to guide inference. You can enable the rescued data column to capture nonconforming data. The pipeline updates the streaming table schema when the source schema changes and schema evolution is enabled.

## Expectations and data quality

Expectations are data quality rules that you define on streaming tables. You attach an expectation to a table, and the pipeline evaluates the rule on each row. If a row violates the rule, the pipeline can drop the row, fail the pipeline, or warn. Expectations help you maintain data quality at the point of ingestion. The following SQL example defines an expectation on a streaming table.

```sql
-- Create a streaming table with expectations.
-- The CONSTRAINT clause defines a data quality rule.
-- The EXPECT clause specifies the rule and the action.
-- The ON VIOLATION DROP ROW clause drops rows that violate the rule.
CREATE OR REFRESH STREAMING TABLE sales.silver.orders_clean (
  CONSTRAINT valid_amount EXPECT (amount > 0) ON VIOLATION DROP ROW,
  CONSTRAINT valid_order_id EXPECT (order_id IS NOT NULL) ON VIOLATION DROP ROW
)
AS SELECT * FROM STREAM sales.bronze.orders_bronze;
```

The example defines two expectations. The first requires the amount to be positive. The second requires the order ID to be not null. Rows that violate either expectation are dropped. The pipeline records the results in the event log, which you can query to monitor data quality. The following Python example defines the same expectations.

```python
# Import the pipelines module.
from pyspark import pipelines as dp

# Define a streaming table with expectations.
# The @dp.expect_or_drop decorator drops rows that violate the rule.
@dp.table
@dp.expect_or_drop("valid_amount", "amount > 0")
@dp.expect_or_drop("valid_order_id", "order_id IS NOT NULL")
def orders_clean():
    return dp.read_stream("sales.bronze.orders_bronze")
```

The Python example uses the `@dp.expect_or_drop` decorator to define expectations that drop rows on violation. The expectations are evaluated as part of the pipeline update. You can query the event log to see how many rows passed or failed each expectation.

## Null handling, case sensitivity, and time zones

Null handling in streaming tables follows the same rules as in other Spark operations. Nulls in the source are preserved unless you filter or replace them. If a target column is non-nullable, a null value causes the write to fail. You can use expectations to drop rows with nulls in required columns. You can use `coalesce` to replace nulls with defaults. In SQL, you use `COALESCE`. In Python, you use `coalesce`. The rescued data column captures values that do not match the schema, which can include nulls or type mismatches.

Case sensitivity affects string comparisons and column names. In Spark SQL, column names are case-insensitive by default. String values are case-sensitive. If the source data has inconsistent casing, normalize it with `upper` or `lower`, or use a case-insensitive collation if the table is configured for one. Unity Catalog supports collations at the column level.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. When you use `current_timestamp()` or `current_date()` in a streaming table definition, the values are computed in the session time zone. To avoid off-by-hours errors, set the session time zone explicitly to UTC at the start of your pipeline with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Store timestamps in UTC and convert to local time only for display.

## Best practices

Use streaming tables for ingestion. They process data incrementally and provide exactly-once semantics. Use materialized views for aggregations and transformations that require the full dataset.

Store your pipeline source code in a Git folder for version control. The Lakeflow Pipelines Editor supports a default folder structure with `transformations` for source code and `explorations` for ad hoc analysis. Version control makes it easier to review changes and roll back mistakes.

Define expectations for data quality. Use `expect_or_drop` to filter invalid rows, `expect_or_fail` for strict validation, and `expect` for monitoring. Monitor the event log to see how many rows pass or fail each expectation.

Use schema hints to control inferred types. Schema hints are especially useful for CSV and JSON files, where the default inference treats all columns as strings. They guide the inference and avoid type mismatches.

Set the session time zone explicitly to UTC. This avoids off-by-hours errors when parsing timestamps.

Use the `STREAM` keyword for incremental sources. Use `read_stream` in Python for streaming tables. Use `read` for materialized views.

Monitor the pipeline. Use the event log to track progress, expectations, and errors. Set up alerts for failures and for data quality violations.

## Common mistakes and pitfalls

The most common mistake is omitting the `STREAM` keyword. Without `STREAM`, the source is read as a batch, and the streaming table processes the entire dataset on each run. This is inefficient and defeats the purpose of a streaming table.

A second mistake is using a materialized view for an incremental workload. Materialized views recompute the full dataset. If the dataset is large, this is expensive and slow. Use a streaming table for incremental workloads.

A third mistake is not defining expectations. Expectations catch data quality issues early. Without them, invalid rows may reach downstream tables and cause incorrect results.

A fourth mistake is using `expect_or_fail` for every expectation. Failing the pipeline on every violation can cause unnecessary downtime. Use `expect_or_drop` or `expect` for non-critical rules.

A fifth mistake is not setting the session time zone. Timestamps are stored in UTC. If you compare them to local time without converting, you may get incorrect results.

A sixth mistake is not monitoring the event log. The event log records progress, expectations, and errors. If you do not monitor it, you may miss data quality issues or failures.

A seventh mistake is using `SELECT *` without considering the schema. `SELECT *` is convenient but it can include columns that are not needed and can break when the source schema changes. For production pipelines, select the columns you need explicitly.

## Testing streaming tables

Testing streaming tables involves verifying that the transformations produce the expected results and that the expectations behave as intended. You can test the transformation logic with batch DataFrames that simulate the streaming schema. The following example shows a test for a filter used in a silver streaming table.

```python
from pyspark.sql import Row
from pyspark.sql.functions import col

# Create a small DataFrame with test data.
# The data includes a row with a negative amount to test the filter.
test_data = [
    Row(order_id=1, amount=100.0),
    Row(order_id=2, amount=-50.0),
    Row(order_id=3, amount=200.0),
]
df_test = spark.createDataFrame(test_data)

# Apply the same filter used in the silver streaming table.
df_filtered = df_test.filter(col("amount") > 0)

# Verify that the negative amount row is dropped.
assert df_filtered.count() == 2, f"Expected 2 rows, got {df_filtered.count()}"

# Verify that the remaining rows have positive amounts.
rows = df_filtered.collect()
assert rows[0].amount == 100.0
assert rows[1].amount == 200.0
```

The test verifies that the filter drops the negative amount row. Run tests like this in your CI pipeline against a small local Spark session. For pipeline-level testing, use the pipeline testing framework to run the pipeline with test data and validate the output. Clean up temporary tables after the test.

## Performance considerations

Streaming table performance depends on the source, the transformation, and the cluster resources. File sources with Auto Loader are efficient when using file notification mode with file events. Kafka sources are efficient when the topic has enough partitions to support the desired throughput.

The pipeline maximizes parallelism by running independent tables in parallel. This improves performance but also increases resource usage. Size the cluster to match the workload. Use autoscaling to adjust the cluster size dynamically.

Schema inference adds a small overhead at the start of the pipeline. Once the schema is inferred and stored, subsequent runs use the stored schema. Schema evolution can cause the pipeline to restart, which adds latency.

The event log records progress and expectations. Query the event log with filters to limit the amount of data scanned. Partition the event log by date if possible.

Use the `availableNow` trigger for scheduled pipelines. It processes all available data and stops, which reduces compute cost compared to a continuously running pipeline.

## An end-to-end example

Consider a scenario where you ingest JSON order files from cloud storage into a bronze streaming table, clean them into a silver streaming table with expectations, and aggregate them into a gold materialized view. The following SQL example shows the complete pipeline.

```sql
-- Create a bronze streaming table that reads JSON files with Auto Loader.
-- The STREAM keyword tells the pipeline to read the files incrementally.
CREATE OR REFRESH STREAMING TABLE sales.bronze.orders_bronze
AS SELECT *
FROM STREAM read_files(
  '/Volumes/sales/bronze/raw/orders/',
  format => 'json'
);

-- Create a silver streaming table that reads from the bronze table.
-- The STREAM keyword reads the bronze table incrementally.
-- The WHERE clause filters out invalid rows.
-- The constraints drop rows that violate the rules.
CREATE OR REFRESH STREAMING TABLE sales.silver.orders_clean (
  CONSTRAINT valid_amount EXPECT (amount > 0) ON VIOLATION DROP ROW,
  CONSTRAINT valid_order_id EXPECT (order_id IS NOT NULL) ON VIOLATION DROP ROW
)
AS SELECT *
FROM STREAM sales.bronze.orders_bronze
WHERE amount IS NOT NULL;

-- Create a gold materialized view that aggregates the silver table.
-- The materialized view is recomputed when the pipeline runs.
CREATE OR REFRESH MATERIALIZED VIEW sales.gold.daily_sales
AS SELECT
  order_date,
  SUM(amount) AS total_sales,
  COUNT(*) AS order_count
FROM sales.silver.orders_clean
GROUP BY order_date;
```

The SQL example defines three objects: a bronze streaming table, a silver streaming table, and a gold materialized view. The bronze table reads JSON files with Auto Loader. The silver table reads from the bronze table incrementally, filters out null amounts, and applies two expectations. The gold materialized view aggregates the silver table by date. The pipeline determines the execution order, manages checkpoints, and validates data quality. All tables are in Unity Catalog and are governed.
