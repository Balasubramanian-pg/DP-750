## Ingest from message buses

A message bus is a system that receives streams of events from producers and delivers them to consumers. Producers publish messages to named channels called topics, and consumers subscribe to those topics to read the messages. Apache Kafka is a widely used distributed message bus. Azure Event Hubs is a managed message bus on Azure that provides a Kafka-compatible endpoint. Amazon Kinesis and Google Pub/Sub are similar services on other clouds. In Azure Databricks, Lakeflow Spark Declarative Pipelines supports ingestion from these message buses, with Event Hubs being the most common choice for Azure environments. You can read from a message bus as a streaming source and write the data to a Delta table in Unity Catalog, where it is governed and available for downstream transformation.

Message buses matter because they decouple data producers from data consumers. A sensor can publish readings to a topic without knowing which applications will consume them. Multiple consumers can read the same topic independently, each at its own pace. This decoupling enables scalable, fault-tolerant architectures. In a lakehouse, the message bus is often the entry point for real-time data. You read from the bus, parse the payloads, and land the raw events in a bronze table. The medallion architecture then takes over: silver tables clean and conform the data, and gold tables aggregate it for analytics. Ingesting from message buses is therefore a foundational skill for building real-time data pipelines.

These notes cover how to ingest data from message buses in Lakeflow Spark Declarative Pipelines. They explain how to read from Kafka in SQL and Python, how to connect to Azure Event Hubs through its Kafka-compatible interface, and how to manage authentication with secrets and pipeline parameters. They show how to parse the payload, handle schema, and enforce data quality with expectations. They also cover null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand how to build reliable message bus ingestion pipelines that land data in Unity Catalog.

## Understanding message buses and their role in ingestion

A message bus stores events in topics. A topic is a named, partitioned log. Partitions allow the bus to scale horizontally: messages within a partition are ordered, but messages across partitions are not. Producers write messages to topics, and consumers read them by subscribing to the topic and tracking their position, called an offset, within each partition. The bus retains messages for a configured period, so consumers can replay them if needed. This model provides durability, scalability, and replayability.

In a medallion architecture, message bus ingestion typically lands data in the bronze layer. The bronze table holds the raw events exactly as they arrived, often with minimal transformation. This preserves the original data for auditing and reprocessing. The silver layer then parses and cleans the data, and the gold layer aggregates it. Unity Catalog governs all layers. When you ingest from a message bus, you write to a streaming table in Unity Catalog. The pipeline manages checkpointing and schema evolution automatically.

The following table compares common message bus services and their ingestion options in Azure Databricks.

| Service | Protocol | Databricks ingestion | Typical use |
|---|---|---|---|
| Apache Kafka | Kafka protocol | `read_kafka` or `spark.readStream.format("kafka")` | Self-managed or cloud Kafka |
| Azure Event Hubs | Kafka-compatible endpoint | Kafka connector with SASL | Azure-native event streaming |
| Azure Event Hubs | Native Event Hubs | `eventhubs` format | Event Hubs-specific features |
| Amazon Kinesis | Kinesis API | Kinesis connector | AWS event streaming |
| Google Pub/Sub | Pub/Sub API | Pub/Sub connector | GCP event streaming |

The table shows that Kafka and Event Hubs can be read with the Kafka connector. Event Hubs also has a native connector. For Azure environments, Event Hubs with the Kafka-compatible interface is a common choice because it reuses the Kafka connector and code. The rest of these notes focuses on Kafka and Event Hubs.

## Reading from Kafka in SQL

Lakeflow Spark Declarative Pipelines provides a SQL function called `read_kafka` for reading from Kafka topics. The function returns a streaming DataFrame with the standard Kafka schema: `key`, `value`, `topic`, `partition`, `offset`, `timestamp`, and `timestampType`. The `key` and `value` columns are binary. You typically cast the `value` column to string and parse it with `from_json`. The following SQL example creates a streaming table that reads raw events from a Kafka topic.

```sql
-- Create a streaming table that reads from a Kafka topic.
-- The read_kafka function reads from Kafka.
-- The bootstrapServers option specifies the Kafka cluster.
-- The subscribe option names the topic to read from.
-- The table is created in Unity Catalog and is governed by Unity Catalog.
CREATE OR REFRESH STREAMING TABLE sales.bronze.events_raw
AS SELECT *
FROM STREAM read_kafka(
  bootstrapServers => 'kafka_server:9092',
  subscribe => 'events_topic'
);
```

The example creates a streaming table named `sales.bronze.events_raw`. The `read_kafka` function reads from the topic `events_topic` on the Kafka cluster at `kafka_server:9092`. The `STREAM` keyword tells the pipeline to process the topic incrementally. The pipeline manages the checkpoint location. The table contains the raw Kafka columns. To use the payload, you parse the `value` column. The following SQL example parses a JSON payload.

```sql
-- Create a streaming table that parses JSON from Kafka.
-- The from_json function parses the JSON string using the provided schema.
-- The schema describes the structure of the JSON payload.
-- The result is a struct column. The select statement expands the struct.
CREATE OR REFRESH STREAMING TABLE sales.bronze.orders_parsed
AS SELECT
  from_json(
    CAST(value AS STRING),
    'order_id STRING, customer_id STRING, amount DOUBLE, order_time TIMESTAMP'
  ).order_id AS order_id,
  from_json(
    CAST(value AS STRING),
    'order_id STRING, customer_id STRING, amount DOUBLE, order_time TIMESTAMP'
  ).customer_id AS customer_id,
  from_json(
    CAST(value AS STRING),
    'order_id STRING, customer_id STRING, amount DOUBLE, order_time TIMESTAMP'
  ).amount AS amount,
  from_json(
    CAST(value AS STRING),
    'order_id STRING, customer_id STRING, amount DOUBLE, order_time TIMESTAMP'
  ).order_time AS order_time
FROM STREAM read_kafka(
  bootstrapServers => 'kafka_server:9092',
  subscribe => 'orders_topic'
);
```

The example parses the JSON payload from the `value` column. The `from_json` function takes the JSON string and a schema definition. The schema is written as a string in DDL format. The result is a struct. The `SELECT` statement extracts the fields and names them. The streaming table `sales.bronze.orders_parsed` contains the parsed columns. The pipeline processes new messages incrementally.

You can also specify additional options for `read_kafka`, such as `startingOffsets`, `endingOffsets`, and consumer group settings. The `startingOffsets` option determines where to begin when starting a new query. Once the pipeline has a checkpoint, subsequent runs resume from the checkpoint and ignore `startingOffsets`. The following table summarizes common `read_kafka` options.

| Option | Meaning | Default |
|---|---|---|
| `bootstrapServers` | Kafka cluster address | Required |
| `subscribe` | Topic to subscribe to | Required |
| `startingOffsets` | Where to start on a new query | `latest` |
| `endingOffsets` | Where to stop in batch mode | `latest` |
| `kafka.security.protocol` | Security protocol | `PLAINTEXT` |
| `kafka.sasl.mechanism` | SASL mechanism | None |

The table shows the options you can pass to `read_kafka`. For secured Kafka clusters, you set the security protocol and SASL mechanism. For Event Hubs, you use SASL_SSL and PLAIN, as described later.

## Reading from Kafka in Python

In Python, you use the standard Spark Kafka connector with `spark.readStream.format("kafka")`. You define a streaming table with the `@dp.table` decorator. The function returns a streaming DataFrame. The following Python example creates a streaming table that reads from Kafka.

```python
# Import the pipelines module.
# The dp module provides the table decorator and other pipeline APIs.
from pyspark import pipelines as dp

# Define a streaming table using the @dp.table decorator.
# The decorator registers the function as a streaming table in the pipeline.
# The function returns a streaming DataFrame that the pipeline writes to the table.
@dp.table
def events_raw():
    # Read from Kafka as a stream.
    # The format is "kafka".
    # The kafka.bootstrap.servers option specifies the Kafka cluster.
    # The subscribe option names the topic to read from.
    # The load method starts the stream.
    return (
        spark.readStream
            .format("kafka")
            .option("kafka.bootstrap.servers", "kafka_server:9092")
            .option("subscribe", "events_topic")
            .load()
    )
```

The example defines a streaming table named `events_raw`. The function reads from the Kafka topic `events_topic`. The pipeline manages checkpointing and schema evolution. To parse the payload, you add a `select` with `from_json`. The following Python example parses JSON.

```python
# Import the pipelines module and the from_json function.
from pyspark import pipelines as dp
from pyspark.sql.functions import from_json, col
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, TimestampType

# Define the schema of the JSON payload.
schema = StructType([
    StructField("order_id", StringType(), nullable=False),
    StructField("customer_id", StringType(), nullable=True),
    StructField("amount", DoubleType(), nullable=True),
    StructField("order_time", TimestampType(), nullable=True),
])

# Define a streaming table that parses JSON from Kafka.
@dp.table
def orders_parsed():
    # Read from Kafka as a stream.
    df_raw = (spark.readStream
        .format("kafka")
        .option("kafka.bootstrap.servers", "kafka_server:9092")
        .option("subscribe", "orders_topic")
        .load())
    # Parse the JSON payload from the value column.
    # The value column is binary, so cast it to string first.
    # from_json parses the JSON string using the defined schema.
    return (df_raw
        .select(from_json(col("value").cast("string"), schema).alias("data"))
        .select("data.*"))
```

The example reads from Kafka, parses the JSON payload using an explicit schema, and produces a streaming DataFrame with the parsed columns. The pipeline writes the result to the streaming table `orders_parsed`. The schema is defined in Python using `StructType` and `StructField`. This is the recommended approach for Python pipelines because it is explicit and type-safe.

## Connecting to Azure Event Hubs via the Kafka-compatible interface

Azure Event Hubs provides a Kafka-compatible endpoint. You can use the Kafka connector to read from Event Hubs by pointing to the Event Hubs namespace and configuring SASL authentication. The bootstrap servers use the Event Hubs namespace followed by `.servicebus.windows.net:9093`. The security protocol is `SASL_SSL`, and the SASL mechanism is `PLAIN`. The username is the literal string `$ConnectionString`, and the password is the Event Hubs connection string. The following Python example shows how to configure the connection.

```python
# Import the pipelines module.
from pyspark import pipelines as dp

# Retrieve the Event Hubs namespace and name from pipeline parameters.
# Pipeline parameters are configured in the pipeline settings.
# They allow you to pass non-sensitive configuration values without hardcoding.
EH_NAMESPACE = spark.conf.get("eh.namespace")
EH_NAME = spark.conf.get("eh.name")

# Retrieve the Event Hubs connection string from a secret scope.
# The connection string contains the shared access key.
# Never hardcode the connection string in the pipeline code.
EH_CONN_STR = dbutils.secrets.get(scope="eh-secrets", key="connection-string")

# Define the Kafka options for Event Hubs.
# The bootstrap servers use the Event Hubs namespace and port 9093.
# The subscribe option names the Event Hub (which is a topic in Kafka terms).
# The SASL mechanism is PLAIN, and the security protocol is SASL_SSL.
# The JAAS config provides the username and password for authentication.
# The username is the literal string "$ConnectionString".
# The password is the connection string retrieved from the secret scope.
KAFKA_OPTIONS = {
    "kafka.bootstrap.servers": f"{EH_NAMESPACE}.servicebus.windows.net:9093",
    "subscribe": EH_NAME,
    "kafka.sasl.mechanism": "PLAIN",
    "kafka.security.protocol": "SASL_SSL",
    "kafka.sasl.jaas.config": f'kafkashaded.org.apache.kafka.common.security.plain.PlainLoginModule required username="$ConnectionString" password="{EH_CONN_STR}";'
}

# Define a streaming table that reads from Event Hubs.
# The @dp.table decorator registers the function as a streaming table.
# The function returns a streaming DataFrame.
@dp.table
def events_bronze():
    return (
        spark.readStream
            .format("kafka")
            .options(**KAFKA_OPTIONS)
            .load()
    )
```

The example reads from Event Hubs using the Kafka connector. The connection string is retrieved from a secret scope. The namespace and Event Hub name are retrieved from pipeline parameters. The `options(**KAFKA_OPTIONS)` unpacks the dictionary into individual options. The resulting streaming table `events_bronze` contains the raw Event Hubs messages in the standard Kafka schema. You can parse the `value` column as shown earlier.

The equivalent SQL example uses `read_kafka` with the same options. The following SQL example shows how.

```sql
-- Create a streaming table that reads from Event Hubs via the Kafka interface.
-- The read_kafka function reads from Kafka.
-- The bootstrapServers option uses the Event Hubs namespace and port 9093.
-- The subscribe option names the Event Hub.
-- The kafka.sasl.mechanism and kafka.security.protocol options enable SASL_SSL.
-- The kafka.sasl.jaas.config option provides the connection string.
-- The connection string is retrieved from a secret scope using the secret function.
CREATE OR REFRESH STREAMING TABLE sales.bronze.events_bronze
AS SELECT *
FROM STREAM read_kafka(
  bootstrapServers => '${eh.namespace}.servicebus.windows.net:9093',
  subscribe => '${eh.name}',
  `kafka.sasl.mechanism` => 'PLAIN',
  `kafka.security.protocol` => 'SASL_SSL',
  `kafka.sasl.jaas.config` => 'kafkashaded.org.apache.kafka.common.security.plain.PlainLoginModule required username="$ConnectionString" password="' || secret('eh-secrets', 'connection-string') || '";'
);
```

The SQL example uses the `secret` function to retrieve the connection string from a secret scope. The `${eh.namespace}` and `${eh.name}` are pipeline parameters. The options are passed as named arguments to `read_kafka`. The backticks around the option names that contain dots are required in SQL. The resulting streaming table contains the raw Event Hubs messages.

## Authentication and secrets management

Authentication is a critical part of message bus ingestion. You must provide credentials to connect to the bus. For Kafka, you might use SASL/PLAIN, SASL/SCRAM, or SSL with client certificates. For Event Hubs, you use a connection string that contains a shared access key. You should never hardcode credentials in your pipeline code. Instead, store them in Azure Databricks secrets. A secret scope is a collection of secrets that are stored securely and can be referenced in notebooks and pipelines. You retrieve a secret with `dbutils.secrets.get` in Python or `secret` in SQL. The following table summarizes the secret management approach for message buses.

| Credential | Storage | Retrieval in Python | Retrieval in SQL |
|---|---|---|---|
| Kafka SASL username | Secret scope | `dbutils.secrets.get("scope", "key")` | `secret("scope", "key")` |
| Kafka SASL password | Secret scope | `dbutils.secrets.get("scope", "key")` | `secret("scope", "key")` |
| Event Hubs connection string | Secret scope | `dbutils.secrets.get("scope", "key")` | `secret("scope", "key")` |
| SSL certificate | Secret scope or volume | `dbutils.secrets.get` or file read | Not directly supported |

The table shows that secrets are stored in secret scopes and retrieved with the appropriate function. For SSL certificates, you may need to store the certificate in a Unity Catalog volume and read it in the pipeline. The key point is to avoid hardcoding credentials. Use secret scopes for all sensitive values.

By using parameters, you can deploy the same pipeline code to development, staging, and production with different settings. The table shows examples of parameters. You configure them in the pipeline settings. In the pipeline code, you retrieve them with `spark.conf.get("eh.namespace")` in Python or `${eh.namespace}` in SQL. The following Python example shows how to use parameters for the Event Hubs namespace and name.

## Schema handling and evolution

Schema handling for message bus ingestion involves two schemas: the schema of the message bus source and the schema of the target table. The message bus source, such as Kafka or Event Hubs, has a fixed schema with binary `key` and `value` columns. You parse the `value` column using `from_json` and an explicit schema that describes your payload. The target table schema is derived from the `SELECT` statement. The pipeline manages schema evolution for the target table. If the payload schema changes, you update the `from_json` schema in the pipeline code. The pipeline then processes new data with the updated schema. The following table summarizes schema controls.

| Control | Mechanism | Effect |
|---|---|---|
| Payload schema | `from_json` with explicit schema | Parses the binary value into typed columns |
| Target schema | Derived from `SELECT` | Defines the columns of the streaming table |
| Schema evolution | Pipeline settings | Adds new columns to the target table |
| Expectations | Pipeline constraints | Drops, fails, or warns on invalid rows |

The table shows that you control the payload schema explicitly in the pipeline code. The target schema is derived from the query. Schema evolution is controlled by the pipeline settings. Expectations validate data quality. For example, you can define an expectation that `order_id` is not null. If a row violates the expectation, the pipeline can drop it.

## Null handling, case sensitivity, and time zones

Null handling in message bus ingestion follows the same rules as other Spark operations. Nulls in the payload are preserved unless you filter or replace them. If a target column is non-nullable, a null value causes the write to fail. You should handle nulls in the transformation step. For example, you can filter out rows with null keys or replace null values with a default using `coalesce`. The `from_json` function returns null for fields that are missing or cannot be parsed. You can use `when` and `otherwise` to handle these cases.

Case sensitivity affects string comparisons and column names. In Spark SQL, column names are case-insensitive by default. String values are case-sensitive. If the payload contains inconsistent casing, normalize it with `upper` or `lower`, or use a case-insensitive collation if the table is configured for one. The JSON field names are case-sensitive when using `from_json`. If the JSON has a field named `OrderID` and your schema has `order_id`, the field will be null. Ensure that the schema matches the JSON field names exactly.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. When you parse a timestamp from the payload, it is interpreted in the session time zone unless it includes an explicit offset. To avoid off-by-hours errors, set the session time zone explicitly to UTC at the start of your pipeline with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Store timestamps in UTC and convert to local time only for display.

## Best practices

Use secret scopes for credentials. Never hardcode connection strings or passwords in pipeline code. Retrieve them with `dbutils.secrets.get` in Python or `secret` in SQL.

Use pipeline parameters for non-sensitive configuration. Parameters allow you to deploy the same pipeline code to different environments without changes.

Define the payload schema explicitly. Use `from_json` with a `StructType` in Python or a DDL string in SQL. Do not rely on inference for the payload.

Use expectations to validate data quality. Define expectations that check for null keys, invalid values, or missing fields. Monitor the event log to see how many rows pass or fail each expectation.

Set the session time zone explicitly to UTC. This avoids off-by-hours errors when parsing timestamps.

Monitor the pipeline. Use the event log to track progress, expectations, and errors. Set up alerts for failures and for latency spikes.

## Common mistakes and pitfalls

The most common mistake is hardcoding credentials. Always use secret scopes. Hardcoded credentials are a security risk and are difficult to rotate.

A second mistake is not defining the payload schema explicitly. Without an explicit schema, `from_json` may infer incorrect types or fail. Define the schema with `StructType` in Python or a DDL string in SQL.

A third mistake is mismatching JSON field names and the schema. JSON field names are case-sensitive. If the field names do not match, the values are null. Ensure that the schema matches the JSON exactly.

A fourth mistake is not setting the session time zone. Timestamps are stored in UTC. If you compare them to local time without converting, you may get incorrect results.

A fifth mistake is ignoring the event log. The event log records progress, expectations, and errors. If you do not monitor it, you may miss data quality issues or failures.

A sixth mistake is using the wrong trigger. For scheduled ingestion, use the `availableNow` trigger. For continuous ingestion, use the default trigger or a `processingTime` trigger.

## Testing message bus ingestion

Testing message bus ingestion involves verifying that the pipeline reads messages, parses the payload, and writes the expected rows to the target table. You can test the parsing logic with batch DataFrames that simulate the message bus schema. The following Python example shows a test for parsing JSON from a Kafka-like DataFrame.

```python
from pyspark.sql import Row
from pyspark.sql.functions import from_json, col
from pyspark.sql.types import StructType, StructField, StringType, DoubleType

# Define the schema of the JSON payload.
schema = StructType([
    StructField("order_id", StringType(), nullable=False),
    StructField("amount", DoubleType(), nullable=True),
])

# Create a batch DataFrame that simulates the Kafka source.
# The value column contains JSON strings as binary.
test_data = [
    Row(value=b'{"order_id": "O1", "amount": 100.0}'),
    Row(value=b'{"order_id": "O2", "amount": 200.0}'),
]
df_test = spark.createDataFrame(test_data)

# Apply the same parsing logic used in the pipeline.
df_parsed = (df_test
    .select(from_json(col("value").cast("string"), schema).alias("data"))
    .select("data.*"))

# Verify the result.
rows = df_parsed.collect()
assert rows[0].order_id == "O1" and rows[0].amount == 100.0
assert rows[1].order_id == "O2" and rows[1].amount == 200.0
```

The test creates a small DataFrame with JSON strings, applies the parsing logic, and verifies the result. Run tests like this in your CI pipeline against a small local Spark session. For end-to-end testing, use a test Kafka topic or Event Hub, produce test messages, run the pipeline with the `availableNow` trigger, and verify the output in the target table.

## Performance considerations

Performance of message bus ingestion depends on the number of partitions in the topic, the size of the messages, and the cluster resources. The number of partitions determines the maximum parallelism. Spark reads from each partition in parallel. Ensure that the topic has enough partitions to support the desired throughput. If the topic has few partitions, the ingestion is limited by the number of partitions.

Micro-batch size affects latency and throughput. Smaller micro-batches reduce latency but increase overhead. Larger micro-batches increase throughput but increase latency. The trigger controls the cadence. Use the `availableNow` trigger for scheduled jobs to process all available data and stop. Use the default trigger for continuous low-latency ingestion.

State management is important for aggregations. If you perform stateful operations such as windowed aggregations, use watermarks to bound the state. Without a watermark, the state grows indefinitely and can cause memory issues.

Checkpointing adds overhead. The pipeline manages the checkpoint location automatically. Ensure that the checkpoint location is in durable storage. Do not apply aggressive lifecycle policies that delete checkpoint files.

## An end-to-end example

Consider a scenario where you ingest order events from Azure Event Hubs into a bronze table, parse the JSON payload, and write the parsed data to a silver table with an expectation. The following Python example shows the complete pipeline.

```python
from pyspark import pipelines as dp
from pyspark.sql.functions import from_json, col, when
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, TimestampType

# Retrieve Event Hubs configuration from pipeline parameters and secrets.
EH_NAMESPACE = spark.conf.get("eh.namespace")
EH_NAME = spark.conf.get("eh.name")
EH_CONN_STR = dbutils.secrets.get(scope="eh-secrets", key="connection-string")

# Define the Kafka options for Event Hubs.
KAFKA_OPTIONS = {
    "kafka.bootstrap.servers": f"{EH_NAMESPACE}.servicebus.windows.net:9093",
    "subscribe": EH_NAME,
    "kafka.sasl.mechanism": "PLAIN",
    "kafka.security.protocol": "SASL_SSL",
    "kafka.sasl.jaas.config": f'kafkashaded.org.apache.kafka.common.security.plain.PlainLoginModule required username="$ConnectionString" password="{EH_CONN_STR}";'
}

# Define the schema of the JSON payload.
schema = StructType([
    StructField("order_id", StringType(), nullable=False),
    StructField("customer_id", StringType(), nullable=True),
    StructField("amount", DoubleType(), nullable=True),
    StructField("order_time", TimestampType(), nullable=True),
])

# Define the bronze streaming table that reads raw events from Event Hubs.
@dp.table
def events_bronze():
    return (
        spark.readStream
            .format("kafka")
            .options(**KAFKA_OPTIONS)
            .load()
    )

# Define the silver streaming table that parses the JSON and applies an expectation.
@dp.table
@dp.expect_or_drop("valid_amount", "amount > 0")
def orders_silver():
    return (
        dp.read_stream("events_bronze")
            .select(from_json(col("value").cast("string"), schema).alias("data"))
            .select("data.*")
            .filter(col("amount").isNotNull())
    )
```

The example reads from Event Hubs into the `events_bronze` streaming table. It then reads from `events_bronze`, parses the JSON payload, and writes to `orders_silver`. The `orders_silver` table has an expectation that drops rows where the amount is not positive. The pipeline manages checkpointing, schema evolution, and data quality. All tables are in Unity Catalog and are governed.
