## Create tables from queries with CTAS

`CREATE TABLE AS SELECT`, usually called CTAS, is a SQL statement that creates a new table and populates it with the result of a query in a single operation. You write a `SELECT` statement that reads from one or more sources, applies transformations, and produces a result set. The CTAS statement takes that result set and writes it to a new table. The table schema is derived from the query result, so you do not need to define columns or data types separately. In Azure Databricks, the table is created as a Delta table by default, which provides ACID transactions, time travel, schema enforcement, and efficient query performance. The table is registered in Unity Catalog, so it is governed by the same access controls, lineage tracking, and auditing that apply to all other tables in the lakehouse.

CTAS matters because it combines two steps that are often performed separately. Without CTAS, you would create an empty table with explicit column definitions, then insert data into it with an `INSERT INTO` or `INSERT OVERWRITE` statement. CTAS does both in one atomic operation. The table does not exist until the query completes successfully. If the query fails, no table is created. This atomicity makes CTAS reliable for initial data loads, one-time migrations, and full refreshes of derived tables. It is also a natural fit for the medallion architecture. You can use CTAS to read raw files into a bronze table, clean and conform data into a silver table, or aggregate data into a gold table. Each layer is a CTAS query that reads from the previous layer and writes a new table.

These notes cover CTAS from first principles. They explain the syntax, how the schema is derived, how CTAS interacts with Delta Lake and Unity Catalog, and how to use CTAS with the `read_files` table-valued function. They explain the difference between `CREATE TABLE AS SELECT`, `CREATE OR REPLACE TABLE AS SELECT`, and `CREATE TABLE IF NOT EXISTS AS SELECT`. They show the PySpark equivalents using `spark.sql` and the DataFrame write API. They cover transformations during ingestion, schema enforcement and evolution, null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand how to use CTAS to create tables from queries reliably and efficiently.

## What CTAS does and when to use it

CTAS is a data definition statement and a data manipulation statement combined. The `CREATE TABLE` part defines the table. The `AS SELECT` part provides the data and the schema. The table is created with the columns and types produced by the query. Column names come from the query's select list. If a column is an expression, you should give it an alias so that the resulting column has a meaningful name. Without an alias, Spark generates a name based on the expression, such as `upper(customer_name)`, which is awkward to reference later.

CTAS is the right choice when you need to create a new table from a query and you do not need to update it incrementally. It is ideal for initial data loads, one-time migrations, and full refreshes of derived tables. It is not the right choice when you need to append new rows to an existing table, update existing rows, or merge changes. For those operations, use `INSERT INTO`, `INSERT OVERWRITE`, or `MERGE`. CTAS creates a new table each time it runs. If the table already exists, the statement fails unless you use `CREATE OR REPLACE TABLE AS SELECT` or `CREATE TABLE IF NOT EXISTS AS SELECT`. The `IF NOT EXISTS` clause skips execution entirely if the table exists, so it does not update the table. The `OR REPLACE` clause replaces the existing table.

The following table compares CTAS with other common loading statements.

| Statement | Creates table | Replaces existing table | Updates existing table | Typical use |
|---|---|---|---|---|
| `CREATE TABLE AS SELECT` | Yes | No, fails if table exists | No | Initial load, one-time migration |
| `CREATE OR REPLACE TABLE AS SELECT` | Yes | Yes | No | Repeatable full refresh |
| `CREATE TABLE IF NOT EXISTS AS SELECT` | Yes | No, skips if table exists | No | Idempotent creation without update |
| `INSERT INTO` | No | No | Appends rows | Incremental load |
| `INSERT OVERWRITE` | No | Yes, for full table or partition | No | Full refresh of existing table |
| `MERGE` | No | No | Updates, inserts, deletes | Upsert, CDC |

The table shows that CTAS is a creation statement, not an update statement. It is designed for the first load or a full rebuild, not for incremental changes.

## CTAS syntax and schema derivation

The basic syntax of CTAS is `CREATE TABLE table_name AS SELECT ...`. The table name uses the three-level namespace of Unity Catalog: catalog, schema, and table. For example, `sales.bronze.customers` refers to the `customers` table in the `bronze` schema of the `sales` catalog. The `SELECT` statement can read from any queryable source, including files, external databases, and other tables. The schema of the new table is derived from the query result.

The following SQL example creates a table from a query that reads an external staging table, applies a transformation, and filters rows.

```sql
-- Create a new table in Unity Catalog from a query.
-- The table is created in the sales.bronze schema.
-- The schema of the table is derived from the SELECT list.
-- The table is a Delta table by default.
CREATE TABLE sales.bronze.customers AS
SELECT
    -- Select the customer identifier.
    customer_id,
    -- Convert the customer name to uppercase.
    -- The alias customer_name gives the column a clear name.
    -- Without the alias, the column would be named upper(customer_name).
    UPPER(customer_name) AS customer_name,
    -- Select the email address.
    email,
    -- Select the created date.
    created_date
FROM external_staging.raw_customers
-- Filter to only active customers.
-- Rows where customer_status is not 'active' are excluded.
WHERE customer_status = 'active';
```

The example creates a new table named `sales.bronze.customers`. The schema is derived from the four columns in the select list. The `customer_name` column is the result of the `UPPER` function, and the alias gives it a readable name. The `WHERE` clause filters the rows. The table is created as a Delta table in Unity Catalog. If the table already exists, the statement fails. If the query fails, no table is created.

CTAS can also specify table properties, partitioning, and comments. The following SQL example creates a partitioned table with a comment.

```sql
-- Create a partitioned table from a query.
-- The table is partitioned by the order_date column.
-- Partitioning organizes data into separate directories by date,
-- which can improve query performance for date-filtered queries.
-- The COMMENT clause adds a description to the table.
CREATE TABLE sales.bronze.orders
COMMENT 'Raw orders ingested from cloud storage'
PARTITIONED BY (order_date)
AS
SELECT
    order_id,
    customer_id,
    order_date,
    order_amount,
    order_status
FROM read_files(
    '/Volumes/sales/bronze/raw/orders/',
    format => 'parquet'
);
```

The example creates a table partitioned by `order_date`. The data is read from Parquet files in a Unity Catalog volume using the `read_files` function. The `COMMENT` clause adds a description. The `PARTITIONED BY` clause specifies the partition column. Partitioning is a design choice that should be based on the query patterns. Choose partition columns that are commonly used in filters and that have a reasonable number of distinct values.

## Using CTAS with read_files

The `read_files` table-valued function reads files directly in SQL. It supports CSV, JSON, Parquet, and other formats. It is useful when you want to ingest files into a table without leaving the SQL environment. You use `read_files` inside the `SELECT` statement of a CTAS. The function takes the file path and options that specify the format and parsing behavior.

The following SQL example creates a table from CSV files using `read_files`.

```sql
-- Create a table from CSV files using read_files.
-- The read_files function reads the files and returns a table.
-- The format option specifies that the files are CSV.
-- The header option tells read_files that the first row contains column names.
-- The inferSchema option tells read_files to infer column types.
CREATE TABLE sales.bronze.transactions AS
SELECT *
FROM read_files(
    '/Volumes/sales/bronze/raw/transactions/*.csv',
    format => 'csv',
    header => 'true',
    inferSchema => 'true'
);
```

The example reads all CSV files in the specified directory and creates a table. The `inferSchema` option tells Spark to infer the column types. Inference is convenient for exploration, but for production it is better to define the schema explicitly. You can define the schema in the `read_files` call by providing a `schema` option, or you can use CTAS with a query that casts columns to the desired types.

The following SQL example reads Parquet files with an explicit schema.

```sql
-- Create a table from Parquet files with an explicit schema.
-- Parquet files carry their own schema, so no schema option is needed.
-- The read_files function reads the schema from the file metadata.
CREATE TABLE sales.bronze.events AS
SELECT *
FROM read_files(
    '/Volumes/sales/bronze/raw/events/*.parquet',
    format => 'parquet'
);
```

Parquet files are self-describing, so the schema is read from the file metadata. This makes Parquet a good choice for ingestion because the schema is explicit and does not require inference. CSV and JSON files do not carry type information, so you must either infer the schema or define it explicitly.

## Creating or replacing tables with CTAS

`CREATE TABLE AS SELECT` fails if the table already exists. This is a safety feature. It prevents accidental overwrites. If you want to create the table only if it does not exist, use `CREATE TABLE IF NOT EXISTS AS SELECT`. If the table exists, the statement does nothing. It does not update the table. This is useful for idempotent creation, but it is not useful for refreshing the table.

If you want to replace the table each time the statement runs, use `CREATE OR REPLACE TABLE AS SELECT`. This statement replaces the existing table with a new one. The schema of the new table is derived from the query, so the replacement can change the schema. The data is replaced entirely. The operation is atomic in Delta Lake, so readers see either the old table or the new table, never a partial state.

The following SQL example creates or replaces a table.

```sql
-- Create or replace a table from a query.
-- If the table exists, it is replaced with the new data and schema.
-- If the table does not exist, it is created.
-- The operation is atomic: readers see either the old table or the new table.
CREATE OR REPLACE TABLE sales.gold.daily_sales AS
SELECT
    order_date,
    region,
    -- Sum the order amounts for each date and region.
    SUM(order_amount) AS total_sales,
    -- Count the orders for each date and region.
    COUNT(*) AS order_count
FROM sales.silver.orders
-- Group by date and region.
GROUP BY order_date, region;
```

The example creates or replaces the `sales.gold.daily_sales` table. If the table exists, it is replaced with the new aggregation. If it does not exist, it is created. This is a common pattern for gold tables that are rebuilt on a schedule. The operation replaces the entire table, so it is a full refresh. It does not perform incremental updates.

The following table compares the three creation statements.

| Statement | If table does not exist | If table exists |
|---|---|---|
| `CREATE TABLE AS SELECT` | Creates table | Fails |
| `CREATE TABLE IF NOT EXISTS AS SELECT` | Creates table | Skips, does nothing |
| `CREATE OR REPLACE TABLE AS SELECT` | Creates table | Replaces table |

The table shows that `CREATE TABLE AS SELECT` is the strictest. It creates the table only if it does not exist. `IF NOT EXISTS` is idempotent but does not update. `OR REPLACE` replaces the table and is suitable for repeatable full refreshes.

## PySpark equivalents of CTAS

PySpark does not have a `CREATE TABLE AS SELECT` statement in the DataFrame API, but you can achieve the same result in two ways. First, you can run the SQL statement with `spark.sql()`. Second, you can build a DataFrame and write it with `saveAsTable`. Both approaches create a Delta table in Unity Catalog.

The following PySpark example runs a CTAS statement with `spark.sql()`.

```python
# Run a CTAS statement using spark.sql.
# The SQL statement creates a table from a query.
# The table is created in the sales.bronze schema.
# The schema is derived from the query result.
spark.sql("""
    CREATE TABLE sales.bronze.customers AS
    SELECT
        customer_id,
        UPPER(customer_name) AS customer_name,
        email,
        created_date
    FROM external_staging.raw_customers
    WHERE customer_status = 'active'
""")
```

The example runs the same CTAS statement shown earlier. The `spark.sql()` method executes the SQL and returns an empty DataFrame. The table is created as a side effect. This approach is useful when you prefer SQL for the transformation logic but want to run it from a Python notebook.

The second approach builds a DataFrame and writes it with `saveAsTable`. The following PySpark example reads a source, applies transformations, and writes the result to a new table.

```python
# Import the functions needed for the transformations.
from pyspark.sql.functions import col, upper

# Read the external staging table.
df_raw = spark.read.table("external_staging.raw_customers")

# Apply the transformations.
df_transformed = (df_raw
    # Filter to active customers.
    .filter(col("customer_status") == "active")
    # Select and transform the columns.
    .select(
        col("customer_id"),
        # Convert the customer name to uppercase.
        upper(col("customer_name")).alias("customer_name"),
        col("email"),
        col("created_date")
    ))

# Write the result to a new table.
# mode("overwrite") creates the table if it does not exist
# and replaces it if it does.
# saveAsTable uses the three-level namespace.
df_transformed.write.mode("overwrite").saveAsTable("sales.bronze.customers")
```

The PySpark example produces the same result as the CTAS statement. The `mode("overwrite")` creates the table if it does not exist and replaces it if it does. This is similar to `CREATE OR REPLACE TABLE AS SELECT`. If you want the behavior of `CREATE TABLE AS SELECT`, which fails if the table exists, use `mode("error")`, which is the default. If you want the behavior of `CREATE TABLE IF NOT EXISTS`, you can check for the table's existence before writing, or use `mode("ignore")`, which does nothing if the table exists.

The following table compares the SQL and PySpark approaches.

| Aspect | SQL CTAS | PySpark saveAsTable |
|---|---|---|
| Create only if not exists | `CREATE TABLE AS SELECT` | `mode("error")` |
| Create or skip | `CREATE TABLE IF NOT EXISTS AS SELECT` | `mode("ignore")` |
| Create or replace | `CREATE OR REPLACE TABLE AS SELECT` | `mode("overwrite")` |
| Schema derivation | From query | From DataFrame |
| Partitioning | `PARTITIONED BY` | `partitionBy` |
| Table properties | `TBLPROPERTIES` | `option` methods |

The table shows that the two approaches are equivalent in capability. The SQL form is more concise for pure SQL transformations. The PySpark form is useful when the transformation logic depends on Python control flow or when the DataFrame is built from multiple sources.

## Schema enforcement, evolution, and expectations

CTAS creates a table with the schema derived from the query. Delta Lake enforces that schema on subsequent writes. If you later append data with a different schema, the write fails unless schema evolution is enabled. If you use `CREATE OR REPLACE TABLE AS SELECT`, the schema is replaced along with the data. This means that a schema change in the query is reflected in the new table. You should be deliberate about schema changes because they can break downstream consumers that expect a fixed set of columns.

Schema evolution is not used during CTAS because the table is created from the query. It applies to subsequent writes. If you need to add a column to an existing table, you can use `ALTER TABLE ADD COLUMN`, or you can use a write with `mergeSchema` enabled. If you need to replace the schema entirely, use `CREATE OR REPLACE TABLE AS SELECT`.

Expectations are data quality rules that you define in Lakeflow Spark Declarative Pipelines. CTAS itself does not have expectations, but you can apply data quality rules in the query that populates the table. For example, you can filter out rows where a key is null, or you can use `CASE` expressions to validate values. If you use Lakeflow Spark Declarative Pipelines, you can define expectations on the tables that the pipeline creates.

The following table summarizes the schema controls.

| Control | Mechanism | Effect |
|---|---|---|
| Schema enforcement | Delta Lake write | Rejects writes that do not match the table schema |
| Schema evolution | `mergeSchema` option or `ALTER TABLE` | Adds new columns to the table |
| Schema replacement | `CREATE OR REPLACE TABLE AS SELECT` | Replaces the table schema and data |
| Expectations | Lakeflow Spark Declarative Pipelines | Drops, fails, or warns on rows that violate a rule |

The table shows that CTAS creates the schema, Delta Lake enforces it, and schema evolution or replacement changes it. Use these controls deliberately.

## Handling nulls, case sensitivity, and time zones

Null handling in CTAS follows the same rules as in any SQL query. The `SELECT` statement produces values, and those values are written to the table. If a column is nullable and the query produces a null, the table contains a null. If the query produces a non-null value, the table contains the value. CTAS does not automatically convert nulls. You should handle nulls in the query using `COALESCE`, `CASE`, or `WHERE` clauses. For example, `COALESCE(order_amount, 0)` replaces null amounts with zero. `WHERE customer_id IS NOT NULL` filters out rows with null keys.

Case sensitivity affects string comparisons and column names. In Spark SQL, column names are case-insensitive by default. `Customer_ID` and `customer_id` refer to the same column. String values are case-sensitive. `'Active'` and `'active'` are different values. If your source data has inconsistent casing, you should normalize it in the query using `UPPER` or `LOWER`. For example, `WHERE UPPER(customer_status) = 'ACTIVE'` matches both `'Active'` and `'active'`. Be aware that applying a function to a column can prevent predicate pushdown and may force a full scan.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. The session time zone is set by `spark.sql.session.timeZone`. When you use `current_timestamp()` or `current_date()` in a CTAS query, the values are computed in the session time zone. If the session time zone differs from the time zone in which the data was written, the results may be off by hours. To avoid this, set the session time zone explicitly at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Use timestamp literals with explicit offsets when comparing to timestamps. Store timestamps in UTC and convert to local time only for display.

## Best practices

Use explicit column aliases for expressions. A column named `upper(customer_name)` is hard to reference and unclear. An alias such as `customer_name` makes the table easier to use.

Define the schema explicitly when reading files. Schema inference is convenient for exploration, but it requires an extra pass over the data and can produce unexpected types. For production CTAS statements that read CSV or JSON, provide an explicit schema or cast the columns in the query.

Use `CREATE OR REPLACE TABLE AS SELECT` for repeatable full refreshes. It replaces the table atomically and handles the case where the table already exists. Use `CREATE TABLE AS SELECT` for initial loads where you want to fail if the table already exists.

Partition or cluster tables based on query patterns. If you frequently filter by date, partition by date. If you frequently filter by a high-cardinality column, consider liquid clustering. Partitioning and clustering improve query performance by allowing the optimizer to skip files.

Set the session time zone explicitly to UTC. This avoids off-by-hours errors when using `current_timestamp()` and `current_date()`.

Handle nulls deliberately. Decide whether nulls should be preserved, replaced with a default, or filtered out. Use `COALESCE`, `CASE`, or `WHERE` clauses in the query.

Test the query before running CTAS. Run the `SELECT` part with a `LIMIT` clause to verify the columns, types, and rows. Check the schema with `DESCRIBE` or by inspecting the DataFrame.

## Common mistakes and pitfalls

The most common mistake is expecting CTAS to update an existing table. CTAS fails if the table exists. It does not update or append. Use `CREATE OR REPLACE TABLE AS SELECT` if you want to replace the table, or `INSERT INTO` or `MERGE` if you want to update it.

A second mistake is using `CREATE TABLE IF NOT EXISTS AS SELECT` and expecting it to refresh the table. If the table exists, the statement does nothing. It does not update the table. This is useful for idempotent creation but not for refresh.

A third mistake is using schema inference for CSV or JSON files in a production pipeline. Inference requires an extra pass over the data and can produce unexpected types, such as inferring numeric IDs as integers and losing leading zeros. Define the schema explicitly or cast the columns.

A fourth mistake is forgetting to alias expressions. Without an alias, the column name is derived from the expression, which is hard to reference. Always alias expressions in the select list.

A fifth mistake is not setting the session time zone. `current_timestamp()` and `current_date()` use the session time zone. If the session time zone differs from the data time zone, the results may be inconsistent.

A sixth mistake is creating a table without considering partitioning or clustering. A table that is not partitioned or clustered may be slow to query if it is large. Choose partitioning or clustering based on the query patterns.

A seventh mistake is using `CREATE OR REPLACE TABLE AS SELECT` without communicating schema changes. Replacing the table replaces the schema. Downstream consumers that expect a fixed set of columns may break.

## Testing CTAS logic

Test CTAS logic by running the query as a `SELECT` before creating the table. This lets you verify the columns, types, and rows without creating a table. The following SQL example runs the query with a limit.

```sql
-- Test the query before creating the table.
-- The LIMIT clause returns a small sample of rows.
-- Verify that the columns, types, and values are as expected.
SELECT
    customer_id,
    UPPER(customer_name) AS customer_name,
    email,
    created_date
FROM external_staging.raw_customers
WHERE customer_status = 'active'
LIMIT 10;
```

The example returns ten rows. You can inspect the result and verify that the transformation is correct. Once you are satisfied, you can run the CTAS statement.

You can also test CTAS logic with PySpark by building the DataFrame and inspecting it before writing. The following PySpark example builds the transformed DataFrame and displays it.

```python
# Import the functions needed for the transformations.
from pyspark.sql.functions import col, upper

# Read the external staging table.
df_raw = spark.read.table("external_staging.raw_customers")

# Apply the transformations.
df_transformed = (df_raw
    .filter(col("customer_status") == "active")
    .select(
        col("customer_id"),
        upper(col("customer_name")).alias("customer_name"),
        col("email"),
        col("created_date")
    ))

# Display the transformed DataFrame.
# This does not create a table. It only shows the result.

display(df_transformed)
```

The example displays the transformed DataFrame. You can verify the columns and values before writing the table. Once you are satisfied, you can write the DataFrame with `saveAsTable`.

## Performance considerations

CTAS reads from the source and writes to the destination in a single job. The performance depends on the size of the source, the complexity of the query, and the write pattern. If the query includes joins, aggregations, or sorts, Spark performs a shuffle, which is the most expensive operation. Reduce the size of the input by filtering and selecting only the needed columns before the join or aggregation.

The number of output files affects query performance. If the query produces too many small files, queries against the table are slow because each file has metadata overhead. Use `coalesce` or `repartition` to control the number of partitions before the write, or run `OPTIMIZE` after the CTAS to compact small files. Aim for files of 100 MB to 1 GB.

Partitioning and clustering improve query performance. If you frequently filter by a column, partition by that column or use liquid clustering. Choose partition columns that have a reasonable number of distinct values. Avoid high-cardinality partition columns, which create many small directories.

Delta Lake stores per-file statistics that the optimizer uses to skip files. When you create a table with CTAS, the new files have statistics for the columns. Filters on raw columns can use these statistics. Filters on expressions cannot. If you filter on a transformed value frequently, materialize the transformed value in a column at CTAS time so that statistics are collected for it.

Use `CREATE OR REPLACE TABLE AS SELECT` for full refreshes instead of `INSERT OVERWRITE` when the table schema may change. `CREATE OR REPLACE` replaces the schema along with the data, which is useful when the query changes. `INSERT OVERWRITE` requires the existing table schema to match the query result.

## An end-to-end example

Consider a scenario where you need to ingest raw orders from Parquet files, clean and conform them into a silver table, and aggregate them into a gold table. The pipeline uses CTAS for each layer. The bronze table is created from the raw files with minimal transformation. The silver table is created from the bronze table with cleaning and filtering. The gold table is created from the silver table with aggregation.

The following SQL example creates the bronze, silver, and gold tables.

```sql
-- Create the bronze table from raw Parquet files.
-- The read_files function reads the files.
-- The schema is read from the Parquet metadata.
CREATE TABLE sales.bronze.orders AS
SELECT *
FROM read_files(
    '/Volumes/sales/bronze/raw/orders/',
    format => 'parquet'
);

-- Create the silver table from the bronze table.
-- The query filters out invalid rows and casts columns to the correct types.
CREATE TABLE sales.silver.orders AS
SELECT
    order_id,
    customer_id,
    -- Cast the order date to a date type.
    CAST(order_date AS DATE) AS order_date,
    -- Cast the order amount to a decimal type.
    CAST(order_amount AS DECIMAL(10, 2)) AS order_amount,
    order_status
FROM sales.bronze.orders
-- Filter out rows with a null order ID or amount.
WHERE order_id IS NOT NULL
  AND order_amount IS NOT NULL
  -- Filter out rows with a negative or zero amount.
  AND order_amount > 0;

-- Create the gold table from the silver table.
-- The query aggregates the orders by date and status.
CREATE TABLE sales.gold.daily_order_summary AS
SELECT
    order_date,
    order_status,
    -- Sum the order amounts.
    SUM(order_amount) AS total_amount,
    -- Count the orders.
    COUNT(*) AS order_count
FROM sales.silver.orders
-- Group by date and status.
GROUP BY order_date, order_status;
```

The example creates three tables. The bronze table stores the raw data. The silver table cleans and filters the data. The gold table aggregates the data. Each table is created with CTAS. The schema of each table is derived from its query. The tables are Delta tables in Unity Catalog, so they are governed and support time travel and schema enforcement.

CTAS supports table properties, partitioning, comments, and the `read_files` table-valued function for reading files. `CREATE TABLE AS SELECT` fails if the table exists. `CREATE TABLE IF NOT EXISTS AS SELECT` creates the table only if it does not exist and does nothing if it does. `CREATE OR REPLACE TABLE AS SELECT` replaces the existing table with the new data and schema. The PySpark equivalents use `spark.sql()` to run the SQL statement or `DataFrame.write.saveAsTable()` with the appropriate mode.

Schema enforcement, schema evolution, and expectations apply to CTAS and subsequent writes. Delta Lake enforces the table schema.
