## Choose the right method

Choosing the right ingestion method is a design decision that affects correctness, cost, and maintainability. In Azure Databricks, SQL provides three primary methods for loading data into Unity Catalog tables: `CREATE TABLE AS SELECT` (CTAS), `CREATE OR REPLACE TABLE`, and `COPY INTO`. Each method addresses a different pattern of data flow. CTAS creates a new table from a query and fails if the table already exists. `CREATE OR REPLACE TABLE` replaces an existing table entirely while preserving permissions, history, and governance policies. `COPY INTO` appends new files to an existing table and skips files that have already been loaded. Auto Loader is a complementary approach for file-based ingestion that requires automatic schema inference, file notifications, or exactly-once guarantees at high scale.

The choice matters because using the wrong method can create duplicate rows, lose table permissions, break downstream consumers, or waste compute. A pipeline that appends the same batch twice creates duplicates. A pipeline that drops and recreates a table loses grants and row filters. A pipeline that runs CTAS on a schedule fails after the first run because the table already exists. A pipeline that uses `COPY INTO` for millions of files becomes slow because directory listing does not scale. Understanding the behavior of each method lets you match the method to the scenario. The method should be determined by whether the source is a query or files, whether the target table already exists, whether the load is a one-time event or a recurring pattern, and whether the data is incremental or a full replacement.

These notes explain how to choose among CTAS, `CREATE OR REPLACE TABLE`, and `COPY INTO`, and when to use Auto Loader instead. They describe each method, show SQL and PySpark examples with full comments, and provide a decision framework. They cover schema enforcement, schema evolution, expectations, null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example. The goal is that you can read these notes alone and confidently select the right ingestion method for any pipeline that loads data into Unity Catalog.

## Understanding the three SQL ingestion methods

The three SQL methods differ in whether they create, replace, or append to a table. CTAS creates a new table from a query. It is a creation statement. If the table already exists, the statement fails. `CREATE OR REPLACE TABLE` creates a table if it does not exist and replaces it if it does. It is a full refresh statement. `COPY INTO` appends rows from files to an existing table. It does not create the table and does not replace existing rows. It is an incremental ingestion statement.

The following table summarizes the three methods.

| Method | Best for | Behavior |
|---|---|---|
| CTAS | Initial data loads, one-time migrations, creating tables from queries | Creates a new table; fails if table exists |
| CREATE OR REPLACE | Periodic full refreshes, replacing staging tables | Replaces entire table; preserves permissions |
| COPY INTO | Ongoing file ingestion, incremental loads | Appends to existing table; skips loaded files |

The table shows that the methods are complementary rather than competing. CTAS is for the first load. `CREATE OR REPLACE` is for rebuilding a table. `COPY INTO` is for adding new files to an existing table. A single pipeline can use all three at different stages. For example, a bronze table might be created with CTAS from an initial extract, refreshed with `CREATE OR REPLACE` when the source is corrected, and then loaded incrementally with `COPY INTO` as new files arrive.

## CTAS: Creating tables from queries

CTAS, or `CREATE TABLE AS SELECT`, creates a new table and populates it with the result of a query. The schema of the table is derived from the query result. The table is created as a Delta table by default and registered in Unity Catalog. CTAS is the right choice for initial data loads, one-time migrations, and creating derived tables from existing data. It is not the right choice for recurring loads because it fails if the table already exists. If you need a recurring full refresh, use `CREATE OR REPLACE TABLE`. If you need to append new rows, use `COPY INTO` or `INSERT INTO`.

The following SQL example creates a table from a query that reads a staging table, applies a transformation, and filters rows.

```sql
-- Create a new table in Unity Catalog from a query.
-- The table is created in the sales.bronze schema.
-- The schema of the table is derived from the SELECT list.
-- The table is a Delta table by default.
CREATE TABLE sales.bronze.customers AS
SELECT
    -- Select the customer identifier.
    customer_id,
    -- Convert the customer name to uppercase.
    -- The alias customer_name gives the column a clear name.
    UPPER(customer_name) AS customer_name,
    -- Select the email address.
    email,
    -- Select the created date.
    created_date
FROM external_staging.raw_customers
-- Filter to only active customers.
WHERE customer_status = 'active';
```

The example creates a new table named `sales.bronze.customers`. The schema is derived from the four columns in the select list. The `customer_name` column is the result of the `UPPER` function. The `WHERE` clause filters the rows. If the table already exists, the statement fails. If the query fails, no table is created. This atomic behavior makes CTAS reliable for initial loads.

The equivalent PySpark operation builds a DataFrame and writes it with `saveAsTable` using the default error mode, which fails if the table exists.

```python
# Import the functions needed for the transformations.
from pyspark.sql.functions import col, upper

# Read the external staging table.
df_raw = spark.read.table("external_staging.raw_customers")

# Apply the transformations.
df_transformed = (df_raw
    # Filter to active customers.
    .filter(col("customer_status") == "active")
    # Select and transform the columns.
    .select(
        col("customer_id"),
        # Convert the customer name to uppercase.
        upper(col("customer_name")).alias("customer_name"),
        col("email"),
        col("created_date")
    ))

# Write the result to a new table.
# The default mode is "error", which fails if the table already exists.
# This matches the behavior of CREATE TABLE AS SELECT.
df_transformed.write.saveAsTable("sales.bronze.customers")
```

The PySpark example produces the same result as the CTAS statement. The default write mode is `error`, which fails if the table exists. If you want to create the table only if it does not exist, you can use `mode("ignore")`. If you want to replace the table, use `mode("overwrite")`, which is equivalent to `CREATE OR REPLACE TABLE`.

## CREATE OR REPLACE TABLE: Periodic full refreshes

`CREATE OR REPLACE TABLE` creates a new table or replaces an existing table with the result of a query. It is the recommended way to perform full refreshes in Delta Lake and Unity Catalog. Unlike dropping and recreating a table, it preserves the table's identity, privileges, history, row filters, and column masks. The replacement is atomic, so readers see either the old table or the new table, never a partial state. Use it for periodic full refreshes, replacing staging tables, and rebuilding derived tables when the entire contents should be replaced.

The following SQL example creates or replaces a daily metrics table.

```sql
-- Create or replace the daily metrics table.
-- If the table does not exist, it is created.
-- If the table exists, it is replaced with the new data and schema.
-- Privileges, history, row filters, and column masks are preserved.
CREATE OR REPLACE TABLE sales.gold.daily_metrics AS
SELECT
    -- The report date is the grouping column.
    report_date,
    -- Sum the revenue for each date.
    SUM(revenue) AS total_revenue,
    -- Count the distinct customers for each date.
    COUNT(DISTINCT customer_id) AS unique_customers
FROM sales.silver.transactions
-- Filter to the last 30 days.
-- CURRENT_DATE returns the current date in the session time zone.
WHERE report_date >= CURRENT_DATE - INTERVAL 30 DAYS
-- Group by the report date.
GROUP BY report_date;
```

The example creates or replaces `sales.gold.daily_metrics`. The schema is derived from the query. The table is a Delta table in Unity Catalog. If the table already exists, its governance metadata is preserved. The data and schema are replaced.

The PySpark equivalent runs the SQL statement with `spark.sql()`.

```python
# Run a CREATE OR REPLACE TABLE statement using spark.sql.
# The SQL statement creates or replaces the daily metrics table.
spark.sql("""
    CREATE OR REPLACE TABLE sales.gold.daily_metrics AS
    SELECT
        report_date,
        SUM(revenue) AS total_revenue,
        COUNT(DISTINCT customer_id) AS unique_customers
    FROM sales.silver.transactions
    WHERE report_date >= CURRENT_DATE - INTERVAL 30 DAYS
    GROUP BY report_date
""")
```

The example runs the same SQL statement from a Python notebook. The table is created or replaced. The operation is atomic. Downstream consumers continue to access the table without reconfiguration. If you use `DataFrame.write.mode("overwrite").saveAsTable()`, the table is replaced, but the SQL command is preferred for preserving governance metadata.

## COPY INTO: Ongoing incremental file ingestion

`COPY INTO` loads files from cloud storage into an existing Delta table. It is designed for incremental ingestion. It tracks which files have already been loaded and skips them on subsequent runs. This idempotency makes it safe to retry and suitable for scheduled pipelines. The target table must already exist. `COPY INTO` appends rows to the table. It does not replace or update existing rows. Use it when new files arrive regularly and you want to add their contents to a growing table.

The following SQL example loads JSON files into a bronze table.

```sql
-- Load JSON files from a Unity Catalog volume into the target table.
-- The COPY INTO command appends rows to the existing table.
-- Files that have already been loaded are skipped automatically.
COPY INTO sales.bronze.events
-- The FROM clause specifies the source directory.
FROM '/Volumes/sales/bronze/raw/events/'
-- The FILEFORMAT clause specifies that the files are JSON.
FILEFORMAT = JSON
-- The FORMAT_OPTIONS clause configures how the JSON is parsed.
-- The multiline option tells Spark that each file contains a single
-- JSON object or array that spans multiple lines.
FORMAT_OPTIONS ('multiline' = 'true');
```

The example appends JSON rows to `sales.bronze.events`. The command skips files that have already been loaded. You can run `COPY INTO` from PySpark with `spark.sql()`.

```python
# Run the COPY INTO command from a PySpark notebook.
# spark.sql() executes the SQL statement and returns an empty DataFrame.
spark.sql("""
    COPY INTO sales.bronze.events
    FROM '/Volumes/sales/bronze/raw/events/'
    FILEFORMAT = JSON
    FORMAT_OPTIONS ('multiline' = 'true')
""")
```

`COPY INTO` supports file selection with `PATTERN` and `FILES`, schema evolution with `mergeSchema`, and validation with `VALIDATE`. These options let you control which files are loaded and how the table schema evolves. `COPY INTO` works well when ingesting files in the order of thousands over time. For sources that will grow to millions of files or more, Auto Loader is the recommended approach.

## Auto Loader as a complementary approach

Auto Loader is a specialized streaming source for files in cloud storage. It automatically detects new files as they arrive, infers the schema, and processes files incrementally. It uses a schema location to store the inferred schema and a checkpoint location to track progress. It supports file notification services and can scale to millions of files without the overhead of directory listing. Auto Loader provides exactly-once processing guarantees when configured with a reliable checkpoint location. Databricks recommends streaming tables backed by Auto Loader as a scalable, long-term alternative for SQL-based file ingestion.

The following PySpark example uses Auto Loader to read CSV files and write to a Unity Catalog table.

```python
# Configure Auto Loader to read from cloud storage.
# The format "cloudFiles" is the Auto Loader source.
# The cloudFiles.format option specifies the file format (csv).
# The cloudFiles.schemaLocation stores the inferred schema.
# The header option tells Auto Loader that the CSV files have a header.
df_auto = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "csv")
    .option("cloudFiles.schemaLocation", "/schemas/transactions")
    .option("header", "true")
    .load("/Volumes/sales/bronze/incoming/"))

# Write the stream to a Delta table in Unity Catalog.
# The checkpoint location tracks which files have been processed.
# The trigger "availableNow" processes all new files and stops.
(df_auto.writeStream
   .option("checkpointLocation", "/checkpoints/transactions")
   .trigger(availableNow=True)
   .toTable("sales.bronze.transactions_auto"))
```

Auto Loader is the right choice when the source is files and the volume is large or growing. It handles file detection, schema inference, and schema evolution automatically. It is more efficient than `COPY INTO` for millions of files because it does not scan the entire directory on every run. Use `COPY INTO` for simpler, scheduled batch ingestion of thousands of files. Use Auto Loader for continuous or high-scale ingestion.

## Decision framework: matching method to scenario

The choice of method depends on the source, the target, and the pattern of data flow. The following table maps common scenarios to the recommended method.

| Scenario | Recommended method | Reason |
|---|---|---|
| Initial load from a query | CTAS | Creates the table and populates it in one step |
| One-time migration | CTAS | Simple, atomic, schema derived from query |
| Periodic full refresh of a table | `CREATE OR REPLACE TABLE` | Replaces contents while preserving governance |
| Replacing a staging table | `CREATE OR REPLACE TABLE` | Atomic replacement, no downtime |
| Ongoing ingestion of new files | `COPY INTO` | Idempotent, appends only new files |
| Incremental file ingestion at scale | Auto Loader | Handles millions of files, schema inference |
| Continuous file ingestion | Auto Loader | Low latency, exactly-once |
| Append rows from a DataFrame | `INSERT INTO` or `append` mode | Adds rows without replacing |
| Update existing rows | `MERGE` | Upsert based on a key |

The table shows that CTAS and `CREATE OR REPLACE` are for table creation and full refresh. `COPY INTO` and Auto Loader are for file-based incremental ingestion. `INSERT INTO` and `MERGE` are for row-based operations. In a medallion architecture, CTAS is often used for the initial bronze load, `COPY INTO` or Auto Loader for ongoing bronze ingestion, `CREATE OR REPLACE` for silver and gold refreshes, and `MERGE` for slowly changing dimensions.

## Schema enforcement, evolution, and expectations

Schema enforcement and evolution behave differently across the methods. CTAS derives the schema from the query and creates the table with that schema. `CREATE OR REPLACE TABLE` replaces the schema along with the data. `COPY INTO` enforces the existing table schema and can evolve it with `mergeSchema`. Auto Loader infers the schema and stores it in a schema location, and it supports schema evolution.

The following table summarizes schema behavior.

| Method | Schema behavior | Evolution support |
|---|---|---|
| CTAS | Derived from query, creates table | Not applicable; new table each run |
| CREATE OR REPLACE | Replaces schema and data | Full schema replacement |
| COPY INTO | Enforces table schema | `mergeSchema` copy option |
| Auto Loader | Infers schema, stores in schema location | Automatic with schema location |

Expectations are data quality rules defined in Lakeflow Spark Declarative Pipelines. They can be attached to tables created by any method. Expectations drop, fail, or warn on rows that violate a rule. For example, an expectation can require that `order_id` is not null. Expectations complement schema enforcement by validating business rules.

## Null handling, case sensitivity, and time zones

Null handling differs by method and file format. In CSV files, empty strings may be treated as empty strings or as nulls depending on the `nullValue` option. In JSON files, the JSON literal `null` is treated as a null. In Parquet files, nulls are stored explicitly. If the target column is nullable, nulls are written. If the target column is non-nullable, the load fails. You should handle nulls in the query or transformation before loading.

Case sensitivity affects column names and string values. In Spark SQL, column names are case-insensitive by default. String values are case-sensitive. If source data has inconsistent casing, normalize it with `UPPER` or `LOWER`, or use a case-insensitive collation if the table is configured for one. Applying a function to a column can prevent predicate pushdown.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. When parsing timestamps from files or using `CURRENT_DATE` and `CURRENT_TIMESTAMP`, the session time zone determines the interpretation. Set the session time zone explicitly to UTC at the start of the job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Store timestamps in UTC and convert to local time only for display.

## Best practices

Use CTAS for initial loads and one-time migrations. It creates the table and populates it in a single atomic operation. Define the schema explicitly with casts and aliases to control the resulting table schema.

Use `CREATE OR REPLACE TABLE` for periodic full refreshes. It preserves table identity, privileges, history, row filters, and column masks. It is safer than dropping and recreating the table.

Use `COPY INTO` for incremental file ingestion when the number of files is in the thousands. It is idempotent and skips files that have already been loaded. Create the target table before running `COPY INTO`. Use `PATTERN` or `FILES` to control file selection. Use `VALIDATE` to check data before loading.

Use Auto Loader for file-based ingestion at scale or when you need continuous ingestion, automatic schema inference, or exactly-once guarantees. Auto Loader is recommended for sources that will grow to millions of files or more.

Set the session time zone explicitly to UTC. This avoids off-by-hours errors when parsing timestamps and using date functions.

Use schema evolution deliberately. `CREATE OR REPLACE TABLE` replaces the schema. `COPY INTO` with `mergeSchema` adds columns. Auto Loader evolves the schema automatically. Communicate schema changes to downstream consumers.

Define expectations in Lakeflow Spark Declarative Pipelines to validate data quality. Expectations catch invalid rows early.

Test the query or file load before running the production statement. Run the `SELECT` part with a `LIMIT` clause to verify columns and rows. Use `VALIDATE` for `COPY INTO`.

## Common mistakes and pitfalls

The most common mistake is using CTAS for a recurring load. CTAS fails if the table already exists. Use `CREATE OR REPLACE TABLE` for recurring full refreshes or `COPY INTO` for incremental loads.

A second mistake is using `CREATE OR REPLACE TABLE` for incremental updates. It replaces the entire table. If you only want to add new rows, use `INSERT INTO` or `COPY INTO`. If you want to update existing rows, use `MERGE`.

A third mistake is running `COPY INTO` without creating the target table first. The command fails if the table does not exist. Create the table with `CREATE TABLE IF NOT EXISTS`.

A fourth mistake is modifying source files after they have been loaded. `COPY INTO` tracks loaded files. If a file is modified, the change may not be detected. Treat source files as immutable.

A fifth mistake is using `COPY INTO` for millions of files. Directory listing does not scale. Use Auto Loader instead.

A sixth mistake is enabling schema evolution without communicating the change. Adding columns changes the table schema and may break downstream consumers.

A seventh mistake is not setting the session time zone. Timestamps are parsed in the session time zone. If the session time zone differs from the data time zone, the results may be incorrect.

An eighth mistake is forgetting that `CREATE OR REPLACE TABLE` replaces the schema. Downstream queries that use `SELECT *` or reference specific columns may break.

## Testing ingestion logic

Test ingestion logic with small files and known data. For CTAS and `CREATE OR REPLACE`, run the query as a `SELECT` before creating or replacing the table. For `COPY INTO`, create a test table, load a small file, run the command twice, and verify that no duplicates are added. For Auto Loader, use a test directory and verify that new files are processed.

The following SQL example tests `COPY INTO` idempotency.

```sql
-- Create a test table for COPY INTO testing.
CREATE TABLE IF NOT EXISTS tmp.copy_test (
    id INT,
    name STRING
);

-- Load a small CSV file into the test table.
COPY INTO tmp.copy_test
FROM '/Volumes/tmp/raw/'
FILEFORMAT = CSV
FORMAT_OPTIONS ('header' = 'true');

-- Query the test table to verify the rows were loaded.
SELECT * FROM tmp.copy_test;

-- Run the same COPY INTO command again.
-- The second run should load nothing because the file was already loaded.
COPY INTO tmp.copy_test
FROM '/Volumes/tmp/raw/'
FILEFORMAT = CSV
FORMAT_OPTIONS ('header' = 'true');

-- Query the table again.
-- The row count should be the same as after the first load.
SELECT COUNT(*) FROM tmp.copy_test;
```

The example verifies that `COPY INTO` is idempotent. Run tests like this in your CI pipeline against a small local Spark session. Clean up temporary tables and files after the test.

## Performance considerations

CTAS and `CREATE OR REPLACE TABLE` read from the source and write to the destination in a single job. The performance depends on the size of the source, the complexity of the query, and the write pattern. Reduce input size by filtering and selecting only the needed columns. Control the number of output files with `coalesce` or `repartition`, or run `OPTIMIZE` after the load.

`COPY INTO` performance depends on the number of files. Many small files are inefficient. Aim for files of 100 MB to 1 GB. Use `PATTERN` or `FILES` to reduce the number of files scanned. Run `OPTIMIZE` periodically to compact small files.

Auto Loader is optimized for large numbers of files. It uses file notification services and checkpointing to track progress. It scales to millions of files. Use the `availableNow` trigger for scheduled jobs to process all available data and stop.

Partitioning and clustering improve query performance. Choose partition columns based on query patterns. Avoid high-cardinality partition columns. Liquid clustering is an alternative that adapts as data changes.

Delta Lake stores per-file statistics that the optimizer uses to skip files. Filters on raw columns can use these statistics. Filters on expressions cannot. Materialize transformed values in columns when you filter on them frequently.
