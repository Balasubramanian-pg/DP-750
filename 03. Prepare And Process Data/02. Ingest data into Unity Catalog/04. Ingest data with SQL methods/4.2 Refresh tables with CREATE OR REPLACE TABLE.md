## Refresh tables with CREATE OR REPLACE TABLE

`CREATE OR REPLACE TABLE` is a SQL statement that either creates a new table or completely replaces the contents and schema of an existing table. When the table does not exist, the statement creates it. When the table already exists, the statement atomically replaces the table with the result of the query. The replacement is not a drop-and-recreate operation. Delta Lake and Unity Catalog preserve the table's identity, its history, its granted privileges, and any row filters or column masks attached to it. Downstream users and applications continue to access the table without reconfiguration because the table's name, location, and governance metadata remain intact. The data and schema are replaced, but the table itself is not destroyed.

This operation matters because full refreshes are common in analytical pipelines. A daily metrics table is rebuilt each night from the latest transactions. A product catalog is refreshed from a source system on a schedule. A gold aggregation is recalculated from silver data after a correction. In each case, the entire table must be replaced with a new result set. Without `CREATE OR REPLACE TABLE`, you would drop the table and recreate it. Dropping a table removes its privileges, its history, its row filters, and its column masks. Downstream consumers lose access until you reapply the grants and policies. `CREATE OR REPLACE TABLE` avoids this disruption. It replaces the data while preserving the table's governance and identity.

These notes cover `CREATE OR REPLACE TABLE` from first principles. They explain how it differs from `DROP TABLE` followed by `CREATE TABLE`, how it preserves metadata and privileges, and how it interacts with Delta Lake and Unity Catalog. They show how to use the statement with a `SELECT` query, how to load data from files with `read_files`, and how to achieve the same result in PySpark. They cover schema derivation, schema enforcement, schema evolution, expectations, null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand how to refresh tables reliably and safely.

## Understanding CREATE OR REPLACE TABLE

`CREATE OR REPLACE TABLE` is a single atomic statement. It either creates a new table or replaces an existing one. When it replaces an existing table, it does not drop the table and then create a new one. Instead, it commits a new version of the table in the Delta transaction log. The table's identity, including its name, its location, and its properties, is preserved. The data and schema are replaced with the result of the query. Because the operation is atomic, readers see either the old table or the new table, never a partial state. If the query fails, the table is left unchanged. If the query succeeds, the new data becomes visible in one commit.

### How it differs from DROP and CREATE

The traditional way to fully refresh a table is to drop it and then create it again. This approach has several problems. Dropping a table removes its metadata, including its privileges, its history, and any row filters or column masks. When you recreate the table, you must reapply all of these. If you forget to reapply a grant, a downstream consumer loses access. If you forget to reapply a row filter, sensitive data becomes visible. The drop-and-create approach also creates a window during which the table does not exist. Queries against the table fail during that window. If the create step fails, the table remains dropped, and you must recover it from a backup or rebuild it.

`CREATE OR REPLACE TABLE` avoids these problems. The table is never dropped. Its identity is preserved. Its privileges, history, row filters, and column masks remain in place. The replacement is atomic, so there is no window during which the table is unavailable. If the query fails, the existing table remains unchanged. This makes `CREATE OR REPLACE TABLE` the safer choice for full refreshes in production.

The following table compares the two approaches.

| Aspect | DROP and CREATE | CREATE OR REPLACE TABLE |
|---|---|---|
| Table identity | Lost and recreated | Preserved |
| Privileges | Lost, must be reapplied | Preserved |
| Row filters and column masks | Lost, must be reapplied | Preserved |
| Table history | Lost | Preserved |
| Availability during refresh | Table unavailable between drop and create | Table always available |
| Atomicity | Two separate operations | One atomic operation |
| Failure recovery | Table may remain dropped | Table remains unchanged on failure |

The table shows that `CREATE OR REPLACE TABLE` is superior in every dimension except that it does not allow you to change the table's location or certain immutable properties. If you need to change the table's location, you must drop and recreate it, or use a different approach such as `ALTER TABLE` or a new table with a different name.

### Preserving metadata, privileges, and policies

When `CREATE OR REPLACE TABLE` replaces an existing table, it preserves the table's metadata, privileges, and policies. The table's comment, its table properties, its partitioning, its clustering, and its location are preserved unless the query explicitly changes them. Privileges granted on the table are preserved. If a user or group had `SELECT` on the table, they continue to have `SELECT` on the replaced table. If a row filter or column mask was attached to the table, it remains attached. This is important for governance. You can refresh the data without reconfiguring access controls.

The schema is replaced. The new schema is derived from the query result. If the query produces a different set of columns or different data types, the table schema changes accordingly. This is a form of schema evolution, but it is a full replacement rather than an additive change. You should be deliberate about schema changes because they can break downstream consumers that expect a fixed set of columns. If you need to preserve the existing schema and only replace the data, you can cast the query results to match the existing schema, or use `INSERT OVERWRITE` instead.

## Syntax and usage

The basic syntax of `CREATE OR REPLACE TABLE` is similar to `CREATE TABLE AS SELECT`, with the addition of the `OR REPLACE` clause. The statement takes a table name and a `SELECT` query. The table is created or replaced with the query result. The table is a Delta table by default and is registered in Unity Catalog.

### Basic syntax with AS SELECT

The following SQL example creates or replaces a daily metrics table.

```sql
-- Create or replace the daily metrics table.
-- If the table does not exist, it is created.
-- If the table exists, it is replaced with the new data and schema.
-- The table is created in the sales.gold schema in Unity Catalog.
CREATE OR REPLACE TABLE sales.gold.daily_metrics AS
SELECT
    -- The report date is the grouping column.
    report_date,
    -- Sum the revenue for each date.
    SUM(revenue) AS total_revenue,
    -- Count the distinct customers for each date.
    -- COUNT(DISTINCT ...) ignores nulls in the customer_id column.
    COUNT(DISTINCT customer_id) AS unique_customers
FROM sales.silver.transactions
-- Filter to the last 30 days.
-- CURRENT_DATE returns the current date in the session time zone.
-- The interval arithmetic subtracts 30 days.
WHERE report_date >= CURRENT_DATE - INTERVAL 30 DAYS
-- Group by the report date.
GROUP BY report_date;
```

The example creates or replaces `sales.gold.daily_metrics` with an aggregation of transactions from the last 30 days. The schema of the table is derived from the query: `report_date`, `total_revenue`, and `unique_customers`. The table is a Delta table in Unity Catalog. If the table already exists, its privileges, row filters, and column masks are preserved. The data and schema are replaced.

### Using read_files for file-based refresh

You can use `read_files` inside the `SELECT` statement to load data directly from files. The following SQL example creates or replaces a products table from a CSV file.

```sql
-- Create or replace the products table from a CSV file.
-- The read_files function reads the file and returns a table.
-- The format option specifies that the file is CSV.
-- The header option tells read_files that the first row contains column names.
CREATE OR REPLACE TABLE sales.bronze.products AS
SELECT *
FROM read_files(
    '/Volumes/sales/bronze/raw/products.csv',
    format => 'csv',
    header => true
);
```

The example reads a CSV file and creates or replaces the `sales.bronze.products` table. The schema is inferred from the CSV file. For production pipelines, you should define the schema explicitly to avoid inference and to ensure deterministic types. You can define the schema in the `read_files` call by providing a `schema` option, or you can cast the columns in the query.

### PySpark equivalents

PySpark does not have a dedicated `CREATE OR REPLACE TABLE` method in the DataFrame API. You can achieve the same result in two ways. First, you can run the SQL statement with `spark.sql()`. Second, you can use `DataFrame.write.mode("overwrite").saveAsTable()`. However, `saveAsTable` with overwrite mode may not preserve all metadata and privileges in the same way as the SQL command. In Databricks, the SQL command is the recommended way to perform a full refresh with metadata preservation. The following PySpark example runs the SQL command.

```python
# Run a CREATE OR REPLACE TABLE statement using spark.sql.
# The SQL statement creates or replaces the daily metrics table.
# The table is created in the sales.gold schema.
spark.sql("""
    CREATE OR REPLACE TABLE sales.gold.daily_metrics AS
    SELECT
        report_date,
        SUM(revenue) AS total_revenue,
        COUNT(DISTINCT customer_id) AS unique_customers
    FROM sales.silver.transactions
    WHERE report_date >= CURRENT_DATE - INTERVAL 30 DAYS
    GROUP BY report_date
""")
```

The example runs the same SQL statement from a Python notebook. The `spark.sql()` method executes the statement. The table is created or replaced. This approach is useful when you prefer to write the transformation logic in SQL but run it from a PySpark notebook.

If you use `DataFrame.write.mode("overwrite").saveAsTable()`, the table is replaced, but the behavior regarding privileges and metadata may differ. In Databricks, `saveAsTable` with overwrite mode replaces the data and schema, but it may not preserve row filters and column masks. The SQL `CREATE OR REPLACE TABLE` command is specifically designed to preserve those. For production pipelines that require governance preservation, use the SQL command.

## Schema handling and evolution

`CREATE OR REPLACE TABLE` replaces the table schema with the schema of the query result. This is a full schema replacement, not an additive change. If the query produces a different set of columns or different data types, the table schema changes. Existing data is removed along with the old schema. This is different from schema evolution, which adds new columns to an existing table while preserving existing data.

### Schema derivation

The schema of the new table is derived from the `SELECT` list. Column names come from the aliases in the select list. If a column is an expression without an alias, Spark generates a name based on the expression. Data types are derived from the expressions. If you need the new table to have a specific schema, you can cast the columns in the query to the desired types. The following SQL example casts columns to specific types.

```sql
-- Create or replace a table with an explicit schema.
-- The CAST function converts the columns to the desired types.
-- The aliases give the columns clear names.
CREATE OR REPLACE TABLE sales.silver.orders AS
SELECT
    CAST(order_id AS INT) AS order_id,
    CAST(customer_id AS INT) AS customer_id,
    CAST(order_date AS DATE) AS order_date,
    CAST(order_amount AS DECIMAL(10, 2)) AS order_amount,
    CAST(order_status AS STRING) AS order_status
FROM sales.bronze.orders;
```

The example casts each column to a specific type. The resulting table has the exact schema defined by the casts and aliases. This is useful when the source data has types that are not suitable for analysis, such as strings that should be dates or numbers.

### Schema enforcement and evolution

After the table is created or replaced, Delta Lake enforces the table schema on subsequent writes. If you later append data with a different schema, the write fails unless schema evolution is enabled. If you need to change the schema again, you can run `CREATE OR REPLACE TABLE` again with a new query. This replaces the schema and the data. If you need to add a column without replacing the data, use `ALTER TABLE ADD COLUMN` or a write with `mergeSchema` enabled.

The following table summarizes the schema controls.

| Control | Mechanism | Effect |
|---|---|---|
| Schema derivation | `CREATE OR REPLACE TABLE AS SELECT` | Derives schema from query result |
| Schema enforcement | Delta Lake write | Rejects writes that do not match the table schema |
| Schema evolution | `mergeSchema` option or `ALTER TABLE` | Adds new columns to the table |
| Schema replacement | `CREATE OR REPLACE TABLE AS SELECT` | Replaces the table schema and data |

The table shows that `CREATE OR REPLACE TABLE` is a schema replacement operation. Use it when you want to change the schema and replace the data. Use schema evolution when you want to add columns and keep the data.

### Expectations

Expectations are data quality rules that you define in Lakeflow Spark Declarative Pipelines. `CREATE OR REPLACE TABLE` itself does not have expectations, but you can apply data quality rules in the query that populates the table. For example, you can filter out rows where a key is null, or you can use `CASE` expressions to validate values. If you use Lakeflow Spark Declarative Pipelines, you can define expectations on the tables that the pipeline creates. Expectations help you maintain data quality at the point of ingestion.

## Refresh strategies in the medallion architecture

In a medallion architecture, `CREATE OR REPLACE TABLE` is used at different layers for different purposes. In the bronze layer, it is used to ingest raw files or external data into a table. The bronze table is often fully refreshed from the source. In the silver layer, it is used to clean and conform the data. The silver table is refreshed from the bronze table. In the gold layer, it is used to aggregate and denormalize the data. The gold table is refreshed from the silver table. In each layer, the refresh replaces the entire table contents with the latest result.

The following table summarizes the use of `CREATE OR REPLACE TABLE` in each layer.

| Layer | Source | Typical use |
|---|---|---|
| Bronze | Raw files, external databases | Initial load, full refresh from source |
| Silver | Bronze tables | Clean and conform data, full refresh |
| Gold | Silver tables | Aggregate and denormalize, full refresh |

The table shows that `CREATE OR REPLACE TABLE` is a full refresh operation. It is not incremental. For incremental updates, use `COPY INTO`, `MERGE`, or `INSERT INTO`. If the source data changes frequently and only a small portion changes, an incremental approach is more efficient. If the source data is small or changes completely, a full refresh is simpler and more reliable.

## Null handling, case sensitivity, and time zones

Null handling in `CREATE OR REPLACE TABLE` follows the same rules as in any SQL query. The `SELECT` statement produces values, and those values are written to the table. If a column is nullable and the query produces a null, the table contains a null. If the query produces a non-null value, the table contains the value. You should handle nulls in the query using `COALESCE`, `CASE`, or `WHERE` clauses. For example, `COALESCE(order_amount, 0)` replaces null amounts with zero. `WHERE customer_id IS NOT NULL` filters out rows with null keys. If you want the new table to have non-nullable columns, you can use `CAST` and `WHERE` clauses to enforce that no nulls are present, but Delta Lake does not enforce non-nullability unless you define the column as `NOT NULL` in the table schema.

Case sensitivity affects string comparisons and column names. In Spark SQL, column names are case-insensitive by default. String values are case-sensitive. If your source data has inconsistent casing, you should normalize it in the query using `UPPER` or `LOWER`. For example, `WHERE UPPER(order_status) = 'COMPLETE'` matches both `'Complete'` and `'complete'`. Be aware that applying a function to a column can prevent predicate pushdown and may force a full scan.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. The session time zone is set by `spark.sql.session.timeZone`. When you use `CURRENT_DATE` or `CURRENT_TIMESTAMP` in a query, the values are computed in the session time zone. If the session time zone differs from the time zone in which the data was written, the results may be off by hours. To avoid this, set the session time zone explicitly at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Use timestamp literals with explicit offsets when comparing to timestamps. Store timestamps in UTC and convert to local time only for display.

## Best practices

Use `CREATE OR REPLACE TABLE` for full refreshes. It preserves table identity, privileges, history, row filters, and column masks. It is safer than dropping and recreating the table.

Do not use `CREATE OR REPLACE TABLE` for incremental updates. It replaces the entire table. For incremental updates, use `COPY INTO`, `MERGE`, or `INSERT INTO`.

Define the schema explicitly in the query. Use `CAST` and aliases to ensure that the new table has the exact schema you want. Avoid relying on schema inference for production pipelines.

Set the session time zone explicitly to UTC. This avoids off-by-hours errors when using `CURRENT_DATE` and `CURRENT_TIMESTAMP`.

Handle nulls deliberately. Decide whether nulls should be preserved, replaced with a default, or filtered out. Use `COALESCE`, `CASE`, or `WHERE` clauses in the query.

Test the query before running `CREATE OR REPLACE TABLE`. Run the `SELECT` part with a `LIMIT` clause to verify the columns, types, and rows. Check the schema with `DESCRIBE` or by inspecting the DataFrame.

Communicate schema changes. Replacing the table replaces the schema. Downstream consumers that expect a fixed set of columns may break. Notify them before making schema changes.

## Common mistakes and pitfalls

The most common mistake is using `CREATE OR REPLACE TABLE` for incremental updates. It replaces the entire table. If you only want to add new rows, use `INSERT INTO` or `COPY INTO`. If you want to update existing rows, use `MERGE`.

A second mistake is forgetting that `CREATE OR REPLACE TABLE` replaces the schema. If the query produces a different set of columns, the table schema changes. Downstream queries that use `SELECT *` or reference specific columns may break.

A third mistake is not setting the session time zone. `CURRENT_DATE` and `CURRENT_TIMESTAMP` use the session time zone. If the session time zone differs from the data time zone, the results may be inconsistent.

A fourth mistake is assuming that `CREATE OR REPLACE TABLE` preserves the table's location. If the table is an external table, the location is preserved. If the table is a managed table, the location is managed by Unity Catalog. In general, the location is preserved, but if you need to change the location, you must use a different approach.

A fifth mistake is using `CREATE OR REPLACE TABLE` without testing the query. If the query has an error or produces unexpected results, the table is replaced with the wrong data. Always test the query first.

A sixth mistake is not communicating schema changes. Replacing the table replaces the schema. Downstream consumers may break if they expect a fixed set of columns.

## Testing CREATE OR REPLACE TABLE

Test `CREATE OR REPLACE TABLE` by running the query as a `SELECT` before creating or replacing the table. This lets you verify the columns, types, and rows without modifying the table. The following SQL example runs the query with a limit.

```sql
-- Test the query before creating or replacing the table.
-- The LIMIT clause returns a small sample of rows.
-- Verify that the columns, types, and values are as expected.
SELECT
    report_date,
    SUM(revenue) AS total_revenue,
    COUNT(DISTINCT customer_id) AS unique_customers
FROM sales.silver.transactions
WHERE report_date >= CURRENT_DATE - INTERVAL 30 DAYS
GROUP BY report_date
LIMIT 10;
```

The example returns ten rows. You can inspect the result and verify that the transformation is correct. Once you are satisfied, you can run the `CREATE OR REPLACE TABLE` statement.

You can also test with PySpark by building the DataFrame and inspecting it before writing. The following PySpark example builds the transformed DataFrame and displays it.

```python
from pyspark.sql.functions import col, sum, countDistinct, current_date, date_sub

# Read the silver transactions table.
df_transactions = spark.read.table("sales.silver.transactions")

# Apply the transformations.
df_metrics = (df_transactions
    .filter(col("report_date") >= date_sub(current_date(), 30))
    .groupBy("report_date")
    .agg(
        sum("revenue").alias("total_revenue"),
        countDistinct("customer_id").alias("unique_customers")
    ))

# Display the transformed DataFrame.
# This does not create or replace a table. It only shows the result.
display(df_metrics)
```

The example displays the transformed DataFrame. You can verify the columns and values before writing the table. Once you are satisfied, you can run the SQL command or write the DataFrame with `saveAsTable` using overwrite mode.

## Performance considerations

`CREATE OR REPLACE TABLE` reads from the source and writes to the destination in a single job. The performance depends on the size of the source, the complexity of the query, and the write pattern. If the query includes joins, aggregations, or sorts, Spark performs a shuffle, which is the most expensive operation. Reduce the size of the input by filtering and selecting only the needed columns before the join or aggregation.

The number of output files affects query performance. If the query produces too many small files, queries against the table are slow because each file has metadata overhead. Use `coalesce` or `repartition` to control the number of partitions before the write, or run `OPTIMIZE` after the refresh to compact small files. Aim for files of 100 MB to 1 GB.

Partitioning and clustering improve query performance. If you frequently filter by a column, partition by that column or use liquid clustering. Choose partition columns that have a reasonable number of distinct values. Avoid high-cardinality partition columns, which create many small directories.

Delta Lake stores per-file statistics that the optimizer uses to skip files. When you create or replace a table, the new files have statistics for the columns. Filters on raw columns can use these statistics. Filters on expressions cannot. If you filter on a transformed value frequently, materialize the transformed value in a column at refresh time so that statistics are collected for it.

`CREATE OR REPLACE TABLE` is atomic. Readers see either the old table or the new table. There is no window during which the table is unavailable. This is important for production pipelines that cannot afford downtime.

## An end-to-end example

Consider a scenario where you need to refresh a gold table that summarizes daily sales by region. The source is a silver transactions table. The gold table is refreshed each night with the latest 30 days of data. The pipeline uses `CREATE OR REPLACE TABLE` to replace the gold table. The following SQL example shows the refresh.

```sql
-- Create or replace the gold daily sales summary table.
-- The table is refreshed with the last 30 days of transactions.
-- The table is created in the sales.gold schema.
CREATE OR REPLACE TABLE sales.gold.daily_sales_summary AS
SELECT
    -- The transaction date is the grouping column.
    transaction_date,
    -- The region is the second grouping column.
    region,
    -- Sum the sales amounts for each date and region.
    SUM(sales_amount) AS total_sales,
    -- Count the transactions for each date and region.
    COUNT(*) AS transaction_count,
    -- Count the distinct customers for each date and region.
    COUNT(DISTINCT customer_id) AS unique_customers
FROM sales.silver.transactions
-- Filter to the last 30 days.
WHERE transaction_date >= CURRENT_DATE - INTERVAL 30 DAYS
-- Group by date and region.
GROUP BY transaction_date, region;
```

The example creates or replaces the `sales.gold.daily_sales_summary` table with an aggregation of the last 30 days of transactions. The table is a Delta table in Unity Catalog. If the table already exists, its privileges, row filters, and column masks are preserved. The data and schema are replaced.

The equivalent PySpark example runs the same SQL statement.

```python
# Run the CREATE OR REPLACE TABLE statement using spark.sql.
spark.sql("""
    CREATE OR REPLACE TABLE sales.gold.daily_sales_summary AS
    SELECT
        transaction_date,
        region,
        SUM(sales_amount) AS total_sales,
        COUNT(*) AS transaction_count,
        COUNT(DISTINCT customer_id) AS unique_customers
    FROM sales.silver.transactions
    WHERE transaction_date >= CURRENT_DATE - INTERVAL 30 DAYS
    GROUP BY transaction_date, region
""")
```

The example runs the same SQL statement from a Python notebook. The table is created or replaced. The operation is atomic. Downstream consumers continue to access the table without reconfiguration.

## Summary

`CREATE OR REPLACE TABLE` is a SQL statement that either creates a new table or completely replaces an existing table with the result of a query. It is the recommended way to perform full refreshes in Delta Lake and Unity Catalog. Unlike dropping and recreating a table, it preserves the table's identity, privileges, history, row filters, and column masks. The replacement is atomic, so readers see either the old table or the new table, never a partial state. If the query fails, the existing table remains unchanged.

The statement is used with a `SELECT` query or with `read_files` to load data from files. The schema is derived from the query result. You can cast columns and use aliases to control the schema. The PySpark equivalent is to run the SQL statement with `spark.sql()` or to use `DataFrame.write.mode("overwrite").saveAsTable()`, though the SQL command is preferred for preserving governance metadata.

Schema handling is important. `CREATE OR REPLACE TABLE` replaces the schema along with the data. Use `CAST` and aliases to define the schema explicitly. After the table is created or replaced, Delta Lake enforces the schema on subsequent writes. Use schema evolution or `ALTER TABLE` to add columns without replacing the data.

In a medallion architecture, `CREATE OR REPLACE TABLE` is used to refresh tables at each layer. Bronze tables are refreshed from raw sources, silver tables from bronze, and gold tables from silver. It is a full refresh operation and is not suitable for incremental updates. For incremental updates, use `COPY INTO`, `MERGE`, or `INSERT INTO`.

Null handling, case sensitivity, and time zones affect the query and the resulting table. Set the session time zone explicitly to UTC. Normalize string casing. Handle nulls deliberately. Best practices include using `CREATE OR REPLACE TABLE` for full refreshes, defining the schema explicitly, setting the session time zone, handling nulls, testing the query before running the statement, and communicating schema changes. Common mistakes include using it for incremental updates, forgetting that it replaces the schema, not setting the session time zone, and not testing the query.

Test the query as a `SELECT` before creating or replacing the table. Performance depends on the query complexity and the write pattern. Reduce input size, control the number of output files, partition or cluster for query performance, and use Delta statistics. `CREATE OR REPLACE TABLE` is a safe, atomic, and governed way to refresh tables in Unity Catalog.
