## Load files incrementally with COPY INTO

`COPY INTO` is a SQL command in Azure Databricks that loads files from cloud storage into an existing Delta table. It reads a set of files from a source location, parses them according to the format you specify, and appends the resulting rows to the target table. The command is designed for incremental ingestion. It tracks which files have already been loaded and skips them on subsequent runs. This behavior is called idempotency. If you run the same `COPY INTO` statement twice, the second run does not load the same files again. This makes the command safe to retry after a failure and suitable for scheduled pipelines that run repeatedly.

`COPY INTO` matters because file-based ingestion is a common pattern in the lakehouse. Raw data arrives in cloud storage as CSV, JSON, Parquet, or other files. A pipeline must load those files into a Delta table in Unity Catalog without duplicating rows or missing files. Without idempotency, a pipeline that fails halfway through and restarts would reload files that were already processed, creating duplicates. Without tracking, a pipeline would have to compare the source and target on every run, which is expensive. `COPY INTO` solves both problems. It records the files it has loaded and uses that record to skip them. The target table must already exist, and the command appends to it.

These notes cover `COPY INTO` from first principles. They explain how idempotency works, how to create the target table, how to configure file selection with `PATTERN` and `FILES`, and how to handle schema changes with `mergeSchema`. They explain how to validate data without loading it using the `VALIDATE` clause. They show how `COPY INTO` fits into the medallion architecture and how it compares with Auto Loader and CTAS. They also cover null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand how to use `COPY INTO` to load files incrementally and reliably into Unity Catalog.

## Understanding COPY INTO and idempotent ingestion

`COPY INTO` is an append operation. It reads files from a source location and adds the rows to an existing Delta table. It does not replace the table. It does not update existing rows. It does not delete rows. It only appends. If you need to replace the table, use `CREATE OR REPLACE TABLE` or `INSERT OVERWRITE`. If you need to update existing rows, use `MERGE`. `COPY INTO` is the right tool when new files arrive regularly and you want to add their contents to a growing table.

The defining feature of `COPY INTO` is idempotency. When you run the command, it compares the files in the source location with the files it has already loaded. Files that have been loaded before are skipped. Files that are new are loaded. The record of loaded files is stored in the Delta table's transaction log. This means that if you run the same command twice, the second run loads nothing. If you add new files and run the command again, only the new files are loaded. This behavior holds even if the command fails partway through. On the next run, the files that were successfully loaded are skipped, and the remaining files are loaded.

Idempotency depends on the source files being immutable. If a file is modified after it has been loaded, `COPY INTO` may not detect the change and may skip the file, leaving the table with stale data. If a file is deleted and recreated with the same name, `COPY INTO` may treat it as a new file or skip it depending on the metadata. For reliable idempotency, source files should be written once and never modified. If you need to reprocess a file, use the `FILES` option to load it explicitly, or use the `force` copy option to reload all files. The following table compares `COPY INTO` with other loading commands.

| Command | Operation | Idempotent | Typical use |
|---|---|---|---|
| `COPY INTO` | Append new files | Yes, skips loaded files | Incremental file ingestion |
| `INSERT INTO` | Append rows | No | Incremental row ingestion |
| `CREATE OR REPLACE TABLE` | Replace table | No | Full refresh |
| `MERGE` | Update, insert, delete | Yes, if key is unique | Upsert, CDC |

The table shows that `COPY INTO` is unique because it is idempotent for file-based ingestion. `INSERT INTO` is not idempotent; running it twice duplicates rows. `CREATE OR REPLACE TABLE` replaces the table. `MERGE` is idempotent when the matching key is unique. Use `COPY INTO` when your source is files and you want to load new files without duplicates.

## Prerequisites and basic syntax

Before you run `COPY INTO`, the target table must exist. `COPY INTO` does not create the table. You create the table with `CREATE TABLE` and specify the schema. The schema must match the structure of the files you are loading, or the load fails unless schema evolution is enabled. The following SQL example creates a target table for event data.

```sql
-- Create the target table if it does not already exist.
-- The IF NOT EXISTS clause makes the statement idempotent.
-- If the table already exists, the statement does nothing.
CREATE TABLE IF NOT EXISTS sales.bronze.events (
    -- The event_id column stores the unique identifier for each event.
    event_id STRING,
    -- The event_type column stores the category of the event.
    event_type STRING,
    -- The event_timestamp column stores the time the event occurred.
    event_timestamp TIMESTAMP,
    -- The payload column stores the raw event data as a string.
    payload STRING
);
```

The example creates a table named `sales.bronze.events` in Unity Catalog. The table has four columns. The `IF NOT EXISTS` clause prevents an error if the table already exists. The table is a Delta table by default. Once the table exists, you can load files into it with `COPY INTO`. The following SQL example loads JSON files into the table.

```sql
-- Load JSON files from a Unity Catalog volume into the target table.
-- The COPY INTO command appends rows to the existing table.
-- Files that have already been loaded are skipped automatically.
COPY INTO sales.bronze.events
-- The FROM clause specifies the source directory.
-- The path is a Unity Catalog volume path.
FROM '/Volumes/sales/bronze/raw/events/'
-- The FILEFORMAT clause specifies that the files are JSON.
FILEFORMAT = JSON
-- The FORMAT_OPTIONS clause configures how the JSON is parsed.
-- The multiline option tells Spark that each file contains a single
-- JSON object or array that spans multiple lines.
FORMAT_OPTIONS ('multiline' = 'true');
```

The example loads JSON files from the volume path into the `sales.bronze.events` table. The `FILEFORMAT` clause specifies JSON. The `FORMAT_OPTIONS` clause sets `multiline` to `true`, which tells Spark that the JSON is not line-delimited. The command appends the rows to the table. If the command is run again, the files that were already loaded are skipped. You can run `COPY INTO` from a PySpark notebook by using `spark.sql()`. The following PySpark example runs the same command.

```python
# Run the COPY INTO command from a PySpark notebook.
# spark.sql() executes the SQL statement and returns an empty DataFrame.
# The table is updated as a side effect.
spark.sql("""
    COPY INTO sales.bronze.events
    FROM '/Volumes/sales/bronze/raw/events/'
    FILEFORMAT = JSON
    FORMAT_OPTIONS ('multiline' = 'true')
""")
```

The example runs the `COPY INTO` statement from Python. The SQL string is passed to `spark.sql()`. The command executes and appends the new files. This approach is useful when you want to use the PySpark DataFrame API for other parts of the pipeline but still use `COPY INTO` for file ingestion.

## Configuring file selection

Source directories often contain many files, and you may not want to load all of them. `COPY INTO` provides two options for selecting files: `PATTERN` and `FILES`. `PATTERN` selects files by a glob pattern. `FILES` selects specific files by name. You use one or the other, not both. The following table compares the two options.

| Option | Selection method | Use case |
|---|---|---|
| `PATTERN` | Glob pattern matching | Load files with a common naming convention |
| `FILES` | Explicit list of file names | Load specific files, such as reprocessing a known batch |

The `PATTERN` option is useful when files follow a naming convention. For example, if orders files are named `orders_2024_01.parquet`, `orders_2024_02.parquet`, and so on, you can load only the 2024 files with a pattern. The following SQL example shows `PATTERN`.

```sql
-- Load only files that match a pattern.
-- The PATTERN clause uses a glob pattern.
-- The pattern 'orders_2024*.parquet' matches files that start with
-- 'orders_2024' and end with '.parquet'.
COPY INTO sales.bronze.orders
FROM '/Volumes/sales/bronze/raw/orders/'
FILEFORMAT = PARQUET
PATTERN = 'orders_2024*.parquet';
```

The example loads only Parquet files whose names start with `orders_2024`. Files that do not match the pattern are ignored. The `PATTERN` option is evaluated before the idempotency check. Files that match the pattern but have already been loaded are still skipped. The `FILES` option is useful when you need to load a specific set of files, such as when reprocessing a known batch. The following SQL example shows `FILES`.

```sql
-- Load specific files by name.
-- The FILES clause lists the exact file names to load.
-- The files must exist in the source directory.
COPY INTO sales.bronze.orders
FROM '/Volumes/sales/bronze/raw/orders/'
FILEFORMAT = PARQUET
FILES = ('orders_001.parquet', 'orders_002.parquet');
```

The example loads only `orders_001.parquet` and `orders_002.parquet`. Other files in the directory are ignored. The `FILES` option is useful when you need to reload a specific file after a correction. If the file has already been loaded, `COPY INTO` skips it unless you use the `force` copy option. The `force` option tells `COPY INTO` to load the files even if they have been loaded before. Use it with care because it can create duplicates.

## Handling schema and data quality

`COPY INTO` provides options for handling schema changes and validating data. The `mergeSchema` copy option allows the table schema to evolve when new columns appear in the source files. The `VALIDATE` clause checks whether the data can be parsed and matches the table schema without actually loading it. These options help you maintain data quality and adapt to changing sources.

### Schema evolution with mergeSchema

By default, `COPY INTO` enforces the target table schema. If a source file has a column that the table does not have, the load fails. If the source file is missing a column that the table has, the column is written as null if it is nullable. If the column is non-nullable, the load fails. To allow new columns to be added to the table, use the `mergeSchema` copy option. The following SQL example shows `mergeSchema`.

```sql
-- Load CSV files with schema evolution enabled.
-- The FORMAT_OPTIONS clause configures CSV parsing.
-- The header option uses the first row as column names.
-- The inferSchema option detects column types.
-- The COPY_OPTIONS clause enables schema evolution.
-- The mergeSchema option adds new columns from the source to the table.
COPY INTO sales.bronze.sensor_data
FROM '/Volumes/sales/bronze/raw/sensors/'
FILEFORMAT = CSV
FORMAT_OPTIONS (
    'header' = 'true',
    'inferSchema' = 'true'
)
COPY_OPTIONS ('mergeSchema' = 'true');
```

The example loads CSV files and enables schema evolution. If a source file has a new column, the column is added to the table. Existing rows get null in the new column. Schema evolution should be used deliberately. Adding a column changes the table schema and may break downstream consumers that expect a fixed set of columns. In a medallion architecture, schema changes are usually managed in the bronze layer and propagated to silver and gold through transformations. If you use Lakeflow Spark Declarative Pipelines, you can define expectations on downstream tables to validate data quality.

### Validating data without loading

The `VALIDATE` clause checks whether the data can be parsed, matches the table schema, and satisfies nullability and check constraints. It does not load the data. It returns a result set with information about the validation. The following SQL example shows `VALIDATE ALL`.

```sql
-- Validate all files without loading them.
-- The VALIDATE clause checks whether the data can be parsed and
-- matches the table schema. It does not append rows to the table.
COPY INTO sales.bronze.sensor_data
FROM '/Volumes/sales/bronze/raw/sensors/'
FILEFORMAT = CSV
VALIDATE ALL;
```

The example validates all files in the source directory. The result includes the number of rows that would be loaded, the number of rows that failed validation, and the reasons for failure. Use `VALIDATE` before loading a new batch to catch parsing errors and schema mismatches. This is especially useful when the source format changes or when you are onboarding a new data source.

## Incremental ingestion patterns and the medallion architecture

`COPY INTO` is commonly used in the bronze layer of the medallion architecture. The bronze layer holds raw data as it arrived from the source. Files land in cloud storage or a Unity Catalog volume. A scheduled job runs `COPY INTO` to append new files to a bronze Delta table. The job runs repeatedly, and `COPY INTO` ensures that each file is loaded exactly once. The bronze table grows over time and preserves the raw history. Downstream transformations read from the bronze table and write to silver and gold tables. The silver layer cleans and conforms the data. The gold layer aggregates and denormalizes it.

`COPY INTO` is a batch command. It runs on a schedule, not continuously. If you need continuous ingestion with low latency, use Auto Loader. Auto Loader is a streaming source that detects new files as they arrive and processes them incrementally. It also tracks which files have been processed. The following table compares `COPY INTO` and Auto Loader.

| Aspect | COPY INTO | Auto Loader |
|---|---|---|
| Processing mode | Batch | Streaming |
| Trigger | Scheduled | Continuous or scheduled |
| File detection | Scans the directory | Uses file notification or directory listing |
| Schema inference | Optional | Automatic with schema location |
| Schema evolution | mergeSchema option | Supported with schema location |
| Latency | Depends on schedule | Low |
| Use case | Scheduled batch ingestion | Continuous or near-real-time ingestion |

The table shows that `COPY INTO` is simpler and suitable for scheduled batch ingestion. Auto Loader is more complex but provides lower latency and automatic schema management. Both are idempotent. Both write to Delta tables. Choose `COPY INTO` when the freshness requirement is minutes or hours and you want a simple SQL command. Choose Auto Loader when you need continuous ingestion or automatic schema evolution.

## Null handling, case sensitivity, and time zones

Null handling in `COPY INTO` depends on the file format and the options. In CSV files, empty strings may be treated as empty strings or as nulls depending on the `nullValue` option. By default, an empty string in a CSV file is treated as an empty string, not a null. To treat empty strings as nulls, set the `nullValue` option to an empty string. In JSON files, the JSON literal `null` is treated as a null. In Parquet files, nulls are stored explicitly. If the target column is nullable, nulls are written. If the target column is non-nullable, the load fails. You should ensure that non-nullable columns in the target have a default or that the source does not produce nulls for those columns.

Case sensitivity affects column names and string values. In Spark SQL, column names are case-insensitive by default. `Event_ID` and `event_id` refer to the same column. String values are case-sensitive. `'Click'` and `'click'` are different values. If your source data has inconsistent casing, normalize it in a downstream transformation or use a case-insensitive collation if the table is configured for one. Be aware that applying a function to a column can prevent predicate pushdown.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. When `COPY INTO` parses a timestamp from a file, it interprets the timestamp in the session time zone unless the file includes an explicit offset. To avoid off-by-hours errors, set the session time zone explicitly at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Use timestamp literals with explicit offsets when comparing to timestamps. Store timestamps in UTC and convert to local time only for display.

## Best practices

Create the target table before running `COPY INTO`. The command does not create the table. Use `CREATE TABLE IF NOT EXISTS` to make the creation step idempotent.

Use `COPY INTO` for incremental file ingestion. It is idempotent and skips files that have already been loaded. It is the right choice when new files arrive regularly and you want to append them to a Delta table.

Use `PATTERN` or `FILES` to control which files are loaded. `PATTERN` is useful for naming conventions. `FILES` is useful for reprocessing specific files.

Use `mergeSchema` deliberately. It adds new columns to the table. This changes the schema and may break downstream consumers. Communicate schema changes and test downstream queries.

Use `VALIDATE` before loading a new batch. It catches parsing errors and schema mismatches without modifying the table. It is especially useful when onboarding a new source.

Set the session time zone explicitly to UTC. This avoids off-by-hours errors when parsing timestamps.

Monitor the table size and file count. `COPY INTO` appends new files. Over time, the table may accumulate many small files. Run `OPTIMIZE` periodically to compact small files into larger ones.

Use Unity Catalog for governance. The target table is a Unity Catalog table. Permissions, lineage, and auditing are managed by Unity Catalog.

## Common mistakes and pitfalls

The most common mistake is running `COPY INTO` without creating the target table first. The command fails if the table does not exist. Create the table with `CREATE TABLE IF NOT EXISTS` before running `COPY INTO`.

A second mistake is modifying source files after they have been loaded. `COPY INTO` tracks loaded files. If a file is modified, the change may not be detected, and the table may contain stale data. Treat source files as immutable.

A third mistake is using `COPY INTO` when `INSERT INTO` or `MERGE` is needed. `COPY INTO` only appends rows from files. If you need to update existing rows, use `MERGE`. If you need to insert individual rows, use `INSERT INTO`.

A fourth mistake is enabling `mergeSchema` without communicating the change. Adding columns changes the table schema and may break downstream consumers that expect a fixed set of columns.

A fifth mistake is not setting the session time zone. Timestamps are parsed in the session time zone. If the session time zone differs from the time zone in which the files were written, the timestamps may be incorrect.

A sixth mistake is using `force` without understanding the consequences. The `force` copy option reloads files even if they have already been loaded. This can create duplicates. Use it only when you intend to reload files.

A seventh mistake is ignoring the `VALIDATE` clause. Validating before loading catches errors early and prevents bad data from entering the table.

## Testing COPY INTO logic

Test `COPY INTO` with small files and a test table. Verify that the command loads the expected rows, that it skips files on subsequent runs, and that schema evolution works as expected. The following SQL example creates a test table, loads a small file, and validates the result.

```sql
-- Create a test table for COPY INTO testing.
CREATE TABLE IF NOT EXISTS tmp.copy_test (
    id INT,
    name STRING
);

-- Load a small CSV file into the test table.
COPY INTO tmp.copy_test
FROM '/Volumes/tmp/raw/'
FILEFORMAT = CSV
FORMAT_OPTIONS ('header' = 'true');

-- Query the test table to verify the rows were loaded.
SELECT * FROM tmp.copy_test;

-- Run the same COPY INTO command again.
-- The second run should load nothing because the file was already loaded.
COPY INTO tmp.copy_test
FROM '/Volumes/tmp/raw/'
FILEFORMAT = CSV
FORMAT_OPTIONS ('header' = 'true');

-- Query the table again.
-- The row count should be the same as after the first load.
SELECT COUNT(*) FROM tmp.copy_test;
```

The example creates a test table, loads a CSV file, and verifies the row count. It then runs the same command again and verifies that no duplicates were added. This confirms that idempotency is working. You can also test schema evolution by adding a new column to the CSV file and running `COPY INTO` with `mergeSchema`. The following PySpark example tests schema evolution.

```python
# Run a COPY INTO command with mergeSchema from PySpark.
spark.sql("""
    COPY INTO tmp.copy_test
    FROM '/Volumes/tmp/raw/'
    FILEFORMAT = CSV
    FORMAT_OPTIONS ('header' = 'true')
    COPY_OPTIONS ('mergeSchema' = 'true')
""")

# Verify that the new column was added to the table.

assert "new_column" in columns, f"Expected new_column in {columns}"
```

The test verifies that schema evolution added the new column. Run tests like this in your CI pipeline against a small local Spark session. Clean up temporary tables and files after the test.

## Performance considerations

`COPY INTO` performance depends on the number of files, their size, and the format. Many small files are inefficient because each file has metadata overhead and the command must open many files. Aim for files of 100 MB to 1 GB. If your source produces many small files, consider compacting them before loading or using Auto Loader, which is optimized for many small files.

The `PATTERN` and `FILES` options reduce the number of files that `COPY INTO` must scan. If you only need to load a subset of files, use one of these options to avoid scanning the entire directory. This is especially important when the source directory contains many files that have already been loaded.

`COPY INTO` uses the Delta table's transaction log to track loaded files. The log grows as more files are loaded. For very large tables with many files, the log can become a performance bottleneck. Run `OPTIMIZE` periodically to compact small files and reduce the number of files in the table. In Databricks, predictive optimization can do this automatically for Unity Catalog managed tables.

Partitioning improves query performance but does not directly affect `COPY INTO` performance. If the target table is partitioned, `COPY INTO` writes rows to the appropriate partitions. Partition columns should be chosen based on query patterns. Avoid high-cardinality partition columns.

Use `COPY INTO` with a schedule that matches the arrival rate of files. Running it too frequently adds overhead without benefit. Running it too infrequently increases latency. Choose a schedule that balances latency with cost.

## An end-to-end example

Consider a scenario where you need to ingest daily order files from a cloud storage volume into a bronze table, validate the files, and then transform the data into a silver table. The following SQL example shows the complete pipeline.

```sql
-- Create the bronze orders table.
CREATE TABLE IF NOT EXISTS sales.bronze.orders (
    order_id STRING,
    customer_id STRING,
    order_date DATE,
    order_amount DECIMAL(10, 2),
    order_status STRING
);

-- Validate the daily order files before loading.
COPY INTO sales.bronze.orders
FROM '/Volumes/sales/bronze/raw/orders/'
FILEFORMAT = PARQUET
VALIDATE ALL;

-- Load the daily order files into the bronze table.
COPY INTO sales.bronze.orders
FROM '/Volumes/sales/bronze/raw/orders/'
FILEFORMAT = PARQUET;

-- Create the silver orders table from the bronze table.
CREATE OR REPLACE TABLE sales.silver.orders AS
SELECT
    order_id,
    customer_id,
    order_date,
    order_amount,
    order_status
FROM sales.bronze.orders
WHERE order_amount > 0
  AND order_status IS NOT NULL;
```

The example creates a bronze table, validates the files, loads the files, and creates a silver table. The bronze table holds the raw data. The silver table filters out invalid rows and selects the columns needed for analysis. The pipeline uses `COPY INTO` for incremental ingestion and `CREATE OR REPLACE TABLE` for the silver transformation. The bronze table grows over time as new files arrive. The silver table is rebuilt from the bronze table on each run.
