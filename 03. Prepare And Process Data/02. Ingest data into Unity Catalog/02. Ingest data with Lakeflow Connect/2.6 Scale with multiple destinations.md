## Scale with multiple destinations

A single ingestion pipeline in Lakeflow Connect can write the same source data to more than one destination table in Unity Catalog. Each destination is defined in the ingestion definition as a separate object. The pipeline reads the source once and writes the result to each destination. This capability is useful when different teams need isolated copies of the same source data, when separate governance boundaries are required, or when the same data must land in different schemas for different purposes. Instead of creating multiple pipelines that each read the same source, you create one pipeline with multiple destinations. The source is read once, which reduces load on the source system and simplifies pipeline management.

Multiple destinations matter because data is consumed by many teams with different needs. A sales analytics team might need customer data in a `sales.analytics` schema, while a marketing team needs the same customer data in a `marketing.campaigns` schema. If you create two separate pipelines, each reads the source independently, which doubles the load on the source and doubles the operational overhead. A single pipeline with two destinations reads the source once and writes to both schemas. Each destination is a separate Delta table in Unity Catalog, so each is governed independently. You can grant different permissions to each table, apply different row-level filters or column masks, and track lineage separately. The pipeline remains one unit to monitor and schedule, while the destinations remain independent for governance and consumption.

These notes cover multiple destinations from first principles. They explain how to configure a pipeline with multiple destinations, how to use custom destination table names, and how each destination is governed in Unity Catalog. They explain how to monitor ingestion progress, set up failure notifications, and adjust schedules. They explain how Lakeflow Connect automatically creates jobs for each schedule and how you can add additional processing tasks after ingestion completes. They also cover schema enforcement, schema evolution, expectations, null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example. Each concept is introduced in prose, then shown in configuration or code with full comments, then interpreted. The goal is that you can read these notes alone and understand how to scale ingestion with multiple destinations while maintaining governance and operational control.

## Understanding multiple destinations

An ingestion pipeline is defined by an ingestion definition. The ingestion definition contains a list of objects. Each object maps a source table to a destination catalog and schema. When the list contains more than one object, the pipeline writes to multiple destinations. The source table can be the same in each object, or different. The destinations can be in the same catalog or different catalogs, and in the same schema or different schemas. The pipeline reads each source table once and writes the result to each destination. If two objects reference the same source table, the source is read once and the result is written to both destinations.

The following table compares a single-destination pipeline with a multiple-destination pipeline.

| Aspect | Single destination | Multiple destinations |
|---|---|---|
| Source reads | One per source table | One per source table |
| Destination writes | One per source table | One per destination object |
| Pipeline management | One pipeline | One pipeline |
| Governance | One table | Separate table per destination |
| Source load | Baseline | Same as single destination for the same source |
| Storage | One copy | One copy per destination |

The table shows that multiple destinations do not increase source load when the same source table is used. The source is read once. The writes increase, and storage increases because each destination stores its own copy. The governance benefit is that each destination is a separate table, so permissions and policies can differ.

Multiple destinations are useful in several scenarios. First, when different teams need isolated copies of the same data. Second, when the same data must be transformed differently for different consumers. For example, one destination might include only non-sensitive columns, while another includes all columns for a restricted team. Third, when the same data must land in different layers of the medallion architecture. For example, one destination might be a bronze table with raw data, and another might be a silver table with cleaned data. Fourth, when you are migrating from one schema to another and need both to be available during the transition.

## Configuring multiple destinations

You configure multiple destinations in the ingestion definition by listing multiple objects. Each object specifies a source table and a destination. The following YAML example shows a pipeline that ingests the `customers` table to two destinations.

```yaml
# Ingestion definition with two destinations.
# The same source table is ingested to two different catalogs and schemas.
# The pipeline reads the source once and writes to both destinations.
objects:
  # First destination: the sales.analytics schema.
  - table:
      # The source table is customers.
      source_table: customers
      # The destination catalog is sales.
      destination_catalog: sales
      # The destination schema is analytics.
      destination_schema: analytics
  # Second destination: the marketing.campaigns schema.
  - table:
      # The same source table is used again.
      source_table: customers
      # The destination catalog is marketing.
      destination_catalog: marketing
      # The destination schema is campaigns.
      destination_schema: campaigns
```

The example defines two objects. Both read the `customers` table. The first writes to `sales.analytics.customers`. The second writes to `marketing.campaigns.customers`. The pipeline reads the source once and writes to both destinations. Each destination is a separate Delta table in Unity Catalog. You can grant different permissions to each table. For example, the sales team can have `SELECT` on `sales.analytics.customers`, and the marketing team can have `SELECT` on `marketing.campaigns.customers`. Neither team needs access to the other table.

If you need to ingest the same source table to multiple destinations within the same schema, you must specify a custom `destination_table` name for each. Without a custom name, the destination table defaults to the source table name, and the second object would attempt to write to the same table as the first. The following YAML example shows how to use custom destination table names.

```yaml
# Ingestion definition with custom destination table names.
# The same source table is ingested twice into the same schema,
# but with different destination table names.
objects:
  # First destination: the sales.analytics.customers_full table.
  - table:
      source_table: customers
      destination_catalog: sales
      destination_schema: analytics
      # The custom destination table name avoids a collision with the next object.
      destination_table: customers_full
  # Second destination: the sales.analytics.customers_minimal table.
  - table:
      source_table: customers
      destination_catalog: sales
      destination_schema: analytics
      # This destination uses a different table name.
      destination_table: customers_minimal
```

The example ingests the `customers` table twice into the `sales.analytics` schema. The first destination is `sales.analytics.customers_full`. The second is `sales.analytics.customers_minimal`. Without the custom `destination_table` names, both objects would try to write to `sales.analytics.customers`, which would cause an error or overwrite. The custom names keep the destinations separate.

Once the pipeline is running, you can query each destination with SQL and PySpark. The following SQL example queries both destinations and compares their row counts.

```sql
-- Query the row count of the full customers destination.
-- The table is created by the pipeline in the sales.analytics schema.
SELECT COUNT(*) AS full_count
FROM sales.analytics.customers_full;

-- Query the row count of the minimal customers destination.
-- The table is created by the pipeline in the sales.analytics schema.
SELECT COUNT(*) AS minimal_count
FROM sales.analytics.customers_minimal;
```

The equivalent PySpark example reads both tables and computes their row counts.

```python
# Read the full customers destination.
df_full = spark.read.table("sales.analytics.customers_full")

# Read the minimal customers destination.
df_minimal = spark.read.table("sales.analytics.customers_minimal")

# Compute the row counts.
full_count = df_full.count()
minimal_count = df_minimal.count()

# Print the counts.
# If the pipeline is working correctly, both counts should be equal
# when both destinations ingest the same source rows.
print(f"Full count: {full_count}")
print(f"Minimal count: {minimal_count}")
```

The queries show that each destination is a standard Delta table. You can query it, join it, and transform it like any other table. The pipeline updates both destinations as changes arrive in the source.

## Governance and Unity Catalog implications

Each destination is a separate table in Unity Catalog. This means each destination has its own permissions, its own lineage, and its own schema. You can grant `SELECT` on one destination to one group and `SELECT` on another destination to a different group. You can apply row-level filters and column masks to one destination without affecting the other. This separation is the primary governance benefit of multiple destinations. It lets you tailor access to each consumer without duplicating the ingestion logic.

Schema enforcement and schema evolution apply per destination. If the source schema changes, the pipeline may evolve the schema of each destination if schema evolution is enabled. However, if the destinations have different column selection settings, their schemas may differ. For example, one destination might use `include_columns` to ingest only a subset of columns, while another ingests all columns. When the source adds a new column, the destination with `include_columns` does not ingest it unless the include list is updated. The destination without `include_columns` may ingest it if schema evolution is enabled. You should configure column selection and schema evolution per destination to match the governance requirements of each consumer.

Expectations are data quality rules that you define in Lakeflow Spark Declarative Pipelines. You can attach expectations to downstream tables that read from the destinations. Expectations can drop, fail, or warn on rows that violate a rule. If one destination is used for sensitive analytics, you might attach stricter expectations to the downstream tables that read from it. If another destination is used for exploratory analysis, you might use looser expectations. The pipeline itself does not enforce expectations; the transformations that read from the destinations do.

The following table summarizes the governance controls per destination.

| Control | Per destination | Notes |
|---|---|---|
| Permissions | Yes | Grant `SELECT` or `MODIFY` separately |
| Row-level filters | Yes | Apply to one destination without affecting others |
| Column masks | Yes | Mask sensitive columns in one destination |
| Column selection | Yes | Use `include_columns` or `exclude_columns` per object |
| Schema evolution | Yes | Enable or disable per destination |
| Expectations | Downstream | Defined in pipelines that read from the destination |

The table shows that most governance controls are per destination. This gives you fine-grained control over who can see what data. It also means you must configure each destination deliberately. A change to one destination does not automatically propagate to another.

## Monitoring ingestion progress

Once your pipelines are running, you monitor ingestion progress through the pipeline details page in the Databricks workspace. The page shows the status of each table, the number of rows ingested, the latency, and any errors. You can also query the pipeline status programmatically with the Databricks SDK. The following Python example shows how to retrieve the status of a pipeline and its latest updates.

```python
# Import the Databricks SDK for Python.
from databricks.sdk import WorkspaceClient

# Create a WorkspaceClient using the default authentication.
w = WorkspaceClient()

# Retrieve the pipeline by ID.
# The pipeline_id is returned when the pipeline is created.
pipeline = w.pipelines.get(pipeline_id="my-pipeline-id")

# Print the pipeline name and state.
print(f"Pipeline: {pipeline.name}")
print(f"State: {pipeline.state}")

# Retrieve the latest updates for the pipeline.
# Each update represents a run of the pipeline.
# The updates list contains the status of each update, including
# the start time, end time, and any errors.
updates = w.pipelines.list_updates(pipeline_id="my-pipeline-id")

# Print the status of the most recent update.
if updates:
    latest = updates[0]
    print(f"Latest update: {latest.update_id}")
    print(f"State: {latest.state}")
    print(f"Creation time: {latest.creation_time}")
```

The example retrieves the pipeline and its latest updates. The `state` field indicates whether the pipeline is running, idle, or failed. The updates list contains the history of runs. You can use this information to build monitoring dashboards or alerts.

You can also monitor the destination tables directly by querying them. The following SQL example checks the freshness of each destination by finding the maximum timestamp in a timestamp column.

```sql
-- Check the freshness of the full customers destination.
-- The maximum last_updated value indicates the most recent record ingested.
SELECT MAX(last_updated) AS latest_full
FROM sales.analytics.customers_full;

-- Check the freshness of the minimal customers destination.
SELECT MAX(last_updated) AS latest_minimal
FROM sales.analytics.customers_minimal;
```

The equivalent PySpark example reads both tables and computes the maximum timestamp.

```python
# Import the max function.
from pyspark.sql.functions import max

# Read the full customers destination.
df_full = spark.read.table("sales.analytics.customers_full")

# Compute the maximum last_updated value.
latest_full = df_full.agg(max("last_updated")).collect()[0][0]
print(f"Latest full: {latest_full}")

# Read the minimal customers destination.
df_minimal = spark.read.table("sales.analytics.customers_minimal")

# Compute the maximum last_updated value.
latest_minimal = df_minimal.agg(max("last_updated")).collect()[0][0]
print(f"Latest minimal: {latest_minimal}")
```

The queries show how to verify that each destination is receiving data. If one destination is stale, you can investigate the pipeline configuration for that object.

## Failure notifications and alerts

You can configure failure notifications on the pipeline so that you are alerted when an ingestion run fails. Notifications can be sent by email or by webhook. You configure them in the pipeline settings or in the pipeline definition. The following YAML example shows a notification configuration.

```yaml
# Notification configuration for a pipeline.
# The notifications block specifies who is alerted when the pipeline fails.
notifications:
  # Email notifications are sent to the listed addresses.
  - email:
      # The email addresses to notify on failure.
      on_failure:
        - data-engineering@example.com
  # Webhook notifications send an HTTP POST to the specified URL.
  - webhook:
      # The webhook URL to call on failure.
      on_failure:
        - https://hooks.example.com/pipeline-failure
```

The example configures email and webhook notifications for pipeline failures. When a run fails, the pipeline sends an email to the data engineering team and calls the webhook. You can use webhooks to integrate with incident management systems, chat applications, or custom alerting services. Notifications help you detect failures quickly and reduce the time to recovery.

## Adjusting schedules and jobs

You can adjust the pipeline schedule through the pipeline details page or programmatically. The schedule controls when and how frequently the pipeline runs. For CDC pipelines, the schedule is often continuous. For query-based and SaaS pipelines, the schedule is often a cron expression or a fixed interval. When you define a schedule, Lakeflow Connect automatically creates a job for that schedule. The job runs the pipeline. You can view the job in the Jobs section of the workspace and add additional processing tasks after ingestion completes.

The following YAML example shows a job definition that runs an ingestion pipeline and then runs a notebook to perform post-ingestion processing.

```yaml
# Job definition that runs an ingestion pipeline and a post-processing notebook.
resources:
  jobs:
    ingestion_and_processing:
      name: ingestion-and-processing-job
      tasks:
        # Task 1: run the ingestion pipeline.
        - task_key: run_ingestion
          pipeline_task:
            # The pipeline_id identifies the ingestion pipeline.
            pipeline_id: ${resources.pipelines.sales_pipeline.id}
        # Task 2: run a notebook after the ingestion completes.
        # The depends_on clause ensures that this task runs only after
        # the ingestion task succeeds.
        - task_key: post_process
          depends_on:
            - task_key: run_ingestion
          notebook_task:
            # The notebook path identifies the post-processing notebook.
            notebook_path: /Repos/data-engineering/post_process
```

The example defines a job with two tasks. The first task runs the ingestion pipeline. The second task runs a notebook only after the ingestion task succeeds. This pattern lets you chain additional processing, such as data quality checks, aggregation, or notifications, after ingestion completes. The job is managed by Databricks and can be scheduled or triggered manually.

## Best practices

Use a single pipeline with multiple destinations instead of multiple pipelines when the same source data is needed by more than one consumer. A single pipeline reads the source once, which reduces load on the source and simplifies monitoring.

Use custom destination table names when ingesting the same source table to multiple destinations within the same schema. Without custom names, the destinations collide.

Configure permissions per destination. Grant each team access only to the destination it needs. Use Unity Catalog to apply row-level filters and column masks where required.

Configure column selection per destination. If one consumer needs only a subset of columns, use `include_columns` for that destination. If another consumer needs all columns, use `exclude_columns` or no column selection.

Monitor each destination separately. Check row counts and freshness to ensure that every destination is receiving data. A pipeline can succeed for one destination and fail for another if the destinations have different configurations.

Set up failure notifications. Configure email or webhook notifications so that you are alerted when a pipeline run fails.

Use the auto-created jobs to add post-ingestion processing. Chain tasks that validate data quality, update downstream tables, or send notifications.

## Common mistakes and pitfalls

The most common mistake is creating multiple pipelines for the same source when a single pipeline with multiple destinations would suffice. Multiple pipelines read the source multiple times, increasing load and operational overhead.

A second mistake is forgetting to set a custom `destination_table` name when ingesting the same source table to multiple destinations within the same schema. Without a custom name, the destinations collide.

A third mistake is assuming that a schema change propagates to all destinations in the same way. If destinations have different column selection settings, the schema change may affect them differently. Review each destination after a source schema change.

A fourth mistake is not configuring permissions per destination. If you grant access to one destination, other destinations remain inaccessible unless you grant access separately. This is a feature, not a bug, but it can surprise you if you expect access to propagate.

A fifth mistake is ignoring failure notifications. If you do not configure notifications, you may not know that a pipeline failed until a consumer reports stale data.

A sixth mistake is not monitoring each destination. A pipeline can be running, but one destination may be lagging due to a configuration issue. Check row counts and freshness for each destination.

## Testing multiple destinations

Test multiple destinations by verifying that each destination receives the expected rows. You can test the configuration by running the pipeline on a small source and checking the row counts in each destination. The following example shows a test that writes a small DataFrame to two destinations and verifies the counts.

```python
from pyspark.sql import Row

# Create a small DataFrame with test data.
test_data = [
    Row(id=1, name="Alice", amount=100.0),
    Row(id=2, name="Bob", amount=200.0),
]
df_test = spark.createDataFrame(test_data)

# Write the DataFrame to two destinations.
# In a real pipeline, the ingestion definition writes to both destinations.
# Here we simulate the behavior by writing to two temporary tables.
df_test.write.mode("overwrite").saveAsTable("tmp.destination_full")
df_test.write.mode("overwrite").saveAsTable("tmp.destination_minimal")

# Read both destinations and verify the row counts.
full_count = spark.read.table("tmp.destination_full").count()
minimal_count = spark.read.table("tmp.destination_minimal").count()

# Assert that both destinations have the same number of rows.
assert full_count == 2, f"Full destination count failed: {full_count}"
assert minimal_count == 2, f"Minimal destination count failed: {minimal_count}"
```

The test verifies that both destinations receive the same rows. Run tests like this in your CI pipeline against a small local Spark session. For pipeline configuration, validate the YAML before deploying it.

## Performance considerations

A single pipeline with multiple destinations reads the source once and writes to each destination. The source read is not duplicated, so the load on the source is the same as a single-destination pipeline. The writes are duplicated, so the compute and storage costs increase with the number of destinations. Each destination is a separate Delta table, so each destination requires its own storage and its own compaction.

Use `include_columns` to reduce the volume of data written to each destination. If one destination needs only a few columns, excluding the rest reduces the write volume and storage cost for that destination.

Run `OPTIMIZE` on each destination periodically to compact small files. Each destination accumulates files independently, so each needs its own maintenance.

Monitor the pipeline duration. Writing to multiple destinations increases the time the pipeline takes to complete. If the pipeline is on a tight schedule, consider whether all destinations are necessary or whether some can be combined.
