## Lakeflow Connect connector types

Lakeflow Connect is a managed ingestion service in Azure Databricks that provides prebuilt connectors for common enterprise sources. Instead of writing custom extraction code with JDBC drivers or REST API clients, you configure a connection to a source, select the objects to ingest, and Lakeflow Connect handles the extraction, schema management, and loading into Unity Catalog tables. The service is part of the Lakeflow family, which also includes Lakeflow Spark Declarative Pipelines for transformation and orchestration. Lakeflow Connect is designed to reduce the operational burden of ingestion. It manages authentication, retries, checkpointing, and schema evolution. It integrates natively with Unity Catalog, so every table it creates is governed by the same access controls, lineage, and auditing that apply to the rest of your lakehouse.

The connectors are organized into three categories, each suited to different source types and ingestion requirements. SaaS connectors ingest data from enterprise applications such as Salesforce, HubSpot, Jira, and Workday by calling the source application's API. Database connectors use change data capture, often abbreviated as CDC, to continuously extract changes from relational databases such as MySQL, PostgreSQL, and SQL Server. Query-based connectors ingest data from databases by running scheduled queries against the source and tracking new or updated rows with a cursor column. Each category has different setup requirements, latency characteristics, and operational tradeoffs. Understanding these differences helps you choose the right connector for each source and design pipelines that are reliable, efficient, and governed.

These notes cover the three connector types from first principles. They explain what Lakeflow Connect is, how each connector category works, when to use each one, and how to configure them. They show code examples for configuring connectors with the Databricks SDK and for querying the resulting Unity Catalog tables with SQL and PySpark. They also cover schema enforcement, schema evolution, expectations, null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example that combines CDC and query-based connectors in a medallion architecture. The goal is that you can read these notes alone and understand how to choose and configure the right Lakeflow Connect connector for any supported source.

## What Lakeflow Connect is and why connector types matter

Lakeflow Connect is a fully managed ingestion service. You do not provision clusters or write extraction code. You create a connection that stores the credentials and endpoint for the source, then create a pipeline that specifies which objects to ingest and where to write them. Lakeflow Connect supports three categories of connectors, and each category uses a different mechanism to detect and extract changes. The mechanism determines the latency, the load on the source system, and the complexity of setup. Choosing the wrong category can lead to missed data, excessive load on the source, or unnecessary operational work.

The following table summarizes the three connector categories.

| Connector type | Description |
|---|---|
| SaaS connectors | Ingest data from enterprise SaaS applications including Salesforce, HubSpot, Jira, and Workday. The connector handles extraction directly through the source API. |
| Database connectors (CDC) | Ingest data from relational databases like MySQL, PostgreSQL, and SQL Server using change data capture. These connectors use an ingestion gateway to continuously extract changes from the source `binlog`. |
| Query-based connectors | Ingest data from databases by querying the source directly on a schedule, without requiring CDC configuration. These connectors use a cursor column—a monotonically increasing timestamp or integer column—to track which rows are new or updated since the last run. No gateway or staging storage is required. |

The table shows that the categories differ in how they detect changes. SaaS connectors use the application's API. Database CDC connectors read the database transaction log, often called the `binlog`. Query-based connectors run scheduled queries and track a cursor column. The rest of these notes explains each category in detail, starting with SaaS connectors, then CDC connectors, then query-based connectors. The notes focus more on the database connectors because they are the most common in enterprise data engineering and because the CDC and query-based approaches illustrate the key tradeoffs.

## SaaS connectors

SaaS connectors ingest data from cloud applications that expose a REST or SOAP API. The connector authenticates to the application, calls the API endpoints that correspond to the objects you selected, and writes the results to a Unity Catalog table. The connector handles pagination, rate limiting, and retries. It also handles incremental extraction when the API supports it, such as by using a `last_modified` timestamp or a change data capture endpoint. SaaS connectors are the simplest to configure because they do not require access to the underlying database or file system. You provide credentials, select objects, and the connector does the rest.

SaaS connectors are the right choice when your source is a supported application and you do not need real-time latency. The extraction frequency is configurable, often ranging from every few minutes to once a day. The load on the source application is determined by the API rate limits and the volume of data. Because the connector uses the application's API, it respects the application's security model. You grant the connector a service account or an API token with read access to the objects you want to ingest. The connector never bypasses the application's access controls.

The following example shows how to configure a Salesforce connection using the Databricks SDK for Python. The connection stores the credentials and endpoint. After the connection is created, you create a pipeline that ingests specific Salesforce objects into Unity Catalog tables.

```python
# Import the Databricks SDK for Python.
# The SDK provides a programmatic way to manage Databricks resources.
from databricks.sdk import WorkspaceClient
from databricks.sdk.service import catalog

# Create a WorkspaceClient using the default authentication.
# In a notebook, the client automatically uses the notebook's credentials.
# In a job, it uses the service principal or managed identity.
w = WorkspaceClient()

# Create a connection to Salesforce.
# The name is a unique identifier for the connection in Unity Catalog.
# The connection_type specifies the source system.
# The options dictionary holds the authentication details.
# For Salesforce, you typically provide an instance URL and a token.
# In production, store secrets in a secret scope and reference them here.
connection = w.connections.create(
    name="salesforce_connection",
    connection_type=catalog.ConnectionType.SALESFORCE,
    options={
        "instance_url": "https://mycompany.my.salesforce.com",
        "auth_type": "oauth2",
        "client_id": "your_client_id",
        "client_secret": "{{secrets/salesforce/client_secret}}"
    }
)

# After the connection is created, you create a pipeline that ingests
# Salesforce objects. The pipeline definition specifies the source
# connection, the objects to ingest, and the target Unity Catalog schema.
# The pipeline runs on a schedule and writes to Delta tables.
```

The example creates a connection to Salesforce. The connection is stored in Unity Catalog, so access to it is governed by Unity Catalog permissions. The `options` dictionary contains the authentication details. In production, you should use a secret scope to avoid hardcoding secrets. After the connection exists, you define a pipeline that references the connection and specifies the objects to ingest, such as `Account`, `Contact`, and `Opportunity`. The pipeline writes the data to Delta tables in the target schema.

Once the data is ingested, you query it with SQL or PySpark like any other Delta table. The following SQL example reads the ingested Salesforce accounts.

```sql
-- Query the ingested Salesforce accounts table.
-- The table is created by Lakeflow Connect in the salesforce_bronze schema.
-- The table is a Delta table registered in Unity Catalog.
SELECT
  Id AS account_id,
  Name AS account_name,
  Industry,
  AnnualRevenue
FROM salesforce_bronze.accounts
-- Filter to accounts with revenue above one million.
WHERE AnnualRevenue > 1000000
-- Order by revenue, largest first.
ORDER BY AnnualRevenue DESC;
```

The equivalent PySpark query reads the same table and applies the same filter.

```python
# Read the ingested Salesforce accounts table.
df_accounts = spark.read.table("salesforce_bronze.accounts")

# Filter to accounts with revenue above one million.
df_filtered = df_accounts.filter(df_accounts.AnnualRevenue > 1000000)

# Select the columns of interest and order by revenue.
df_result = df_filtered.select(
    "Id",
    "Name",
    "Industry",
    "AnnualRevenue"
).orderBy("AnnualRevenue", ascending=False)

# Display the result.
display(df_result)
```

SaaS connectors are simple to use, but they have limitations. The API may not expose every change, so incremental extraction may miss deletes or may not capture every update. The API rate limits may slow down extraction for large objects. If you need real-time or near-real-time ingestion, a CDC connector is a better choice, provided the source database supports it. If the source is a SaaS application, you must use the API, and the SaaS connector is the right tool.

## Database connectors with change data capture

Database connectors use change data capture to extract changes from relational databases. CDC reads the database transaction log, often called the `binlog` in MySQL or the write-ahead log in PostgreSQL and SQL Server. The log records every insert, update, and delete that the database applies. A CDC connector reads the log continuously and converts the changes into a stream of events. Because the log is the authoritative record of changes, CDC captures every change, including deletes, and does so with low latency. The source database is not queried directly, so the load on the database is minimal. The connector runs an ingestion gateway, which is a small agent that reads the log and forwards the changes to Databricks. The gateway is deployed in your environment, close to the source database, to reduce network latency and to keep the data within your network.

Database CDC connectors are the right choice when you need continuous, low-latency ingestion from a relational database and the database supports CDC. Supported databases include MySQL, PostgreSQL, and SQL Server. The connector handles initial snapshots and ongoing incremental changes. It creates a target Delta table in Unity Catalog and keeps it synchronized with the source. The connector also handles schema changes. If a column is added to the source table, the connector can evolve the target schema. If a column is dropped, the connector may mark it as nullable or stop ingesting it, depending on the configuration.

The following example shows how to configure a CDC connection and pipeline using the Databricks SDK. The connection stores the source database credentials and the gateway information. The pipeline specifies the tables to ingest and the target schema.

```python
# Import the Databricks SDK for Python.
from databricks.sdk import WorkspaceClient
from databricks.sdk.service import catalog

# Create a WorkspaceClient.
w = WorkspaceClient()

# Create a connection to a MySQL database with CDC.
# The connection_type is MYSQL.
# The options include the host, port, database name, and credentials.
# The gateway_id references an ingestion gateway that you deployed
# in your environment. The gateway reads the binlog and forwards changes.
connection = w.connections.create(
    name="mysql_cdc_connection",
    connection_type=catalog.ConnectionType.MYSQL,
    options={
        "host": "mysql.internal.example.com",
        "port": "3306",
        "database": "sales",
        "user": "cdc_user",
        "password": "{{secrets/mysql/cdc_password}}",
        "gateway_id": "my-ingestion-gateway"
    }
)

# Create a pipeline that ingests changes from the MySQL database.
# The pipeline specifies the source connection, the tables to ingest,
# and the target Unity Catalog schema.
# The pipeline runs continuously and applies changes to the target tables.
pipeline = w.pipelines.create(
    name="mysql_cdc_pipeline",
    connection_name="mysql_cdc_connection",
    target_schema="sales_bronze",
    tables=["customers", "orders", "order_items"]
)
```

The example creates a CDC connection and a pipeline. The connection references an ingestion gateway that you deploy in your environment. The gateway reads the MySQL binlog and forwards changes to Databricks. The pipeline ingests the `customers`, `orders`, and `order_items` tables and writes them to the `sales_bronze` schema. The pipeline runs continuously, so changes appear in the target tables within seconds or minutes of occurring in the source.

Once the data is ingested, you query it with SQL and PySpark. The target tables are Delta tables, so they support all Delta Lake features, including time travel and schema evolution. The following SQL example queries the ingested orders table.

```sql
-- Query the ingested orders table.
-- The table is created by the CDC pipeline in the sales_bronze schema.
-- The table contains the current state of the orders table in MySQL.
SELECT
  order_id,
  customer_id,
  order_date,
  total_amount
FROM sales_bronze.orders
-- Filter to orders placed in the last 30 days.
WHERE order_date >= current_date() - INTERVAL 30 DAYS
-- Order by order date, most recent first.
ORDER BY order_date DESC;
```

The equivalent PySpark query reads the same table and applies the same filter.

```python
# Import the functions needed for the filter.
from pyspark.sql.functions import col, current_date, date_sub

# Read the ingested orders table.
df_orders = spark.read.table("sales_bronze.orders")

# Filter to orders placed in the last 30 days.
df_recent = df_orders.filter(
    col("order_date") >= date_sub(current_date(), 30)
)

# Select the columns of interest and order by order date.
df_result = df_recent.select(
    "order_id",
    "customer_id",
    "order_date",
    "total_amount"
).orderBy(col("order_date").desc())

# Display the result.
display(df_result)
```

CDC connectors provide the lowest latency and the most complete change capture. They capture deletes, which query-based connectors may miss unless the source uses soft deletes. They also minimize load on the source database because they read the log rather than querying tables. The tradeoff is the setup complexity. You must deploy and maintain an ingestion gateway, and the source database must be configured to allow CDC. If you cannot deploy a gateway or the database does not support CDC, use a query-based connector.

## Query-based connectors

Query-based connectors ingest data from databases by running scheduled queries against the source. They do not use CDC or a gateway. Instead, they rely on a cursor column, which is a monotonically increasing timestamp or integer column in the source table. The connector records the highest value of the cursor column from the previous run and uses it to filter the next query. For example, if the cursor column is `last_updated` and the last run ingested rows up to `2026-01-15 10:00:00`, the next run queries for rows where `last_updated > '2026-01-15 10:00:00'`. This captures new rows and updates to existing rows, provided that the cursor column is updated whenever a row changes. Deletes are not captured unless the source uses soft deletes that set a flag or update the cursor column.

Query-based connectors are simpler to set up than CDC connectors. They do not require a gateway, and they do not require special database configuration. They run direct queries against the source tables on a schedule. The schedule is configurable, often ranging from every few minutes to once a day. The load on the source database is determined by the query complexity and the frequency. Because the connector queries the source directly, the query should be efficient. It should filter on the cursor column and select only the columns needed. It should also avoid expensive joins or aggregations that could slow down the source.

Query-based connectors are the right choice when the source database does not support CDC, when you cannot deploy a gateway, or when the latency requirement is measured in minutes or hours rather than seconds. They are also useful for sources that are read-only replicas, where CDC may not be available. They are not suitable for capturing deletes, and they may miss updates if the cursor column is not updated reliably. You should verify that the source application updates the cursor column on every change.

The following example shows how to configure a query-based connection and pipeline using the Databricks SDK. The connection stores the source database credentials. The pipeline specifies the query, the cursor column, and the target schema.

```python
# Import the Databricks SDK for Python.
from databricks.sdk import WorkspaceClient
from databricks.sdk.service import catalog

# Create a WorkspaceClient.
w = WorkspaceClient()

# Create a connection to a PostgreSQL database.
# The connection_type is POSTGRESQL.
# The options include the host, port, database name, and credentials.
# No gateway is required for query-based connectors.
connection = w.connections.create(
    name="postgres_query_connection",
    connection_type=catalog.ConnectionType.POSTGRESQL,
    options={
        "host": "postgres.internal.example.com",
        "port": "5432",
        "database": "sales",
        "user": "query_user",
        "password": "{{secrets/postgres/query_password}}"
    }
)

# Create a pipeline that ingests data using a query-based connector.
# The pipeline specifies the source connection, the query to run,
# the cursor column used to track new and updated rows,
# and the target Unity Catalog schema.
# The query should select only the columns needed and filter on the cursor column.
pipeline = w.pipelines.create(
    name="postgres_query_pipeline",
    connection_name="postgres_query_connection",
    target_schema="sales_bronze",
    query="""
        SELECT
            order_id,
            customer_id,
            order_date,
            total_amount,
            last_updated
        FROM orders
        WHERE last_updated > :last_cursor
    """,
    cursor_column="last_updated"
)
```

The example creates a query-based connection and pipeline. The connection stores the PostgreSQL credentials. The pipeline defines a query that selects orders updated after the last cursor value. The `cursor_column` parameter tells the connector which column to use to track progress. The connector stores the highest cursor value from each run and uses it in the next run. The query uses a named parameter `:last_cursor` that the connector replaces with the stored value. The pipeline runs on a schedule and writes the results to the `sales_bronze` schema.

Once the data is ingested, you query it with SQL and PySpark. The following SQL example queries the ingested orders table.

```sql
-- Query the ingested orders table.
-- The table is created by the query-based pipeline in the sales_bronze schema.
-- The table contains rows that were new or updated since the last run.
SELECT
  order_id,
  customer_id,
  order_date,
  total_amount,
  last_updated
FROM sales_bronze.orders
-- Filter to orders updated in the last 24 hours.
WHERE last_updated >= current_timestamp() - INTERVAL 24 HOURS
-- Order by last_updated, most recent first.
ORDER BY last_updated DESC;
```

The equivalent PySpark query reads the same table and applies the same filter.

```python
# Import the functions needed for the filter.
from pyspark.sql.functions import col, current_timestamp, expr

# Read the ingested orders table.
df_orders = spark.read.table("sales_bronze.orders")

# Filter to orders updated in the last 24 hours.
df_recent = df_orders.filter(
    col("last_updated") >= current_timestamp() - expr("INTERVAL 24 HOURS")
)

# Select the columns of interest and order by last_updated.
df_result = df_recent.select(
    "order_id",
    "customer_id",
    "order_date",
    "total_amount",
    "last_updated"
).orderBy(col("last_updated").desc())

# Display the result.
display(df_result)
```

Query-based connectors are simpler than CDC connectors but have limitations. They do not capture deletes unless the source uses soft deletes. They may miss updates if the cursor column is not updated on every change. They put load on the source database because they run queries directly. They are best for sources where CDC is not available and where the latency requirement is minutes or hours. If you need deletes and low latency, use CDC. If you need simplicity and can tolerate the limitations, use query-based.

## Comparing connector types

The three connector types differ in their mechanism, latency, setup complexity, and suitability. The following table compares them across several dimensions.

| Dimension | SaaS connectors | Database CDC connectors | Query-based connectors |
|---|---|---|---|
| Source type | SaaS applications | Relational databases | Relational databases |
| Mechanism | API calls | Binlog / transaction log | Scheduled queries with cursor |
| Latency | Minutes to hours | Seconds to minutes | Minutes to hours |
| Captures deletes | Depends on API | Yes | No (unless soft deletes) |
| Gateway required | No | Yes | No |
| Load on source | API rate limits | Minimal (reads log) | Query load |
| Setup complexity | Low | High | Medium |
| Use case | Salesforce, HubSpot, Jira | MySQL, PostgreSQL, SQL Server | Databases without CDC |

The table shows that CDC connectors provide the lowest latency and the most complete change capture, but they require a gateway and database configuration. Query-based connectors are simpler but do not capture deletes and put query load on the source. SaaS connectors are specific to applications and use the application's API. The choice depends on the source and the requirements. If the source is a supported SaaS application, use a SaaS connector. If the source is a relational database that supports CDC and you need low latency, use a CDC connector. If the database does not support CDC or you cannot deploy a gateway, use a query-based connector.

## Schema enforcement, evolution, and expectations

Lakeflow Connect integrates with Delta Lake and Unity Catalog to enforce schema and handle schema evolution. When a connector ingests data, it writes to a Delta table. Delta Lake enforces the table schema. If the source schema changes, such as a new column being added, the connector can evolve the target schema if schema evolution is enabled. Schema evolution adds the new column to the target table. Existing rows get null in the new column. If a column is dropped from the source, the connector may leave the column in the target table and stop populating it, or it may fail depending on the configuration. You should decide how to handle schema changes before enabling a connector.

Expectations are data quality rules that you can define in Lakeflow Spark Declarative Pipelines. If you use Lakeflow Connect together with Lakeflow Spark Declarative Pipelines, you can attach expectations to the tables that the connector writes to. Expectations can drop, fail, or warn on rows that violate a rule. For example, you can define an expectation that `order_id` is not null. If a row violates the expectation, the pipeline can drop it before it reaches downstream tables. Expectations help you maintain data quality at the point of ingestion. They are not a replacement for schema enforcement, but they complement it.

The following example shows a Lakeflow Spark Declarative Pipeline that reads from a table ingested by Lakeflow Connect and applies an expectation.

```python
import dlt
from pyspark.sql.functions import col

# Define a silver table that reads from the bronze table ingested by Lakeflow Connect.
# The @dlt.expect_or_drop decorator defines an expectation that drops rows
# where the amount is null or negative.
@dlt.table(
    name="silver_orders",
    comment="Cleaned orders from the bronze layer"
)
@dlt.expect_or_drop("valid_amount", "amount > 0")
def silver_orders():
    return (dlt.read("sales_bronze.orders")
            .filter(col("amount").isNotNull()))
```

The example defines a silver table that reads from the bronze orders table. The expectation `valid_amount` drops rows where the amount is not positive. This ensures that only valid orders reach the silver layer.

## Null handling, case sensitivity, and time zones

Null handling is important for ingestion. Lakeflow Connect connectors preserve nulls from the source. If a source column is null, the target column is null, provided the target column is nullable. If the target column is non-nullable, the write fails. You should ensure that non-nullable columns in the target have a default or that the source does not produce nulls for those columns. If the source uses empty strings to represent missing values, you may want to convert them to nulls in a downstream transformation. Lakeflow Connect does not automatically convert empty strings to nulls.

Case sensitivity affects string comparisons. By default, Spark's string comparisons are case-sensitive. If the source has inconsistent casing in a key column, joins and merges may not match rows that should match. You can normalize the case in a downstream transformation or use a case-insensitive collation if the table is configured for one. Unity Catalog supports collations at the column level. Be aware that applying a function to a column can prevent predicate pushdown.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. Lakeflow Connect writes timestamps in UTC. When you query the data, the session time zone determines how the timestamps are displayed. To avoid confusion, set the session time zone explicitly at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Use timestamp literals with explicit offsets when comparing to timestamps. Store timestamps in UTC and convert to local time only for display.

## An end-to-end example

Consider a scenario where you ingest data from two sources: a MySQL database using a CDC connector and a Salesforce application using a SaaS connector. You want to build a medallion architecture with bronze, silver, and gold layers. The bronze layer contains the raw ingested data. The silver layer cleans and conforms the data. The gold layer aggregates the data for analytics.

The following example shows a Lakeflow Spark Declarative Pipeline that reads from both bronze tables, joins them, and produces a gold table.

```python
import dlt
from pyspark.sql.functions import col, sum, count

# Define a silver table for MySQL orders.
# The bronze table is ingested by the CDC connector.
# The silver table filters out invalid orders.
@dlt.table(
    name="silver_orders",
    comment="Cleaned orders from MySQL"
)
@dlt.expect_or_drop("valid_amount", "total_amount > 0")
def silver_orders():
    return (dlt.read("sales_bronze.orders")
            .filter(col("total_amount").isNotNull()))

# Define a silver table for Salesforce accounts.
# The bronze table is ingested by the SaaS connector.
@dlt.table(
    name="silver_accounts",
    comment="Cleaned accounts from Salesforce"
)
def silver_accounts():
    return (dlt.read("salesforce_bronze.accounts")
            .select(
                col("Id").alias("account_id"),
                col("Name").alias("account_name"),
                col("Industry"),
                col("AnnualRevenue")
            ))

# Define a gold table that joins orders and accounts and aggregates by industry.
@dlt.table(
    name="gold_revenue_by_industry",
    comment="Total revenue by industry"
)
def gold_revenue_by_industry():
    # Read the silver tables.
    orders = dlt.read("silver_orders")
    accounts = dlt.read("silver_accounts")
    # Join orders to accounts on customer_id.
    joined = orders.join(accounts, orders.customer_id == accounts.account_id, "inner")
    # Aggregate revenue by industry.
    return (joined.groupBy("Industry")
            .agg(
                sum("total_amount").alias("total_revenue"),
                count("*").alias("order_count")
            ))
```

The example defines three tables: two silver tables and one gold table. The silver orders table reads from the MySQL bronze table and filters out invalid orders. The silver accounts table reads from the Salesforce bronze table and renames columns. The gold table joins the two silver tables and aggregates revenue by industry. The pipeline is declarative. The framework handles orchestration, dependencies, and data quality. All tables are in Unity Catalog and are governed.

## Best practices

Choose the connector type based on the source and the latency requirement. Use SaaS connectors for supported applications, CDC connectors for relational databases that support CDC and require low latency, and query-based connectors for databases without CDC or when a gateway cannot be deployed.

Verify that the source supports the connector. CDC requires that the database has binary logging enabled and that the connector user has the necessary permissions. Query-based connectors require a reliable cursor column that is updated on every change.

Use a dedicated user for ingestion with the minimum permissions required. For CDC, the user needs replication permissions. For query-based, the user needs read access to the source tables.

Store credentials in a secret scope. Do not hardcode credentials in connection definitions. Unity Catalog connections can reference secrets.

Enable schema evolution deliberately. Schema changes in the source can propagate to the target. Communicate changes to downstream consumers and test the impact.

Define expectations for data quality. Use Lakeflow Spark Declarative Pipelines to attach expectations to the tables that connectors write to. Expectations catch invalid rows early.

Monitor ingestion pipelines. Track metrics such as rows ingested, latency, and errors. Set up alerts for failures and for unusual patterns.

Use partitioning and clustering on the target tables to improve query performance. Choose columns that are commonly used in filters and joins.

## Common mistakes and pitfalls

The most common mistake is choosing the wrong connector type. Using a query-based connector when CDC is available can miss deletes and add unnecessary load to the source. Using a CDC connector when the database does not support it will fail.

A second mistake is not verifying that the cursor column is updated on every change. If the source application does not update the cursor column when a row changes, the query-based connector will miss the update.

A third mistake is forgetting to deploy the ingestion gateway for CDC connectors. The gateway must be deployed in your environment and must have network access to both the source database and Databricks.

A fourth mistake is not handling schema changes. If the source schema changes and schema evolution is not enabled, the ingestion pipeline will fail. Enable schema evolution and test it with a small change before relying on it in production.

A fifth mistake is not setting the session time zone. Timestamps are stored in UTC. If you compare them to local time without converting, you may get incorrect results.

A sixth mistake is ignoring case sensitivity. String comparisons are case-sensitive by default. Normalize casing or use a collation if needed.

A seventh mistake is not monitoring the pipeline. Ingestion pipelines can fail silently if not monitored. Set up alerts for failures and for latency spikes.

## Testing ingestion logic

Test ingestion logic with a small source and a target table that you can inspect. For CDC connectors, you can simulate changes in the source and verify that they appear in the target. For query-based connectors, you can insert rows with different cursor values and verify that the connector ingests the correct rows. The following example shows a test for a query-based connector's cursor logic.

```python
from pyspark.sql import Row

# Create a small DataFrame with test data.
# The cursor column is last_updated.
test_data = [
    Row(id=1, value="A", last_updated="2026-01-15 10:00:00"),
    Row(id=2, value="B", last_updated="2026-01-15 11:00:00"),
    Row(id=3, value="C", last_updated="2026-01-15 12:00:00"),
]
df_test = spark.createDataFrame(test_data)

# Simulate the cursor logic.
# The last cursor value from the previous run is 11:00:00.
last_cursor = "2026-01-15 11:00:00"

# Filter to rows updated after the last cursor.
df_new = df_test.filter(df_test.last_updated > last_cursor)

# Assert that only the row with 12:00:00 is returned.
assert df_new.count() == 1, f"Expected 1 row, got {df_new.count()}"
assert df_new.collect()[0].id == 3, "Expected row with id 3"
```

Run tests like this in your CI pipeline against a small local Spark session. For connectors, you can also use the Databricks SDK to create a test pipeline and verify that it writes the expected data.

## Performance considerations

Performance depends on the connector type and the volume of data. SaaS connectors are limited by the API rate limits. If the source has a large volume of data, the initial snapshot may take a long time. Incremental extraction is faster because it only fetches changes.

CDC connectors have minimal impact on the source database because they read the transaction log. The ingestion gateway must be sized appropriately for the volume of changes. The gateway should be deployed close to the source database to reduce network latency.

Query-based connectors put query load on the source database. The query should be efficient. Filter on the cursor column and select only the needed columns. Avoid joins and aggregations in the source query. Schedule the connector at a frequency that balances latency with source load.

Target table performance depends on file size and partitioning. Lakeflow Connect writes to Delta tables. It may create many small files during incremental ingestion. Run `OPTIMIZE` periodically to compact small files. Use partitioning or liquid clustering on columns that are commonly used in filters.

Use `availableNow` trigger for scheduled pipelines to process all available data and stop. This is more cost-effective than a continuously running cluster.

## Summary

Lakeflow Connect provides three categories of managed connectors: SaaS connectors, database CDC connectors, and query-based connectors. SaaS connectors ingest data from enterprise applications through the source API. They are simple to configure and respect the application's security model. Database CDC connectors read the database transaction log to capture every change with low latency. They require an ingestion gateway and database configuration. Query-based connectors run scheduled queries against the source and track new or updated rows using a cursor column. They are simpler than CDC but do not capture deletes and put query load on the source.

The choice of connector depends on the source and the latency requirement. Use SaaS connectors for supported applications, CDC connectors for relational databases that support CDC and require low latency, and query-based connectors for databases without CDC or when a gateway cannot be deployed. Each connector writes to Delta tables in Unity Catalog, so the data is governed by Unity Catalog access controls, lineage, and auditing.

Schema enforcement, schema evolution, and expectations apply to all connectors. Delta Lake enforces the table schema. Schema evolution adds new columns during ingestion. Expectations in Lakeflow Spark Declarative Pipelines validate data quality and drop or flag invalid rows. Null handling, case sensitivity, and time zones affect ingestion and querying. Set the session time zone explicitly, normalize string casing, and handle nulls deliberately.

Best practices include choosing the right connector type, verifying source support, using dedicated users with minimal permissions, storing credentials in secret scopes, enabling schema evolution deliberately, defining expectations, and monitoring pipelines. Common mistakes include choosing the wrong connector, not updating the cursor column, forgetting the gateway, ignoring schema changes, and not setting the session time zone.

Test ingestion logic with small datasets and verify cursor behavior. Performance depends on the connector type and the volume of data. Optimize source queries, size the gateway appropriately, and compact small files in the target tables.

By understanding the three connector types and their tradeoffs, you can build reliable, governed ingestion pipelines that bring data from diverse sources into Unity Catalog with the latency and completeness your organization requires.
