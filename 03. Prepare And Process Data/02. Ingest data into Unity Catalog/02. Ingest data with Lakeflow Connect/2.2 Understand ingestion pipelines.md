## Understand ingestion pipelines

An ingestion pipeline is a configured workflow that moves data from an external source system into a target table in Unity Catalog. In Lakeflow Connect, a pipeline is not a piece of code you write and maintain. It is a declarative definition that specifies where the data comes from, which objects to extract, where to write them, and how often to run. Lakeflow Connect handles the extraction, the schema management, the checkpointing, and the loading. You provide the connection details and the ingestion definition, and the service does the rest. This approach reduces the amount of custom code in your pipelines and makes ingestion a configuration task rather than a development task.

Each pipeline consists of three core components. The connection stores the credentials and endpoint information for the source system. You create a connection once and reuse it across multiple pipelines that read from the same source. The ingestion definition specifies which tables or objects to extract and their destination catalogs and schemas in Unity Catalog. The pipeline schedule controls when and how frequently data flows from source to destination. These three components are the building blocks of every Lakeflow Connect pipeline, regardless of the connector type. Understanding how they fit together is the first step toward configuring pipelines that are reliable, maintainable, and governed.

When you create an ingestion pipeline for a database connector such as SQL Server, Lakeflow Connect also creates an ingestion gateway. The gateway is a small agent that runs in your environment, close to the source database. It continuously extracts change data from the source and stages it for processing. For SaaS connectors such as Salesforce, the connector handles extraction directly through the application's API, and no separate gateway is required. This difference in architecture affects the setup complexity, the network requirements, and the operational burden of maintaining the pipeline. Database connectors require more setup because of the gateway, but they provide lower latency and capture deletes. SaaS connectors are simpler to configure but depend on the application's API and its rate limits.

These notes cover ingestion pipelines from first principles. They explain the three core components, how they work together, and how to configure them. They explain the role of the ingestion gateway for database connectors and why it is not needed for SaaS connectors. They show code examples for creating connections, defining ingestion pipelines, and querying the resulting Unity Catalog tables. They also cover schema enforcement, schema evolution, expectations, null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example that ties the concepts together. The goal is that you can read these notes alone and understand how to build and operate ingestion pipelines with Lakeflow Connect.

## The three core components of an ingestion pipeline

Every Lakeflow Connect pipeline is built from three components: a connection, an ingestion definition, and a schedule. The connection is the reusable credential store. The ingestion definition is the mapping from source objects to target tables. The schedule is the timing and frequency of extraction. These components are separate so that you can reuse a connection across many pipelines and change the schedule without reconfiguring the source credentials. The separation also makes governance easier. Connections and pipelines are Unity Catalog objects, so access to them is controlled by Unity Catalog permissions.

### Connections

A connection is a Unity Catalog object that stores the credentials and endpoint information for a source system. It is created once and referenced by one or more ingestion pipelines. The connection holds the host, port, database name, authentication method, and any other parameters needed to reach the source. It does not hold the data itself. It holds the information needed to get the data. Because connections are Unity Catalog objects, they are governed by Unity Catalog permissions. Only users with permission to use a connection can create pipelines that reference it. This prevents unauthorized access to source systems.

The following table summarizes the information a connection typically holds for different source types.

| Source type | Connection fields | Authentication |
|---|---|---|
| SaaS application | Instance URL, API version | OAuth token, API key |
| Relational database (CDC) | Host, port, database, gateway ID | Username, password |
| Relational database (query-based) | Host, port, database | Username, password |

The table shows that the connection fields vary by source type. A SaaS connection needs the application's URL and API version. A database connection needs the host, port, and database name. A CDC connection also needs the gateway ID, which identifies the ingestion gateway that reads the transaction log. A query-based connection does not need a gateway because it runs queries directly against the source.

### Ingestion definitions

An ingestion definition specifies which source objects to extract and where to write them. It maps each source table or object to a target table in Unity Catalog. The target table is specified with the three-level namespace: catalog, schema, and table. The ingestion definition also specifies how to handle schema changes, whether to capture deletes, and any transformations that should be applied during ingestion. For database connectors, the ingestion definition lists the tables to ingest. For SaaS connectors, it lists the objects or API endpoints to extract.

The ingestion definition is declarative. You describe what you want, not how to get it. Lakeflow Connect determines the most efficient way to extract the data. For CDC connectors, it reads the transaction log and applies changes to the target. For query-based connectors, it runs the query with the cursor filter and writes the results. For SaaS connectors, it calls the API and paginates through the results. The ingestion definition does not contain extraction code. It contains the configuration that the service uses to generate the extraction plan.

### Pipeline schedules

The pipeline schedule controls when and how frequently the pipeline runs. A schedule can be a cron expression, a fixed interval, or a continuous trigger. For CDC connectors, the pipeline often runs continuously to capture changes with low latency. For query-based connectors, the pipeline runs on a schedule, such as every hour or every day. For SaaS connectors, the pipeline runs on a schedule that respects the API rate limits and the freshness requirement. The schedule determines the latency of the data in the target table. A more frequent schedule reduces latency but increases load on the source and the compute cost. A less frequent schedule reduces cost but increases the time between when data changes in the source and when it appears in the target.

The following table compares schedule options.

| Schedule type | Latency | Cost | Typical use |
|---|---|---|---|
| Continuous | Seconds | High | CDC pipelines that need near-real-time data |
| Fixed interval (for example, every 15 minutes) | Minutes | Medium | Query-based or SaaS pipelines with moderate freshness needs |
| Cron (for example, daily at midnight) | Hours | Low | Batch pipelines that run once a day |

The table shows that the schedule is a tradeoff between latency and cost. Choose the schedule that matches the freshness requirement of the downstream consumers. If the data is used for real-time dashboards, use a continuous or short-interval schedule. If the data is used for daily reports, a daily schedule is sufficient.

## How ingestion pipelines differ by connector type

The three components of a pipeline are the same for all connector types, but the architecture differs. The differences affect the setup, the network requirements, and the operational burden. The following sections explain how pipelines work for SaaS connectors and for database connectors, including the role of the ingestion gateway.

### SaaS connectors: direct API extraction

A SaaS connector extracts data directly from the application's API. The connection stores the instance URL and the authentication token. The ingestion definition lists the objects to extract, such as `Account`, `Contact`, and `Opportunity` in Salesforce. The pipeline schedule determines how often the connector calls the API. There is no gateway and no staging storage. The connector calls the API, receives the data, and writes it to the target Delta table in Unity Catalog.

The advantage of SaaS connectors is simplicity. You do not need to deploy or maintain any infrastructure in your environment. The connector runs entirely within the Databricks platform. The disadvantage is that the connector depends on the application's API. The API may have rate limits that slow down extraction. It may not expose deletes or may expose them only through a separate endpoint. It may change without notice, requiring the connector to be updated. Despite these limitations, SaaS connectors are the right choice for supported applications because they eliminate the need for custom API code.

The following example shows how to create a Salesforce connection and an ingestion pipeline using the Databricks SDK for Python.

```python
# Import the Databricks SDK for Python.
from databricks.sdk import WorkspaceClient
from databricks.sdk.service import catalog

# Create a WorkspaceClient using the default authentication.
w = WorkspaceClient()

# Create a connection to Salesforce.
# The name is a unique identifier in Unity Catalog.
# The connection_type specifies the source system.
# The options dictionary holds the authentication details.
# In production, store secrets in a secret scope and reference them here.
connection = w.connections.create(
    name="salesforce_connection",
    connection_type=catalog.ConnectionType.SALESFORCE,
    options={
        "instance_url": "https://mycompany.my.salesforce.com",
        "auth_type": "oauth2",
        "client_id": "your_client_id",
        "client_secret": "{{secrets/salesforce/client_secret}}"
    }
)

# Create an ingestion pipeline that uses the connection.
# The pipeline specifies the source connection, the objects to ingest,
# and the target Unity Catalog schema.
# The pipeline runs on a schedule and writes to Delta tables.
pipeline = w.pipelines.create(
    name="salesforce_ingestion_pipeline",
    connection_name="salesforce_connection",
    target_schema="salesforce_bronze",
    objects=["Account", "Contact", "Opportunity"]
)
```

The example creates a connection and a pipeline. The connection stores the Salesforce credentials. The pipeline ingests the `Account`, `Contact`, and `Opportunity` objects into the `salesforce_bronze` schema. The pipeline runs on the default schedule. You can change the schedule after creation.

### Database connectors: the ingestion gateway

A database connector uses an ingestion gateway to extract changes from the source database. The gateway is a small agent that runs in your environment, close to the source database. It reads the database transaction log, often called the `binlog` in MySQL or the write-ahead log in PostgreSQL and SQL Server. The log records every insert, update, and delete. The gateway converts the changes into a stream and forwards them to Databricks. The connector then writes the changes to the target Delta table in Unity Catalog. The gateway is not needed for SaaS connectors because SaaS applications expose changes through their APIs. It is needed for database connectors because databases do not expose their transaction logs over the network by default, and even if they did, reading the log requires special permissions and configuration.

The gateway has several responsibilities. It reads the transaction log continuously. It tracks the position in the log so that it can resume after a restart. It stages the changes in a local store before forwarding them. It handles network interruptions by retrying. It also performs the initial snapshot, which reads the full contents of the source tables before starting incremental extraction. The initial snapshot can take a long time for large tables. The gateway must have network access to both the source database and Databricks. It must have a user account with the permissions needed to read the transaction log. For MySQL, this means the `REPLICATION SLAVE` and `REPLICATION CLIENT` privileges. For PostgreSQL, it means the `REPLICATION` role and access to the replication slot.

The following example shows how to create a CDC connection and pipeline for SQL Server using the Databricks SDK. The connection references the gateway.

```python
# Import the Databricks SDK for Python.
from databricks.sdk import WorkspaceClient
from databricks.sdk.service import catalog

# Create a WorkspaceClient.
w = WorkspaceClient()

# Create a connection to SQL Server with CDC.
# The connection_type is SQLSERVER.
# The options include the host, port, database, and credentials.
# The gateway_id references an ingestion gateway deployed in your environment.
connection = w.connections.create(
    name="sqlserver_cdc_connection",
    connection_type=catalog.ConnectionType.SQLSERVER,
    options={
        "host": "sqlserver.internal.example.com",
        "port": "1433",
        "database": "SalesDB",
        "user": "cdc_user",
        "password": "{{secrets/sqlserver/cdc_password}}",
        "gateway_id": "my-sqlserver-gateway"
    }
)

# Create a pipeline that ingests changes from SQL Server.
# The pipeline specifies the source connection, the tables to ingest,
# and the target Unity Catalog schema.
pipeline = w.pipelines.create(
    name="sqlserver_cdc_pipeline",
    connection_name="sqlserver_cdc_connection",
    target_schema="sales_bronze",
    tables=["dbo.Customers", "dbo.Orders", "dbo.OrderItems"]
)
```

The example creates a CDC connection and pipeline. The connection references the gateway. The pipeline ingests the `Customers`, `Orders`, and `OrderItems` tables from SQL Server into the `sales_bronze` schema. The pipeline runs continuously to capture changes with low latency.

Once the data is ingested, you query it with SQL and PySpark. The following SQL example reads the ingested orders.

```sql
-- Query the ingested orders table.
-- The table is created by the CDC pipeline in the sales_bronze schema.
SELECT
  order_id,
  customer_id,
  order_date,
  total_amount
FROM sales_bronze.orders
-- Filter to orders placed in the last 30 days.
WHERE order_date >= current_date() - INTERVAL 30 DAYS
-- Order by order date, most recent first.
ORDER BY order_date DESC;
```

The equivalent PySpark query reads the same table and applies the same filter.

```python
# Import the functions needed for the filter.
from pyspark.sql.functions import col, current_date, date_sub

# Read the ingested orders table.
df_orders = spark.read.table("sales_bronze.orders")

# Filter to orders placed in the last 30 days.
df_recent = df_orders.filter(
    col("order_date") >= date_sub(current_date(), 30)
)

# Select the columns of interest and order by order date.
df_result = df_recent.select(
    "order_id",
    "customer_id",
    "order_date",
    "total_amount"
).orderBy(col("order_date").desc())

# Display the result.
display(df_result)
```

The gateway is the key difference between database connectors and SaaS connectors. It adds setup complexity because you must deploy and maintain it. But it provides lower latency and captures deletes, which SaaS connectors may not. If you need continuous ingestion from a relational database, the gateway is necessary. If you can tolerate the latency and limitations of the API, a SaaS connector is simpler.

## Configuring an ingestion pipeline

Configuring a pipeline involves three steps: creating the connection, defining the ingestion definition, and setting the schedule. The steps can be performed through the Databricks UI or programmatically with the Databricks SDK. The following sections describe each step.

### Creating a connection

A connection is created once and reused across pipelines. To create a connection, you provide the source type, the endpoint information, and the credentials. The credentials should be stored in a secret scope, not hardcoded. Unity Catalog connections can reference secrets using the `{{secrets/scope/key}}` syntax. The following example shows how to create a connection for a PostgreSQL database.

```python
# Import the Databricks SDK.
from databricks.sdk import WorkspaceClient
from databricks.sdk.service import catalog

# Create a WorkspaceClient.
w = WorkspaceClient()

# Create a connection to PostgreSQL.
# The connection_type is POSTGRESQL.
# The options include the host, port, database, and credentials.
# The password references a secret scope instead of a hardcoded value.
connection = w.connections.create(
    name="postgres_connection",
    connection_type=catalog.ConnectionType.POSTGRESQL,
    options={
        "host": "postgres.internal.example.com",
        "port": "5432",
        "database": "sales",
        "user": "query_user",
        "password": "{{secrets/postgres/query_password}}"
    }
)
```

The example creates a connection to PostgreSQL. The connection can be used by multiple pipelines. If the credentials change, you update the connection, and all pipelines that reference it use the new credentials.

### Defining the ingestion definition

The ingestion definition specifies which objects to extract and where to write them. For a database connector, you list the tables. For a SaaS connector, you list the objects. You also specify the target schema in Unity Catalog. The following example shows how to define an ingestion pipeline for a database connector.

```python
# Create an ingestion pipeline.
# The pipeline references the connection created earlier.
# The target_schema specifies the Unity Catalog schema where tables are written.
# The tables list names the source tables to ingest.
pipeline = w.pipelines.create(
    name="postgres_ingestion_pipeline",
    connection_name="postgres_connection",
    target_schema="sales_bronze",
    tables=["public.customers", "public.orders", "public.order_items"]
)
```

The example creates a pipeline that ingests three tables from PostgreSQL into the `sales_bronze` schema. The target tables are created automatically if they do not exist. If they exist, the pipeline updates them according to the ingestion mode.

### Setting the pipeline schedule

The schedule controls when and how frequently the pipeline runs. You can set the schedule when you create the pipeline or update it later. The schedule is specified as a cron expression or a fixed interval. The following example shows how to update a pipeline to run every hour.

```python
# Update the pipeline to run every hour.
# The schedule is specified as a cron expression.
# The cron expression "0 0 * * * *" means every hour on the hour.
w.pipelines.update(
    pipeline_id="postgres_ingestion_pipeline",
    schedule={
        "quartz_cron_expression": "0 0 * * * *",
        "timezone_id": "UTC"
    }
)
```

The example sets the schedule to run every hour in UTC. The time zone should be set explicitly to avoid ambiguity. If the source data is in a different time zone, the schedule should account for that.

## Schema enforcement, evolution, and expectations

Lakeflow Connect integrates with Delta Lake and Unity Catalog to enforce schema and handle schema evolution. When a connector ingests data, it writes to a Delta table. Delta Lake enforces the table schema. If the source schema changes, such as a new column being added, the connector can evolve the target schema if schema evolution is enabled. Schema evolution adds the new column to the target table. Existing rows get null in the new column. If a column is dropped from the source, the connector may leave the column in the target table and stop populating it, or it may fail depending on the configuration. You should decide how to handle schema changes before enabling a connector.

Expectations are data quality rules that you can define in Lakeflow Spark Declarative Pipelines. If you use Lakeflow Connect together with Lakeflow Spark Declarative Pipelines, you can attach expectations to the tables that the connector writes to. Expectations can drop, fail, or warn on rows that violate a rule. For example, you can define an expectation that `order_id` is not null. If a row violates the expectation, the pipeline can drop it before it reaches downstream tables. Expectations help you maintain data quality at the point of ingestion. They are not a replacement for schema enforcement, but they complement it.

The following table summarizes the schema and quality controls.

| Control | Mechanism | Effect |
|---|---|---|
| Schema enforcement | Delta Lake write | Rejects writes that do not match the table schema |
| Schema evolution | Connector option | Adds new columns to the target table during ingestion |
| Expectations | Lakeflow Spark Declarative Pipelines | Drops, fails, or warns on rows that violate a rule |

The table shows that schema enforcement and evolution are about structure, while expectations are about data quality. Use schema enforcement to protect the table, schema evolution to handle legitimate schema changes, and expectations to validate business rules.

## Null handling, case sensitivity, and time zones

Null handling is important for ingestion. Lakeflow Connect connectors preserve nulls from the source. If a source column is null, the target column is null, provided the target column is nullable. If the target column is non-nullable, the write fails. You should ensure that non-nullable columns in the target have a default or that the source does not produce nulls for those columns. If the source uses empty strings to represent missing values, you may want to convert them to nulls in a downstream transformation. Lakeflow Connect does not automatically convert empty strings to nulls.

Case sensitivity affects string comparisons. By default, Spark's string comparisons are case-sensitive. If the source has inconsistent casing in a key column, joins and merges may not match rows that should match. You can normalize the case in a downstream transformation or use a case-insensitive collation if the table is configured for one. Unity Catalog supports collations at the column level. Be aware that applying a function to a column can prevent predicate pushdown.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. Lakeflow Connect writes timestamps in UTC. When you query the data, the session time zone determines how the timestamps are displayed. To avoid confusion, set the session time zone explicitly at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Use timestamp literals with explicit offsets when comparing to timestamps. Store timestamps in UTC and convert to local time only for display.

## An end-to-end example

Consider a scenario where you ingest data from SQL Server using a CDC connector and from Salesforce using a SaaS connector. You want to build a medallion architecture with bronze, silver, and gold layers. The bronze layer contains the raw ingested data. The silver layer cleans and conforms the data. The gold layer aggregates the data for analytics.

The following example shows a Lakeflow Spark Declarative Pipeline that reads from both bronze tables, joins them, and produces a gold table.

```python
import dlt
from pyspark.sql.functions import col, sum, count

# Define a silver table for SQL Server orders.
# The bronze table is ingested by the CDC connector.
# The silver table filters out invalid orders.
@dlt.table(
    name="silver_orders",
    comment="Cleaned orders from SQL Server"
)
@dlt.expect_or_drop("valid_amount", "total_amount > 0")
def silver_orders():
    return (dlt.read("sales_bronze.orders")
            .filter(col("total_amount").isNotNull()))

# Define a silver table for Salesforce accounts.
# The bronze table is ingested by the SaaS connector.
@dlt.table(
    name="silver_accounts",
    comment="Cleaned accounts from Salesforce"
)
def silver_accounts():
    return (dlt.read("salesforce_bronze.accounts")
            .select(
                col("Id").alias("account_id"),
                col("Name").alias("account_name"),
                col("Industry"),
                col("AnnualRevenue")
            ))

# Define a gold table that joins orders and accounts and aggregates by industry.
@dlt.table(
    name="gold_revenue_by_industry",
    comment="Total revenue by industry"
)
def gold_revenue_by_industry():
    # Read the silver tables.
    orders = dlt.read("silver_orders")
    accounts = dlt.read("silver_accounts")
    # Join orders to accounts on customer_id.
    joined = orders.join(accounts, orders.customer_id == accounts.account_id, "inner")
    # Aggregate revenue by industry.
    return (joined.groupBy("Industry")
            .agg(
                sum("total_amount").alias("total_revenue"),
                count("*").alias("order_count")
            ))
```

The example defines three tables: two silver tables and one gold table. The silver orders table reads from the SQL Server bronze table and filters out invalid orders. The silver accounts table reads from the Salesforce bronze table and renames columns. The gold table joins the two silver tables and aggregates revenue by industry. The pipeline is declarative. The framework handles orchestration, dependencies, and data quality. All tables are in Unity Catalog and are governed.

## Best practices

Create connections once and reuse them across pipelines. This reduces the number of credential stores and makes it easier to rotate credentials.

Store credentials in a secret scope. Do not hardcode credentials in connection definitions. Unity Catalog connections can reference secrets using the `{{secrets/scope/key}}` syntax.

Set the pipeline schedule to match the freshness requirement. Use a continuous schedule for CDC pipelines that need near-real-time data. Use a longer interval for query-based or SaaS pipelines that can tolerate more latency.

Enable schema evolution deliberately. Schema changes in the source can propagate to the target. Communicate changes to downstream consumers and test the impact before enabling evolution in production.

Define expectations for data quality. Use Lakeflow Spark Declarative Pipelines to attach expectations to the tables that connectors write to. Expectations catch invalid rows early.

Monitor ingestion pipelines. Track metrics such as rows ingested, latency, and errors. Set up alerts for failures and for unusual patterns.

Use partitioning and clustering on the target tables to improve query performance. Choose columns that are commonly used in filters and joins.

Set the session time zone explicitly to UTC. This avoids off-by-hours errors when querying timestamps.

## Common mistakes and pitfalls

The most common mistake is not deploying the ingestion gateway for a database connector. The gateway must be deployed in your environment and must have network access to both the source database and Databricks. Without the gateway, the pipeline cannot run.

A second mistake is choosing the wrong connector type. Using a query-based connector when CDC is available can miss deletes and add unnecessary load to the source. Using a CDC connector when the database does not support it will fail.

A third mistake is not verifying that the source user has the necessary permissions. For CDC, the user needs replication permissions. For query-based, the user needs read access to the source tables. For SaaS, the user needs API access to the objects being ingested.

A fourth mistake is hardcoding credentials. Always use a secret scope. Hardcoded credentials are a security risk and are difficult to rotate.

A fifth mistake is not handling schema changes. If the source schema changes and schema evolution is not enabled, the ingestion pipeline will fail. Enable schema evolution and test it with a small change before relying on it in production.

A sixth mistake is not setting the session time zone. Timestamps are stored in UTC. If you compare them to local time without converting, you may get incorrect results.

A seventh mistake is not monitoring the pipeline. Ingestion pipelines can fail silently if not monitored. Set up alerts for failures and for latency spikes.

## Testing ingestion pipelines

Test ingestion pipelines with a small source and a target table that you can inspect. For CDC connectors, you can simulate changes in the source and verify that they appear in the target. For query-based connectors, you can insert rows with different cursor values and verify that the connector ingests the correct rows. For SaaS connectors, you can use a sandbox instance of the application and verify that the connector extracts the expected objects.

The following example shows a test for a query-based connector's cursor logic.

```python
from pyspark.sql import Row

# Create a small DataFrame with test data.
# The cursor column is last_updated.
test_data = [
    Row(id=1, value="A", last_updated="2026-01-15 10:00:00"),
    Row(id=2, value="B", last_updated="2026-01-15 11:00:00"),
    Row(id=3, value="C", last_updated="2026-01-15 12:00:00"),
]
df_test = spark.createDataFrame(test_data)

# Simulate the cursor logic.
# The last cursor value from the previous run is 11:00:00.
last_cursor = "2026-01-15 11:00:00"

# Filter to rows updated after the last cursor.
df_new = df_test.filter(df_test.last_updated > last_cursor)

# Assert that only the row with 12:00:00 is returned.
assert df_new.count() == 1, f"Expected 1 row, got {df_new.count()}"
assert df_new.collect()[0].id == 3, "Expected row with id 3"
```

Run tests like this in your CI pipeline against a small local Spark session. For connectors, you can also use the Databricks SDK to create a test pipeline and verify that it writes the expected data.

## Performance considerations

Performance depends on the connector type and the volume of data. SaaS connectors are limited by the API rate limits. If the source has a large volume of data, the initial snapshot may take a long time. Incremental extraction is faster because it only fetches changes.

CDC connectors have minimal impact on the source database because they read the transaction log. The ingestion gateway must be sized appropriately for the volume of changes. The gateway should be deployed close to the source database to reduce network latency.

Query-based connectors put query load on the source database. The query should be efficient. Filter on the cursor column and select only the needed columns. Avoid joins and aggregations in the source query. Schedule the connector at a frequency that balances latency with source load.

Target table performance depends on file size and partitioning. Lakeflow Connect writes to Delta tables. It may create many small files during incremental ingestion. Run `OPTIMIZE` periodically to compact small files. Use partitioning or liquid clustering on columns that are commonly used in filters.

Use the `availableNow` trigger for scheduled pipelines to process all available data and stop. This is more cost-effective than a continuously running cluster.
