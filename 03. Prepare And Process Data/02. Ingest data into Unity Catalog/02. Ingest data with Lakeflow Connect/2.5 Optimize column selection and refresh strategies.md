## Optimize column selection and refresh strategies

Column selection and refresh strategy are two of the most impactful configuration choices you make when setting up an ingestion pipeline. Column selection determines which columns from the source table are brought into the lakehouse. It directly controls the volume of data transferred over the network, the amount of storage consumed, and the sensitivity of the data that lands in Unity Catalog. Refresh strategy determines how the destination table is updated when incremental processing cannot recover from schema changes or data inconsistencies. A full refresh clears the destination table and reloads all records from scratch. Together, these two settings let you tune an ingestion pipeline for cost, performance, and correctness without writing custom code.

Column selection matters because source tables often contain more columns than analytics requires. An operational orders table might have fifty columns, but a downstream report might use only five. Ingesting all fifty columns transfers unnecessary data, consumes storage, and exposes columns that may contain sensitive information. By selecting only the columns you need, you reduce the volume of data that flows through the pipeline, lower storage costs, and limit the blast radius of a data breach. Column selection is also a governance control. If a source column contains personally identifiable information, you can exclude it from ingestion entirely, so it never lands in the lakehouse and never needs to be masked or protected.

Refresh strategy matters because incremental ingestion is not always sufficient. Change data capture and cursor-based extraction work well when the source schema is stable and the cursor column is reliable. But source schemas change, cursor columns can be reset, and data inconsistencies can accumulate. When incremental processing cannot recover, a full refresh is the fallback. A full refresh clears the destination table and reloads all records from scratch. It is a heavy operation, but it guarantees that the destination reflects the current state of the source. Lakeflow Connect minimizes downtime during a full refresh by maintaining the existing data until the new snapshot completes. You can also configure a full refresh window to schedule these operations during off-peak hours.

These notes cover column selection and refresh strategies from first principles. They explain how `include_columns` and `exclude_columns` work, when to use each, and how they interact with schema evolution. They explain what a full refresh does, when to trigger one, how Lakeflow Connect minimizes downtime, and how to configure a full refresh window. They show configuration examples in YAML and query examples in SQL and PySpark. They also cover schema enforcement, schema evolution, expectations, null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example. The goal is that you can read these notes alone and understand how to optimize column selection and refresh strategies for your ingestion pipelines.

## Understanding column selection

Column selection is the configuration that determines which columns from the source table are ingested into the destination table. By default, Lakeflow Connect ingests all columns from the source. For tables with many columns, or columns that contain sensitive data, this default is not always appropriate. Column selection lets you narrow the set of ingested columns. You use the `include_columns` or `exclude_columns` settings in the table configuration. These settings are mutually exclusive. You cannot use both in the same table configuration. You choose one approach based on whether it is easier to list the columns you want or the columns you do not want.

The following table summarizes the two approaches.

| Setting | Behavior | New source columns | Best for |
|---|---|---|---|
| `include_columns` | Only the listed columns are ingested | Not ingested by default | Sources with many columns, or when only a few columns are needed |
| `exclude_columns` | All columns except the listed ones are ingested | Ingested by default | Sources where most columns are needed, but a few should be excluded |

The table shows that `include_columns` is a whitelist and `exclude_columns` is a blacklist. The choice depends on whether the set of columns you want is smaller or larger than the set you do not want. If you need five columns out of fifty, use `include_columns`. If you need forty-five out of fifty, use `exclude_columns`.

### Using include_columns

`include_columns` specifies the exact set of columns to ingest. Only the listed columns appear in the destination table. If the source adds a new column, it does not automatically appear in the destination. You must update the configuration to include it. This behavior is desirable when you want strict control over the destination schema. It prevents unexpected columns from appearing in the lakehouse, which can break downstream consumers that expect a fixed set of columns. It also prevents sensitive columns from being ingested by accident. If a source table adds a new column that contains personal data, `include_columns` ensures that the column is not ingested until you explicitly add it to the configuration.

The following YAML example shows how to configure `include_columns` for an ingestion pipeline.

```yaml
# Table configuration with include_columns.
# Only the listed columns are ingested into the destination table.
# Newly added source columns do not automatically appear in the destination.
# This is a whitelist approach: you list exactly what you want.
table_configuration:
  # The include_columns setting lists the columns to ingest.
  # The order of the columns in the list does not matter.
  # The destination table has exactly these columns.
  include_columns:
    # The customer identifier is needed for joins with other tables.
    - customer_id
    # The order date is needed for time-based analysis.
    - order_date
    # The total amount is needed for revenue calculations.
    - total_amount
```

The example ingests only `customer_id`, `order_date`, and `total_amount`. Columns that are not listed, such as `shipping_address`, `customer_email`, or `internal_notes`, are not ingested. This reduces the volume of data transferred and stored, and it prevents sensitive columns from landing in the lakehouse.

The equivalent result when querying the destination table is a DataFrame with only the selected columns. The following PySpark example reads the destination table and verifies the column set.

```python
# Read the destination table that was ingested with include_columns.
df_orders = spark.read.table("sales.bronze.orders")

# Print the columns to verify that only the selected columns are present.
# The expected columns are customer_id, order_date, and total_amount.
# If other columns appear, the include_columns configuration was not applied.
print(df_orders.columns)

# Select the columns for analysis.
# This step is not strictly necessary because the table already has only
# the selected columns, but it documents the expected schema.
df_selected = df_orders.select(
    "customer_id",
    "order_date",
    "total_amount"
)

# Display the result.
display(df_selected)
```

The example reads the destination table and confirms that only the selected columns are present. If the source added a new column and `include_columns` is configured, that column does not appear in the destination until you update the configuration.

### Using exclude_columns

`exclude_columns` specifies the set of columns to exclude from ingestion. All other columns are ingested, including new columns that appear in the source. This behavior is desirable when most columns are needed but a few should be excluded. For example, you might exclude a column that contains large binary data, a column that contains sensitive information, or a column that is not useful for analytics. With `exclude_columns`, new columns are included by default, so you do not need to update the configuration when the source adds a column that should be ingested.

The following YAML example shows how to configure `exclude_columns`.

```yaml
# Table configuration with exclude_columns.
# All columns except the listed ones are ingested.
# Newly added source columns are ingested by default.
# This is a blacklist approach: you list what you do not want.
table_configuration:
  # The exclude_columns setting lists the columns to exclude from ingestion.
  # The order of the columns in the list does not matter.
  exclude_columns:
    # Exclude the customer email to avoid ingesting personal data.
    - customer_email
    # Exclude the internal notes column because it is not useful for analytics.
    - internal_notes
    # Exclude the large binary attachment column to reduce data volume.
    - attachment_blob
```

The example ingests all columns except `customer_email`, `internal_notes`, and `attachment_blob`. If the source adds a new column called `loyalty_tier`, that column is ingested automatically because it is not in the exclude list. This is convenient, but it means you must monitor new columns to ensure they do not contain sensitive data.

### Comparing include_columns and exclude_columns

The choice between `include_columns` and `exclude_columns` depends on your priorities. `include_columns` gives you strict control and prevents unexpected columns from appearing in the destination. It is the safer choice when the source schema changes frequently or when sensitive data is a concern. `exclude_columns` is more convenient when most columns are needed and only a few should be excluded. It automatically picks up new columns, which reduces maintenance, but it requires you to monitor the source for new columns that should not be ingested.

The following table compares the two approaches across several dimensions.

| Dimension | include_columns | exclude_columns |
|---|---|---|
| Control over schema | Strict | Loose |
| New source columns | Not ingested by default | Ingested by default |
| Maintenance | Higher, because you must update the list when the source changes | Lower, because new columns are included automatically |
| Sensitive data protection | Strong, because unlisted columns are never ingested | Weaker, because new columns are ingested unless explicitly excluded |
| Best for | Sources with many columns or sensitive data | Sources where most columns are needed |

The table shows that `include_columns` is the safer choice for sensitive data and strict schema control. `exclude_columns` is more convenient for sources where most columns are needed. In practice, many teams use `include_columns` for bronze ingestion because it gives them explicit control over what lands in the lakehouse. The silver and gold layers then select from the bronze table.

### Column selection and schema evolution

Column selection interacts with schema evolution. If schema evolution is enabled and `include_columns` is configured, new source columns are not added to the destination because they are not in the include list. If schema evolution is enabled and `exclude_columns` is configured, new source columns are added to the destination because they are not in the exclude list. This interaction is important to understand. If you want to prevent new columns from being ingested, use `include_columns`. If you want new columns to be ingested automatically, use `exclude_columns`.

The following table summarizes the interaction.

| Column selection | Schema evolution enabled | New source column behavior |
|---|---|---|
| `include_columns` | Yes | Not ingested, because not in the include list |
| `include_columns` | No | Not ingested, because not in the include list |
| `exclude_columns` | Yes | Ingested, because not in the exclude list |
| `exclude_columns` | No | Not ingested, because schema evolution is disabled |

The table shows that `include_columns` always prevents new columns from being ingested, regardless of schema evolution. `exclude_columns` allows new columns only if schema evolution is enabled. Choose the combination that matches your governance requirements.

## Full refresh strategy

A full refresh clears the destination table and reloads all records from the source. It is the fallback when incremental processing cannot recover from schema changes or data inconsistencies. Incremental processing relies on change data capture or a cursor column to identify changes. If the source schema changes in a way that breaks the incremental logic, or if the cursor column is reset or corrupted, incremental processing may miss changes or produce incorrect results. A full refresh sidesteps these problems by reading the entire source table and replacing the destination contents.

A full refresh is a heavy operation. It reads the entire source table, which can be large. It writes a new copy of the destination table, which consumes storage and compute. It may take a long time to complete. Because of these costs, full refreshes should be used sparingly. They are not a routine operation. They are a recovery mechanism for situations where incremental processing has failed or where the destination must be rebuilt from scratch. You should understand when a full refresh is necessary and how to schedule it to minimize disruption.

### When to use a full refresh

A full refresh is appropriate in several situations. The first is when the source schema changes in a way that incremental processing cannot handle. For example, if a column is renamed or its data type changes, the incremental pipeline may fail or produce incorrect data. A full refresh rebuilds the destination with the new schema. The second situation is when the cursor column is reset or corrupted. If the cursor column values decrease or become null, the incremental pipeline may skip rows or re-ingest rows. A full refresh resets the cursor and rebuilds the destination. The third situation is when data inconsistencies are detected. If the destination table does not match the source, a full refresh corrects the discrepancy. The fourth situation is when you change the pipeline configuration in a way that affects the destination schema. For example, if you add a column to the `include_columns` list, a full refresh may be needed to populate the new column for existing rows.

The following table summarizes the situations that call for a full refresh.

| Situation | Why incremental fails | Why full refresh helps |
|---|---|---|
| Source schema changed | Incremental pipeline cannot map old and new columns | Rebuilds destination with the new schema |
| Cursor column reset | Incremental pipeline may skip or re-ingest rows | Resets the cursor and rebuilds the destination |
| Data inconsistency detected | Destination does not match source | Replaces destination with a fresh snapshot |
| Column selection changed | New column is not populated for existing rows | Repopulates all rows with the new column set |

The table shows that a full refresh is a recovery mechanism. It is not something you run on a schedule. It is something you trigger when incremental processing has failed or when the destination must be rebuilt.

### How Lakeflow Connect minimizes downtime during full refresh

A full refresh could cause downtime if it cleared the destination table before loading the new data. During the load, the destination table would be empty or incomplete, and queries against it would return wrong results. Lakeflow Connect avoids this by maintaining the existing data until the new snapshot completes. The pipeline reads the full source table into a staging area, and only when the snapshot is complete does it swap the new data into the destination. This means that readers see either the old data or the new data, never a partial state. The swap is atomic, so there is no window during which the destination is empty.

This behavior is important for production pipelines. If a full refresh is triggered during business hours, queries against the destination table continue to work. They see the old data until the new snapshot is ready, and then they see the new data. The transition is instantaneous from the reader's perspective. You do not need to take the table offline or notify downstream consumers.

### Configuring a full refresh

You can trigger a full refresh through the Databricks UI, the CLI, or the SDK. In the UI, you select the pipeline, choose the table, and click the full refresh button. In the CLI or SDK, you use the API to request a full refresh for a specific table. The following example shows how to trigger a full refresh using the Databricks SDK for Python.

```python
# Import the Databricks SDK for Python.
from databricks.sdk import WorkspaceClient

# Create a WorkspaceClient using the default authentication.
w = WorkspaceClient()

# Trigger a full refresh for a specific table in a pipeline.
# The pipeline_id identifies the pipeline.
# The table name identifies the table to refresh.
# The full_refresh method clears the destination and reloads all records.
w.pipelines.trigger_full_refresh(
    pipeline_id="my-pipeline-id",
    table="sales.bronze.orders"
)
```

The example triggers a full refresh for the `orders` table in the pipeline. The pipeline reads the entire source table and replaces the destination. The operation runs asynchronously. You can monitor its progress in the UI or by polling the pipeline status.

## Full refresh window

A full refresh window is a scheduled period during which full refreshes are allowed to run. It prevents full refreshes from starting during peak business hours, when the extra load on the source and the cluster could affect performance. You configure the window in the pipeline settings. The window is specified as a start time and a duration, or as a cron expression that defines when the window is open. When a full refresh is triggered outside the window, it is queued and started when the window opens. This lets you trigger a full refresh at any time without worrying about the impact on peak hours.

The following YAML example shows how to configure a full refresh window.

```yaml
# Pipeline configuration with a full refresh window.
# The window defines when full refreshes are allowed to run.
# Full refreshes triggered outside the window are queued until the window opens.
table_configuration:
  # The full_refresh_window setting defines the allowed period.
  # The start time and duration are specified in the pipeline's time zone.
  # In this example, the window opens at 2:00 AM and lasts for 2 hours.
  full_refresh_window:
    # The start time is specified as a cron expression.
    # "0 0 2 * * ?" means 2:00 AM every day.
    start: "0 0 2 * * ?"
    # The duration is specified in minutes.
    # 120 minutes equals 2 hours.
    duration_minutes: 120
```

The example configures a full refresh window that opens at 2:00 AM every day and lasts for two hours. Full refreshes triggered during this window start immediately. Full refreshes triggered outside the window are queued until the next window. This ensures that full refreshes run during off-peak hours, when the load on the source and the cluster is low.

The time zone of the window is the pipeline's time zone, which defaults to UTC. If your business operates in a different time zone, you should set the pipeline's time zone to match. For example, if your business operates in US Eastern Time, you might set the pipeline's time zone to `America/New_York` and configure the window to open at 2:00 AM Eastern. This avoids confusion and ensures that the window aligns with your off-peak hours.

## Combining column selection and refresh strategies

Column selection and refresh strategy work together. Column selection determines what data is in the destination table. Refresh strategy determines how the destination is updated. A well-designed pipeline uses both to balance cost, performance, and correctness.

Consider a pipeline that ingests orders from SQL Server. The source table has fifty columns, but the analytics team needs only ten. You configure `include_columns` with the ten columns. This reduces the volume of data transferred and stored. The pipeline uses CDC for incremental extraction. If the source schema changes, such as a column being renamed, the incremental pipeline may fail. You trigger a full refresh to rebuild the destination with the new schema. The full refresh reads the full source table but ingests only the ten columns in the include list. The refresh window ensures that the full refresh runs at 2:00 AM, when the source database is not under heavy load.

The following YAML example shows a pipeline configuration that combines column selection and a full refresh window.

```yaml
# Pipeline configuration that combines column selection and refresh strategy.
# The table configuration specifies the columns to ingest and the refresh window.
table_configuration:
  # Include only the columns needed for analytics.
  # New source columns are not ingested until they are added to this list.
  include_columns:
    - order_id
    - customer_id
    - order_date
    - total_amount
    - status
    - region
    - product_category
    - quantity
    - discount
    - shipping_cost
  # Use SCD type 1 to keep the destination reflecting the current state.
  scd_type: SCD_TYPE_1
  # The primary key identifies rows for merge operations.
  primary_keys:
    - order_id
  # The sequence_by column orders changes.
  sequence_by: last_modified
  # The full refresh window defines when full refreshes are allowed.
  # In this example, the window opens at 2:00 AM and lasts for 2 hours.
  full_refresh_window:
    start: "0 0 2 * * ?"
    duration_minutes: 120
```

The example combines `include_columns` with a full refresh window. The pipeline ingests only the ten listed columns. If the source adds a new column, it is not ingested until the configuration is updated. The full refresh window ensures that full refreshes run during off-peak hours. This configuration balances data volume, schema control, and operational safety.

## Schema enforcement, evolution, and expectations

Schema enforcement and evolution apply to column selection and refresh. When the pipeline writes to the destination table, Delta Lake enforces the table schema. If the source schema changes and `include_columns` is configured, the new column is not ingested because it is not in the include list. If `exclude_columns` is configured and schema evolution is enabled, the new column is ingested. You should decide how to handle schema changes based on your governance requirements.

Expectations are data quality rules that you define in Lakeflow Spark Declarative Pipelines. You can attach expectations to the destination table or to downstream tables. Expectations can drop, fail, or warn on rows that violate a rule. For example, you can define an expectation that `order_id` is not null and that `total_amount` is positive. If a row violates either expectation, the pipeline can drop it before it reaches downstream tables. Expectations help you maintain data quality even when column selection and refresh strategies change.

The following table summarizes the schema and quality controls.

| Control | Mechanism | Effect |
|---|---|---|
| Schema enforcement | Delta Lake write | Rejects writes that do not match the table schema |
| Schema evolution | Connector option | Adds new columns to the target table during ingestion |
| Column selection | `include_columns` or `exclude_columns` | Controls which columns are ingested |
| Expectations | Lakeflow Spark Declarative Pipelines | Drops, fails, or warns on rows that violate a rule |

The table shows that column selection controls what is ingested, schema enforcement and evolution control how the schema changes, and expectations control data quality. Use these controls together to build robust pipelines.

## Null handling, case sensitivity, and time zones

Null handling is important for column selection and refresh. If you use `include_columns` and a selected column contains nulls, the destination column contains nulls. If the destination column is non-nullable, the write fails. You should ensure that non-nullable columns in the destination have a default or that the source does not produce nulls for those columns. If you use `exclude_columns` and a column that contains nulls is not excluded, the nulls are preserved in the destination. Rows with a null cursor column are not ingested by query-based connectors. You should ensure that the cursor column is not null for rows that should be ingested.

Case sensitivity affects string comparisons. By default, Spark's string comparisons are case-sensitive. If the source has inconsistent casing in a key column, joins and merges may not match rows that should match. You can normalize the case in a downstream transformation or use a case-insensitive collation if the table is configured for one. Unity Catalog supports collations at the column level.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. The pipeline writes timestamps in UTC. When you query the data, the session time zone determines how the timestamps are displayed. To avoid confusion, set the session time zone explicitly at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. The full refresh window is configured in the pipeline's time zone, which defaults to UTC. If your business operates in a different time zone, set the pipeline's time zone to match.

## An end-to-end example

Consider a scenario where you ingest customer data from a PostgreSQL database. The source table has thirty columns, but the analytics team needs only eight. You configure `include_columns` with the eight columns. The pipeline uses a query-based connector with a cursor column. You configure a full refresh window to ensure that full refreshes run at 2:00 AM. The following YAML example shows the complete pipeline configuration.

```yaml
# Pipeline configuration for ingesting customer data from PostgreSQL.
# The pipeline uses a query-based connector with a cursor column.
# Column selection reduces the data volume to only the needed columns.
# The full refresh window ensures that full refreshes run at 2:00 AM.
ingestion_definition:
  # The connection stores the credentials for the source database.
  connection_name: postgres_connection
  # The source catalog and schema identify the source database and schema.
  source_catalog: sales
  source_schema: public
  # The source table is the table to ingest.
  source_table: customers
  # The cursor column tracks which rows are new or updated.
  cursor_column: last_updated
  # The primary keys identify rows for merge operations.
  primary_keys:
    - customer_id
  # Use SCD type 1 to keep the destination reflecting the current state.
  scd_type: SCD_TYPE_1
  # Include only the columns needed for analytics.
  # New source columns are not ingested until they are added to this list.
  include_columns:
    - customer_id
    - customer_name
    - email
    - phone
    - region
    - segment
    - created_date
    - last_updated
  # The destination catalog and schema specify where the target table is written.
  destination_catalog: sales
  destination_schema: bronze
  # The destination table defaults to the source table name if not specified.
  destination_table: customers
  # The full refresh window defines when full refreshes are allowed.
  full_refresh_window:
    # The window opens at 2:00 AM every day.
    start: "0 0 2 * * ?"
    # The window lasts for 2 hours.
    duration_minutes: 120
```

The example configures a pipeline that ingests eight columns from the `customers` table. The cursor column is `last_updated`. The primary key is `customer_id`. The SCD type is `SCD_TYPE_1`. The destination is `sales.bronze.customers`. The full refresh window opens at 2:00 AM and lasts for two hours.

Once the pipeline is running, you query the destination table with SQL and PySpark. The following SQL example queries the ingested customers.

```sql
-- Query the ingested customers table.
-- The table is created by the pipeline in the sales.bronze schema.
-- Only the eight selected columns are present in the table.
SELECT
  customer_id,
  customer_name,
  region,
  segment
FROM sales.bronze.customers
-- Filter to customers in the enterprise segment.
WHERE segment = 'Enterprise'
-- Order by customer name.
ORDER BY customer_name;
```

The equivalent PySpark query reads the same table and applies the same filter.

```python
# Import the col function for column references.
from pyspark.sql.functions import col

# Read the ingested customers table.
df_customers = spark.read.table("sales.bronze.customers")

# Filter to customers in the enterprise segment.
df_enterprise = df_customers.filter(col("segment") == "Enterprise")

# Select the columns of interest and order by customer name.
df_result = df_enterprise.select(
    "customer_id",
    "customer_name",
    "region",
    "segment"
).orderBy("customer_name")

# Display the result.
display(df_result)
```

The queries show that the destination table contains only the selected columns. The full refresh window ensures that full refreshes run during off-peak hours. This configuration balances data volume, schema control, and operational safety.

## Best practices

Use `include_columns` when you need strict control over the destination schema or when sensitive data is a concern. Use `exclude_columns` when most columns are needed and only a few should be excluded. Remember that `include_columns` prevents new source columns from being ingested automatically, while `exclude_columns` allows them.

Select only the columns you need. Ingesting unnecessary columns increases data transfer, storage costs, and the risk of exposing sensitive data. Review the column list periodically and remove columns that are no longer used.

Trigger a full refresh only when incremental processing cannot recover. Full refresh is a heavy operation. Use it as a recovery mechanism, not as a routine operation.

Configure a full refresh window to schedule full refreshes during off-peak hours. This prevents full refreshes from competing with peak-hour workloads for compute and network resources.

Set the pipeline's time zone to match your business operations. The full refresh window is configured in the pipeline's time zone. If your business operates in a different time zone, set the pipeline's time zone to match.

Monitor the destination table schema. If you use `exclude_columns` and schema evolution is enabled, new columns are ingested automatically. Monitor the source for new columns that should not be ingested and add them to the exclude list.

Use expectations to validate data quality. Attach expectations to the destination table or to downstream tables. Expectations catch invalid rows early.

## Common mistakes and pitfalls

The most common mistake is using both `include_columns` and `exclude_columns` in the same table configuration. They are mutually exclusive. Choose one approach.

A second mistake is forgetting that `include_columns` prevents new source columns from being ingested. If the source adds a column that you need, you must update the configuration. If you do not, the column does not appear in the destination.

A third mistake is using `exclude_columns` and assuming that new source columns will not be ingested. New columns are ingested by default unless schema evolution is disabled or the columns are added to the exclude list. Monitor the source for new columns and update the exclude list as needed.

A fourth mistake is triggering a full refresh without a full refresh window. A full refresh during peak hours can compete with other workloads and slow down the source database. Configure a full refresh window and schedule full refreshes during off-peak hours.

A fifth mistake is assuming that a full refresh is instantaneous. A full refresh reads the entire source table and writes a new copy of the destination. It can take a long time for large tables. Plan for the duration and monitor the progress.

A sixth mistake is not setting the pipeline's time zone. The full refresh window is configured in the pipeline's time zone. If the pipeline's time zone does not match your business operations, the window may open at the wrong time.

A seventh mistake is not monitoring the destination table schema. If the schema changes unexpectedly, downstream consumers may break. Monitor the schema and communicate changes to downstream teams.

## Testing column selection and refresh

Test column selection and refresh with a small source and a destination table that you can inspect. For column selection, verify that only the selected columns appear in the destination. For full refresh, verify that the destination is cleared and reloaded with the correct data. The following example shows a test for column selection.

```python
from pyspark.sql import Row

# Create a small DataFrame with more columns than needed.
test_data = [
    Row(id=1, name="Alice", amount=100.0, email="alice@example.com", notes="vip"),
    Row(id=2, name="Bob", amount=200.0, email="bob@example.com", notes="regular"),
]
df_test = spark.createDataFrame(test_data)

# Simulate column selection by selecting only the needed columns.
# In a real pipeline, the include_columns configuration does this automatically.
df_selected = df_test.select("id", "name", "amount")

# Verify that only the selected columns are present.
expected_columns = ["id", "name", "amount"]
assert df_selected.columns == expected_columns, f"Expected {expected_columns}, got {df_selected.columns}"

# Verify that the excluded columns are not present.
assert "email" not in df_selected.columns, "email should not be present"
assert "notes" not in df_selected.columns, "notes should not be present"
```

The test verifies that the selected columns are present and the excluded columns are absent. Run tests like this in your CI pipeline against a small local Spark session. For pipeline configuration, validate the YAML before deploying it.

## Performance considerations

Column selection improves performance by reducing the volume of data transferred and stored. Fewer columns mean less network bandwidth, less storage, and faster queries. If you use `include_columns`, the pipeline reads only the selected columns from the source, which reduces the load on the source database. If you use `exclude_columns`, the pipeline reads all columns except the excluded ones, which may still be a large volume if the excluded columns are few.

Full refresh is expensive. It reads the entire source table and writes a new copy of the destination. The cost is proportional to the size of the source table. Schedule full refreshes during off-peak hours and use a full refresh window to control when they run. Monitor the duration and adjust the window if needed.

Destination table performance depends on file size and partitioning. The pipeline writes to Delta tables. It may create many small files during incremental ingestion. Run `OPTIMIZE` periodically to compact small files. Use partitioning or liquid clustering on columns that are commonly used in filters.

Use the `availableNow` trigger for scheduled pipelines to process all available data and stop. This is more cost-effective than a continuously running cluster.

## Summary

Column selection and refresh strategy are two configuration choices that control the volume, cost, and correctness of an ingestion pipeline. Column selection determines which columns from the source are ingested. You use `include_columns` to whitelist the columns you want, or `exclude_columns` to blacklist the columns you do not want. `include_columns` gives you strict control and prevents new source columns from being ingested automatically. `exclude_columns` is more convenient when most columns are needed and allows new columns to be ingested by default.

Full refresh clears the destination table and reloads all records from the source. It is the fallback when incremental processing cannot recover from schema changes or data inconsistencies. Lakeflow Connect minimizes downtime during full refresh by maintaining the existing data until the new snapshot completes. The swap is atomic, so readers see either the old data or the new data.

A full refresh window schedules full refreshes during off-peak hours. You configure the window as a start time and duration. Full refreshes triggered outside the window are queued until the window opens. The window is configured in the pipeline's time zone, which defaults to UTC.

Schema enforcement, schema evolution, and expectations apply to column selection and refresh. Column selection controls what is ingested. Schema enforcement and evolution control how the schema changes. Expectations validate data quality. Null handling, case sensitivity, and time zones affect ingestion and querying. Set the session time zone explicitly to UTC, normalize string casing, and handle nulls deliberately.

Best practices include using `include_columns` for strict control and sensitive data protection, using `exclude_columns` for convenience, triggering full refreshes only when necessary, configuring a full refresh window, setting the pipeline's time zone, and monitoring the destination schema. Common mistakes include using both column selection settings, forgetting that `include_columns` prevents new columns from being ingested, triggering full refreshes without a window, and not setting the pipeline's time zone.

Test column selection and refresh with small datasets and validate the configuration before deploying. Performance improves with column selection because it reduces data volume. Full refresh is expensive, so schedule it during off-peak hours and monitor its duration. Compact small files in the destination table and use partitioning or liquid clustering for query performance.

By optimizing column selection and refresh strategies, you can build ingestion pipelines that are efficient, governed, and resilient to schema changes and data inconsistencies.
