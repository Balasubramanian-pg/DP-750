## Control data extraction behavior

Data extraction is the process of reading data from a source system and bringing it into the lakehouse. The way you extract data determines how much load you place on the source, how quickly changes appear in the destination, and how much history you preserve. Lakeflow Connect gives you several controls over extraction behavior. The most fundamental choice is between snapshot extraction and incremental extraction. A snapshot reads the entire source table on each run. Incremental extraction reads only the data that has changed since the last run. Incremental extraction is more efficient because it reduces the volume of data transferred and the load on the source. It is also faster, because the pipeline processes only the changed rows rather than the full table.

The choice between snapshot and incremental depends on the source and the requirements. For database connectors, Lakeflow Connect uses change data capture to track modifications at the source. When CDC is enabled on the source database, the ingestion gateway captures inserts, updates, and deletes incrementally. This means subsequent pipeline runs process only changed records. For query-based connectors, incremental extraction relies on a cursor column—a monotonically increasing timestamp or integer column—to identify rows that are new or updated. For SaaS connectors, the availability of incremental extraction depends on the API and the objects being ingested. Some APIs expose change tracking endpoints; others require full snapshots.

The second important control is the slowly changing dimension setting, often called SCD type. The SCD type determines how the destination table handles changes to existing records. SCD type 1 overwrites existing records when updates occur, so the destination table always reflects the current state of the source. SCD type 2 preserves historical versions of records. When a row changes, the pipeline marks the previous version as inactive and adds the new version. This approach tracks how data evolves over time. SCD type 2 requires a sequence column to order changes and produces two additional columns in the destination table, `__START_AT` and `__END_AT`, that record each version's active period.

These notes cover the controls over data extraction behavior in Lakeflow Connect. They explain snapshot and incremental extraction, how they work for different connector types, and when to use each. They explain the SCD type setting, how SCD type 1 and type 2 differ, and how to configure them. They explain the `sequence_by` cursor column, how it tracks progress, and what happens when it is not specified. They explain the `__START_AT` and `__END_AT` columns and how to query them. They also cover additional controls such as column selection, full refresh, and multiple destinations. Each concept is introduced in prose, then shown in configuration examples with full comments, then interpreted. The goal is that you can read these notes alone and understand how to control extraction behavior to match the needs of your pipeline.

## Snapshot extraction

Snapshot extraction reads all rows from the source table on each pipeline run. It does not track changes. Every run produces a fresh copy of the source data, and the destination table is replaced or updated with the full set. Snapshot extraction is simple and predictable. It does not require CDC to be enabled on the source, and it does not require a cursor column. It works with any source that can be queried. The tradeoff is cost and load. If the source table is large, reading all rows on every run is expensive. It puts load on the source database, consumes network bandwidth, and increases the time and compute cost of each pipeline run.

Snapshot extraction is the default for some connectors. For example, Lakeflow Connect ingests Workday reports using snapshot mode by default. Each pipeline update reads all rows in the report. For small tables or reports that change infrequently, snapshot extraction is acceptable. It is also useful when the source does not support CDC or when you cannot rely on a cursor column. If the source table has no reliable monotonically increasing column, or if the cursor column is not updated on every change, snapshot extraction is the safer choice. It guarantees that the destination reflects the full current state of the source, even if some changes were not captured incrementally.

The following table compares snapshot and incremental extraction.

| Aspect | Snapshot extraction | Incremental extraction |
|---|---|---|
| Data read per run | All rows | Only changed rows |
| Load on source | High for large tables | Low |
| Latency of changes | Depends on run frequency | Low, especially with CDC |
| Captures deletes | Yes, because full table is read | Only if CDC or soft deletes are supported |
| Requires CDC | No | Yes for database connectors, or a cursor column |
| Requires cursor column | No | Yes for query-based connectors |
| Typical use | Small tables, sources without CDC | Large tables, CDC-enabled databases |

The table shows that snapshot extraction is simpler but more expensive. Incremental extraction is more efficient but requires either CDC or a reliable cursor column. The choice depends on the size of the source, the availability of CDC, and the freshness requirement.

## Incremental extraction with change data capture

Incremental extraction reads only the data that has changed since the last pipeline run. For database connectors, Lakeflow Connect uses change data capture to track modifications at the source. CDC reads the database transaction log, often called the `binlog` in MySQL or the write-ahead log in PostgreSQL and SQL Server. The log records every insert, update, and delete that the database applies. The ingestion gateway reads the log continuously and converts the changes into a stream of events. Because the log is the authoritative record of changes, CDC captures every change, including deletes, and does so with low latency. The source database is not queried directly for changes, so the load on the database is minimal. The gateway tracks its position in the log so that it can resume after a restart.

Incremental extraction with CDC is the right choice when the source database supports CDC and you need low-latency ingestion. Supported databases include MySQL, PostgreSQL, and SQL Server. The initial run performs a snapshot to establish a baseline. Subsequent runs apply only the changes. The destination table stays synchronized with the source. If the source table is large and changes frequently, incremental extraction with CDC is far more efficient than snapshot extraction. It reads only the changed rows, so the volume of data transferred is proportional to the number of changes, not the size of the table.

The following table summarizes the CDC capabilities of supported database connectors.

| Database | CDC mechanism | Captures deletes | Latency |
|---|---|---|---|
| MySQL | Binlog | Yes | Seconds to minutes |
| PostgreSQL | Write-ahead log / logical replication | Yes | Seconds to minutes |
| SQL Server | Change data capture | Yes | Seconds to minutes |
| Oracle | LogMiner | Yes | Seconds to minutes |

The table shows that all supported database connectors capture deletes and provide low latency. This is a significant advantage over query-based incremental extraction, which does not capture deletes unless the source uses soft deletes.

## Incremental extraction with a cursor column

Query-based connectors do not use CDC. Instead, they use a cursor column—a monotonically increasing timestamp or integer column—to track progress. On each run, the connector reads the maximum cursor value from the previous run and queries the source for rows where the cursor column is greater than that value. This captures new rows and updates to existing rows, provided that the cursor column is updated whenever a row changes. The connector stores the maximum cursor value after each successful run and uses it as the lower bound filter on the next run.

The cursor column must satisfy several requirements. It must be a single column. Composite cursors are not supported. It must increase monotonically; values must never decrease. Rows with cursor values at or below the stored high-water mark are not re-ingested on subsequent runs. Rows with a null cursor column are not ingested. Supported column types include timestamp or date types, numeric types such as integer or decimal, binary types, and string types. Timestamp and date types are recommended because they are easy to reason about and usually correspond to a `last_modified` or `updated_at` column in the source.

The following YAML example shows how to configure a query-based connector with a cursor column.

```yaml
# Pipeline configuration for a query-based connector.
# The ingestion_definition block specifies the source and destination.
ingestion_definition:
  # The connection stores the credentials for the source database.
  connection_name: postgres_connection
  # The source catalog and schema identify the source database and schema.
  source_catalog: sales
  source_schema: public
  # The source table is the table to ingest.
  source_table: orders
  # The cursor column tracks which rows are new or updated.
  # It must be a single monotonically increasing column.
  # Rows with a null cursor value are not ingested.
  cursor_column: last_updated
  # The primary keys identify rows for merge operations.
  # Required for SCD_TYPE_1 and SCD_TYPE_2 modes.
  primary_keys:
    - order_id
  # The SCD type determines how the destination handles changes.
  # SCD_TYPE_1 overwrites existing records to reflect the current state.
  scd_type: SCD_TYPE_1
  # The destination catalog and schema specify where the target table is written.
  destination_catalog: sales
  destination_schema: bronze
  # The destination table defaults to the source table name if not specified.
  destination_table: orders
```

The YAML defines a query-based connector that ingests the `orders` table from PostgreSQL. The `cursor_column` is `last_updated`. On each run, the connector queries for rows where `last_updated` is greater than the stored high-water mark. The `primary_keys` list identifies rows for merge operations. The `scd_type` is `SCD_TYPE_1`, so the destination reflects the current state of the source. The destination table is `sales.bronze.orders`.

The cursor column is the linchpin of query-based incremental extraction. If the cursor column is not updated on every change, the connector may miss updates. If the cursor column is null for some rows, those rows are not ingested. If the cursor column decreases for any reason, the connector may re-ingest rows or miss them. You should verify that the source application reliably updates the cursor column and that the column is never null for rows that should be ingested.

## SCD type 1: overwriting changes

SCD type 1 is the default history tracking mode for most connectors. When a row in the source changes, the connector overwrites the corresponding row in the destination table. The destination table always reflects the current state of the source data. There is no history of previous versions. SCD type 1 is simple and efficient. It keeps the destination table small, because each source row corresponds to exactly one destination row. It is the right choice when you only need the current state of the data and you do not need to track how values changed over time.

SCD type 1 works with both CDC and query-based incremental extraction. With CDC, the connector receives an update event for each change. With a query-based connector, the connector detects changes by comparing the cursor column. In both cases, the connector merges the changed rows into the destination table, overwriting existing rows that match the primary key. Deletes are handled differently depending on the connector. CDC connectors capture deletes and remove the corresponding rows from the destination. Query-based connectors do not capture hard deletes unless the source uses soft deletes that update the cursor column.

The following YAML example shows a table configuration for SCD type 1.

```yaml
# Table configuration for SCD type 1.
# The scd_type is set to SCD_TYPE_1, which is the default.
# Updates overwrite existing records in the destination table.
table_configuration:
  scd_type: SCD_TYPE_1
  # The primary keys identify rows for merge operations.
  # The connector uses these keys to match source rows to destination rows.
  primary_keys:
    - customer_id
  # The sequence_by column orders changes when multiple changes occur.
  # It is not required for SCD type 1, but it can be specified
  # to ensure deterministic results when changes arrive out of order.
  sequence_by: last_modified
```

The example sets `scd_type` to `SCD_TYPE_1` and specifies the primary key and a `sequence_by` column. The `sequence_by` column is optional for SCD type 1, but it is useful when changes may arrive out of order. It tells the connector which change is the most recent, so the destination reflects the latest state.

## SCD type 2: preserving history

SCD type 2 preserves historical versions of records. When a row changes, the pipeline marks the previous version as inactive and adds the new version. This approach tracks how data evolves over time. It is the right choice when you need to answer questions about the past, such as "what was the customer's address when they placed this order" or "how has the product price changed over time." SCD type 2 is more complex than SCD type 1 because it produces multiple rows per source entity. Each version has a validity period, recorded in the `__START_AT` and `__END_AT` columns. The current version has a null in `__END_AT`.

SCD type 2 requires a `sequence_by` column. The sequence column determines the order of changes. When multiple changes occur for the same primary key, the connector uses the sequence column to determine which change is the most recent. The sequence column must be sortable. Common choices are a `last_modified` timestamp or a version number. The connector also requires primary keys to identify which rows belong to the same entity. Without primary keys, the connector cannot determine which rows should be grouped into a single history.

The following YAML example shows a table configuration for SCD type 2.

```yaml
# Table configuration for SCD type 2.
# The scd_type is set to SCD_TYPE_2, which preserves historical versions.
# The destination table includes __START_AT and __END_AT columns
# that record each version's active period.
table_configuration:
  scd_type: SCD_TYPE_2
  # The sequence_by column orders changes.
  # It is required for SCD type 2.
  # The connector uses this column to determine which change is the most recent
  # when multiple changes arrive for the same primary key.
  sequence_by: last_modified
  # The primary keys identify rows for merge operations.
  # They group multiple versions of the same entity into a single history.
  primary_keys:
    - customer_id
```

The example sets `scd_type` to `SCD_TYPE_2` and specifies `sequence_by` and `primary_keys`. The `sequence_by` column is `last_modified`. The primary key is `customer_id`. The destination table will include `__START_AT` and `__END_AT` columns.

The `__START_AT` column records the time when the version became active. The `__END_AT` column records the time when the version became inactive. For the current version, `__END_AT` is null. The following table shows an example of an SCD type 2 table for a customer whose address changed twice.

| customer_id | address | __START_AT | __END_AT |
|---|---|---|---|
| 1 | 123 Main St | 2024-01-01 | 2024-06-15 |
| 1 | 456 Oak Ave | 2024-06-15 | 2024-09-20 |
| 1 | 789 Pine Rd | 2024-09-20 | null |

The table shows that the customer had three addresses over time. The first address was active from January 1, 2024, to June 15, 2024. The second address was active from June 15, 2024, to September 20, 2024. The third address became active on September 20, 2024, and is the current version, indicated by the null in `__END_AT`. To query the current address, you filter on `__END_AT IS NULL`. To query the address at a specific point in time, you filter on `__START_AT <= point_in_time AND (__END_AT > point_in_time OR __END_AT IS NULL)`.

The following SQL example shows how to query the current version of an SCD type 2 table.

```sql
-- Query the current version of each customer record.
-- The __END_AT column is null for the current version.
-- The double underscore prefix is part of the column name.
SELECT
  customer_id,
  address,
  __START_AT,
  __END_AT
FROM sales.silver.customers_history
-- Filter to the current version.
-- __END_AT IS NULL indicates an active record.
WHERE __END_AT IS NULL;
```

The equivalent PySpark query reads the same table and applies the same filter.

```python
# Import the col function for column references.
from pyspark.sql.functions import col

# Read the SCD type 2 table.
df_history = spark.read.table("sales.silver.customers_history")

# Filter to the current version of each record.
# __END_AT IS NULL indicates an active record.
df_current = df_history.filter(col("__END_AT").isNull())

# Display the current records.
display(df_current)
```

The queries show how to retrieve the current state from an SCD type 2 table. To query a historical state, you change the filter to match the point in time you are interested in.

## The sequence_by column

The `sequence_by` column is the column that determines the logical order of changes. It is required for SCD type 2 and optional for SCD type 1. It is also used by query-based connectors to track incremental progress. In the context of SCD, the `sequence_by` column tells the connector which change is the most recent when multiple changes arrive for the same primary key. This is important when changes arrive out of order. For example, if a row is updated twice in quick succession, the change events might arrive at the connector in reverse order. Without a `sequence_by` column, the connector might apply the older change last, leaving the destination with stale data. With a `sequence_by` column, the connector sorts the changes and applies the most recent one last.

The `sequence_by` column must be sortable. Common choices are a `last_modified` timestamp, a version number, or a monotonically increasing integer. The column must be present in the source data. If the source does not have a suitable column, you cannot use SCD type 2. For query-based connectors, the `sequence_by` column is the same as the cursor column. The connector uses it both to track progress and to order changes. For CDC connectors, the `sequence_by` column is separate from the CDC mechanism. The CDC log provides the changes, and the `sequence_by` column provides the order.

The following YAML example shows how to specify the `sequence_by` column in a table configuration.

```yaml
# Table configuration with sequence_by.
# The sequence_by column orders changes for SCD type 2.
# It is also used by query-based connectors to track incremental progress.
table_configuration:
  scd_type: SCD_TYPE_2
  # The sequence_by column determines the logical order of changes.
  # It must be a sortable column, such as a timestamp or a version number.
  # The connector uses it to resolve out-of-order changes.
  sequence_by: last_modified
```

The example sets `sequence_by` to `last_modified`. The connector uses this column to order changes. If two changes have the same `last_modified` value, the order is not deterministic. You should choose a column that is unique for each change or that has a tie-breaking mechanism.

## The __START_AT and __END_AT columns

When you enable SCD type 2, the destination table includes two additional columns: `__START_AT` and `__END_AT`. These columns record the validity period of each version. The `__START_AT` column records the time when the version became active. The `__END_AT` column records the time when the version became inactive. For the current version, `__END_AT` is null. The data type of these columns matches the data type of the `sequence_by` column. If `sequence_by` is a timestamp, the validity columns are timestamps. If `sequence_by` is an integer, the validity columns are integers.

The `__START_AT` and `__END_AT` columns are automatically added and maintained by the pipeline. You should not write to them directly. They are part of the destination table schema and are used by queries to retrieve the correct version at a point in time. The following table summarizes the meaning of the columns.

| Column | Meaning | Value for current version |
|---|---|---|
| `__START_AT` | When the version became active | The sequence value of the change |
| `__END_AT` | When the version became inactive | Null |

The table shows that the current version has a null in `__END_AT`. This is the standard convention for SCD type 2. To query the current version, you filter on `__END_AT IS NULL`. To query a historical version, you filter on `__START_AT <= point_in_time AND (__END_AT > point_in_time OR __END_AT IS NULL)`.

The `__START_AT` and `__END_AT` columns are also useful for auditing and debugging. You can see when each version of a record was created and when it was superseded. This helps you understand how the data has changed over time and whether the pipeline is capturing changes correctly.

## Additional extraction controls

Beyond snapshot versus incremental and SCD type, Lakeflow Connect offers several other controls over extraction behavior. These controls help you optimize the volume of data transferred, manage schema changes, and handle failures.

### Column selection

Not every column in the source table may be relevant for analytics. Lakeflow Connect lets you specify exactly which columns to include or exclude from ingestion. You use the `include_columns` or `exclude_columns` settings in the table configuration. With `include_columns`, only the listed columns are ingested. Newly added source columns do not automatically appear in the destination. With `exclude_columns`, all columns except the listed ones are ingested. New columns are included by default. Explicit column selection reduces data transfer volumes and storage costs. It is also a way to protect sensitive columns from being ingested into the lakehouse.

The following YAML example shows how to specify included columns.

```yaml
# Table configuration with explicit column selection.
# Only the listed columns are ingested.
# Newly added source columns do not automatically appear in the destination.
table_configuration:
  include_columns:
    - customer_id
    - order_date
    - total_amount
```

The example ingests only `customer_id`, `order_date`, and `total_amount`. Columns that are not listed are not ingested. This reduces the volume of data transferred and stored.

### Full refresh

In situations where incremental processing cannot recover from schema changes or data inconsistencies, you can trigger a full refresh. A full refresh clears the destination table and reloads all records from scratch. Lakeflow Connect minimizes downtime during a full refresh by maintaining the existing data until the new snapshot completes. You can also configure a full refresh window to schedule when these operations occur, avoiding disruption during peak business hours. Full refresh is a heavy operation. It reads the entire source table and rewrites the destination table. Use it sparingly and schedule it during off-peak hours.

### Multiple destinations

A single ingestion pipeline can write to multiple destination catalogs and schemas. This capability is useful when different teams need isolated copies of the same source data. You specify multiple objects in the ingestion definition, each with its own destination catalog and schema. You can even ingest the same source table to multiple destinations within the same schema by specifying a custom destination table name. This reduces the number of pipelines you need to manage and ensures that all copies are updated from the same source.

The following YAML example shows an ingestion definition with multiple destinations.

```yaml
# Ingestion definition with multiple destinations.
# The same source table is ingested to two different catalogs.
ingestion_definition:
  objects:
    # First destination: the sales.analytics schema.
    - table:
        source_table: customers
        destination_catalog: sales
        destination_schema: analytics
    # Second destination: the marketing.campaigns schema.
    - table:
        source_table: customers
        destination_catalog: marketing
        destination_schema: campaigns
```

The example ingests the `customers` table to both `sales.analytics.customers` and `marketing.campaigns.customers`. Each team has its own copy, and both copies are updated by the same pipeline.

## Schema enforcement, evolution, and expectations

Schema enforcement and evolution apply to extraction. When the connector writes to the destination table, Delta Lake enforces the table schema. If the source schema changes, such as a new column being added, the pipeline can evolve the target schema if schema evolution is enabled. Schema evolution adds the new column to the target table. Existing rows get null in the new column. If a column is dropped from the source, the pipeline may leave the column in the target table and stop populating it, or it may fail depending on the configuration. You should decide how to handle schema changes before enabling the pipeline.

Expectations are data quality rules that you define in Lakeflow Spark Declarative Pipelines. You can attach expectations to the destination table or to downstream tables. Expectations can drop, fail, or warn on rows that violate a rule. For example, you can define an expectation that `order_id` is not null. If a row violates the expectation, the pipeline can drop it before it reaches downstream tables. Expectations help you maintain data quality at the point of ingestion.

The following table summarizes the schema and quality controls.

| Control | Mechanism | Effect |
|---|---|---|
| Schema enforcement | Delta Lake write | Rejects writes that do not match the table schema |
| Schema evolution | Connector option | Adds new columns to the target table during ingestion |
| Expectations | Lakeflow Spark Declarative Pipelines | Drops, fails, or warns on rows that violate a rule |

The table shows that schema enforcement and evolution are about structure, while expectations are about data quality. Use schema enforcement to protect the table, schema evolution to handle legitimate schema changes, and expectations to validate business rules.

## Null handling, case sensitivity, and time zones

Null handling is important for extraction. The connector preserves nulls from the source. If a source column is null, the target column is null, provided the target column is nullable. If the target column is non-nullable, the write fails. Rows with a null cursor column are not ingested by query-based connectors. You should ensure that the cursor column is not null for rows that should be ingested, and that non-nullable columns in the target have a default or that the source does not produce nulls for those columns.

Case sensitivity affects string comparisons. By default, Spark's string comparisons are case-sensitive. If the source has inconsistent casing in a key column, joins and merges may not match rows that should match. You can normalize the case in a downstream transformation or use a case-insensitive collation if the table is configured for one. Unity Catalog supports collations at the column level.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. The connector writes timestamps in UTC. When you query the data, the session time zone determines how the timestamps are displayed. To avoid confusion, set the session time zone explicitly at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Use timestamp literals with explicit offsets when comparing to timestamps.

## Best practices

Choose incremental extraction when the source supports it. Incremental extraction is more efficient and places less load on the source. Use CDC for database connectors when the database supports it. Use a cursor column for query-based connectors when a reliable monotonically increasing column exists.

Use SCD type 1 when you only need the current state. SCD type 1 is simpler and keeps the destination table small. Use SCD type 2 when you need to track history. SCD type 2 is more complex but preserves the evolution of records over time.

Choose a reliable `sequence_by` column. The column must be sortable and must be updated on every change. If the column is not reliable, changes may be applied out of order, and the destination may reflect the wrong state.

Use explicit column selection to reduce data volume. Ingest only the columns you need. This reduces transfer volumes and storage costs, and it protects sensitive columns.

Schedule full refreshes during off-peak hours. Full refresh is a heavy operation. Use the full refresh window to avoid disrupting peak business hours.

Set the session time zone explicitly to UTC. This avoids off-by-hours errors when querying timestamps.

Monitor the cursor column for nulls and decreases. Nulls and decreases can cause rows to be skipped or re-ingested. Set up alerts for anomalies.

## Common mistakes and pitfalls

The most common mistake is choosing the wrong extraction mode. Using snapshot extraction for a large, frequently changing table is expensive and slow. Using incremental extraction when the source does not have a reliable cursor column can result in missing data.

A second mistake is using a cursor column that is not updated on every change. If the source application does not update the cursor column when a row changes, the query-based connector will miss the update. Verify that the cursor column is reliable.

A third mistake is not specifying a `sequence_by` column for SCD type 2. Without a `sequence_by` column, the connector cannot determine which change is the most recent. The destination may reflect an older version of the record.

A fourth mistake is using a non-unique `sequence_by` column. If multiple changes have the same sequence value, the order is not deterministic. Choose a column that is unique for each change or that has a tie-breaking mechanism.

A fifth mistake is forgetting that SCD type 2 creates multiple rows per entity. Queries that do not filter on `__END_AT IS NULL` will return historical versions and may produce incorrect aggregations. Always filter to the current version when you need the current state.

A sixth mistake is enabling schema evolution without communication. Adding columns changes the table schema and may break downstream consumers that expect a fixed set of columns.

A seventh mistake is not setting the session time zone. Timestamps are stored in UTC. If you compare them to local time without converting, you may get incorrect results.

## Testing extraction configuration

Test extraction configuration with a small source and a destination table that you can inspect. For CDC connectors, you can simulate changes in the source and verify that they appear in the destination. For query-based connectors, you can insert rows with different cursor values and verify that the connector ingests the correct rows. For SCD type 2, you can update a row multiple times and verify that the destination contains the correct history with accurate `__START_AT` and `__END_AT` values.

The following example shows a test for SCD type 2 behavior using a small DataFrame.

```python
from pyspark.sql import Row

# Create a small DataFrame that simulates an SCD type 2 table.
# The table has two versions of customer 1 and one version of customer 2.
# The __END_AT column is null for the current version.
scd_data = [
    Row(customer_id=1, address="123 Main St", __START_AT="2024-01-01", __END_AT="2024-06-15"),
    Row(customer_id=1, address="456 Oak Ave", __START_AT="2024-06-15", __END_AT=None),
    Row(customer_id=2, address="789 Pine Rd", __START_AT="2024-03-01", __END_AT=None),
]
df_scd = spark.createDataFrame(scd_data)

# Query the current version of each customer.
# __END_AT IS NULL indicates the current version.
df_current = df_scd.filter(df_scd.__END_AT.isNull())

# Assert that there are two current records.
assert df_current.count() == 2, f"Expected 2 current records, got {df_current.count()}"

# Assert that customer 1 has the current address 456 Oak Ave.
customer_1 = [row for row in df_current.collect() if row.customer_id == 1][0]
assert customer_1.address == "456 Oak Ave", f"Expected 456 Oak Ave, got {customer_1.address}"
```

The test verifies that the SCD type 2 table contains the correct current versions. Run tests like this in your CI pipeline against a small local Spark session. For pipeline configuration, validate the YAML before deploying it.

## Performance considerations

Incremental extraction is more efficient than snapshot extraction for large tables. It reads only the changed rows, so the volume of data transferred is proportional to the number of changes, not the size of the table. CDC has minimal impact on the source database because it reads the transaction log. Query-based connectors put query load on the source database, so the query should be efficient. Filter on the cursor column and select only the needed columns.

The ingestion gateway must be sized appropriately for the volume of changes. Deploy the gateway close to the source database to reduce network latency. The gateway runs continuously, so it consumes compute even when the pipeline is idle. Size the compute for the workload, because the initial snapshot can fail on undersized compute.

Destination table performance depends on file size and partitioning. The pipeline writes to Delta tables. It may create many small files during incremental ingestion. Run `OPTIMIZE` periodically to compact small files. Use partitioning or liquid clustering on columns that are commonly used in filters.

Use the `availableNow` trigger for scheduled pipelines to process all available data and stop. This is more cost-effective than a continuously running cluster.

## Summary

Controlling data extraction behavior in Lakeflow Connect means choosing between snapshot and incremental extraction, selecting the right SCD type, and configuring the supporting settings such as the cursor column, column selection, and full refresh.

Snapshot extraction reads all rows from the source on each run. It is simple and predictable but expensive for large tables. Incremental extraction reads only changed rows. For database connectors, it uses change data capture to read the transaction log. For query-based connectors, it uses a cursor column—a monotonically increasing timestamp or integer column—to track new and updated rows. Incremental extraction is more efficient but requires either CDC or a reliable cursor column.

The SCD type setting determines how the destination handles changes. SCD type 1 overwrites existing records, so the destination reflects the current state. SCD type 2 preserves historical versions. When a row changes, the previous version is marked inactive and a new version is added. SCD type 2 requires a `sequence_by` column to order changes and produces `__START_AT` and `__END_AT` columns that record each version's active period. The current version has a null in `__END_AT`. To query the current state, filter on `__END_AT IS NULL`.

The `sequence_by` column determines the logical order of changes. It is required for SCD type 2 and optional for SCD type 1. It must be sortable and reliable. For query-based connectors, the `sequence_by` column is the same as the cursor column.

Additional controls include column selection, full refresh, and multiple destinations. Column selection reduces data volume and protects sensitive columns. Full refresh reloads the entire table and should be scheduled during off-peak hours. Multiple destinations let a single pipeline write to several catalogs and schemas.

Schema enforcement, schema evolution, and expectations apply to extraction. Null handling, case sensitivity, and time zones affect extraction and querying. Set the session time zone explicitly to UTC, normalize string casing, and handle nulls deliberately.

Best practices include choosing incremental extraction when possible, using SCD type 1 for current state and SCD type 2 for history, choosing a reliable `sequence_by` column, using explicit column selection, and scheduling full refreshes during off-peak hours. Common mistakes include choosing the wrong extraction mode, using an unreliable cursor column, forgetting the `sequence_by` column for SCD type 2, and forgetting to filter on `__END_AT IS NULL` when querying current state.

Test extraction configuration with small datasets that include multiple changes and verify that the destination contains the correct current and historical records. Performance depends on the extraction mode and the volume of changes. Incremental extraction with CDC is the most efficient. Query-based extraction puts load on the source, so optimize the query. Compact small files in the destination table and set the session time zone explicitly.

By understanding these controls, you can configure Lakeflow Connect pipelines that extract data efficiently, preserve the history you need, and keep the destination table consistent with the source.
