## Configure ingestion pipelines

Configuring an ingestion pipeline means defining the connection, the objects to extract, the destination in Unity Catalog, and the schedule that drives the flow of data. In Lakeflow Connect, you can perform this configuration through several surfaces: the Databricks UI, Asset Bundles, notebooks, and the command-line interface. Each surface produces the same underlying pipeline definition. The UI is the simplest for initial setup because it guides you through the steps with a wizard. Asset Bundles are the right choice for version-controlled, repeatable deployments across environments. Notebooks and the SDK give you programmatic control for automation and integration with existing code. The CLI is useful for scripting and for environments where a graphical interface is not available.

The choice of surface does not change what the pipeline does. It changes how you create and manage it. A pipeline created in the UI can be updated with an Asset Bundle, and a pipeline created with the SDK can be viewed in the UI. The pipeline definition is stored in the workspace and references the connection and the ingestion gateway. Understanding the configuration surfaces helps you choose the one that fits your workflow. If you are exploring a new source, the UI is fastest. If you are deploying to production, Asset Bundles give you reproducibility and code review. If you are building a custom orchestration layer, the SDK or CLI gives you the control you need.

These notes cover the configuration of ingestion pipelines from first principles. They explain the four configuration surfaces and when to use each. They walk through a complete scenario of ingesting customer order data from SQL Server, showing the UI steps and the equivalent Asset Bundle definition. They show how to configure pipelines with the CLI and the Python SDK. They explain the role of the ingestion gateway, the destination catalog and schema, and the streaming tables that the pipeline creates. They also cover schema enforcement, schema evolution, expectations, null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand how to configure an ingestion pipeline for any supported source.

## Configuration surfaces for ingestion pipelines

Four surfaces are available for configuring ingestion pipelines: the Databricks UI, Asset Bundles, notebooks, and the CLI. Each surface targets a different workflow. The UI is interactive and guided. Asset Bundles are declarative and version-controlled. Notebooks and the SDK are programmatic. The CLI is scriptable. All four produce the same pipeline definition, so you can switch between them as your needs change.

The following table compares the surfaces.

| Surface | Best for | Version control | Repeatability | Learning curve |
|---|---|---|---|---|
| Databricks UI | Initial setup, exploration | No | Manual | Low |
| Asset Bundles | Production deployments, CI/CD | Yes | High | Medium |
| Notebooks and SDK | Automation, custom orchestration | Yes, if notebooks are in Git | High | Medium |
| CLI | Scripting, headless environments | Yes, if scripts are in Git | High | Medium |

The table shows that the UI is the easiest to start with but the hardest to reproduce. Asset Bundles are the recommended approach for production because they are declarative and can be stored in Git, reviewed, and deployed consistently. Notebooks and the SDK are useful when the pipeline configuration depends on dynamic values or when it is part of a larger orchestration. The CLI is useful for one-off commands and for environments where the UI is not accessible.

In practice, many teams start with the UI to understand the source and the options, then move to Asset Bundles for production. The UI generates a pipeline definition that you can export and adapt. This is a common and effective workflow. The rest of these notes describes each surface and shows how to configure the same pipeline in each.

## Walkthrough: ingesting SQL Server data through the UI

Consider a scenario where you need to ingest customer order data from a SQL Server database into Unity Catalog. The source table is `dbo.orders` in the `SalesDB` database. The target is the `sales.bronze.orders` table. The pipeline should run continuously to capture changes with low latency. The following steps describe how to configure this pipeline through the Databricks UI.

First, you navigate to the Data Ingestion section of the workspace and select SQL Server as the source type. The wizard opens and asks you to create or select an ingestion gateway. The gateway is the agent that reads the SQL Server transaction log and forwards changes to Databricks. If you have not created a gateway, the wizard guides you through the process. You provide the host and port of the SQL Server instance, the credentials for the gateway user, and the network configuration. The gateway must have network access to both the SQL Server instance and Databricks. Once the gateway is running, the wizard confirms the connection.

Second, you select or create a connection. The connection stores the credentials and endpoint information for the source. You provide the host, port, database name, and credentials. In production, you should store the credentials in a secret scope and reference them in the connection. The wizard lets you test the connection before proceeding.

Third, you choose the tables to ingest. The wizard lists the tables available in the source database. You select `dbo.orders`. You then specify the destination catalog and schema. In this scenario, the destination is `sales.bronze`. The wizard shows the fully qualified target table name, `sales.bronze.orders`, and lets you confirm. You can also choose whether to ingest the full table or only changes, and whether to enable schema evolution.

Fourth, you set the pipeline schedule. For a CDC pipeline, the schedule is usually continuous, so the pipeline runs as long as the cluster is available. You can also set a specific schedule if you prefer. The wizard creates the pipeline and starts it. The target table appears in Unity Catalog as a streaming table.

The following YAML example shows the equivalent Asset Bundle definition for the same pipeline.

```yaml
# Asset Bundle definition for the SQL Server ingestion pipeline.
# The resources section defines the pipelines managed by this bundle.
resources:
  pipelines:
    # The pipeline_sqlserver key is a logical name used within the bundle.
    pipeline_sqlserver:
      # The display name of the pipeline in the Databricks workspace.
      name: customer-orders-pipeline
      # The target catalog in Unity Catalog.
      catalog: sales
      # The target schema in Unity Catalog.
      schema: bronze
      # The ingestion definition specifies the gateway and the objects to ingest.
      ingestion_definition:
        # The ingestion gateway reads the SQL Server transaction log.
        # The ID references a gateway resource defined elsewhere in the bundle.
        ingestion_gateway_id: ${resources.pipelines.gateway.id}
        # The objects list names the source tables and their destinations.
        objects:
          # Each object maps one source table to one target table.
          - table:
              # The schema of the source table in SQL Server.
              source_schema: dbo
              # The name of the source table in SQL Server.
              source_table: orders
              # The destination catalog in Unity Catalog.
              destination_catalog: sales
              # The destination schema in Unity Catalog.
              destination_schema: bronze
```

The YAML defines a pipeline named `customer-orders-pipeline` in the `sales` catalog and `bronze` schema. The `ingestion_definition` section references the ingestion gateway and lists the objects to ingest. Each object maps a source schema and table to a destination catalog and schema. The destination table name defaults to the source table name, so the target is `sales.bronze.orders`. The `${resources.pipelines.gateway.id}` syntax references another resource in the bundle, which is how Asset Bundles link resources together. This makes the bundle portable across environments because the gateway ID is resolved at deployment time.

With this configuration, the pipeline extracts the `orders` table from the source database and loads it into `sales.bronze.orders` in Unity Catalog. The target table is a streaming table, which means it is continuously updated as changes arrive. Streaming tables are Delta tables with additional metadata that marks them as the target of a streaming pipeline. They support all Delta Lake features, including time travel and schema evolution. You can query them with SQL and PySpark like any other Delta table.

## Configuring pipelines with Asset Bundles

Asset Bundles are the recommended approach for production deployments. A bundle is a collection of resources defined in YAML files and stored in a Git repository. You use the Databricks CLI to validate, deploy, and run the bundle. Bundles support multiple environments, such as development, staging, and production, by using variables and targets. This makes it easy to promote a pipeline from one environment to another without changing the configuration.

The following example shows a more complete Asset Bundle definition with a gateway, a connection, and a pipeline that ingests multiple tables.

```yaml
# Asset Bundle definition for a SQL Server ingestion setup.
# The bundle includes a gateway, a connection, and a pipeline.
bundle:
  # The name of the bundle.
  name: sales-ingestion

# Variables are resolved at deployment time.
# They allow the same bundle to be deployed to different environments.
variables:
  # The catalog where the target tables are created.
  catalog:
    default: sales
  # The schema where the target tables are created.
  schema:
    default: bronze

# Resources are the Databricks objects managed by this bundle.
resources:
  # The ingestion gateway that reads the SQL Server transaction log.
  gateways:
    sqlserver_gateway:
      name: sqlserver-gateway
      # The gateway connection details are environment-specific.
      # In production, these would come from a secret scope.
      connection:
        host: sqlserver.internal.example.com
        port: 1433
  # The connection that stores the source credentials.
  connections:
    sqlserver_connection:
      name: sqlserver-connection
      connection_type: SQLSERVER
      options:
        host: sqlserver.internal.example.com
        port: "1433"
        database: SalesDB
        user: cdc_user
        # The password references a secret scope.
        password: "{{secrets/sqlserver/cdc_password}}"
  # The ingestion pipeline that uses the gateway and connection.
  pipelines:
    sales_pipeline:
      name: sales-ingestion-pipeline
      # The target catalog and schema use the bundle variables.
      catalog: ${var.catalog}
      schema: ${var.schema}
      ingestion_definition:
        # The gateway ID is resolved from the gateway resource.
        ingestion_gateway_id: ${resources.gateways.sqlserver_gateway.id}
        # The connection name is resolved from the connection resource.
        connection_name: ${resources.connections.sqlserver_connection.name}
        # The objects list names the tables to ingest.
        objects:
          - table:
              source_schema: dbo
              source_table: orders
              destination_catalog: ${var.catalog}
              destination_schema: ${var.schema}
          - table:
              source_schema: dbo
              source_table: order_items
              destination_catalog: ${var.catalog}
              destination_schema: ${var.schema}
          - table:
              source_schema: dbo
              source_table: customers
              destination_catalog: ${var.catalog}
              destination_schema: ${var.schema}
```

The bundle defines a gateway, a connection, and a pipeline. The gateway and connection are separate resources so that they can be reused by other pipelines. The pipeline references them using the `${resources...}` syntax. The `catalog` and `schema` variables allow the same bundle to be deployed to different environments. For example, you could deploy to a development environment with `catalog=dev` and `schema=bronze`, and to production with `catalog=sales` and `schema=bronze`. The pipeline definition does not change.

To deploy the bundle, you run the Databricks CLI commands `databricks bundle validate` and `databricks bundle deploy`. The validate command checks the YAML for syntax and reference errors. The deploy command creates or updates the resources in the workspace. You can then run the pipeline with `databricks bundle run`. The following example shows the commands.

```bash
# Validate the bundle before deploying.
# This checks the YAML syntax and resolves references.
databricks bundle validate

# Deploy the bundle to the default target.
# This creates or updates the gateway, connection, and pipeline.
databricks bundle deploy

# Run the pipeline.
# The pipeline name is the logical name defined in the bundle.
databricks bundle run sales_pipeline
```

The commands deploy the bundle and start the pipeline. The pipeline runs continuously if the schedule is continuous. You can monitor it in the UI or with the CLI. The bundle can be stored in Git, so changes are reviewed and tracked like any other code.

## Configuring pipelines with the CLI

The Databricks CLI provides commands for creating and managing pipelines without a bundle. This is useful for one-off commands or for scripting in environments where bundles are not used. The CLI commands mirror the API, so you can create a pipeline by providing a JSON definition. The following example shows how to create a pipeline with the CLI.

```bash
# Create an ingestion pipeline using the Databricks CLI.
# The pipeline definition is provided as a JSON file.
databricks pipelines create --json '{
  "name": "customer-orders-pipeline",
  "catalog": "sales",
  "schema": "bronze",
  "ingestion_definition": {
    "ingestion_gateway_id": "my-gateway-id",
    "connection_name": "sqlserver-connection",
    "objects": [
      {
        "table": {
          "source_schema": "dbo",
          "source_table": "orders",
          "destination_catalog": "sales",
          "destination_schema": "bronze"
        }
      }
    ]
  }
}'
```

The CLI command creates a pipeline with the specified name, catalog, schema, and ingestion definition. The `ingestion_gateway_id` and `connection_name` reference existing resources. The command returns the pipeline ID, which you can use to start, stop, or update the pipeline. The CLI is useful for automation scripts and for creating pipelines in CI/CD systems that do not use Asset Bundles.

## Configuring pipelines with notebooks and the SDK

The Python SDK provides a programmatic way to create and manage pipelines. This is useful when the pipeline configuration depends on dynamic values, such as a list of tables read from a configuration file, or when the pipeline is part of a larger workflow. The following example shows how to create a pipeline with the SDK.

```python
# Import the Databricks SDK for Python.
from databricks.sdk import WorkspaceClient
from databricks.sdk.service import pipelines

# Create a WorkspaceClient using the default authentication.
# In a notebook, the client uses the notebook's credentials.
w = WorkspaceClient()

# Create the ingestion pipeline.
# The pipeline references an existing gateway and connection.
# The objects list names the source tables and their destinations.
pipeline = w.pipelines.create(
    name="customer-orders-pipeline",
    catalog="sales",
    schema="bronze",
    ingestion_definition=pipelines.IngestionDefinition(
        ingestion_gateway_id="my-gateway-id",
        connection_name="sqlserver-connection",
        objects=[
            pipelines.IngestionObject(
                table=pipelines.TableIngestion(
                    source_schema="dbo",
                    source_table="orders",
                    destination_catalog="sales",
                    destination_schema="bronze"
                )
            )
        ]
    )
)

# Print the pipeline ID for reference.
print(f"Created pipeline: {pipeline.pipeline_id}")
```

The SDK example creates the same pipeline as the UI and the Asset Bundle. The pipeline ID is returned and can be used to start, stop, or update the pipeline. The SDK is useful when you need to create pipelines dynamically or when you want to integrate pipeline creation into a larger Python application.

Once the pipeline is created and running, you query the target table with SQL and PySpark. The following SQL example reads the ingested orders.

```sql
-- Query the ingested orders table.
-- The table is a streaming table in the sales.bronze schema.
-- Streaming tables support all Delta Lake features.
SELECT
  order_id,
  customer_id,
  order_date,
  total_amount
FROM sales.bronze.orders
-- Filter to orders placed in the last 30 days.
WHERE order_date >= current_date() - INTERVAL 30 DAYS
-- Order by order date, most recent first.
ORDER BY order_date DESC;
```

The equivalent PySpark query reads the same table and applies the same filter.

```python
# Import the functions needed for the filter.
from pyspark.sql.functions import col, current_date, date_sub

# Read the ingested orders table.
df_orders = spark.read.table("sales.bronze.orders")

# Filter to orders placed in the last 30 days.
df_recent = df_orders.filter(
    col("order_date") >= date_sub(current_date(), 30)
)

# Select the columns of interest and order by order date.
df_result = df_recent.select(
    "order_id",
    "customer_id",
    "order_date",
    "total_amount"
).orderBy(col("order_date").desc())

# Display the result.
display(df_result)
```

The queries show that the ingested data is available as a standard Delta table. You can join it, aggregate it, and transform it like any other table in Unity Catalog.

## Streaming tables as the destination

Ingestion pipelines write to streaming tables. A streaming table is a Delta table that is continuously updated by a streaming pipeline. It is registered in Unity Catalog and supports all Delta Lake features, including ACID transactions, time travel, and schema evolution. The difference between a streaming table and a regular Delta table is that the streaming table is marked as the target of a streaming pipeline. This means that the pipeline manages the table's contents, and you should not write to it directly. If you need to transform the data, you read from the streaming table and write to a new table.

Streaming tables have some restrictions. They do not support all write operations. For example, you cannot run an `UPDATE` or `DELETE` statement directly on a streaming table. You can read from it and write to another table. If you need to modify the data, you use a downstream table, such as a silver or gold table, and apply the transformations there. This separation keeps the ingestion layer clean and makes it easy to reprocess the data if needed.

The following table compares streaming tables with regular Delta tables.

| Aspect | Streaming table | Regular Delta table |
|---|---|---|
| Updated by | Streaming pipeline | Any write operation |
| Write restrictions | No direct `UPDATE` or `DELETE` | Supports all writes |
| Use case | Ingestion target | Transformation target, silver and gold layers |
| Time travel | Yes | Yes |
| Schema evolution | Yes, controlled by the pipeline | Yes, controlled by the writer |

The table shows that streaming tables are specialized for ingestion. They are the landing point for data from external sources. Downstream transformations read from streaming tables and write to regular Delta tables.

## Schema enforcement, evolution, and expectations

Schema enforcement and evolution apply to ingestion pipelines. When the pipeline writes to the streaming table, Delta Lake enforces the table schema. If the source schema changes, such as a new column being added, the pipeline can evolve the target schema if schema evolution is enabled. Schema evolution adds the new column to the target table. Existing rows get null in the new column. If a column is dropped from the source, the pipeline may leave the column in the target table and stop populating it, or it may fail depending on the configuration. You should decide how to handle schema changes before enabling the pipeline.

Expectations are data quality rules that you define in Lakeflow Spark Declarative Pipelines. You can attach expectations to the streaming table or to downstream tables. Expectations can drop, fail, or warn on rows that violate a rule. For example, you can define an expectation that `order_id` is not null. If a row violates the expectation, the pipeline can drop it before it reaches downstream tables. Expectations help you maintain data quality at the point of ingestion.

The following example shows a Lakeflow Spark Declarative Pipeline that reads from a streaming table and applies an expectation.

```python
import dlt
from pyspark.sql.functions import col

# Define a silver table that reads from the bronze streaming table.
# The @dlt.expect_or_drop decorator defines an expectation that drops rows
# where the amount is null or negative.
@dlt.table(
    name="silver_orders",
    comment="Cleaned orders from the bronze streaming table"
)
@dlt.expect_or_drop("valid_amount", "total_amount > 0")
def silver_orders():
    return (dlt.read("sales.bronze.orders")
            .filter(col("total_amount").isNotNull()))
```

The example defines a silver table that reads from the bronze streaming table. The expectation `valid_amount` drops rows where the amount is not positive. This ensures that only valid orders reach the silver layer.

## Null handling, case sensitivity, and time zones

Null handling is important for ingestion. The pipeline preserves nulls from the source. If a source column is null, the target column is null, provided the target column is nullable. If the target column is non-nullable, the write fails. You should ensure that non-nullable columns in the target have a default or that the source does not produce nulls for those columns. If the source uses empty strings to represent missing values, you may want to convert them to nulls in a downstream transformation.

Case sensitivity affects string comparisons. By default, Spark's string comparisons are case-sensitive. If the source has inconsistent casing in a key column, joins and merges may not match rows that should match. You can normalize the case in a downstream transformation or use a case-insensitive collation if the table is configured for one. Unity Catalog supports collations at the column level.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. The pipeline writes timestamps in UTC. When you query the data, the session time zone determines how the timestamps are displayed. To avoid confusion, set the session time zone explicitly at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Use timestamp literals with explicit offsets when comparing to timestamps.

## An end-to-end example

Consider a scenario where you ingest data from SQL Server into a bronze streaming table and then transform it into silver and gold tables. The following example shows the complete setup using Asset Bundles and Lakeflow Spark Declarative Pipelines.

The Asset Bundle defines the gateway, connection, and pipeline.

```yaml
bundle:
  name: sales-ingestion

variables:
  catalog:
    default: sales
  schema:
    default: bronze

resources:
  gateways:
    sqlserver_gateway:
      name: sqlserver-gateway
      connection:
        host: sqlserver.internal.example.com
        port: 1433
  connections:
    sqlserver_connection:
      name: sqlserver-connection
      connection_type: SQLSERVER
      options:
        host: sqlserver.internal.example.com
        port: "1433"
        database: SalesDB
        user: cdc_user
        password: "{{secrets/sqlserver/cdc_password}}"
  pipelines:
    sales_pipeline:
      name: sales-ingestion-pipeline
      catalog: ${var.catalog}
      schema: ${var.schema}
      ingestion_definition:
        ingestion_gateway_id: ${resources.gateways.sqlserver_gateway.id}
        connection_name: ${resources.connections.sqlserver_connection.name}
        objects:
          - table:
              source_schema: dbo
              source_table: orders
              destination_catalog: ${var.catalog}
              destination_schema: ${var.schema}
          - table:
              source_schema: dbo
              source_table: customers
              destination_catalog: ${var.catalog}
              destination_schema: ${var.schema}
```

The Lakeflow Spark Declarative Pipeline defines the silver and gold tables.

```python
import dlt
from pyspark.sql.functions import col, sum, count

# Define a silver orders table that reads from the bronze streaming table.
@dlt.table(
    name="silver_orders",
    comment="Cleaned orders from the bronze layer"
)
@dlt.expect_or_drop("valid_amount", "total_amount > 0")
def silver_orders():
    return (dlt.read("sales.bronze.orders")
            .filter(col("total_amount").isNotNull()))

# Define a silver customers table that reads from the bronze streaming table.
@dlt.table(
    name="silver_customers",
    comment="Cleaned customers from the bronze layer"
)
def silver_customers():
    return (dlt.read("sales.bronze.customers")
            .filter(col("customer_id").isNotNull()))

# Define a gold table that joins orders and customers and aggregates by region.
@dlt.table(
    name="gold_sales_by_region",
    comment="Total sales by customer region"
)
def gold_sales_by_region():
    orders = dlt.read("silver_orders")
    customers = dlt.read("silver_customers")
    joined = orders.join(customers, orders.customer_id == customers.customer_id, "inner")
    return (joined.groupBy("region")
            .agg(
                sum("total_amount").alias("total_sales"),
                count("*").alias("order_count")
            ))
```

The example shows the complete pipeline from ingestion to aggregation. The Asset Bundle defines the ingestion pipeline that writes to the bronze streaming tables. The Lakeflow Spark Declarative Pipeline reads from the bronze tables and produces silver and gold tables. All tables are in Unity Catalog and are governed.

## Best practices

Use Asset Bundles for production deployments. Bundles are declarative, version-controlled, and repeatable across environments. Store the bundle in Git and deploy with the Databricks CLI.

Create connections and gateways as separate resources so that they can be reused across pipelines. This reduces duplication and makes credential rotation easier.

Store credentials in a secret scope. Reference secrets in the connection definition using the `{{secrets/scope/key}}` syntax. Do not hardcode credentials.

Set the pipeline schedule to match the freshness requirement. Use continuous for CDC pipelines that need near-real-time data. Use a longer interval for query-based or SaaS pipelines that can tolerate more latency.

Enable schema evolution deliberately. Schema changes in the source can propagate to the target. Communicate changes to downstream consumers and test the impact before enabling evolution in production.

Define expectations for data quality. Attach expectations to the streaming table or to downstream tables. Expectations catch invalid rows early.

Monitor ingestion pipelines. Track metrics such as rows ingested, latency, and errors. Set up alerts for failures and for unusual patterns.

Use the UI for exploration and the Asset Bundles for production. The UI is fast for understanding a new source. The Asset Bundles are reliable for deployment.

## Common mistakes and pitfalls

The most common mistake is hardcoding credentials. Always use a secret scope. Hardcoded credentials are a security risk and are difficult to rotate.

A second mistake is not deploying the ingestion gateway. The gateway must be deployed in your environment and must have network access to both the source database and Databricks. Without the gateway, the pipeline cannot run.

A third mistake is choosing the wrong destination catalog or schema. The destination must exist in Unity Catalog, and you must have permission to create tables in it. Verify the destination before creating the pipeline.

A fourth mistake is not handling schema changes. If the source schema changes and schema evolution is not enabled, the ingestion pipeline will fail. Enable schema evolution and test it with a small change before relying on it in production.

A fifth mistake is not setting the session time zone. Timestamps are stored in UTC. If you compare them to local time without converting, you may get incorrect results.

A sixth mistake is writing directly to a streaming table. Streaming tables are managed by the pipeline. Writing to them directly can corrupt the pipeline's state. Use downstream tables for transformations.

A seventh mistake is not monitoring the pipeline. Ingestion pipelines can fail silently if not monitored. Set up alerts for failures and for latency spikes.

## Testing ingestion pipeline configuration

Test ingestion pipeline configuration with a small source and a target table that you can inspect. For CDC pipelines, you can simulate changes in the source and verify that they appear in the target. For query-based pipelines, you can insert rows with different cursor values and verify that the pipeline ingests the correct rows. For SaaS pipelines, you can use a sandbox instance of the application and verify that the pipeline extracts the expected objects.

You can also validate the bundle before deploying it. The `databricks bundle validate` command checks the YAML for syntax and reference errors. It resolves the resource references and reports any missing resources. This catches many configuration mistakes before they reach production.

The following example shows a test for a pipeline's schema evolution behavior. The test creates a source table, ingests it, adds a column to the source, and verifies that the column appears in the target.

```python
from pyspark.sql import Row
from delta.tables import DeltaTable

# Create a source DataFrame with two columns.
source_data = [
    Row(id=1, value="A"),
    Row(id=2, value="B"),
]
df_source = spark.createDataFrame(source_data)

# Write the source to a temporary table.
df_source.write.mode("overwrite").saveAsTable("tmp.source")

# Create a target table with the same schema.
df_source.write.mode("overwrite").saveAsTable("tmp.target")

# Add a new column to the source.
df_source_with_new = df_source.withColumn("new_col", lit("X"))
df_source_with_new.write.mode("overwrite").saveAsTable("tmp.source")

# Simulate the ingestion with schema evolution.
# In a real pipeline, the connector handles this automatically.
df_ingested = spark.read.table("tmp.source")
df_ingested.write.mode("append").option("mergeSchema", "true").saveAsTable("tmp.target")

# Verify that the new column appears in the target.
target_columns = spark.read.table("tmp.target").columns
assert "new_col" in target_columns, f"Expected new_col in {target_columns}"
```

Run tests like this in your CI pipeline against a small local Spark session. Clean up temporary tables after the test.

## Performance considerations

Performance depends on the connector type and the volume of data. CDC connectors have minimal impact on the source database because they read the transaction log. The ingestion gateway must be sized appropriately for the volume of changes. Deploy the gateway close to the source database to reduce network latency.

Query-based connectors put query load on the source database. The query should be efficient. Filter on the cursor column and select only the needed columns. Avoid joins and aggregations in the source query. Schedule the connector at a frequency that balances latency with source load.

SaaS connectors are limited by the API rate limits. If the source has a large volume of data, the initial snapshot may take a long time. Incremental extraction is faster because it only fetches changes.

Target table performance depends on file size and partitioning. The pipeline writes to Delta tables. It may create many small files during incremental ingestion. Run `OPTIMIZE` periodically to compact small files. Use partitioning or liquid clustering on columns that are commonly used in filters.

Use the `availableNow` trigger for scheduled pipelines to process all available data and stop. This is more cost-effective than a continuously running cluster.

Schema enforcement, schema evolution, and expectations apply to ingestion pipelines. Delta Lake enforces the table schema. Schema evolution adds new columns during ingestion. Expectations validate data quality and drop or flag invalid rows. Null handling, case sensitivity, and time zones affect ingestion and querying. Set the session time zone explicitly, normalize string casing, and handle nulls deliberately.

Best practices include using Asset Bundles for production, creating connections and gateways as separate resources, storing credentials in secret scopes, setting the schedule to match freshness requirements, enabling schema evolution deliberately, defining expectations, and monitoring pipelines. Common mistakes include hardcoding credentials, not deploying the gateway, choosing the wrong destination, ignoring schema changes, and writing directly to streaming tables.

Test ingestion pipelines with small sources and inspect the target tables. Validate Asset Bundles before deploying them. Performance depends on the connector type and the volume of data. Optimize source queries, size the gateway appropriately, and compact small files in the target tables.
