## Control processing with triggers

A trigger in Structured Streaming is the setting that determines when the streaming engine processes the next batch of data. Structured Streaming does not process each record individually by default. It groups incoming records into micro-batches and executes a query plan for each micro-batch. The trigger controls the cadence of those micro-batches. It decides whether the engine processes data continuously as soon as it arrives, at a fixed interval, or only when you explicitly ask it to process all available data and stop. The trigger is one of the most important configuration choices in a streaming pipeline because it directly affects latency, cost, and resource usage.

Triggers matter because streaming workloads have different requirements. A fraud detection pipeline might need to process each transaction within seconds. A nightly reporting pipeline might only need to process new data once an hour. A development pipeline might need to process all available data and stop so that the developer can inspect the result. Using the wrong trigger can lead to excessive cost, unnecessary latency, or a pipeline that never stops. The trigger is the control that matches the processing cadence to the business requirement.

These notes cover the trigger options available in Azure Databricks Structured Streaming. They explain the default trigger, the `processingTime` trigger, the `availableNow` trigger, the deprecated `once` trigger, and the continuous and real-time triggers. They explain how each trigger interacts with checkpoints, how to schedule streaming jobs with Databricks Jobs, and how triggers map to SQL streaming tables in Lakeflow Spark Declarative Pipelines. They also cover best practices, common mistakes, testing, performance, and an end-to-end example. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand how to control processing with triggers in any streaming pipeline.

## Understanding triggers and micro-batches

Structured Streaming processes data incrementally using a micro-batch execution model. When data arrives from the source, the engine groups the new records into a micro-batch. It applies the transformations to the micro-batch, writes the result to the sink, and updates the checkpoint. The trigger determines when the next micro-batch starts. The default trigger starts the next micro-batch as soon as the previous micro-batch completes. This provides the lowest latency because the engine is always working on the latest data. It also consumes compute continuously because the cluster remains active as long as the stream runs.

A trigger can change this behavior. The `processingTime` trigger processes data at fixed intervals. For example, `processingTime="10 seconds"` tells the engine to start a micro-batch every ten seconds, regardless of how much data has arrived. This reduces the number of micro-batches and can lower compute cost, at the expense of higher latency. The `availableNow` trigger processes all unprocessed data since the last checkpoint and then stops the stream. This is useful for scheduled jobs because the cluster can be shut down after the stream completes. The deprecated `once` trigger processes one micro-batch and stops. Continuous and real-time triggers provide lower latency than the default micro-batch model by processing data continuously rather than in discrete batches.

The following table summarizes the trigger options.

| Trigger | Behavior | Latency | Compute usage | Typical use |
|---|---|---|---|---|
| Default | Processes next batch as soon as previous completes | Lowest micro-batch latency | Continuous | Always-on streaming |
| `processingTime="10 seconds"` | Processes at fixed intervals | Depends on interval | Periodic | Controlled resource usage |
| `availableNow=True` | Processes all available data, then stops | Batch-like | Short-lived | Scheduled jobs |
| `once=True` | Processes one micro-batch, then stops | Batch-like | Short-lived | Deprecated; use availableNow |
| `continuous="1 second"` | Processes continuously with low latency | Very low | Continuous | Ultra-low-latency applications |
| `realTime=True` | Processes in real time with millisecond latency | Lowest | Continuous | Real-time applications |

The table shows that triggers trade off latency against compute usage. The default trigger provides the lowest micro-batch latency but uses compute continuously. The `availableNow` trigger provides batch-like latency but uses compute only while the job runs. The continuous and real-time triggers provide the lowest latency but require more resources and have more restrictions.

## The default trigger

The default trigger is used when you do not specify a trigger in `writeStream`. It processes the next micro-batch as soon as the previous micro-batch completes. If no new data is available, the engine waits for new data and starts a micro-batch when it arrives. This provides continuous processing with the lowest micro-batch latency. It is the right choice for always-on streaming pipelines that need to process data as soon as it arrives.

The following PySpark example shows a streaming write with the default trigger.

```python
# Import the functions needed for parsing.
from pyspark.sql.functions import col, from_json
from pyspark.sql.types import StructType, StructField, StringType, DoubleType

# Define the schema of the JSON payload.
schema = StructType([
    # The sensor_id identifies the device that produced the reading.
    StructField("sensor_id", StringType(), nullable=False),
    # The temperature is the measured value.
    StructField("temperature", DoubleType(), nullable=True),
])

# Read from a Kafka topic as a stream.
df_raw = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker:9092")
    .option("subscribe", "sensor-readings")
    .load())

# Parse the JSON payload from the value column.
df_parsed = (df_raw
    .select(from_json(col("value").cast("string"), schema).alias("data"))
    .select("data.*"))

# Write the stream to a Unity Catalog table without specifying a trigger.
# The default trigger processes the next micro-batch as soon as the
# previous micro-batch completes. The stream runs continuously until
# it is stopped.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/Volumes/manufacturing/checkpoints/sensor_readings")
    .toTable("manufacturing.bronze.sensor_readings"))
```

The example reads from Kafka, parses JSON, and writes to a Unity Catalog table. Because no trigger is specified, the default trigger is used. The stream runs continuously until it is stopped. The checkpoint location stores the progress. If the stream is stopped and restarted, it resumes from the checkpoint. The default trigger is suitable for always-on ingestion where low latency is required and compute cost is acceptable.

## The processingTime trigger

The `processingTime` trigger processes data at fixed intervals. You specify the interval as a string, such as `"10 seconds"`, `"1 minute"`, or `"1 hour"`. The engine starts a micro-batch at each interval, processes all data that has arrived since the previous micro-batch, and then waits for the next interval. This reduces the number of micro-batches and can lower compute cost because the engine is idle between intervals. The tradeoff is higher latency. Data that arrives just after a micro-batch starts must wait until the next interval.

The following PySpark example shows a streaming write with a `processingTime` trigger.

```python
# Write the stream with a processingTime trigger.
# The trigger processes a micro-batch every 30 seconds.
# Data that arrives between intervals is processed at the next interval.
# This reduces the number of micro-batches and lowers compute cost
# compared to the default trigger, at the expense of higher latency.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/Volumes/manufacturing/checkpoints/sensor_readings")
    .trigger(processingTime="30 seconds")
    .toTable("manufacturing.bronze.sensor_readings"))
```

The example processes a micro-batch every 30 seconds. If no new data has arrived, the engine still starts a micro-batch at the interval, but the micro-batch may be empty. The checkpoint records progress after each micro-batch. The `processingTime` trigger is useful when the source produces data at a known rate and you want to control the frequency of writes. It is also useful when the sink has limited throughput and you want to batch writes to reduce load.

## The availableNow trigger

The `availableNow` trigger processes all unprocessed data since the last checkpoint and then stops the stream. It is designed for scheduled jobs. You configure the trigger with `availableNow=True`. The engine processes all available data in one or more micro-batches, commits the results, updates the checkpoint, and stops. The next time the job runs, it resumes from the checkpoint and processes only the data that arrived since the previous run. This combines the efficiency of streaming, which processes only new data, with the predictability of scheduled batch jobs.

The following PySpark example shows a streaming write with the `availableNow` trigger.

```python
# Write the stream with the availableNow trigger.
# The trigger processes all unprocessed data since the last checkpoint
# and then stops the stream. The job can be scheduled with Databricks Jobs
# to run at regular intervals.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/Volumes/manufacturing/checkpoints/sensor_readings")
    .trigger(availableNow=True)
    .toTable("manufacturing.bronze.sensor_readings"))
```

The example processes all available data and stops. If the stream is run again, it resumes from the checkpoint and processes only new data. The `availableNow` trigger is the recommended replacement for the deprecated `once` trigger. It is more flexible because it can process multiple micro-batches if the volume of data is large, whereas `once` processes only one micro-batch. The `availableNow` trigger is ideal for pipelines that need to run every few minutes or every hour. You can schedule the job with Databricks Jobs, and the cluster can be shut down between runs to save cost.

## The once trigger (deprecated)

The `once` trigger processes one micro-batch and then stops. It was the original way to process available data in a single batch. It is now deprecated. The `availableNow` trigger is the recommended replacement because it can process all available data, even if it requires multiple micro-batches. The `once` trigger is limited to one micro-batch, so it may not process all data if the volume is large. Do not use `once` in new pipelines. Use `availableNow` instead.

## Continuous and real-time triggers

Databricks supports continuous and real-time triggers for applications that need lower latency than the default micro-batch model. The continuous trigger uses a continuous processing mode that processes data with low latency, often in the range of milliseconds to seconds. You configure it with `trigger(continuous="1 second")`. The real-time trigger provides even lower latency. These triggers are more complex and have restrictions. Not all operations are supported. For example, some stateful operations may not be available. They also require more compute resources because the engine processes data continuously. Use them only when the latency requirement cannot be met by the default or `processingTime` triggers.

The following table compares continuous and real-time triggers with the default trigger.

| Trigger | Latency | Supported operations | Compute cost |
|---|---|---|---|
| Default | Seconds | All streaming operations | Continuous |
| `continuous="1 second"` | Milliseconds to seconds | Limited set | High |
| `realTime=True` | Milliseconds | Limited set | Very high |

The table shows that continuous and real-time triggers provide the lowest latency but have limited operation support and higher cost. Use them when the application requires sub-second latency and the operations you need are supported.

## Choosing a trigger

The choice of trigger depends on the latency requirement, the cost constraints, and the scheduling pattern. The following table maps common scenarios to the recommended trigger.

| Scenario | Recommended trigger | Reason |
|---|---|---|
| Always-on ingestion with low latency | Default | Processes data as soon as it arrives |
| Ingestion with moderate latency and controlled cost | `processingTime` | Processes at fixed intervals |
| Scheduled incremental processing | `availableNow` | Processes all new data and stops |
| Ultra-low-latency application | `continuous` or `realTime` | Processes data continuously with minimal latency |
| Development and testing | `availableNow` | Processes available data and stops for inspection |

The table shows that `availableNow` is the best choice for scheduled jobs. It combines streaming efficiency with batch predictability. The default trigger is best for always-on pipelines. The `processingTime` trigger is best when you need to control the frequency of writes. Continuous and real-time triggers are best for specialized low-latency applications.

## Triggers in SQL and Lakeflow Spark Declarative Pipelines

In SQL, you define streaming tables with `CREATE OR REFRESH STREAMING TABLE`. The trigger is not specified in the SQL statement. Instead, the pipeline that contains the streaming table has a mode: continuous or triggered. In continuous mode, the pipeline runs continuously and processes data as it arrives. In triggered mode, the pipeline runs on a schedule and processes available data, similar to the `availableNow` trigger. You configure the mode in the pipeline settings or in the Asset Bundle definition. The following YAML example shows a pipeline configured for triggered mode.

```yaml
# Pipeline configuration for a triggered SQL pipeline.
# The pipeline runs on a schedule and processes available data.
resources:
  pipelines:
    sensor_pipeline:
      name: sensor-pipeline
      catalog: manufacturing
      schema: bronze
      # The continuous property is set to false for triggered mode.
      # In triggered mode, the pipeline processes available data and stops.
      continuous: false
      # The schedule defines when the pipeline runs.
      schedule:
        quartz_cron_expression: "0 0 * * * *"
        timezone_id: "UTC"
```

The example configures a pipeline to run every hour in triggered mode. The SQL streaming tables inside the pipeline are processed when the pipeline runs. The checkpoint is managed by the pipeline. This is the SQL equivalent of the `availableNow` trigger. For continuous mode, set `continuous: true`. The pipeline runs continuously and processes data as it arrives.

## Schema enforcement, null handling, and time zones

Triggers do not change schema enforcement, null handling, or time zone behavior. Schema enforcement is handled by Delta Lake when the stream writes to the target table. Null handling is determined by the transformations in the stream. Time zones affect timestamps in the data, not the trigger. Set the session time zone explicitly to UTC at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")` to avoid off-by-hours errors. The trigger only controls when micro-batches run, not how data is parsed or written.

## Best practices

Choose the trigger that matches the latency requirement and the cost constraint. Use the default trigger for always-on low-latency ingestion. Use `processingTime` when you need to control the frequency of writes. Use `availableNow` for scheduled incremental processing.

Use `availableNow` with Databricks Jobs. Schedule the job to run at the desired interval. The cluster can be shut down between runs, which reduces cost.

Always configure a checkpoint location. The checkpoint stores the progress of the stream and allows it to resume after a failure. Without a checkpoint, the stream cannot recover and may reprocess or lose data.

Do not use the deprecated `once` trigger. Use `availableNow` instead. It can process all available data, even if it requires multiple micro-batches.

Use continuous and real-time triggers only when the latency requirement cannot be met by the default or `processingTime` triggers. They have limited operation support and higher cost.

Monitor the stream. Track metrics such as input rate, processing rate, batch duration, and latency. Set up alerts for failures and for latency spikes.

## Common mistakes and pitfalls

The most common mistake is not configuring a checkpoint location. Without a checkpoint, the stream cannot recover from failures and may reprocess or lose data.

A second mistake is using the default trigger for a scheduled job. The default trigger runs continuously. If you want a scheduled job, use `availableNow` with Databricks Jobs.

A third mistake is using the deprecated `once` trigger. It processes only one micro-batch and may not process all available data. Use `availableNow` instead.

A fourth mistake is setting a `processingTime` interval that is too short. A very short interval increases overhead and compute cost without reducing latency significantly. Choose an interval that matches the data arrival rate and the latency requirement.

A fifth mistake is setting a `processingTime` interval that is too long. A long interval increases latency. Data that arrives just after a micro-batch starts must wait until the next interval.

A sixth mistake is using continuous or real-time triggers for operations that are not supported. Check the documentation for supported operations before using these triggers.

A seventh mistake is not monitoring the stream. Streaming queries can fail silently if not monitored. Set up alerts for failures and for latency spikes.

## Testing trigger behavior

Testing trigger behavior involves verifying that the stream processes data at the expected cadence and that it stops when expected. You can test the `availableNow` trigger by running a stream with a small dataset and verifying that it processes all data and stops. The following example shows a test for the `availableNow` trigger.

```python
from pyspark.sql import Row

# Create a small DataFrame and write it to a test source.
test_data = [
    Row(id=1, value="A"),
    Row(id=2, value="B"),
]
df_test = spark.createDataFrame(test_data)
df_test.write.mode("overwrite").saveAsTable("tmp.test_source")

# Read the source as a stream.
df_stream = spark.readStream.table("tmp.test_source")

# Write the stream with the availableNow trigger.
# The stream processes all available data and stops.
query = (df_stream
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/tmp/checkpoints/test_available_now")
    .trigger(availableNow=True)
    .toTable("tmp.test_target"))

# Wait for the stream to stop.
# The awaitTermination method blocks until the stream stops.
query.awaitTermination()

# Verify that the target table contains the expected rows.
assert spark.read.table("tmp.test_target").count() == 2
```

The test verifies that the `availableNow` trigger processes all available data and stops. Run tests like this in your CI pipeline against a small local Spark session. Clean up temporary tables and checkpoint directories after the test.

## Performance considerations

The trigger affects performance and cost. The default trigger provides the lowest latency but uses compute continuously. The `processingTime` trigger reduces compute usage by processing at intervals. The `availableNow` trigger uses compute only while the job runs, which is the most cost-effective for scheduled jobs.

Micro-batch size affects performance. Smaller micro-batches reduce latency but increase overhead. Larger micro-batches increase throughput but increase latency. The trigger controls the cadence, which affects the micro-batch size. A longer `processingTime` interval produces larger micro-batches because more data accumulates between intervals. A shorter interval produces smaller micro-batches.

Checkpointing adds overhead. The checkpoint is written on each micro-batch. The `availableNow` trigger writes a checkpoint at the end of the run and then stops. The default trigger writes a checkpoint on every micro-batch. Use a reliable storage location with low latency for the checkpoint.

Use the `availableNow` trigger with Databricks Jobs for scheduled pipelines. The cluster can be shut down between runs, which reduces cost. Use the default trigger for always-on pipelines that require low latency.

## An end-to-end example

Consider a scenario where sensor data arrives continuously from manufacturing equipment. You want to ingest the raw readings into a bronze table every hour. You use the `availableNow` trigger with a Databricks Job that runs every hour. The following PySpark example shows the complete pipeline.

```python
from pyspark.sql.functions import col, from_json
from pyspark.sql.types import StructType, StructField, StringType, DoubleType

# Define the schema of the JSON payload.
schema = StructType([
    StructField("sensor_id", StringType(), nullable=False),
    StructField("temperature", DoubleType(), nullable=True),
])

# Read from Kafka.
df_raw = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker:9092")
    .option("subscribe", "sensor-readings")
    .option("startingOffsets", "latest")
    .load())

# Parse the JSON payload.
df_parsed = (df_raw
    .select(from_json(col("value").cast("string"), schema).alias("data"))
    .select("data.*"))

# Write the stream with the availableNow trigger.
# The stream processes all available data and stops.
# The job runs every hour and processes only new data.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/Volumes/manufacturing/checkpoints/hourly_sensor_readings")
    .trigger(availableNow=True)
    .toTable("manufacturing.bronze.sensor_readings"))
```

The example reads from Kafka, parses JSON, and writes to a bronze table with the `availableNow` trigger. The job processes all available data and stops. The next run resumes from the checkpoint and processes only new data. This pattern combines the efficiency of streaming with the predictability of scheduled batch jobs.

Test trigger behavior with small datasets and verify that the stream processes data at the expected cadence and stops when expected.
