## Connect to Kafka and Event Hubs

A message bus is a system that receives streams of events from producers and delivers them to consumers. Apache Kafka is a distributed message bus that stores events in topics, which are partitioned and replicated logs. Azure Event Hubs is a managed message bus on Azure that provides an Apache Kafka-compatible endpoint. Because Event Hubs exposes a Kafka-compatible interface, you can use the same Kafka connector in Spark to read from both Kafka and Event Hubs. This unification means you write one set of code and change only the connection details and authentication. For cases where you need Event Hubs-specific features, Azure Databricks also provides a native Event Hubs connector that uses the `eventhubs` format. Both approaches let you ingest streaming data into Unity Catalog tables with exactly-once processing guarantees.

Message buses matter because they decouple producers from consumers. A sensor can publish a reading to a topic without knowing which applications will consume it. A consumer can read from the topic at its own pace, and multiple consumers can read the same topic independently. This decoupling enables scalable, fault-tolerant architectures. In a lakehouse, the message bus is often the entry point for real-time data. You read from Kafka or Event Hubs, parse the payloads, and write the results to Delta tables in Unity Catalog. The medallion architecture then takes over: bronze tables hold raw events, silver tables hold cleaned and conformed data, and gold tables hold aggregations for analytics.

These notes cover how to connect to Kafka and Event Hubs from Azure Databricks. They explain the Kafka-compatible interface, the native Event Hubs connector, the schemas they return, and how to parse the payloads. They show PySpark code examples with full comments. They also cover authentication with secrets, checkpointing, schema enforcement, null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example. The goal is that you can read these notes alone and understand how to build streaming ingestion pipelines from Kafka and Event Hubs into Unity Catalog.

## The Kafka-compatible interface

Apache Kafka uses a binary protocol for producing and consuming messages. Azure Event Hubs implements a compatible endpoint that speaks the Kafka protocol. This means that any Kafka client, including the Spark Kafka connector, can connect to Event Hubs by pointing to the Event Hubs namespace and providing the appropriate authentication. The benefit is code reuse. You write the same `spark.readStream.format("kafka")` code for both services. The only differences are the bootstrap servers and the security configuration.

The Kafka source in Spark returns a DataFrame with a fixed schema. The columns are `key`, `value`, `topic`, `partition`, `offset`, `timestamp`, and `timestampType`. The `key` and `value` columns are binary. The `topic`, `partition`, and `offset` columns identify where the message came from. The `timestamp` column is the time the message was appended to the topic, in the broker's time. The `timestampType` column indicates whether the timestamp is the create time or the log append time. The following table summarizes the schema.

| Column | Type | Description |
|---|---|---|
| `key` | binary | The message key, often used for partitioning |
| `value` | binary | The message payload |
| `topic` | string | The topic the message belongs to |
| `partition` | int | The partition within the topic |
| `offset` | long | The offset of the message within the partition |
| `timestamp` | timestamp | The time the message was appended |
| `timestampType` | int | The type of timestamp (0 = create time, 1 = log append time) |

Because `key` and `value` are binary, you typically cast them to string and parse the content. If the payload is JSON, you use `from_json`. If it is Avro, you use `from_avro`. If it is a custom format, you parse the string or bytes according to your format.

## Connecting to Kafka

The following example shows how to read from a Kafka topic. It uses the Kafka source, specifies the bootstrap servers and the topic, and sets the starting offsets.

```python
# Import the functions needed for parsing.
from pyspark.sql.functions import col, from_json
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, TimestampType

# Define the schema of the JSON payload.
# The schema describes the structure of the value column.
schema = StructType([
    # The device_id identifies the device that produced the reading.
    StructField("device_id", StringType(), nullable=False),
    # The temperature is the measured value.
    StructField("temperature", DoubleType(), nullable=True),
    # The reading_time is when the device produced the reading.
    StructField("reading_time", TimestampType(), nullable=True),
])

# Configure the Kafka source.
# The format is "kafka".
# The kafka.bootstrap.servers option specifies the Kafka cluster.
# The subscribe option names the topic to read from.
# The startingOffsets option determines where to begin when starting a new query.
# "latest" means start from new data only. Use "earliest" to read from the beginning.
df_raw = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker-server:9092")
    .option("subscribe", "sensor-readings")
    .option("startingOffsets", "latest")
    .load())

# Cast the value column to string and parse the JSON.
# The value column is binary, so cast it to string first.
# from_json parses the JSON string using the defined schema.
df_parsed = (df_raw
    .select(from_json(col("value").cast("string"), schema).alias("data"))
    .select("data.*"))
```

The example reads from a Kafka topic named `sensor-readings`. The `startingOffsets` option is set to `latest`, so the stream starts from new messages. If you want to read all messages from the beginning, set it to `earliest`. Once a checkpoint is configured, subsequent runs resume from the checkpoint and ignore `startingOffsets`. The `value` column is binary, so it is cast to string and parsed with `from_json`. The result is a streaming DataFrame with columns `device_id`, `temperature`, and `reading_time`.

## Connecting to Azure Event Hubs via the Kafka-compatible interface

Azure Event Hubs provides a Kafka-compatible endpoint. To connect, you point the Kafka connector to the Event Hubs namespace and configure SASL authentication. The bootstrap servers use the Event Hubs namespace followed by `.servicebus.windows.net:9093`. The security protocol is `SASL_SSL`, and the SASL mechanism is `PLAIN`. The username is the literal string `$ConnectionString`, and the password is the Event Hubs connection string. The following example shows how to configure the connection.

```python
# Retrieve the Event Hubs connection string from a secret scope.
# The connection string contains the namespace and the shared access key.
connection_string = dbutils.secrets.get(scope="eventhubs", key="connection-string")

# Define the Kafka options for Event Hubs.
# The bootstrap servers use the Event Hubs namespace and port 9093.
# The subscribe option names the Event Hub (which is a topic in Kafka terms).
# The SASL mechanism is PLAIN, and the security protocol is SASL_SSL.
# The JAAS config provides the username and password for authentication.
# The username is the literal string "$ConnectionString".
# The password is the connection string retrieved from the secret scope.
kafka_options = {
    "kafka.bootstrap.servers": "your-namespace.servicebus.windows.net:9093",
    "subscribe": "your-eventhub",
    "kafka.sasl.mechanism": "PLAIN",
    "kafka.security.protocol": "SASL_SSL",
    "kafka.sasl.jaas.config": f'kafkashaded.org.apache.kafka.common.security.plain.PlainLoginModule required username="$ConnectionString" password="{connection_string}";'
}

# Read the stream using the Kafka source with the Event Hubs options.
df_stream = (spark.readStream
    .format("kafka")
    .options(**kafka_options)
    .load())
```

The example retrieves the connection string from a secret scope and configures the Kafka options. The `options(**kafka_options)` unpacks the dictionary into individual options. The stream reads from the Event Hub named `your-eventhub` in the namespace `your-namespace`. The schema is the same as the Kafka schema: `key`, `value`, `topic`, `partition`, `offset`, `timestamp`, and `timestampType`. The `value` column contains the event payload as binary. You parse it the same way you parse Kafka messages.

## Using the native Event Hubs connector

Azure Databricks provides a native Event Hubs connector that uses the `eventhubs` format. This connector simplifies authentication and provides direct access to Event Hubs-specific features. It does not require the SASL configuration. You provide the connection string directly. The native connector returns a different schema than the Kafka-compatible interface. The event payload is stored in the `body` column instead of `value`. Additional Event Hubs metadata columns are included, such as `partition`, `offset`, `sequenceNumber`, `enqueuedTime`, `publisher`, `partitionKey`, `properties`, and `systemProperties`. The following table compares the schemas.

| Column | Kafka-compatible | Native Event Hubs |
|---|---|---|
| Payload | `value` (binary) | `body` (binary) |
| Key | `key` (binary) | `properties` or `partitionKey` |
| Topic | `topic` | Not applicable |
| Partition | `partition` | `partition` |
| Offset | `offset` | `offset` |
| Timestamp | `timestamp` | `enqueuedTime` |
| Additional metadata | `timestampType` | `sequenceNumber`, `publisher`, etc. |

The following example shows how to read from Event Hubs using the native connector.

```python
# Retrieve the Event Hubs connection string from a secret scope.
connection_string = dbutils.secrets.get(scope="eventhubs", key="connection-string")

# Read the stream using the native Event Hubs connector.
# The format is "eventhubs".
# The eventhubs.connectionString option provides the connection string.
# The eventhubs.consumerGroup option specifies the consumer group.
# The eventhubs.startingPosition option controls where to begin reading.
events = (spark.readStream
    .format("eventhubs")
    .option("eventhubs.connectionString", connection_string)
    .option("eventhubs.consumerGroup", "$Default")
    .option("eventhubs.startingPosition", '{"offset": "-1", "seqNo": -1, "enqueuedTime": null, "isInclusive": true}')
    .load())

# Extract the payload from the body column.
# The body column is binary, so cast it to string.
payload = events.selectExpr("CAST(body AS STRING) AS payload")
```

## Parsing the payload

Whether you use the Kafka-compatible interface or the native Event Hubs connector, the payload is binary. You must cast it to a string and parse it according to the format. JSON is the most common format. The following example shows how to parse JSON from the Kafka `value` column. The same approach applies to the `body` column of the native Event Hubs connector.

```python
# Import the from_json function and schema types.
from pyspark.sql.functions import from_json, col
from pyspark.sql.types import StructType, StructField, StringType, DoubleType

# Define the schema of the JSON payload.
schema = StructType([
    StructField("device_id", StringType(), nullable=False),
    StructField("temperature", DoubleType(), nullable=True),
])

# Parse the JSON payload from the value column.
# The value column is binary, so cast it to string first.
# from_json parses the JSON string using the defined schema.
# The result is a struct column. The select statement expands
# the struct into separate columns.
df_parsed = (df_raw
    .select(from_json(col("value").cast("string"), schema).alias("data"))
    .select("data.*"))
```

If the payload is Avro, you use `from_avro`. If it is a custom binary format, you use a user-defined function to parse the bytes. The schema you define must match the structure of the payload. If the payload has nested objects or arrays, the schema must reflect that. If the payload varies between messages, you can use the VARIANT data type to store the raw payload and extract fields later.

## Authentication and secrets management

Both Kafka and Event Hubs require authentication. For Kafka, you might use SASL/PLAIN, SASL/SCRAM, or SSL with client certificates. For Event Hubs, you use the connection string, which contains a shared access key. You should never hardcode credentials in notebooks or code. Use Databricks secret scopes to store credentials and retrieve them with `dbutils.secrets.get`. The following example shows how to store and retrieve a connection string.

```python
# Retrieve the connection string from a secret scope.
# The scope is named "eventhubs" and the key is "connection-string".
# The secret scope must be created before this code runs.
connection_string = dbutils.secrets.get(scope="eventhubs", key="connection-string")
```

Secret scopes are managed by Databricks and integrate with Azure Key Vault or Databricks-backed scopes. Using secret scopes ensures that credentials are not visible in notebook output or logs. You can also use service principals or managed identities for authentication to Event Hubs. For Kafka, you can use SASL with a username and password stored in a secret scope.

## Checkpointing and exactly-once semantics

Streaming ingestion from Kafka and Event Hubs requires a checkpoint location. The checkpoint stores the offsets of the messages that have been processed. If the stream fails and restarts, it resumes from the last checkpoint and does not reprocess or miss messages. The checkpoint location must be in reliable storage, such as cloud storage or a Unity Catalog volume. The following example shows how to write a stream to a Delta table with a checkpoint.

```python
# Write the parsed stream to a Unity Catalog table.
# The format is "delta".
# The outputMode "append" writes only new rows.
# The checkpointLocation stores the progress of the stream.
# The trigger "availableNow" processes all available data and stops.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/checkpoints/sensor_readings")
    .trigger(availableNow=True)
    .toTable("manufacturing.bronze.sensor_readings"))
```

The `checkpointLocation` is the directory where Spark stores the offsets and state. The `trigger(availableNow=True)` processes all available data and stops, which is useful for scheduled jobs. For continuous processing, omit the trigger or use `processingTime`. Exactly-once semantics are achieved when the source is replayable, the checkpoint is durable, and the sink is idempotent. Delta Lake is idempotent when the write is coordinated with the checkpoint update.

## Schema enforcement and evolution

Delta Lake enforces the schema of the target table. When you write a streaming DataFrame to a Delta table, Delta Lake compares the DataFrame schema with the table schema. If the DataFrame has extra columns, the write fails unless schema evolution is enabled. If the DataFrame is missing nullable columns, those columns are written as null. If a non-nullable column is missing, the write fails. You can enable schema evolution with the `mergeSchema` option. The following example shows a streaming write with schema evolution.

```python
# Write the stream with schema evolution enabled.
# The mergeSchema option allows the write to add new columns
# to the target table. Existing rows get null in the new columns.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/checkpoints/sensor_readings")
    .option("mergeSchema", "true")
    .toTable("manufacturing.bronze.sensor_readings"))
```

Schema evolution should be used deliberately. Adding a column changes the table schema and may break downstream consumers. In a medallion architecture, schema changes are usually managed in the bronze layer and propagated to silver and gold through transformations. Expectations in Lakeflow Spark Declarative Pipelines can validate data quality and drop or flag invalid rows.

## Null handling, case sensitivity, and time zones

Null handling in streaming ingestion follows the same rules as batch processing. Nulls in the payload are preserved unless you filter or replace them. If a target column is non-nullable, a null value causes the write to fail. You should handle nulls in the transformation step. For example, you can filter out rows with null keys or replace null values with a default using `coalesce`. The `key` column in Kafka can be null if the producer did not set a key. The `value` column is typically not null, but it can be empty. You should validate the payload and handle missing fields.

Case sensitivity affects string comparisons and column names. In Spark SQL, column names are case-insensitive by default. String values are case-sensitive. If the payload contains inconsistent casing, normalize it with `upper` or `lower`, or use a case-insensitive collation if the table is configured for one. The JSON field names are case-sensitive when using `from_json`. If the JSON has a field named `DeviceID` and your schema has `device_id`, the field will be null. Ensure that the schema matches the JSON field names exactly.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. The `timestamp` column from Kafka is in UTC. When you parse a timestamp from the payload, it is interpreted in the session time zone unless it includes an explicit offset. To avoid off-by-hours errors, set the session time zone explicitly at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Use timestamp literals with explicit offsets when comparing to timestamps. Store timestamps in UTC and convert to local time only for display.

## Best practices

Use secret scopes for credentials. Never hardcode connection strings or passwords in notebooks. Retrieve them with `dbutils.secrets.get`.

Always configure a checkpoint location. The checkpoint stores the progress of the stream and allows it to resume after a failure. Use reliable storage such as cloud storage or a Unity Catalog volume.

Define the payload schema explicitly. Schema inference is not supported for streaming sources. Use `from_json` with an explicit schema to parse the payload.

Use the Kafka-compatible interface for code portability. If you might switch between Kafka and Event Hubs, use the Kafka connector with the appropriate options. This allows you to reuse the same code.

Use the native Event Hubs connector when you need Event Hubs-specific features. The native connector provides additional metadata columns and simplifies authentication.

Set the session time zone explicitly to UTC. This avoids off-by-hours errors when parsing timestamps.

Use the `availableNow` trigger for scheduled jobs. It processes all available data and stops, which is more cost-effective than a continuously running cluster.

Monitor streaming queries. Track metrics such as input rate, processing rate, batch duration, and latency. Set up alerts for failures and for latency spikes.

## Common mistakes and pitfalls

The most common mistake is not configuring a checkpoint location. Without a checkpoint, the stream cannot recover from failures and may reprocess or lose data.

A second mistake is hardcoding credentials. Always use a secret scope. Hardcoded credentials are a security risk and are difficult to rotate.

A third mistake is using schema inference for the payload. Streaming sources do not support schema inference. Define the schema explicitly with `from_json` or `from_avro`.

A fourth mistake is mismatching the JSON field names and the schema. If the JSON field is `DeviceID` and the schema has `device_id`, the field will be null. Ensure that the schema matches the JSON exactly, including case.

A fifth mistake is not setting the session time zone. Timestamps are stored in UTC. If you compare them to local time without converting, you may get incorrect results.

A sixth mistake is using the wrong starting position. The `startingOffsets` option in Kafka and the `startingPosition` option in Event Hubs control where the stream begins. Once a checkpoint is configured, the starting position is ignored. If you need to reprocess data, you must use a new checkpoint location.

A seventh mistake is not monitoring the stream. Streaming queries can fail silently if not monitored. Set up alerts for failures and for latency spikes.

## Testing streaming ingestion

Testing streaming ingestion from Kafka and Event Hubs is challenging because the sources are external. You can test the parsing and transformation logic by using a batch DataFrame that simulates the streaming schema. The following example shows a test for parsing JSON from a Kafka-like DataFrame.

```python
from pyspark.sql import Row
from pyspark.sql.functions import from_json, col
from pyspark.sql.types import StructType, StructField, StringType, DoubleType

# Define the schema of the JSON payload.
schema = StructType([
    StructField("device_id", StringType(), nullable=False),
    StructField("temperature", DoubleType(), nullable=True),
])

# Create a batch DataFrame that simulates the Kafka source.
# The value column contains JSON strings.
test_data = [
    Row(value=b'{"device_id": "S1", "temperature": 100.0}'),
    Row(value=b'{"device_id": "S2", "temperature": 90.0}'),
]
df_test = spark.createDataFrame(test_data)

# Apply the same parsing logic used in the stream.
df_parsed = (df_test
    .select(from_json(col("value").cast("string"), schema).alias("data"))
    .select("data.*"))

# Verify the result.
rows = df_parsed.collect()
assert rows[0].device_id == "S1" and rows[0].temperature == 100.0
assert rows[1].device_id == "S2" and rows[1].temperature == 90.0
```

For end-to-end testing, you can use a test Kafka cluster or Event Hubs namespace. Produce test messages, run the stream with a `availableNow` trigger, and verify the output in the target table. Clean up the test resources after the test.

## Performance considerations

Streaming performance depends on the source, the processing logic, and the sink. Kafka and Event Hubs are designed for high throughput. The number of partitions in the topic determines the maximum parallelism. Spark reads from each partition in parallel. If the topic has few partitions, the stream is limited by the number of partitions. Ensure that the topic has enough partitions to support the desired throughput.

Micro-batch size affects latency and throughput. Smaller micro-batches reduce latency but increase overhead. Larger micro-batches increase throughput but increase latency. The default trigger processes data as soon as it arrives. You can use `processingTime` to control the interval.

State management is important for aggregations. Watermarks bound the state, but you should also monitor the state size. If the state grows too large, the stream may run out of memory. Use watermarks and windows to keep the state bounded.

Checkpointing adds overhead. The checkpoint is written on each micro-batch. Use a reliable storage location with low latency. Avoid using a location that is slow or has high contention.

Destination performance depends on file size and partitioning. The stream writes to Delta tables. It may create many small files. Run `OPTIMIZE` periodically to compact small files. Use partitioning or liquid clustering on columns that are commonly used in filters.

Use the `availableNow` trigger for scheduled jobs to process all available data and stop. This is more cost-effective than a continuously running cluster.

## An end-to-end example

Consider a scenario where sensor data arrives continuously from manufacturing equipment. You read the data from Kafka, parse the JSON payload, write the raw readings to a bronze table, compute 5-minute aggregates, and write the aggregates to a silver table. The following example shows the complete pipeline.

```python
from pyspark.sql.functions import (
    col, from_json, window, avg, max, min
)
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, TimestampType

# Define the schema of the JSON payload.
schema = StructType([
    StructField("sensor_id", StringType(), nullable=False),
    StructField("temperature", DoubleType(), nullable=True),
    StructField("reading_time", TimestampType(), nullable=True),
])

# Configure the Kafka source.
df_raw = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker:9092")
    .option("subscribe", "sensor-readings")
    .option("startingOffsets", "latest")
    .load())

# Parse the JSON payload.
df_parsed = (df_raw
    .select(from_json(col("value").cast("string"), schema).alias("data"))
    .select("data.*"))

# Write the raw readings to a bronze table.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/checkpoints/bronze_sensor_readings")
    .trigger(availableNow=True)
    .toTable("manufacturing.bronze.sensor_readings"))

# Compute 5-minute aggregates for a silver table.
df_aggregated = (df_parsed
    .withWatermark("reading_time", "2 minutes")
    .groupBy(window("reading_time", "5 minutes"), "sensor_id")
    .agg(
        avg("temperature").alias("avg_temperature"),
        max("temperature").alias("max_temperature"),
        min("temperature").alias("min_temperature")
    ))

# Write the aggregates to a silver table.
(df_aggregated
    .writeStream
    .format("delta")
    .outputMode("update")
    .option("checkpointLocation", "/checkpoints/silver_sensor_aggregates")
    .trigger(availableNow=True)
    .toTable("manufacturing.silver.sensor_aggregates"))
```

The example reads from Kafka, parses JSON, writes raw readings to a bronze table, computes 5-minute aggregates, and writes the aggregates to a silver table. The bronze write uses `append` mode. The silver write uses `update` mode. Both streams have their own checkpoint locations. The pipeline provides exactly-once processing and stores the data in Unity Catalog. The same pipeline can be adapted to Event Hubs by changing the source options and authentication.
