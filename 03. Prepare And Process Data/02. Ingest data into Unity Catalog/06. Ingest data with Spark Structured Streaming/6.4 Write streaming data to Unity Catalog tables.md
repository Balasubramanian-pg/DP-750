## Write streaming data to Unity Catalog tables

Writing streaming data to a Unity Catalog table means taking a streaming DataFrame produced by `spark.readStream` and persisting its rows to a Delta table registered in Unity Catalog. The write is performed with the `writeStream` API, which mirrors the batch `write` API but is designed for continuous or incremental execution. You specify the format as `delta`, choose an output mode, provide a checkpoint location, and call `toTable` with the three-level namespace of the target table. Unity Catalog governs the table, so permissions, lineage, and auditing apply automatically. The table is a Delta table, which provides ACID transactions, time travel, and schema enforcement. Streaming writes to Unity Catalog are the standard way to land real-time data in the lakehouse.

Streaming writes matter because many data sources produce data continuously and require low-latency ingestion. A batch job that runs every hour cannot support a dashboard that needs to reflect events within seconds. A streaming write processes each micro-batch as it arrives and commits the rows to the Delta table. The table is immediately queryable by SQL and PySpark. Downstream transformations can read from the streaming table and write to silver and gold tables. In a medallion architecture, streaming writes are most common in the bronze layer, where raw events land, but they can also be used in silver and gold when the transformations are incremental.

These notes cover how to write streaming data to Unity Catalog tables. They explain the `writeStream` API, the `toTable` method, and the role of checkpoints. They explain the three output modes—append, update, and complete—and when to use each. They show PySpark examples for writing streaming DataFrames to Unity Catalog tables, and SQL examples for defining streaming tables in Lakeflow Spark Declarative Pipelines. They also cover schema enforcement, schema evolution, null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand how to persist streaming data into Unity Catalog reliably and efficiently.

## The writeStream API and Unity Catalog integration

The `writeStream` API is the entry point for writing a streaming DataFrame. It returns a `DataStreamWriter` object. You configure it with the format, output mode, checkpoint location, and any options, and then call `toTable` or `start` to begin the stream. The `toTable` method writes to a Unity Catalog table. The table must be a Delta table. If the table does not exist, it is created with the schema of the streaming DataFrame. If the table exists, the stream appends or updates rows according to the output mode. Unity Catalog governs the table from the moment it is created.

The following table compares batch writes and streaming writes to Unity Catalog tables.

| Aspect | Batch write | Streaming write |
|---|---|---|
| API | `DataFrame.write` | `DataFrame.writeStream` |
| Execution | One job per write | Continuous or micro-batch |
| Target method | `saveAsTable` | `toTable` |
| Checkpoint | Not required | Required |
| Output modes | Not applicable | `append`, `update`, `complete` |
| Fault tolerance | Re-run the job | Checkpoint and resume |

The table shows that streaming writes require a checkpoint and an output mode, while batch writes do not. The `toTable` method is used for streaming writes, while `saveAsTable` is used for batch writes. Both create Delta tables in Unity Catalog.

The following PySpark example shows a basic streaming write to a Unity Catalog table.

```python
# Import the functions needed for parsing.
from pyspark.sql.functions import col, from_json
from pyspark.sql.types import StructType, StructField, StringType, DoubleType

# Define the schema of the JSON payload.
schema = StructType([
    # The sensor_id identifies the device that produced the reading.
    StructField("sensor_id", StringType(), nullable=False),
    # The temperature is the measured value.
    StructField("temperature", DoubleType(), nullable=True),
])

# Read from a Kafka topic as a stream.
df_raw = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker:9092")
    .option("subscribe", "sensor-readings")
    .load())

# Parse the JSON payload from the value column.
# The value column is binary, so cast it to string first.
df_parsed = (df_raw
    .select(from_json(col("value").cast("string"), schema).alias("data"))
    .select("data.*"))

# Write the parsed stream to a Unity Catalog table.
# The format is "delta".
# The outputMode "append" writes only new rows.
# The checkpointLocation stores the progress of the stream.
# The toTable method writes to the specified Unity Catalog table.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/Volumes/manufacturing/checkpoints/sensor_readings")
    .toTable("manufacturing.bronze.sensor_readings"))
```

The example reads from Kafka, parses JSON, and writes the result to `manufacturing.bronze.sensor_readings`. The `outputMode("append")` writes only new rows. The `checkpointLocation` stores the progress of the stream. The `toTable` method writes to the Unity Catalog table. The table is created if it does not exist. If it exists, the stream appends to it. Unity Catalog governs the table.

## Output modes: append, update, and complete

The output mode determines which records are written to the target table. There are three modes: `append`, `update`, and `complete`. The mode you choose depends on the operation and the destination. The following table summarizes the modes.

| Output mode | Behavior | Supported operations |
|---|---|---|
| `append` | Only new rows are written | Most operations, filters, joins |
| `update` | Changed rows are written | Aggregations without finalization |
| `complete` | All rows are rewritten | Aggregations with complete result |

The `append` mode is the default for most operations. It writes only new rows. It is used when the stream produces new rows and never updates existing ones. Filters, projections, and joins typically use `append` mode. For ingestion scenarios where you are appending raw data, `append` is the appropriate mode.

The `update` mode writes changed rows. It is used with aggregations that update the result as new data arrives. For example, a running total per customer is updated when a new transaction arrives. The `update` mode writes only the rows that changed, which is more efficient than rewriting the entire result.

The `complete` mode rewrites all rows on each trigger. It is used with aggregations that need the complete result, such as a global count. It is not supported for all operations and can be expensive because it rewrites the entire result. Use it only when necessary.

The following PySpark example shows an aggregation with `update` mode.

```python
# Import the aggregation functions.
from pyspark.sql.functions import col, sum, count

# Aggregate the stream by sensor.
# The groupBy and agg operations are supported on streaming DataFrames.
df_aggregated = (df_parsed
    .groupBy("sensor_id")
    .agg(
        sum("temperature").alias("total_temperature"),
        count("*").alias("reading_count")
    ))

# Write the aggregation with update mode.
# The update mode writes changed rows as new data arrives.
(df_aggregated
    .writeStream
    .format("delta")
    .outputMode("update")
    .option("checkpointLocation", "/Volumes/manufacturing/checkpoints/sensor_aggregates")
    .toTable("manufacturing.silver.sensor_aggregates"))
```

The example aggregates readings by sensor and writes the result with `update` mode. As new readings arrive, the totals for affected sensors are updated in the destination table. The `update` mode writes only the rows that changed, which is more efficient than rewriting the entire result.

## Writing streaming data to Unity Catalog tables with SQL

In addition to PySpark, you can write streaming data to Unity Catalog tables using SQL in Lakeflow Spark Declarative Pipelines. You define a streaming table with `CREATE OR REFRESH STREAMING TABLE`. The pipeline manages the checkpoint location automatically. You do not specify a checkpoint. The pipeline handles fault tolerance and exactly-once semantics. The following SQL example creates a streaming table from a Kafka source.

```sql
-- Create a streaming table from a Kafka source.
-- The pipeline manages the checkpoint location automatically.
-- The table is created in Unity Catalog and is governed by Unity Catalog.
CREATE OR REFRESH STREAMING TABLE manufacturing.bronze.sensor_readings
AS SELECT
    -- Parse the JSON payload from the Kafka value column.
    -- The value column is binary, so cast it to string.
    from_json(CAST(value AS STRING), 'sensor_id STRING, temperature DOUBLE').sensor_id AS sensor_id,
    from_json(CAST(value AS STRING), 'sensor_id STRING, temperature DOUBLE').temperature AS temperature
FROM STREAM read_kafka(
    bootstrapServers => 'broker:9092',
    subscribe => 'sensor-readings'
);
```

The SQL example uses the `read_kafka` function and a streaming table. The checkpoint is managed by the pipeline and stored in a location controlled by Databricks. You do not need to configure it manually. This is simpler than the PySpark approach, but it gives you less control over the checkpoint location. For pipelines that require a specific checkpoint location, use PySpark.

You can also define streaming tables that read from other streaming tables, creating a pipeline of transformations. The following SQL example defines a silver table that aggregates the bronze data.

```sql
-- Create a silver streaming table that aggregates the bronze data.
-- The table reads from the bronze streaming table.
-- The pipeline manages the checkpoint and state automatically.
CREATE OR REFRESH STREAMING TABLE manufacturing.silver.sensor_aggregates
AS SELECT
    sensor_id,
    -- Compute the average temperature per sensor.
    AVG(temperature) AS avg_temperature,
    -- Count the readings per sensor.
    COUNT(*) AS reading_count
FROM STREAM manufacturing.bronze.sensor_readings
GROUP BY sensor_id;
```

The silver table aggregates the bronze data. The pipeline handles the incremental processing. The table is in Unity Catalog and is governed. This declarative approach is the recommended way to build streaming pipelines in Databricks because it handles orchestration, checkpointing, and data quality.

## Schema enforcement and evolution

Delta Lake enforces the schema of the target table. When you write a streaming DataFrame to a Unity Catalog table, Delta Lake compares the DataFrame schema with the table schema. If the DataFrame has extra columns, the write fails unless schema evolution is enabled. If the DataFrame is missing nullable columns, those columns are written as null. If a non-nullable column is missing, the write fails. Schema enforcement protects the table from accidental corruption.

Schema evolution allows the stream to add new columns to the table. In PySpark, you enable it with the `mergeSchema` option. The following example shows a streaming write with schema evolution.

```python
# Write the stream with schema evolution enabled.
# The mergeSchema option allows the write to add new columns
# to the target table. Existing rows get null in the new columns.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/Volumes/manufacturing/checkpoints/sensor_readings")
    .option("mergeSchema", "true")
    .toTable("manufacturing.bronze.sensor_readings"))
```

The example enables schema evolution. If the streaming DataFrame has a column that the table does not have, the column is added to the table. If the table has columns that the DataFrame does not have, those columns are written as null if they are nullable. Schema evolution should be used deliberately. Adding a column changes the table schema and may break downstream consumers that expect a fixed set of columns.

In SQL streaming tables, schema evolution is handled by the pipeline. You can define expectations to validate data quality. Expectations can drop, fail, or warn on rows that violate a rule. For example, you can define an expectation that `sensor_id` is not null. If a row violates the expectation, the pipeline can drop it before it reaches the table.

## Null handling, case sensitivity, and time zones

Null handling in streaming writes follows the same rules as batch writes. Nulls in the source are preserved unless you filter or replace them. If a target column is non-nullable, a null value causes the write to fail. You should handle nulls in the transformation step. For example, you can filter out rows with null keys or replace null values with a default using `coalesce`. The checkpoint does not affect null handling; it only records progress.

Case sensitivity affects string comparisons and column names. In Spark SQL, column names are case-insensitive by default. String values are case-sensitive. If the payload contains inconsistent casing, normalize it with `upper` or `lower`, or use a case-insensitive collation if the table is configured for one. The checkpoint does not affect case sensitivity.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. The checkpoint stores offsets and state, which are time-agnostic. However, the data you process may include timestamps. Set the session time zone explicitly to UTC at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. This avoids off-by-hours errors when parsing timestamps.

## Checkpoints and fault tolerance

Every streaming write requires a checkpoint location. The checkpoint stores the progress of the stream and allows it to resume after a failure. Without a checkpoint, the stream cannot recover and may reprocess or lose data. The checkpoint location must be a reliable, durable storage path. Cloud storage and Unity Catalog volumes are the best choices. Do not use local disk.

Each streaming query must have its own unique checkpoint location. Sharing checkpoints between different queries causes data processing errors. The checkpoint stores the query plan and the offsets for a specific query. If two queries use the same checkpoint, they will conflict.

The following table summarizes the relationship between checkpoints, Delta Lake, and Unity Catalog.

| Aspect | Role |
|---|---|
| Delta Lake | Provides ACID transactions and idempotent writes |
| Unity Catalog | Governs the target table and the checkpoint volume |
| Checkpoint | Records progress and state for fault tolerance |
| Streaming query | Coordinates checkpoint updates with Delta Lake commits |

Exactly-once processing requires a replayable source, a durable checkpoint, and an idempotent sink. Delta Lake is idempotent when the write is coordinated with the checkpoint update. Structured Streaming coordinates the checkpoint update and the sink write so that they either both succeed or both fail.

## Best practices

Use a unique checkpoint location for each streaming query. Sharing checkpoints causes conflicts and data errors.

Store checkpoints in durable storage. Use cloud storage or a Unity Catalog volume. Do not use local disk.

Use Unity Catalog volumes for governance. Volumes are governed by Unity Catalog, so you can control access and audit usage.

Set the session time zone explicitly to UTC. This avoids off-by-hours errors when parsing timestamps.

Use the `append` output mode for raw ingestion. It writes only new rows and is the most efficient mode for ingestion workloads.

Use the `update` output mode for aggregations that produce updates. It writes only changed rows.

Use the `complete` output mode only when necessary. It rewrites all rows and can be expensive.

Enable schema evolution deliberately. Adding columns changes the table schema and may break downstream consumers.

Monitor streaming queries. Track metrics such as input rate, processing rate, batch duration, and latency. Set up alerts for failures and for latency spikes.

## Common mistakes and pitfalls

The most common mistake is not configuring a checkpoint location. Without a checkpoint, the stream cannot recover from failures and may reprocess or lose data.

A second mistake is sharing a checkpoint location between two queries. This causes conflicts and data errors.

A third mistake is using a local path for the checkpoint. Local paths are not durable and are lost when the cluster restarts.

A fourth mistake is using the wrong output mode. `append` is for new rows, `update` is for changed rows, and `complete` is for full rewrites. Using the wrong mode can produce incorrect results or fail.

A fifth mistake is enabling schema evolution without communicating the change. Adding columns changes the table schema and may break downstream consumers.

A sixth mistake is not setting the session time zone. Timestamps are stored in UTC. If you compare them to local time without converting, you may get incorrect results.

A seventh mistake is not monitoring the stream. Streaming queries can fail silently if not monitored. Set up alerts for failures and for latency spikes.

## Testing streaming writes

Testing streaming writes involves verifying that the stream writes the expected rows to the Unity Catalog table and that it can recover from a restart. You can test the transformation logic with a batch DataFrame that simulates the streaming schema. The following example shows a test for the parsing logic.

```python
from pyspark.sql import Row
from pyspark.sql.functions import from_json, col
from pyspark.sql.types import StructType, StructField, StringType, DoubleType

# Define the schema of the JSON payload.
schema = StructType([
    StructField("sensor_id", StringType(), nullable=False),
    StructField("temperature", DoubleType(), nullable=True),
])

# Create a batch DataFrame that simulates the Kafka source.
test_data = [
    Row(value=b'{"sensor_id": "S1", "temperature": 100.0}'),
    Row(value=b'{"sensor_id": "S2", "temperature": 90.0}'),
]
df_test = spark.createDataFrame(test_data)

# Apply the same parsing logic used in the stream.
df_parsed = (df_test
    .select(from_json(col("value").cast("string"), schema).alias("data"))
    .select("data.*"))

# Verify the result.
rows = df_parsed.collect()
assert rows[0].sensor_id == "S1" and rows[0].temperature == 100.0
assert rows[1].sensor_id == "S2" and rows[1].temperature == 90.0
```

For end-to-end testing, use a test source that you can control, such as a directory of files or a test Kafka topic. Run the stream with a `availableNow` trigger, and verify the output in the target table. Clean up the test resources after the test.

## Performance considerations

Streaming write performance depends on the source, the processing logic, and the sink. The number of partitions in the source determines the maximum parallelism. Ensure that the source has enough partitions to support the desired throughput.

Micro-batch size affects latency and throughput. Smaller micro-batches reduce latency but increase overhead. Larger micro-batches increase throughput but increase latency. The default trigger processes data as soon as it arrives. You can use `processingTime` to control the interval.

State management is important for aggregations. Watermarks bound the state, but you should also monitor the state size. If the state grows too large, the stream may run out of memory. Use watermarks and windows to keep the state bounded.

Checkpointing adds overhead. The checkpoint is written on each micro-batch. Use a reliable storage location with low latency. Avoid using a location that is slow or has high contention.

Destination performance depends on file size and partitioning. The stream writes to Delta tables. It may create many small files. Run `OPTIMIZE` periodically to compact small files. Use partitioning or liquid clustering on columns that are commonly used in filters.

Use the `availableNow` trigger for scheduled jobs to process all available data and stop. This is more cost-effective than a continuously running cluster.

## An end-to-end example

Consider a scenario where sensor data arrives continuously from manufacturing equipment. You read the data from Kafka, parse the JSON payload, write the raw readings to a bronze table, compute 5-minute aggregates, and write the aggregates to a silver table. The following example shows the complete pipeline using PySpark.

```python
from pyspark.sql.functions import (
    col, from_json, window, avg, max, min
)
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, TimestampType

# Define the schema of the JSON payload.
schema = StructType([
    StructField("sensor_id", StringType(), nullable=False),
    StructField("temperature", DoubleType(), nullable=True),
    StructField("reading_time", TimestampType(), nullable=True),
])

# Read from Kafka.
df_raw = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker:9092")
    .option("subscribe", "sensor-readings")
    .option("startingOffsets", "latest")
    .load())

# Parse the JSON payload.
df_parsed = (df_raw
    .select(from_json(col("value").cast("string"), schema).alias("data"))
    .select("data.*"))

# Define the checkpoint location for the bronze query.
checkpoint_bronze = "/Volumes/manufacturing/checkpoints/bronze_sensor_readings"

# Write raw readings to a bronze table.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", checkpoint_bronze)
    .trigger(availableNow=True)
    .toTable("manufacturing.bronze.sensor_readings"))

# Define the checkpoint location for the silver query.
checkpoint_silver = "/Volumes/manufacturing/checkpoints/silver_sensor_aggregates"

# Compute 5-minute aggregates.
df_aggregated = (df_parsed
    .withWatermark("reading_time", "2 minutes")
    .groupBy(window("reading_time", "5 minutes"), "sensor_id")
    .agg(
        avg("temperature").alias("avg_temperature"),
        max("temperature").alias("max_temperature"),
        min("temperature").alias("min_temperature")
    ))

# Write aggregates to a silver table.
(df_aggregated
    .writeStream
    .format("delta")
    .outputMode("update")
    .option("checkpointLocation", checkpoint_silver)
    .trigger(availableNow=True)
    .toTable("manufacturing.silver.sensor_aggregates"))
```

The example reads from Kafka, parses JSON, writes raw readings to a bronze table, computes 5-minute aggregates, and writes the aggregates to a silver table. The bronze write uses `append` mode. The silver write uses `update` mode. Both streams have their own checkpoint locations. The pipeline provides exactly-once processing and stores the data in Unity Catalog.

## Summary

Writing streaming data to Unity Catalog tables uses the `writeStream` API with the `delta` format and the `toTable` method. The target table is a Delta table governed by Unity Catalog. The write requires a checkpoint location to store progress and provide fault tolerance. Each streaming query must have its own unique checkpoint location. Checkpoints should be stored in durable storage such as cloud storage or a Unity Catalog volume.

The output mode determines which records are written. `append` writes only new rows and is the default for ingestion. `update` writes changed rows and is used with aggregations. `complete` rewrites all rows and is used sparingly. Delta Lake enforces the table schema. Schema evolution can add new columns during a write. Null handling, case sensitivity, and time zones affect the data but not the checkpoint mechanism. Set the session time zone explicitly to UTC.

In SQL, Lakeflow Spark Declarative Pipelines provide streaming tables with automatic checkpoint management. You define `CREATE OR REFRESH STREAMING TABLE` and the pipeline handles fault tolerance. This is the recommended approach for declarative pipelines.

Best practices include using unique checkpoints, durable storage, Unity Catalog volumes, the correct output mode, schema evolution deliberately, and monitoring the stream. Common mistakes include missing checkpoints, shared checkpoints, local paths, wrong output modes, and not setting the session time zone. Test streaming writes with batch DataFrames or controlled test sources. Performance depends on the source, micro-batch size, state management, and the sink. Use watermarks to bound state, compact small files, and use the `availableNow` trigger for scheduled jobs. By understanding these concepts, you can build reliable streaming ingestion pipelines that land data in Unity Catalog with exactly-once guarantees.
