## Configure checkpoint locations

A checkpoint is a durable record of the progress of a streaming query. It stores the offsets of the source records that have been processed, the state of any stateful operations such as aggregations, and the metadata needed to reconstruct the query. When a streaming job starts, it reads the checkpoint and resumes from the last committed offset. If the job stops unexpectedly, it can restart and continue from where it left off without reprocessing records it has already processed or missing records that arrived while it was down. In Structured Streaming, the checkpoint location is configured when you write a streaming DataFrame to a sink. The location must be a reliable, durable storage path, and each streaming query must have its own unique checkpoint directory.

Checkpoints matter because streaming jobs are long-running and must be fault-tolerant. A job that processes data continuously for months will encounter failures: network partitions, cluster restarts, source outages, or code errors. Without a checkpoint, the job cannot recover gracefully. It would either reprocess data from the beginning, creating duplicates, or lose data that arrived during the failure. A checkpoint provides exactly-once processing guarantees when combined with a replayable source and an idempotent sink. It is the mechanism that makes Structured Streaming suitable for production pipelines that feed Unity Catalog tables.

These notes cover checkpoint configuration from first principles. They explain what a checkpoint contains, why it is necessary, how to choose a location, and how to avoid common mistakes. They show PySpark examples for configuring checkpoints in `writeStream` and SQL examples for streaming tables that manage checkpoints automatically. They cover the relationship between checkpoints and Delta Lake, Unity Catalog, schema enforcement, and the medallion architecture. They also cover null handling, case sensitivity, time zones, best practices, common pitfalls, testing, performance, and an end-to-end example. The goal is that you can read these notes alone and understand how to configure checkpoint locations correctly for any streaming pipeline.

## What checkpoints are and why they matter

A checkpoint is a directory that Spark uses to store the progress of a streaming query. The directory contains several files and subdirectories. The `offsets` directory stores the source offsets that have been processed for each micro-batch. The `commits` directory stores a record of completed micro-batches. The `state` directory stores the state of stateful operations, such as the accumulators for aggregations or the join keys for stream-stream joins. The `metadata` file stores the query plan and configuration. Together, these files allow Spark to resume a query from exactly where it left off.

The following example shows a basic streaming write with a checkpoint location.

```python
# Import the functions needed for the streaming query.
from pyspark.sql.functions import col, from_json
from pyspark.sql.types import StructType, StructField, StringType, DoubleType

# Define the schema of the JSON payload.
schema = StructType([
    StructField("sensor_id", StringType(), nullable=False),
    StructField("temperature", DoubleType(), nullable=True),
])

# Read from a streaming source.
# In this example, the source is a Kafka topic.
df_raw = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker:9092")
    .option("subscribe", "sensor-readings")
    .load())

# Parse the JSON payload.
df_parsed = (df_raw
    .select(from_json(col("value").cast("string"), schema).alias("data"))
    .select("data.*"))

# Define the checkpoint location.
# The location must be a durable path, such as a cloud storage directory
# or a Unity Catalog volume. Do not use a local path.
checkpoint_path = "/Volumes/manufacturing/checkpoints/sensor_ingestion"

# Write the stream to a Delta table.
# The checkpointLocation option tells Spark where to store the progress.
# Each streaming query must have its own unique checkpoint location.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", checkpoint_path)
    .trigger(availableNow=True)
    .toTable("manufacturing.bronze.sensor_readings"))
```

The example defines a checkpoint path in a Unity Catalog volume. The `checkpointLocation` option is passed to `writeStream`. When the query runs, Spark writes the checkpoint files to that location. If the query is stopped and restarted, it reads the checkpoint and resumes from the last processed offset. The `trigger(availableNow=True)` processes all available data and stops, which is useful for scheduled jobs. For continuous processing, you would omit the trigger or use a `processingTime` trigger.

The equivalent SQL approach uses a streaming table in Lakeflow Spark Declarative Pipelines. In SQL, you define a streaming table, and the pipeline manages the checkpoint automatically. You do not specify a checkpoint location manually. The following SQL example creates a streaming table from a Kafka source.

```sql
-- Create a streaming table from a Kafka source.
-- The pipeline manages the checkpoint location automatically.
-- The table is created in Unity Catalog and is governed by Unity Catalog.
CREATE OR REFRESH STREAMING TABLE manufacturing.bronze.sensor_readings
AS SELECT
    -- Parse the JSON payload from the Kafka value column.
    -- The value column is binary, so cast it to string.
    from_json(CAST(value AS STRING), 'sensor_id STRING, temperature DOUBLE').sensor_id AS sensor_id,
    from_json(CAST(value AS STRING), 'sensor_id STRING, temperature DOUBLE').temperature AS temperature
FROM STREAM read_kafka(
    bootstrapServers => 'broker:9092',
    subscribe => 'sensor-readings'
);
```

The SQL example uses the `read_kafka` function and a streaming table. The checkpoint is managed by the pipeline and stored in a location controlled by Databricks. You do not need to configure it manually. This is simpler than the PySpark approach, but it gives you less control over the checkpoint location. For pipelines that require a specific checkpoint location, use PySpark.

## The role of checkpoints in fault tolerance

Checkpoints provide fault tolerance by recording the exact progress of a streaming query. When a query fails, Spark can restart it and resume from the last committed checkpoint. The following table summarizes the components of a checkpoint and their purpose.

| Component | Purpose |
|---|---|
| `offsets` | Records the source offsets processed in each micro-batch |
| `commits` | Records completed micro-batches |
| `state` | Stores the state of stateful operations |
| `metadata` | Stores the query plan and configuration |

The `offsets` directory is the most critical for recovery. It records which records have been processed. When the query restarts, Spark reads the latest offsets and resumes from there. The `commits` directory confirms which micro-batches have been fully committed to the sink. The `state` directory is used for stateful operations such as aggregations and joins. If the state is lost, the query cannot recover correctly. The `metadata` file stores the query plan. If the query plan changes in a way that is incompatible with the checkpoint, the query fails to start.

Exactly-once processing requires three conditions: a replayable source, a durable checkpoint, and an idempotent sink. A replayable source can re-deliver records from a given offset. Kafka is replayable. File sources are replayable if the files are immutable. A durable checkpoint records progress in reliable storage. An idempotent sink can handle the same record being written more than once without creating duplicates. Delta Lake is idempotent when the write is coordinated with the checkpoint update. Structured Streaming coordinates the checkpoint update and the sink write so that they either both succeed or both fail. This coordination is what provides exactly-once semantics.

## Choosing a checkpoint location

The checkpoint location must be a reliable, durable storage path. It should not be a local path because local storage is not durable and is lost when the cluster restarts. The following table compares common storage options.

| Storage option | Durability | Performance | Governance |
|---|---|---|---|
| Cloud storage (ADLS, S3, GCS) | High | High | Managed by storage account |
| Unity Catalog volume | High | High | Governed by Unity Catalog |
| DBFS root | High | Medium | Managed by workspace |
| Local disk | Low | High | Not durable |

The table shows that cloud storage and Unity Catalog volumes are the best choices. Unity Catalog volumes provide governance in addition to durability. You can grant permissions on the volume and audit access. Cloud storage is durable but requires separate governance. DBFS root is durable but is being deprecated in favor of Unity Catalog volumes. Local disk is not durable and should never be used for checkpoints.

When you choose a checkpoint location, consider the following factors. First, the location must be accessible from all nodes in the cluster. Cloud storage and Unity Catalog volumes meet this requirement. Second, the location must have sufficient retention. Checkpoint files are small, but they accumulate over time. You should configure a retention policy to delete old checkpoints after a reasonable period. Third, the location should be close to the compute to minimize latency. For example, if your cluster runs in the same region as your storage account, latency is low.

The following example shows how to configure a checkpoint location in a Unity Catalog volume.

```python
# Define the checkpoint location in a Unity Catalog volume.
# The volume is named "checkpoints" in the "manufacturing" catalog and schema.
# The path uses the /Volumes/ prefix.
checkpoint_path = "/Volumes/manufacturing/checkpoints/sensor_ingestion"

# Write the stream with the checkpoint location.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", checkpoint_path)
    .trigger(availableNow=True)
    .toTable("manufacturing.bronze.sensor_readings"))
```

The example uses a Unity Catalog volume path. The volume is governed by Unity Catalog, so you can control who can read and write the checkpoint files. This is useful for security and compliance. If you use cloud storage directly, you manage access with storage account keys or service principals.

## Unique checkpoints per query

Each streaming query must have its own unique checkpoint location. Sharing a checkpoint between different queries causes data processing errors. The checkpoint stores the query plan and the offsets for a specific query. If two queries use the same checkpoint, they will conflict. One query may read the offsets of the other, leading to incorrect processing, duplicate writes, or missing data. The following table summarizes the consequences of sharing checkpoints.

| Scenario | Consequence |
|---|---|
| Two queries write to the same table with the same checkpoint | Duplicate writes, conflicting offsets |
| Two queries read from the same source with the same checkpoint | One query may skip records, the other may reprocess |
| A query is modified and reuses the checkpoint | The query may fail to start due to incompatible plan |

The safest approach is to use a unique directory for each streaming query. You can include the query name in the path. The following example shows two queries with different checkpoint locations.

```python
# Define two checkpoint locations for two different queries.
# Each query writes to a different table.
checkpoint_path_bronze = "/Volumes/manufacturing/checkpoints/bronze_sensor_readings"
checkpoint_path_silver = "/Volumes/manufacturing/checkpoints/silver_sensor_aggregates"

# Query 1: Write raw readings to a bronze table.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", checkpoint_path_bronze)
    .trigger(availableNow=True)
    .toTable("manufacturing.bronze.sensor_readings"))

# Query 2: Write aggregates to a silver table.
(df_aggregated
    .writeStream
    .format("delta")
    .outputMode("update")
    .option("checkpointLocation", checkpoint_path_silver)
    .trigger(availableNow=True)
    .toTable("manufacturing.silver.sensor_aggregates"))
```

The example uses separate checkpoint paths for the bronze and silver queries. This prevents conflicts and allows each query to recover independently. If one query fails, it can be restarted without affecting the other.

## Checkpoints with Delta Lake and Unity Catalog

Delta Lake and Unity Catalog work together to provide reliable streaming ingestion. When you write a stream to a Delta table in Unity Catalog, the table is governed by Unity Catalog. The checkpoint is stored in a location you specify. The checkpoint location can be a Unity Catalog volume or cloud storage. If you use a Unity Catalog volume, the checkpoint files are governed by Unity Catalog. You can grant permissions on the volume and audit access.

The following table summarizes the interaction between checkpoints, Delta Lake, and Unity Catalog.

| Aspect | Role |
|---|---|
| Delta Lake | Provides ACID transactions and idempotent writes |
| Unity Catalog | Governs the target table and the checkpoint volume |
| Checkpoint | Records progress and state for fault tolerance |
| Streaming query | Coordinates checkpoint updates with Delta Lake commits |

The coordination between the checkpoint and Delta Lake is what provides exactly-once semantics. When a micro-batch completes, Spark writes the data to the Delta table and updates the checkpoint. If the data write succeeds but the checkpoint update fails, the micro-batch is retried. Because Delta Lake is idempotent for the same batch, the retry does not create duplicates. If the checkpoint update succeeds but the data write fails, the micro-batch is not marked as complete, and it is retried on restart. This coordination ensures that each record is processed exactly once.

## Schema enforcement, evolution, and expectations

Checkpoints interact with schema enforcement and evolution. When you write a streaming DataFrame to a Delta table, Delta Lake enforces the table schema. If the DataFrame has extra columns, the write fails unless schema evolution is enabled. The checkpoint stores the schema of the streaming query. If you change the query to add a column, the checkpoint may be incompatible. In that case, you must use a new checkpoint location and start the query from scratch.

The following table summarizes schema-related considerations.

| Scenario | Action |
|---|---|
| Adding a column to the target table | Use schema evolution or a new checkpoint |
| Changing the query logic | Use a new checkpoint location |
| Changing the output mode | Use a new checkpoint location |
| Changing the source | Use a new checkpoint location |

Expectations in Lakeflow Spark Declarative Pipelines can validate data quality. If a row violates an expectation, the pipeline can drop it before it reaches the table. Expectations are defined on the table, not on the checkpoint. They complement schema enforcement by validating business rules.

## Null handling, case sensitivity, and time zones

Null handling in streaming ingestion follows the same rules as batch processing. Nulls in the source are preserved unless you filter or replace them. If a target column is non-nullable, a null value causes the write to fail. You should handle nulls in the transformation step. For example, you can filter out rows with null keys or replace null values with a default using `coalesce`. The checkpoint does not affect null handling; it only records progress.

Case sensitivity affects string comparisons and column names. In Spark SQL, column names are case-insensitive by default. String values are case-sensitive. If the payload contains inconsistent casing, normalize it with `upper` or `lower`, or use a case-insensitive collation if the table is configured for one. The checkpoint does not affect case sensitivity.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. The checkpoint stores offsets and state, which are time-agnostic. However, the data you process may include timestamps. Set the session time zone explicitly to UTC at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. This avoids off-by-hours errors when parsing timestamps.

## Best practices

Use a unique checkpoint location for each streaming query. Sharing checkpoints causes conflicts and data errors.

Store checkpoints in durable storage. Use cloud storage or a Unity Catalog volume. Do not use local disk.

Use a Unity Catalog volume for governance. Volumes are governed by Unity Catalog, so you can control access and audit usage.

Set a retention policy for checkpoint files. Checkpoints accumulate over time. Delete old checkpoints after a reasonable period, such as 30 days.

Do not modify the query logic without changing the checkpoint location. If you change the query in a way that is incompatible with the checkpoint, the query fails to start. Use a new checkpoint location.

Monitor the checkpoint location. Ensure that the storage is not full and that writes are succeeding. A failed checkpoint write causes the stream to fail.

Use the `availableNow` trigger for scheduled jobs. It processes all available data and stops, which is more cost-effective than a continuously running cluster.

## Common mistakes and pitfalls

The most common mistake is sharing a checkpoint location between two queries. This causes conflicts and data errors. Always use a unique checkpoint location for each query.

A second mistake is using a local path for the checkpoint. Local paths are not durable and are lost when the cluster restarts. Use cloud storage or a Unity Catalog volume.

A third mistake is changing the query logic without changing the checkpoint location. The checkpoint stores the query plan. If the plan changes, the query may fail to start. Use a new checkpoint location.

A fourth mistake is not monitoring the checkpoint location. If the storage is full or the write fails, the stream fails. Monitor the checkpoint location and set up alerts.

A fifth mistake is assuming that the checkpoint is a backup. The checkpoint is not a backup of the data. It is a record of progress. The data is stored in the Delta table. Use Delta Lake time travel or backups for data recovery.

A sixth mistake is using the same checkpoint for a batch job and a streaming job. Batch jobs do not use checkpoints. Do not configure a checkpoint for a batch write.

## Testing checkpoint configuration

Testing checkpoint configuration involves verifying that a streaming query can stop and restart without reprocessing or missing data. You can test this by running a query with a small dataset, stopping it, adding more data, and restarting it. The following example shows a test for checkpoint recovery.

```python
from pyspark.sql import Row
from pyspark.sql.functions import col

# Create a test DataFrame and write it to a Delta table.
test_data = [
    Row(id=1, value="A"),
    Row(id=2, value="B"),
]
df_test = spark.createDataFrame(test_data)
df_test.write.mode("overwrite").saveAsTable("tmp.test_source")

# Define a streaming read from the Delta table.
# Note: reading a Delta table as a stream requires the table to be a source.
# For testing, we can use a rate source or a file source.
# This is a simplified example.

# Define a checkpoint location for the test.
checkpoint_path = "/tmp/checkpoints/test_query"

# Run the streaming query with availableNow.
(df_test.writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", checkpoint_path)
    .trigger(availableNow=True)
    .toTable("tmp.test_target"))

# Verify the result.
assert spark.read.table("tmp.test_target").count() == 2

# Add more data to the source.
new_data = [Row(id=3, value="C")]
df_new = spark.createDataFrame(new_data)
df_new.write.mode("append").saveAsTable("tmp.test_source")

# Restart the streaming query.
# It should process only the new data because the checkpoint records
# that the first two rows were already processed.
# (Note: This requires the source to be a streaming source that tracks offsets.)
```

The test verifies that the checkpoint allows the query to resume without reprocessing. For a complete test, use a source that supports offsets, such as Kafka or a file source. Clean up the temporary tables and checkpoint directory after the test.

## Performance considerations

Checkpointing adds a small amount of overhead to each micro-batch. The checkpoint files are written to durable storage, which adds latency. The overhead is usually small compared to the data processing, but it can be noticeable for very small micro-batches. To reduce overhead, use a storage location with low latency, such as a Unity Catalog volume in the same region as the cluster.

The size of the checkpoint state grows with the number of keys in stateful operations. For aggregations with many groups, the state can become large. Use watermarks to bound the state. Watermarks tell Spark when to drop old state. Without a watermark, the state grows indefinitely.

Checkpoint files accumulate over time. The `offsets` and `commits` directories grow with each micro-batch. For long-running queries, this can consume a significant amount of storage. Configure a retention policy to delete old checkpoints. In Databricks, the checkpoint location can be cleaned up automatically if you use a managed location.

Use the `availableNow` trigger for scheduled jobs. It processes all available data and stops. This reduces compute cost compared to a continuously running cluster. The checkpoint ensures that the next run resumes from where the previous run stopped.

## An end-to-end example

Consider a scenario where you ingest sensor data from Kafka into a bronze table and compute aggregates into a silver table. The pipeline uses two streaming queries, each with its own checkpoint location. The following example shows the complete pipeline.

```python
from pyspark.sql.functions import (
    col, from_json, window, avg, max, min
)
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, TimestampType

# Define the schema of the JSON payload.
schema = StructType([
    StructField("sensor_id", StringType(), nullable=False),
    StructField("temperature", DoubleType(), nullable=True),
    StructField("reading_time", TimestampType(), nullable=True),
])

# Read from Kafka.
df_raw = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker:9092")
    .option("subscribe", "sensor-readings")
    .option("startingOffsets", "latest")
    .load())

# Parse the JSON payload.
df_parsed = (df_raw
    .select(from_json(col("value").cast("string"), schema).alias("data"))
    .select("data.*"))

# Define the checkpoint location for the bronze query.
checkpoint_bronze = "/Volumes/manufacturing/checkpoints/bronze_sensor_readings"

# Write raw readings to a bronze table.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", checkpoint_bronze)
    .trigger(availableNow=True)
    .toTable("manufacturing.bronze.sensor_readings"))

# Define the checkpoint location for the silver query.
checkpoint_silver = "/Volumes/manufacturing/checkpoints/silver_sensor_aggregates"

# Compute 5-minute aggregates.
df_aggregated = (df_parsed
    .withWatermark("reading_time", "2 minutes")
    .groupBy(window("reading_time", "5 minutes"), "sensor_id")
    .agg(
        avg("temperature").alias("avg_temperature"),
        max("temperature").alias("max_temperature"),
        min("temperature").alias("min_temperature")
    ))

# Write aggregates to a silver table.
(df_aggregated
    .writeStream
    .format("delta")
    .outputMode("update")
    .option("checkpointLocation", checkpoint_silver)
    .trigger(availableNow=True)
    .toTable("manufacturing.silver.sensor_aggregates"))
```

The example uses two checkpoint locations, one for each query. The bronze query writes raw readings. The silver query writes aggregates. Both use the `availableNow` trigger. The checkpoints ensure that each query resumes from the last processed offset. The pipeline provides exactly-once processing and stores the data in Unity Catalog.
