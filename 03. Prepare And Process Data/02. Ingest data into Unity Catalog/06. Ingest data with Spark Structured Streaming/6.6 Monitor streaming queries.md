## Monitor streaming queries

A streaming query is a long-running process that reads from a source, applies transformations, and writes to a sink. Unlike a batch job, which runs to completion and stops, a streaming query runs continuously or on a schedule until it is stopped or fails. Because it runs for a long time, it can encounter problems that are not visible in a single execution. Data may arrive faster than the query can process it. A source may stop sending data. A sink may reject writes because of schema changes. A checkpoint may become corrupt. Monitoring is the practice of observing the query's health, performance, and progress so that you can detect and respond to these problems before they affect downstream consumers.

Monitoring matters because streaming pipelines feed real-time dashboards, alerting systems, and operational applications. If a streaming query falls behind, the data in the target table becomes stale. If it fails, the target table stops updating. If it silently drops records, the data becomes incomplete. These problems are often invisible without monitoring. The Spark UI provides a visual view of active queries, but production pipelines need automated monitoring that can send alerts, trigger retries, and provide historical trends. Azure Databricks provides several mechanisms for monitoring: the Spark UI, the `StreamingQuery` object in PySpark, the pipeline event log for Lakeflow Spark Declarative Pipelines, and system tables that record streaming metrics.

These notes cover how to monitor streaming queries from first principles. They explain the Spark UI Structured Streaming tab, the programmatic `StreamingQuery` API, the key metrics that indicate health, how to use `awaitTermination` and error handling, how to set up alerts, and how to monitor SQL streaming tables in Lakeflow Spark Declarative Pipelines. They also cover null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand how to monitor streaming queries in production and respond to problems quickly.

## Understanding streaming query monitoring

A streaming query is represented by a `StreamingQuery` object. When you call `writeStream.start()` or `writeStream.toTable()`, Spark returns a `StreamingQuery` object. This object is the handle to the running query. It provides methods to check whether the query is active, to get its current status, to view recent progress, and to stop it. The query also emits progress events after each micro-batch. These events contain metrics such as the number of input rows, the number of processed rows, the batch duration, and the scheduling delay. Monitoring is the act of collecting and interpreting these events.

The metrics are organized around micro-batches. Each micro-batch has an ID, a timestamp, and a set of metrics. The metrics include the input rate, which is the number of rows per second arriving from the source. The processing rate is the number of rows per second the query is processing. If the input rate is consistently higher than the processing rate, the query is falling behind. The batch duration is the time it takes to process a micro-batch. The scheduling delay is the time the micro-batch waited before it started. A growing scheduling delay indicates that the query cannot keep up with the arrival rate. The latency is the time from when a record arrived to when it was written to the sink.

The following table summarizes the key metrics.

| Metric | Meaning | Healthy range |
|---|---|---|
| `inputRowsPerSecond` | Rows arriving per second | Stable or fluctuating with source |
| `processedRowsPerSecond` | Rows processed per second | Should match or exceed input rate |
| `batchDuration` | Time to process a micro-batch | Stable, within the trigger interval |
| `schedulingDelay` | Time a batch waited before starting | Near zero |
| `latency` | Time from arrival to write | Within the latency requirement |
| `numInputRows` | Rows in the current micro-batch | Varies with source |
| `stateOperators` | State size for stateful operations | Bounded, not growing indefinitely |

The table shows that the most important comparison is between input rate and processing rate. If the processing rate is lower than the input rate, the query accumulates a backlog. The scheduling delay grows, and the latency increases. If the backlog grows without bound, the query may eventually fail due to memory pressure or checkpoint growth.

## Monitoring with the Spark UI

The Spark UI provides a visual view of active streaming queries. In a Databricks notebook or cluster, you can open the Spark UI and navigate to the Structured Streaming tab. The tab lists all active streaming queries in the cluster. For each query, you can see the query name, the ID, the status, and a summary of the most recent micro-batch. You can also see a timeline of micro-batches, which shows the batch duration, the scheduling delay, and the processing time. The timeline helps you identify whether the query is keeping up with the input rate or falling behind.

The Structured Streaming tab also provides detailed statistics for each query. You can see the input rate, the processing rate, the number of input rows, the number of processed rows, and the state size for stateful operations. You can click into a query to see the query plan and the progress of each micro-batch. The UI is useful for interactive debugging and for understanding the behavior of a query during development. For production pipelines, the UI is not sufficient because it only shows active queries and does not provide historical data or alerts.

## Monitoring programmatically with the StreamingQuery object

The `StreamingQuery` object provides programmatic access to the query's status and progress. You can use it to build custom monitoring, to log metrics, or to trigger alerts. The following example shows how to create a query and check its status.

```python
# Import the functions needed for parsing.
from pyspark.sql.functions import col, from_json
from pyspark.sql.types import StructType, StructField, StringType, DoubleType

# Define the schema of the JSON payload.
schema = StructType([
    # The sensor_id identifies the device that produced the reading.
    StructField("sensor_id", StringType(), nullable=False),
    # The temperature is the measured value.
    StructField("temperature", DoubleType(), nullable=True),
])

# Read from a Kafka topic as a stream.
df_raw = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker:9092")
    .option("subscribe", "sensor-readings")
    .load())

# Parse the JSON payload from the value column.
df_parsed = (df_raw
    .select(from_json(col("value").cast("string"), schema).alias("data"))
    .select("data.*"))

# Start the streaming query and capture the StreamingQuery object.
# The query writes to a Unity Catalog table with a checkpoint location.
query = (df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/Volumes/manufacturing/checkpoints/sensor_readings")
    .trigger(availableNow=True)
    .toTable("manufacturing.bronze.sensor_readings"))

# Check whether the query is still running.
# isActive returns True if the query is active, False if it has stopped.
print(query.isActive)

# Get the current status of the query.
# status returns a dictionary with the query ID, name, and current state.
print(query.status)

# View the recent progress of the query.
# recentProgress returns a list of the most recent micro-batch progress reports.
# Each report contains metrics such as inputRowsPerSecond and batchDuration.
print(query.recentProgress)
```

The example starts a streaming query and captures the `StreamingQuery` object. The `isActive` property tells you whether the query is running. The `status` property returns a dictionary with the query ID, name, and state. The `recentProgress` property returns a list of progress reports for recent micro-batches. You can use these properties to build custom monitoring. For example, you can log the `inputRowsPerSecond` and `processedRowsPerSecond` to a table and visualize the trend.

The following table summarizes the methods and properties of the `StreamingQuery` object.

| Method or property | Description |
|---|---|
| `isActive` | True if the query is running |
| `status` | Dictionary with query ID, name, and state |
| `recentProgress` | List of recent progress reports |
| `lastProgress` | The most recent progress report |
| `exception` | The exception if the query failed |
| `stop()` | Stops the query |
| `awaitTermination()` | Blocks until the query stops or fails |
| `processAllAvailable()` | Blocks until all available data is processed |

The table shows the main methods for monitoring and controlling a query. The `recentProgress` and `lastProgress` properties are the primary sources of metrics. The `exception` property is used for error handling.

## Using awaitTermination and error handling

The `awaitTermination()` method blocks the calling thread until the query stops. If the query fails, `awaitTermination()` raises the exception that caused the failure. You can use it to wait for a streaming job to complete, especially when using the `availableNow` trigger. For production workloads, wrap `awaitTermination()` in a try/except block to capture failures and respond appropriately. The following example shows error handling.

```python
# Start the streaming query.
query = (df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/Volumes/manufacturing/checkpoints/sensor_readings")
    .trigger(availableNow=True)
    .toTable("manufacturing.bronze.sensor_readings"))

# Wait for the query to terminate and handle failures.
try:
    # awaitTermination blocks until the query stops or fails.
    query.awaitTermination()
except Exception as e:
    # If the query fails, log the error and take corrective action.
    # The exception message contains the reason for the failure.
    print(f"Stream failed: {e}")
    # You can also inspect the query exception directly.
    print(f"Query exception: {query.exception}")
    # Depending on the failure, you might retry the query, send an alert,
    # or fail the job so that the orchestrator can retry.
    raise
```

The example waits for the query to terminate and catches any exception. If the query fails, it logs the error and re-raises it. Re-raising the exception is important in a Databricks Job because it marks the job as failed and allows the job's retry policy to take effect. If you catch the exception and do not re-raise it, the job appears to succeed even though the stream failed.

## Key streaming metrics and what they tell you

The progress reports contain many metrics. Understanding what each metric means helps you diagnose problems. The following table describes the most important metrics.

| Metric | Description | What to watch for |
|---|---|---|
| `inputRowsPerSecond` | Rows arriving per second | Sudden spikes or drops |
| `processedRowsPerSecond` | Rows processed per second | Should be close to input rate |
| `batchDuration` | Time to process a batch | Growing batch duration indicates a backlog |
| `schedulingDelay` | Time a batch waited before starting | Growing delay means the query cannot keep up |
| `numInputRows` | Rows in the current batch | Very large batches may cause memory issues |
| `stateOperators` | State size for stateful operations | Unbounded growth indicates missing watermark |
| `durationMs` | Breakdown of batch time | Identify which phase is slow |

The `inputRowsPerSecond` and `processedRowsPerSecond` are the most important metrics for throughput. If the processed rate is consistently lower than the input rate, the query is falling behind. The `batchDuration` and `schedulingDelay` indicate whether the query is keeping up. If the batch duration is longer than the trigger interval, the next batch is delayed. If the scheduling delay grows, the query is accumulating a backlog. The `stateOperators` metric shows the size of the state for stateful operations such as aggregations. If the state grows without bound, it usually means that a watermark is missing or set incorrectly. The `durationMs` breakdown shows how much time is spent in different phases, such as adding data, processing, and writing to the sink. This helps you identify bottlenecks.

For Kafka sources, the progress report also includes the consumer lag, which is the difference between the latest offset in the topic and the offset the query has processed. A growing lag indicates that the query is falling behind. The following example shows how to extract the lag from the progress report.

```python
# Get the latest progress report.
progress = query.lastProgress

# The sources field contains information about each source.
# For Kafka, the sources field includes the latest offset and the processed offset.
if progress and "sources" in progress:
    for source in progress["sources"]:
        # The metrics field contains the consumer lag for Kafka sources.
        # The lag is the difference between the latest offset and the processed offset.
        if "metrics" in source and "consumerLag" in source["metrics"]:
            print(f"Consumer lag: {source['metrics']['consumerLag']}")
```

The example extracts the consumer lag from the progress report. You can log this value and alert if it exceeds a threshold. A growing lag is an early warning that the query cannot keep up with the input rate.

## Setting up alerts and production monitoring

In production, you need automated monitoring that can detect problems and notify the team. Databricks provides several options. You can use Databricks Jobs with retry policies and notifications. You can use Databricks SQL alerts to query system tables and send alerts when metrics exceed thresholds. You can also use a custom `StreamingQueryListener` to capture progress events and send them to a monitoring system.

The following example shows a custom `StreamingQueryListener` that logs progress metrics.

```python
from pyspark.sql.streaming import StreamingQueryListener

# Define a custom listener that logs progress events.
# The listener is called after each micro-batch.
class MetricsLogger(StreamingQueryListener):
    def onQueryStarted(self, event):
        # Called when a query starts.
        print(f"Query started: {event.id}")

    def onQueryProgress(self, event):
        # Called after each micro-batch.
        # The event contains the progress report.
        progress = event.progress
        input_rate = progress.get("inputRowsPerSecond", 0)
        processed_rate = progress.get("processedRowsPerSecond", 0)
        batch_duration = progress.get("batchDuration", 0)
        print(f"Input rate: {input_rate}, Processed rate: {processed_rate}, Batch duration: {batch_duration}")

    def onQueryTerminated(self, event):
        # Called when a query stops or fails.
        print(f"Query terminated: {event.id}, exception: {event.exception}")

# Register the listener with the Spark session.
spark.streams.addListener(MetricsLogger())
```

The example defines a listener that logs input rate, processed rate, and batch duration after each micro-batch. You can extend the listener to write metrics to a Delta table or send them to a monitoring system such as Prometheus or Azure Monitor. The listener is called for all streaming queries in the Spark session, so you can use it to monitor multiple queries.

For SQL streaming tables in Lakeflow Spark Declarative Pipelines, the pipeline event log records events such as updates, data quality violations, and errors. You can query the event log with SQL. The following SQL example queries the event log for a pipeline.

```sql
-- Query the pipeline event log for recent updates.
-- The event log is a Delta table that records pipeline events.
-- The table is in the pipeline's event log schema.
SELECT
  timestamp,
  event_type,
  message,
  details
FROM event_log(TABLE(manufacturing.bronze.sensor_readings))
-- Filter to events from the last hour.
WHERE timestamp >= current_timestamp() - INTERVAL 1 HOUR
-- Order by timestamp, most recent first.
ORDER BY timestamp DESC;
```

The example queries the event log for the `sensor_readings` streaming table. The `event_log` function returns the events for the table. You can filter by event type to see errors, data quality violations, or updates. This is useful for monitoring SQL pipelines and for debugging failures.

## Monitoring SQL streaming tables in Lakeflow Spark Declarative Pipelines

Lakeflow Spark Declarative Pipelines provide a declarative way to build streaming pipelines. Each pipeline has an event log that records the progress and status of its tables. The event log is a Delta table that you can query with SQL. It contains information about pipeline updates, data quality expectations, and errors. You can use the event log to monitor the pipeline and to set up alerts. The following table summarizes the event types.

| Event type | Description |
|---|---|
| `update_progress` | Progress of a pipeline update |
| `flow_progress` | Progress of a flow within a pipeline |
| `expectation` | Data quality expectation results |
| `error` | Errors encountered during processing |

The table shows that the event log records not only progress but also data quality expectations. Expectations are rules that you define on tables. If a row violates an expectation, the event log records the violation. You can query the event log to see how many rows passed or failed each expectation. This helps you monitor data quality in addition to performance.

## Null handling, case sensitivity, and time zones

Monitoring metrics are numeric and do not involve null handling directly. However, the data that the stream processes may contain nulls. If a null causes a write to fail, the query fails, and the failure appears in the monitoring metrics. You should handle nulls in the transformation step to avoid failures. For example, you can filter out rows with null keys or replace null values with a default using `coalesce`. The monitoring metrics will show a drop in the input rate if the filter removes many rows.

Case sensitivity affects string comparisons in the monitoring queries. If you query the event log and filter on a string column, the comparison is case-sensitive by default. Use the correct case or normalize the case with `upper` or `lower`. The monitoring metrics themselves are numeric and are not affected by case sensitivity.

Time zones affect the timestamps in the monitoring data. The progress reports include timestamps in the session time zone. The event log records timestamps in UTC. When you query the event log, the timestamps are displayed in the session time zone. Set the session time zone explicitly to UTC at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")` to ensure consistency. Use timestamp literals with explicit offsets when comparing to timestamps.

## Best practices

Monitor both the Spark UI and programmatic metrics. The Spark UI is useful for interactive debugging, but production monitoring requires automated collection and alerting.

Track input rate and processing rate together. The most important indicator of health is whether the processing rate keeps up with the input rate. If the processing rate is consistently lower, the query is falling behind.

Monitor consumer lag for Kafka sources. A growing lag is an early warning that the query cannot keep up. Set a threshold and alert when the lag exceeds it.

Monitor batch duration and scheduling delay. Growing batch duration or scheduling delay indicates a backlog. Investigate the cause, such as a slow sink, a large state, or insufficient cluster resources.

Monitor state size for stateful operations. Unbounded state growth usually means a watermark is missing or set incorrectly. Add a watermark to bound the state.

Use `awaitTermination` with error handling. Re-raise exceptions in Databricks Jobs so that the job is marked as failed and the retry policy can take effect.

Set up alerts. Use Databricks SQL alerts on system tables or the event log. Send notifications to email, Slack, or PagerDuty when metrics exceed thresholds.

Log metrics to a Delta table. Use a `StreamingQueryListener` to write metrics to a Delta table. You can then query the table to visualize trends and set up alerts.

## Common mistakes and pitfalls

The most common mistake is not monitoring streaming queries at all. Streaming queries can fail silently if not monitored. Set up monitoring from the start.

A second mistake is only looking at the Spark UI. The Spark UI shows only active queries and does not provide historical data or alerts. Use programmatic monitoring for production.

A third mistake is ignoring consumer lag. A growing lag is an early warning that the query is falling behind. If you ignore it, the query may eventually fail or produce stale data.

A fourth mistake is not setting a watermark for stateful operations. Without a watermark, the state grows without bound, leading to memory issues and slow performance. The state size metric will show the growth.

A fifth mistake is catching exceptions from `awaitTermination` without re-raising them. If you do not re-raise, the Databricks Job appears to succeed even though the stream failed. The job's retry policy will not take effect.

A sixth mistake is not setting the session time zone. The progress reports and event logs use timestamps. If the session time zone differs from the time zone you expect, the timestamps may be confusing. Set the session time zone explicitly to UTC.

A seventh mistake is not monitoring data quality expectations. Expectations in Lakeflow Spark Declarative Pipelines can drop or flag invalid rows. If you do not monitor the expectation results, you may not notice that data quality is degrading.

## Testing monitoring logic

Testing monitoring logic involves verifying that your monitoring code correctly captures metrics and handles failures. You can test the `StreamingQuery` API with a small streaming query. The following example shows a test for query status and progress.

```python
from pyspark.sql import Row

# Create a small DataFrame and write it to a test source.
test_data = [
    Row(id=1, value="A"),
    Row(id=2, value="B"),
]
df_test = spark.createDataFrame(test_data)
df_test.write.mode("overwrite").saveAsTable("tmp.test_source")

# Read the source as a stream.
df_stream = spark.readStream.table("tmp.test_source")

# Start the query with the availableNow trigger.
query = (df_stream
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/tmp/checkpoints/test_monitoring")
    .trigger(availableNow=True)
    .toTable("tmp.test_target"))

# Wait for the query to terminate.
query.awaitTermination()

# Verify that the query is no longer active.
assert not query.isActive, "Query should be inactive after termination"

# Verify that the target table contains the expected rows.
assert spark.read.table("tmp.test_target").count() == 2
```

The test verifies that the query terminates and that the target table contains the expected rows. You can also test the `recentProgress` property to ensure that it contains metrics. Run tests like this in your CI pipeline against a small local Spark session. Clean up temporary tables and checkpoint directories after the test.

## Performance considerations

Monitoring itself has a cost. The `recentProgress` property returns a list of progress reports. If you call it frequently, it can consume memory. The `StreamingQueryListener` is called after each micro-batch. If the listener performs expensive operations, it can slow down the stream. Keep the listener lightweight. Write metrics to a Delta table asynchronously or batch the writes.

The frequency of progress reports depends on the trigger. With the default trigger, progress reports are generated for each micro-batch. With the `availableNow` trigger, progress reports are generated during the run and then the query stops. With the `processingTime` trigger, progress reports are generated at each interval. The volume of monitoring data is proportional to the number of micro-batches. For high-frequency streams, consider aggregating metrics before writing them to a table.

Monitoring queries against the event log can be expensive if the event log is large. Use filters on the timestamp column to limit the amount of data scanned. Partition the event log by date if possible. Use Delta Lake statistics to skip files.

## An end-to-end example

Consider a scenario where you have a streaming pipeline that reads from Kafka, writes to a bronze table, and aggregates to a silver table. You want to monitor the pipeline and alert if the consumer lag exceeds a threshold. The following example shows how to set up monitoring with a `StreamingQueryListener` and a Databricks SQL alert.

```python
from pyspark.sql.streaming import StreamingQueryListener
from pyspark.sql.functions import col, from_json
from pyspark.sql.types import StructType, StructField, StringType, DoubleType

# Define the schema of the JSON payload.
schema = StructType([
    StructField("sensor_id", StringType(), nullable=False),
    StructField("temperature", DoubleType(), nullable=True),
])

# Read from Kafka.
df_raw = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker:9092")
    .option("subscribe", "sensor-readings")
    .load())

# Parse the JSON payload.
df_parsed = (df_raw
    .select(from_json(col("value").cast("string"), schema).alias("data"))
    .select("data.*"))

# Define a listener that writes metrics to a Delta table.
class MetricsWriter(StreamingQueryListener):
    def onQueryProgress(self, event):
        # Extract the metrics from the progress report.
        progress = event.progress
        metrics = [(
            progress["id"],
            progress["timestamp"],
            progress.get("inputRowsPerSecond", 0),
            progress.get("processedRowsPerSecond", 0),
            progress.get("batchDuration", 0),
            progress.get("schedulingDelay", 0)
        )]
        # Write the metrics to a Delta table.
        # In production, use a separate thread or a queue to avoid blocking.
        spark.createDataFrame(metrics, ["id", "timestamp", "input_rate", "processed_rate", "batch_duration", "scheduling_delay"]) \
            .write.mode("append").saveAsTable("monitoring.streaming_metrics")

# Register the listener.
spark.streams.addListener(MetricsWriter())

# Start the streaming query.
query = (df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/Volumes/manufacturing/checkpoints/sensor_readings")
    .trigger(availableNow=True)
    .toTable("manufacturing.bronze.sensor_readings"))

# Wait for the query to terminate.
query.awaitTermination()
```

The example defines a listener that writes metrics to a Delta table. You can then create a Databricks SQL alert that queries the `monitoring.streaming_metrics` table and sends an alert if the processed rate is lower than the input rate for a sustained period. You can also create alerts on consumer lag by querying the progress reports or the Kafka metrics.

## Summary

Monitoring streaming queries is essential for production pipelines. The Spark UI provides a visual view of active queries, but production monitoring requires programmatic access to metrics and automated alerts. The `StreamingQuery` object provides methods and properties to check whether a query is active, get its status, view recent progress, and handle failures. The `awaitTermination` method blocks until the query stops or fails. Wrap it in a try/except block and re-raise exceptions in Databricks Jobs.

The key metrics are input rate, processed rate, batch duration, scheduling delay, latency, and state size. The most important comparison is between input rate and processed rate. If the processed rate is consistently lower, the query is falling behind. Consumer lag for Kafka sources is an early warning. State size for stateful operations should be bounded by a watermark.

Use a `StreamingQueryListener` to capture progress events and write metrics to a Delta table. Use Databricks SQL alerts to query system tables or the event log and send notifications. For SQL streaming tables in Lakeflow Spark Declarative Pipelines, query the event log to monitor progress, expectations, and errors. The event log records data quality violations in addition to performance metrics.

Null handling, case sensitivity, and time zones affect the data and the monitoring queries. Set the session time zone explicitly to UTC. Best practices include monitoring both the Spark UI and programmatic metrics, tracking input and processed rates together, monitoring consumer lag, monitoring batch duration and state size, using `awaitTermination` with error handling, setting up alerts, and logging metrics to a Delta table. Common mistakes include not monitoring at all, relying only on the Spark UI, ignoring consumer lag, not setting a watermark, catching exceptions without re-raising, and not setting the session time zone.

Test monitoring logic with small streaming queries. Performance considerations include the cost of progress reports and the frequency of monitoring queries. Keep listeners lightweight and aggregate metrics before writing. By monitoring streaming queries effectively, you can detect problems early, respond quickly, and keep your lakehouse pipelines healthy and reliable.
