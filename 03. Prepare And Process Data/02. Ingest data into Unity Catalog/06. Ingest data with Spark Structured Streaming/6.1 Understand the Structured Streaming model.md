## Understand the Structured Streaming model

Structured Streaming is a stream processing model built into Apache Spark that treats incoming data as an unbounded table that grows continuously as new data arrives. Instead of reading a bounded dataset once, as you do with `spark.read`, you use `spark.readStream` to create a streaming DataFrame. This DataFrame represents a table that never stops growing. New rows appear at the bottom as data arrives from the source. You apply the same transformations you already know from the DataFrame API, such as `filter`, `select`, `withColumn`, `groupBy`, and `join`, and Spark applies them incrementally to the new data. The result is a continuously updated output that you write to a sink with `writeStream`.

The model matters because many data sources produce data continuously and with low latency requirements. Consider a manufacturing plant where sensors on equipment emit readings every few seconds. A batch job that runs every hour would leave the operations team blind to conditions that develop within minutes. A streaming job that processes each reading within seconds of its arrival lets the team react immediately. The same pattern applies to financial transactions, application logs, clickstream events, and change data capture feeds. Structured Streaming provides a single API for all of these sources, with the same transformations and the same fault tolerance guarantees.

Fault tolerance is a core part of the model. Streaming jobs run for long periods and can fail for many reasons: a network partition, a cluster restart, a source outage, or a code error. If a job fails and restarts, it must not reprocess data it has already processed, and it must not miss data that arrived while it was down. Structured Streaming solves this with checkpoints. A checkpoint is a durable record of the progress of the stream. It stores which records have been processed and what state the stream has accumulated. When the job restarts, it reads the checkpoint and resumes from where it left off. With a properly configured checkpoint and a replayable source, Structured Streaming provides exactly-once processing guarantees.

## The unbounded table model

The central idea of Structured Streaming is that a stream is a table. When you read from a streaming source, you get a DataFrame that represents an unbounded table. The table has a schema, just like a batch table. New rows are appended to the table as data arrives. You cannot see the entire table at once because it never ends, but you can define transformations and outputs as if it were a table. The streaming engine translates those transformations into an incremental execution plan that processes only the new data in each micro-batch.

This model is different from older stream processing systems that required you to think in terms of individual events and low-level operators. Structured Streaming lets you think in terms of tables and queries. A filter on a streaming DataFrame is the same operation as a filter on a batch DataFrame. A group-by and aggregation is the same operation, though it requires a watermark to bound the state. A join between two streaming DataFrames is supported when the join condition allows the engine to bound the state. The engine handles the complexity of incremental execution, state management, and fault tolerance.

The following table compares the batch table model with the streaming table model.

| Aspect | Batch table | Streaming table |
|---|---|---|
| Data extent | Bounded | Unbounded |
| Read method | `spark.read` | `spark.readStream` |
| Execution | One job per action | Continuous micro-batches |
| Actions | `count`, `collect`, `show` | `writeStream` only |
| State | Not required | Required for aggregations and joins |
| Fault tolerance | Re-run the job | Checkpoints and replayable source |
| Latency | Minutes to hours | Seconds to minutes |

The table shows that streaming tables are unbounded and require state and checkpoints, while batch tables are bounded and can be re-run. The transformations are largely the same, but the execution model and fault tolerance guarantees differ.

## The three-step pattern: source, transform, sink

Every Structured Streaming pipeline follows the same three-step pattern. First, you configure the source with `spark.readStream`. The source defines where the data comes from and how it is parsed. Second, you apply transformations to shape the data. The transformations are the same as in batch processing, with some restrictions. Third, you write the result to a sink with `writeStream`. The sink defines where the data goes, the output mode, and the checkpoint location.

### Step 1: Configure the source

The source is configured with `spark.readStream`. You specify the format, the connection details, and any options needed to parse the data. For Kafka, you provide the bootstrap servers and the topic. For file sources, you provide the directory path and the file format. For Auto Loader, you use the `cloudFiles` format and specify the schema location. The following example shows a Kafka source.

```python
# Import the functions needed for parsing.
from pyspark.sql.functions import col, from_json
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, TimestampType

# Define the schema of the JSON payload.
# The schema describes the structure of the value column.
schema = StructType([
    # The sensor_id identifies the device that produced the reading.
    StructField("sensor_id", StringType(), nullable=False),
    # The temperature is the measured value.
    StructField("temperature", DoubleType(), nullable=True),
    # The reading_time is when the sensor produced the reading.
    StructField("reading_time", TimestampType(), nullable=True),
])

# Configure the Kafka source.
# The format is "kafka".
# The bootstrap servers specify the Kafka cluster.
# The subscribe option names the topic.
# The startingOffsets option determines where to begin on a new query.
df_raw = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker:9092")
    .option("subscribe", "sensor-readings")
    .option("startingOffsets", "latest")
    .load())

# Parse the JSON payload from the value column.
# The value column is binary, so cast it to string first.
# from_json parses the JSON string using the defined schema.
df_parsed = (df_raw
    .select(from_json(col("value").cast("string"), schema).alias("data"))
    .select("data.*"))
```

The example configures a Kafka source, parses the JSON payload, and produces a streaming DataFrame with columns `sensor_id`, `temperature`, and `reading_time`. The `startingOffsets` option determines where to begin when starting a new query. Once a checkpoint is configured, subsequent runs resume from the checkpoint and ignore `startingOffsets`.

### Step 2: Apply transformations

Transformations shape the streaming DataFrame. You can filter, select, aggregate, join, and apply user-defined functions. The same rules apply as in batch processing, with some restrictions. Global sorts are not supported because the data is unbounded. Aggregations require a watermark to bound the state. Joins between two streams require a watermark on both sides and a time constraint. The following example applies a filter, a watermark, and an aggregation.

```python
# Import the window and aggregation functions.
from pyspark.sql.functions import window, avg, max, min

# Filter out readings with a null temperature.
df_filtered = df_parsed.filter(col("temperature").isNotNull())

# Apply a watermark and aggregate in 5-minute windows.
# The watermark of 2 minutes tells Spark to wait up to 2 minutes
# for late data before finalizing a window.
# The window function groups readings into 5-minute windows.
df_windowed = (df_filtered
    .withWatermark("reading_time", "2 minutes")
    .groupBy(window("reading_time", "5 minutes"), "sensor_id")
    .agg(
        # Compute the average temperature in each window.
        avg("temperature").alias("avg_temperature"),
        # Find the maximum temperature in each window.
        max("temperature").alias("max_temperature"),
        # Find the minimum temperature in each window.
        min("temperature").alias("min_temperature")
    ))
```

The example filters null temperatures, applies a watermark, and aggregates by 5-minute windows and sensor ID. The watermark bounds the state and allows Spark to finalize windows. Without a watermark, Spark would have to keep all data forever to handle arbitrarily late data.

### Step 3: Write to a sink

The sink is configured with `writeStream`. You specify the output mode, the checkpoint location, and the destination. The destination can be a Delta table in Unity Catalog, a file location, or a message bus. The following example writes to a Delta table.

```python
# Write the windowed aggregation to a Unity Catalog table.
# The format is "delta", which is the default for Unity Catalog tables.
# The outputMode "update" writes changed rows as new data arrives.
# The checkpointLocation stores the progress of the stream.
# The trigger "availableNow" processes all available data and stops.
(df_windowed
    .writeStream
    .format("delta")
    .outputMode("update")
    .option("checkpointLocation", "/checkpoints/sensor_aggregates")
    .trigger(availableNow=True)
    .toTable("manufacturing.silver.sensor_aggregates"))
```

The example writes the aggregation to `manufacturing.silver.sensor_aggregates`. The `outputMode("update")` writes changed rows. The `checkpointLocation` stores the progress of the stream. The `trigger(availableNow=True)` processes all available data and stops. This is useful for scheduled jobs. For continuous processing, omit the trigger or use `processingTime`.

## Checkpoints and fault tolerance

A checkpoint is a durable record of the progress of a stream. It stores the offsets of the source that have been processed, the state of any aggregations, and the metadata needed to resume. When a streaming job starts, it reads the checkpoint and resumes from the last processed offset. If the checkpoint does not exist, the job starts from the beginning or from the `startingOffsets` option, depending on the source. If the job fails, it can be restarted, and it will resume from the checkpoint without reprocessing or missing data.

The checkpoint location must be in reliable storage. For cloud deployments, use cloud storage such as S3, ADLS, or GCS, or a Unity Catalog volume. Do not use a local path because it is not durable and is lost if the cluster is restarted. The checkpoint is written on every micro-batch. If the checkpoint write fails, the stream fails. This is intentional: the stream cannot make progress without a durable record of its progress.

The following table summarizes the components of a checkpoint.

| Component | Purpose |
|---|---|
| Source offsets | Records which source records have been processed |
| State store | Stores the state of aggregations and joins |
| Metadata | Stores the query plan and configuration |
| Commit log | Records completed micro-batches |

The table shows that a checkpoint stores more than just offsets. It also stores the state of stateful operations and the metadata needed to reconstruct the query. This is why the checkpoint location must be stable across restarts. If you change the query logic in a way that is not compatible with the checkpoint, the stream may fail to start. In that case, you must use a new checkpoint location and start the stream from scratch.

Exactly-once processing requires three things: a replayable source, a durable checkpoint, and an idempotent sink. A replayable source is one that can re-deliver records from a given offset. Kafka is replayable. File sources are replayable if the files are immutable. A durable checkpoint records progress. An idempotent sink is one that can handle the same record being written more than once without creating duplicates. Delta Lake is idempotent when the write is part of a transaction that also updates the checkpoint. Structured Streaming coordinates the checkpoint update and the sink write so that they either both succeed or both fail. This is what provides exactly-once semantics.

## Sources and sinks

Structured Streaming supports several sources and sinks. The source determines how data enters the stream. The sink determines how data leaves. The following table summarizes the common sources.

| Source | Format | Use case |
|---|---|---|
| Kafka | `kafka` | Message bus, event streams |
| Event Hubs | `eventhubs` | Azure message bus |
| File source | `csv`, `json`, `parquet` | Files arriving in a directory |
| Auto Loader | `cloudFiles` | Scalable file ingestion |
| Delta table | `delta` | Streaming reads from a Delta table |
| Rate | `rate` | Testing and benchmarking |

The following table summarizes the common sinks.

| Sink | Format | Use case |
|---|---|---|
| Delta table | `delta` | Persistent storage in Unity Catalog |
| Kafka | `kafka` | Write to a message bus |
| File sink | `parquet`, `json`, `csv` | Write to files |
| Console | `console` | Debugging |
| Memory | `memory` | Debugging and testing |

The Delta table sink is the most common for ingestion pipelines because it writes to Unity Catalog, which provides governance and ACID transactions. The console and memory sinks are useful for debugging but are not suitable for production.

## Output modes and triggers

The output mode determines which records are written to the sink. There are three modes: `append`, `update`, and `complete`. The `append` mode writes only new rows. It is the default for most operations and is used when the stream produces new rows and never updates existing ones. The `update` mode writes changed rows. It is used with aggregations that update the result as new data arrives. The `complete` mode rewrites all rows on each trigger. It is used with aggregations that need the complete result, such as a running count.

The following table summarizes the output modes.

| Output mode | Behavior | Supported operations |
|---|---|---|
| `append` | Writes only new rows | Most operations, filters, joins |
| `update` | Writes changed rows | Aggregations without finalization |
| `complete` | Rewrites all rows | Aggregations with complete result |

A trigger controls how often the stream processes data. The default trigger processes data as soon as it arrives. The `processingTime` trigger processes data at a fixed interval. The `availableNow` trigger processes all available data and stops. The `continuous` trigger processes data continuously with low latency. The following table summarizes the triggers.

| Trigger | Behavior | Use case |
|---|---|---|
| Default | Processes each micro-batch as soon as possible | Low-latency streaming |
| `processingTime` | Processes at a fixed interval | Controlled resource usage |
| `availableNow` | Processes all available data and stops | Scheduled jobs |
| `continuous` | Processes data continuously | Ultra-low-latency applications |

The `availableNow` trigger is useful for scheduled jobs. It processes all available data and stops, which is more cost-effective than a continuously running cluster. The `continuous` trigger provides the lowest latency but is more expensive and has more restrictions.

## Schema enforcement, null handling, and time zones

Schema enforcement applies to streaming writes. Delta Lake enforces the schema of the target table. If the streaming DataFrame has extra columns, the write fails unless schema evolution is enabled. If the DataFrame is missing nullable columns, those columns are written as null. If a non-nullable column is missing, the write fails. For streaming file sources, schema inference is not supported. You must define the schema explicitly. Auto Loader supports schema inference and stores the inferred schema in a schema location.

Null handling in streaming follows the same rules as in batch processing. Nulls in the source are preserved in the target unless you filter or replace them. If a target column is non-nullable, a null value causes the write to fail. You should handle nulls in the transformation step. For example, you can filter out rows with null keys or replace null values with a default using `coalesce`.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. When you use `current_timestamp()` or `current_date()` in a streaming query, the values are computed in the session time zone. Event-time processing uses the timestamp in the data, which should be stored in UTC. To avoid off-by-hours errors, set the session time zone explicitly at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Use timestamp literals with explicit offsets when comparing to timestamps.

## Best practices

Always configure a checkpoint location. The checkpoint stores the progress of the stream and allows it to resume after a failure. Without a checkpoint, the stream cannot recover and may reprocess or lose data. Use reliable storage such as cloud storage or a Unity Catalog volume.

Use Auto Loader for file-based streaming. Auto Loader handles file detection, schema inference, and schema evolution automatically. It is more efficient and more robust than the generic file source.

Define schemas explicitly for streaming file sources. Schema inference is not supported for streaming file sources. Explicit schemas make the pipeline deterministic and avoid the extra pass required for inference.

Use watermarks for streaming aggregations. A watermark bounds the state and allows Spark to finalize windows. Without a watermark, Spark must keep all data forever to handle late data.

Use the `availableNow` trigger for scheduled jobs. It processes all available data and stops, which is more cost-effective than a continuously running cluster.

Set the session time zone explicitly to UTC. This avoids off-by-hours errors when reading and writing timestamps.

Use schema evolution deliberately. Adding columns changes the table schema and may break downstream consumers.

Monitor streaming queries. Track metrics such as input rate, processing rate, batch duration, and latency. Set up alerts for failures and for latency spikes.

## Common mistakes and pitfalls

The most common mistake is not configuring a checkpoint location. Without a checkpoint, the stream cannot recover from failures and may reprocess or lose data. Always configure a checkpoint.

A second mistake is using schema inference for streaming file sources. Schema inference is not supported for streaming sources. Define the schema explicitly.

A third mistake is using an output mode that is not supported for the operation. For example, `complete` mode is not supported for all operations. Check the documentation for the operation you are using.

A fourth mistake is not setting a watermark for streaming aggregations. Without a watermark, Spark must keep all data forever to handle late data. This can cause memory issues and slow performance.

A fifth mistake is using a local path for the checkpoint location. Local paths are not durable. Use cloud storage or a Unity Catalog volume.

A sixth mistake is not handling late data. If data arrives after the watermark, it is dropped. Decide how to handle late data based on your business requirements.

A seventh mistake is not monitoring the stream. Streaming queries can fail silently if not monitored. Set up alerts for failures and for latency spikes.

## Testing streaming pipelines

Testing streaming pipelines is more complex than testing batch pipelines because the data is unbounded. You can test streaming logic by using a batch DataFrame as a source or by using a test source that you can control. The following example shows a test for a streaming aggregation using a batch DataFrame.

```python
from pyspark.sql import Row
from pyspark.sql.functions import window, avg
from datetime import datetime

# Create a batch DataFrame with test data.
# The data includes readings at different times.
test_data = [
    Row(sensor_id="S1", temperature=100.0, reading_time=datetime(2026, 1, 15, 10, 0)),
    Row(sensor_id="S1", temperature=110.0, reading_time=datetime(2026, 1, 15, 10, 2)),
    Row(sensor_id="S2", temperature=90.0, reading_time=datetime(2026, 1, 15, 10, 3)),
]
df_test = spark.createDataFrame(test_data)

# Apply the same aggregation logic used in the stream.
# The window function groups readings into 5-minute windows.
df_aggregated = (df_test
    .groupBy(window("reading_time", "5 minutes"), "sensor_id")
    .agg(avg("temperature").alias("avg_temperature")))

# Collect the result and verify.
rows = df_aggregated.orderBy("sensor_id").collect()
# Sensor S1 has two readings in the same window, average 105.
assert rows[0].sensor_id == "S1" and rows[0].avg_temperature == 105.0
# Sensor S2 has one reading, average 90.
assert rows[1].sensor_id == "S2" and rows[1].avg_temperature == 90.0
```

The test uses a batch DataFrame to verify the aggregation logic. Streaming logic that does not depend on streaming-specific features such as watermarks can be tested this way. For streaming-specific features, use a test source that produces data at a controlled rate.

## Performance considerations

Streaming performance depends on the source, the processing logic, and the sink. Kafka sources are fast but require careful configuration of partitions and consumer groups. File sources are limited by the rate at which files arrive and the number of files. Auto Loader is optimized for file sources and can scale to millions of files.

Micro-batch size affects latency and throughput. Smaller micro-batches reduce latency but increase overhead. Larger micro-batches increase throughput but increase latency. The default trigger processes data as soon as it arrives. You can use `processingTime` to control the interval.

State management is important for aggregations. Watermarks bound the state, but you should also monitor the state size. If the state grows too large, the stream may run out of memory. Use watermarks and windows to keep the state bounded.

Checkpointing adds overhead. The checkpoint is written on each micro-batch. Use a reliable storage location with low latency. Avoid using a location that is slow or has high contention.

Destination performance depends on file size and partitioning. The stream writes to Delta tables. It may create many small files. Run `OPTIMIZE` periodically to compact small files. Use partitioning or liquid clustering on columns that are commonly used in filters.

Use the `availableNow` trigger for scheduled jobs to process all available data and stop. This is more cost-effective than a continuously running cluster.

## An end-to-end example

Consider a scenario where sensor data arrives continuously from manufacturing equipment. You want to ingest the raw readings into a bronze table and compute rolling aggregates into a silver table. The following example shows the complete pipeline.

```python
from pyspark.sql.functions import (
    col, from_json, window, avg, max, min, current_timestamp
)
from pyspark.sql.types import StructType, StructField, StringType, DoubleType, TimestampType

# Define the schema of the JSON payload.
schema = StructType([
    StructField("sensor_id", StringType(), nullable=False),
    StructField("temperature", DoubleType(), nullable=True),
    StructField("reading_time", TimestampType(), nullable=True),
])

# Configure the Kafka source.
df_raw = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker:9092")
    .option("subscribe", "sensor-readings")
    .option("startingOffsets", "latest")
    .load())

# Parse the JSON payload.
df_parsed = (df_raw
    .select(from_json(col("value").cast("string"), schema).alias("data"))
    .select("data.*"))

# Write the raw readings to a bronze table.
(df_parsed
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/checkpoints/bronze_sensor_readings")
    .toTable("manufacturing.bronze.sensor_readings"))

# Compute 5-minute aggregates for a silver table.
df_aggregated = (df_parsed
    .withWatermark("reading_time", "2 minutes")
    .groupBy(window("reading_time", "5 minutes"), "sensor_id")
    .agg(
        avg("temperature").alias("avg_temperature"),
        max("temperature").alias("max_temperature"),
        min("temperature").alias("min_temperature")
    ))

# Write the aggregates to a silver table.
(df_aggregated
    .writeStream
    .format("delta")
    .outputMode("update")
    .option("checkpointLocation", "/checkpoints/silver_sensor_aggregates")
    .toTable("manufacturing.silver.sensor_aggregates"))
```

The example reads from Kafka, parses JSON, writes raw readings to a bronze table, computes 5-minute aggregates, and writes the aggregates to a silver table. The bronze write uses `append` mode because it writes raw readings. The silver write uses `update` mode because it updates the aggregation as new data arrives. Both streams have their own checkpoint locations. The pipeline provides exactly-once processing and stores the data in Unity Catalog.

You use `spark.readStream` to create a streaming DataFrame and apply the same transformations you use in batch processing. The model provides exactly-once processing guarantees when configured with a replayable source, a durable checkpoint, and an idempotent sink.

Every Structured Streaming pipeline follows a three-step pattern. First, configure the source with `spark.readStream`. Second, apply transformations to shape the data. Third, write to a sink with `writeStream`. The sink requires a checkpoint location, which stores the progress of the stream and allows it to resume after a failure. Without a checkpoint, the stream cannot recover and may reprocess or lose data.

Structured Streaming supports several sources, including Kafka, Event Hubs, file sources, Auto Loader, and Delta tables. It supports sinks including Delta tables, Kafka, files, console, and memory. The output mode determines which records are written: `append` writes new rows, `update` writes changed rows, and `complete` rewrites all rows. Triggers control how often the stream processes data. Best practices include always configuring a checkpoint, using Auto Loader for file-based streaming, defining schemas explicitly, using watermarks, using the `availableNow` trigger for scheduled jobs, and monitoring streaming queries.
