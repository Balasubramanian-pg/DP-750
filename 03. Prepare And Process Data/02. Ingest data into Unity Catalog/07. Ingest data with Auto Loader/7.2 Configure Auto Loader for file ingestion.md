## Configure Auto Loader for file ingestion

Auto Loader is a Structured Streaming source in Azure Databricks that incrementally and efficiently processes new data files as they arrive in cloud storage. It is implemented as a source called `cloudFiles` that you use with `spark.readStream`. You provide the input directory path, configure the file format and schema options, and Auto Loader handles file discovery, schema inference, and incremental processing. The result is a streaming DataFrame that you write to a Delta table in Unity Catalog. Auto Loader scales to process billions of files for migration or backfill and supports near real-time ingestion of millions of files per hour. It is the recommended way to ingest files into the lakehouse.

Configuring Auto Loader correctly matters because file-based ingestion is one of the most common patterns in the lakehouse. Raw data lands in cloud storage as CSV, JSON, Parquet, Avro, ORC, XML, text, or binary files. A pipeline must detect new files, parse them, and load them into a table without duplicating or missing data. Manual approaches such as listing directories and tracking processed files in a separate table are error-prone and do not scale. Auto Loader solves these problems with a checkpoint-based mechanism that provides exactly-once processing guarantees. It integrates with Unity Catalog, so every file it ingests is governed by the same access controls, lineage, and auditing that apply to the rest of the lakehouse. In a medallion architecture, Auto Loader is the standard way to land raw files into the bronze layer.

These notes explain how to configure Auto Loader for file ingestion. They describe the `cloudFiles` source, the schema location and checkpoint location, the file formats supported, and the triggers that control processing. They show PySpark and SQL examples with full comments. They also cover schema inference, schema evolution, rescued data, Unity Catalog integration, null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example. The goal is that you can read these notes alone and understand how to configure Auto Loader pipelines reliably and efficiently.

## Understanding the cloudFiles source

Auto Loader is a streaming source that monitors a cloud storage location and incrementally processes new files. It maintains state about which files it has already processed, ensuring each file is ingested exactly once. When you start an Auto Loader stream, it can process existing files in the directory and then continuously watch for new arrivals. The stream stores progress information in a checkpoint location, which allows it to resume from exactly where it stopped if interrupted. Auto Loader also stores the inferred schema in a schema location so that it can track schema changes over time.

The `cloudFiles` source is configured with `spark.readStream.format("cloudFiles")`. You specify the file format with `cloudFiles.format`, the schema location with `cloudFiles.schemaLocation`, and the input path in the `load` method. Auto Loader supports JSON, CSV, Parquet, Avro, ORC, XML, text, and binary files. The following table summarizes the key options.

| Option | Purpose | Required |
|---|---|---|
| `cloudFiles.format` | Specifies the source file format | Yes |
| `cloudFiles.schemaLocation` | Stores the inferred schema and tracks schema changes | Yes |
| `cloudFiles.schemaEvolutionMode` | Controls how schema changes are handled | No, default is `addNewColumns` |
| `cloudFiles.useManagedFileEvents` | Enables file notification mode with file events | No, recommended for production |
| `rescuedDataColumn` | Stores values that do not match the schema | No, recommended when using rescue mode |
| `cloudFiles.inferColumnTypes` | Infers data types for JSON and CSV | No, default is `false` |

The table shows the options that control format, schema, file detection, and data rescue. The `cloudFiles.format` and `cloudFiles.schemaLocation` options are required. The other options have defaults or are recommended for specific scenarios.

## Basic PySpark configuration

The following example shows how to configure Auto Loader to read JSON files from Azure Data Lake Storage and write them to a Unity Catalog table. It uses the `availableNow` trigger to process all currently available files and then stop.

```python
# Define the base path for the Auto Loader stream.
# The base path is used to derive the schema and checkpoint paths.
# In production, store these paths in a Unity Catalog volume.
base_path = "abfss://container@storage.dfs.core.windows.net/autoloader/orders"

# Define the schema location.
# Auto Loader stores the inferred schema in this directory.
# The schema location must be a durable path.
schema_path = f"{base_path}/schema"

# Define the checkpoint location.
# The checkpoint stores the progress of the stream.
# Each stream must have its own checkpoint location.
checkpoint_path = f"{base_path}/checkpoint"

# Configure Auto Loader to read JSON files.
# The format "cloudFiles" is the Auto Loader source.
# The cloudFiles.format option specifies the file format (json).
# The cloudFiles.schemaLocation option stores the inferred schema.
df_auto = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", schema_path)
    .load("abfss://container@storage.dfs.core.windows.net/incoming/orders/"))

# Write the stream to a Unity Catalog table.
# The checkpointLocation option stores the progress of the stream.
# The trigger availableNow processes all available data and stops.
(df_auto
    .writeStream
    .option("checkpointLocation", checkpoint_path)
    .trigger(availableNow=True)
    .toTable("sales.bronze.orders"))
```

The example defines a base path, a schema path, and a checkpoint path. It configures Auto Loader to read JSON files from the incoming directory. It writes the stream to `sales.bronze.orders` with the `availableNow` trigger. The `cloudFiles.schemaLocation` stores the inferred schema. The `checkpointLocation` stores the progress of the stream. The `availableNow` trigger processes all available data and stops, which is useful for scheduled batch jobs.

The schema location and checkpoint location can be the same, but keeping them separate allows you to reset a stream without losing the inferred schema. If you reset the stream, you delete the checkpoint location and start from the beginning. If the schema location is separate, the inferred schema is preserved. This is useful when you need to reprocess data without re-inferring the schema.

## Using triggers for batch and continuous processing

Auto Loader uses Structured Streaming triggers to control when data is processed. The `availableNow` trigger processes all currently available files and then stops. This pattern works well for scheduled batch jobs. For continuous processing, you can omit the trigger or use `trigger(processingTime="1 minute")` to process files in intervals. The following table summarizes the trigger options for Auto Loader.

| Trigger | Behavior | Recommended for |
|---|---|---|
| `availableNow=True` | Processes all available data and stops | Scheduled batch jobs |
| Default | Processes continuously as data arrives | Continuous ingestion |
| `processingTime="1 minute"` | Processes at fixed intervals | Controlled resource usage |
| File arrival | Starts when new files arrive | Low-latency ingestion with file events |

The `availableNow` trigger is the most cost-effective for scheduled jobs because the cluster can be shut down between runs. The default trigger is suitable for continuous ingestion where low latency is required. The `processingTime` trigger reduces the number of micro-batches and can lower compute cost. The file arrival trigger is the most cost-effective for low-latency ingestion because compute runs only when new files arrive.

The following example shows a stream configured with a `processingTime` trigger.

```python
# Configure Auto Loader to read CSV files.
df_auto_csv = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "csv")
    .option("cloudFiles.schemaLocation", "/Volumes/sales/bronze/schemas/sales")
    .option("header", "true")
    .load("/Volumes/sales/bronze/raw/sales/"))

# Write the stream with a processingTime trigger.
# The trigger processes a micro-batch every 1 minute.
# Data that arrives between intervals is processed at the next interval.
(df_auto_csv
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/Volumes/sales/bronze/checkpoints/sales")
    .trigger(processingTime="1 minute")
    .toTable("sales.bronze.sales"))
```

The example processes a micro-batch every minute. If no new data has arrived, the engine still starts a micro-batch at the interval, but the micro-batch may be empty. The checkpoint records progress after each micro-batch. The `processingTime` trigger is useful when the source produces data at a known rate and you want to control the frequency of writes.

## Using SQL syntax with read_files

Auto Loader also supports SQL syntax through the `read_files` table-valued function. This approach is useful when you prefer SQL or when working in SQL notebooks. The following SQL example reads JSON files with a schema hint.

```sql
-- Read JSON files using the read_files table-valued function.
-- The first argument is the input path.
-- The format option specifies that the files are JSON.
-- The schemaHints option provides a hint for the schema.
-- The hint is used to guide schema inference and to cast columns.
SELECT *
FROM read_files(
  'abfss://container@storage.dfs.core.windows.net/incoming/orders/',
  format => 'json',
  schemaHints => 'order_id INT, amount DECIMAL(10,2)'
);
```

The example reads JSON files and provides a schema hint. The `schemaHints` option tells Auto Loader the expected types for `order_id` and `amount`. This is useful when the inferred types are not what you want. For example, JSON numbers may be inferred as doubles, but you may want them as integers or decimals. The schema hint guides the inference and the cast.

When using `read_files` with streaming tables in Lakeflow Spark Declarative Pipelines, Auto Loader capabilities are automatically enabled. Use the `STREAM` keyword to enable incremental processing. The following SQL example creates a streaming table from files.

```sql
-- Create a streaming table from files using read_files.
-- The STREAM keyword enables incremental processing.
-- The pipeline manages checkpointing and schema evolution automatically.
CREATE OR REFRESH STREAMING TABLE bronze_orders
AS SELECT * FROM STREAM read_files(
  'abfss://container@storage.dfs.core.windows.net/incoming/orders/',
  format => 'json'
);
```

The example creates a streaming table named `bronze_orders`. The `STREAM` keyword tells the pipeline to use Auto Loader for incremental processing. The pipeline manages the checkpoint location and schema evolution automatically. You do not need to configure the checkpoint or schema location manually. This is the recommended approach for SQL-based ingestion in Lakeflow Spark Declarative Pipelines.

## Schema inference and evolution

Auto Loader can automatically detect the schema of the data it loads and evolve the schema as new columns are introduced. This eliminates the need to manually track and apply schema changes. Auto Loader stores the schema in the `cloudFiles.schemaLocation` directory. When it first reads data, it samples the first 50 GB or 1000 files that it discovers, whichever limit is crossed first, to infer the schema. For formats that do not encode data types, such as JSON, CSV, and XML, Auto Loader infers all columns as strings unless `cloudFiles.inferColumnTypes` is set to `true`. For formats with typed schemas, such as Parquet and Avro, Auto Loader samples a subset of files and merges their schemas.

Auto Loader supports several schema evolution modes, which you set with `cloudFiles.schemaEvolutionMode`. The following table summarizes the modes.

| Mode | Behavior | Use case |
|---|---|---|
| `addNewColumns` | Adds new columns to the schema | Default; schema evolves as new columns appear |
| `rescue` | Does not evolve the schema; new columns are rescued | When you want to handle schema changes manually |
| `failOnNewColumns` | Fails the stream when a new column appears | When schema changes require manual intervention |
| `none` | Does not evolve the schema; new columns are ignored | When the schema is fixed |

The `rescue` mode uses a rescued data column, typically named `_rescued_data`, to store values that do not match the schema. This prevents data loss when the source schema changes or when values have unexpected types. The following example shows how to configure schema evolution with rescue mode.

```python
# Configure Auto Loader with schema evolution and rescue.
# The cloudFiles.schemaEvolutionMode option is set to "rescue".
# The rescuedDataColumn option specifies a column to store rescued data.
df_rescue = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", "/Volumes/sales/bronze/schemas/orders")
    .option("cloudFiles.schemaEvolutionMode", "rescue")
    .option("rescuedDataColumn", "_rescued_data")
    .load("/Volumes/sales/bronze/raw/orders/"))
```

The example configures Auto Loader to rescue data that does not match the schema. The rescued data column stores the original values, which you can inspect later using semi-structured data access APIs. This is useful when the source schema changes frequently or when data quality is uncertain.

## Unity Catalog integration and storage locations

Auto Loader integrates with Unity Catalog. You can securely ingest data from external locations configured with Unity Catalog. Databricks recommends storing checkpoint and schema evolution information in storage locations managed by Unity Catalog. File notification mode is only supported on compute with dedicated access mode. When you use Auto Loader with Unity Catalog, you need `READ FILES` permission on the external location and `WRITE FILES` and `CREATE TABLE` permission on the target location.

The following example shows how to use Auto Loader with Unity Catalog to load into a managed table.

```python
# Define the checkpoint path in a Unity Catalog volume.
checkpoint_path = "/Volumes/sales/bronze/checkpoints/orders"

# Define the schema path in a Unity Catalog volume.
schema_path = "/Volumes/sales/bronze/schemas/orders"

# Configure Auto Loader to read from a Unity Catalog external location.
df_unity = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", schema_path)
    .option("cloudFiles.useManagedFileEvents", "true")
    .load("abfss://sales-source@storageaccount.dfs.core.windows.net/orders/"))

# Write to a Unity Catalog managed table.
(df_unity
    .writeStream
    .option("checkpointLocation", checkpoint_path)
    .trigger(availableNow=True)
    .toTable("sales.bronze.orders"))
```

The example reads from an Azure Data Lake Storage location and writes to a Unity Catalog managed table. The checkpoint and schema locations are stored in Unity Catalog volumes. File events are enabled on the external location, so Auto Loader uses file notification mode with file events. This is the recommended configuration for production workloads.

## Null handling, case sensitivity, and time zones

Null handling in Auto Loader follows the same rules as other streaming sources. Nulls in the source files are preserved unless you filter or replace them. If a target column is non-nullable, a null value causes the write to fail. You should handle nulls in the transformation step. For example, you can filter out rows with null keys or replace null values with a default using `coalesce`. The rescued data column captures values that do not match the schema, which can include nulls or type mismatches.

Case sensitivity affects string comparisons and column names. In Spark SQL, column names are case-insensitive by default. String values are case-sensitive. If the source data has inconsistent casing, normalize it with `upper` or `lower`, or use a case-insensitive collation if the table is configured for one. The schema location stores the column names as inferred. If the source files have columns with different casing, Auto Loader may infer them as separate columns.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. When Auto Loader parses timestamps from files, it interprets them in the session time zone unless the file includes an explicit offset. To avoid off-by-hours errors, set the session time zone explicitly to UTC at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Store timestamps in UTC and convert to local time only for display.

## Best practices

Use file notification mode with file events for most production workloads. It is more scalable and cost-effective than directory listing mode. Enable file events on the external location and set `cloudFiles.useManagedFileEvents` to `true` in the stream configuration.

Use a separate schema location for each Auto Loader stream. The schema location stores the inferred schema and tracks schema changes. Sharing a schema location between streams can cause conflicts.

Use a unique checkpoint location for each stream. The checkpoint stores the progress of the stream. Sharing a checkpoint between streams causes data processing errors.

Store checkpoint and schema locations in Unity Catalog managed storage. This ensures consistent governance and avoids permission issues with nested paths.

Use the `availableNow` trigger for scheduled jobs. It processes all available data and stops, which reduces compute cost. Use a file arrival trigger for low-latency ingestion with file events.

Handle schema evolution deliberately. Use `addNewColumns` mode to add new columns automatically. Use `rescuedDataColumn` to capture data that does not match the schema. Use `failOnNewColumns` when schema changes require manual intervention.

Set the session time zone explicitly to UTC. This avoids off-by-hours errors when parsing timestamps.

Monitor the stream. Track metrics such as input rate, processed rate, and batch duration. Use the Auto Loader observability features to monitor progress and detect issues.

## Common mistakes and pitfalls

The most common mistake is using directory listing mode for large directories. Directory listing scans the entire directory on each trigger, which becomes slow and expensive as the directory grows. Use file notification mode with file events instead.

A second mistake is not configuring a schema location. Without a schema location, Auto Loader cannot infer or evolve the schema. The stream fails or produces unexpected results.

A third mistake is sharing a checkpoint location between streams. Each stream must have its own checkpoint location. Sharing causes conflicts and data errors.

A fourth mistake is using file notification mode on compute without dedicated access mode. File notification mode is only supported on compute with dedicated access mode.

A fifth mistake is not handling out-of-order files. Auto Loader does not guarantee the order in which files are discovered or processed. Design your pipelines to handle out-of-order arrivals.

A sixth mistake is ignoring the rescued data column. When schema evolution is enabled, values that do not match the schema are rescued. If you do not inspect the rescued data, you may miss data quality issues.

A seventh mistake is not setting the session time zone. Timestamps are stored in UTC. If you compare them to local time without converting, you may get incorrect results.

## Testing Auto Loader configuration

Testing Auto Loader configuration involves verifying that the stream discovers new files, infers the schema, and writes the expected rows to the target table. You can test with a small directory of files and the `availableNow` trigger. The following example shows a test for Auto Loader.

```python
from pyspark.sql import Row

# Create a test directory with a small CSV file.
test_data = [Row(id=1, name="Alice", amount=100.0)]
df_test = spark.createDataFrame(test_data)
df_test.write.mode("overwrite").option("header", "true").csv("/tmp/auto_loader_test/")

# Configure Auto Loader to read the test directory.
df_auto = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "csv")
    .option("cloudFiles.schemaLocation", "/tmp/auto_loader_schema")
    .option("header", "true")
    .load("/tmp/auto_loader_test/"))

# Write the stream with availableNow.
query = (df_auto
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/tmp/auto_loader_checkpoint")
    .trigger(availableNow=True)
    .toTable("tmp.auto_loader_target"))

# Wait for the query to terminate.
query.awaitTermination()

# Verify the result.
assert spark.read.table("tmp.auto_loader_target").count() == 1
```

The test creates a small CSV file, configures Auto Loader to read it, writes to a target table, and verifies the row count. Run tests like this in your CI pipeline against a small local Spark session. Clean up temporary files and tables after the test.

## Performance considerations

Auto Loader performance depends on the file detection mode, the file format, and the size of the files. File notification mode with file events is the most performant and scalable mode. Directory listing mode is limited by the size of the directory. Parquet and Avro files are faster to read than CSV and JSON because they are columnar and self-describing.

The number of files affects performance. Many small files are inefficient because each file has metadata overhead. Aim for files of 100 MB to 1 GB. If your source produces many small files, consider compacting them before ingestion or running `OPTIMIZE` after ingestion to compact the target table.

Use a separate volume for each subpath when using file events. This scopes file discovery to only the relevant objects and avoids unnecessary file discovery overhead.

Use the `availableNow` trigger for scheduled jobs to process all available data and stop. This reduces compute cost compared to a continuously running cluster.

## An end-to-end example

Consider a scenario where you ingest JSON order files from cloud storage into a bronze table, and then aggregate them into a silver table. The pipeline uses Auto Loader with file notification mode and file events. The following example shows the complete setup.

```python
from pyspark.sql.functions import col, sum, count

# Configure Auto Loader to read JSON files with file events.
df_auto = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", "/Volumes/sales/bronze/schemas/orders")
    .option("cloudFiles.useManagedFileEvents", "true")
    .option("rescuedDataColumn", "_rescued_data")
    .load("/Volumes/sales/bronze/raw/orders/"))

# Write raw orders to a bronze table.
(df_auto
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/Volumes/sales/bronze/checkpoints/orders")
    .option("mergeSchema", "true")
    .trigger(availableNow=True)
    .toTable("sales.bronze.orders"))

# Read the bronze table and aggregate into a silver table.
df_bronze = spark.read.table("sales.bronze.orders")
df_silver = (df_bronze
    .filter(col("amount").isNotNull())
    .groupBy("customer_id")
    .agg(
        sum("amount").alias("total_amount"),
        count("*").alias("order_count")
    ))

# Write the silver table.
df_silver.write.mode("overwrite").saveAsTable("sales.silver.customer_totals")
```

The example reads JSON files with Auto Loader, writes to a bronze table, aggregates the data, and writes to a silver table. The bronze table uses `mergeSchema` to evolve the schema as new columns appear. The silver table is rebuilt from the bronze table. The pipeline uses file notification mode with file events for scalability and cost efficiency.
