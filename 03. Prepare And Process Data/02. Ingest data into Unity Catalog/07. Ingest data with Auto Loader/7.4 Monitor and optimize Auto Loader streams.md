## Monitor and optimize Auto Loader streams

Auto Loader is a Structured Streaming source in Azure Databricks that incrementally and efficiently processes new data files as they arrive in cloud storage. It uses the `cloudFiles` format with `spark.readStream` to detect new files, infer schemas, and process each file exactly once. Monitoring an Auto Loader stream means observing its progress, the number of files discovered, the number of files processed, the volume of data waiting, and any errors or schema changes. Optimizing an Auto Loader stream means tuning its configuration so that it processes data efficiently at scale, without overwhelming the cluster, the source storage, or the checkpoint location.

Monitoring and optimization matter because Auto Loader pipelines often run continuously or on a frequent schedule, and they can process millions of files. Without monitoring, you cannot tell whether the stream is keeping up with incoming data, whether files are being skipped, or whether the checkpoint is healthy. Without optimization, a stream can become slow, expensive, or unstable as data volumes grow. A stream that uses directory listing mode on a large directory will spend more time listing files than processing them. A stream that allows unbounded micro-batches can run out of memory. A stream that uses a checkpoint location with an aggressive lifecycle policy can lose critical state and require a full restart.

These notes cover how to monitor and optimize Auto Loader streams. They explain the `cloud_files_state` SQL function, the Structured Streaming progress metrics, the `_metadata` column, and the options that control processing rate, such as `cloudFiles.maxFilesPerTrigger` and `cloudFiles.maxBytesPerTrigger`. They explain how to protect the checkpoint location, how to integrate Auto Loader with Lakeflow Spark Declarative Pipelines, and how to use file notification mode with file events for scalability. They also cover null handling, case sensitivity, time zones, schema enforcement, expectations, best practices, common mistakes, testing, performance, and an end-to-end example. Each concept is introduced in prose, then shown in code with full comments, then interpreted. The goal is that you can read these notes alone and understand how to keep Auto Loader streams healthy, efficient, and reliable.

## Understanding Auto Loader monitoring and optimization

Auto Loader monitoring is the practice of observing the state of the stream and the files it has discovered. It answers questions such as: How many files have been discovered? How many have been processed? How many are outstanding? How many bytes are waiting? How long does each micro-batch take? Is the stream keeping up with the arrival rate? Optimization is the practice of adjusting configuration options and infrastructure choices to improve throughput, reduce cost, and maintain stability. The two are connected. Monitoring tells you what is happening. Optimization tells you what to change.

The following table summarizes the key metrics and options for monitoring and optimization.

| Area | Tool or option | Purpose |
|---|---|---|
| File discovery state | `cloud_files_state` SQL function | Query the state of discovered files |
| Streaming progress | Spark UI, `StreamingQuery` API | View input rate, processed rate, batch duration |
| Outstanding work | `numFilesOutstanding`, `numBytesOutstanding` | See how much work is waiting |
| Processing rate | `cloudFiles.maxFilesPerTrigger` | Limit files per micro-batch |
| Processing volume | `cloudFiles.maxBytesPerTrigger` | Limit bytes per micro-batch |
| File-level metadata | `_metadata` column | Access file path, name, size, modification time |
| Checkpoint health | Checkpoint location | Store progress and state durably |
| Scalability | File notification mode with file events | Avoid directory listing overhead |

The table shows that monitoring and optimization cover file discovery, processing progress, rate control, metadata access, and checkpoint management. The rest of these notes explains each area in detail.

## Monitoring file discovery with cloud_files_state

Auto Loader provides a SQL function called `cloud_files_state` that returns the state of the files that Auto Loader has discovered for a given checkpoint location. The function takes the checkpoint path as an argument and returns a table with one row per discovered file. The table includes columns such as the file path, the file size, the file modification time, and the processing status. You can use this function to verify that files are being discovered and processed as expected. It is useful for debugging, for auditing, and for building custom monitoring dashboards.

The following SQL example queries the state of an Auto Loader stream.

```sql
-- Query the state of discovered files for an Auto Loader stream.
-- The cloud_files_state function takes the checkpoint path as an argument.
-- The checkpoint path is the same path used in the checkpointLocation option.
-- The function returns one row per discovered file.
SELECT
  -- The file path shows where the file is stored.
  path,
  -- The file size shows the size of the file in bytes.
  size,
  -- The modification time shows when the file was last changed.
  modification_time,
  -- The processing status shows whether the file has been processed.
  -- Common values include "PROCESSED" and "DISCOVERED".
  status
FROM cloud_files_state('/Volumes/sales/bronze/checkpoints/orders')
-- Filter to files that have not been processed.
-- This shows the outstanding work for the stream.
WHERE status = 'DISCOVERED'
-- Order by modification time, oldest first.
ORDER BY modification_time;
```

The example queries the checkpoint location and returns the files that have been discovered but not yet processed. The `status` column indicates whether a file is `DISCOVERED` or `PROCESSED`. If many files are in `DISCOVERED` status, the stream is falling behind. If files are stuck in `DISCOVERED` for a long time, there may be a problem with the stream, such as a failure that has stopped processing. You can also count the files by status to get a summary.

The following SQL example counts files by status.

```sql
-- Count files by processing status.
-- This gives a summary of how many files are processed and how many are waiting.
SELECT
  status,
  COUNT(*) AS file_count,
  SUM(size) AS total_bytes
FROM cloud_files_state('/Volumes/sales/bronze/checkpoints/orders')
GROUP BY status
ORDER BY status;
```

The example returns the number of files and the total bytes for each status. This is useful for monitoring the backlog. A growing `DISCOVERED` count with a stable `PROCESSED` count indicates that the stream cannot keep up.

You can run `cloud_files_state` from PySpark by using `spark.sql`. The following PySpark example runs the same query.

```python
# Run the cloud_files_state query from PySpark.
# spark.sql executes the SQL statement and returns a DataFrame.
df_state = spark.sql("""
    SELECT
      status,
      COUNT(*) AS file_count,
      SUM(size) AS total_bytes
    FROM cloud_files_state('/Volumes/sales/bronze/checkpoints/orders')
    GROUP BY status
    ORDER BY status
""")

# Display the result.
display(df_state)
```

The PySpark example returns the same summary as the SQL example. You can use this DataFrame to build alerts or to log the state to a monitoring table.

## Monitoring streaming progress with Structured Streaming metrics

Auto Loader reports its progress through the Structured Streaming metrics. You can view these metrics in the Spark UI under the Structured Streaming tab. The tab shows the input rate, the processed rate, the batch duration, and the scheduling delay for each micro-batch. For Auto Loader, the metrics also include `numFilesOutstanding` and `numBytesOutstanding`, which show how many files and how many bytes are waiting to be processed. These metrics are useful for understanding whether the stream is keeping up with the arrival rate.

The following table summarizes the Auto Loader-specific metrics.

| Metric | Meaning | What to watch for |
|---|---|---|
| `numFilesOutstanding` | Files discovered but not yet processed | Growing value indicates a backlog |
| `numBytesOutstanding` | Bytes waiting to be processed | Growing value indicates a backlog |
| `inputRowsPerSecond` | Rows arriving per second | Sudden spikes or drops |
| `processedRowsPerSecond` | Rows processed per second | Should be close to input rate |
| `batchDuration` | Time to process a micro-batch | Growing value indicates slow processing |
| `schedulingDelay` | Time a batch waited before starting | Growing value indicates a backlog |

The table shows that `numFilesOutstanding` and `numBytesOutstanding` are the most direct indicators of Auto Loader backlog. If these values grow, the stream is not processing files as fast as they arrive. You can access these metrics programmatically through the `StreamingQuery` object. The following PySpark example shows how to read the latest progress and extract the Auto Loader metrics.

```python
# Start the Auto Loader stream and capture the StreamingQuery object.
# The query writes to a Unity Catalog table.
query = (df_auto
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/Volumes/sales/bronze/checkpoints/orders")
    .trigger(availableNow=True)
    .toTable("sales.bronze.orders"))

# Wait for the query to terminate.
query.awaitTermination()

# Get the last progress report.
# The lastProgress property returns a dictionary with the most recent metrics.
progress = query.lastProgress

# Extract the Auto Loader metrics from the progress report.
# The sources field contains information about each source.
# For Auto Loader, the metrics include numFilesOutstanding and numBytesOutstanding.
if progress and "sources" in progress:
    for source in progress["sources"]:
        # The metrics field contains the Auto Loader-specific metrics.
        metrics = source.get("metrics", {})
        # Print the number of files and bytes outstanding.
        print(f"Files outstanding: {metrics.get('numFilesOutstanding', 0)}")
        print(f"Bytes outstanding: {metrics.get('numBytesOutstanding', 0)}")
```

The example starts the stream, waits for it to finish, and then reads the last progress report. It extracts `numFilesOutstanding` and `numBytesOutstanding` from the source metrics. In a continuous stream, you would read these metrics periodically and log them to a monitoring table. A growing backlog is an early warning that the stream needs more resources or a lower processing rate.

## Controlling processing rate with maxFilesPerTrigger and maxBytesPerTrigger

For high-volume workloads, you can control the processing rate with `cloudFiles.maxFilesPerTrigger` and `cloudFiles.maxBytesPerTrigger`. These options limit the number of files or the number of bytes that Auto Loader processes in a single micro-batch. They prevent any single micro-batch from becoming too large, which can cause memory issues or long batch durations. They also help you manage the load on the cluster and the sink. The following table summarizes the options.

| Option | Meaning | Default |
|---|---|---|
| `cloudFiles.maxFilesPerTrigger` | Maximum number of files per micro-batch | 1000 |
| `cloudFiles.maxBytesPerTrigger` | Maximum number of bytes per micro-batch | No limit |

The table shows that `maxFilesPerTrigger` has a default of 1000, while `maxBytesPerTrigger` has no default limit. You can set either or both. If both are set, Auto Loader processes files until either limit is reached. The following PySpark example shows how to set both options.

```python
# Configure Auto Loader with rate limits.
# The cloudFiles.maxFilesPerTrigger option limits the number of files
# processed in a single micro-batch to 1000.
# The cloudFiles.maxBytesPerTrigger option limits the number of bytes
# processed in a single micro-batch to 1 gigabyte.
# These limits prevent any single micro-batch from becoming too large.
df_rate_limited = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "parquet")
    .option("cloudFiles.schemaLocation", "/Volumes/sales/bronze/schemas/orders")
    .option("cloudFiles.maxFilesPerTrigger", "1000")
    .option("cloudFiles.maxBytesPerTrigger", "1g")
    .load("/Volumes/sales/bronze/raw/orders/"))
```

The example reads Parquet files with a maximum of 1000 files and 1 GB per micro-batch. If the source has many small files, the file limit is reached first. If the source has fewer, larger files, the byte limit is reached first. Setting these limits helps keep micro-batches predictable and prevents out-of-memory errors. You can adjust the limits based on the cluster size and the file sizes. For a small cluster, use lower limits. For a large cluster, use higher limits.

## Protecting the checkpoint location

The checkpoint location stores critical state information for the Auto Loader stream. It records which files have been discovered and which have been processed. It also stores the state of any stateful operations, such as aggregations. If the checkpoint files are deleted or corrupted, the stream loses its state and must restart from scratch. This can cause reprocessing of all files, which is expensive and may create duplicates. To protect the checkpoint location, avoid applying cloud storage lifecycle policies that delete files after a short period. If you must use a lifecycle policy, set the retention period long enough to cover the maximum expected downtime of the stream. Also, ensure that the checkpoint location is in durable storage, such as cloud storage or a Unity Catalog volume, and that it is not in a temporary or local path.

The following table summarizes checkpoint protection practices.

| Practice | Reason |
|---|---|
| Use durable storage | Local paths are lost when the cluster stops |
| Avoid aggressive lifecycle policies | Deleting checkpoint files corrupts stream state |
| Set retention longer than maximum downtime | Allows the stream to resume after long outages |
| Use a separate checkpoint location per stream | Prevents conflicts between streams |
| Monitor checkpoint size | Large checkpoints can slow down the stream |

The table shows that checkpoint protection is about durability, retention, isolation, and monitoring. A corrupted checkpoint requires a full restart, which is costly. Treat the checkpoint location as critical infrastructure.

## Accessing file-level metadata with the _metadata column

Auto Loader provides a hidden column called `_metadata` that contains information about each source file. You can select this column to access file-level metadata in your ingested data. The `_metadata` column includes fields such as `file_path`, `file_name`, `file_size`, and `file_modification_time`. This is useful for auditing, for debugging, and for building pipelines that need to know which file a row came from. The following PySpark example shows how to select the `_metadata` fields.

```python
# Read from Auto Loader and select the _metadata fields.
# The _metadata column is a hidden column that contains file-level metadata.
# The file_path field shows the full path of the source file.
# The file_name field shows the name of the source file.
# The file_size field shows the size of the file in bytes.
# The file_modification_time field shows when the file was last modified.
df_with_metadata = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "parquet")
    .option("cloudFiles.schemaLocation", "/Volumes/sales/bronze/schemas/orders")
    .load("/Volumes/sales/bronze/raw/orders/")
    .select(
        "*",
        "_metadata.file_path",
        "_metadata.file_name",
        "_metadata.file_size",
        "_metadata.file_modification_time"
    ))
```

The example selects all columns from the data and adds four metadata columns. The metadata columns are prefixed with `_metadata.`. You can use these columns to filter, group, or audit the data. For example, you can find all rows that came from a specific file, or you can check the modification time to see when the data was written.

You can also access the `_metadata` column in SQL. The following SQL example uses `read_files` and selects the metadata fields.

```sql
-- Read files and select the _metadata fields.
-- The _metadata column is available in the read_files function.
-- The file_path field shows the full path of the source file.
SELECT
  *,
  _metadata.file_path AS source_file,
  _metadata.file_modification_time AS source_mod_time
FROM read_files(
  '/Volumes/sales/bronze/raw/orders/',
  format => 'parquet'
);
```

The SQL example reads Parquet files and selects the file path and modification time. The `_metadata` column is available in `read_files` and in streaming tables in Lakeflow Spark Declarative Pipelines. Use it to add file-level context to your data.

## Optimizing Auto Loader for high-volume workloads

High-volume workloads require optimization beyond the default configuration. The most important optimization is to use file notification mode with file events. File notification mode uses cloud notification services to receive events when new files arrive. It avoids repeated directory listings, which are slow and expensive for large directories. File events are enabled on the external location in Unity Catalog. When file events are enabled, Auto Loader receives notifications directly, which reduces latency and cloud API costs. File notification mode is supported on compute with dedicated access mode.

The following table summarizes optimization techniques for high-volume workloads.

| Technique | Benefit | Requirement |
|---|---|---|
| File notification mode with file events | Avoids directory listing, scales to millions of files | Dedicated access mode, file events enabled |
| `cloudFiles.maxFilesPerTrigger` | Controls micro-batch size | None |
| `cloudFiles.maxBytesPerTrigger` | Controls micro-batch size | None |
| File notification with queue | Scales to high file arrival rates | Notification and queue setup |
| Separate schema and checkpoint locations | Allows reset without losing schema | None |
| `availableNow` trigger for scheduled jobs | Reduces compute cost | None |
| `processingTime` trigger for continuous jobs | Controls processing interval | None |

The table shows that file notification mode is the most impactful optimization for high-volume workloads. It avoids the overhead of listing directories and scales to millions of files per hour. The rate-limiting options help keep micro-batches predictable. The trigger choice depends on the latency requirement. Use `availableNow` for scheduled jobs and `processingTime` for continuous jobs with controlled intervals.

## Integration with Lakeflow Spark Declarative Pipelines

Auto Loader integrates with Lakeflow Spark Declarative Pipelines. You can define streaming tables that read from files using `read_files` with the `STREAM` keyword. The pipeline manages checkpointing and schema evolution automatically. You do not need to configure the checkpoint or schema location manually. The pipeline also provides an event log that records progress, data quality expectations, and errors. You can query the event log to monitor the pipeline. The following SQL example creates a streaming table from files using Auto Loader.

```sql
-- Create a streaming table from files using read_files.
-- The STREAM keyword enables Auto Loader for incremental processing.
-- The pipeline manages checkpointing and schema evolution automatically.
CREATE OR REFRESH STREAMING TABLE sales.bronze.orders
AS SELECT * FROM STREAM read_files(
  '/Volumes/sales/bronze/raw/orders/',
  format => 'json'
);
```

The example creates a streaming table named `sales.bronze.orders`. The pipeline uses Auto Loader to process new files incrementally. The checkpoint and schema locations are managed by the pipeline. You can monitor the pipeline through the event log. The following SQL example queries the event log for recent progress.

```sql
-- Query the pipeline event log for recent progress.
-- The event_log function returns events for the specified table.
-- The events include progress updates, expectation results, and errors.
SELECT
  timestamp,
  event_type,
  message,
  details
FROM event_log(TABLE(sales.bronze.orders))
-- Filter to events from the last hour.
WHERE timestamp >= current_timestamp() - INTERVAL 1 HOUR
-- Order by timestamp, most recent first.
ORDER BY timestamp DESC;
```

The example queries the event log for the `orders` streaming table. The event log records progress updates, data quality expectation results, and errors. You can use this to monitor the pipeline and to set up alerts.

## Best practices

Use file notification mode with file events for high-volume workloads. It avoids directory listing overhead and scales to millions of files. Enable file events on the external location and use dedicated access mode.

Monitor `numFilesOutstanding` and `numBytesOutstanding` regularly. A growing backlog indicates that the stream cannot keep up with the arrival rate. Adjust the cluster size or the processing rate limits.

Set `cloudFiles.maxFilesPerTrigger` and `cloudFiles.maxBytesPerTrigger` to prevent oversized micro-batches. Choose limits that match the cluster size and the file sizes.

Protect the checkpoint location. Use durable storage, avoid aggressive lifecycle policies, and set retention longer than the maximum expected downtime. Use a separate checkpoint location per stream.

Store the schema location in a durable, governed location. Keep it separate from the checkpoint location so that you can reset the stream without losing the inferred schema.

Use the `_metadata` column to add file-level context to your data. It is useful for auditing and debugging.

Use schema hints and choose the right schema evolution mode. Monitor the rescued data column to detect schema drift and data quality issues.

Set the session time zone explicitly to UTC. This avoids off-by-hours errors when parsing timestamps.

## Common mistakes and pitfalls

The most common mistake is applying a lifecycle policy to the checkpoint location that deletes files after a short period. This corrupts the stream state and requires a full restart. Set retention longer than the maximum expected downtime.

A second mistake is using directory listing mode for large directories. Directory listing scans the entire directory on each trigger, which becomes slow and expensive. Use file notification mode with file events.

A third mistake is not monitoring `numFilesOutstanding` and `numBytesOutstanding`. A growing backlog can cause the stream to fall far behind and eventually fail. Monitor these metrics and respond to growth.

A fourth mistake is setting `maxFilesPerTrigger` or `maxBytesPerTrigger` too high. Large micro-batches can cause out-of-memory errors or long batch durations. Set limits that match the cluster size.

A fifth mistake is setting the limits too low. Very small micro-batches increase overhead and reduce throughput. Balance the limits with the cluster resources.

A sixth mistake is sharing a checkpoint location between streams. Each stream must have its own checkpoint location. Sharing causes conflicts and data errors.

A seventh mistake is ignoring the rescued data column. The rescued data column captures nonconforming data. If you do not monitor it, you may miss data quality issues.

An eighth mistake is not setting the session time zone. Timestamps are stored in UTC. If you compare them to local time without converting, you may get incorrect results.

## Testing Auto Loader monitoring and optimization

Testing Auto Loader monitoring involves verifying that the stream discovers files, processes them, and reports the expected metrics. You can test with a small directory of files and the `availableNow` trigger. The following PySpark example tests the `cloud_files_state` function and the `_metadata` column.

```python
from pyspark.sql import Row

df_test.write.mode("overwrite").json("/tmp/auto_loader_monitor_test/")

df_auto = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", "/tmp/auto_loader_monitor_schema")
    .load("/tmp/auto_loader_monitor_test/"))

# Write the stream with availableNow.
query = (df_auto
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/tmp/auto_loader_monitor_checkpoint")
    .trigger(availableNow=True)
    .toTable("tmp.auto_loader_monitor_target"))

# Wait for the query to terminate.

# Query the cloud_files_state function to verify the file was processed.
```

## Performance considerations

Auto Loader performance depends on the file detection mode, the file format, the file size, the processing rate limits, and the cluster resources. File notification mode with file events is the most performant and scalable mode. Directory listing mode is limited by the size of the directory. Parquet and Avro files are faster to read than CSV and JSON because they are columnar and self-describing.

The number of files affects performance. Many small files are inefficient because each file has metadata overhead. Aim for files of 100 MB to 1 GB. If your source produces many small files, consider compacting them before ingestion or running `OPTIMIZE` after ingestion to compact the target table.

The processing rate limits affect performance. `maxFilesPerTrigger` and `maxBytesPerTrigger` control the micro-batch size. Larger micro-batches increase throughput but use more memory. Smaller micro-batches reduce memory usage but increase overhead. Choose limits that match the cluster size and the file sizes.

The checkpoint location affects performance. The checkpoint is written on each micro-batch. Use a reliable storage location with low latency. Avoid locations that are slow or have high contention. Monitor the checkpoint size and clean up old checkpoints if necessary.

The trigger affects performance and cost. Use `availableNow` for scheduled jobs to process all available data and stop. Use `processingTime` for continuous jobs with controlled intervals. Use the default trigger for the lowest latency.

## An end-to-end example

Consider a scenario where you ingest Parquet order files from cloud storage into a bronze table. The stream uses file notification mode with file events, rate limits to control micro-batch size, and monitoring to track progress. The following PySpark example shows the complete configuration.

```python
from pyspark.sql.functions import col

# Configure Auto Loader with file events and rate limits.
df_auto = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "parquet")
    .option("cloudFiles.schemaLocation", "/Volumes/sales/bronze/schemas/orders")
    .option("cloudFiles.useManagedFileEvents", "true")
    .option("cloudFiles.maxFilesPerTrigger", "1000")
    .option("cloudFiles.maxBytesPerTrigger", "1g")
    .load("/Volumes/sales/bronze/raw/orders/"))

# Write the stream to a bronze table.
query = (df_auto
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/Volumes/sales/bronze/checkpoints/orders")
    .option("mergeSchema", "true")
    .trigger(availableNow=True)
    .toTable("sales.bronze.orders"))

# Wait for the query to terminate.
query.awaitTermination()

# Query the cloud_files_state function to check the file backlog.
df_backlog = spark.sql("""
    SELECT
      status,
      COUNT(*) AS file_count,
      SUM(size) AS total_bytes
    FROM cloud_files_state('/Volumes/sales/bronze/checkpoints/orders')
    GROUP BY status
""")
display(df_backlog)

# Read the bronze table and select the _metadata column.
df_bronze = spark.read.table("sales.bronze.orders")
df_bronze.select("order_id", "amount", "_metadata.file_path").display()
```

The example reads Parquet files with file events and rate limits, writes to a bronze table, checks the file backlog, and selects file-level metadata. This configuration is optimized for high-volume workloads and provides monitoring information.
