## Understand how Auto Loader works

Auto Loader is a Structured Streaming source in Azure Databricks that incrementally and efficiently processes new data files as they arrive in cloud storage. Instead of scanning an entire directory on every run, Auto Loader maintains state about which files it has already processed and discovers only new files. It is implemented as a source called `cloudFiles` that you use with `spark.readStream`. You provide the input directory path, configure the file format and schema options, and Auto Loader handles file discovery, schema inference, and incremental processing. The result is a streaming DataFrame that you write to a Delta table in Unity Catalog. Auto Loader scales to process billions of files for migration or backfill and supports near real-time ingestion of millions of files per hour.

Auto Loader matters because file-based ingestion is one of the most common patterns in the lakehouse. Raw data lands in cloud storage as CSV, JSON, Parquet, or other files. A pipeline must detect new files, parse them, and load them into a table without duplicating or missing data. Manual approaches such as listing directories and tracking processed files in a separate table are error-prone and do not scale. Auto Loader solves these problems with a checkpoint-based mechanism that provides exactly-once processing guarantees. It integrates with Unity Catalog, so every file it ingests is governed by the same access controls, lineage, and auditing that apply to the rest of the lakehouse. In a medallion architecture, Auto Loader is the standard way to land raw files into the bronze layer.

These notes explain how Auto Loader works from first principles. They describe the unbounded table model, the two file detection modes (directory listing and file notification), schema inference and evolution, checkpointing and exactly-once semantics, triggers, and Unity Catalog integration. They show PySpark and SQL examples with full comments. They also cover null handling, case sensitivity, time zones, best practices, common mistakes, testing, performance, and an end-to-end example. The goal is that you can read these notes alone and understand how to configure and operate Auto Loader pipelines reliably and efficiently.

## The unbounded table model and Auto Loader

Structured Streaming treats incoming data as an unbounded table that grows continuously. When you read from a streaming source, you get a DataFrame that represents this table. New rows appear as data arrives. You apply the same transformations you use in batch processing, and you write the result to a sink. Auto Loader is a streaming source for files. It presents files as rows in an unbounded table. Each file that appears in the input directory becomes new rows in the table. Auto Loader discovers the files, reads them according to the format you specify, and produces a stream of rows.

The following example shows the basic pattern for reading files with Auto Loader.

```python
# Configure Auto Loader to read JSON files from cloud storage.
# The format "cloudFiles" is the Auto Loader source.
# The cloudFiles.format option specifies the file format (json).
# The cloudFiles.schemaLocation stores the inferred schema.
# The header option is not used for JSON, but it is shown here
# as a placeholder for format-specific options.
df_auto = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", "/Volumes/sales/bronze/schemas/orders")
    .load("/Volumes/sales/bronze/raw/orders/"))

# Display the schema of the streaming DataFrame.
# Auto Loader infers the schema from a sample of the files.
df_auto.printSchema()
```

The example configures Auto Loader to read JSON files from a Unity Catalog volume path. The `cloudFiles.format` option specifies the file format. The `cloudFiles.schemaLocation` option tells Auto Loader where to store the inferred schema. The `load` method specifies the input directory. Auto Loader processes new files as they arrive and produces a streaming DataFrame. The schema is inferred from a sample of the files, and the inferred schema is stored in the schema location so that it can be reused and evolved over time.

## File detection modes: directory listing and file notification

Auto Loader supports two modes for detecting new files: directory listing and file notification. In directory listing mode, Auto Loader periodically lists the input directory to discover new files. This mode requires no additional configuration beyond access to the data on cloud storage. It is simple to set up and works with any cloud storage that Spark can access. In file notification mode, Auto Loader uses cloud notification services to receive events when new files arrive. This mode is more efficient for large-scale workloads because it avoids repeated directory listings. Databricks recommends file notification mode with file events enabled for most workloads.

The following table compares the two modes.

| Aspect | Directory listing | File notification |
|---|---|---|
| Mechanism | Lists the input directory | Subscribes to cloud notifications |
| Setup | No additional permissions | Requires notification and queue setup |
| Scalability | Limited by directory size | Scales to millions of files per hour |
| Cost | Higher LIST API costs | Lower cloud API costs |
| Latency | Depends on listing interval | Near real-time |
| Recommended for | Small directories, backfills | Most production workloads |

The table shows that file notification mode is more scalable and cost-effective for production workloads. Directory listing is simpler to set up and is suitable for small directories or one-time backfills.

### Directory listing mode

Directory listing mode is the default. Auto Loader identifies new files by listing the input directory. In Databricks Runtime 9.1 and above, Auto Loader can automatically detect whether files are arriving with lexical ordering and reduce the number of API calls needed to detect new files. The following example shows a stream configured for directory listing mode.

```python
# Configure Auto Loader in directory listing mode.
# Directory listing mode is the default, so no additional option is needed.
df_directory = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "csv")
    .option("cloudFiles.schemaLocation", "/Volumes/sales/bronze/schemas/sales")
    .option("header", "true")
    .load("/Volumes/sales/bronze/raw/sales/"))
```

The example reads CSV files using directory listing. Auto Loader lists the input directory on each trigger, discovers new files, and processes them. The schema location stores the inferred schema. Directory listing mode is suitable for small directories where the number of files is limited and the listing cost is acceptable.

### File notification mode

File notification mode leverages cloud notification and queue services. Auto Loader can automatically set up a notification service and queue service that subscribe to file events from the input directory. If you enable file events on the external location, you do not need to provide additional permissions when you set up the stream. File notification mode with file events is more performant and scalable than directory listing. Databricks recommends migrating from directory listing to file notification with file events for significant performance improvements.

The following example shows a stream configured for file notification mode with file events.

```python
# Configure Auto Loader in file notification mode with file events.
# The cloudFiles.useManagedFileEvents option tells Auto Loader to use
# the file events configured on the external location.
# This requires that file events are enabled on the external location
# and that the compute has dedicated access mode.
df_notification = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "parquet")
    .option("cloudFiles.schemaLocation", "/Volumes/sales/bronze/schemas/events")
    .option("cloudFiles.useManagedFileEvents", "true")
    .load("/Volumes/sales/bronze/raw/events/"))
```

The example uses `cloudFiles.useManagedFileEvents` set to `true`. This tells Auto Loader to use the file events that are configured on the external location. The external location must have file events enabled. The compute must use dedicated access mode. When file events are enabled, Auto Loader receives notifications directly when files arrive, which reduces latency and cloud API costs.

## Schema inference and evolution

Auto Loader can automatically detect the schema of the data it loads and evolve the schema as new columns are introduced. This eliminates the need to manually track and apply schema changes. Auto Loader stores the schema in the `cloudFiles.schemaLocation` directory. When it first reads data, it samples the first 50 GB or 1000 files that it discovers, whichever limit is crossed first, to infer the schema. For formats that do not encode data types, such as JSON, CSV, and XML, Auto Loader infers all columns as strings. For formats with typed schemas, such as Parquet and Avro, Auto Loader samples a subset of files and merges their schemas.

Auto Loader supports several schema evolution modes, which you set with `cloudFiles.schemaEvolutionMode`. The following table summarizes the modes.

| Mode | Behavior | Use case |
|---|---|---|
| `addNewColumns` | Adds new columns to the schema | Default; schema evolves as new columns appear |
| `rescue` | Does not evolve the schema; new columns are rescued | When you want to handle schema changes manually |
| `failOnNewColumns` | Fails the stream when a new column appears | When schema changes require manual intervention |
| `none` | Does not evolve the schema; new columns are ignored | When the schema is fixed |

The `rescue` mode uses a rescued data column, typically named `_rescued_data`, to store values that do not match the schema. This prevents data loss when the source schema changes or when values have unexpected types. The following example shows how to configure schema evolution.

```python
# Configure Auto Loader with schema evolution.
# The cloudFiles.schemaEvolutionMode option controls how the schema evolves.
# The addNewColumns mode adds new columns to the schema automatically.
# The rescuedDataColumn option specifies a column to store rescued data.
df_evolving = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", "/Volumes/sales/bronze/schemas/orders")
    .option("cloudFiles.schemaEvolutionMode", "addNewColumns")
    .option("rescuedDataColumn", "_rescued_data")
    .load("/Volumes/sales/bronze/raw/orders/"))
```

The example configures Auto Loader to add new columns automatically and to rescue data that does not match the schema. The rescued data column stores the original values, which you can inspect later using semi-structured data access APIs.

## Checkpoints and exactly-once processing

Auto Loader stores the metadata of discovered files in a scalable key-value store in the checkpoint location. This key-value store ensures that data is processed exactly once. In case of failures, Auto Loader resumes from where it left off by using the information stored in the checkpoint location. It continues to provide exactly-once guarantees when writing data into Delta Lake. You do not need to maintain or manage any state yourself to achieve fault tolerance or exactly-once semantics.

The following example shows a streaming write with a checkpoint location.

```python
# Write the Auto Loader stream to a Unity Catalog table.
# The checkpointLocation option stores the progress of the stream.
# The schemaLocation stores the inferred schema.
# The trigger availableNow processes all available data and stops.
(df_auto
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/Volumes/sales/bronze/checkpoints/orders")
    .option("mergeSchema", "true")
    .trigger(availableNow=True)
    .toTable("sales.bronze.orders"))
```

The example writes the stream to `sales.bronze.orders`. The `checkpointLocation` stores the progress of the stream. The `mergeSchema` option allows the table schema to evolve as new columns appear. The `trigger(availableNow=True)` processes all available data and stops, which is useful for scheduled jobs.

## Triggers and scheduling

Auto Loader uses Structured Streaming triggers to control when data is processed. The `availableNow` trigger processes all available data and then stops. It is the recommended trigger for scheduled incremental batch processing. Databricks recommends using `Trigger.AvailableNow` for all incremental batch processing workloads. For continuous ingestion, you can use the default trigger or a `processingTime` trigger. For low-latency ingestion with file events, you can use a file arrival trigger, which starts the pipeline when new files arrive.

The following table summarizes the trigger options for Auto Loader.

| Trigger | Behavior | Recommended for |
|---|---|---|
| `availableNow=True` | Processes all available data and stops | Scheduled batch jobs |
| Default | Processes continuously as data arrives | Continuous ingestion |
| `processingTime` | Processes at fixed intervals | Controlled resource usage |
| File arrival | Starts when new files arrive | Low-latency ingestion with file events |

The `availableNow` trigger is the most cost-effective for scheduled jobs because the cluster can be shut down between runs. The file arrival trigger is the most cost-effective for low-latency ingestion because compute runs only when new files arrive.

## Unity Catalog integration

Auto Loader can securely ingest data from external locations configured with Unity Catalog. Databricks recommends storing checkpoint and schema evolution information in storage locations managed by Unity Catalog. File notification mode is only supported on compute with dedicated access mode. When you use Auto Loader with Unity Catalog, you need `READ FILES` permission on the external location and `WRITE FILES` and `CREATE TABLE` permission on the target location.

The following example shows how to use Auto Loader with Unity Catalog to load into a managed table.

```python
# Define the checkpoint path in a Unity Catalog volume.
checkpoint_path = "/Volumes/sales/bronze/checkpoints/orders"

# Configure Auto Loader to read from a Unity Catalog external location.
df_unity = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", checkpoint_path)
    .option("cloudFiles.useManagedFileEvents", "true")
    .load("abfss://sales-source@storageaccount.dfs.core.windows.net/orders/"))

# Write to a Unity Catalog managed table.
(df_unity
    .writeStream
    .option("checkpointLocation", checkpoint_path)
    .trigger(availableNow=True)
    .toTable("sales.bronze.orders"))
```

The example reads from an Azure Data Lake Storage location and writes to a Unity Catalog managed table. The checkpoint and schema locations are stored in a Unity Catalog volume. File events are enabled on the external location, so Auto Loader uses file notification mode with file events.

## Null handling, case sensitivity, and time zones

Null handling in Auto Loader follows the same rules as other streaming sources. Nulls in the source files are preserved unless you filter or replace them. If a target column is non-nullable, a null value causes the write to fail. You should handle nulls in the transformation step. For example, you can filter out rows with null keys or replace null values with a default using `coalesce`. The rescued data column captures values that do not match the schema, which can include nulls or type mismatches.

Case sensitivity affects string comparisons and column names. In Spark SQL, column names are case-insensitive by default. String values are case-sensitive. If the source data has inconsistent casing, normalize it with `upper` or `lower`, or use a case-insensitive collation if the table is configured for one. The schema location stores the column names as inferred. If the source files have columns with different casing, Auto Loader may infer them as separate columns.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. When Auto Loader parses timestamps from files, it interprets them in the session time zone unless the file includes an explicit offset. To avoid off-by-hours errors, set the session time zone explicitly to UTC at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Store timestamps in UTC and convert to local time only for display.

## Best practices

Use file notification mode with file events for most production workloads. It is more scalable and cost-effective than directory listing mode. Enable file events on the external location and set `cloudFiles.useManagedFileEvents` to `true` in the stream configuration.

Use a separate schema location for each Auto Loader stream. The schema location stores the inferred schema and tracks schema changes. Sharing a schema location between streams can cause conflicts.

Use a unique checkpoint location for each stream. The checkpoint stores the progress of the stream. Sharing a checkpoint between streams causes data processing errors.

Use the `availableNow` trigger for scheduled jobs. It processes all available data and stops, which reduces compute cost. Use a file arrival trigger for low-latency ingestion with file events.

Handle schema evolution deliberately. Use `addNewColumns` mode to add new columns automatically. Use `rescuedDataColumn` to capture data that does not match the schema. Use `failOnNewColumns` when schema changes require manual intervention.

Monitor the stream. Track metrics such as input rate, processed rate, and batch duration. Use the Auto Loader observability features to monitor progress and detect issues.

## Common mistakes and pitfalls

The most common mistake is using directory listing mode for large directories. Directory listing scans the entire directory on each trigger, which becomes slow and expensive as the directory grows. Use file notification mode with file events instead.

A second mistake is not configuring a schema location. Without a schema location, Auto Loader cannot infer or evolve the schema. The stream fails or produces unexpected results.

A third mistake is sharing a checkpoint location between streams. Each stream must have its own checkpoint location. Sharing causes conflicts and data errors.

A fourth mistake is using file notification mode on compute without dedicated access mode. File notification mode is only supported on compute with dedicated access mode.

A fifth mistake is not handling out-of-order files. Auto Loader does not guarantee the order in which files are discovered or processed. Design your pipelines to handle out-of-order arrivals.

A sixth mistake is ignoring the rescued data column. When schema evolution is enabled, values that do not match the schema are rescued. If you do not inspect the rescued data, you may miss data quality issues.

## Testing Auto Loader logic

Testing Auto Loader logic involves verifying that the stream discovers new files, infers the schema, and writes the expected rows to the target table. You can test with a small directory of files and the `availableNow` trigger. The following example shows a test for Auto Loader.

```python
from pyspark.sql import Row

# Create a test directory with a small CSV file.
test_data = [Row(id=1, name="Alice", amount=100.0)]
df_test = spark.createDataFrame(test_data)
df_test.write.mode("overwrite").option("header", "true").csv("/tmp/auto_loader_test/")

# Configure Auto Loader to read the test directory.
df_auto = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "csv")
    .option("cloudFiles.schemaLocation", "/tmp/auto_loader_schema")
    .option("header", "true")
    .load("/tmp/auto_loader_test/"))

# Write the stream with availableNow.
query = (df_auto
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/tmp/auto_loader_checkpoint")
    .trigger(availableNow=True)
    .toTable("tmp.auto_loader_target"))

# Wait for the query to terminate.
query.awaitTermination()

# Verify the result.
assert spark.read.table("tmp.auto_loader_target").count() == 1
```

The test creates a small CSV file, configures Auto Loader to read it, writes to a target table, and verifies the row count. Run tests like this in your CI pipeline against a small local Spark session. Clean up temporary files and tables after the test.

## Performance considerations

Auto Loader performance depends on the file detection mode, the file format, and the size of the files. File notification mode with file events is the most performant and scalable mode. Directory listing mode is limited by the size of the directory. Parquet and Avro files are faster to read than CSV and JSON because they are columnar and self-describing.

The number of files affects performance. Many small files are inefficient because each file has metadata overhead. Aim for files of 100 MB to 1 GB. If your source produces many small files, consider compacting them before ingestion or running `OPTIMIZE` after ingestion to compact the target table.

Use a separate volume for each subpath when using file events. This scopes file discovery to only the relevant objects and avoids unnecessary file discovery overhead.

Use the `availableNow` trigger for scheduled jobs to process all available data and stop. This reduces compute cost compared to a continuously running cluster.

## An end-to-end example

Consider a scenario where you ingest JSON order files from cloud storage into a bronze table, and then aggregate them into a silver table. The pipeline uses Auto Loader with file notification mode and file events. The following example shows the complete setup.

```python
from pyspark.sql.functions import col, sum, count

# Configure Auto Loader to read JSON files with file events.
df_auto = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaLocation", "/Volumes/sales/bronze/schemas/orders")
    .option("cloudFiles.useManagedFileEvents", "true")
    .option("rescuedDataColumn", "_rescued_data")
    .load("/Volumes/sales/bronze/raw/orders/"))

# Write raw orders to a bronze table.
(df_auto
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/Volumes/sales/bronze/checkpoints/orders")
    .option("mergeSchema", "true")
    .trigger(availableNow=True)
    .toTable("sales.bronze.orders"))

# Read the bronze table and aggregate into a silver table.
df_bronze = spark.read.table("sales.bronze.orders")
df_silver = (df_bronze
    .filter(col("amount").isNotNull())
    .groupBy("customer_id")
    .agg(
        sum("amount").alias("total_amount"),
        count("*").alias("order_count")
    ))

# Write the silver table.
df_silver.write.mode("overwrite").saveAsTable("sales.silver.customer_totals")
```

The example reads JSON files with Auto Loader, writes to a bronze table, aggregates the data, and writes to a silver table. The bronze table uses `mergeSchema` to evolve the schema as new columns appear. The silver table is rebuilt from the bronze table. The pipeline uses file notification mode with file events for scalability and cost efficiency.

## Summary

Auto Loader is a Structured Streaming source for incrementally processing new files in cloud storage. It maintains state about processed files in a checkpoint location, providing exactly-once processing guarantees. It supports two file detection modes: directory listing and file notification. File notification mode with file events is recommended for most production workloads because it is more scalable and cost-effective. Auto Loader infers the schema from a sample of files and stores it in a schema location. It supports schema evolution modes such as `addNewColumns`, `rescue`, `failOnNewColumns`, and `none`. The rescued data column captures values that do not match the schema.

Auto Loader integrates with Unity Catalog, so ingested data is governed by Unity Catalog access controls and lineage. Checkpoints and schema locations should be stored in Unity Catalog volumes. File notification mode is supported on compute with dedicated access mode. Auto Loader supports the `availableNow` trigger for scheduled batch processing and file arrival triggers for low-latency ingestion.

Null handling, case sensitivity, and time zones affect the data but not the Auto Loader mechanism. Set the session time zone explicitly to UTC. Best practices include using file notification mode with file events, separate schema and checkpoint locations, and the `availableNow` trigger for scheduled jobs. Common mistakes include using directory listing for large directories, not configuring a schema location, sharing checkpoints, and ignoring out-of-order files. Test Auto Loader with small files and the `availableNow` trigger. Performance depends on the file detection mode, file format, and file size. By understanding Auto Loader, you can build reliable, scalable file ingestion pipelines that land data in Unity Catalog efficiently and correctly.
