## Handle schema inference and evolution

Schema inference is the process of examining source data and automatically determining the column names and data types that describe it. Schema evolution is the process of updating that schema when the source data changes, such as when a new column appears or a column's data type changes. In Azure Databricks, Auto Loader provides both capabilities for file-based ingestion. When you configure an Auto Loader stream with the `cloudFiles` format, you can let Auto Loader sample the incoming files, infer a schema, store that schema in a schema location, and evolve it over time as new data arrives. This removes the need to define and maintain schemas manually for every source, which is especially valuable when files come from many producers and their structure changes without notice.

Schema inference and evolution matter because file schemas are rarely static. A CSV export from an operational system might add a column when the system is upgraded. A JSON event stream might introduce a new field when a new application version is deployed. A Parquet dataset might change a column from `INT` to `LONG` when the volume of data grows. If your pipeline cannot handle these changes, it either fails, drops the new data, or writes incorrect types. Auto Loader provides options to control exactly how schema changes are handled. It can add new columns, widen types, rescue nonconforming data, fail the stream, or ignore the change. The choice depends on your governance requirements and the tolerance for data loss.

These notes cover schema inference and evolution in Auto Loader from first principles. They explain how inference works, how to enable type inference for JSON and CSV, how the schema location stores the inferred schema, and how the schema evolution modes determine the behavior when new columns or types appear. They explain the rescued data column, schema hints, and type widening. They show PySpark and SQL examples with full comments. They also cover null handling, case sensitivity, time zones, schema enforcement, expectations, best practices, common mistakes, testing, performance, and an end-to-end example. The goal is that you can read these notes alone and understand how to configure Auto Loader so that schema changes are handled deliberately and safely.

## How schema inference works in Auto Loader

Auto Loader infers the schema of source files by sampling a subset of the data. It does not read every file before starting. By default, it samples the first 50 GB or 1000 files that it discovers, whichever limit is crossed first. For formats that do not carry type information, such as JSON, CSV, and XML, Auto Loader infers all columns as strings unless you enable type inference. This conservative default prevents type mismatches that could cause data loss. For formats that carry type information, such as Parquet and Avro, Auto Loader samples a subset of files and merges their schemas. The inferred schema is stored in the `cloudFiles.schemaLocation` directory. Auto Loader uses this stored schema on subsequent runs and updates it when schema evolution is enabled.

The following table summarizes the default inference behavior by format.

| Format | Default inferred types | Type inference option |
|---|---|---|
| JSON | All columns as strings | `cloudFiles.inferColumnTypes` |
| CSV | All columns as strings | `cloudFiles.inferColumnTypes` |
| XML | All columns as strings | `cloudFiles.inferColumnTypes` |
| Parquet | Types from file metadata | Not applicable |
| Avro | Types from file metadata | Not applicable |
| ORC | Types from file metadata | Not applicable |

The table shows that JSON, CSV, and XML require an explicit option to infer types. Parquet, Avro, and ORC carry their own type information, so Auto Loader reads it from the file metadata. For JSON and CSV, inferring all columns as strings is safe because it never fails on a type mismatch. You can cast columns later in the pipeline or enable type inference to have Auto Loader infer the types during the initial sample.

The following PySpark example shows how to enable type inference for JSON files.

```python
# Configure Auto Loader to read JSON files with type inference.
# The cloudFiles.format option specifies the file format (json).
# The cloudFiles.inferColumnTypes option tells Auto Loader to infer
# column types from the data instead of treating all columns as strings.
# The cloudFiles.schemaLocation stores the inferred schema.
df_json = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.inferColumnTypes", "true")
    .option("cloudFiles.schemaLocation", "/Volumes/sales/bronze/schemas/orders")
    .load("/Volumes/sales/bronze/raw/orders/"))

# Display the inferred schema.
# The schema shows the column names and data types.
df_json.printSchema()
```

The example reads JSON files and enables type inference. Auto Loader samples the files and infers types such as `INT`, `DOUBLE`, `STRING`, and `TIMESTAMP`. The inferred schema is stored in the schema location. On subsequent runs, Auto Loader uses the stored schema. If new columns appear and schema evolution is enabled, Auto Loader updates the schema. If type inference is not enabled, all columns are strings, and you must cast them in the pipeline.

The equivalent SQL approach uses the `read_files` table-valued function. The following SQL example reads JSON files with a schema hint to guide inference.

```sql
-- Read JSON files using the read_files table-valued function.
-- The format option specifies that the files are JSON.
-- The schemaHints option provides type hints for specific columns.
-- The hints guide Auto Loader when inferring the schema.
SELECT *
FROM read_files(
  '/Volumes/sales/bronze/raw/orders/',
  format => 'json',
  schemaHints => 'order_id INT, order_date DATE, amount DECIMAL(10,2)'
);
```

The example reads JSON files and provides schema hints for `order_id`, `order_date`, and `amount`. The hints tell Auto Loader the expected types for these columns, overriding the default string inference. Schema hints are useful when you know the correct types and want to avoid inference errors. They do not replace schema evolution; they guide the initial inference.

## Schema evolution modes

When Auto Loader detects a new column or a type change, the `cloudFiles.schemaEvolutionMode` option determines what happens. The mode controls whether the stream fails, evolves the schema, rescues the data, or ignores the change. The following table summarizes the modes.

| Mode | Behavior |
|---|---|
| `addNewColumns` | Stream fails. New columns are added to the schema. On restart, stream continues with the updated schema. This is the default when no schema is provided. |
| `addNewColumnsWithTypeWidening` | Stream fails. New columns are added to the schema and supported data type changes (such as `INT` to `LONG`) are widened automatically. Unsupported type changes are captured in `_rescued_data`. Requires Databricks Runtime 16.4+. |
| `rescue` | Schema is never evolved and stream does not fail. All new columns are captured in the `_rescued_data` column. |
| `failOnNewColumns` | Stream fails. Stream does not restart unless the provided schema is updated or the offending data file is removed. |
| `none` | Schema is not evolved, new columns are ignored, and data is not rescued unless the `rescuedDataColumn` option is set. This is the default when a schema is provided. |

The table shows that the modes range from fully automatic evolution to strict failure. `addNewColumns` is the default when no schema is provided. It fails the stream when a new column appears, adds the column to the stored schema, and then continues on restart. This behavior is intentional: it ensures that schema changes are visible and that the stream does not silently accept new columns without updating the schema location. `addNewColumnsWithTypeWidening` extends this by also widening supported types, such as `INT` to `LONG`. `rescue` never evolves the schema and never fails; it captures all nonconforming data in the rescued data column. `failOnNewColumns` fails and requires manual intervention. `none` ignores new columns and is the default when you provide a schema.

The following PySpark example shows how to configure the `rescue` mode.

```python
# Configure Auto Loader with the rescue schema evolution mode.
# The cloudFiles.schemaEvolutionMode option is set to "rescue".
# In rescue mode, the schema is never evolved and the stream does not fail.
# New columns and type mismatches are captured in the rescued data column.
# The rescuedDataColumn option specifies the name of the rescued data column.
df_rescue = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaEvolutionMode", "rescue")
    .option("cloudFiles.schemaLocation", "/Volumes/sales/bronze/schemas/orders")
    .option("rescuedDataColumn", "_rescued_data")
    .load("/Volumes/sales/bronze/raw/orders/"))

# Display the schema.
# The schema includes the expected columns and the rescued data column.
df_rescue.printSchema()
```

The example configures Auto Loader to rescue nonconforming data. When a new column appears, it is not added to the schema. Instead, the value is stored in the `_rescued_data` column. When a value cannot be cast to the expected type, it is also stored in the rescued data column. This prevents data loss and allows you to inspect the rescued data later. The stream does not fail, so it continues processing. This mode is useful when the source schema changes frequently and you want to handle changes manually in a downstream process.

## The rescued data column

The rescued data column captures any data that does not match the expected schema, including type mismatches and unexpected columns. Auto Loader automatically adds this column when inferring the schema. The default name is `_rescued_data`. You can rename it with the `rescuedDataColumn` option. The rescued data column is stored as a JSON string that contains the rescued values and the reason they were rescued. You can query the column to inspect the rescued data and decide how to handle it.

The following table summarizes what the rescued data column captures.

| Situation | What is rescued |
|---|---|
| New column not in schema | The value of the new column |
| Type mismatch | The original value that could not be cast |
| Missing required field | The entire record or the missing field |
| Malformed record | The raw record |

The table shows that the rescued data column is a safety net for data that does not conform to the schema. It prevents data loss when the source data changes or contains unexpected values. You should monitor the rescued data column to detect data quality issues. If the rescued data grows, it may indicate that the schema needs to be updated or that the source is producing malformed data.

The following PySpark example shows how to rename the rescued data column and query it.

```python
# Configure Auto Loader with a custom rescued data column name.
# The rescuedDataColumn option renames the column from the default
# "_rescued_data" to "my_rescued_data".
df_custom_rescue = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "csv")
    .option("cloudFiles.schemaEvolutionMode", "rescue")
    .option("cloudFiles.schemaLocation", "/Volumes/sales/bronze/schemas/sales")
    .option("rescuedDataColumn", "my_rescued_data")
    .load("/Volumes/sales/bronze/raw/sales/"))

# After writing to a table, query the rescued data column
# to inspect the rescued values.
# The column contains a JSON string with the rescued data.
df_written = spark.read.table("sales.bronze.sales")
df_rescued = df_written.filter(df_written.my_rescued_data.isNotNull())
display(df_rescued)
```

The example configures Auto Loader with a custom rescued data column name. After the stream writes to a table, you can query the rescued data column to inspect the rescued values. The column contains a JSON string. You can parse it with `from_json` or store it as a VARIANT column for further analysis. Monitoring the rescued data column helps you detect schema drift and data quality problems.

## Schema hints

Schema hints let you override the inferred types for specific columns. You use the `cloudFiles.schemaHints` option in PySpark or the `schemaHints` option in SQL. Schema hints are useful when Auto Loader infers a type that is not what you want. For example, JSON numbers may be inferred as `DOUBLE`, but you may want them as `INT` or `DECIMAL`. CSV columns may be inferred as `STRING`, but you may want them as `DATE` or `TIMESTAMP`. Schema hints guide the inference and the cast.

The following PySpark example shows how to use schema hints.

```python
# Configure Auto Loader with schema hints.
# The cloudFiles.schemaHints option provides type hints for specific columns.
# The hint "order_date DATE, amount DECIMAL(10,2)" tells Auto Loader
# to treat order_date as a DATE and amount as a DECIMAL(10,2).
df_hints = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "csv")
    .option("cloudFiles.schemaLocation", "/Volumes/sales/bronze/schemas/orders")
    .option("cloudFiles.schemaHints", "order_date DATE, amount DECIMAL(10,2)")
    .option("header", "true")
    .load("/Volumes/sales/bronze/raw/orders/"))
```

The example reads CSV files and provides schema hints for `order_date` and `amount`. Auto Loader uses the hints when inferring the schema. If the source data contains values that cannot be cast to the hinted types, the values are rescued if rescue mode is enabled, or the stream fails if rescue mode is not enabled. Schema hints are not a substitute for schema evolution; they only guide the initial inference.

The equivalent SQL example uses `schemaHints`.

```sql
-- Read CSV files with schema hints.
-- The schemaHints option provides type hints for specific columns.
SELECT *
FROM read_files(
  '/Volumes/sales/bronze/raw/orders/',
  format => 'csv',
  header => true,
  schemaHints => 'order_date DATE, amount DECIMAL(10,2)'
);
```

The SQL example reads CSV files with the same hints. The `schemaHints` option is supported by `read_files` and by streaming tables in Lakeflow Spark Declarative Pipelines. Use schema hints when you know the correct types and want to avoid inference errors.

## Type widening

`addNewColumnsWithTypeWidening` is a schema evolution mode that adds new columns and widens supported data types automatically. Type widening means changing a column's type to a broader type that can hold all existing values. For example, an `INT` column can be widened to `LONG` or `DECIMAL`. A `FLOAT` column can be widened to `DOUBLE`. Unsupported type changes are captured in the rescued data column. This mode requires Databricks Runtime 16.4 or above.

The following table summarizes supported type widening.

| Original type | Widened type |
|---|---|
| `INT` | `LONG`, `DECIMAL`, `DOUBLE` |
| `LONG` | `DECIMAL`, `DOUBLE` |
| `FLOAT` | `DOUBLE` |
| `DATE` | `TIMESTAMP` |

The table shows that type widening follows a safe progression from narrower to broader types. Widening is safe because every value of the original type can be represented in the widened type. Narrowing is not supported because it could lose data. If the source changes a column from `LONG` to `INT`, the change is not a widening, and it is captured in the rescued data column.

The following PySpark example shows how to configure type widening.

```python
# Configure Auto Loader with type widening.
# The cloudFiles.schemaEvolutionMode option is set to
# "addNewColumnsWithTypeWidening".
# New columns are added, and supported type changes are widened automatically.
# Unsupported type changes are captured in the rescued data column.
df_widening = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "parquet")
    .option("cloudFiles.schemaLocation", "/Volumes/sales/bronze/schemas/events")
    .option("cloudFiles.schemaEvolutionMode", "addNewColumnsWithTypeWidening")
    .option("rescuedDataColumn", "_rescued_data")
    .load("/Volumes/sales/bronze/raw/events/"))
```

The example reads Parquet files and enables type widening. If a column changes from `INT` to `LONG`, Auto Loader widens the type in the schema. If a column changes from `LONG` to `INT`, the change is not a widening, and the value is rescued. Type widening reduces the need for manual schema updates when types grow over time.

## Null handling, case sensitivity, and time zones

Null handling in schema inference and evolution follows the same rules as other streaming sources. Nulls in the source files are preserved unless you filter or replace them. If a target column is non-nullable, a null value causes the write to fail. You should handle nulls in the transformation step. For example, you can filter out rows with null keys or replace null values with a default using `coalesce`. The rescued data column captures values that do not match the schema, which can include nulls or type mismatches. When schema inference samples files, it may infer a column as nullable even if all sampled values are non-null. The nullability of a column in the inferred schema is not a guarantee about the data.

Case sensitivity affects string comparisons and column names. In Spark SQL, column names are case-insensitive by default. String values are case-sensitive. If the source data has inconsistent casing, normalize it with `upper` or `lower`, or use a case-insensitive collation if the table is configured for one. The schema location stores the column names as inferred. If the source files have columns with different casing, Auto Loader may infer them as separate columns. You can use schema hints to standardize column names and types.

Time zones affect timestamps. Spark stores timestamps internally in UTC and displays them in the session time zone. When Auto Loader parses timestamps from files, it interprets them in the session time zone unless the file includes an explicit offset. To avoid off-by-hours errors, set the session time zone explicitly to UTC at the start of your job with `spark.conf.set("spark.sql.session.timeZone", "UTC")`. Store timestamps in UTC and convert to local time only for display. Schema inference may infer a timestamp column as a string if the format is ambiguous. Use schema hints to force a timestamp type when you know the format.

## Schema enforcement, evolution, and expectations

Delta Lake enforces the schema of the target table. When Auto Loader writes to a Delta table, Delta Lake compares the DataFrame schema with the table schema. If the DataFrame has extra columns, the write fails unless schema evolution is enabled. If the DataFrame is missing nullable columns, those columns are written as null. If a non-nullable column is missing, the write fails. Auto Loader's schema evolution modes control how the stream schema changes. The target table schema evolves when the stream schema evolves and the write uses `mergeSchema`.

Expectations in Lakeflow Spark Declarative Pipelines validate data quality. You can attach expectations to streaming tables that Auto Loader populates. Expectations can drop, fail, or warn on rows that violate a rule. For example, you can define an expectation that `order_id` is not null. If a row violates the expectation, the pipeline can drop it before it reaches downstream tables. Expectations complement schema enforcement by validating business rules. They do not replace schema evolution; they validate the values that conform to the schema.

The following table summarizes the schema and quality controls.

| Control | Mechanism | Effect |
|---|---|---|
| Schema inference | Auto Loader sampling | Derives column names and types |
| Schema evolution | `cloudFiles.schemaEvolutionMode` | Adds columns, widens types, rescues data, or fails |
| Schema enforcement | Delta Lake write | Rejects writes that do not match the table schema |
| Schema evolution on write | `mergeSchema` option | Adds new columns to the target table |
| Expectations | Lakeflow Spark Declarative Pipelines | Drops, fails, or warns on rows that violate a rule |

The table shows that schema inference and evolution operate at the stream level, while schema enforcement and evolution on write operate at the table level. Expectations validate data quality. Use these controls together to build robust pipelines.

## Best practices

Choose the schema evolution mode that matches your governance requirements. Use `addNewColumns` when you want the schema to evolve automatically. Use `rescue` when you want to handle schema changes manually and prevent data loss. Use `failOnNewColumns` when schema changes require manual approval. Use `none` when the schema is fixed and you want to ignore new columns.

Use schema hints when you know the correct types. Schema hints guide inference and avoid type mismatches. They are especially useful for CSV and JSON files where the default inference treats all columns as strings.

Monitor the rescued data column. If the rescued data grows, it indicates schema drift or data quality problems. Query the rescued data column regularly and decide whether to update the schema or fix the source.

Store the schema location in a durable, governed location. Use a Unity Catalog volume so that the schema location is governed by Unity Catalog. Keep the schema location separate from the checkpoint location so that you can reset the stream without losing the inferred schema.

Use type widening when types grow over time. `addNewColumnsWithTypeWidening` reduces the need for manual schema updates. It requires Databricks Runtime 16.4 or above.

Set the session time zone explicitly to UTC. This avoids off-by-hours errors when parsing timestamps. Use schema hints to force timestamp types when the format is known.

Use expectations to validate data quality. Attach expectations to the streaming table or to downstream tables. Expectations catch invalid rows early.

## Common mistakes and pitfalls

The most common mistake is assuming that JSON and CSV columns are typed by default. They are inferred as strings unless you enable `cloudFiles.inferColumnTypes` or provide schema hints. If you do not cast the columns, downstream calculations may produce incorrect results.

A second mistake is using the wrong schema evolution mode. `addNewColumns` fails the stream when a new column appears. If you do not restart the stream, it remains failed. Use `rescue` if you want the stream to continue without failing.

A third mistake is ignoring the rescued data column. The rescued data column captures nonconforming data. If you do not monitor it, you may miss data quality issues. Query the rescued data column regularly.

A fourth mistake is sharing a schema location between streams. Each stream must have its own schema location. Sharing causes conflicts and incorrect schema evolution.

A fifth mistake is not setting the session time zone. Timestamps are stored in UTC. If you compare them to local time without converting, you may get incorrect results.

A sixth mistake is using `none` mode and expecting new columns to appear. `none` mode ignores new columns. If you want new columns to be added, use `addNewColumns`.

A seventh mistake is using type widening on a runtime that does not support it. `addNewColumnsWithTypeWidening` requires Databricks Runtime 16.4 or above. Check the runtime version before using it.

## Testing schema inference and evolution

Testing schema inference and evolution involves verifying that the stream infers the expected schema, handles new columns correctly, and rescues nonconforming data. You can test with a small directory of files and the `availableNow` trigger. The following example shows a test for schema inference and rescue mode.

```python
from pyspark.sql import Row

# Create a test directory with a small JSON file.
test_data = [Row(order_id=1, amount=100.0)]
df_test = spark.createDataFrame(test_data)
df_test.write.mode("overwrite").json("/tmp/schema_test/")

# Configure Auto Loader with rescue mode.
df_auto = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.schemaEvolutionMode", "rescue")
    .option("cloudFiles.schemaLocation", "/tmp/schema_test_schema")
    .option("rescuedDataColumn", "_rescued_data")
    .load("/tmp/schema_test/"))

# Write the stream with availableNow.
query = (df_auto
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/tmp/schema_test_checkpoint")
    .trigger(availableNow=True)
    .toTable("tmp.schema_test_target"))

# Wait for the query to terminate.
query.awaitTermination()

# Verify that the target table contains the expected row.
assert spark.read.table("tmp.schema_test_target").count() == 1

# Add a new file with a new column.
new_data = [Row(order_id=2, amount=200.0, new_column="value")]
df_new = spark.createDataFrame(new_data)
df_new.write.mode("append").json("/tmp/schema_test/")

# Restart the stream with availableNow.
query2 = (df_auto
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/tmp/schema_test_checkpoint")
    .trigger(availableNow=True)
    .toTable("tmp.schema_test_target"))

# Wait for the query to terminate.
query2.awaitTermination()

# Verify that the new column was rescued.
df_result = spark.read.table("tmp.schema_test_target")
assert df_result.filter(df_result._rescued_data.isNotNull()).count() == 1
```

The test verifies that the initial file is loaded and that a new column in a subsequent file is rescued. Run tests like this in your CI pipeline against a small local Spark session. Clean up temporary files and tables after the test.

## Performance considerations

Schema inference adds a small overhead at the start of the stream because Auto Loader samples files to infer the schema. The overhead is usually small compared to the data processing. Once the schema is inferred and stored, subsequent runs use the stored schema and do not re-infer unless the schema evolves.

Schema evolution can cause the stream to restart. When `addNewColumns` mode detects a new column, it fails the stream and updates the schema. On restart, the stream continues with the updated schema. This restart adds latency. If you need continuous processing without restarts, use `rescue` mode, which does not fail or evolve the schema.

The rescued data column adds a small amount of storage overhead because it stores the rescued values. The overhead is proportional to the amount of nonconforming data. Monitor the rescued data column and address the root cause if it grows.

Type widening requires Databricks Runtime 16.4 or above. It may add a small overhead when a type change is detected. The overhead is usually negligible.

Use file notification mode with file events to reduce the overhead of file discovery. File notification mode is more efficient than directory listing mode, especially for large directories.

## An end-to-end example

Consider a scenario where you ingest JSON order files from cloud storage into a bronze table. The source files occasionally add new columns and change types. You want the stream to continue processing without failing, and you want to capture nonconforming data in a rescued data column. The following example shows the complete configuration.

```python
from pyspark.sql.functions import col

# Configure Auto Loader with rescue mode and type inference.
df_auto = (spark.readStream
    .format("cloudFiles")
    .option("cloudFiles.format", "json")
    .option("cloudFiles.inferColumnTypes", "true")
    .option("cloudFiles.schemaEvolutionMode", "rescue")
    .option("cloudFiles.schemaLocation", "/Volumes/sales/bronze/schemas/orders")
    .option("rescuedDataColumn", "_rescued_data")
    .load("/Volumes/sales/bronze/raw/orders/"))

# Write the raw orders to a bronze table.
(df_auto
    .writeStream
    .format("delta")
    .outputMode("append")
    .option("checkpointLocation", "/Volumes/sales/bronze/checkpoints/orders")
    .option("mergeSchema", "true")
    .trigger(availableNow=True)
    .toTable("sales.bronze.orders"))

# Query the rescued data column to inspect nonconforming data.
df_bronze = spark.read.table("sales.bronze.orders")
df_rescued = df_bronze.filter(col("_rescued_data").isNotNull())
display(df_rescued)
```

The example reads JSON files with type inference and rescue mode. New columns and type mismatches are captured in the `_rescued_data` column. The stream does not fail. The bronze table uses `mergeSchema` to allow the schema to evolve when the stream schema evolves. The rescued data column is queried to inspect nonconforming data. This configuration is resilient to schema changes and prevents data loss.

## Summary

Schema inference is the process of examining source data and determining column names and data types. Schema evolution is the process of updating that schema when the source data changes. Auto Loader provides both capabilities for file-based ingestion. It samples files to infer the schema, stores the inferred schema in a schema location, and uses schema evolution modes to control how new columns and type changes are handled.

For JSON, CSV, and XML files, Auto Loader infers all columns as strings by default. Use `cloudFiles.inferColumnTypes` to enable type inference. Use schema hints to override inferred types for specific columns. The schema location stores the inferred schema and must be durable and governed. Keep the schema location separate from the checkpoint location so that you can reset the stream without losing the inferred schema.

The schema evolution modes are `addNewColumns`, `addNewColumnsWithTypeWidening`, `rescue`, `failOnNewColumns`, and `none`. `addNewColumns` is the default when no schema is provided. It fails the stream when a new column appears and adds the column to the schema. `addNewColumnsWithTypeWidening` also widens supported types and requires Databricks Runtime 16.4 or above. `rescue` never evolves the schema and captures all nonconforming data in the rescued data column. `failOnNewColumns` fails and requires manual intervention. `none` ignores new columns and is the default when a schema is provided.

The rescued data column captures values that do not match the expected schema, including type mismatches and unexpected columns. It prevents data loss and allows you to inspect nonconforming data. You can rename it with the `rescuedDataColumn` option. Monitor the rescued data column to detect schema drift and data quality issues.

Null handling, case sensitivity, and time zones affect the data. Set the session time zone explicitly to UTC. Normalize string casing. Handle nulls deliberately. Delta Lake enforces the table schema. Expectations in Lakeflow Spark Declarative Pipelines validate data quality.

Best practices include choosing the right schema evolution mode, using schema hints, monitoring the rescued data column, storing the schema location in a governed location, using type widening when appropriate, and setting the session time zone. Common mistakes include assuming typed columns for JSON and CSV, using the wrong schema evolution mode, ignoring the rescued data column, sharing a schema location, and not setting the session time zone.

Test schema inference and evolution with small files and the `availableNow` trigger. Performance depends on the inference overhead, schema evolution restarts, and the volume of rescued data. Use file notification mode with file events for efficient file discovery. By understanding schema inference and evolution, you can build resilient Auto Loader pipelines that adapt to changing source data without losing data or failing unexpectedly.
