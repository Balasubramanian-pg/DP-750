## Apply a Requirements-Driven Design Framework

Effective ingestion design is not about choosing the most advanced tool; it is about selecting the simplest pattern that satisfies business constraints. A requirements-driven framework ensures that every technical decision—from extraction logic to file format—is justified by specific operational needs. This approach prevents over-engineering, controls costs, and builds pipelines that remain robust as data volumes grow.

### Step 1: Gather Requirements

Before writing a single line of code, you must define the boundaries of the problem. Answering these questions creates a clear specification for your pipeline.

| Requirement Category | Key Questions |
| :--- | :--- |
| **Data Volume** | What is the total size of the source? How many rows change per run? What is the projected annual growth rate? |
| **Latency** | How fresh must the data be? Is "end-of-day" sufficient, or do you need sub-minute freshness? Are there strict SLAs? |
| **Source Capabilities** | Does the source support Change Data Capture (CDC)? Can it produce Parquet, or only CSV? Is there a reliable timestamp or sequence ID? |
| **Data Quality** | Is the source data validated? Do you need to handle schema drift or missing fields? |
| **Network & Security** | What is the available bandwidth? Are there firewalls, VPNs, or private link requirements? |
| **Cost Constraints** | What is the budget for compute and storage? Is the goal to minimize DBUs, storage costs, or data transfer fees? |

### Step 2: Map Requirements to Extraction Type

Use your gathered requirements to select the most appropriate extraction pattern. The goal is to balance efficiency with complexity.

| If your requirements indicate... | Then choose... | Rationale |
| :--- | :--- | :--- |
| Small volume (<100K rows), no change tracking, simple rebuild acceptable | **Full Extraction** | Lowest implementation effort; negligible cost for small datasets. |
| Large volume, reliable change indicator (timestamp/ID), hourly/daily freshness | **Incremental Extraction** | Processes only deltas; scales efficiently with data growth. |
| Real-time/near real-time freshness, event-based source, always-on infrastructure | **Streaming Extraction** | Lowest latency; reacts to events as they occur. |
| Need to capture deletes/updates, audit trail required, transaction log access | **CDC Extraction** | Highest fidelity; mirrors source system state exactly. |

### Step 3: Select Source File Format

When you have control over the landing zone format, choose the one that best aligns with your downstream usage patterns.

| If your scenario involves... | Then prefer... | Rationale |
| :--- | :--- | :--- |
| Large analytical datasets, columnar queries, compression needs | **Parquet** | High compression, column pruning, embedded schema. |
| Interoperability, human readability, simple structures | **CSV or JSON** | Universal support, easy to debug, but less efficient. |
| Hierarchical or nested data structures | **JSON or XML** | Preserves complex relationships without flattening. |
| High-frequency streaming with schema evolution | **Avro** | Compact binary format, excellent schema evolution support. |

### Step 4: Validate Your Design

Before implementation, stress-test your design against potential failure points.

*   **Latency Check:** Does the chosen extraction type meet the freshness SLA? If not, downstream reports will be stale.
*   **Scalability Check:** Will this approach still work if data volume doubles next year? If not, you are building a technical debt bomb.
*   **Capability Check:** Does the source system actually support the features you are relying on (e.g., CDC, timestamps)? If not, the pipeline will fail at runtime.
*   **Cost Check:** Are the estimated compute and storage costs within budget? If not, the solution is financially unsustainable.
*   **Quality Check:** Have you planned for data validation? If not, bad data will propagate silently through your lakehouse.

### Practical Example: E-Commerce Order Ingestion

**Scenario:** An e-commerce platform needs to ingest order data from a PostgreSQL database for hourly reporting.

1.  **Gather Requirements:**
    *   **Volume:** 50,000 new orders/day; 2 million total rows.
    *   **Latency:** 1-hour freshness is acceptable.
    *   **Source:** PostgreSQL has an `order_updated_at` timestamp but no native CDC.
    *   **Cost:** Minimize compute usage.

2.  **Map to Extraction Type:**
    *   **Decision:** **Incremental Extraction**.
    *   **Why?** Full extraction of 2 million rows hourly is wasteful. Streaming is overkill for 1-hour latency. CDC is unavailable. Incremental extraction using the timestamp is the most efficient fit.

3.  **Select File Format:**
    *   **Decision:** **Parquet**.
    *   **Why?** The data is structured and tabular. Parquet offers superior compression and query performance for analytics compared to CSV or JSON.

4.  **Validate Design:**
    *   ✅ Meets 1-hour latency.
    *   ✅ Scales well (processes ~2,000 changes/hour instead of 2 million).
    *   ✅ Uses existing `order_updated_at` column.
    *   ✅ Reduces compute costs significantly.

> [!TIP]
> **Document Your Decisions**
> Create a **Design Decision Record (DDR)** for each major pipeline. Document *why* you chose incremental over streaming, or Parquet over CSV. When requirements change or issues arise, this documentation provides the context needed to troubleshoot or refactor effectively.

By applying this framework, you move from ad-hoc scripting to engineered data solutions. Each pipeline becomes a deliberate response to business needs, ensuring that your lakehouse remains performant, cost-effective, and reliable.
