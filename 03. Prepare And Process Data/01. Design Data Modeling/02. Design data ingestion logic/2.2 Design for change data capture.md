## Design for Change Data Capture

Change Data Capture (CDC) is the gold standard for data ingestion when fidelity and efficiency are paramount. Unlike simple incremental extraction, which typically only captures new rows or updated timestamps, CDC captures the **intent** of every change: inserts, updates, and critically, deletes. This allows your lakehouse to become a true mirror of your operational systems, maintaining exact parity with source databases without the overhead of full extractions.

### How CDC Works

In a CDC pipeline, the source system exposes a stream of changes rather than just static snapshots. Each change record includes:
1.  **The Data:** The values of the row before and/or after the change.
2.  **The Operation Type:** A flag indicating whether the row was inserted (`I`), updated (`U`), or deleted (`D`).
3.  **Metadata:** Sequence numbers or timestamps to ensure events are processed in the correct order.

This granularity enables use cases that are difficult or impossible with standard incremental loads, such as:
*   **Accurate Delete Replication:** When a customer requests data deletion for compliance (GDPR/CCPA), CDC ensures that record is removed from your lakehouse, not just marked as inactive.
*   **Audit Trails:** You can maintain a history of every modification made to a record, providing a complete lineage of how data evolved over time.
*   **Key Updates:** If a primary key changes in the source, CDC allows you to track that transition accurately, whereas timestamp-based extraction might treat it as a delete and a separate insert.

### Sources of Change Data

When designing for CDC, your approach depends on how the source system exposes these changes:

| Source Type | Mechanism | Description |
| :--- | :--- | :--- |
| **Relational Databases** | Transaction Logs | Systems like SQL Server, PostgreSQL, or Oracle expose changes via their transaction logs (e.g., SQL Server CDC, Debezium). This is the most efficient method as it has minimal impact on source performance. |
| **Delta Lake Tables** | Change Data Feed (CDF) | Delta tables can be configured to emit a change feed. Downstream pipelines can read this feed directly using `table_changes()`, enabling efficient multi-hop architectures. |
| **NoSQL/Cloud DBs** | Built-in Feeds | Services like Azure Cosmos DB provide native change feeds that push updates to downstream consumers as they happen. |
| **Legacy Systems** | Snapshot Comparison | For systems without CDC support, you must compare periodic snapshots to infer changes. This is less efficient and may miss intermediate states between snapshots. |

> [!IMPORTANT]
> **Sequencing is Critical**
> CDC events must be processed in the exact order they occurred in the source system. Your source data must include a reliable sequencing column—such as a monotonically increasing sequence number or a high-precision timestamp. Without this, out-of-order events can lead to data corruption, where an older update overwrites a newer one. In Azure Databricks, streaming tables and Delta Live Tables handle this sequencing automatically when properly configured, ensuring exactly-once semantics even in the face of network delays or retries.

### Implementing CDC in Databricks

Azure Databricks simplifies CDC implementation through **Auto Loader** for file-based sources and **Delta Live Tables (DLT)** for database replication. By leveraging these tools, you can build resilient pipelines that automatically handle schema evolution, late-arriving data, and complex merge logic, ensuring your lakehouse remains a trusted, up-to-date reflection of your business operations.
