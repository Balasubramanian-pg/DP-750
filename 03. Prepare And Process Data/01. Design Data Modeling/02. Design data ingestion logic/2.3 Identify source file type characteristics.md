## Identify Source File Type Characteristics

When data arrives as files rather than through direct database connections, the file format dictates the architecture of your ingestion pipeline. The choice between text-based, columnar, and semi-structured formats influences processing speed, storage costs, and the complexity of schema management. Understanding these characteristics allows you to design pipelines that are both robust and efficient.

### Text-Based Formats: CSV and JSON

CSV and JSON are ubiquitous due to their human readability and broad support across legacy systems. However, their simplicity comes at a cost for large-scale analytical processing.

*   **Schema Variability:** Text files lack embedded schema definitions. A CSV might have inconsistent column orders, missing headers, or varying data types across files. This requires your ingestion logic to include robust schema inference or strict schema enforcement to prevent data corruption.
*   **Parse Overhead:** Every value in a text file must be parsed from a string into its native type (e.g., converting `"123.45"` to a `DOUBLE`). This CPU-intensive process slows down ingestion and query performance compared to binary formats.
*   **Storage Inefficiency:** Text formats do not compress as effectively as binary alternatives because they store data as characters rather than optimized binary representations.

> [!NOTE]
> **When to Use Text Formats**
> Stick to CSV or JSON when source systems are legacy applications that cannot produce other formats, or when data volumes are small enough that parsing overhead is negligible. For high-volume ingestion, consider converting these files to Parquet immediately upon landing in the lakehouse.

### Columnar Formats: Parquet and ORC

Columnar formats like Parquet and ORC are designed for analytical workloads. They store data by column rather than by row, offering significant advantages for read-heavy operations.

*   **Compression Efficiency:** By grouping similar values together, columnar formats achieve much higher compression ratios. This reduces storage costs and network I/O during data transfer.
*   **Column Pruning:** Analytical queries often select only a subset of columns. Columnar formats allow the engine to read only the necessary columns from disk, skipping irrelevant data entirely. This can reduce I/O by orders of magnitude.
*   **Embedded Schema:** These formats include metadata describing column names, types, and structure. This eliminates the need for schema inference and ensures consistency across files.

> [!TIP]
> **Design for Columnar Sources**
> If you have control over how upstream systems export data, mandate Parquet or ORC. This shifts the computational cost of formatting from your ingestion pipeline to the source system, resulting in faster, cheaper, and more reliable loads into Azure Databricks.

### Semi-Structured Formats: Nested JSON and XML

Semi-structured data represents hierarchical relationships that do not fit neatly into flat tables. Ingesting this data requires special consideration for schema evolution and structure.

*   **Schema Extraction:** Unlike Parquet, JSON and XML may not have a rigid schema. You must decide whether to infer the schema dynamically (which can be slow and error-prone) or define it explicitly using DDL.
*   **Flattening vs. Nesting:** You must choose between preserving the nested structure (using `STRUCT` or `ARRAY` types in Delta Lake) or flattening the data into a wide table. Preserving nesting maintains fidelity but can complicate SQL queries; flattening simplifies analysis but may lead to data duplication.
*   **Structural Variance:** Documents within the same source may have different fields. Your ingestion logic must handle missing fields gracefully, typically by filling them with `NULL` values.

| Format | Best For | Key Challenge | Optimization Strategy |
| :--- | :--- | :--- | :--- |
| **CSV** | Legacy exports, small datasets | Schema inconsistency, parse overhead | Enforce schema on read; convert to Parquet early. |
| **JSON** | API responses, nested data | Structural variance, parsing cost | Use Auto Loader with schema hints; preserve nesting if possible. |
| **Parquet** | Analytical workloads, large volumes | Write complexity at source | Mandate as standard for all new high-volume pipelines. |
| **XML** | Enterprise legacy systems | Complex parsing, verbosity | Convert to JSON or Parquet during initial ingestion. |

By aligning your ingestion design with the inherent characteristics of your source file types, you minimize friction and maximize the performance of your downstream analytics.
