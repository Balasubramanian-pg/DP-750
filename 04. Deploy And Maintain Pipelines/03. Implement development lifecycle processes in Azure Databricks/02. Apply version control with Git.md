# Apply version control with Git



## Apply Git version control best practices

Data engineering projects require systematic tracking of code changes, collaboration across teams, and the ability to **reproduce work reliably**. When you apply version control best practices using Git within Azure Databricks, you establish a foundation for professional development workflows. **Git folders** integrate directly into your workspace, providing a visual interface for managing repositories without leaving your development environment.

# Git Folders in Azure Databricks

Git folders embed version control directly into the workspace. This integration removes the friction of external tools, allowing standard Git operations—cloning, branching, committing, pushing—to occur within the development environment.

> **Info:** Git folders connect to remote repositories hosted on Azure DevOps, GitHub, GitLab, or Bitbucket. The folder mirrors the repository structure, supporting notebooks, Python files, SQL scripts, and other assets.

## Core Capabilities

*   **Visual Client:** Perform Git operations via the workspace UI.
*   **API Access:** Automate Git workflows programmatically.
*   **Asset Support:** Version control for notebooks, `.py`, `.sql`, and configuration files.
*   **Collaboration:** Multiple team members map individual Git folders to the same remote repository.

## Collaboration Model

Each developer maintains a personal Git folder linked to the shared remote. This isolation is critical for team stability.

> **Tip:** Each team member should work in their own Git folder connected to the shared repository. This practice prevents accidental branch switches or conflicts that can occur when multiple users perform Git operations on the same workspace folder.

### Why Isolation Matters

*   **Branch Safety:** Prevents one user’s checkout from disrupting another’s work.
*   **Conflict Reduction:** Eliminates race conditions during commit and push operations.
*   **Personal Context:** Allows developers to maintain local uncommitted changes without affecting teammates.

> **Note:** While Git folders provide the interface, the underlying repository remains the single source of truth. Changes are only shared when pushed to the remote, ensuring that local experimentation does not impact the team until explicitly integrated.

## Workflow Integration

1.  **Clone:** Connect your Git folder to the remote repository.
2.  **Branch:** Create a feature branch for isolated development.
3.  **Commit:** Save changes locally with descriptive messages.
4.  **Push:** Upload commits to the remote repository.
5.  **Pull Request:** Initiate code review and merge into the main branch.

This sequence transforms the workspace from a collection of static files into a dynamic, version-controlled development surface.

# Cloning a Repository

Cloning establishes the link between your workspace and the remote codebase. It creates a local mirror, granting immediate access to the latest versioned assets.

## Steps to Clone

1.  **Navigate:** In the sidebar, select **Workspace** and choose the target directory.
2.  **Initiate:** Select **Create** > **Git folder**.
3.  **Configure:**
    *   Enter the repository URL (e.g., `https://example.com/organization/project.git`).
    *   Select the Git provider from the dropdown.
    *   Assign a name for the local folder.
4.  **Execute:** Select **Create Git folder**.

> **Info:** The cloning process pulls the repository structure into your workspace. Notebooks, Python files, and SQL scripts become immediately editable.

[![Screenshot of the Create Git folder dialog.](media/2-create-git-folder.png)](media/2-create-git-folder.png#lightbox "media/2-create-git-folder.png#lightbox")

## Post-Clone State

*   **Visibility:** Repository contents appear in the workspace navigation.
*   **Readiness:** Files are unlocked for editing.
*   **Sync Status:** The local folder reflects the remote’s default branch at the time of cloning.

>[!Note]
> **Note:** Cloning is a one-time setup per user. Subsequent updates are handled through pull and push operations, not re-cloning.

## Pull changes from the remote repository

When collaborating with a team, others push changes to the shared repository that you need to incorporate into your local work. **Pulling updates** ensures you're working with the **latest version** of the codebase.

To pull changes:

1. Open the Git dialog.
2. Select **Pull** to fetch and merge changes from the remote repository.
3. If conflicts exist between remote changes and your local modifications, resolve them using the **conflict resolution interface**.

[![Screenshot of the git dialog in Azure Databricks.](media/2-commit-push.png)](media/2-commit-push.png#lightbox "media/2-commit-push.png#lightbox")

**Pull regularly**, especially before starting new work, to minimize integration issues. When you pull changes that modify notebook source code, the **notebook state resets**. This means cell outputs, comments, and version history for that notebook clear to reflect the updated content.

## Keep your repository organized

A well-organized repository makes collaboration easier and reduces confusion. Apply these practices to maintain a clean, navigable codebase:

* **Use `.gitignore` files** to exclude files that shouldn't be tracked, such as temporary outputs, credentials, or environment-specific configurations. Files already tracked by Git require explicit removal before `.gitignore` applies to them.
* **Structure folders logically** by grouping related notebooks, libraries, and configuration files. Git folders support creating structures at any depth under your user directory.
* **Remove stale branches** from your Git provider after merging to keep the branch list manageable. Local branches persist for up to 30 days after the remote branch is deleted.

Note

Git folders have size constraints. Working branches are limited to 1 GB, and Databricks recommends keeping the total number of assets below 20,000. For large repositories, consider using **sparse checkout** to work with only the directories you need.

When everyone follows consistent organization practices, team members can find what they need quickly and understand how the codebase fits together.
