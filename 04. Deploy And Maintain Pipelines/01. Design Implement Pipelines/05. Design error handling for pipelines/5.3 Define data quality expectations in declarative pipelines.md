# Lakeflow Declarative Pipelines: Data Quality Expectations

## The Expectation Model

-   **Constraints validate records inline during data flow**
    Expectations operate at the row level as data moves through pipeline stages, eliminating the need for separate validation jobs or post-hoc quality checks. This integration ensures that quality rules execute with the same performance characteristics as transformation logic, avoiding the latency and cost of double-processing datasets solely for verification purposes.

-   **Three distinct actions govern failure responses**
    The platform provides granular control over how invalid records impact pipeline execution. Choosing the correct action requires understanding the business criticality of each constraint and the tolerance for data imperfection in downstream consumers.

## Action Behaviors and Use Cases

-   **Warn: Log metrics while preserving all records**
    Invalid records write to the target table alongside valid ones, but violation counts appear in pipeline metrics and monitoring dashboards. This approach suits exploratory phases where you are establishing baseline quality levels or scenarios where downstream systems have their own filtering logic. It enables trend analysis without disrupting operational continuity, allowing teams to identify deteriorating source quality before it becomes critical.

-   **Drop: Exclude invalid records from targets**
    Records failing the constraint vanish from the output dataset, ensuring only compliant data reaches downstream consumers. This action prevents corruption of analytical models or reporting layers by silently removing problematic rows. Use drop when partial completeness is preferable to inaccurate data, such as filtering out transactions with missing customer IDs where the remaining dataset remains statistically valid for aggregation.

-   **Fail: Halt the specific flow immediately**
    Pipeline execution stops for the affected flow when violations occur, preventing any further processing of potentially compromised data. This strict enforcement applies to constraints where violation indicates fundamental system breakdowns—such as primary key uniqueness violations or negative values in financial amounts. Fail actions protect data integrity at the cost of availability, requiring manual intervention or automated remediation before processing resumes.

## Isolation and Parallelism

-   **Flow-level isolation prevents cascading failures**
    When a fail expectation triggers, only the specific data flow containing the violation stops. Other parallel flows within the same pipeline continue processing unaffected datasets. This architectural choice recognizes that modern data platforms ingest diverse sources with independent quality profiles; a schema change in one vendor’s feed should not halt ingestion from thirty other healthy sources.

-   **Parallel flow continuation maintains platform availability**
    By isolating failures to individual flows, the pipeline preserves throughput for healthy data streams while quarantining problematic ones. This behavior reduces the blast radius of data quality issues and ensures that business-critical datasets remain fresh even when peripheral sources experience temporary degradation. Operators can address failed flows individually without coordinating complex restart procedures for the entire pipeline.

## Implementation Strategy

-   **Layer expectations based on constraint criticality**
    Apply warn actions to emerging quality concerns where you need visibility but not interruption. Upgrade to drop actions for established rules where invalid data provides no analytical value. Reserve fail actions for non-negotiable business rules where violation indicates data so fundamentally flawed that proceeding would create liability or operational risk.

-   **Monitor expectation metrics for proactive quality management**
    Even when using drop or fail actions, track violation rates over time to identify source system degradation. Rising warning counts often precede hard failures, providing early indicators that source teams need to address upstream data generation issues. Integrating these metrics into operational dashboards transforms data quality from a reactive debugging exercise into a proactive monitoring discipline.
