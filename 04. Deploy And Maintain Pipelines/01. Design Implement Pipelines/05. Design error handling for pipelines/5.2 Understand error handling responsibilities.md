# Lakeflow Jobs: Error Handling Responsibilities

## The Shared Responsibility Model

-   **Platform manages infrastructure-level resilience automatically**
    Azure Databricks handles cluster node failures, network interruptions within the control plane, and resource provisioning issues without requiring engineer intervention. This abstraction means you do not need to write code to restart failed executors or manage heartbeat timeouts for standard Spark operations. The platform’s automatic recovery mechanisms ensure that transient hardware or virtualization glitches do not translate into pipeline failures, allowing you to focus on logic rather than infrastructure stability.

-   **Engineers own data-level and application logic integrity**
    Your responsibility begins where the platform’s generic safeguards end: validating that incoming data matches expected schemas, handling business rule violations, and managing interactions with external systems. If a source system sends a string where an integer is expected, or if a transformation divides by zero due to unexpected nulls, the platform cannot determine the correct business response. These scenarios require explicit error handling strategies defined within your notebooks, SQL queries, or pipeline configurations.

## Failure Scenario Classification

-   **Source data anomalies require validation and routing logic**
    Invalid formats, missing required fields, or schema drift represent data quality issues that must be caught before they corrupt downstream tables. The appropriate response often involves isolating bad records into dead letter queues while allowing valid data to proceed, rather than halting the entire pipeline. This distinction preserves throughput for the majority of correct records while creating an audit trail for remediation.

-   **Transformation logic errors demand defensive coding practices**
    Unexpected values during calculations—such as nulls in aggregation keys or out-of-range dates—indicate gaps in assumption testing. These failures should trigger detailed logging that captures the specific record context causing the issue, enabling rapid debugging. Depending on business criticality, you might choose to fail fast to prevent partial updates or implement default value substitutions to maintain continuity.

-   **External service timeouts necessitate retry and fallback strategies**
    Connections to third-party APIs, legacy databases, or cloud storage services introduce dependencies outside your control. Transient network issues warrant automatic retries with exponential backoff, while persistent failures might require switching to backup data sources or alerting operators for manual intervention. Treating all external calls as potentially unreliable prevents single points of failure from cascading through your entire workflow.

-   **Compute resource unavailability remains a platform concern**
    When clusters fail to start or scale due to quota limits or regional capacity issues, the platform manages the retry logic and notification processes. However, you should design pipelines to be idempotent so that when resources become available and jobs rerun, they do not create duplicate records or inconsistent states. This preparation ensures that infrastructure recovery does not introduce data integrity problems.

## Response Strategy Determination

-   **Immediate termination suits critical data integrity violations**
    When an error indicates fundamental misunderstandings of the data model—such as primary key collisions or mandatory field absence across entire batches—continuing processing risks generating misleading analytics. Failing fast in these scenarios protects downstream consumers from acting on corrupted information and forces immediate attention to root causes at the source system level.

-   **Continue-with-logging applies to isolated record-level issues**
    For large-scale ingestion pipelines where individual malformed records are statistically inevitable, stopping the entire job creates unnecessary operational burden. Logging the specific failures with sufficient context allows batch completion while providing engineers with the data needed to fix source systems or update validation rules. This approach balances operational efficiency with data quality monitoring.

-   **Hybrid approaches combine isolation with alerting thresholds**
    Some pipelines benefit from continuing processing while monitoring error rates against predefined thresholds. If invalid records exceed five percent of total volume, the pipeline might switch from logging mode to failure mode, triggering alerts and halting further processing. This dynamic response adapts to normal noise levels while catching significant degradation events that indicate systemic problems.
