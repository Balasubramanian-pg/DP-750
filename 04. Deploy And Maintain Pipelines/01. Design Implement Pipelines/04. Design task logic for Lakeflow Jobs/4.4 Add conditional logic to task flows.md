# Lakeflow Jobs: Conditional Execution Patterns

## If/Else Branching (Data-Driven Decisions)

-   **Evaluates expressions against task values, job parameters, or dynamic references**
    The condition engine parses Jinja-style templates at runtime to resolve actual values from upstream task outputs or global job configurations. This allows the branching logic to remain static in definition while responding dynamically to changing data states without requiring code changes between runs.

-   **Use when processing paths depend on data content or quality metrics**
    This mechanism exists specifically for business logic where the shape of the pipeline must adapt to what the data actually contains. It separates orchestration structure from data validation, ensuring that routing decisions are traceable to specific dataset characteristics rather than opaque script behavior buried inside transformation tasks.

-   **Example threshold logic: `{{tasks.quality_check.values.invalid_count}} > 100`**
    This syntax demonstrates direct access to named task outputs within conditional expressions. The double-brace notation signals template resolution, while the comparison operator defines the boolean gate; understanding this pattern is essential because malformed references fail silently or throw runtime errors depending on platform configuration.

-   **Routes execution to true/false branches based on expression result**
    Each branch represents a distinct subgraph of tasks that only activates when its corresponding condition evaluates correctly. Tasks outside the active branch do not consume compute resources or appear as skipped in most monitoring views, which keeps execution graphs clean and cost-efficient when dealing with mutually exclusive processing paths.

-   **Typical use cases: remediation workflows, data quality gates, volume-based routing**
    These scenarios share a common trait where downstream processing validity depends entirely on upstream data characteristics. Remediation triggers when corruption exceeds tolerance, quality gates halt pipelines before bad data propagates, and volume routing selects batch versus streaming processors based on record counts observed during ingestion.

## Run If Conditions (State-Driven Execution)

-   **Evaluates upstream task outcomes automatically without explicit expressions**
    The scheduler inspects task completion metadata directly rather than parsing user-defined conditions. This removes an entire class of potential bugs related to null handling, type coercion, or missing value references that plague expression-based branching when applied to operational concerns like failure detection.

-   **Use for operational control flow rather than data validation**
    State-driven conditions address workflow reliability questions independent of payload content. Whether a notification should fire depends on whether the ETL succeeded, not on how many rows were processed; conflating these concerns creates fragile pipelines where operational side effects accidentally couple to business data schemas.

-   **Handles success/failure/completion states of dependent tasks**
    Three primary states drive evaluation: successful completion, terminal failure, and any-completion regardless of outcome. This trinary model covers most operational patterns including retry logic, alerting, and resource cleanup without requiring users to construct complex boolean expressions that replicate built-in scheduler semantics.

-   **Typical use cases: error notifications, cleanup operations, fallback data sources**
    Notifications trigger on failure states to alert operators; cleanup tasks run on any-completion to release temporary resources even when preceding transformations crash; fallback sources activate when primary ingestion fails but alternative datasets remain available. Each pattern relies purely on execution metadata rather than inspecting returned values.

-   **No Jinja templating required—system manages state evaluation**
    Configuration happens through dropdown selections or simple boolean flags in the visual designer rather than text-based expressions. This reduces cognitive load during pipeline authoring and eliminates template syntax errors that can be difficult to debug when conditions evaluate unexpectedly due to whitespace issues or escaped characters.

## Implementation Guidance

-   **If/else for business logic decisions based on data values**
    Reserve expression-based branching exclusively for scenarios where the correct processing path cannot be determined without inspecting payload content. This maintains clear separation between what the data requires and how the infrastructure responds, making pipelines easier to reason about during incident response or compliance audits.

-   **Run if for workflow orchestration and error handling**
    Operational concerns should never require parsing task output values to determine appropriate responses. Using state-driven conditions for notifications, retries, and cleanup ensures these behaviors remain stable across schema evolution and prevents accidental coupling between infrastructure resilience patterns and business data contracts.

-   **Visual designer distinguishes these as separate dependency types**
    The UI enforces conceptual separation by exposing different configuration interfaces for each mechanism. This design choice reflects fundamental architectural differences in evaluation timing and data access patterns; attempting to work around this distinction typically indicates a misunderstanding of which conditional primitive suits the problem at hand.

-   **Avoid mixing data-driven and state-driven conditions in the same decision point**
    Combining both mechanisms within a single branching node creates evaluation order ambiguities and debugging complexity. When a decision requires both data inspection and state awareness, decompose it into sequential steps where state evaluation happens first to short-circuit unnecessary data processing, or restructure so each concern owns its own dedicated conditional gate.
