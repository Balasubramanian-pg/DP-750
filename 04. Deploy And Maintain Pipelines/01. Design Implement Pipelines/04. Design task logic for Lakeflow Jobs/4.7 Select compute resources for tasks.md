# Lakeflow Jobs: Compute Resource Selection

## Compute Type Mapping

-   **Notebooks and Python scripts leverage Serverless jobs compute**
    This option removes cluster provisioning delays and eliminates the need to manage instance types or Spark configurations manually. The platform handles scaling based on workload demands, making it ideal for standard ETL transformations where custom environment setup adds little value beyond increased maintenance burden.

-   **SQL queries and files execute on Serverless SQL warehouses**
    SQL workloads benefit from warehouse-optimized execution engines that handle query planning, caching, and concurrency differently than general-purpose Spark clusters. Using dedicated SQL compute ensures compatibility with BI tools and leverages optimizations specific to analytical query patterns rather than forcing SQL through a general Spark interpreter.

-   **Lakeflow Spark Declarative Pipelines use Serverless pipeline compute**
    Declarative pipelines operate under a different execution model than imperative notebooks, requiring compute environments tuned for metadata-driven orchestration rather than code-based transformation logic. Serverless pipeline compute abstracts away the underlying Spark configuration while maintaining the performance characteristics needed for large-scale data movement operations.

-   **JAR files and Spark Submit tasks require Classic jobs compute**
    Legacy applications or specialized Java/Scala workloads often depend on specific Spark versions, custom JVM arguments, or pre-installed libraries that serverless environments cannot accommodate. Classic compute provides the granular control necessary for these scenarios, allowing explicit specification of instance types, driver memory settings, and dependency management strategies.

## Multi-Compute Job Patterns

-   **Tasks within a single job can utilize different compute resources**
    A typical production pipeline might route SQL aggregation steps to a SQL warehouse for optimized query performance while running complex Python-based machine learning preprocessing on Serverless jobs compute. This hybrid approach matches each task to its most efficient execution environment rather than forcing all work through a single compute type that may be suboptimal for certain operations.

-   **Mixed compute strategies reduce total cost of ownership**
    By assigning SQL tasks to warehouses and notebook tasks to jobs compute, you avoid paying for oversized clusters that must accommodate both workload types simultaneously. Each compute resource scales independently based on its specific task requirements, preventing resource waste from over-provisioning for peak demands of one task type when others remain idle.

## Shared vs. Dedicated Cluster Tradeoffs

-   **Shared clusters reduce startup latency but incur idle costs**
    When multiple tasks reference the same cluster configuration, the platform keeps the cluster alive between task executions to avoid repeated initialization overhead. This benefits pipelines with many short-running tasks that would otherwise spend disproportionate time starting and stopping clusters. However, the cluster continues consuming resources during gaps between tasks, creating cost inefficiencies if those gaps extend beyond brief intervals.

-   **Dedicated clusters provide isolation at the expense of startup time**
    Assigning unique cluster configurations to individual tasks ensures complete resource separation, preventing one task's memory leaks or CPU spikes from impacting others. This isolation simplifies debugging and performance tuning since each task operates in a predictable environment. The tradeoff involves accepting cluster startup delays for each task, which may become significant if tasks execute frequently with small data volumes.

## Serverless vs. Classic Compute Decision Framework

-   **Serverless compute eliminates operational overhead for production workflows**
    Automatic scaling, patch management, and capacity planning happen transparently, allowing teams to focus on pipeline logic rather than infrastructure maintenance. Serverless options suit most production scenarios where standard Spark configurations meet performance requirements and custom library dependencies remain minimal or manageable through supported installation mechanisms.

-   **Classic compute serves specialized requirements needing explicit control**
    Scenarios demanding specific Spark versions for compatibility, custom instance types for memory-intensive operations, or particular network configurations for security compliance require Classic compute. These situations typically arise in legacy migration projects, highly regulated environments with strict infrastructure controls, or workloads with unusual resource profiles that serverless defaults cannot accommodate efficiently.

## Implementation Strategy

-   **Start with serverless defaults and migrate to Classic only when necessary**
    Begin pipeline development using serverless compute for all task types to establish baseline functionality without infrastructure complexity. Profile actual resource consumption during testing to identify tasks that exceed serverless limits or require specific configurations, then selectively migrate only those tasks to Classic compute. This incremental approach prevents premature optimization while ensuring critical paths receive appropriate resources.

-   **Monitor compute utilization to refine resource allocation**
    Track cluster uptime, task execution duration, and resource consumption metrics to identify opportunities for consolidation or separation. Tasks that consistently execute quickly may benefit from shared clusters to amortize startup costs, while long-running tasks with variable resource demands might justify dedicated serverless instances that scale independently. Regular review of these metrics ensures compute strategy evolves alongside actual workload characteristics rather than remaining static based on initial assumptions.
