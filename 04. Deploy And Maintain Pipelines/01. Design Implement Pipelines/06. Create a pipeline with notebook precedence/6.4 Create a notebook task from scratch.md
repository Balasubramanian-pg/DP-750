# Lakeflow Jobs: Creating Notebook Tasks from Scratch

## Initial Job Configuration

-   **Descriptive task naming establishes operational clarity**
    Names like `ingest_sales_data` or `validate_customer_records` immediately communicate purpose within the DAG visualization and execution logs. Generic labels such as "Task 1" obscure pipeline intent, complicating troubleshooting when failures occur during off-hours or when team members unfamiliar with the original design investigate incidents. Consistent naming conventions support automated monitoring rules that alert on specific functional areas rather than opaque task identifiers.

-   **Notebook type selection defines execution context**
    Choosing "Notebook" from the type dropdown signals to the platform that the task requires a Spark-enabled environment capable of interpreting cell-based code structures. This selection determines which configuration options appear in subsequent steps, such as parameter passing mechanisms and widget handling. Selecting incorrect types like "JAR" or "Python Script" would require fundamentally different setup procedures and compute configurations.

## Source and Path Management

-   **Workspace source binding links tasks to editable artifacts**
    Selecting "Workspace" as the source directs the job to execute notebooks stored in the Databricks workspace file system. This approach suits rapid development cycles where engineers iterate directly in the browser interface. However, workspace-bound notebooks lack the version control rigor of Git-integrated repositories, making them vulnerable to untracked changes that can introduce inconsistencies between development and production executions.

-   **Path browsing ensures accurate artifact reference**
    Navigating the directory structure to select the correct notebook prevents execution errors caused by typos or outdated file references. The path resolution happens at job creation time, locking the task to a specific notebook location. If notebooks move or rename after job creation, the task fails unless paths update accordingly. This brittleness underscores the value of stable directory structures and change management processes for production pipelines.

## Compute Resource Assignment

-   **Task-level compute configuration overrides job defaults**
    Specifying compute resources during task creation allows granular matching of hardware capabilities to workload requirements. Ingestion tasks processing large raw files might need memory-optimized instances, while lightweight validation notebooks run efficiently on minimal serverless configurations. This flexibility prevents over-provisioning expensive clusters for simple tasks or under-provisioning critical transformations that would otherwise timeout or fail due to resource constraints.

-   **Compute selection impacts startup latency and cost efficiency**
    Serverless compute options eliminate cluster provisioning delays but may carry premium pricing compared to classic clusters with reserved capacity. Classic compute provides more control over instance types and Spark versions but incurs startup overhead each time the task runs. Balancing these tradeoffs requires understanding execution frequency, data volume patterns, and budget constraints to optimize total cost of ownership without sacrificing performance.

## Pipeline Expansion Strategy

-   **Sequential task creation leverages automatic dependency inheritance**
    When adding new tasks while an existing node remains selected in the DAG, the platform automatically creates a dependency from the new task to the selected one. This behavior accelerates linear pipeline assembly by reducing manual configuration steps for common ETL patterns where each stage logically follows the previous one. Engineers can rapidly build ingestion-transformation-loading chains without explicitly configuring each dependency link.

-   **Dependency review prevents unintended serialization**
    Automatic dependency inheritance assumes sequential logic, which may not suit all pipeline designs. Parallel branches requiring independent execution must have dependencies manually removed or restructured to avoid unnecessary waiting. Regularly reviewing the DAG after initial creation ensures that automatic behaviors align with intended parallelism opportunities, preventing performance bottlenecks where independent tasks serialize due to default configuration choices.

## Operational Best Practices

-   **Validate notebook existence before job scheduling**
    Confirming that referenced notebooks exist and contain valid code prevents immediate job failures upon first execution. Testing notebooks interactively before embedding them in jobs identifies syntax errors, missing libraries, or permission issues that would otherwise surface only during scheduled runs. This validation step reduces mean time to recovery by catching configuration problems during development rather than production.

-   **Document parameter expectations alongside task creation**
    Notebooks requiring input parameters should have those parameters documented in task descriptions or associated documentation. Future maintainers need to understand what values the notebook expects, their formats, and default behaviors when parameters are omitted. Clear documentation prevents misconfiguration during job cloning or parameter updates that could silently alter processing logic without obvious error indicators.
