# Lakeflow Jobs: Inter-Notebook Parameter Passing

## Configuration Mechanics

-   **Key-value pairs bridge orchestration and execution contexts**
    Defining parameters in the job UI creates a static mapping that resolves before the notebook starts. The "Key" field must exactly match the widget name defined in the notebook code, while the "Value" field accepts static strings, job-level parameter references like `{{job.parameters.date}}`, or dynamic values from upstream tasks. This separation allows operations teams to modify execution inputs without touching source code, supporting rapid adaptation to changing business requirements or remediation scenarios.

-   **Widget definition establishes contract expectations**
    Using `dbutils.widgets.text()` with a default value creates a safety net for missing parameters. If a job configuration omits a required key, the notebook falls back to the specified default rather than throwing an immediate error. This behavior supports flexible reuse where some jobs provide explicit values while others rely on sensible defaults, though critical parameters should omit defaults to force explicit configuration and prevent silent processing of incorrect data ranges.

## Runtime Retrieval and Usage

-   **dbutils.widgets.get() resolves injected values at runtime**
    This method retrieves the actual value passed by the job scheduler, converting it from a string to the appropriate type if necessary. Since all widget values arrive as strings, notebooks must handle type conversion explicitly for dates, integers, or booleans used in filtering logic. Failing to convert types can lead to subtle bugs where string comparisons behave differently than expected numeric or date comparisons, particularly when dealing with leading zeros or format variations.

-   **Parameter injection enables dynamic query construction**
    Embedding retrieved parameters into Spark SQL filters or DataFrame operations allows single notebooks to process arbitrary data subsets. The example showing `filter(f"date = '{process_date}'")` demonstrates how a static script becomes a flexible tool capable of handling daily increments, historical backfills, or ad-hoc date ranges based solely on input configuration. This pattern eliminates code duplication across multiple similar jobs while maintaining clear audit trails of what data each run processed.

## Reusability and Maintenance

-   **Single notebook serves multiple operational scenarios**
    A well-parameterized ingestion notebook can handle production scheduling, development testing, and historical remediation without modification. Changing the `process_date` parameter shifts the temporal focus, while adjusting a `source_path` parameter might switch between staging and production data locations. This versatility reduces the total number of artifacts to maintain and ensures that bug fixes or performance improvements apply uniformly across all use cases.

-   **Parameter documentation prevents configuration drift**
    As notebooks accumulate multiple parameters, tracking their purpose, valid formats, and dependencies becomes critical. Documenting expected values in task descriptions or external wikis helps new team members configure jobs correctly without reverse-engineering notebook logic. Undocumented parameters often lead to misconfigurations where invalid date formats or misspelled paths cause failures that appear unrelated to the root cause, extending troubleshooting time unnecessarily.

## Advanced Integration Patterns

-   **Dynamic references connect upstream outputs to downstream inputs**
    Using Jinja-style templates like `{{tasks.ingest.values.output_path}}` allows parameters to derive from previous task results rather than static configuration. This chaining enables adaptive pipelines where later stages respond to actual data characteristics discovered during earlier processing. For example, a validation task might pass a list of problematic files to a remediation task, creating a feedback loop that adjusts processing based on real-time quality metrics.

-   **Default values balance flexibility with safety**
    Providing sensible defaults for non-critical parameters reduces configuration burden for standard runs while allowing overrides for special cases. However, critical parameters like target table names or environment identifiers should lack defaults to force explicit decision-making. This distinction prevents accidental processing of production data with development configurations or vice versa, enforcing intentional operational choices through configuration requirements.
